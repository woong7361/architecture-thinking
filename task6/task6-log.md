**Assistant**

좋아. 결제/주문 도메인 기준으로 말하면, **멱등성은 “같은 요청이 여러 번 들어와도 결과가 한 번 처리된 것처럼 보장하는 설계”**야.

특히 결제/주문에서는 중요도가 매우 높아. 이유는 단순해:

- 사용자가 결제 버튼을 두 번 누를 수 있음
- 모바일 네트워크가 끊겨서 클라이언트가 재시도할 수 있음
- 서버가 결제 승인 후 응답 전에 죽을 수 있음
- PG사 응답, 웹훅, 내부 이벤트가 중복으로 올 수 있음
- 메시지 큐는 보통 “정확히 한 번”이 아니라 “최소 한 번” 전달을 전제로 봐야 함

이때 멱등성이 없으면 같은 주문에 대해 **중복 결제, 중복 재고 차감, 중복 쿠폰 사용, 중복 포인트 적립** 같은 사고가 난다. 결제 도메인에서는 이게 단순 버그가 아니라 정산, CS, 법적 분쟁으로 이어질 수 있어.

**일반적인 구현 방법 1: Idempotency-Key 저장**

클라이언트가 요청마다 고유한 `Idempotency-Key`를 보내고, 서버가 이 키를 저장해두는 방식이야.

예를 들어:

```http
POST /payments
Idempotency-Key: order-123-payment-attempt-1
```

서버는 처리 전에 이 키가 이미 있는지 확인한다.

- 처음 보는 키면 결제 처리 시작
- 이미 성공한 키면 기존 성공 응답을 그대로 반환
- 이미 처리 중이면 `409 Conflict`나 “처리 중” 응답
- 이미 실패했지만 재시도 가능한 실패인지, 확정 실패인지 정책적으로 판단

중요한 점은 단순히 “키가 있으면 막는다”가 아니야. **요청 파라미터 해시도 같이 저장**해야 해. 같은 키로 금액이나 주문 ID가 다른 요청이 오면 재사용 오류로 막아야 한다.

저장 예시는 이런 형태가 좋아:

```text
idempotency_key
request_hash
status: PROCESSING | SUCCESS | FAILED
response_body
created_at
expires_at
```

이 방식은 외부 API, 특히 `POST /payments`, `POST /orders`, `POST /refunds`에 잘 맞는다.

한계도 있어. 키 저장소가 장애 나면 처리 정책이 복잡해지고, 키 만료 시간을 너무 짧게 잡으면 늦은 재시도를 못 막는다. 결제라면 보통 몇 시간에서 며칠 정도는 보관하는 쪽을 검토한다.

**일반적인 구현 방법 2: DB 유니크 제약으로 비즈니스 중복 방지**

결제는 “같은 주문에 대해 성공 결제는 하나만 가능” 같은 비즈니스 불변식이 있어. 이건 애플리케이션 코드만 믿지 말고 DB 제약으로 막는 게 좋다.

예를 들어 결제 테이블에:

```sql
UNIQUE(order_id, payment_type)
```

또는 “성공 결제는 주문당 하나”를 보장하는 제약을 둔다.

이렇게 하면 동시에 두 요청이 들어와도 DB가 마지막 방어선을 해준다. 애플리케이션에서 먼저 조회하고 없으면 insert 하는 방식만 쓰면 race condition이 생길 수 있어. 그래서 `unique constraint` + 트랜잭션 + 충돌 시 기존 레코드 조회 패턴이 현실적이다.

예:

```text
1. payment_attempt insert 시도
2. unique constraint 충돌 발생
3. 기존 payment_attempt 조회
4. 기존 상태에 따라 같은 응답 반환 또는 처리 중 응답
```

이 방식의 장점은 강력하다는 거야. 단점은 “응답을 그대로 재현”하는 데는 Idempotency-Key 방식보다 부족할 수 있어. 그래서 실제 결제 API에서는 두 방식을 같이 쓰는 경우가 많다.

**추가로 중요한 방법: 상태 전이 제한**

주문/결제는 상태 머신으로 봐야 해.

예를 들어 주문 상태:

```text
CREATED -> PAYMENT_PENDING -> PAID -> FULFILLING -> COMPLETED
```

결제 상태:

```text
READY -> AUTHORIZED -> CAPTURED -> FAILED -> CANCELED
```

여기서 이미 `PAID`인 주문에 다시 `PAID` 처리를 하면 안 된다. 웹훅이 두 번 와도:

```text
if order.status == PAID:
    return success
```

처럼 “이미 반영된 이벤트”로 처리해야 한다.

다만 이것만으로는 부족해. 동시에 두 프로세스가 같은 상태를 보고 둘 다 업데이트할 수 있기 때문에, 상태 전이에는 보통 아래 중 하나가 필요하다.

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = :order_id
  AND status = 'PAYMENT_PENDING';
```

영향받은 row가 1개면 내가 성공적으로 전이한 것이고, 0개면 이미 누군가 처리했거나 상태가 맞지 않는 거야.

결론적으로 결제/주문 API의 멱등성은 보통 이렇게 조합해서 설계한다.

```text
외부 요청 중복 방지: Idempotency-Key
비즈니스 중복 방지: DB unique constraint
상태 중복 반영 방지: 상태 전이 조건부 업데이트
외부 이벤트 중복 방지: event_id/webhook_id 저장
```

주니어 엔지니어에게 내가 강조하고 싶은 건 이거야:

**멱등성은 “프론트에서 버튼 비활성화하면 되지 않나?” 수준의 문제가 아니다.**  
프론트 방어는 UX 개선일 뿐이고, 결제/주문에서는 백엔드와 DB가 최종적으로 중복 처리를 막아야 한다.

질문해줘. 설계안, 코드, 테이블 구조, API 흐름을 가져오면 내가 시니어 엔지니어 관점에서 “이게 실제 장애 상황에서 버티는지” 기준으로 비판적으로 봐줄게.

**Assistant**

좋아. 네가 잡은 섹션은 기본 골격으로 꽤 좋다. 다만 결제/주문 도메인에서 “설명답게” 보이려면 단순 개념 설명보다 **장애 상황에서 왜 필요한지**, **어디까지 보장하고 어디부터 보장하지 못하는지**가 드러나야 해.

내가 추천하는 구성은 이거야.

1. **멱등성의 정의**

같은 요청을 한 번 보내든 여러 번 보내든, 시스템의 최종 결과가 동일하게 유지되는 성질이라고 정의하면 돼.

단, 중요한 보완이 있어.  
“응답까지 항상 완전히 같아야 한다”는 뜻은 아니고, API 설계에서는 보통 **최종 상태가 중복으로 변하지 않도록 보장하는 것**에 초점을 둔다. 결제 API에서는 가능하면 이전 응답도 재사용하는 방식이 더 좋고.

2. **왜 사용하는가**

이 섹션은 꼭 필요해. 특히 결제/주문에서는 다음을 연결해야 해.

- 네트워크 타임아웃으로 클라이언트가 재시도함
- 사용자가 결제 버튼을 여러 번 누름
- 서버가 결제 처리 후 응답 전에 실패함
- PG사 웹훅이 중복으로 도착함
- 메시지 큐 이벤트가 중복 소비됨

결론은: **중복 결제, 중복 주문 생성, 중복 재고 차감, 중복 쿠폰 사용을 막기 위해 사용한다**고 정리하면 좋아.

3. **보통 어떤 경우에 사용하는가**

여기서는 모든 API가 아니라, “부작용이 있는 요청”에 사용한다고 잡으면 정확해.

대표적으로:

- 주문 생성
- 결제 승인
- 결제 취소/환불
- 재고 차감
- 쿠폰 사용
- 포인트 적립/차감
- 외부 웹훅 처리
- 메시지 큐 이벤트 소비

반대로 단순 조회 API인 `GET /orders/{id}` 같은 경우는 HTTP 의미상 원래 멱등적인 편이라 별도의 idempotency key까지는 보통 필요하지 않다.

4. **가장 일반적인 구현 방법 3가지**

이 섹션은 아주 좋고, 답변의 핵심이 될 수 있어.

추천하는 3가지는:

- **Idempotency-Key 방식**
  클라이언트가 고유 키를 보내고 서버가 처리 결과를 저장해 중복 요청에 기존 결과를 반환한다.

- **DB unique constraint 방식**
  `order_id`, `payment_id`, `transaction_id`, `event_id` 등에 유니크 제약을 걸어 물리적으로 중복 저장을 막는다.

- **상태 전이 조건 검사 방식**
  `PAYMENT_PENDING -> PAID`처럼 허용된 상태 전이만 처리하고, 이미 `PAID`인 주문은 다시 처리하지 않는다.

결제/주문에서는 보통 이 3개를 따로 고르는 게 아니라 **같이 쓴다**고 설명하는 게 현실적이야.

5. **사용 시 주의점**

이것도 꼭 필요해. 여기에 좋은 내용이 많이 들어간다.

- 같은 idempotency key로 다른 요청 본문이 오면 막아야 함
- 처리 중인 요청에 대한 정책이 필요함
- 성공 응답을 저장할지, 상태만 저장할지 결정해야 함
- 키 만료 시간이 너무 짧으면 늦은 재시도를 못 막음
- 애플리케이션 조회 후 insert만으로는 동시성 문제를 못 막음
- 외부 PG 호출과 내부 DB 저장 사이의 실패를 고려해야 함
- 멱등성은 “정확히 한 번 실행”을 보장하는 마법이 아니라 “중복 효과를 방지하는 설계”임

6. **기타사항**

이 섹션은 약간 애매해. “기타사항”이라고 두면 글이 흐려질 수 있어. 대신 더 명확한 섹션으로 나누는 걸 추천해.

추가하면 좋은 섹션은 아래야.

**멱등성이 보장하지 않는 것**

이건 꼭 넣는 게 좋아. 주니어 입장에서 오해하기 쉬운 부분이야.

예를 들면:

- 요청이 반드시 성공한다는 뜻은 아님
- 외부 PG사가 정확히 한 번만 처리한다는 뜻도 아님
- 동시성 제어를 자동으로 해결하지 않음
- 트랜잭션 경계가 잘못되면 여전히 불일치가 생길 수 있음

**결제/주문 도메인 예시 시나리오**

개념 설명만 하면 추상적이니까, 짧은 예시를 넣는 게 좋아.

예:

```text
1. 사용자가 결제 요청을 보냄
2. 서버가 PG 승인 요청을 보냄
3. PG 승인은 성공했지만 서버 응답이 타임아웃됨
4. 클라이언트가 같은 idempotency key로 재시도함
5. 서버는 기존 결제 성공 결과를 반환함
```

이런 시나리오가 있으면 왜 필요한지 바로 이해돼.

**권장 설계 요약**

마지막에 실무 기준으로 정리하면 좋아.

예:

```text

```

내가 보기엔 최종 목차는 이렇게 가면 가장 탄탄해.

```text

2. 왜 사용하는가

4. 결제/주문 도메인에서 중요한 이유
5. 일반적인 구현 방법 3가지

7. 멱등성이 보장하지 않는 것

```

네가 제안한 구성은 맞는 방향이고, 여기에 **“보장하지 않는 것”**과 **“결제/주문 예시 시나리오”**를 추가하면 답변의 깊이가 확 올라갈 거야.

라고 말했는데 그러면 응답이 달라진다면 사용자 입장에서는 동작이 바뀌었다고 생각할 수 있는데, 멱등성이라는건 시스템 입장에서만 동일한 동작을 하면 되는거야? output은 상관 없이?

**Assistant**

좋은 질문이야. 여기서 구분을 정확히 해야 해.

**엄밀한 멱등성의 핵심은 “시스템 상태에 대한 효과(effect)가 동일한가”**야.  
즉 같은 요청을 여러 번 보내도 **결제 1번, 재고 차감 1번, 쿠폰 사용 1번**처럼 최종 상태가 중복으로 변하지 않으면 멱등성의 핵심은 만족한다고 볼 수 있어.

하지만 API 설계 관점에서는 그걸로 끝내면 부족해.  
사용자나 클라이언트 입장에서는 응답이 완전히 다르면 “다른 일이 일어난 것 아닌가?”라고 해석할 수 있기 때문이야.

예를 들어 첫 요청 응답이:

```json
{
  "status": "PAID",
  "paymentId": "pay_123"
}
```

인데 재시도 응답이:

```json
{
  "status": "DUPLICATE_REQUEST"
}
```

이면 시스템 상태는 멱등적일 수 있어. 결제는 한 번만 됐으니까.  
하지만 클라이언트는 이걸 성공으로 봐야 하는지, 실패로 봐야 하는지 헷갈릴 수 있다.

그래서 결제/주문 API에서는 보통 더 강하게 설계해서:

```text
같은 멱등성 키 + 같은 요청 내용이면
가능한 한 같은 HTTP status와 같은 response body를 반환한다.
```

이게 가장 클라이언트 친화적이고 안전한 방식이야.

다만 “항상 응답까지 완전히 동일해야만 멱등성이다”라고 말하면 조금 부정확해져. 예를 들어 응답에 `processedAt`, `retrievedAt`, `retryCount`, `serverTraceId` 같은 값이 들어가면 재시도마다 달라질 수 있어. 그래도 결제 상태와 비즈니스 결과가 같다면 멱등성 자체가 깨졌다고 보지는 않아.

정리하면 이렇게 보면 돼.

```text
최소 기준:
같은 요청을 여러 번 보내도 시스템의 최종 상태와 비즈니스 효과가 동일해야 한다.

좋은 API 설계 기준:
최종 상태뿐 아니라 클라이언트가 해석하는 결과도 동일하게 보이도록,
가능하면 같은 성공 응답을 재사용한다.

달라져도 되는 응답:
traceId, 응답 생성 시각, retryCount 같은 관측/메타데이터.

달라지면 위험한 응답:
성공/실패 여부, 결제 ID, 주문 상태, 승인 금액, 쿠폰 사용 결과.
```

그래서 네가 표시한 문장은 약간 보완하는 게 좋아. 이렇게 바꾸면 더 정확해.

```text
주의할 점은 멱등성이 이론적으로는 응답 본문이 아니라 시스템 상태에 대한 효과가 동일한지를 중심으로 판단된다는 것이다. 다만 결제 API처럼 클라이언트가 응답을 기준으로 후속 동작을 결정하는 경우에는, 같은 멱등성 키와 같은 요청 내용에 대해 가능하면 이전과 같은 성공 응답을 반환하도록 설계하는 것이 안전하다.
```

이 표현이 더 낫다.  
“output은 상관없다”가 아니라, **정의의 중심은 상태 변화이고, 실무 API에서는 응답 일관성도 사실상 중요 요구사항으로 봐야 한다**가 정확해.

**멱등성 구현 방식 분류**

1. **연산 자체를 멱등적으로 설계**

같은 요청을 여러 번 해도 결과가 같도록 API 의미를 설계하는 방식이야.

예:

```http
PUT /users/1/email
{
  "email": "a@example.com"
}
```

이건 여러 번 호출해도 이메일이 같은 값으로 설정될 뿐이야.  
반대로 `POST /points/add 1000`처럼 “추가” 의미는 여러 번 호출하면 포인트가 계속 늘어나므로 멱등적이지 않다.

2. **Idempotency-Key 저장**

클라이언트가 고유 키를 보내고, 서버가 그 키와 요청 해시, 처리 상태, 응답 결과를 저장하는 방식.

결제 승인, 주문 생성, 환불 요청 같은 `POST` API에서 가장 자주 쓰인다.

3. **클라이언트 또는 서버가 발급한 비즈니스 식별자 사용**

예를 들어 주문 생성 전에 `orderId`, `paymentIntentId`, `couponIssueId`를 먼저 만들고, 이후 요청은 그 ID 기준으로 처리하는 방식이야.

```text
POST /orders/{orderId}/pay
```

같은 `orderId`에 대해 결제 성공은 한 번만 허용할 수 있다.

4. **DB 유니크 제약 조건**

중복되면 안 되는 비즈니스 키에 유니크 제약을 둔다.

예:

```text
pg_transaction_id unique
webhook_event_id unique
coupon_issue_request_id unique
order_id + success_payment unique
```

중요한 건 애플리케이션 코드만 믿지 않고 DB가 마지막 방어선을 맡게 하는 거야.

5. **UPSERT / Insert-if-not-exists**

중복 요청이 들어오면 새로 만들지 않고 기존 레코드를 사용한다.

예:

```sql
INSERT INTO coupon_issues(user_id, coupon_id)
VALUES (:user_id, :coupon_id)
ON CONFLICT (user_id, coupon_id)
DO NOTHING;
```

쿠폰 발급, 좋아요, 장바구니 항목 추가 같은 곳에서 자주 쓰인다.

6. **상태 전이 조건 검사**

현재 상태가 기대한 상태일 때만 다음 상태로 변경한다.

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = :order_id
  AND status = 'PAYMENT_PENDING';
```

이건 멱등성뿐 아니라 동시성 제어에도 중요하다.  
이미 `PAID`인 주문에 결제 성공 이벤트가 다시 와도 중복 반영하지 않는다.

7. **이벤트 ID 기반 중복 제거**

웹훅이나 메시지 큐 이벤트에는 보통 이벤트 ID가 있다.  
처리한 `event_id`를 저장하고, 같은 이벤트가 다시 오면 무시하거나 기존 처리 결과를 반환한다.

```text
payment.succeeded event_id = evt_123
```

이건 PG 웹훅, Kafka/SQS/RabbitMQ 컨슈머에서 매우 중요하다.

8. **Inbox 패턴**

외부 이벤트를 바로 처리하지 않고, 먼저 `inbox_events` 테이블에 저장한 뒤 처리한다.  
`event_id`에 유니크 제약을 걸어서 중복 이벤트 저장을 막는다.

웹훅/메시지 소비 쪽 멱등성 구현에 많이 쓴다.

9. **Outbox 패턴**

내부 상태 변경과 이벤트 발행을 같은 트랜잭션 안에서 기록하고, 나중에 outbox worker가 발행한다.

이건 “중복 요청 방지” 자체라기보다는, 결제 성공 저장 후 이벤트 발행 실패 같은 문제를 줄이는 정합성 패턴이야. 발행 이벤트에도 고유 ID를 둬서 소비자가 멱등적으로 처리하게 만든다.

10. **락 사용**

분산 락, DB row lock, advisory lock 등으로 같은 주문/결제에 대한 처리를 직렬화할 수 있다.

하지만 락은 보조 수단이야. 락 TTL 만료, 프로세스 죽음, 네트워크 지연이 있어서 **락만으로 멱등성을 보장한다고 보면 위험하다.** 보통 DB 제약, 상태 조건, 멱등성 기록과 같이 쓴다.

11. **Optimistic Lock / Version Check**

레코드의 버전을 보고 기대한 버전일 때만 업데이트한다.

```sql
UPDATE orders
SET status = 'PAID',
    version = version + 1
WHERE id = :order_id
  AND version = :expected_version;
```

중복 처리 방지보다는 동시 수정 충돌을 막는 성격이 강하지만, 상태 전이와 함께 쓰면 멱등성 구현을 보강한다.

12. **외부 PG의 멱등성 기능 사용**

Stripe, PayPal 같은 결제 API는 자체 idempotency key 또는 request id 기능을 제공한다.  
우리 서버도 멱등성을 구현해야 하지만, PG 호출에도 동일한 의미의 키를 전달하면 외부 중복 결제 위험을 줄일 수 있다.

13. **Append-only Ledger + Unique Reference**

결제/정산/포인트 같은 금전성 데이터는 값을 덮어쓰기보다 원장 테이블에 append-only로 기록하는 경우가 많다.  
이때 각 원장 항목에 `business_reference_id`를 두고 유니크하게 관리하면 같은 거래가 두 번 기록되는 것을 막을 수 있다.

14. **재처리/정산 기반 복구**

장애 후 PG 거래 조회, 주문 상태 비교, 정산 데이터 대조로 불일치를 복구하는 방식이다.  
이건 멱등성의 직접 구현이라기보다는, 멱등성으로도 막지 못한 불확실성을 복구하는 안전망이다.

정리하면, 네 문서의 3가지는 틀린 건 아니야. 다만 제목을 **“일반적인 구현 방법 3가지”**라고 하면 대표 방식으로는 괜찮고, “모든 방식”처럼 보이면 부족해.

결제/주문 도메인에서 핵심만 고르면 보통 이 조합이 가장 중요해:

```text
Idempotency-Key
DB unique constraint
상태 전이 조건 검사
이벤트 ID 중복 제거
외부 PG idempotency key
복구/정산 프로세스
```

문서에는 3가지를 메인으로 설명하고, “그 밖에 함께 쓰는 보조 패턴”으로 이벤트 ID, Inbox/Outbox, 락, PG 멱등성 기능 정도를 짧게 추가하면 균형이 좋아.

```text
1. 식별자 기반 중복 제거 전략
   - Idempotency-Key
   - event_id
   - webhook_id
   - request_id
   - inbox_events 테이블
   - DB unique constraint

2. 비즈니스 상태/효과 기반 방어 전략
   - 연산 자체를 멱등적으로 설계
   - 상태 전이 조건 검사
   - 이미 처리된 상태면 재반영하지 않기
   - 성공 결제는 주문당 하나만 허용
   - 조건부 UPDATE
   - 필요 시 락이나 optimistic lock으로 동시성 보조

3. 복구/정합성 보정 전략
   - PG 거래 조회 후 주문 상태 보정
   - 정산 데이터 대조
   - 실패 이벤트 재처리
   - outbox 기반 이벤트 재발행
   - 운영 배치나 reconciliation job
```

그래서 네 말은 큰 방향에서 맞고, 문서에는 이렇게 정리하는 게 가장 정확해:

```text
멱등성 구현은 크게 중복 요청을 식별하는 전략, 중복 요청이 들어와도 비즈니스 효과가 한 번만 반영되도록 하는 상태/로직 설계, 그리고 장애 이후 불일치를 복구하는 정합성 보정 전략으로 나눌 수 있다.
```

단, 마지막 복구 전략은 “멱등성을 구현하는 직접 방식”이라기보다 **멱등성 설계와 함께 필요한 운영 안전망**이라고 구분해두는 게 좋아.

멱등성 설계의 직접 목표는 이거야.

```text
같은 요청 또는 같은 이벤트가 여러 번 들어와도
```

예를 들면:

```text
같은 결제 승인 요청이 두 번 들어와도 결제는 한 번만 승인

같은 쿠폰 발급 요청이 두 번 와도 쿠폰은 한 번만 발급
```

반면 복구/정합성 보정은 이런 상황을 다뤄.

```text
PG 결제는 성공했는데 우리 DB에는 실패로 남음
주문은 PAID가 되었는데 결제 성공 이벤트 발행은 실패함
웹훅이 지연되어 내부 상태와 PG 상태가 어긋남
컨슈머가 처리 중 죽어서 이벤트 상태가 애매해짐
정산 데이터와 내부 결제 데이터가 다름
```

이건 “같은 요청이 여러 번 왔다”의 문제가 아니라, **분산 시스템의 일부 단계는 성공하고 일부 단계는 실패한 문제**야. 그래서 멱등성이라기보다 **정합성 보정, reconciliation, recovery** 쪽에 가깝다.

다만 결제/주문 시스템에서는 둘을 같이 설계해야 해. 이유는 멱등성이 있어도 아래 같은 빈틈이 생길 수 있기 때문이야.

```text
1. 서버가 PG에 결제 승인 요청
2. PG 결제 성공
3. 서버가 DB에 성공 상태 저장하기 전에 장애
4. 클라이언트는 타임아웃으로 재시도
```

이때 멱등성 키만 보고는 내부 기록이 없을 수도 있어. 그러면 PG 거래 조회 같은 복구 절차가 필요해.

그래서 표현은 이렇게 하는 게 정확해.

```text
복구/정합성 보정 전략은 멱등성 구현 방식이라기보다는, 멱등성 설계와 함께 필요한 운영 안전장치다. 멱등성이 중복 실행을 예방하는 설계라면, 복구/정합성 보정은 장애로 인해 이미 어긋난 상태를 나중에 찾아 맞추는 설계다.
```

즉 네 말대로, **멱등성 설계가 뚫렸을 때의 안전장치**라고 볼 수 있어. 다만 “뚫렸다”는 표현보다 더 정확히는 **멱등성이 다루는 범위를 벗어난 장애를 보정하는 장치**에 가깝다.

```text
## 4. 멱등성을 구현하는 큰 방향과 대표 방법

멱등성 구현은 크게 두 축으로 나눠 볼 수 있다.

첫째, 중복 요청을 식별하는 방식이다.
같은 요청이나 같은 이벤트를 구분할 수 있는 고유 식별자를 저장하고,
이미 처리한 식별자가 다시 들어오면 새로 처리하지 않는다.

대표 예시는 다음과 같다.
- Idempotency-Key
- PG 거래 ID
- 웹훅 event_id
- 메시지 event_id
- DB unique constraint
- inbox_events 테이블

둘째, 비즈니스 효과가 중복 반영되지 않도록 상태와 연산을 설계하는 방식이다.
중복 요청이 들어오더라도 현재 상태와 비즈니스 규칙을 확인해
결제, 주문, 재고, 쿠폰 같은 효과가 한 번만 반영되도록 한다.

대표 예시는 다음과 같다.
- 연산 자체를 멱등적으로 설계
- 상태 전이 조건 검사
- 이미 처리된 상태면 재반영하지 않기
- 조건부 UPDATE
- 성공 결제는 주문당 하나만 허용
- 필요 시 락이나 optimistic lock으로 동시성 보조

실제 결제/주문 시스템에서는 이 두 축을 따로 선택하기보다 함께 사용한다.
예를 들어 결제 승인 API는 Idempotency-Key로 중복 요청을 식별하고,
DB 유니크 제약과 상태 전이 조건으로 실제 결제 성공 처리가 중복 반영되지 않게 막는다.
```

그 다음에 현재의 대표 구현 3가지를 이어가면 좋아.

```text
이 두 축을 기준으로 결제/주문 도메인에서 특히 자주 쓰는 대표 구현 방법은 다음 3가지다.
```

그리고 기존 구조:

```text
### 4-1. Idempotency-Key 방식
### 4-2. DB 유니크 제약 조건 방식
### 4-3. 상태 전이 조건 검사 방식
```

이렇게 가면 흐름이 훨씬 좋아져.

다만 여기서 하나 비판적으로 볼 점이 있어.  
`DB unique constraint`는 “식별자 기반 중복 제거”이기도 하고 “비즈니스 불변식 강제”이기도 해. 예를 들어 `event_id unique`는 식별자 기반이고, “성공 결제는 주문당 하나”는 비즈니스 규칙 기반이야. 그래서 문서에서는 이렇게 써야 정확해.

```text
DB 유니크 제약은 어떤 컬럼에 거느냐에 따라 두 축 모두에 사용될 수 있다.
event_id나 request_id에 걸면 중복 식별자 제거이고,
order_id + 성공 결제 상태에 걸면 비즈니스 규칙을 DB에서 강제하는 방식이다.
```

이 문장까지 넣으면 문서의 정확도가 올라가.

내가 추천하는 4번 최종 구성은 이거야.

```text
## 4. 멱등성을 구현하는 큰 방향과 대표 방법

4-0. 구현의 두 축
- 중복 요청을 식별하는 방식
- 비즈니스 효과가 중복 반영되지 않도록 상태와 연산을 설계하는 방식

4-1. Idempotency-Key 방식
4-2. DB 유니크 제약 조건 방식
```

핵심은 이렇게 잡으면 돼.

```text
1. 같은 요청 재시도는 같은 결과를 반환한다.
2. 같은 사용자가 같은 쿠폰을 여러 번 발급받지 못하게 한다.

```

```text
- coupon_id + user_id unique 제약

```

예시 의사코드는 이렇게 쓰면 충분해.

```java
@Transactional
IssueCouponResponse issueCoupon(
    Long userId,
    Long couponId,
    String idempotencyKey
) {
    // 1. 같은 Idempotency-Key 요청이면 기존 결과 반환
    IdempotencyRecord record = idempotencyRepository.findByKey(idempotencyKey);

    if (record != null) {
        if (!record.isSameRequest(userId, couponId)) {
            throw new BadRequestException("잘못 재사용된 Idempotency-Key");
        }

        if (record.isSuccess()) {
            return record.savedResponse();
        }

        if (record.isProcessing()) {
            throw new ConflictException("이미 처리 중인 요청");
        }
    }

    idempotencyRepository.saveProcessing(idempotencyKey, userId, couponId);

    // 2. 이미 발급받은 쿠폰이면 중복 발급하지 않고 기존 결과 반환
    CouponIssue existingIssue =
        couponIssueRepository.findByUserIdAndCouponId(userId, couponId);

    if (existingIssue != null) {
        IssueCouponResponse response = IssueCouponResponse.alreadyIssued(existingIssue.getId());
        idempotencyRepository.saveSuccess(idempotencyKey, response);
        return response;
    }

    // 3. 남은 수량이 있을 때만 원자적으로 차감
    int updatedRows = couponRepository.decreaseRemainingCount(couponId);

    if (updatedRows == 0) {
        IssueCouponResponse response = IssueCouponResponse.soldOut();
        idempotencyRepository.saveSuccess(idempotencyKey, response);
        return response;
    }

    // 4. 실제 쿠폰 발급
    CouponIssue issue = couponIssueRepository.save(userId, couponId);

    IssueCouponResponse response = IssueCouponResponse.success(issue.getId());
    idempotencyRepository.saveSuccess(idempotencyKey, response);

    return response;
}
```

MySQL 쪽 핵심은 이런 식이야.

```sql
UPDATE coupons
SET remaining_count = remaining_count - 1
WHERE id = :coupon_id
  AND remaining_count > 0;
```

그리고 유니크 제약은 필요해.

```sql
UNIQUE KEY uk_idempotency_key (idempotency_key);
UNIQUE KEY uk_coupon_issue_user_coupon (user_id, coupon_id);
```

여기서 중요한 건 `SELECT remaining_count` 후에 애플리케이션에서 판단하고 차감하면 동시 요청에서 초과 발급될 수 있다는 점이야. 그래서 수량 차감은 반드시 `remaining_count > 0` 조건이 붙은 `UPDATE`로 처리하는 게 좋아.

**Assistant**

아니. **의사코드(Pseudo-code)는 실제 실행 가능한 코드라기보다, 핵심 로직의 흐름을 코드처럼 표현한 설명용 코드**야.

내가 방금 쓴 건 Java 문법을 흉내 낸 **Java 스타일 의사코드**에 가까워. 실제 프로젝트에서 그대로 컴파일되지는 않아. 예를 들어 이런 것들은 실제 코드가 아니라 설명용이야.

```java
record.isSameRequest(userId, couponId)
IssueCouponResponse.alreadyIssued(...)
idempotencyRepository.saveProcessing(...)
```

이런 메서드는 실제로 존재하는 게 아니라, “이 시점에 이런 검증/저장을 해야 한다”는 의미를 표현한 거야.

과제에서 “의사코드(Pseudo-code)나 짧은 스니펫”이라고 했으니까 선택지는 두 가지야.

```text
1. 의사코드
   - 언어에 덜 종속적
   - 흐름 설명이 목적
   - 컴파일 안 되어도 됨

2. 짧은 스니펫
   - Java/MySQL에 더 가까운 실제 코드 조각
   - 다만 전체 애플리케이션은 아니므로 그대로 실행되지는 않을 수 있음
```

과제 답변으로는 오히려 의사코드가 좋아. 핵심은 프레임워크 코드가 아니라 멱등성 보장 로직이니까.

더 의사코드답게 쓰면 이렇게 할 수 있어.

```text
쿠폰 발급 요청(userId, couponId, idempotencyKey)

1. idempotencyKey로 기존 요청 기록을 조회한다.
2. 기록이 있고 요청 내용이 같으며 성공 상태라면 기존 응답을 반환한다.
3. 기록이 처리 중이면 중복 요청으로 보고 처리 중 응답을 반환한다.
4. 기록이 없으면 PROCESSING 상태로 저장한다.
5. userId + couponId로 이미 발급된 쿠폰이 있는지 확인한다.
6. 이미 발급됐다면 기존 발급 결과를 저장하고 반환한다.
7. 쿠폰 수량을 조건부로 차감한다.
   UPDATE coupons
   SET remaining_count = remaining_count - 1
   WHERE id = couponId AND remaining_count > 0
8. 차감된 row가 0이면 품절 응답을 저장하고 반환한다.
9. coupon_issues에 발급 이력을 저장한다.
10. 성공 응답을 idempotency 기록에 저장하고 반환한다.
```

이게 더 “의사코드”에 가까워.  
Java/MySQL을 드러내고 싶으면 여기에 `@Transactional`, `UNIQUE(user_id, coupon_id)`, `UNIQUE(idempotency_key)` 정도만 붙이면 충분해.

**User**

idempotencyKey를 쿠폰 테이블에 같이 있다고 생각하면 더 편하지 않을까? 따로 테이블이 있는게 아니라

**Assistant**

그렇게 생각할 수는 있는데, **쿠폰 테이블에 `idempotencyKey`를 같이 두는 건 보통 맞지 않아.**  
여기서 “쿠폰”과 “요청”의 생명주기가 다르기 때문이야.

쿠폰 테이블은 보통 이런 정보를 가진다.

```text
coupons
- coupon_id
- name
- total_count
- remaining_count
- valid_from
- valid_to
```

이건 **쿠폰 상품/정책**에 대한 테이블이야.  
반면 `idempotencyKey`는 이런 정보야.

```text
idempotencyKey
- 특정 사용자가
- 특정 시점에
- 특정 API 요청을
- 중복 재시도했는지 구분하는 요청 식별자
```

즉 `idempotencyKey`는 쿠폰 자체의 속성이 아니라 **요청의 속성**이야.

예를 들어 쿠폰 하나에 사용자 10만 명이 발급 요청을 보낼 수 있어. 그러면 `coupons` 테이블 한 row에 10만 개의 idempotency key를 넣을 수는 없어. 컬럼 하나로는 한 요청밖에 표현하지 못하고, 배열/JSON으로 넣으면 조회, unique 제약, 만료 처리, 동시성 제어가 어려워져.

더 자연스러운 위치는 이 둘 중 하나야.

```text
1. 별도 idempotency_requests 테이블
   - API 요청 단위로 멱등성 관리

2. coupon_issues 테이블
   - 실제 쿠폰 발급 이력에 request_id 또는 idempotency_key 저장
```

선착순 쿠폰 발급에서는 간단히 하려면 `coupon_issues`에 넣는 방식도 가능해.

```text
coupon_issues
- issue_id
- coupon_id
- user_id
- idempotency_key
- status
- created_at
```

그리고 unique 제약을 둔다.

```sql
UNIQUE(idempotency_key)
UNIQUE(user_id, coupon_id)
```

이렇게 하면:

```text
- 같은 idempotencyKey 재시도 방지
- 같은 사용자의 같은 쿠폰 중복 발급 방지
```

둘 다 어느 정도 잡을 수 있어.

다만 시니어 관점에서 보면, **idempotency_requests 별도 테이블이 더 일반적이고 확장성이 좋아.** 이유는 성공/실패/처리 중 상태, 요청 해시, 응답 본문, 만료 시간 같은 “요청 처리 정보”를 발급 이력과 분리해서 관리할 수 있기 때문이야.

정리하면:

```text
coupons 테이블에 idempotencyKey를 두는 건 부적절하다.
coupon_issues 테이블에 두는 건 간단한 설계에서는 가능하다.
idempotency_requests 별도 테이블은 더 일반적이고 확장성 있는 설계다.
```

과제용 의사코드는 너무 복잡해지지 않게 하려면 이렇게 잡는 게 좋아.

```text
idempotency_requests: 요청 중복 방지
coupon_issues: 사용자별 쿠폰 중복 발급 방지
coupons: 남은 수량 관리
```

이 구분이 가장 깔끔해.

**User**

근데 외부 API가없는데 processing으로 저장하는 이유가 있어?

**Assistant**

좋은 질문이야. **외부 API가 없으면 `PROCESSING` 상태의 필요성은 줄어들어.**  
하지만 완전히 쓸모없는 건 아니고, 동시 요청을 어떻게 처리할지에 따라 달라져.

`PROCESSING`을 두는 이유는 보통 이거야.

```text
첫 번째 요청이 아직 처리 중일 때,
같은 Idempotency-Key를 가진 두 번째 요청이 들어오면
"이미 처리 중"이라고 판단하기 위해서
```

결제처럼 PG 호출이 있으면 처리 시간이 길고 결과가 불확실하니까 `PROCESSING`이 꽤 중요해. 그런데 선착순 쿠폰 발급처럼 내부 DB 트랜잭션만으로 짧게 끝나는 API라면 선택지가 생겨.

**간단한 쿠폰 발급 API라면 `PROCESSING` 없이도 가능해.**

예를 들어 이렇게 할 수 있어.

```text
1. coupon_issues에 user_id + coupon_id unique 제약을 둔다.
2. idempotency_key에도 unique 제약을 둔다.
3. 트랜잭션 안에서 조건부 재고 차감 후 발급 이력을 insert한다.
4. 중복 insert가 발생하면 기존 발급 이력을 조회해 반환한다.
```

이 경우 멱등성의 핵심은 `PROCESSING` 상태보다:

```text
- unique(idempotency_key)
- unique(user_id, coupon_id)
- UPDATE coupons SET remaining_count = remaining_count - 1
  WHERE id = ? AND remaining_count > 0
```

이 세 가지야.

다만 `PROCESSING`이 있으면 좋은 경우도 있어.

```text
- 쿠폰 발급 후 알림 발송, 이벤트 발행 같은 후속 작업이 있다.
- 요청 처리 시간이 길 수 있다.
- 같은 키로 동시에 들어온 요청에 409 처리 중 응답을 주고 싶다.
- 성공/실패 응답을 idempotency 테이블에 저장해 재시도에 같은 응답을 주고 싶다.
```

하지만 과제의 “선착순 쿠폰 발급 API”를 간결하게 설명하려면, **`PROCESSING`은 빼도 된다**고 보는 게 좋아. 외부 API도 없고 내부 DB로 끝나는 흐름이면 오히려 단순한 설계가 낫다.

추천 의사코드는 이렇게 가면 돼.

```text
쿠폰 발급 요청(userId, couponId, idempotencyKey)

1. 같은 idempotencyKey의 발급 결과가 있으면 기존 결과를 반환한다.
2. 같은 userId + couponId 발급 이력이 있으면 이미 발급된 결과를 반환한다.
3. 남은 수량이 있을 때만 원자적으로 차감한다.
   UPDATE coupons
   SET remaining_count = remaining_count - 1
   WHERE id = couponId
     AND remaining_count > 0
4. 차감된 row가 0이면 품절을 반환한다.
5. coupon_issues에 발급 이력을 저장한다.
   이때 idempotencyKey, userId, couponId에 unique 제약을 둔다.
6. 발급 성공 결과를 반환한다.
```

이 답변에서 `PROCESSING`을 빼면 과제 수준에 더 맞아.  
결론: **외부 API가 없는 짧은 DB 트랜잭션 기반 쿠폰 발급에서는 `PROCESSING`은 필수는 아니고, unique 제약 + 조건부 UPDATE가 더 핵심이다.**

이것도 conflict 걸려서 같은 값 줄 수 있는거 아니야?

예를 들어 `idempotency_key`에 unique 제약이 있으면:

```text
1. 첫 번째 요청이 idempotency_key = abc 로 insert
2. 동시에 두 번째 요청도 abc 로 insert 시도
3. 두 번째 요청은 unique conflict 발생
4. 두 번째 요청은 기존 레코드나 발급 이력을 조회해서 응답
```

다만 여기서 중요한 차이가 있어.

**충돌이 났을 때 기존 결과가 아직 없을 수 있다.**

첫 번째 요청이 아직 트랜잭션 안에서 처리 중이면, 두 번째 요청은 conflict를 감지하더라도 “성공 결과”를 바로 못 읽을 수 있어. 이때 선택지는 보통 셋이야.

```text
1. 409 Conflict / 처리 중 반환
2. 짧게 재조회하며 대기 후 기존 결과 반환
3. DB 락 대기 후 첫 요청 커밋 결과를 읽고 반환
```

그래서 네 말처럼 **conflict를 걸어서 같은 값을 줄 수는 있는데**, 항상 바로 같은 값을 줄 수 있는 건 아니야. 첫 요청이 이미 커밋된 뒤라면 기존 성공 결과를 반환할 수 있고, 아직 처리 중이면 `409`나 재시도 안내가 더 자연스러울 수 있어.

정리하면:

```text
PROCESSING 상태를 저장하는 방식:
- 처리 중임을 명시적으로 표현한다.
- 같은 키 재요청에 409 같은 응답을 주기 쉽다.
- 결제처럼 긴 작업에 유리하다.

unique conflict만 이용하는 방식:
- 구조가 단순하다.
- 짧은 DB 트랜잭션 API에 적합하다.
- 충돌 시 기존 결과가 없을 수 있어 재조회/409/락 대기 정책이 필요하다.
```

선착순 쿠폰 발급 API라면 답안에서는 이렇게 쓰는 게 가볍고 정확해.

```text
같은 idempotencyKey로 insert하다가 unique conflict가 나면 기존 발급 결과를 조회해 반환한다.
아직 첫 요청이 커밋 전이라 결과가 없으면 409 처리 중 응답을 반환하거나 짧게 재조회한다.
```

즉, **네 말이 맞고**, `PROCESSING`은 필수라기보다 “처리 중 상태를 더 명확히 관리하고 싶을 때 쓰는 선택지”로 보는 게 맞아.
