## Scenario B. 티켓 예매 시스템 문제 해결 시나리오

### 1. 문제 정의

상황: 오픈 1분 만에 10만 명 동시 접속 예상, 1만 석 한정. 중복 차감(Overbooking) 없이 1만 명에게만 정확히 판매해야 함.

#### 1.1 상황 요약

- 동시 접속 규모: 10만 명
- 판매 수량: 1만 석
- 반드시 보장해야 하는 조건: 중복 차감이나 초과 판매 없이 정확히 1만 명에게만 티켓 판매

#### 1.2 핵심 기술적 문제

- 핵심 문제 한 문장 정의: 짧은 시간에 대량의 동시 요청이 몰리는 상황에서, 시스템 전체가 판매 가능 수량과 주문 상태의 정합성을 잃지 않도록 제어하는 문제
- 단순 트래픽 처리 문제가 아닌 이유:
  - 서버를 많이 늘려도 같은 좌석이나 같은 재고를 동시에 차감하려는 경쟁 조건은 사라지지 않는다.
  - 결제, 주문, 좌석 확정은 여러 상태를 거치므로 한 단계만 성공하고 다음 단계가 실패하는 불일치가 발생할 수 있다.
  - 사용자의 새로고침, 중복 클릭, 네트워크 재시도 때문에 같은 요청이 여러 번 처리될 수 있다.
- 중복 차감 / 초과 판매가 발생할 수 있는 지점:
  - 재고 조회 후 차감 사이에 다른 요청이 먼저 재고를 차감하는 경우
  - 동일 좌석을 여러 트랜잭션이 동시에 확정하는 경우
  - 결제 성공 후 좌석 확정 실패, 또는 좌석 점유 후 결제 실패가 복구되지 않는 경우
  - 메시지 큐나 이벤트 발행 실패로 주문 상태와 재고 상태가 어긋나는 경우

#### 1.3 문제를 나누어 보는 관점

- 동시성 제어 문제: 같은 재고 또는 좌석에 대한 경쟁 요청 중 하나만 성공시키는 문제
- 대기열 / 트래픽 제어 문제: 10만 명의 요청을 한꺼번에 핵심 트랜잭션 구간으로 보내지 않는 문제
- 결제와 좌석 확정의 원자성 문제: 외부 결제 시스템과 내부 주문/좌석 상태를 최종적으로 일관되게 맞추는 문제

---

### 2. 핵심 엔지니어링 요구사항

#### 2.1 재고 정합성 보장

- 전체 판매 수량은 반드시 1만 석을 초과하지 않아야 한다.
- 동일 좌석이 두 명 이상에게 중복 배정되지 않아야 한다.
- 애플리케이션 코드뿐 아니라 DB 제약조건, 조건부 업데이트, unique constraint 같은 마지막 방어선이 필요하다.

#### 2.2 원자적 처리 보장

- 좌석 확인, 재고 차감, 주문 생성, 좌석 확정은 중간 상태 불일치 없이 처리되어야 한다.
- 내부 DB 변경은 가능한 하나의 트랜잭션 안에서 묶는다.
- 결제는 외부 시스템이므로 DB 트랜잭션에 직접 오래 묶지 않고, 주문 상태 전이와 보상 처리로 일관성을 맞춘다.

#### 2.3 동시 요청 제어

- 동시에 많은 구매 요청이 들어와도 재고 차감 로직은 안전하게 제어되어야 한다.
- 같은 사용자의 중복 요청이나 재시도가 중복 구매로 이어지지 않아야 한다.
- idempotency key를 두어 같은 구매 시도는 한 번만 처리되도록 해야 한다.

#### 2.4 트래픽 제어

- 오픈 직후 10만 명의 요청이 한꺼번에 핵심 처리 구간으로 몰리지 않도록 제어해야 한다.
- 대기열이나 요청 제한을 통해 시스템이 감당 가능한 수준으로 요청을 흘려보내야 한다.
- 구매 진입 전 단계와 실제 재고 차감 단계의 부하를 분리해야 한다.

#### 2.5 실패 복구

- 결제 실패, 타임아웃, 서버 장애가 발생했을 때 점유된 좌석이 복구되어야 한다.
- 주문 상태를 추적할 수 있어야 하며, 불일치가 발생하면 보상 처리할 수 있어야 한다.
- 예: 좌석 `AVAILABLE -> HELD -> SOLD`, 주문 `PENDING_PAYMENT -> PAID -> CONFIRMED` 같은 상태 머신을 둔다.

### 3. 재고 정합성 보장 방식 비교

#### 3.1 Pessimistic Lock, 비관적 락

##### 개요

- 충돌이 자주 발생한다고 가정하고, 재고나 좌석 row를 먼저 잠근 뒤 처리하는 방식이다.
- 대표적으로 DB에서 `SELECT ... FOR UPDATE`를 사용한다.
- 같은 row를 수정하려는 다른 트랜잭션은 기존 트랜잭션이 commit 또는 rollback될 때까지 대기한다.

##### 장점

- 같은 row에 대한 변경을 DB가 직렬화해주므로 정합성이 강하고, 구현 흐름도 직관적이다.
- DB 트랜잭션과 잘 맞는다. 주문 생성, 좌석 점유, 재고 차감을 한 트랜잭션으로 묶기 쉽다.
- 충돌이 실제로 매우 잦은 구간에서는 재시도 폭탄이 발생하는 낙관적 락보다 예측 가능할 수 있다.

##### 단점

- 락 대기 때문에 처리량이 급격히 떨어질 수 있다.
- 특정 공연의 전체 재고 row 하나에 요청이 몰리면 해당 row가 병목이 된다.
- 트랜잭션이 길어지면 DB 커넥션과 락을 오래 점유한다.
- 데드락, 락 타임아웃, 장애 시 롤백 처리를 신경 써야 한다.
- 결제처럼 오래 걸리는 외부 호출을 락 안에 넣으면 시스템 전체가 쉽게 막힌다.

##### 적합한 상황

- 트래픽이 아주 크지 않거나, 좌석/재고 단위가 잘게 나뉘어 락 경합이 제한적인 경우
- 구독 변경, 결제 상태 변경, 관리자 승인처럼 특정 row의 상태 변경 순서가 중요하지만, 같은 row에 대한 동시 경합은 높지 않은 경우
- 구현 복잡도를 낮추고 DB 트랜잭션 중심으로 안전하게 처리하고 싶은 경우

##### 이 시나리오에서의 판단

- 10만 명이 1만 석에 동시에 몰리는 티켓 오픈에서는 단독 해법으로는 병목 가능성이 크다.
- 다만 좌석 확정처럼 특정 좌석 row의 상태 변경 순서를 명확히 제어해야 하는 구간에서는 제한적으로 사용할 수 있다.

---

#### 3.2 분산 락, Redis Lock 등

##### 개요

- 여러 애플리케이션 서버가 같은 자원에 접근할 때, DB 밖의 공통 저장소를 이용해 락을 잡는 방식이다.
- Redis의 `SET key value NX PX` 같은 명령으로 특정 재고나 좌석에 대한 락을 획득한다.
- 락을 얻은 요청만 DB 재고 차감 또는 좌석 확정 로직으로 들어간다.

##### 장점

- 여러 애플리케이션 서버가 같은 잠금 기준을 공유할 수 있어, 서버별 로컬 락으로 막기 어려운 동시성 문제를 제어할 수 있다.
- DB 변경 구간에 들어가기 전에 요청을 걸러낼 수 있어, DB row lock 경합이나 동시 update 충돌을 줄일 수 있다.
- DB 트랜잭션과 분리된 애플리케이션 레벨의 진입 제어 수단으로 사용할 수 있고, 좌석/공연/사용자/쿠폰 같은 도메인 자원 단위로 락 기준을 유연하게 잡을 수 있다.

##### 단점

- Redis 락의 획득/해제와 DB 변경은 하나의 트랜잭션으로 묶이지 않기 때문에, 둘 사이의 불일치 가능성을 별도로 다뤄야 한다.(ex. ttl 만료, 시스템 다운)
- Redis 장애, 네트워크 지연, split-brain 상황을 고려해야 한다.
- 특정 공연 전체를 하나의 락 키로 묶으면 Redis 락 자체가 단일 병목 지점이 될 수 있다.
- 추가적인 인프라와 관리 비용이 필요하다.

##### 적합한 상황

- DB 락 경합을 줄이고 싶은 경우
- 여러 애플리케이션 서버나 worker가 같은 업무 로직을 동시에 실행할 수 있어, 프로세스 내부 락만으로는 동시성을 제어할 수 없는 경우
- 좌석 점유, 쿠폰 발급, 주문 확정처럼 동시에 실행되면 안 되는 업무 로직 단위로 락 기준을 명확히 잡을 수 있는 경우

##### 이 시나리오에서의 판단

- 단독 해법으로 쓰기보다는 DB의 atomic update, unique constraint와 함께 써야 한다.
- 특히 Redis 락을 사용하더라도 최종 판매 수량이 1만 석을 넘지 않는지는 DB 조건부 업데이트로 한 번 더 보장해야 한다.

#### 3.3 Optimistic Lock, 낙관적 락

##### 개요

- 충돌이 드물다고 가정하고 먼저 락을 잡지 않은 채 읽은 뒤, 수정 시점에 version이 그대로인지 확인하는 방식이다.
- 보통 row에 `version` 컬럼을 두고 update 조건에 포함한다.
- 예: `UPDATE inventory SET remaining_count = remaining_count - 1, version = version + 1 WHERE event_id = ? AND version = ? AND remaining_count > 0`

##### 장점

- 락을 선점하지 않으므로 평상시 처리량이 좋다.
- DB 락 대기 시간이 짧고 데드락 위험이 낮다.
- 충돌이 적은 도메인에서는 구현과 운영이 비교적 효율적이다.
- 변경 충돌을 명시적으로 감지할 수 있다.

##### 단점

- 티켓 오픈처럼 같은 재고에 요청이 집중되는 상황에서는 충돌이 매우 많아진다.
- 실패한 요청이 재시도되면서 DB 부하가 더 커질 수 있다.
- 재시도 정책, 최대 재시도 횟수, 사용자 응답 전략을 별도로 설계해야 한다.
- hot row에 대한 경쟁이 심하면 성공보다 실패 update가 많아질 수 있다.

##### 적합한 상황

- 충돌 가능성이 낮고 읽기 비중이 높은 시스템
- 같은 자원에 동시 수정이 많이 몰리지 않는 경우
- 재시도 비용이 낮고, 사용자에게 잠시 후 재시도를 안내해도 괜찮은 경우
- 재고가 여러 상품이나 여러 좌석 그룹에 넓게 분산되어 있는 경우

##### 이 시나리오에서의 판단

- 오픈 직후 특정 공연 재고에 요청이 집중되므로 단독 해법으로는 부적합하다.
- 다만 좌석 그룹이 충분히 분산되어 있거나, 대기열로 진입량을 강하게 제한한 뒤라면 사용할 수 있다.

#### 3.4 Single Writer / Inventory Service

##### 개요

- 재고 변경 권한을 하나의 서비스 또는 하나의 순차 처리 흐름에 집중시키는 방식이다.
- 여러 서버가 직접 DB 재고를 수정하지 않고, 재고 서비스가 요청을 받아 순서대로 처리한다.
- 구현 형태는 단일 inventory service, actor model, Kafka partition 단위 소비자, command queue 기반 worker 등이 될 수 있다.

##### 장점

- 같은 재고에 대한 변경을 한 줄로 세울 수 있어 정합성 모델이 명확하다.
- DB 락 경합을 애플리케이션/큐 레벨의 순차 처리로 줄일 수 있다.
- 트래픽 폭주를 queue가 흡수하므로 핵심 처리 구간을 보호하기 좋다.
- 이벤트별, 공연별, 좌석 구역별 partition을 나누면 순서 보장과 확장성을 함께 얻을 수 있다.
- 재고 변경 로직이 한 서비스에 모여 감사 로그, 모니터링, 복구 정책을 관리하기 쉽다.

##### 단점

- 구조가 복잡해진다. 큐, consumer, 재처리, 중복 메시지, 순서 보장, 장애 복구를 설계해야 한다.
- 비동기 처리이므로 사용자가 즉시 확정 결과를 받지 못할 수 있다.
- 특정 인기 공연이 하나의 partition에 몰리면 single writer 자체가 병목이 될 수 있다.
- 메시지는 최소 한 번 전달되는 경우가 많으므로 idempotency 처리가 필수다.
- 재고 서비스가 장애 나면 해당 재고 처리가 지연된다.

##### 적합한 상황

- 대규모 트래픽을 직접 DB 트랜잭션으로 받기 어려운 경우
- 재고 변경 순서를 명확히 보장하고 싶은 경우
- 티켓 예매, 한정판 판매, 쿠폰 발급처럼 선착순 처리와 트래픽 흡수가 모두 중요한 경우
- 사용자에게 대기, 처리 중, 확정/실패 같은 상태 기반 UX를 제공할 수 있는 경우

##### 이 시나리오에서의 판단

- 10만 명이 동시에 몰리는 상황에서는 가장 현실적인 상위 아키텍처 후보이다.
- 단, single writer만으로 끝내면 안 되고 DB atomic update, unique constraint, idempotency key를 함께 둬야 한다.

### 4. 비교 요약

| 방식 | 핵심 아이디어 | 장점 | 단점 | 적합한 상황 |
| --- | --- | --- | --- | --- |
| Pessimistic Lock | 먼저 DB row를 잠그고 처리 | 정합성 강함, 트랜잭션 모델 단순 | 락 대기, DB 병목, 데드락 위험 | 트래픽이 제한적이거나 좌석 단위 경합이 낮은 경우 |
| 분산 락 | Redis 등으로 애플리케이션 간 락 공유 | DB 진입 전 경합 감소, 분산 서버 대응 | TTL/장애/해제 안정성 복잡 | 짧은 임계 구역, 락 키를 잘게 나눌 수 있는 경우 |
| Atomic Update | 조건부 update 한 문장으로 차감 | 단순하고 강한 최종 방어선, 초과 판매 방지 | hot row 병목, 좌석 배정/결제 문제는 별도 | 수량 재고 차감, 최종 판매 수량 보장 |
| Optimistic Lock | version으로 충돌 감지 | 평상시 처리량 좋음, 락 대기 적음 | 충돌 폭증 시 재시도 부하 큼 | 충돌이 낮거나 진입량이 제한된 경우 |
| Single Writer / Inventory Service | 재고 변경을 한 처리 흐름으로 직렬화 | 순서 보장, 트래픽 흡수, 정합성 모델 명확 | 비동기 복잡도, consumer 병목, 운영 부담 | 대규모 선착순 판매, 대기열/큐 기반 처리 |

### 5. 최종 선택 방향

#### 5.1 선택할 방식

- 선택한 아키텍처: 대기열 + Single Writer / Inventory Service + DB Atomic Update + DB 제약조건
- 보조 수단: idempotency key, 좌석 unique constraint, 주문/좌석 상태 머신, TTL 기반 임시 점유, 보상 처리
- 분산 락은 필요한 구간에 제한적으로 사용하고, 최종 정합성 보장의 핵심으로 두지는 않는다.

#### 5.2 선택 이유

- 정확성 측면:
  - 재고 변경을 inventory service에서 순차 처리하면 같은 재고에 대한 경쟁 조건을 크게 줄일 수 있다.
  - DB atomic update와 unique constraint를 마지막 방어선으로 두면 애플리케이션 버그나 중복 메시지가 있어도 초과 판매를 막을 수 있다.
- 성능 측면:
  - 10만 명의 요청을 한꺼번에 DB 트랜잭션으로 보내지 않고, 대기열과 queue로 흡수한다.
  - inventory service는 시스템이 감당 가능한 속도로 재고 차감 명령을 처리한다.
- 장애 대응 측면:
  - 메시지와 주문 상태를 남기면 중간 실패를 재처리할 수 있다.
  - 결제 실패, 확정 실패, 타임아웃은 상태 머신과 보상 트랜잭션으로 복구한다.
- 운영 복잡도 측면:
  - 단순 DB 락보다 구조는 복잡하지만, 10만 명 동시 접속이라는 조건에서는 필요한 복잡도라고 본다.
  - 재고 변경 로직을 한 서비스에 모으면 모니터링과 장애 대응 지점을 명확히 할 수 있다.

#### 5.3 남는 Trade-off

- 비동기 처리로 인해 사용자가 즉시 확정 결과를 받지 못할 수 있다.
  - 보완: 대기 순번, 처리 중 상태, 예상 대기 시간, 확정/실패 알림을 제공한다.
- 특정 인기 공연이 하나의 writer나 partition에 몰리면 병목이 될 수 있다.
  - 보완: 공연, 좌석 구역, 좌석 블록 단위로 partition을 나누되, 같은 좌석/재고의 순서는 유지한다.
- 메시지 중복 처리 가능성이 있다.
  - 보완: command id, order id, idempotency key를 저장하고 이미 처리된 요청은 재처리하지 않는다.
- 결제와 좌석 확정을 완전한 하나의 분산 트랜잭션으로 묶기 어렵다.
  - 보완: 주문 상태 전이, 임시 점유 TTL, 결제 취소, 보상 트랜잭션, 재처리 worker로 최종 일관성을 맞춘다.

### 6. 결론

#### 6.1 핵심 요약

- 이 문제의 본질:
  - "서버를 얼마나 많이 띄우는가"보다 "같은 재고에 대한 변경을 어떻게 안전하게 직렬화하거나 원자화할 것인가"가 핵심이다.
  - 동시에 결제, 주문, 좌석 상태가 실패 상황에서도 일관된 최종 상태로 수렴해야 한다.
- 가장 중요한 설계 원칙:
  - 핵심 재고 차감 구간은 짧고 명확하게 유지한다.
  - 외부 결제 호출을 DB 락 안에 오래 묶지 않는다.
  - 애플리케이션 제어와 DB 제약조건을 함께 둔다.
  - 실패와 재시도를 정상 흐름의 일부로 보고 idempotency와 보상 처리를 설계한다.

#### 6.2 최종 답변 방향

"정확히 1만 명에게만 판매"를 보장하기 위해서는 단순히 Redis Lock이나 DB Lock 하나를 선택하는 것보다, 트래픽을 대기열로 흡수하고 재고 변경은 Single Writer / Inventory Service가 순차적으로 처리하며, 최종 차감은 DB Atomic Update와 unique constraint로 방어하는 조합이 적합하다.

즉, 대규모 티켓 예매 시스템에서는 다음 조합이 가장 현실적이다.

1. 대기열로 구매 진입량 제한
2. inventory service가 재고 변경 명령을 순차 처리
3. DB 조건부 atomic update로 1만 석 초과 차감 방지
4. 좌석 단위 unique constraint로 중복 배정 방지
5. idempotency key로 중복 요청 방지
6. 주문/좌석 상태 머신과 보상 처리로 결제 실패와 장애 복구

이렇게 설계하면 순간 트래픽은 queue와 대기열이 흡수하고, 재고 정합성은 inventory service와 DB 제약조건이 함께 보장하며, 실패 상황은 상태 전이와 보상 로직으로 복구할 수 있다.
