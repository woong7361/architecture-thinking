# skeleton-agent 설계 문서 (v0) — 레이어 단위 골격 생성 + 경계 게이트 파이프라인

> 상태: **가설(밑그림)**. 확정 스펙 아님. 구현·실행이 검증하며, 뒤 단계에서 앞 단계로 되돌아오는 것을
> 막지 않는다. 이름 `skeleton-agent`도 잠정이다.

> **공용 스킬 원칙:** 이 스킬은 특정 코드베이스·과제에 묶이지 않는 **범용 레이어 생성 파이프라인**이다.
> 스킬 자산인 프롬프트·스키마·게이트·runner는 **target 무관**을 유지한다. 레이어 목록, 경로 화이트리스트,
> 동결 계약, 게이트 명령 같은 대상별 데이터는 스킬에 넣지 않고 **run 입력(JSON)** 으로 공급한다.
> 이 문서에서 티켓 예매 프로젝트를 드는 곳(§9)은 전부 "적용 예시"이며, 지워도 §0~§8의 규칙은 그대로 성립한다.

---

## 0. 한 장 요약

AI에게 "앱 만들어줘"라고 통째로 시키지 않는다. **아키텍처의 동심원을 안쪽부터 한 겹씩** 시키고,
겹이 끝날 때마다 **기계가 먼저 채점**한다. 채점을 통과한 겹만 다음 겹으로 넘어간다.

```
[겹 하나 지시] → [AI가 그 겹 파일만 생성] → [게이트 4단 자동 채점] → 합격이면 다음 겹 / 불합격이면 그 겹만 재시도
```

이게 가능한 이유는 **시스템을 한 번도 불완전하게 두지 않기 때문**이다. 아직 만들지 않은 자리는 대역으로
채워 두고, 겹이 하나 완성될 때마다 그 자리의 대역을 실물로 바꾼다. 그래서 **매 단계 같은 인수테스트가 돈다**(§5).

기존 두 하네스와의 관계는 이렇다.

| 하네스 | 무엇을 만드나 | 무엇으로 판정하나 |
|---|---|---|
| `generate-test-v1` | 테스트를 만든다 | 루브릭 + 스키마 |
| `refactor-agent` | 기존 코드를 옮긴다 | **동결된 인수테스트가 여전히 GREEN인가** |
| **`skeleton-agent`(이 문서)** | **없던 코드를 층별로 만든다** | **인수테스트가 새로 GREEN이 되는가 + 경계를 안 넘었는가** |

`refactor-agent`가 "행위를 안 깨뜨렸나"를 물었다면, 이 파이프라인은 **"경계를 안 넘고 걷게 만들었나"** 를 묻는다.

## 1. 이 파이프라인이 무엇인가 (범위)

**경계 검증된 레이어 구현 생성기**다. 코드를 실제로 만든다 — 각 레이어마다 Implement가 파일 매니페스트를
내고, Gate가 격리된 worktree에 적용해 컴파일·경계 규칙·인수테스트를 돌린다.

핵심 구분은 **무엇이 증명됐느냐**다. **GREEN ≠ 좋은 코드**:

- 게이트 GREEN이 증명하는 것 = **그 층까지 관통한다 + 의존 방향을 안 어겼다.** 딱 여기까지다.
- 증명하지 않는 것 = **네이밍·응집도·예외 설계가 적절한가.** 그건 사람의 수용/기각 판단 몫이다.
- 그래서 파이프라인은 코드를 만들지만 **"이게 머지할 코드"라고 결정하지 않는다.** 층별 수용/기각과 그 이유를
  사람이 로그로 남기는 것까지가 한 사이클이다.

### 왜 층으로 쪼개나 (통짜 생성과의 비교)

| | 통짜 생성 | 레이어 생성 |
|---|---|---|
| 실패했을 때 | 어디가 원인인지 모른다. 전부 버린다 | 그 층만 버리고 재시도한다 |
| 게이트 | 마지막에 한 번 | 층마다, 그리고 **뒤로 갈수록 커진다** |
| 경계 위반 | 결과물에 섞여 들어가 발견이 늦다 | 위반한 층에서 즉시 빨간불 |
| 컨텍스트 | 전부를 한 번에 줘야 한다 | 그 층이 알아야 할 계약만 준다 |

마지막 줄이 가장 중요하다. **AI에게 안 보여준 것은 어길 수 없다.** 바깥 층 구현을 안 보여주면 안쪽 층이
바깥을 참조할 방법 자체가 없다. 레이어 분할은 프롬프트 위생 장치이기도 하다.

## 2. 재사용 vs 신규

`refactor-agent`의 골격을 **형제 스킬**로 가져와 부품을 교체한다. 새 mode가 아닌 이유는 §11.

| 구성요소 | 재사용 / 신규 | 근거 |
|---|---|---|
| LLM 클라이언트 포트 (`stages/scripts/llm_client.py`) | **재사용(import)** | 공급자 교체 축이 이미 둘 |
| 파일 매니페스트 스키마 + 경로 이탈 차단(`_sanitize`) | **재사용** | 생성 코드를 worktree에 떨구는 계약이 동일 |
| worktree 격리 적용 + 빌드 실행 (`behavior_gate.py`) | **재사용 후 개조** | 뼈대 동일. **판정 대상이 "회귀 없음"에서 "새 GREEN"으로 바뀜** |
| `runs/<id>/` 로그 레이아웃, `.raw.txt` 파싱 실패 보존 | **재사용** | 검수 로그가 곧 제출물 |
| 스키마 검증 + 역할경계 금지필드 (`validate.py`) | **재사용** | 생성기가 자기 점수를 못 매기게 하는 배관 |
| refine 루프 (`contract_error → 재시도 → max_iter`) | **재사용** | 실패 라우팅 구조 동일 |
| **구성·레이어 입력 스키마** (`configurations[]`, `layers[]`) | **신규** | 이 파이프라인의 정체성. 판정 단위가 구성이다(§5) |
| **경로 규약 게이트** (화이트리스트 밖 / 동결 경로 수정 = 즉시 기각) | **신규** | 경계 위반의 **1차 방어이자 가장 싼 검출기** |
| **경계 규칙 게이트** (의존 방향 정적 검사) | **신규** | 사람 눈이 아니라 테스트가 판정하게 만드는 장치 |
| `implement_layer.md` (계약 + 레이어 지시 → 파일 매니페스트) | **신규** | 레이어 하나의 구현 책임 |
| **레이어별 게이트 셀렉터** (층마다 다른 테스트를 돌림) | **신규** | 게이트가 층마다 커져야 함 |
| Diagnose / Critique / Eval 3단계 | **미채택** | §11 |
| 사람 검수 로그 (`review.md` 수용/기각 + 이유) | **신규(수기)** | 자동화 대상 아님 — 판단은 사람 몫 |

> **정직한 재사용 방식:** `llm_client`·매니페스트 유틸처럼 진짜 도메인-불가지론인 조각은 import한다.
> `behavior_gate.py`는 판정 의미가 달라 **복사 후 개조**하고 출처를 주석으로 남긴다.
> 공유 코어 추출은 **소비자가 3개째 생길 때까지 보류**한다.

## 3. 협력 흐름

유스케이스: *"설계는 정해졌다. 이 골격을 AI에게 층별로 만들게 하고, 층마다 자동으로 판정하고 싶다."*

```
[사람] --레이어 계획 + 동결 계약 + baseline--> [Orchestrator]

  각 레이어 L에 대해 순서대로:
    Orchestrator --"L의 파일만 만들어라"--------> [Implement]  → 파일 매니페스트
    Orchestrator --"L을 채점하라"--------------> [Gate] (LLM 없음, 결정적)
         ① 경로 규약  ② 컴파일  ③ 경계 규칙  ④ 인수테스트
         빨간불 → 실패 사유만 붙여 [Implement] 재시도 (max_iter까지)
         초록불 ↓
    [사람] --수용 / 기각 + 이유--------------> review 로그
         기각 → 지시를 고쳐 재시도 (프롬프트·계약을 고치는 것이지 결과물을 손보는 게 아니다)
         수용 → 다음 레이어의 baseline이 된다
```

**뒤 레이어는 앞 레이어의 수용된 결과 위에 쌓인다.** 그래서 3층이 초록불이면 1·2층도 여전히 초록불이라는
뜻이고, 마지막 층의 GREEN이 곧 골격 전체의 관통 증거가 된다.

## 4. 책임 배분

| 객체 | 책임 (변경 이유 하나) | 왜 이 객체인가 |
|---|---|---|
| **사람(Plan)** | 레이어를 정의한다 — 경로·계약·게이트. 그리고 최종 수용/기각 | 아키텍처 의도를 아는 유일 지점. **AI가 정하면 채점 기준을 피고인이 쓰는 셈** |
| **Implement** | 지정된 레이어의 파일 매니페스트만 만든다. 다른 층·테스트는 안 건드림 | 계약과 요구사항을 코드로 옮기는 지점 |
| **Gate** | 사실만 판정한다 — 경로·컴파일·경계·테스트. LLM 없음 | 결정적이어야 하는 유일 지점. 여기 LLM이 끼면 "설득당하는 심판"이 된다 |
| **Orchestrator** | 레이어 순회·재시도·lineage·로그를 조율한다 | 조립 책임. 맨 마지막에 정의 |

**Implement는 자기 코드를 채점하지 않고, Gate는 코드를 고치지 않는다.** 생성과 평가의 분리는
`generate-test` 골격에서 이어받는 불변식이다.

## 5. 판정의 단위 — 층이 아니라 구성

### 난점

**인수테스트는 완전한 시스템을 요구한다. 그런데 층별 생성은 필연적으로 불완전한 중간 상태를 만든다.**
"매 단계 인수테스트로 판정한다"를 곧이곧대로 하려면 이 모순을 먼저 풀어야 한다.

불완전한 상태를 억지로 돌리려 드는 순간 특수 장치가 층마다 늘어나고, 판정 장치가 판정 대상보다 커진다.
방향을 뒤집는다.

### 해법 — 시스템을 한 번도 불완전하게 두지 않는다

포트와 어댑터 구조에서 시스템이 도는 조건은 **모든 포트 자리가 채워져 있을 것** 하나다.
채운 것이 실물인지 대역인지는 시스템이 도는지 여부를 결정하지 않는다. 그러므로

> **아직 만들지 않은 자리는 대역으로 채워 시스템을 항상 완전하게 유지한다.**
> **층 하나가 완성될 때마다 그 자리의 대역을 실물로 승격시킨다.**
> **게이트 = 같은 인수 시나리오가 새 구성에서도 GREEN인가.**

판정 단위는 층이 아니라 **구성**이다. 시나리오는 처음부터 끝까지 한 글자도 바뀌지 않고,
단계마다 바뀌는 것은 **각 자리에 무엇이 꽂혀 있는가**뿐이다.

### 슬롯과 구성

| 용어 | 뜻 |
|---|---|
| **슬롯(slot)** | 실물과 대역이 갈아끼워지는 자리. 대개 포트 하나 또는 조립 지점 하나 |
| **대역(double)** | 그 슬롯을 채우는 심판 쪽 구현. 동결 경로에 산다 |
| **실물(real)** | 파이프라인이 생성한 구현 |
| **구성(configuration)** | 슬롯마다 실물/대역 중 무엇이 꽂혔는지의 조합 + 그 조합을 돌리는 심판 |

대역은 새로 발명하는 물건이 아니다. **테스트를 위해 이미 만들어 둔 것들이 대부분 그대로 대역이다.**
인메모리 저장소, 통제 가능한 외부 연동 더블, 심판이 진입점을 직접 호출하는 방식, 심판이 직접 조립하는 코드가
전부 각 슬롯의 대역이다. 새로 필요한 대역만 추가하면 된다.

### 판정에는 두 종류가 있다

| | **전환 판정 (transition)** | **교체 판정 (swap)** |
|---|---|---|
| 대상 | **행위를 소유한 층** | **기술 세부를 담당한 층** |
| 대역으로 대체 | ❌ 불가. 대역을 두면 심판이 대역을 시험하게 된다 | ✅ 가능 |
| 판정 | **RED → GREEN** | **GREEN 유지** |
| 뜻 | 없던 행위가 생겼다 | 안쪽이 바깥 기술에 묶여 있지 않다 |

**교체 판정이 곧 구조의 증명이다.** 대역을 실물로 바꿨는데 같은 시나리오가 그대로 통과한다면,
안쪽이 그 기술을 모른다는 뜻이다.

이 구분은 §8의 출발선 결정에도 그대로 쓰인다. 행위를 소유한 층은 전환 판정을 받을 수 있으므로 생성 대상
후보이고, 그보다 안쪽은 계약이라 남긴다.

### "대역이 초록불을 만들어 준 것 아닌가"

정당한 의심이다. 층 게이트의 초록불은 "시스템이 동작한다"가 아니라 **"이 구성에서 동작한다"** 이다.
대역이 많이 남은 층일수록 그 초록불이 덮는 범위는 좁다. 두 가지로 답한다.

**첫째, 대역의 종류를 구분한다.**

| 대역의 종류 | 무엇을 대신하나 | 취급 |
|---|---|---|
| **배선 대역** | 객체를 포트 자리에 꽂아주는 조립만. 판정 대상의 행위를 흉내내지 않는다 | 초록불을 왜곡하지 않는다 |
| **행위 대역** | 실제 동작을 흉내낸다 | **반드시 교체 판정으로 실물과 대조**해야 한다 |

행위 대역이 마지막 구성까지 남는 슬롯은 인수테스트가 검증하지 못한 **공백**이므로 명시한다.
이 구분을 안 하면 "대역이 있으니 못 믿는다"와 "다 초록불이니 다 됐다"가 둘 다 틀린 채로 굳는다.

**둘째, 최종 구성 심판을 매 층 함께 돌린다 — 판정에는 쓰지 않고 기록만 한다.**

최종 구성은 대역이 남지 않은 구성이라 **속지 않는다.** 층이 진행될수록 이 심판의 실패 지점이 뒤로 밀리고,
그 이동이 곧 진행도다. 층 게이트가 "이 층이 제 몫을 했나"를 판정한다면, 이 관측은
**"전체가 얼마나 남았나"** 를 보여준다. 둘은 서로를 대체하지 않는다.

### 왜 진행도만으로 판정하지 않는가

"각 단계에서 어디까지 갔는지를 보면 되지 않나"는 자연스러운 대안이고, 실제로 대역이 필요 없어진다.
그럼에도 판정의 기준으로 삼지 않는 이유는 셋이다.

- **실패의 형태는 계약으로 삼기에 불안정하다.** 어디서 막혔는지 판정하려면 예외 타입이나 메시지를 매칭해야
  하는데, 그것은 프레임워크의 구현 세부다. 대역보다 더 잘 깨지는 계약이 된다.
- **인수테스트는 이분법이다.** "몇 단계까지 갔다"를 판정하려면 로그 해석이 필요하고,
  결정론적 게이트가 휴리스틱으로 내려앉는다.
- **그 층의 결함을 그 층에서 잡지 못한다.** 안쪽 층의 버그를 최종 구성이 켜질 때까지 모른 채 지나가면,
  발견 시점에 원인 층을 다시 추적해야 한다. 층별 검수의 존재 이유가 사라진다.

그래서 **판정은 구성으로, 진행도는 관측으로** 나눈다.

### 레이어 정의 — 여섯 가지

| 항목 | 뜻 | 없으면 생기는 일 |
|---|---|---|
| `allowed_paths` | 이 층이 **쓸 수 있는** 경로 화이트리스트 | 아무 데나 파일이 생기고, 경계 위반이 결과물에 섞인다 |
| `frozen_contracts` | 이 층이 **읽기만 하는** 계약 | 계약을 편한 대로 바꿔 하위 호환을 깬다 |
| `requirements` | 이 층이 **만족시켜야 할 것** | 무엇을 만들지 모른다 |
| `promotes` | 이 층이 **실물로 승격시키는 슬롯** | 층이 무엇을 채우는 일인지 불명확해진다 |
| `verdict` | `transition` 인가 `swap` 인가 | 초록불의 **의미**를 모른다. 원래 초록이던 걸 초록이라 우길 수 있다 |
| `gate` | 판정에 쓸 **구성** | "됐다"의 기준이 사람 기분이 된다 |

`verdict`가 있어야 게이트 결과를 해석할 수 있다. 전환 판정 층은 **직전 구성에서 RED였음**을 함께 확인해야
초록불이 의미를 갖는다. 처음부터 초록이면 그 층은 아무것도 하지 않은 것이다.

### 층 순서 규칙

1. **안쪽부터 바깥쪽.** 바깥 층은 안쪽 계약을 참조해야 만들 수 있고 안쪽은 바깥을 몰라도 된다.
   반대로 하면 참조할 계약이 없어 스스로 지어내고, 그 지어낸 계약이 곧 경계 위반이 된다.
2. **구성의 대역은 단조 감소한다.** 층이 진행될수록 대역이 하나씩 줄고 늘지 않는다.
   마지막 구성에서 대역이 남아 있다면, 그 슬롯은 인수테스트가 검증하지 못한 공백이므로 명시한다.
3. **의존 방향이 허락하는 범위에서 게이트가 싼 층을 앞에 둔다.** 구성마다 실행 비용이 다르다.
   싼 구성을 앞에 둘수록 파이프라인 자체의 결함을 싸게 뽑아낸다.

## 6. 게이트 4단 — 무엇이 어떤 위반을 잡나

순서가 곧 비용 순이다. **싼 검출기를 먼저 돌려 비싼 실행을 아낀다.**

| 단 | 검사 | 잡는 위반 | 비용 |
|---|---|---|---|
| ① 경로 규약 | 매니페스트 경로가 `allowed_paths` 안인가, 동결 경로를 안 건드렸나 | **"안쪽 층 파일을 고쳐서 문제를 풀려는 시도"** — 계약 변경, 심판 매수 | 밀리초 |
| ② 컴파일 | 빌드가 되나 | 계약 시그니처 오해, 존재하지 않는 타입 참조 | 초 |
| ③ 경계 규칙 | 정적 의존 방향 검사 | **"경로는 지켰지만 안쪽이 바깥을 import"** — 의존 역전 위반, 프레임워크 침투 | 초 |
| ④ 인수테스트 | 그 층의 게이트 명령 | 경계는 지켰지만 **동작이 틀림** | 분 |

**①과 ③이 이 파이프라인의 핵심 신규 자산이다.** ④만 있으면 "돌아가기만 하면 통과"라서, 안쪽 층에
프레임워크를 끌어들이거나 계약을 바꿔치기해도 초록불이 나올 수 있다. ①과 ③이 그 구멍을 막는다.

### 왜 경계 검사를 사람 눈이 아니라 테스트로 하나

세 가지 이유다.

1. **재현 가능하다.** "이건 경계 위반 같다"는 의견이지만, 빨간불은 사실이다.
2. **AI에게 되먹일 수 있다.** 위반 메시지를 그대로 붙여 재시도시키면 다음 시도에서 고쳐 온다.
   사람의 감상은 프롬프트로 되먹이기 어렵다.
3. **검수 로그의 신뢰도가 올라간다.** "AI가 경계를 어겼다"를 주장이 아니라 로그로 남긴다.

### 심판을 부패시키지 않기

**파이프라인은 테스트 코드를 절대 수정하지 않는다.** 테스트 경로는 전부 동결 경로다.
AI가 빨간불을 테스트를 고쳐 초록으로 만들 수 있으면 게이트는 장식이 된다.
이건 `refactor-agent`에서 이미 확립한 불변식이고 여기서도 그대로 유지한다.

### 심판이 결합해도 되는 것과 안 되는 것

> **심판은 구성이 확정한 것에는 결합해도 되고, 파이프라인이 생성할 것에는 결합하면 안 된다.**

**결합해도 되는 쪽.** 어떤 구성이 "이 슬롯은 실물 기술을 쓴다"고 정의했다면, **그 구성 전용 심판이
그 기술을 아는 것은 정상**이다. 그것이 구성의 정의이기 때문이다. 기술이 달라지면 **새 구성이 생기는 것**이지
기존 심판이 깨지는 것이 아니다. 따라서 **구성마다 심판이 다른 것은 결함이 아니라 설계**이며,
그 차이를 감추려고 추상화를 세울 이유가 없다. 슬롯을 채우는 기술이 하나뿐인데 인터페이스를 뽑는 것은
축이 없는 추상화이므로 과설계다. 두 번째 기술이 실제로 생길 때 승격한다.

**결합하면 안 되는 쪽.** 심판이 **파이프라인이 아직 만들지 않은 타입**을 참조하면, 언어에 따라
심판 자체가 빌드되지 않는다. 한 덩어리로 컴파일되는 언어에서는 심판 하나의 참조 실패가 멀쩡한 심판까지
전부 못 돌게 만든다. **게이트가 켜지지도 않는 상태**가 된다.

판정 기준: **출발선에서 심판이 빌드는 되고 실행만 실패하는가.**
빌드가 깨지면 그건 RED가 아니라 **게이트 고장**이다.

**계약이 심판에게 필요한 것을 안 열어주는 경우**가 있다. 상태 주입이 대표적이다. 계약은 안쪽이 필요로 하는
동작만 갖지, 심판이 원하는 임의 상태를 만들어주지 않는다. 이때는 한 단계 아래의 표현을 직접 쓰고,
그 표현의 이름을 `frozen_contracts`에 계약으로 올린다.
**맞혀야 할 표면을 숨기는 것은 시험이 아니라 함정**이므로, 남는 결합은 전부 공개한다.

### 게이트는 쓰기 전에 리허설한다

게이트를 만들었으면, **파이프라인을 붙이기 전에 손으로 쓴 정답 코드로 각 층을 리허설한다.**
층마다 두 방향을 모두 확인한다.

| 확인 | 기대 | 실패하면 |
|---|---|---|
| **음성** — 그 층이 없는 상태 | 🔴 RED | 게이트가 **공허하다.** 그 층이 뭘 하든 통과한다 |
| **양성** — 그 층의 정답을 넣은 상태 | 🟢 GREEN | 게이트가 **거짓 빨간불**을 낸다. AI 잘못으로 오인한다 |

리허설 없이 파이프라인을 돌리면 빨간불이 났을 때 **"생성물이 틀렸다"와 "게이트가 틀렸다"를 구분할 수 없다.**
그 구분이 안 되면 검수 로그 전체의 신빙성이 무너진다. 실측에서 이 리허설이 잡아낸 결함 두 가지를 남긴다.

- **거짓 빨간불 — 정적 검사 도구가 "대상 0개"를 실패로 취급.** 층을 하나씩 세우는 동안 아직 없는 층을
  겨냥한 규칙은 검사할 대상이 없다. 도구가 이를 실패로 보면, 위반이 아니라 **부재**가 빨간불이 된다.
  아직 없는 층은 위반할 수도 없으므로 통과가 옳다. 반대로 **항상 존재해야 하는 층**은 명시적 가드로
  비어 있지 않음을 확인해, 규칙이 조용히 공허해지는 것을 막는다.
- **공허한 초록불 — 심판이 "부재"와 "거부"를 구분하지 못함.** 프로토콜 경계에서 흔하다. 어댑터가 아예
  없을 때의 응답과 도메인이 거부했을 때의 응답이 같은 코드면, **어댑터가 없어도 그 시나리오가 통과한다.**
  둘을 가르는 관측 가능한 차이를 하나 더 단언해야 한다. 단, 그 차이는 **프로토콜 수준의 계약**으로 잡는다.
  응답 문구 같은 세부에 걸면 생성 대상이 맞춰야 할 표면이 불필요하게 좁아진다.

두 결함 모두 "당연히 그럴 것"이라고 넘긴 가정에서 나왔다. **게이트에 대해서는 당연한 것을 확인 없이 넘기지 않는다.**

### 대역은 심판 쪽 자산이다

대역은 동결 경로에 둔다. 파이프라인이 읽지도 고치지도 못한다.
읽을 수 있으면 그 층의 정답을 베끼고, 고칠 수 있으면 자기가 채워야 할 자리를 대역으로 남겨두고 통과한다.

AI에게는 **대역의 존재도 형태도 알리지 않는다.** 대신 그 슬롯이 만족해야 할 계약만 `frozen_contracts`로
전달한다. 슬롯을 실물로 채우는 층에게 필요한 정보는 계약뿐이고, 대역이 어떻게 생겼는지는 필요하지 않다.

## 7. 정보 차단 (커닝 방지)

이 파이프라인에서 정보 차단은 순환성 문제가 아니라 **평가 타당성** 문제다.
이미 손으로 쓴 정답 코드가 리포지터리에 있는 상황에서 AI에게 그걸 보여주면, 나오는 건 생성이 아니라 복사다.

- Implement는 **해당 층의 정답 구현을 못 본다.** baseline worktree에는 그 층이 아예 없다.
- Implement는 **바깥 층 구현도 못 본다.** 안쪽 층이 바깥을 참조할 재료 자체를 제거한다.
- Implement는 **테스트 본문을 못 본다.** 게이트가 요구하는 표면은 `frozen_contracts`로만 전달한다.
  테스트 본문을 주면 "테스트를 만족시키는 최소 코드"를 역산해 골격이 아니라 통과 트릭이 나온다.
- Implement는 **자기 게이트 결과를 미리 못 본다.** 실패 후 재시도에서만 실패 사유를 받는다.

## 8. 출발선 (baseline) — 어디까지 물릴 것인가

"층별로 다시 만든다"는 곧 **출발선을 뒤로 물린다**는 뜻이다. 출발선을 어디에 두느냐가 이 파이프라인의
가장 중요한 설계 결정이다. 원본 트리는 건드리지 않고, `refactor-agent`의 baseline_ref 패턴을 그대로 쓴다.

### 출발선 규칙

출발선에는 **두 가지가 반드시 남아야** 한다. 하나라도 빠지면 파이프라인이 성립하지 않는다.

| 남겨야 하는 것 | 없으면 생기는 일 |
|---|---|
| **심판** — 행위 명세와 그 글루 | 시험문제를 피고인이 출제한다. 통과가 아무것도 증명하지 못한다 |
| **계약** — 층에 지시할 때 참조시킬 인터페이스·타입 | 층별 지시가 불가능하다. 매 층이 앞 층의 생성물에 얹혀 오염이 누적되고, 한 층이 틀리면 전부 무너진다 |

**"층별 지시·검수"라는 요구 자체가 "안쪽은 고정되어 있다"를 전제한다.** 계약까지 생성 대상에 넣으면
그건 층별 생성이 아니라 이름만 층인 통짜 생성이다.

그 위에서 남길지 말지를 가르는 기준은 하나다 — **사람이 내린 설계 판단인가, 그 판단을 코드로 옮기는
기계적 작업인가.** 전자는 남기고 후자를 생성 대상으로 넘긴다. 설계 판단까지 생성시키면 앞 단계에서
사람이 내린 결정을 AI가 매 실행마다 다시 뒤집는다.

### 절차

```
0. 심판 정비: 심판이 생성 대상 타입을 참조하지 않게 정리한다 (§6)
              + 구성 진행표를 그려 **부족한 대역만** 심판 쪽 자산으로 채운다 (§5)
1. 경계 규칙 테스트 추가 → 현재 코드에서 초록불 확인          ← 규칙집이 먼저다
2. 가장 바깥 층의 새 심판 작성 → 빨간불 확인                  ← 판정자가 먼저다
3. 출발선 커밋/태그 생성: 생성 대상 층의 파일을 제거
   남는 것: 설계 판단 산출물 + 심판 전부 + 빌드 설정 + 컨벤션 문서
   확인: 이 상태에서 심판이 **빌드는 되고 실행만 실패**하는가
4. 파이프라인 실행: 각 층을 worktree에서 생성·채점
5. 수용된 매니페스트를 원본 트리에 반영하고, 손으로 쓴 기존 버전과 diff 비교
```

2번이 1번보다 뒤인 게 중요하다. **심판이 빨간불인 상태에서 시작해야 초록불이 의미를 갖는다.**
처음부터 초록불이면 AI가 아무것도 안 해도 통과한다.

3번의 확인 조건이 §6의 판정 기준이다. 빌드가 깨지면 출발선을 잘못 그은 것이니 0번으로 돌아간다.

5번의 diff 비교는 보너스가 아니라 **이 실험의 대조군**이다. 같은 계약·같은 게이트에서
사람과 AI가 무엇을 다르게 썼는지가 검수 로그의 근거가 된다.

### 출발선 결정

| 아웃바운드/인바운드 포트 | ✅ | **계약.** 층에 지시할 때 참조시킬 대상 |
| 도메인 모델 + 도메인 예외 | ✅ | **사람의 설계 판단.** 불변식을 어느 객체가 소유할지는 앞 단계에서 결정된 사안 |
| 유스케이스 구현 | ❌ **생성 대상** | 확정된 설계를 코드로 옮기는 작업. 협력 순서는 포트와 시나리오에서 도출 가능 |
| 아웃바운드 어댑터 · 조립 · 인바운드 어댑터 | ❌ **생성 대상** | 계약을 기술로 실현하는 작업 |

유스케이스를 생성 대상에 넣은 이유는 두 가지다. 첫째, 골격의 심장을 사람이 다 써두고 껍데기만
생성시키면 "골격을 AI가 만들었다"고 말하기 어렵다. 둘째, **이 층의 게이트는 컨테이너 없이 도는
가장 빠른 심판**이라 파이프라인 자체의 결함을 싸게 뽑아낼 수 있다.

도메인까지 물리지 않은 이유는 포트 시그니처가 도메인 타입을 참조하기 때문이다. 도메인을 생성시키면
계약이 함께 흔들려 층별 지시의 전제가 무너진다.

### 슬롯과 대역

이 대상에는 갈아끼워지는 자리가 다섯 개 있다. **대역은 대부분 이미 존재한다.**

| 슬롯 | 대역 | 지금 있나 | 실물을 만드는 층 |
|---|---|---|---|
| 인바운드 진입 | 심판이 인바운드 포트를 직접 호출 | ✅ 기존 스텝이 하는 방식 그 자체 | L3 |
| 유스케이스 | **없음 — 대역 불가** | — | L0 |
| 저장 | in-memory fake | ✅ `support/` | L1 |
| 결제 | 통제 가능한 더블 | ✅ `TestPaymentConfig` | 없음 |
| 조립 | 심판이 직접 조립 | ⚠️ in-memory 구성엔 있음. 스프링 구성용은 **신규** | L2 |

유스케이스만 대역이 불가능하다. 심판이 판정하려는 행위가 바로 그 자리에 있어서, 대역을 두면
심판이 대역을 시험하게 된다. 그래서 이 층만 전환 판정이고 나머지는 교체 판정이다.

신규로 필요한 대역은 **스프링 구성용 조립 하나**뿐이다.

### 구성 진행표

시나리오는 처음부터 끝까지 동일하다. 바뀌는 것은 각 슬롯에 무엇이 꽂혔는가뿐이다.

| 구성 | 인바운드 | 유스케이스 | 저장 | 결제 | 조립 | 판정 | 컨테이너 |
|---|---|---|---|---|---|---|---|
| **출발선** | 대역 | **없음** | 대역 | 대역 | 대역 | RED — 정상 | ❌ |
| **L0 후** | 대역 | **실물** | 대역 | 대역 | 대역 | **전환** RED→GREEN | ❌ |
| **L1 후** | 대역 | 실물 | **실물** | 대역 | 대역 | **교체** GREEN 유지 | ✅ |
| **L2 후** | 대역 | 실물 | 실물 | 대역 | **실물** | **교체** GREEN 유지 | ✅ |
| **L3 후** | **실물** | 실물 | 실물 | 대역 | 실물 | **교체** GREEN 유지 | ✅ |

- 마지막 행에서 대역이 사라진 자리들을 잇는 한 줄기가 walking skeleton이다.
- **결제만 끝까지 대역**이다. §5 순서 규칙 2에 따라 이 공백은 아래에 명시한다.
- L0 구성만 컨테이너가 필요 없다. §5 순서 규칙 3에 따라 이 층을 맨 앞에 둔다.

대역의 종류(§5)로 나누면 이렇다. **행위를 흉내내는 대역은 전부 교체 판정으로 실물과 대조되고,
마지막까지 남는 행위 대역은 결제 하나뿐이다.**

| 슬롯 | 대역의 종류 | 실물로 교체되나 |
|---|---|---|
| 인바운드 진입 | 행위 대역 — 프로토콜을 건너뛰고 포트를 직접 호출 | ✅ L3 |
| 저장 | 행위 대역 — 메모리로 흉내 | ✅ L1 |
| 조립 | **배선 대역** — 실물 객체를 꽂아주기만 한다 | ✅ L2 |
| 결제 | 행위 대역 | ❌ **끝까지 남음 = 공백** |

### 진행도 관측

층 게이트와 별개로, **매 층 최종 구성 심판을 함께 돌려 결과를 기록한다.** 판정에는 쓰지 않는다.
층이 진행될수록 실패 지점이 뒤로 밀리는 것이 관측되어야 한다.

| 시점 | 최종 구성 심판의 실패 지점 |
|---|---|
| 출발선 | 유스케이스 자리표시자가 예외를 던짐 |
| L0 후 | 저장 포트를 채울 어댑터가 없어 컨텍스트가 뜨지 않음 |
| L1 후 | 조립부가 없어 인바운드 포트 빈이 없음 |
| L2 후 | 엔드포인트가 없어 요청이 닿지 않음 |
| L3 후 | **GREEN** |

밀리지 않으면 그 층은 최종 구성에 아무 기여도 하지 않았다는 신호다. 층 게이트가 초록불이어도 그렇다.

### 레이어 계획

| 층 | `allowed_paths` | `frozen_contracts` | `promotes` | `verdict` | `gate` |
|---|---|---|---|---|---|
| **L0** | `core/application/**` | 인바운드·아웃바운드 포트 전부, 도메인 공개 API | 유스케이스 | `transition` | L0 구성 |
| **L1** | `adapter/out/**` | 아웃바운드 포트, 도메인 재구성 진입점, **저장 스키마 이름** | 저장 | `swap` | L1 구성 |
| **L2** | `config/**` | 인바운드 포트, L1 산출물 | 조립 | `swap` | L2 구성 |
| **L3** | `adapter/in/**` | 인바운드 포트, 도메인 예외 목록, HTTP 계약 | 인바운드 진입 | `swap` | L3 구성 |

동결 경로는 모든 층에서 동일하다: `core/domain/**`, `core/port/**`, `src/test/**`, `pom.xml`, `resources/**`.

`resources/**` 가 동결인 이유는 리허설에서 드러났다. 저장 스키마 생성 설정이 거기 있어 **L1 구성부터
필요하다.** 조립 층이 만들 물건이 아니라 출발선이 갖고 있어야 할 인프라 설정이다.
"조립"이라는 이름만 보고 설정 파일을 함께 묶으면 앞 층이 통과할 수 없게 된다.
**층이 끝나면 그 층의 `allowed_paths`가 동결 경로에 합류한다** — 뒤 층이 앞 층을 고쳐 문제를 회피하지 못하게 한다.

L2가 특히 명확하다. L1과 **심판도 같고 시나리오도 같고, 조립 슬롯만 대역에서 실물로 바뀐다.**
그 하나의 차이로 통과하면, 생성된 조립부가 스스로 런타임을 세운다는 뜻이다.

### 남는 공백 (정직하게)

결제 슬롯은 마지막 구성까지 대역이다. 외부 연동을 인수테스트에서 실제로 호출하지 않기 때문이다.
따라서 **결제 어댑터는 ④ 인수테스트 게이트의 검증을 받지 않는다.** ②·③까지만 게이트되고,
실제 동작 확인은 컨테이너 기동 후 수동 스모크로 남는다. 이 사실을 검수 로그에 명시한다.

### 심판 정비 내역 (§8 절차 0번)

| 구성의 심판 | 현재 | 정비 후 | 이유 |
|---|---|---|---|
| L0 구성 | 포트와 도메인만 참조 | **그대로** | 이미 생성 대상 타입에 결합돼 있지 않다 |
| L1·L2 구성 | 영속 어댑터 타입을 직접 호출해 시딩·검증 | **저장 스키마로 직접 시딩·검증** | 출발선에서 빌드돼야 한다(§6) |
| L3 구성 | 없음 | 신규 작성. HTTP 응답 + 저장 스키마로만 검증 | 처음부터 생성 대상 타입에 결합시키지 않는다 |

정비로 바뀌는 것은 **심판이 상태를 다루는 수단**뿐이다. 시나리오 문장도, 판정 결과도 바뀌지 않는다.

계약이 심판에게 상태 주입을 열어주지 않는 문제가 여기서 실제로 나타난다. 저장 포트의 쓰기 계약은
"아직 예약되지 않은 것만 예약"이라는 도메인 동작이라, "이미 예약된 상태"를 심판이 만들 수 없다.
그래서 §6의 규칙대로 한 단계 아래인 저장 스키마를 직접 쓰고, 테이블·컬럼 이름을 계약으로 올린다.
저장 기술이 달라지면 이 심판이 깨지는 것이 아니라 **새 구성이 생긴다.**

## 10. runs/ 로그 구조 & 제출물 매핑

```
runs/<run_id>/
  input.json                 레이어 계획 스냅샷
  L0/
    attempt_01/
      implement.json         AI가 낸 매니페스트
      gate.json              4단 판정 결과 + 실패 사유
      progress.json          최종 구성 심판의 실패 지점(판정 아님, 관측)
      files/                 적용된 파일 실물
    attempt_02/ ...
    review.md                사람의 수용/기각 + 이유          ← 수기
  L1/ ... L2/ ... L3/ ...
  final.json                 층별 시도 횟수, 최종 판정, 총 소요
  diff-vs-handwritten.md     대조군 비교                      ← 수기
```

과제 제출물과의 대응:

| 제출물 | 여기서 나오는 것 |
|---|---|
| walking skeleton 코드 + 인수테스트 초록불 | L3 게이트 GREEN + CI 로그 |
| 파이프라인(프롬프트·컨텍스트·agent.md) | 이 스킬 디렉터리 + 프로젝트 컨벤션 문서 |
| Layer 단위 검수 로그 | `runs/<id>/L*/review.md` + `gate.json` |
| 경계 위반을 잡아낸 사례 | `gate.json`의 ①·③ 단 실패 기록 |

**위반 사례가 안 나올 수도 있다.** 그때는 지어내지 않고, 적용한 경계 점검과 AI가 지킬 수 있었던 이유를
쓴다. 화이트리스트·동결 계약·정보 차단이 애초에 위반 가능성을 좁혔다면 그것 자체가 결과다.

## 11. 설계 결정 — 왜 이렇게 안 했나

- **왜 Diagnose 단계가 없나.** 설계는 이미 C-3에서 사람이 확정했다. AI에게 다시 진단시키면
  확정된 설계를 흔들 뿐이다. 이 파이프라인의 입력은 "무엇이 잘못됐나"가 아니라 "무엇을 만들라"다.
- **왜 Critique/Eval 루브릭이 없나.** 골격의 품질 축은 아직 축이 하나뿐이다 — **관통하느냐.**
  네이밍·응집도 채점기를 지금 만드는 건 과설계다. 층별 사람 검수 로그가 그 자리를 대신하고,
  로그가 "매번 같은 종류를 지적하고 있다"를 실증하면 그때 루브릭으로 승격한다.
- **왜 새 mode가 아니라 형제 스킬인가.** `refactor-agent`의 게이트는 "회귀 없음"을, 이 파이프라인의
  게이트는 "새 GREEN"을 판정한다. 판정 의미가 반대라 한 스테이지로 합치면 분기로 오염된다.
- **왜 층을 더 잘게 안 쪼개나.** 층의 최소 단위는 **독립적으로 채점 가능한 단위**다.
  게이트를 따로 걸 수 없는 분할은 층이 아니라 파일 목록이다.

## 12. 실행 환경 제약

게이트 ④는 층에 따라 컨테이너 런타임을 요구한다. 로컬에서 런타임이 내려가 있으면 그 층은 CI로 넘어가고,
층별 루프가 분 단위로 느려진다. 그래서 다음 순서로 운용한다.

1. **컨테이너가 필요 없는 층을 먼저 관통시킨다.** ①②③과 in-memory 심판은 로컬에서 초 단위로 돈다.
   파이프라인 자체의 결함은 대부분 여기서 드러나므로, 비싼 층에 도달하기 전에 싸게 잡는다.
2. 컨테이너가 필요한 층은 **로컬 런타임이 살아 있으면 로컬, 아니면 CI 푸시로 판정**한다.

이것이 §5 층 순서 규칙 3의 실제 이유다. 이 대상에서는 의존 방향과 구성 실행 비용의 순서가 마침 일치한다.

**미해결:** 빌드 컨테이너 안에서 테스트용 컨테이너를 띄우는 구성이 이 환경에서 동작하는지 미검증이다.
안 되면 ④는 CI 전용으로 고정한다.
