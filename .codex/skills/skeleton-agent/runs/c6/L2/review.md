# L2 검수 — 조립

> 초안. 최종 판단은 사람이 확인한다.

## 판정: **수용** (1차 시도)

| 게이트 단 | 결과 |
|---|---|
| ① 경로 규약 | 통과 — `config` 안에 파일 1개 |
| ② 컴파일 | 통과 |
| ③ 경계 규칙 | 통과 — 5개 |
| ④ 인수테스트 (조립 대역 **끔**) | **GREEN 7/7** |
| 진행도 관측 (최종 구성) | RED — 진입 층이 없다. 예상대로 |

## 이 층의 판정이 왜 선명한가

L1과 **심판도 같고 시나리오도 같다.** 다른 것은 조립 슬롯 하나뿐이다.

| | L1 게이트 | L2 게이트 |
|---|---|---|
| 심판 | 실제 MySQL 구성 | **동일** |
| 조립 | 대역(`StubCompositionRoot`) 켬 | **끔** |
| 결과 | GREEN | GREEN |

리허설에서 대역을 끄면 `NoSuchBeanDefinitionException`으로 빨간불이 나는 것을 미리 확인해 두었다.
따라서 이 초록불은 **AI가 만든 조립부가 실제로 런타임을 세웠다**는 뜻이며, 다른 해석이 없다.

## 경계 위반: 없음

`config` 밖으로 나간 파일이 없고 Core에 프레임워크가 침투하지 않았다.
Core가 스스로를 빈으로 등록하지 않기 때문에 이 조립 지점이 필요하다는 구조를 그대로 따랐다.

## 지름길을 스스로 거절한 사례 (이 층의 기록거리)

조립부와 조립 대역이 같은 타입의 빈을 등록하면 후보가 둘이 되어 주입이 갈릴 수 있다.
`@ConditionalOnMissingBean`이나 `@Primary` 한 줄이면 피할 수 있고, 통과에는 그 편이 안전하다.
AI는 붙이지 않고 `notes`에 이렇게 적었다.

> 통과를 위해 `@ConditionalOnMissingBean`이나 `@Primary`를 붙이는 쪽은 택하지 않았다 —
> 조립부가 '조건에 따라 자기를 비활성화하는' 코드를 갖는 것은 조립 외의 로직이고,
> 실제 런타임에서 **조립이 조용히 사라지는 경로**를 만드는 일이다.

**판단이 옳다.** L2 게이트는 대역을 끄고 돌리므로 충돌이 애초에 없고, 방어를 붙였다면 운영 환경에서
조립부가 침묵으로 비활성화될 여지를 남겼을 것이다. "막히면 지름길 대신 `notes`" 지시가 실제로 작동한 사례다.

## AI가 남긴 지적에 대한 판단

| # | 지적 | 판단 |
|---|---|---|
| 1 | 대역과의 공존을 이 층에서 확인할 수 없었고, 방어를 붙이지 않기로 했다 | **수용.** 위 참조 |
| 2 | `DiscountPolicy`를 별도 빈으로 노출할지 인라인 생성할지 갈렸다. 교체 축이 없으니 인라인이 더 작다 | 타당한 자기 비판. 다만 인스턴스 생성 책임이 조립부에 있음을 드러내는 현재 선택도 규약과 충돌하지 않는다. **유지** |
