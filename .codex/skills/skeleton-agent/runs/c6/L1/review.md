# L1 검수 — 아웃바운드 어댑터

> 초안. 최종 판단은 사람이 확인한다.

## 판정: 1차 **부분 기각** → 지시 수정 후 재생성 **수용**

| 라운드 | 게이트 | 사람 판단 |
|---|---|---|
| 1차 (`attempt_01_rejected/`, `rejected-01.json`) | ④단까지 전부 GREEN 7/7 | **기각** — 결제 어댑터가 실제 결제사 계약과 불일치 |
| 2차 (`attempt_01/`, `accepted.json`) | GREEN 7/7, 진행도 RED(예상) | **수용** |

기각 시 **산출물을 손보지 않고 지시를 고쳤다.** 결과물을 사람이 고치면 그 층의 판정이 무의미해지고,
같은 실수가 다음 실행에서 되풀이된다. 고쳐야 할 것은 코드가 아니라 입력이었다.

## 게이트가 통과시킨 틀린 코드 (이 실행의 핵심 기록)

1차 산출물은 **4단 게이트를 전부 통과했고 인수테스트 21개가 초록불이었는데 틀렸다.**

```java
// 1차 — 기각
this.chargeUri = URI.create(stripTrailingSlash(baseUrl) + "/payments");
return response.getStatusCode().is2xxSuccessful();
```

실제 결제사 스텁의 계약은 이렇다.

| | 스텁의 실제 계약 | 1차 산출물 |
|---|---|---|
| 경로 | `POST /charge` | `POST /payments` |
| 승인 판정 | 본문 `{"approved": true\|false}` | HTTP 2xx 여부 |
| 거절 시 상태 코드 | **200** | 2xx이므로 **승인으로 처리됨** |

즉 **거절된 결제가 승인으로 처리되는 코드**가 초록불을 받았다.

**왜 게이트가 못 잡았나.** 결제 슬롯은 모든 판정 구성에서 대역이다(설계 문서 §9 "남는 공백").
이 어댑터는 어느 심판에서도 실행되지 않으므로, 인수테스트가 몇 개든 통과 여부와 무관하다.
**초록불이 증명하는 범위는 구성이 정한다**는 명제의 실물 사례다.

**무엇이 잡았나.** AI가 `notes`에 남긴 자기보고:

> 결제사의 엔드포인트 경로와 요청/응답 스키마가 이 층 입력에 없다. `POST {pg.base-url}/payments`,
> 2xx=승인으로 가정했다. 심판 구성에서는 결제가 계속 대역으로 남아 이 가정이 검증되지 않으므로,
> 실제 결제사 계약을 아는 사람이 확인해야 한다.

`notes`는 단서였지 판정이 아니었다. 실제 확인은 사람이 스텁 매핑 파일을 열어서 했고,
거기서 "거절도 200"이라는, AI가 예상조차 못한 부분이 드러났다.

**원인은 AI가 아니라 입력이었다.** L1 지시에 결제사 계약이 빠져 있었다.
"없는 것을 지어내지 마라"고 해놓고 지어낼 수밖에 없는 상태로 준 것이다.
수정한 지시에는 계약을 명시하고, **"이 자리는 인수테스트가 검증하지 않으니 추측하지 말라"** 는 경고를 함께 넣었다.

## 2차 산출물

```java
baseUrl + "/charge", new ChargeRequest(paymentInfo, amount), ChargeResponse.class);
return response != null && response.approved();     // 상태 코드가 아니라 본문으로 판정
```

통신 실패는 미승인으로 접는다. 계약대로다.

## 경계 위반: 없음

`adapter/out` 밖으로 나간 파일이 없고, 영속 타입이 Core로 새지 않았다. 도메인 ↔ 영속 모델 변환을
어댑터 안에서 끝냈다(C-2의 분리 판단과 일치). 경계 규칙 5개 통과.

여기서도 **경로 화이트리스트가 1차 방어로 작동했다.** 도메인 `Ticket`에 영속 애노테이션을 붙이는
지름길은 `core/domain` 수정을 요구하는데, 그건 경계 규칙이 아니라 그 앞의 경로 규약에서 걸린다.

## AI가 남긴 지적에 대한 판단

| # | 지적 | 판단 |
|---|---|---|
| 1 | `ChargePort.charge`가 boolean 하나라 "승인 거절"과 "통신 실패"를 구분할 자리가 없다. 위쪽이 재시도 가능한 실패인지 판단할 근거가 없다 | **타당.** 포트 계약의 빈틈이다. 재시도·대사 정책을 붙일 때 먼저 손봐야 할 지점 |
| 2 | 결제 계약이 입력에 없어 가정했고, 심판이 검증하지 않으니 확인이 필요하다 | **이번 기각의 근거.** 보고한 것이 옳았다 |
| 3 | `TicketRepository.save` 하나가 '신규 저장'과 '예약 확정' 두 의도를 겸해, 어댑터가 `isReserved()`로 호출자의 의도를 추론해야 했다 | **타당.** 포트가 의도를 나눠 표현하면 추론이 사라진다. 계약 개선 후보 |
| 4 | 동시 예약 방어를 `@Version` 대신 조건부 UPDATE로 했다. 저장 스키마가 고정 계약이라 version 컬럼을 늘리면 심판과 어긋난다고 봤다 | **수용.** 판단 근거가 정확하다. 다만 `OptimisticLockingFailureException`이 두 층 사이의 암묵적 계약이 된다는 지적도 맞다 — L3 지시에 이 번역을 명시해 두었다 |
| 5 | `UserRepository`에 저장 계약이 없어, 회원 적재 경로가 이 층 밖에 있어야 한다 | 사실. 현재 범위에선 시드가 그 역할을 한다 |
| 6 | 결제 어댑터에 타임아웃이 없다. 외부 호출이 늦어지면 예매 요청이 묶인다 | **타당.** 설정 접점이 `pg.base-url` 하나뿐이라 이 층에서 만들 수 없었다. 운영 관점 개선 후보 |

## 남은 확인

결제 어댑터는 여전히 **인수테스트가 검증하지 않는다.** 2차 산출물이 스텁과 맞는지는 코드를 읽어 확인했을 뿐이다.
최종 반영 후 `docker compose up` + `declined-card` 스모크로 실제 왕복을 확인해야 한다.
