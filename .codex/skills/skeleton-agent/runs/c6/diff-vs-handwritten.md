# 대조군 비교 — 손으로 쓴 골격 vs 파이프라인이 만든 골격

같은 계약, 같은 심판, 같은 컨벤션에서 사람과 파이프라인이 각각 만든 결과를 나란히 둔다.
손으로 쓴 쪽은 `task3/ticket-reservation`, 파이프라인 쪽은 `task3/ticket-reservation-c6`.

둘 다 같은 인수 시나리오 21개 + 경계 규칙 5개를 통과한다. **관찰 가능한 동작은 동일하다.**
따라서 아래 차이는 전부 "동작은 같은데 다르게 만든 지점"이다.

## 파일 구성

| 손코딩 | 파이프라인 | 차이의 성격 |
|---|---|---|
| `CoreConfig` | `CompositionRoot` | 이름만 다름 |
| `PaymentHttpAdapter` | `PgChargeAdapter` | 이름만 다름 |
| — | **`ReserveTicketRequest`** | 파이프라인이 요청 DTO를 별도 파일로 분리 |
| — | **`TicketPersistenceMapper`·`UserPersistenceMapper`** | 파이프라인이 도메인↔영속 변환을 별도 클래스로 추출 |
| **`DataSeeder`** | — | 파이프라인 쪽엔 없음. 지시에 없었다 |

## 의미 있는 차이 넷

### 1. 비-포트 공개 메서드 — 파이프라인 쪽이 낫다

손코딩 `TicketService`에는 포트에 없는 공개 메서드 `reserveTicket(long, long, String)`이 남아 있다.
파이프라인은 만들지 않았다 — **계약에 없기 때문이다.**

포트에 없는 공개 메서드는 유스케이스의 진입점을 둘로 만든다. 손코딩 쪽은 리팩터링 과정에서 남은
잔재였고, 사람이 그것을 문제로 인식하지 못한 채 지나갔다. 계약만 주고 만들게 하면 그런 잔재가 생기지 않는다.

단, 이것이 가능했던 전제가 있다. **심판이 그 메서드를 부르고 있었다면 계약에 넣어야 했고,
파이프라인도 그대로 재생산했을 것이다.** 준비 단계에서 심판을 포트 호출로 고친 것이 산출물 품질로 이어졌다.

### 2. Mapper 추출 — 판단이 갈리는 지점

손코딩은 도메인↔영속 변환을 어댑터 안의 private 메서드로 두었고("규모가 작아 별도 Mapper는 미추출, YAGNI"),
파이프라인은 `TicketPersistenceMapper`·`UserPersistenceMapper`로 뺐다.

어느 쪽도 규약 위반이 아니다. 변환이 어댑터 경계 안에서 끝난다는 조건은 둘 다 만족한다.
**컨벤션에 "교체 축이 둘 이상일 때만 추상화"라고 적었는데, Mapper 추출은 추상화가 아니라 파일 분리라
그 규칙의 사정권 밖이었다.** 규칙을 더 좁힐지, 이 정도 분리는 허용할지는 사람이 정할 문제다.

### 3. 요청 DTO 분리 — 파이프라인 쪽이 일관적이다

파이프라인은 HTTP 요청 본문을 `ReserveTicketRequest`로 분리했다. 손코딩은 컨트롤러 안의 중첩 record였다.
기능 차이는 없고 파일 배치의 문제다.

다만 파이프라인은 **응답 방향에서는 같은 원칙을 지키지 못했다**고 스스로 지적했다(L3 notes 1).
층 명세가 "결과 DTO를 그대로 직렬화"로 못 박았기 때문이다. 손코딩도 동일한 결합을 갖고 있으나
그때는 아무도 지적하지 않았다. **지시가 만든 결함을 산출물이 되돌려 알려준 사례다.**

### 4. 저장 계약의 두 의도 — 파이프라인이 더 방어적이다

`TicketRepository.save` 하나가 '신규 저장'과 '예약 확정'을 겸한다.

- 손코딩: 항상 조건부 UPDATE. 영향 행이 0이면 충돌 예외.
- 파이프라인: `isReserved()`로 의도를 가르고, 0행일 때 `existsById`로 "행이 아직 없음"과
  "다른 예약이 먼저 확정됨"을 구분한다.

파이프라인 쪽이 한 갈래 더 많다. 그리고 그 추론이 왜 필요했는지를 `notes`에 적었다 —
**포트가 의도를 나눠 표현하면 이 추론이 사라진다.** 계약 개선 후보로 남는다.

## 파이프라인 쪽에만 없는 것

**`DataSeeder`.** 컨테이너 기동 데모용 시드 데이터를 넣는 클래스인데, 층 지시에 포함하지 않았다.
인수테스트는 시나리오가 데이터를 직접 만들므로 이 누락이 게이트에 걸리지 않았다.

L1이 `notes` 5번에서 이 자리를 지적했다 — "회원 데이터를 넣는 경로는 이 층 밖(리소스의 초기화 스크립트 등)에
있어야 한다". **지적이 맞았고, 시드는 어댑터 코드가 아니라 인프라 설정으로 두는 편이 낫다.**
새 폴더에는 `resources`의 초기화 스크립트로 채운다(동결 경로이므로 사람이 작성).

## 총평

**동작이 같은 두 벌을 놓고 보면, 차이는 대부분 "계약에 없던 것을 사람이 관성으로 남겼는가"에서 나왔다.**
파이프라인이 더 나은 지점(1)은 계약 밖의 잔재를 만들지 않은 것이고, 판단이 갈리는 지점(2, 3)은
컨벤션이 그 층위를 규정하지 않은 자리이며, 빠진 지점(`DataSeeder`)은 지시의 누락이다.

세 종류 모두 **산출물의 품질 문제라기보다 입력의 정밀도 문제**였다.
