# L3 검수 — 인바운드 진입 (walking skeleton 완성)

> 초안. 최종 판단은 사람이 확인한다.

## 판정: **수용** (1차 시도)

| 게이트 단 | 결과 |
|---|---|
| ① 경로 규약 | 통과 — `adapter/in/web` 안에 3개 |
| ② 컴파일 | 통과 |
| ③ 경계 규칙 | 통과 — 5개 |
| ④ 인수테스트 (HTTP 관통 구성) | **GREEN 7/7** |
| 진행도 관측 | 이 층의 게이트가 곧 최종 구성이므로 별도 관측 없음 |

## 조립 결과 전체 검증

네 층의 수용본 14개 파일을 출발선 위에 얹어 전체 스위트를 돌렸다.

```
in-memory 구성   7 ✅      실제 MySQL 구성  7 ✅
HTTP 관통 구성   7 ✅      경계 규칙        5 ✅      → 26/26 BUILD SUCCESS
```

**대역이 하나도 없는 구성에서 HTTP 요청 하나가 실제 MySQL까지 닿았다.** 진행도 관측이 L0·L1·L2 내내
RED였다가 여기서 처음 GREEN이 됐다 — 실패 지점이 층마다 뒤로 밀리다 사라진 것이 기록으로 남았다.

## 경계 위반: 없음

인바운드가 아웃바운드를 참조하지 않았고, 도메인 규칙 판단을 어댑터로 끌어오지 않았다.
도메인 예외 → 상태 코드 번역만 한다.

`OptimisticLockingFailureException` 핸들러가 Spring 타입을 참조하지만 **어댑터 안이므로 위반이 아니다.**
경계 규칙이 금지하는 것은 Core의 프레임워크 참조이지 어댑터의 참조가 아니다.

## AI가 남긴 지적에 대한 판단

| # | 지적 | 판단 |
|---|---|---|
| 1 | 성공 응답으로 Core의 출력 DTO를 그대로 직렬화했다. 와이어 포맷이 포트 계약에 묶여, 응답에 필드를 더하려면 Core를 건드려야 한다. **요청 방향은 별도 DTO로 결합을 피했는데 응답만 겸용이라 두 방향의 원칙이 어긋난다** | **가장 값진 지적.** 층 명세가 "결과 DTO를 그대로 직렬화"로 못 박아 생긴 결과이고, 지시가 만든 결함이다. 손으로 쓴 C-4 컨트롤러도 같은 문제를 갖고 있었으나 그때는 아무도 지적하지 않았다. **개선 후보로 남긴다** |
| 2 | `OptimisticLockingFailureException` 핸들러가 실제로 타는 경로를 확인하지 못했다 — **죽은 분기일 수 있다** | **사실일 가능성이 높다.** L1이 조건부 UPDATE 0행일 때 도메인 예외를 던지므로 이 핸들러는 안 탈 수 있다. 앞 층 구현을 읽고 자기 코드가 불필요할 수 있다고 신고한 것이라 신뢰도가 높다. **확인 후 제거 검토** |
| 3 | `produces`를 지정하지 않았다. 성공(json)과 거부(problem+json)의 미디어 타입이 달라 협상에 걸릴 여지가 있어서 | 타당. 거부 응답에는 `contentType`을 명시했다 |
| 4 | 요청 본문 검증을 넣지 않았다. 계약에 정해진 바가 없어 지금은 역직렬화 실패나 결제 거절로 흘러간다 | walking skeleton 범위 밖으로 두는 것이 맞다. **명시적 공백** |
| 5 | `TicketSuspendedException`이 실제로 올라오는 지점의 본문을 못 봐서 이름만 보고 매핑했다 | 정보 차단의 정상적 결과다. 인수테스트가 그 경로를 검증했다 |

## 이 층에서 드러난 정보 차단의 효과

L3는 도메인 예외 클래스의 **이름과 존재만** 받았고 그것이 던져지는 지점의 코드는 못 봤다(지적 5).
그럼에도 매핑이 맞았던 이유는 심판이 그 경로를 검증하기 때문이다.
**계약과 심판이 있으면 구현을 보여주지 않아도 바깥 층을 만들 수 있다**는 것이 실측으로 확인됐다.
