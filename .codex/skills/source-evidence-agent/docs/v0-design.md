# 소스 근거 하네스 v0 설계 (source-evidence-agent)

> 이 문서는 [v1-design.md](v1-design.md)로 대체됐다. 주장 목록을 사람이 쓰는 전제에서 하네스가 뽑는 쪽으로
> 바뀌면서 루브릭의 분모와 게이트 일부가 달라졌다. 바뀐 자리와 이유는 v1의 §16에 있다. 이 문서는 그 결정의
> 출발점으로만 남긴다.

2-1의 `contract-impl-agent`를 소스 리딩으로 옮긴다. 입력은 사람이 확정한 주장 목록과 1차 출처 스냅샷이고,
산출은 주장별 근거 묶음과 사람이 채택·기각을 적을 빈 표다. 스킬 이름은 잠정이다.

## 1. READY는 주장이 참이라는 뜻이 아니다

이 하네스의 통과 상태는 `READY`이고, 뜻은 **"이 주장을 사람이 원문과 대조해 판정할 자료가 갖춰졌다"**다.
주장의 참·거짓은 사람이 채택·기각으로 정한다. `PASS`라는 이름을 쓰지 않는 이유는 2-1에서 게이트를 다
통과한 산출물에 위반이 남았고, 그때 통과를 결론으로 읽은 것이 문제였기 때문이다.

그래서 **어느 단계도 "이 주장은 맞다"를 내지 않는다.** 이 금지가 아래 역할 경계의 뿌리다.

## 2. 입력

| 입력 | 누가 | 하네스의 권한 |
| --- | --- | --- |
| 주장 목록 | 사람 | 읽기. 집합을 바꾸면 위반 |
| 1차 출처 스냅샷 | 사람 | 읽기. 해시로 고정 |
| 대상 코드 | 저장소 | 읽기 |

**주장은 5개에서 8개 사이로 둔다.** 루브릭이 칸을 미충족 주장 수로 가르므로 분모가 흔들리면 같은 점수가
run마다 다른 뜻을 갖는다. 8개를 넘으면 run을 나눈다.

주장 하나의 형식.

```yaml
id: claim-03
sentence: "@Transactional의 isolation 속성은 트랜잭션 시작 시점에 JDBC 커넥션의 격리 수준을 바꾼다."
code: phase2/taskF/alert-kata/src/main/java/com/thinking/tennis/kata/AlertService.java:28
targets: { artifact: spring-framework, version: "6.2.x" }
decides_at:
  kind: source
  symbols: [prepareConnectionForTransaction, setTransactionIsolation]
```

`decides_at`은 주장이 참·거짓으로 갈리는 자리다. 게이트가 여기로 깊이의 기계적 하한을 잡는다. 출처 종류에
따라 형식이 다르다. `kind: source`는 `symbols`를 쓰고 `kind: doc`은 `section`을 쓴다. 산문 출처에는 심볼이
없으므로 심볼 포함을 요구하면 멀쩡한 인용이 탈락한다.

```yaml
id: claim-05
sentence: "REPEATABLE READ의 일반 SELECT는 다른 트랜잭션의 쓰기를 막는 락을 설정하지 않는다."
targets: { artifact: mysql, version: "8.4" }
decides_at:
  kind: doc
  section: innodb-consistent-read
```

주장 목록은 하네스가 만들지 않는다. 판정받는 쪽이 판정 대상을 고르면 쉬운 주장만 올라오고, 주장을 쓰는
일 자체가 이 하네스를 쓰는 목적이다.

출처 스냅샷은 판정의 보조 자산이지만 생성 쪽이 읽어야 한다. 조사 대상이기 때문이다. 정답 자산을 가리는
규칙의 예외이며, 대신 쓰기를 막고 해시를 원장에 남긴다.

### 1차 출처 등급

스냅샷 루트 아래 경로만 1차로 인정한다. 그 밖의 출처가 붙은 인용은 위반이다.

| 루트 | `artifact` |
| --- | --- |
| `sources/jdk-24/` | `jdk` |
| `sources/spring-framework-6.2/` | `spring-framework` |
| `sources/hibernate-orm-6.6/` | `hibernate-orm` |
| `docs/mysql-8.4-refman/` | `mysql` |

javadoc 스냅샷은 두지 않는다. JDK와 Spring의 javadoc은 소스 주석에 그대로 들어 있다.

## 3. 역할 경계

| 단계 | 역할 | 내는 것 | 스키마가 금지하는 것 |
| --- | --- | --- | --- |
| Gen | 조사자 | 주장별 인용, 원문이 말하는 것, 주장과의 차이 | 뒷받침 여부, 점수, 신뢰도 |
| Critique | 반대 조사자 | 주장을 제한하는 인용, 더 깊은 좌표, 주장 수정 발의 | 점수, 수정 반영 |
| Eval | 채점자 | 축별 점수와 센 근거 | 발의, 반영, 통과 판정 |
| Refine | 조사자 재수집 | 보강한 인용, 수정 제안 목록 | 주장 집합 변경 |

Gen에 판정 칸을 두지 않는 것이 핵심이다. Gen이 "뒷받침함"을 쓰면 뒤 단계가 그 문장을 전제로 받아
확인만 하게 된다. Gen은 세 칸을 채운다. 인용문, 원문이 말하는 것, 주장과의 차이다.

Critique는 1차 출처를 직접 읽고 **인용으로** 말한다. 산문 비평만 허용하면 반증할 수 없는 문장이 나오고,
Critique의 인용도 Gen과 같은 게이트를 통과해야 한다.

주장 문장을 고치는 권한은 사람에게 둔다. 주장이 채점의 분모여서 좁히면 점수가 오르고, 주장이 원문보다
넓었다는 발견 자체가 이 하네스의 산출물이다. Critique가 근거 인용과 함께 발의하고 Refine이 제안 목록으로
모으되 반영은 사람이 한다.

## 4. 파이프라인과 단계별 입력

```
주장 목록 ─→ gen ─→ 인용 게이트 ─┬─ 위반 ─→ refine ─→ (게이트 재실행)
                                  └─ 통과 ─→ critique → eval → 합산 ─→ READY
                                                                 └─ 미달 → refine
```

게이트 위반이 있으면 critique와 eval을 건너뛴다. 존재하지 않는 인용에는 반증할 것도 채점할 것도 없으므로
유료 호출 두 번을 아낀다. 건너뛴 이유는 원장에 남긴다.

| 단계 | 받는 것 | 차단하는 것 |
| --- | --- | --- |
| Gen | 주장 목록, 출처 스냅샷, 대상 코드 | 모든 단계 산출 |
| Critique | 주장 목록, Gen의 인용(인용문·경로·심볼), 스냅샷, 코드 | Gen의 `claim_delta`, 모든 점수 |
| Eval | 주장 목록, Gen 산출 전체, 스냅샷, 코드 | Critique 산출, 이전 run 점수 |
| Refine | 주장 목록, 게이트 위반 목록, Critique의 반증 인용, 약한 축 이름 | 축 점수 |

Critique에게 Gen의 `claim_delta`를 가린다. 두 독립 판독이 생기고, **두 서술이 어긋나는 자리가 사람이
먼저 열어 볼 자리**가 된다. 리포트가 그 불일치를 따로 묶는다.

Eval에게 Critique를 넘기지 않는다. 비평이 맞았을 때도 채점이 그것을 확인하는 일만 하게 된다.

Refine에게 점수를 넘기지 않는다. 점수는 방향 없는 목표라 측정값을 움직이는 가장 싼 경로를 고르게 한다.

차단은 runner가 payload를 구성해 물리적으로 걸고, 프롬프트가 "받은 것만 보고 판단하라"를 함께 적는다.

## 5. 게이트

규칙마다 id와 상태를 고정한다. `violation`은 거절로 이어지고, `unmeasured`는 통과도 거절도 아닌 미판정이다.
미판정이 하나라도 있으면 READY가 아니다.

| id | 뜻 | 상태 |
| --- | --- | --- |
| `claim_uncovered` | 주장에 인용이 0개다 | violation |
| `claim_set_changed` | 주장 id 집합이 입력과 다르다 | violation |
| `citation_missing` | 인용 경로가 스냅샷에 없다 | violation |
| `citation_mismatch` | 인용문이 그 자리에 문자열로 없다 | violation |
| `source_out_of_scope` | 스냅샷 루트 밖이거나 주장이 겨눈 `artifact`와 다른 루트다 | violation |
| `anchor_absent` | `decides_at`에 닿지 않았다 | violation |
| `quote_oversized` | 주장당 인용 3개 또는 연속 40줄을 넘는다 | violation |
| `role_breach` | 금지 산출물이 들어왔다 | violation |
| `judge_path_touched` | 게이트·루브릭·스냅샷이 변경 목록에 있다 | violation |
| `eval_unread` | 채점자가 출처나 코드를 열지 못했다 | unmeasured |

`claim_set_changed`가 가장 중요하다. 주장을 더할 수 있으면 쉬운 주장으로 평균을 올리고, 지울 수 있으면
어려운 주장을 버린다.

`anchor_absent`는 출처 종류로 갈라 판정한다. `kind: source`면 `symbols` 중 하나가 인용문 안에 있어야
하고, `kind: doc`이면 인용 경로의 절이나 앵커가 `section`과 같아야 한다.

`eval_unread`를 미판정으로 두는 이유는 2-1에서 채점자가 파일을 못 읽어 다섯 축 중 넷이 1점이 된 일이
있기 때문이다. 측정 실패를 점수로 쓰지 않는다.

`judge_path_touched`는 발생하지 않을 것으로 예상한다. 쓰기 권한이 자기 산출 파일뿐이기 때문이다. 가드로
두고, 탈락 횟수가 계속 0이면 공허한 규칙인지 따로 판단한다.

### 리허설

게이트는 파이프라인을 붙이기 전에 양방향으로 고정한다. `tests/`에 손으로 쓴 정답 묶음 1건과 규칙마다
그 규칙만 깨뜨린 입력 1건을 두고, 정답이 통과하고 각 위반 입력이 그 규칙으로만 탈락하는지 자동 실행한다.
리허설 입력이 없는 규칙은 공허한지 확인된 적이 없는 규칙이다.

## 6. 루브릭 `evidence:v1`

### 축과 분모

분모는 사람이 확정한 주장 목록이다. 주장별로 축마다 충족·미충족을 판정하고, 축 점수는 미충족 주장 수로
정한다.

| 축 | 주장별 충족 조건 |
| --- | --- |
| `grounding` | 인용이 주장 문장을 함의한다. 인용이 다른 것을 말하면 미충족 |
| `scope_fit` | 주장이 원문보다 넓지 않다. 원문이 단 조건이 주장 문장에 없으면 미충족 |
| `depth` | 인용이 주장의 참·거짓을 가르는 자리에 닿았다. 선언·요약·주변만 닿으면 미충족 |
| `counter_evidence` | 주장을 제한하는 조항을 인용으로 가져왔거나, 탐색한 1차 출처 경로를 적고 없음을 선언했다 |

**가중치와 가중 총점을 두지 않는다.** 축이 넷이고 통과 조건이 축별 하한이므로 총점이 할 일이 없다.
축의 중요도 차이는 통과 조건이 아니라 아래 두 문장이 담는다.

`depth`는 게이트의 `anchor_absent`가 기계적 하한을 이미 잡으므로 루브릭이 보는 몫이 작다. 반대로
`scope_fit`과 `counter_evidence`가 이 하네스의 실제 가치다. 환각 인용은 게이트가 전부 잡고, 남는 위험은
진짜 인용으로 원문보다 넓은 주장을 뒷받침하는 것이다.

네 축은 같은 묶음을 네 번 보지 않고 서로 다른 관계를 본다. 인용과 주장의 함의, 주장 문장과 원문의 범위,
인용 위치와 결정 지점, 탐색 범위와 제한 조항이다. 정확한 줄을 찾아 오해할 수 있고(depth 충족, grounding
미충족), 맞지만 얕은 문장을 가져올 수 있고(grounding 충족, depth 미충족), 좁게 적으면서 제한 조항을 한
번도 찾지 않을 수 있다(scope_fit 충족, counter_evidence 미충족).

`contract-impl-agent`처럼 자리를 축에 배분하지는 않는다. 주장 하나를 한 축에만 넣으면 나머지 축이 그
주장을 보지 못한다. 겹침은 자리가 아니라 질문으로 막는다.

### 사다리

네 축이 같은 칸 조건을 쓴다. 미충족이 한 건이라도 있으면 상한은 3이다.

| 점수 | 조건 |
| --- | --- |
| 1 | 미충족 3개 이상 |
| 2 | 미충족 2개 |
| 3 | 미충족 1개 |
| 4 | 미충족 0개 |

상단을 더 쪼개지 않는다. 사람이 읽는 것은 미충족으로 세어진 주장이므로 "미충족 0개"를 둘로 가르는 칸은
어느 판정도 바꾸지 않는다.

채점 근거는 축마다 `"열거 N개, 미충족 K개: [claim-id...]"` 형태로 남긴다. 축 이름을 되풀이한 근거는
조건을 보지 않은 것이다.

### `counter_evidence`의 양성 통제

이 축은 "탐색했고 제한 조항 없음"으로 언제나 충족을 만들 수 있고, 게이트는 없는 것을 반증하지 못한다.
그래서 **제한 조항이 실제로 존재하는 주장을 목록에 하나 이상 섞는다.** 에이전트가 그것을 가져오지 못하면
이 축은 공허하다.

`ReentrantLock`의 공정성 주장이 그 자리다. 공정 모드에서도 `tryLock()`은 대기열을 건너뛴다는 예외가
소스 주석에 있어, 그 문장을 가져오는지로 축이 작동하는지 확인된다.

### 루브릭의 주 용도는 정렬이다

2-1에서 루브릭은 통과를 가르는 문턱이었다. 여기서는 사람이 원문을 열 순서를 정하는 장치로 쓴다. 주장
여덟 개의 근거를 전부 정독하는 것과 미충족으로 세어진 주장부터 정독하는 것은 비용이 다르다. 하한으로도
쓰지만 값의 주 용도는 리포트의 정렬이다.

## 7. 종료 상태

| 상태 | 조건 |
| --- | --- |
| `READY` | violation 0 + unmeasured 0 + 축별 3 이상 |
| `FAILED` | 반복 상한까지 위반이나 미달이 남았다 |
| `ERROR` | 단계 실행 자체가 진행하지 못했다 |

하한 판정은 코드가 한다. 점수는 재료이고 통과는 채점자가 정하지 않는다.

반복 상한은 2다. 실패가 "인용이 없거나 어긋남"이면 한 번의 재수집으로 대개 닫히고, 반복이 깎는 것은
자료의 완성도이지 주장의 참이 아니다. 상한에 닿으면 `FAILED`로 남기고 통과 산출물을 만들지 않는다.
단계 실행 실패와 스냅샷 경로 오류는 반복을 태우지 않는다.

## 8. 도구와 쓰기 범위

**읽기와 검색은 준다. 쓰기와 네트워크는 막는다.** 스냅샷에서 어디를 봐야 하는지 찾는 것이 이 하네스의
작업이므로 파일 검색을 빼면 단계가 성립하지 않는다. 반대로 네트워크를 열면 에이전트가 웹에서 근거를
가져와 스냅샷 고정이 무너지고, 자기 판정의 근거를 자기가 공급하게 된다.

| 대상 | 권한 |
| --- | --- |
| run 폴더의 자기 산출 파일 | 쓰기 |
| 출처 스냅샷, 대상 코드 | 읽기·검색 |
| 게이트·루브릭·프롬프트 | 없음 |
| 네트워크 | 없음 |

판정 경로가 변경 목록에 나타나면 `judge_path_touched`로 탈락한다. 리딩 전용이라 저장소에 쓰는 단계가 없다.
승인이나 샌드박스를 우회하는 플래그는 기본값에도 두지 않는다.

## 9. 실패 기록

실패는 분류와 규칙 id를 붙여 남긴다. 분류는 구조 위반, 게이트 위반, 품질 미달, 역할 침범, 미판정,
단계 실행 실패, 반복 상한 초과다. 품질 미달과 미판정은 파이프라인이 정상 동작한 결과다.

모델 응답 원문은 파싱 전에 저장한다. 성공해도 저장한다. 성공한 검사의 세부는 파일로 남기지 않는다.

## 10. 리포트

사람이 읽는 순서대로 네 묶음을 낸다.

1. 주장별 표 — 주장, 인용, 축별 충족·미충족, **채택·기각 빈 칸**.
2. Gen과 Critique의 서술이 어긋난 자리.
3. Critique가 발의한 주장 수정 제안과 그 근거 인용.
4. Critique가 신고한 코드 불일치 — 주장이 대상 코드가 실제로 의존하는 전제가 아닌 자리.

4번은 축이 아니다. 주장을 고르는 쪽이 사람이므로 어긋난 것은 사람의 잘못이고 에이전트를 채점할 대상이
아니다. 거절로 이어지지 않고 리포트에만 실린다.

## 11. 재사용과 교체

| 재사용 | 교체 |
| --- | --- |
| `runner.py`의 단계 오케스트레이션, 반복 루프, 파일 핸드오프 | 프롬프트 4벌 |
| `ledger.py`, `report.py`, `validate.py`, 스키마 로더 | `input.schema.json` → 주장 목록 + 스냅샷 해시 |
| `stages/scripts/*` (LLM 클라이언트, payload, textio) | 루브릭 축과 칸 조건 |
| 루브릭 파일 형식과 그것을 읽는 코드 | 게이트 내용 → 인용 검증 |
| 규칙 카드 형식, `tools/replay_gate.py` | 규칙 카드 내용 |
| 역할 분리(발의와 반영을 가름) | — |

G0는 쓰지 않는다. 컴파일할 대상이 없다.

**재사용 코드는 복사하고, 복사한 파일 목록을 `BUILD.md`에 적어 변경 금지로 둔다.** 공용 모듈로 빼는
것은 이번 범위가 아니다. 3,000줄짜리 runner를 추출하는 리팩터링을 하네스 제작과 같은 작업에 섞으면
어느 쪽이 깨졌는지 가를 수 없다. 세 번째 하네스가 같은 파일을 요구할 때 별도 작업으로 올린다.

## 12. 아직 없는 것

- 느린 루프가 없다. `slow-loop`, `fixed-point`, `moving-yardstick`, `sample-gate`의 체크리스트는
  해당없음이고, 두 번째 루프를 만들 때 돌린다.
- 재채점 분산을 측정한 기록이 없다. 축별 임계는 run이 쌓인 뒤에 정한다.
- 축 쌍 상관을 볼 표본이 없다. 기록 몇 건으로 축을 합치지 않는다.
- 실행 trace가 없으면 `information-blocking`은 payload 차단까지만 집행되고 프롬프트 지시는 확인할 수 없다.
