# 소스 근거 하네스 v1 설계 (source-evidence-agent)

2-1의 `contract-impl-agent`를 소스 리딩으로 옮긴다. 산출은 주장별 근거 묶음과 사람이 채택·기각을 적을 빈 표다.

v0과 갈리는 자리는 하나다. **주장 목록을 사람이 쓰지 않고 하네스가 뽑는다.** v0은 사람이 확정한 주장 목록을
입력으로 받는 설계였고, 그 전제 위에서 루브릭의 분모와 게이트의 `claim_set_changed`가 서 있었다. 주장을 뽑는
일을 하네스로 옮기면 그 두 장치가 순환하므로 둘을 다른 것으로 바꿔야 한다. 무엇을 바꿨고 왜 바꿨는지는 §16에
모아 둔다.

사람에게 남는 일은 채택·기각 하나다. 판단이 어려운 자리를 전부 사람에게 돌려놓으면 AI가 틀릴 위험은 사라지지만
사람이 읽어야 할 양이 그만큼 늘어난다. 넘길 수 없는 것은 채택·기각인데, 그것이 과제가 사람에게 맡긴 산출물이고
AI가 가져온 근거를 다른 AI가 채택하면 판정 기준이 제자리로 돌아간다.

## 1. 전체 흐름

```
0  재현 테스트 빨간불 고정          재사용. 해시만 기록
1  AI 구현 run                    "동시성 문제를 해결해라". 조건을 주지 않는다
2  리딩 하네스 1 run              Gen → 게이트 → Critique → Eval → Refine
3  사람                           두 칸 대조로 채택 / 기각
```

| 단계 | 산출 | 다음 단계에 무엇으로 들어가는가 |
| --- | --- | --- |
| 0 | 빨간불 로그, 테스트 파일 해시 | 단계 1의 판정 기준 |
| 1 | 자기 평가, 구현, 테스트 로그 | 단계 2의 입력. 주장 추출 대상 |
| 2 | 주장별 근거 묶음, 축 점수, 리포트 | 단계 3이 읽는 것 |
| 3 | 채택·기각 기록 | 과제 제출물 |

단계 0은 새로 만들지 않는다. 재현 테스트는 이미 빨간불로 고정돼 있고 락 구현보다 먼저 쓰였다는 것이 저장소
이력에 남아 있다. 다시 쓰면 이미 한 일을 연출로 다시 하는 것이다.

## 2. READY는 주장이 참이라는 뜻이 아니다

이 하네스의 통과 상태는 `READY`이고, 뜻은 **"이 주장을 사람이 원문과 대조해 판정할 자료가 갖춰졌다"**다.
주장의 참·거짓은 사람이 채택·기각으로 정한다. `PASS`라는 이름을 쓰지 않는 이유는 2-1에서 게이트를 다
통과한 산출물에 위반이 남았고, 그때 통과를 결론으로 읽은 것이 문제였기 때문이다.

그래서 **어느 단계도 "이 주장은 맞다"를 내지 않는다.** 이 금지가 역할 경계의 뿌리다.

## 3. 설계 원칙

- **주장을 뽑는 쪽이 근거도 모은다. 그래서 선별을 기계가 검사한다.** 근거를 찾기 쉬운 주장만 뽑는 편향이
  이 설계의 가장 큰 위험이고, 주장 집합을 묶어 두는 장치는 커버리지 게이트 하나다.
- **한 사실은 한 자리에서 판정한다.** 문자열로 갈리는 것은 게이트가, 원문을 읽어야 아는 것은 루브릭이,
  뜻을 붙여야 아는 것은 비평이 맡는다.
- **고치는 것은 막지 않고 말없이 고치는 것을 막는다.** 주장의 삭제와 수정은 근거와 함께 신고하게 하고,
  신고하지 않은 것은 통과시키지 않는다.
- **점수를 주장 수로 세지 않는다.** 주장이 하네스 산출이므로 평균을 내면 어려운 주장을 지워 올리는 길이
  열린다. 주장마다 축별 칸을 내고 합산하지 않는다.
- **측정하지 못한 것은 판정이 아니다.** 채점자가 출처나 코드를 열지 못했으면 그 점수는 판정이 아니라 측정
  실패이고, 통과도 거절도 아닌 미판정으로 적는다.
- **네트워크는 자료를 가져오는 통로이고 판정은 사본에 대고 한다.** 가져온 페이지를 즉시 떠서 해시를 남기면
  게이트가 재실행에서 같은 판정을 낸다.

## 4. 단계 1: AI 구현 run

프롬프트는 조건을 주지 않는다. "이 테스트가 빨간불이다. 동시 요청에서도 규칙이 지켜지게 해라"까지다. 어떤
방식으로 풀지는 말하지 않는다.

| 주는 것 | 막는 것 |
| --- | --- |
| 대상 서비스와 저장소, 스키마, 빨간불 테스트, F-2의 관찰 결과 | 이미 쓴 락 구현과 그 비교 테스트, F-3 답안, `evidence/` |
| | 테스트 경로 쓰기 |

조건을 주는 것과 이미 쓴 풀이를 가리는 것은 다른 일이다. 전자는 사고를 대신하는 것이라 빼고, 후자는 시험의
전제라 남긴다. 조건을 주지 않았는데 답이 옆에 펼쳐져 있으면 가장 싼 경로가 그것을 복사하는 것이 되어, 조건을
준 것과 결과가 같아진다.

산출은 셋이고 **순서가 고정이다. 자기 평가 → 구현 → 테스트 실행.** 자기 평가에는 무엇을 막았는지, 어느
격리 수준을 전제했는지, 왜 통과할 것인지를 적는다. 실패 로그를 본 뒤에 쓰게 하면 평가가 결과에 맞춰져서,
자기 평가와 테스트가 어긋난 자리가 사라진다.

구현이 테스트를 못 넘겨도 단계 2에 넣는다. 틀린 구현의 전제가 가장 좋은 주장 후보다.

## 5. 하네스 입력

| 입력 | 누가 | 하네스의 권한 |
| --- | --- | --- |
| 대상 코드 | 저장소 | 읽기·검색 |
| 본인 답안의 단정 문장 | 사람 | 읽기 |
| 단계 1의 산출 셋 | 단계 1 | 읽기 |
| 출처 스냅샷과 수집 사본 | 사람과 Gen·Critique | 스냅샷은 읽기. 사본은 수집 시점에만 쓰기, 이후 읽기 |
| 동시성 API 지점 목록 | 추출기 | 없음. 판정 자산이다 |

마지막 줄이 v0과 다른 자리다. 주장 집합의 하한을 사람이 공급하지 않으므로 기계가 공급한다. 추출기가 대상
코드에서 동시성 API 사용 지점을 열거하고, 그 목록이 커버리지 게이트의 분모가 된다. 추출기와 그 목록은 판정
경로에 두고 생성 쪽은 읽지 못한다.

### 주장의 종류

주장은 둘로 갈린다. 종류가 트레이드오프 두 축의 적용 여부를 정한다.

| 종류 | 무엇인가 | 트레이드오프 두 축 |
| --- | --- | --- |
| 사실 | 1차 출처 하나의 인용으로 참·거짓이 갈린다 | 해당없음. 미충족이 아니다 |
| 선택 | 출처가 말해 줄 수 없다. 대상 코드가 이 방식을 택했다는 것 | 적용 |

선택 주장을 사실로 선언해 트레이드오프를 면제받는 길은 따로 막지 않는다. 사실로 선언하면 그 문장을 함의하는
인용을 내놔야 하는데 출처에 그런 문장이 없으므로 `grounding`에서 하한을 못 넘는다. 종류 선언의 도피 경로가
다른 축에서 닫힌다.

### 주장 하나의 형식

```yaml
id: claim-03
kind: fact
sentence: "@Transactional의 isolation 속성은 트랜잭션 시작 시점에 JDBC 커넥션의 격리 수준을 바꾼다."
sites: [site-19, site-22]                         # 지점 목록 안의 id 여야 한다
decides_at:
  kind: source
  symbols: [prepareConnectionForTransaction, setTransactionIsolation]
```

```yaml
id: claim-06
kind: choice
sentence: "같은 사용자 행을 PESSIMISTIC_WRITE로 먼저 잠그는 방식을 택했다."
sites: [site-15]
tradeoffs:
  - dimension: latency
    statement: "..."
    coordinate: evidence/lock-comparison-results.md:14
  - dimension: failure
    statement: "이 차원에서는 교환이 없다. 왜 없는지..."
    coordinate: ...
```

**지점은 배열이고 id 로 적는다.** 주장 하나가 지점 하나만 덮게 하면 주장 수가 지점 수를 따라가야 한다. 같은 API
결정이 여러 줄에 흩어져 있을 때 그것을 한 주장으로 설명하는 것이 정상이고, 추출기를 실제 대상에 돌려
보니 지점이 24개였다. 주장은 10개를 넘기지 않는다. 사람이 읽는 양이 이 상한에 걸려 있다.

좌표 문자열이 아니라 id 로 받는 것도 run 1 전에 리허설이 잡은 자리다. 한 줄에 두 API 가 있으면 좌표가
같아서, 좌표로 세면 한쪽을 덮은 주장이 다른 쪽까지 덮은 것으로 세어진다.

`decides_at`은 주장이 참·거짓으로 갈리는 자리다. 출처 종류에 따라 형식이 다르다. `kind: source`는 `symbols`를
쓰고 `kind: doc`은 `section`을 쓴다. 산문 출처에는 심볼이 없으므로 심볼 포함을 요구하면 멀쩡한 인용이 탈락한다.

`decides_at`을 Gen이 적는다는 것이 v0과 다르고, 그래서 게이트의 앵커 검사가 "Gen이 고른 자리에 Gen이 닿았는가"
까지만 본다. 얕은 자리를 앵커로 적는 것은 게이트가 막지 못하고 `depth` 축이 본다.

### 출처 등급

쓰임이 둘로 갈린다. 사실 주장의 근거가 될 수 있는 것과 트레이드오프의 전제에 좌표를 댈 수 있는 것이 같지 않다.

| 출처 | 등급 | 사실 주장의 인용 | 선택 주장의 인용 | 전제의 좌표 |
| --- | --- | --- | --- | --- |
| 라이브러리 소스, 공식 문서, 명세 문서 | `primary` | 가능 | 가능 | 가능 |
| 대상 코드 | `target` | 불가 | 가능 | 가능 |
| 본인의 측정 로그 | `measured` | 불가 | 불가 | 가능 |
| 블로그, Q&A, 검색 요약 | — | 불가 | 불가 | 불가 |

대상 코드를 등급으로 올린 것은 run 1을 보고 고친 자리다. 선택 주장은 "대상 코드가 이 방식을 택했다"이므로
그 증거가 코드인데, 등급 표에 코드가 없으니 인용할 자리가 없었다. 실제로 세 주장이 측정 로그를 인용으로
써서 탈락했다. 코드를 사실 주장의 인용에서 막는 이유는 코드가 "무엇이 참이다"를 말하지 못하기 때문이다.

측정 로그는 "이 환경에서 이랬다"만 말하므로 "무엇이 참이다"의 근거가 되지 못한다. 반대로 트레이드오프의 전제는
1차 출처가 말해 주지 않는다. 공식 문서는 어느 격리 수준이 무엇을 잠그는지는 적지만 어느 충돌 빈도에서 어느 락이
유리한지는 적지 않는다. 그 자리의 좌표는 측정 로그가 댄다.

블로그를 인용에 쓰면 탈락이지만 탐색 경로로는 남긴다. 2차 자료를 읽고 소스의 어느 줄을 볼지 알아낸 것은 정당한
작업이다.

## 6. 역할 경계

| 단계 | 역할 | 내는 것 | 스키마가 금지하는 것 |
| --- | --- | --- | --- |
| Gen | 조사자 | 주장, 종류, 좌표, 인용, 원문이 말하는 것, 주장과의 차이, 선택 주장의 교환 항목 | 뒷받침 여부, 점수, 신뢰도 |
| Critique | 반대 조사자 | 주장을 제한하는 인용, 더 깊은 좌표, 빠진 자리, 주장 수정 발의 | 점수, 수정 반영 |
| Eval | 채점자 | 축별 칸과 그 근거 | 발의, 반영, 통과 판정 |
| Refine | 조사자 재수집 | 보강한 인용, 신고한 주장 변경 | 축 점수 열람, 커버리지 축소 |

Gen에 판정 칸을 두지 않는 것이 핵심이다. Gen이 "뒷받침함"을 쓰면 뒤 단계가 그 문장을 전제로 받아 확인만 하게
된다. Gen은 재료만 채운다.

Critique의 산출 스키마는 `limiting_clauses`를 필수로 둔다. 비면 구조 위반이고, 제한 조항을 찾지 못했으면 뒤진
1차 출처 경로와 없음 선언을 적어야 한다. 탐색 성실성을 축으로 재지 않고 스키마로 집행하는 이유는 §16에 있다.

주장 문장을 고치는 권한은 Refine에 있지만 신고해야 한다. 주장이 판정의 분모여서 좁히면 점수가 오르고, 주장이
원문보다 넓었다는 발견 자체가 이 하네스의 산출물이다. 신고하지 않은 삭제와 수정은 게이트가 잡는다.

## 7. 파이프라인과 단계별 입력

```
코드·답안·단계1 산출 ─→ gen ─→ 게이트 ─┬─ 위반 ─→ refine ─→ (게이트 재실행)
                                        └─ 통과 ─→ critique → eval → 합산 ─→ READY
                                                                      └─ 미달 → refine
```

게이트 위반이 있으면 critique와 eval을 건너뛴다. 존재하지 않는 인용에는 반증할 것도 채점할 것도 없으므로 유료
호출 두 번을 아낀다. 건너뛴 이유는 원장에 남긴다.

| 단계 | 받는 것 | 차단하는 것 |
| --- | --- | --- |
| Gen | 코드, 답안, 단계 1 산출, 출처 | 모든 단계 산출, 지점 목록 |
| Critique | 주장과 인용, 출처, 코드 | Gen의 `주장과의 차이`, 모든 점수, 지점 목록 |
| Eval | Gen 산출 전체, 출처, 코드 | Critique 산출, 이전 run 점수 |
| Refine | 게이트 위반 목록, Critique의 반증 인용, 약한 축 이름 | 축 점수 |

Critique에게 Gen의 `주장과의 차이`를 가린다. 두 독립 판독이 생기고, **두 서술이 어긋나는 자리가 사람이 먼저
열어 볼 자리**가 된다. 리포트가 그 불일치를 따로 묶는다.

Eval에게 Critique를 넘기지 않는다. 비평이 맞았을 때도 채점이 그것을 확인하는 일만 하게 된다.

Refine에게 점수를 넘기지 않는다. 점수는 방향 없는 목표라 측정값을 움직이는 가장 싼 경로를 고르게 한다.

게이트에는 모든 입력을 준다. 기계적 검사는 anchoring의 대상이 아니다. Gen과 Critique의 인용 집합을 대조하는
검사가 그래서 게이트에 있다.

차단은 runner가 payload를 구성해 물리적으로 걸고, 프롬프트가 "받은 것만 보고 판단하라"를 함께 적는다.

## 8. 게이트

규칙마다 id와 상태를 고정한다. `violation`은 거절로 이어지고, `unmeasured`는 통과도 거절도 아닌 미판정이다.
미판정이 하나라도 있으면 READY가 아니다.

| id | 뜻 | 상태 |
| --- | --- | --- |
| `claim_uncovered` | 주장에 인용이 0개다 | violation |
| `claim_site_unknown` | 주장의 좌표가 지점 목록에 없다 | violation |
| `coverage_gap` | 지점 중 어느 주장도 덮지 않은 것이 있다 | violation |
| `citation_absent` | 인용 경로가 사본에 없거나 인용문이 그 자리에 문자열로 없다 | violation |
| `source_out_of_scope` | 출처 등급 표를 어긴다 | violation |
| `anchor_absent` | `decides_at`에 닿지 않았다 | violation |
| `metric_coordinate_absent` | 교환 항목의 좌표가 없거나 그 좌표가 실존하지 않는다 | violation |
| `limiting_clause_missed` | Critique이 가져온 제한 조항 중 Gen이 안 가져온 것이 있다 | **observation** |
| `claim_change_unreported` | 신고에 없는 주장 삭제나 수정이 있다 | violation |
| `quote_oversized` | 주장당 인용 3개 또는 연속 40줄을 넘는다 | violation |
| `role_breach` | 금지 산출물이 들어왔다 | violation |
| `judge_path_touched` | 게이트·루브릭·지점 목록·사본이 변경 목록에 있다 | violation |
| `eval_unread` | 채점자가 출처나 코드를 열지 못했다 | unmeasured |

`coverage_gap`이 가장 중요하다. 주장을 뽑는 쪽이 판정받는 쪽이므로 자신 없는 자리를 주장으로 세우지 않는 것이
모든 축에서 유리하다. 이 규칙이 그 길을 막는 유일한 장치다.

`metric_coordinate_absent`가 트레이드오프 요구를 기계로 집행한다. 게이트는 교환이 옳은지 판정할 수 없지만
수치에 좌표가 붙어 있고 그 좌표가 실재하는지는 셀 수 있다. 좌표가 그 항목을 뒷받침하는지는 `tradeoff_validity`가
본다.

`limiting_clause_missed`가 Critique의 산출을 Gen의 산출과 대조한다. 두 단계의 인용 경로와 심볼 집합의 차집합
이라 판단이 들어가지 않는다. **거절로 이어지지 않는 관찰이다.** 처음에는 위반으로 뒀는데 run을 돌려 보니
통과를 막는 쳇바퀴가 됐다. Critique은 Gen 뒤에 돌면서 제한 조항을 찾는 일만 하므로 Gen이 안 가져온 조항을
거의 항상 찾아내고, 주장당 인용 3개 상한 안에서 Gen이 그것을 미리 다 인용할 수는 없다. 조항을 안 가져온
것은 사실이지만 그것이 결함인지는 그 조항이 주장을 실제로 깎는지에 달려 있고 그건 판단이라, `grounding`의
4점 조건이 본다. 열거는 남겨 재수집의 입력과 리포트로 보낸다.

`citation_absent`는 **비교 전에 줄 끝을 LF로 정규화한다.** 정규화하지 않으면 사본을 어디서 받았는지에 따라
멀쩡한 인용이 탈락한다. 단계 1에서 실제로 겪은 자리다. 테스트 파일을 한 줄도 고치지 않은 run이 체크아웃의
줄 끝 변환만으로 동결 해시와 어긋났다. 문자열 대조를 쓰는 규칙은 비교 전에 정규화할 것을 규칙 쪽에 적는다.

`anchor_absent`는 출처 종류로 갈라 판정한다. `kind: source`면 `symbols` 중 하나가 인용문 안에 있어야 하고,
`kind: doc`이면 인용 경로의 절이나 앵커가 `section`과 같아야 한다. 이 규칙은 Gen이 고른 앵커에 Gen이 닿았는지
까지만 본다. 앵커 자체가 얕은 것은 `depth` 축이 본다.

차원 라벨은 게이트가 아니라 스키마의 enum이 잡는다. 설정이 지정한 차원 목록을 enum으로 박으면 라벨 없는
산문 교환은 구조 위반으로 떨어진다.

### 리허설

게이트는 파이프라인을 붙이기 전에 양방향으로 고정한다. `tests/`에 손으로 쓴 정답 묶음 1건과 규칙마다 그 규칙만
깨뜨린 입력 1건을 두고, 정답이 통과하고 각 위반 입력이 그 규칙으로만 탈락하는지 자동 실행한다. 리허설 입력이
없는 규칙은 공허한지 확인된 적이 없는 규칙이다.

`coverage_gap`의 리허설은 지점 하나를 일부러 비운 입력이고, `limiting_clause_missed`의 리허설은 Critique에만
있는 조항을 심은 입력이다.

## 9. 루브릭 `claim:v1`

주장마다 축별 칸을 내고 **합산하지 않는다.** 축은 넷이고 서로 다른 칸을 본다.

| 축 | 무엇을 보는가 | 어디를 보는가 | 칸 | 하한 |
| --- | --- | --- | --- | --- |
| `grounding` | 인용이 주장을 함의하고 주장이 원문보다 넓지 않은가 | 주장 문장과 인용문 | 4 | 3 |
| `depth` | 인용이 참·거짓을 가르는 자리인가 | 인용의 위치 | 4 | 3 |
| `tradeoff_coverage` | 지정된 차원 중 몇 개에 교환이 명시됐는가 | 차원 목록 | 5 | 3 |
| `tradeoff_validity` | 명시된 교환이 좌표와 맞고 전제가 붙었는가 | 교환 항목들 | 5 | 3 |

분모가 서로 다른 목록이다. 한 자리가 두 축의 분모에 들어가지 않으므로 가중치를 쓰지 않아도 겹침이 구조적으로
막힌다. 칸 수가 축마다 다른 이유는 조건이 쌓이는 단수가 다르기 때문이다. 5점을 만들려고 칸을 지어 넣으면 그
칸이 다른 축을 침범한다.

### `grounding`

| 칸 | 조건 |
| --- | --- |
| 1 | 인용이 주장과 다른 것을 말한다 |
| 2 | 같은 주제지만 주장 문장을 함의하지 않는다 |
| 3 | 인용이 주장 문장을 함의한다 |
| 4 | 함의하고, 원문이 단 조건이 주장 문장에 들어 있다 |

### `depth`

| 칸 | 조건 |
| --- | --- |
| 1 | 인용이 주장과 무관한 파일이나 절이다 |
| 2 | 선언, 목차, 속성 설명, 요약만 닿았다 |
| 3 | 그 동작을 설명하는 본문에 닿았다 |
| 4 | 그 동작이 결정되는 구현이나 조항 자체에 닿았다. 주장이 거짓이라면 이 자리의 문장이 달라야 한다 |

4점 조건의 뒷문장이 판정 입장이다. 채점자가 "이 자리가 바뀌면 주장의 참·거짓이 바뀌는가"를 묻게 되므로, Gen이
어디를 앵커로 적었는지와 무관하게 판정된다. 게이트의 `anchor_absent`가 순환하는 자리를 이 축이 메운다.

### `tradeoff_coverage`

선택 주장에만 적용한다. 사실 주장은 해당없음이고 미충족이 아니다.

| 칸 | 조건 |
| --- | --- |
| 1 | 명시된 차원 0개 |
| 2 | 1개 |
| 3 | 2개 |
| 4 | 3개 |
| 5 | 지정된 차원 전부 |

한 차원을 충족시키는 방법이 둘이다. 대안 대비 무엇을 얻고 무엇을 치르는지 적거나, **그 차원에서 교환이 없다는
것과 왜 없는지를 적는 것**이다. 교환이 없는 주장에 억지로 비용을 지어내게 하면 없는 트레이드오프가 생겨난다.

차원 목록은 이 문서가 아니라 입력 설정의 데이터에 둔다. 루브릭 본문은 "지정된 차원 중 몇 개"로 쓰고, 로더는
형식에만 의존하므로 다음 대상에서 차원만 갈아끼운다. 동시성 주장에 쓰는 현재 목록은 넷이다.

| 차원 | 묻는 것 |
| --- | --- |
| `latency` | 지연과 처리 시간이 어떻게 달라지는가 |
| `resource` | CPU, 연결, 메모리를 더 쓰는가 덜 쓰는가 |
| `failure` | 실패 양상이 바뀌는가. 대기, 교착, 요청 오류, 재시도 |
| `complexity` | 코드와 운영에서 더 챙길 것이 생기는가 |

규모는 차원에 두지 않는다. 요청이나 인스턴스가 늘면 지연과 자원이 변하는 것이라 별도 차원이 아니라 두 차원의
조건이고, 차원으로 두면 그 둘과 늘 같이 움직인다. 규모는 `tradeoff_validity`의 전제 쪽에서 본다.

`failure`를 남긴 근거는 이 대상에 있다. 가장 강한 격리 수준에서 중복은 0건인데 요청 오류가 전 회차에 발생한
관찰이 이 차원이고, "중복이 0건만으로 성공이라 판단할 수 없다"는 기준을 축으로 옮긴 자리다.

### `tradeoff_validity`

분모는 명시된 교환 항목들이고, **'교환 없음' 선언도 분모에 들어간다.** 이것이 없으면 모든 차원을 '없음'으로
채워 `coverage`를 만점으로 만들고 `validity`는 볼 항목이 없어 분모가 빈다. 선언의 좌표는 왜 교환이 없는지의
근거다.

| 칸 | 조건 |
| --- | --- |
| 1 | 좌표 없는 일반론이 하나 이상 있다 |
| 2 | 전부 좌표가 있지만, 좌표가 가리키는 것이 그 항목을 뒷받침하지 않는 것이 있다 |
| 3 | 모든 항목이 좌표와 맞는다 |
| 4 | 3에 더해, 항목마다 어느 전제에서 성립하는지 적혀 있다 |
| 5 | 4에 더해, 그 전제가 뒤집히는 값을 지목했다. 어느 수치를 넘으면 반대가 되는지 |

2점 칸을 따로 둔 이유가 있다. 그럴듯하지만 좌표 없는 문장이 생성 쪽이 가장 잘 쓰는 종류이고, 1-4에서 근거 없는
문장이 넷 있는 초안이 더 높은 점수를 받은 역전이 그 자리였다. 그 문장이 3점을 받지 못하게 칸을 고정한다.

### 통과 조건과 정렬

`READY`는 게이트 위반 0, 미판정 0, 그리고 모든 주장이 해당 축의 하한을 넘은 것이다. 사실 주장은 앞의 두 축으로
판정한다. 하한 판정은 코드가 한다. 점수는 재료이고 통과는 채점자가 정하지 않는다.

채점 근거는 축마다 산출물을 인용해 적는다. 축 이름을 되풀이한 근거는 조건을 보지 않은 것이다.

리포트의 정렬은 주장별로 하한 미달 축 수가 많은 순, 같으면 칸 합이 낮은 순이다. 루브릭의 주 용도가 이 정렬이다.
주장 전부의 근거를 정독하는 것과 미달 주장부터 정독하는 것은 비용이 다르다.

## 10. 보류 후보: 다섯째 축

**주장 문장 자체의 판정 가능성**을 재는 축이 후보로 남아 있다. 한 주장이 두 가지를 말하는지, 정도 부사로
참·거짓이 갈리지 않는지를 본다. 분모가 주장 문장 하나라서 네 축과 겹치지 않고, 사람의 채택·기각 비용을 직접
좌우한다.

지금 넣지 않는 이유가 둘이다. 금칙 수식어와 접속사는 기계가 세므로 축에 남는 판단은 "한 주장이 둘을 말하는가"
하나이고, 그것은 `grounding`이 상당 부분 잡는다. 두 가지를 말하는 주장은 인용 하나가 그 문장을 함의하지 못해
3점을 넘지 못한다. 그리고 run이 하나도 없는 상태에서는 기존 축 중 어느 것도 그 성질을 재지 않는다는 근거를
적을 수 없다.

올리는 조건을 적어 둔다. **사람이 채택·기각할 때 "이 주장은 갈라서 봐야 한다"가 두 건 이상 나오면** 그때
축으로 올린다. 한 번만 나온 문제는 그 run의 기록으로 남기고 두 번째 사례를 기다린다.

## 11. 종료 상태

| 상태 | 조건 |
| --- | --- |
| `READY` | violation 0 + unmeasured 0 + 모든 주장이 해당 축 하한 충족 |
| `FAILED` | 반복 상한까지 위반이나 미달이 남았다 |
| `ERROR` | 단계 실행 자체가 진행하지 못했다 |

반복 상한은 2다. 실패가 "인용이 없거나 어긋남"이면 한 번의 재수집으로 대개 닫히고, 반복이 깎는 것은 자료의
완성도이지 주장의 참이 아니다. 상한에 닿으면 `FAILED`로 남기고 통과 산출물을 만들지 않는다. 단계 실행 실패와
사본 경로 오류는 반복을 태우지 않는다.

## 12. 도구와 쓰기 범위

**읽기와 검색은 준다. 쓰기는 자기 산출 파일로 막는다.** 출처에서 어디를 봐야 하는지 찾는 것이 이 하네스의
작업이므로 파일 검색을 빼면 단계가 성립하지 않는다.

| 대상 | 권한 |
| --- | --- |
| run 폴더의 자기 산출 파일 | 쓰기 |
| 출처 스냅샷, 대상 코드, 답안, 단계 1 산출 | 읽기·검색 |
| 수집 사본 | 수집 시점에만 쓰기. 이후 읽기 |
| 게이트·루브릭·프롬프트·지점 목록 | 없음 |
| 네트워크 | Gen과 Critique만. 가져온 것은 즉시 사본으로 떠서 해시 |

v0에서 네트워크를 막았던 것을 열었다. 과제가 웹 검색까지 허용하므로 통로는 열고 판정은 사본에 대고 한다.
사본을 떠 두지 않으면 재실행이 같은 판정을 내지 못하고 페이지가 바뀌면 기록이 무너진다.

판정 경로가 변경 목록에 나타나면 `judge_path_touched`로 탈락한다. 승인이나 샌드박스를 우회하는 플래그는
기본값에도 두지 않는다.

## 13. 실패 기록

실패는 분류와 규칙 id를 붙여 남긴다. 분류는 구조 위반, 게이트 위반, 품질 미달, 역할 침범, 미판정, 단계 실행
실패, 반복 상한 초과다. 품질 미달과 미판정은 파이프라인이 정상 동작한 결과다.

모델 응답 원문은 파싱 전에 저장한다. 성공해도 저장한다. 성공한 검사의 세부는 파일로 남기지 않는다.

iteration마다 주장 집합을 원장에 남긴다. 신고 대조가 그 이력에 걸려 있고, 철회된 주장이 리포트에 실린다.

## 14. 리포트

사람이 읽는 순서대로 네 묶음을 낸다.

1. 주장별 표 — 주장, 종류, 인용, 축별 칸, **채택·기각 빈 칸**. §9의 정렬을 따른다.
2. 왼쪽에 인용문, 오른쪽에 사본의 그 줄 범위를 떠낸 두 칸 대조. 사람이 출처를 찾아 열지 않게 한다.
3. Gen과 Critique의 서술이 어긋난 자리, 그리고 철회된 주장과 그 이유.
4. 단계 1의 자기 평가와 테스트 결과가 어긋난 지점, 그리고 그 자리에 붙은 주장과 근거.

주장 종류를 1번 표에 적는 것이 필요하다. 두 축으로 판정된 주장과 네 축으로 판정된 주장을 섞어 읽으면 칸 수가
다른 이유를 모른다.

4번이 두 산출물을 잇는 자리다. 테스트가 빨간불을 준 지점의 근거가 1차 출처 인용으로 닫히면, 판정 기준이
"AI가 맞다고 한다"에서 "소스와 테스트가 맞다고 한다"로 옮겨간 것이 한 화면에 보인다.

## 15. 재사용과 교체

| 재사용 | 교체 |
| --- | --- |
| `runner.py`의 단계 오케스트레이션, 반복 루프, 파일 핸드오프 | 프롬프트 4벌 |
| `ledger.py`, `report.py`, `validate.py`, 스키마 로더 | 루브릭 축과 칸 조건 |
| `stages/scripts/*` — LLM 클라이언트, payload, textio | `input.schema.json` → 코드·답안·단계 1 산출 + 사본 해시 |
| 루브릭 파일 형식과 그것을 읽는 코드 | 게이트 내용 → 인용·커버리지·좌표 검증 |
| 변경 신고 대조 게이트의 구조 | 규칙 카드 내용 |
| 규칙 카드 형식, `tools/replay_gate.py` | — |
| 역할 분리 — 발의와 반영을 가름 | — |

새로 만드는 것은 셋이다. 동시성 API 지점 추출기, 인용과 좌표의 사본 대조, 출처 수집과 해시다.

G0는 쓰지 않는다. 컴파일할 대상이 없다.

**재사용 코드는 복사하고, 복사한 파일 목록을 `BUILD.md`에 적어 변경 금지로 둔다.** 공용 모듈로 빼는 것은
이번 범위가 아니다. runner를 추출하는 리팩터링을 하네스 제작과 같은 작업에 섞으면 어느 쪽이 깨졌는지 가를 수
없다. 세 번째 하네스가 같은 파일을 요구할 때 별도 작업으로 올린다.

## 16. v0에서 바꾼 것과 이유

| 자리 | v0 | v1 | 왜 |
| --- | --- | --- | --- |
| 주장 목록 | 사람이 쓴 입력 | Gen의 산출 | 판단이 어려운 자리를 전부 사람에게 돌리면 사람이 읽을 양이 늘어난다. 과제가 사람에게 맡긴 것은 채택·기각이다 |
| 집합을 묶는 장치 | `claim_set_changed` | `coverage_gap` + 변경 신고 | 입력이 없으므로 입력 대조가 성립하지 않는다. 기계가 만든 지점 목록이 분모가 된다 |
| 축 점수 | 미충족 주장 수로 가름 | 주장별 칸, 합산 없음 | 분모가 하네스 산출이면 평균을 내는 순간 어려운 주장을 지워 올리는 길이 열린다 |
| 트레이드오프 | 축에 없음 | `coverage`와 `validity` 둘 | 주장만으로는 판단 재료가 안 된다. 명시 여부와 정확성은 다른 것이라 축을 가른다 |
| 탐색 성실성 | `counter_evidence` 축 | Critique 스키마 필수 필드 + `limiting_clause_missed` | 재려던 것이 판단이 아니라 산출물의 구조였다. 축은 1점을 주고 지나가지만 스키마는 비는 것만으로 탈락한다 |
| 깊이 | 게이트가 하한, 축은 보조 | 축이 본체, 게이트는 자기 앵커 도달까지 | Gen이 앵커를 적으므로 게이트가 순환한다 |
| 네트워크 | 차단 | 통로로 허용, 사본에 대고 판정 | 과제가 공식 문서와 웹 검색을 허용한다 |
| 코드 의존 | `code_dependent` 축 후보 | 게이트 `claim_site_unknown` | 좌표가 지점 목록 안에 있는지는 문자열로 갈린다 |

run을 돌린 뒤 바꾼 것은 아래 넷이다. 책상에서 읽을 때는 보이지 않았고 실물을 돌려야 나왔다.

| 자리 | 처음 | 지금 | 무엇이 그렇게 만들었나 |
| --- | --- | --- | --- |
| 지점 좌표 | 주장당 하나, 경로 문자열 | 배열, 지점 id | 지점이 24개라 주장 수가 지점 수를 따라가야 했다. 한 줄에 두 API가 있으면 좌표가 같아 한쪽을 덮은 주장이 다른 쪽까지 덮은 것으로 세어졌다 |
| 출처 등급 | primary·measured 둘 | target을 더해 셋 | 선택 주장의 증거는 코드인데 등급 표에 코드가 없어 인용할 자리가 없었다 |
| 좌표 형식 | `경로:12` 만 | 범위와 스냅샷 경로까지 | 여러 줄 측정 표를 가리킬 수 없었고, 좌표를 저장소 뿌리에만 붙여 해석했다 |
| `limiting_clause_missed` | violation | observation | 통과를 막는 쳇바퀴가 됐고 재수집이 상한을 넘겨 두 번 탈락했다 |

## 17. 아직 없는 것

- 느린 루프가 없다. `slow-loop`, `fixed-point`, `moving-yardstick`, `sample-gate`의 체크리스트는 해당없음이고,
  두 번째 루프를 만들 때 돌린다.
- 축 쌍 상관을 볼 표본이 없다. `tradeoff_coverage`와 `tradeoff_validity`가 같이 오르내릴 가능성이 남아 있다.
  분모를 다르게 둔 것이 구조적 방어이고, 임계는 run이 쌓인 뒤에 정한다. 기록 몇 건으로 축을 합치지 않는다.
- 재채점 분산을 측정한 기록이 없다. `tradeoff_validity`가 입장을 고정한 축에 가까워 센 축보다 흔들릴 것으로
  추정되지만, 축별 임계는 run이 쌓인 뒤에 정한다.
- `limiting_clause_missed`가 실제로 탈락을 내는지 확인된 적이 없다. 탈락 횟수가 계속 0이면 Critique이 제한
  조항을 가져오지 않는 것인지 Gen이 놓치지 않는 것인지를 따로 가른다.
- 실행 trace가 없으면 정보 차단은 payload 차단까지만 집행되고 프롬프트 지시는 확인할 수 없다.
