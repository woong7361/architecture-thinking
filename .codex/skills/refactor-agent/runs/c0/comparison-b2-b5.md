## 행위 보존 — *방법*의 차이 (②)

둘 다 6 GREEN이지만 **보장의 성격이 다르다**:
- **파이프라인** = worktree 게이트로 **기계 검증** — 결정적, 거짓 불가. 매 구현 시도마다 자동으로 동결 경계 `.feature`를 돌린다.
- **B-5** = 커밋마다 **사람이 `mvn`을 눈으로** 확인.

→ 파이프라인의 행위보존 보장이 **더 객관적·재현 가능**하다. (단 게이트는 동결 경계만 보므로 "관측 가능한 행위" 한정 — 내부 불변식까지 증명하진 않는다.)

## B-2 비평과의 연결 (③) — arc를 닫는다

B-2가 이 코드를 두 축으로 비평했다. **파이프라인이 그 진단을 실제로 반영했나:**
- **Testability** (B-2: "순수 규칙 하나 검증하려 해도 외부 의존 전체를 Mock으로 세워야 한다")
  → 파이프라인이 결정을 `Ticket`으로 이동 → `new Ticket().reserveBy()` **Mock 0개** = **B-2가 지목한 바로 그 문제를 해결.**
- **Flexibility** (B-2: "포인트결제 추가 시 OCP 위반, 단 YAGNI라 지금 틀린 건 아니다")
  → 파이프라인이 OCP를 **DEFER**(v<2) = **B-2의 판단과 일치.**

→ 파이프라인이 **원 비평을 이해하고 그대로 반영**했다. B-5도 같은 방향(둘 다 B-2를 옳게 해석).

## 어느 쪽이 더 나았나 — 정직한 판정

| | 승 |
|---|---|
| **완성도** | 근접(파이프라인이 #24까지) — 미세하게 **B-5**(개명#1 포함 6기법) |
| **불변식·테스트 용이성** | **대등** |
| **과설계 억제** | **B-5** (파이프라인은 refine 과교정으로 `of()` 도입) |
| **granularity(한 커밋 한 기법)** | **B-5** |
| **속도·재현성·기계 검증** | **파이프라인** |

> **결론:** 완성도·규율·과교정 억제는 사람(B-5) 승. 파이프라인은 진단 일치·행위 안전·YAGNI에서 대등하고
> **빠르며·재현 가능·기계 검증**되고, 자기 약점을 Critique로 드러낸다. B-6가 의도한 "리팩토링 **제안** 에이전트"의
> 위치 그대로 — 대체가 아니라, **사람이 검토·완성하는 검증된 1차 후보**를 낸다.

### 언제 어느 쪽 (결정 가이드)

- **파이프라인** — 빠른·재현 가능·기계 검증된 **1차 리팩토링 후보**가 필요할 때. 진단·행위보존은 믿고, 완성은 사람이.
- **사람(B-5식)** — 완전성, 커밋 granularity, 과교정 억제, 도메인 판단이 중요할 때.

### 핵심 관찰 — 1차 리팩토링은 하되, *그 뒤에 생기는* 부가 리팩토링은 못 한다

파이프라인은 **원본을 한 번 진단→구현**한다. 리팩토링은 종종 **하고 나서야 새 정리거리가 생긴다**(추출로 만든 중복 #2 등).
B-5는 **C1→C6 다중 커밋**이라 "C1/C2로 추출 → C6로 그 중복 제거"처럼 **자기가 만든 결과를 다음 단계가 이어서 정리**한다.
파이프라인은 (현재) **단일 패스**라 이 후속(emergent) 사슬을 못 잇는다 — refine 루프는 *품질 미달을 고치는* 되먹임이지
*성공한 리팩토링 위에 다음을 쌓는* 것이 아니다. → 개선: **PASS 산출물을 새 baseline으로 다시 태우는 다회차**가 B-5의 C1→C6 자동화.

## 과설계 사례 기록 (수행내용 #3)

- **억제 성공**: B-2 답안의 "결제수단을 Strategy로"(OCP, Type B)를 **제안하지 않았다** — 확정 결제수단 카드 1개뿐이라
  `v<2 → DEFER`. 참조 2부 게이트가 결정적으로 억제(`Type B ∧ v<2 ∧ GO` 위반 0). B-5도 동일 DEFER.
- **발생 1건**: refine(설계 2바퀴)이 R3를 **`Ticket.of()` 팩토리**로 바꿔 도입 — **호출처 0개 Type C(Speculative Generality)**.
  저장소 재배선이 스코프 밖인데 그 통로를 미리 만든 **과교정**. **Critique가 `over_engineering`으로 포착**했고,
  이후 루브릭에 **Type C 룰**(호출처 0 새 public/추상 → 최대 3)을 추가해 다음 실행부터 감점된다.
- → 즉 이 kata에서 파이프라인은 **의도된 과설계(OCP)는 억제**했으나, **refine 과교정으로 새 과설계(`of()`)를 냈고**,
  그것을 **자기 Critique가 잡고 결정적 룰로 후속 차단**한다. 억제·탐지 모두 **감이 아니라 게이트 규칙**으로 재현 가능하다.
