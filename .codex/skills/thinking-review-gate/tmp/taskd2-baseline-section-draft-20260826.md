이 절은 “왜 명세가 필요한가”를 다시 설명하기보다 “이전 방식에서 무엇을 바꿨는가”를 보여주는 절로 바꾸는 것이 좋습니다. 앞 절에서 이미 도메인 정책을 AI의 기준선으로 삼겠다는 결론까지 냈기 때문입니다.

제목은 `AI가 따라갈 기준선을 명세로 남겼다`를 추천합니다. 앞 절 마지막 문장의 “AI가 따라갈 기준선”을 그대로 받아서 행동으로 전환됩니다. 기존 제목을 유지하면 도메인 정책과 기준선이라는 말이 앞 절과 반복됩니다.

절의 흐름은 다음처럼 바꾸면 됩니다.

1. 이전에는 정책을 주고 곧바로 테스트 코드를 만들게 했다.
2. 이제는 AI가 구현과 무관한 명세 후보만 만들게 했다.
3. 사람인 내가 정책과 맞는지 검토하고 승인한 명세를 동결했다.
4. AI는 동결된 명세를 기준으로 현재 구현에 필요한 연결 코드와 단위 테스트를 만들었다.
5. 설계가 바뀌면 연결 코드와 단위 테스트만 다시 만들고 명세는 남겼다.

도입 문단은 다음처럼 쓸 수 있습니다.

> 이전에는 AI에게 정책을 주고 곧바로 테스트 코드를 만들게 했다. 이번에는 순서를 바꿨다. AI는 먼저 클래스나 메서드 이름이 없는 도메인 명세 후보만 만들었다. 내가 정책과 맞는지 확인해 승인한 명세는 동결했다. 그 뒤 AI가 이 명세를 기준으로 현재 구현에 필요한 연결 코드와 단위 테스트를 만들게 했다.

기존 다이어그램은 한글 문자 폭과 공백 정렬에 의존하는 가로 구조라 블로그 렌더러에 따라 쉽게 깨집니다. 정렬이 필요 없는 세로 흐름으로 바꾸는 편이 안전합니다.

```text
도메인 정책
↓
AI가 명세 후보 생성
↓
사람이 검토하고 승인
↓
명세 동결
↓
AI가 연결 코드와 단위 테스트 생성
↓
테스트 실행

설계가 바뀌면  연결 코드와 단위 테스트만 다시 생성

```

다이어그램 아래에서는 명세와 생성 코드를 다시 구분하면 됩니다.

> 동결한 명세에는 도메인 용어와 바깥에서 관찰할 수 있는 결과만 남겼다. 클래스 이름과 내부 호출 방식은 적지 않았다. 반면 연결 코드와 단위 테스트는 현재 구현을 알아야 하므로 동결하지 않았다. 설계가 바뀌면 AI가 명세를 기준으로 다시 만들게 했다.

이후에는 현재의 연결 코드 사례를 그대로 붙일 수 있습니다. 사람이 읽는 명세 문장은 바뀌지 않았지만 내부 상태를 직접 바꾸던 연결 코드는 컴파일 단계에서 깨졌고, 유스케이스를 호출하도록 고치자 다시 동작했다는 사례입니다. 이 사례가 “명세는 남고 구현에 묶인 코드는 다시 만든다”를 실제로 보여줍니다.

선택지는 세 가지입니다.

1. 제목, 도입, 다이어그램을 모두 바꾼다. 앞 절과 중복을 없애고 실제 작업 방식으로 바로 넘어가므로 추천합니다.
2. 제목은 유지하고 도입과 다이어그램만 바꾼다. 수정은 적지만 앞 절과 제목의 표현이 반복됩니다.
3. 다이어그램만 고친다. 깨짐은 해결되지만 절의 역할이 여전히 앞 절의 결론을 되풀이합니다.
