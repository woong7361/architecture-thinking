맞습니다. 현재 표의 `예`는 범위를 너무 넓게 잡았습니다. AI가 테스트나 명세 후보, 연결 코드를 생성하는 단계까지 포함하면 같은 입력에 항상 같은 산출물이 나온다고 할 수 없습니다.

결정적인 것은 AI가 아니라 고정된 산출물과 테스트 실행기입니다. AI가 만든 테스트나 명세를 사람이 승인해 고정한 뒤 기계가 실행할 때에만 같은 코드에 같은 판정이 나옵니다. AI에게 매번 다시 생성하게 하면 기준 자체가 달라질 수 있습니다.

따라서 표 앞에 다음 문장을 추가하는 것이 좋습니다.

> 여기서 같은 답을 낸다는 것은 AI가 같은 답변을 만든다는 뜻이 아니다. AI가 만든 기준을 사람이 고정하고, 기계가 그 기준을 실행했을 때 판정이 같다는 뜻이다.

표도 `예/아니오` 대신 조건과 트레이드오프를 드러내도록 바꿔야 합니다.

| 판정 방식 | 같은 답을 얻는 조건 | 구현이 바뀌면 | 트레이드오프와 이번 관찰 |
| --- | --- | --- | --- |
| AI에게 직접 묻는다 | 보장할 수 없다 | 다시 물을 때 답이 달라질 수 있다 | 빠르지만 지적 4건이 실제 실패 2건을 놓쳤다 |
| AI가 만든 테스트 코드를 실행한다 | 생성된 테스트 코드를 고정한 뒤 기계가 실행한다 | 테스트 위치와 호출 방식도 따라 바뀐다 | 실행 결과는 일정하지만 구현 경계를 고정한다 |
| 승인한 도메인 명세를 실행한다 | 명세와 연결 코드를 고정한 뒤 기계가 실행한다 | 명세는 남고 연결 코드는 다시 만든다 | 명세 변경 0줄로 2건을 검출했지만 연결 코드 검증이 필요하다 |

표 뒤의 결론도 `AI가 결정적으로 바뀌었다`는 뜻으로 읽히지 않도록 고쳐야 합니다.

> AI 자체가 결정적으로 바뀐 것은 아니다. AI의 역할을 판정에서 기준 후보와 연결 코드를 만드는 일로 옮겼다. 사람이 기준을 승인해 고정하고 기계가 실행하게 하자 통과와 실패가 같은 형태로 남았다. 대신 사람의 승인 비용이 생겼고, AI가 만든 연결 코드가 제대로 실패하는지는 따로 검증해야 했다.

이 방식의 핵심 트레이드오프는 분명합니다. 매번 AI의 판단을 받는 편의성을 포기하는 대신, 사람이 기준을 승인하는 비용과 연결 코드를 검증하는 비용을 부담하고 판정의 재현성을 얻은 것입니다.
