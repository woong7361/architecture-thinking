## FB-B2-01에 삽입할 답변

**답변:**

외부 사실이 필요하더라도 `Ticket`이 외부 API를 직접 호출하게 하지는 않을 것 같습니다. 애플리케이션 서비스가 자신이 소유한 outbound port를 호출하고, adapter가 외부 응답의 DTO·상태 코드·장애를 `BlacklistStatus`나 `EligibilityFacts` 같은 우리 도메인 값으로 번역한 뒤 domain에 전달하겠습니다. 외부 형식의 번역은 adapter가, 번역된 사실이 예약 가능 여부에 어떤 의미를 갖는지는 domain이 판단합니다.

그러면 도메인 규칙 테스트는 외부 API를 Mock하지 않고 `EligibilityFacts` 값만 넣어 검증할 수 있습니다. 다만 서비스의 조립 테스트에는 outbound port의 Fake나 Stub이 여전히 필요합니다. 외부 시스템이 기존 사실의 공급자만 바꾸는 경우에는 core를 유지할 수 있지만, 외부 응답 때문에 새로운 업무 규칙이 생겼다면 그 정책까지 adapter에 숨기지 않고 domain을 변경해야 합니다.

실시간 판정이라면 번역만으로는 충분하지 않습니다. 조회와 예약 사이에 결과가 바뀔 수 있으므로 판정 시각과 만료, 상태 전이 직전 재확인, 필요하면 버전이나 잠금 같은 일관성 조건도 함께 정해야 합니다.

## FB-B2-02에 삽입할 답변

**답변:**

조립 흐름은 내부 메서드 호출보다 유스케이스의 입력과 최종 결과를 보는 인수테스트로 검증하는 것이 맞다고 생각합니다. 다만 실제 결제 시스템까지 매번 호출하는 종단 간 테스트만으로 모든 분기를 덮기보다는, inbound port부터 실제 service와 Testcontainers DB까지 묶고 결제처럼 통제하기 어려운 외부만 Stub으로 바꾼 컴포넌트 인수테스트를 중심에 두겠습니다. 성공, 결제 실패, 저장 rollback처럼 조립과 transaction이 중요한 대표 경로를 최종 상태와 외부 요청으로 단언합니다.

순수 예약 규칙은 값 기반 단위 테스트로 넓게 검증하고, 저장소와 결제 adapter는 통합·계약 테스트로 각각 확인하겠습니다. 실제 배포 설정과 네트워크까지 포함하는 E2E는 핵심 사용자 경로에 소수만 둡니다. 이 조합은 조립 오류, 도메인 규칙 오류, 외부 계약 오류를 서로 다른 테스트에서 빠르게 국소화하는 대신 테스트 수준이 여러 층으로 나뉘는 관리 비용이 생깁니다.

## FB-B2-03에 삽입할 답변

**답변:**

추상화 시점을 구현 개수 하나로만 고정하기보다 실제 변화의 증거로 판단하겠습니다. 두 번째 결제수단이 구현 대상으로 확정됐거나, 같은 분기가 여러 곳에 복제되고, 결제 변경 때문에 예매 코드가 반복해서 열리거나, 결제수단별 소유권과 생명주기가 독립되기 시작하면 역할을 추출할 시점입니다. 반대로 가능성만 있고 변경 증거가 없다면 인터페이스를 먼저 만들지 않겠습니다.

YAGNI를 지키는 것이 아무 준비도 하지 않는다는 뜻은 아니라고 봅니다. 지금은 결제 호출과 결과 해석을 한곳에 모으고 예약 규칙과 분리된 테스트로 보호해, 실제 변경이 왔을 때 한 지점에서 추출할 수 있게 하겠습니다. 이렇게 하면 현재 복잡도는 낮게 유지할 수 있지만 첫 확장 시 리팩터링 비용은 감수해야 합니다. 공개 계약이나 데이터 마이그레이션처럼 나중에 되돌리기 어려운 변경이라면 가능성과 실패 비용을 함께 평가해 더 일찍 경계를 만들겠습니다.

## FB-B2-04에 삽입할 답변

**답변:**

포인트 결제의 transaction 범위가 다르다는 이유만으로 예매 유스케이스 전체를 바로 분리할 필요는 없다고 생각합니다. 먼저 카드와 포인트가 같은 사전조건·사후조건·완료 상태·실패 의미를 지킬 수 있는지 보겠습니다. 둘 다 `결제가 성공하면 즉시 예약을 확정할 수 있다`는 계약을 지키고 차이가 결제 구현 내부에 머문다면, 공통 예매 흐름은 application service에 두고 `PaymentMethod`만 다형화하는 것이 더 작은 경계입니다.

반대로 결제 방식에 따라 예매 순서, transaction 소유, `PENDING` 같은 완료 상태, 보상·재시도 정책까지 달라져 같은 계약을 유지할 수 없다면 `PaymentMethod.pay()` 뒤에 억지로 숨기지 않겠습니다. 이때는 다형성의 단위를 `ReservationFlow`로 올려 결제별 흐름이 자신의 일관성 전략을 소유하게 합니다. `PaymentMethod`는 공통 흐름을 보존하지만 의미가 다른 결제를 묶으면 거짓 추상화가 되고, `ReservationFlow`는 차이를 정직하게 드러내지만 공통 조회·검증·저장 중복과 구조 복잡도가 늘어납니다.

transaction 경계는 이 객체 경계만 정한다고 자동으로 생기지는 않습니다. 포인트와 티켓이 같은 DB와 transaction manager에 참여한다면 하나의 local transaction으로 묶을 가능성이 있지만, 외부 카드 승인은 local rollback 대상이 아니므로 승인 취소나 재시도 같은 보상이 필요합니다. 현재 피드백에서는 순서·상태·복구 정책의 차이까지 확정되지 않았으므로 우선 `PaymentMethod`에 머물고, 그 차이가 예매 흐름 전체로 실제 전파될 때 `ReservationFlow`로 경계를 올리겠습니다.
