## 문제 지점

- [제출물 반영 완료] `taskC-3.md`에 다이어그램, 다섯 시나리오, 500자 이상의 Why 설명과 체크 표시를 작성했다는 주장은 `input.md`의 확인된 문맥만으로 검증할 수 없습니다. 수정된 파일 내용이나 diff가 근거로 제공되지 않았습니다.
- [근거 추적성] 여러 프로젝트 파일 경로를 제시하지만 관련 클래스, 메서드, 문서 제목까지 연결하지 않아 사용자가 주요 claim을 빠르게 확인하기 어렵습니다. 특히 과제 요구사항, Fake의 Port 구현 관계, 제출물의 각 구성 요소에는 더 구체적인 anchor가 필요합니다.
- [환경 관련 claim] “현재 로컬 `JAVA_HOME`이 Java 8이면 JDK 17 바이트코드를 실행하지 못하는 환경 차이가 실제로 확인됐다”는 내용은 Checked Context에 없습니다. 확인된 사실은 JDK 17을 명시해 테스트를 통과했다는 것뿐입니다.
- [C-2와 영속성 모델] `C-2의 판단`과 `TicketJpaEntity`는 Checked Context에 근거가 없습니다. 또한 “이번 과제에서는 분리합니다”라는 표현은 C-3 제출물에 목표 설계만 반영했다는 뜻인지 실제 코드를 변경했다는 뜻인지 불분명합니다.
- [완료 상태와 계획의 혼재] “실행하고 증명합니다”, “자동 확인합니다”, “같은 이미지를 사용합니다” 같은 표현 때문에 C-5와 C-6에서 수행할 계획이 이미 완료된 작업처럼 읽힙니다. 마지막 문단에서 일부 미구현 항목을 밝히지만, 일곱 보완점 전체의 현재 상태는 명확하지 않습니다.
- [결제 보상 범위] `CancelChargePort`를 목표 설계로 선택한 이유가 walking skeleton의 필수 성공 기준과 연결되지 않았습니다. 저장 실패 후 정합성 문제를 해결한다는 방향은 타당하지만, 보상 실패를 처리할 내구성 있는 기록과 재시도가 미결정인 상태에서 즉시 취소만 목표안으로 확정하면 새로운 실패 경로를 남길 수 있습니다.
- [Repository 복사 의미] 복사본 사용이라는 제안만으로는 얕은 복사인지 깊은 복사인지, 어떤 가변 상태를 격리하는지 확인할 수 없습니다. 실제 변경 시점과 Map에 저장된 객체가 공유되는 경로를 특정해야 수정과 회귀 테스트가 검증 가능합니다.
- [교체 가능성 검증] “Core diff 없음”은 비교 기준점이 정의되지 않으면 재현 가능한 증거가 아닙니다. 두 구성에서 동일 Feature를 실행하는 것 역시 실행 프로필, 조립 방식과 결과 저장 위치가 명시되어야 Adapter 교체 증명이 됩니다.
- [테스트 결과 재현성] 8개 시나리오와 53개 Step의 통과 결과는 유효한 근거지만 실행 디렉터리, 실제 명령, JDK 버전 확인 방법과 결과 artifact 위치가 없어 사용자가 그대로 재현하기 어렵습니다.

## 확인 필요

- 수정된 `task3/assignments/taskC-3.md`에 초안이 열거한 구성 요소와 체크 표시가 실제로 존재하는지 확인해야 합니다.
- C-2 문서의 결정 내용과 현재 코드베이스에 `TicketJpaEntity`가 존재하는지, 아니면 후속 구현에서 새로 만들 계획인지 확인해야 합니다.
- Java 8 환경 차이를 실제로 관찰한 로그나 실행 결과가 있는지 확인해야 합니다.
- C-3의 제출 범위가 목표 구조 문서화까지인지, C-5와 C-6의 구현 변경까지 선행하는 것인지 구분해야 합니다.
- 결제 보상을 C-5 또는 C-6의 필수 범위로 채택할지, 기존 결함을 명시적으로 남기고 별도 결정으로 분리할지 사용자 판단이 필요합니다.
- 다섯 시나리오 각각의 When이 어떤 Inbound Port 연산과 1:1로 대응하는지 제출물에서 실제로 확인해야 합니다.

## 수정 제안

- 제출물 작성 완료 claim마다 `taskC-3.md`의 정확한 제목이나 항목명을 anchor로 연결하고, 가능하면 변경 diff를 근거로 추가합니다.
- 일곱 보완점을 `현재 확인된 문제`, `C-3 문서에 반영`, `C-5 구현·검증 예정`, `C-6 구현·검증 예정`, `사용자 결정 필요`로 구분해 상태를 명시합니다.
- Checked Context에 없는 Java 8 환경 claim은 삭제하거나, 실제 명령과 결과를 근거에 추가한 뒤 제한된 환경에서 확인한 사실로 표현합니다.
- C-2와 `TicketJpaEntity`의 근거를 추가할 수 없다면 특정 선행 결정에 의존한다는 표현을 제거하고, Domain 모델과 영속성 모델 분리를 하나의 설계 대안으로 낮춰 제시합니다.
- `CancelChargePort`는 확정안이 아니라 조건부 추천으로 표현하고, 즉시 보상, 승인·확정 분리, 결함 특성화 유지의 선택 기준에 구현 비용, 정합성 보장 수준과 보상 실패 처리까지 포함합니다.
- Repository 제안에는 공유 참조가 발생하는 코드 경로, 필요한 복사 범위, 저장 실패 후 재조회하는 회귀 시나리오를 연결합니다.
- Adapter 교체 증빙에는 동일 Core 기준점, 두 조립 구성, 실행 명령, GREEN 결과 위치와 자동 의존성 검사 대상을 명시합니다.
- 기존 테스트 결과에는 실행 위치, `mvn clean test` 명령, 사용한 JDK 버전 확인 결과를 함께 제공하고 새 설계의 검증 결과와 명확히 분리합니다.

## 요약

초안은 기존 구조가 이미 헥사고날의 핵심 방향을 가진다는 결론과 Inbound Port 대안의 trade-off를 명확히 제시합니다. 다만 제출물 반영 여부와 일부 환경·설계 claim의 근거가 입력에서 추적되지 않고, 완료된 작업과 후속 계획이 섞여 있으므로 정확한 파일 anchor와 항목별 상태 구분이 필요합니다.
