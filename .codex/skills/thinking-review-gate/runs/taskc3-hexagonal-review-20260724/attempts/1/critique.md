## 문제 지점

- [사용자 요청 충족] 사용자는 `taskC-3.md`의 내용을 확인하고 보완 사항을 제출물에 적어 달라고 요청했지만, 초안은 무엇을 반영했다는 작업 요약만 제공합니다. 실제 제출물의 위치나 수정된 핵심 내용이 없어 사용자가 결과를 확인할 수 없습니다.
- [헥사고날 구조 판정] `TicketService`가 Outbound Port에 의존한다는 근거는 제시했지만, 이를 곧바로 “헥사고날의 핵심을 갖추고 있다”라고 판정하려면 Driver 측 경계, 의존 방향, Adapter 구성까지 어떤 기준으로 충족하거나 미충족하는지 구분해야 합니다.
- [C-3의 목적] C-3을 “기존 설계를 명시적인 헥사고날 구조로 완성하고 증명하는 과제”라고 단정했습니다. 과제 요구가 기존 구조의 식별과 설명인지, 별도 Inbound Port 추가까지 요구하는지는 `task3/assignments/taskC-3.md`의 문구와 연결해 설명해야 합니다.
- [Inbound Port 선택] `ReserveTicketUseCase.reserve(command)`를 도입한 이유는 제시했지만, 서비스 공개 메서드를 그대로 Application 경계로 사용하는 대안과의 trade-off가 없습니다. 별도 인터페이스가 헥사고날의 필수 조건처럼 받아들여질 수 있습니다.
- [제출물 반영 내역] “C-2부터 C-6까지 연결해 추가로 손볼 일곱 가지”라고 했지만 일곱 가지를 열거하지 않아 개수와 내용을 검증할 수 없습니다.
- [결제 보상 설계] 저장 실패 시 `CancelChargePort`로 보상하도록 “고정했다”고 했지만, 과제 요구사항인지 개선 제안인지 구분되지 않습니다. 취소 실패 처리, 멱등성, 트랜잭션 경계 같은 조건도 빠져 있어 구현 방향을 확정하기에는 근거가 부족합니다.
- [In-memory Repository 개선] “복사본 반환이나 저장 성공 시 반영”만으로는 객체 참조 공유 문제를 어떻게 막는지 불명확합니다. 저장 시 복사, 조회 시 복사, 불변 객체 사용 등 선택지별 의미와 검증 시나리오가 필요합니다.
- [검증 결과의 범위] 기존 B-5 테스트 통과는 현재 동작의 회귀 여부만 보여줍니다. 새로 제안한 Inbound Port, 보상 처리, Repository 의미 수정, Adapter 교체 가능성이 검증됐다는 근거는 아닙니다.
- [근거 추적성] 파일명과 테스트 수치는 일부 제시됐지만 정확한 파일 경로와 확인 지점이 충분하지 않습니다. 특히 실제로 수정했다는 `taskC-3.md` 제출물과 그 변경 내용을 직접 따라갈 수 없습니다.
- [범위 불일치 가능성] 마지막 문장의 `C-0`은 확인된 문맥에 근거가 없으며 오기인지 별도 과제인지 판단할 수 없습니다.

## 확인 필요

- `task3/assignments/taskC-3.md`가 기존 구조의 분류와 설명만 요구하는지, 별도 Inbound Port 인터페이스와 코드 변경까지 요구하는지 원문 기준으로 확인해야 합니다.
- 실제 제출물이 어느 파일에 반영되었으며, 현재 상태·목표 구조·Gherkin·Why 설명·추가 보완점이 문서에 들어갔는지 확인해야 합니다.
- `ReserveTicketUseCase`와 `CancelChargePort`가 이미 제출물 또는 코드에 추가된 것인지, 향후 제안인지 구분해야 합니다.
- “일곱 가지” 보완 항목의 전체 목록과 각 항목이 C-3 제출 범위인지 후속 C-4~C-6 작업인지 확인해야 합니다.
- `C-0`이 실제 과제 식별자인지 오기인지 확인해야 합니다.

## 수정 제안

- 첫 결론을 “이미 헥사고날의 핵심 의존 방향은 적용되어 있으나, C-3에서는 각 요소와 경계를 명시하고 근거를 제출해야 한다”처럼 충족한 부분과 보완할 부분을 분리해 작성합니다.
- 실제 수정한 제출물 경로와 반영한 섹션을 명시하고, 사용자가 바로 검토할 수 있도록 핵심 결과를 답변에도 요약합니다.
- `taskC-3.md`의 요구 항목마다 현재 코드의 대응 요소와 근거 파일을 연결합니다. 예를 들어 Core, Inbound 경계, Outbound Port, Adapter, Gherkin When을 각각 어느 파일에서 확인할 수 있는지 제시합니다.
- 별도 Inbound Port 도입과 `TicketService` 공개 메서드 유지라는 두 접근을 비교하고, C-5의 When-Port 1:1 매핑과 C-6의 HTTP Driver 추가 계획 때문에 전자를 추천한다는 조건부 판단으로 바꿉니다.
- 추가 보완 사항을 모두 열거하고 `C-3 제출물에 즉시 반영할 내용`, `C-4~C-6에서 구현·검증할 내용`, `기존 결함으로 별도 결정이 필요한 내용`으로 범위를 나눕니다.
- 결제 보상은 확정된 요구가 아니라 설계 대안으로 표시합니다. 즉시 보상, 상태 기록 후 재처리, 현재 특성화 유지의 trade-off와 추가 결정 사항을 함께 적습니다.
- Repository 문제는 저장·조회 시 복사 또는 도메인 객체 불변화 같은 대안을 비교하고, 저장 실패 뒤 조회 결과가 바뀌지 않아야 한다는 검증 시나리오를 연결합니다.
- 기존 테스트 통과와 제안 사항 검증을 분리합니다. 현재는 회귀 테스트만 통과했고 후속 구조와 동작은 아직 미검증이라고 명확히 표시합니다.
- 근거 없는 `C-0` 표현을 확인 후 수정하고, “완성했다”, “고정했다” 같은 표현은 실제 변경과 검증이 확인된 경우에만 사용합니다.

## 요약

초안은 기존 구조가 헥사고날의 핵심 방향을 이미 가진다는 판단과 주요 보완 후보를 잘 포착했습니다. 그러나 실제 제출물 내용과 위치, 과제 요구와 선택적 개선의 경계, 대안별 trade-off가 드러나지 않아 사용자가 반영 결과를 검증하기 어렵습니다. 특히 Inbound Port와 결제 보상을 필수 결론처럼 단정하지 말고, 과제 원문과 프로젝트 파일에 연결된 조건부 추천으로 수정해야 합니다.
