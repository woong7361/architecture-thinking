## 문제 지점

- [근거 anchor 부족] 초안의 핵심 결론은 입력 맥락과 대체로 일치하지만, 사용자가 따라갈 수 있는 파일 근거가 답변 안에 직접 드러나지 않는다. 특히 `PROBLEM.md:14-37`의 Goodhart 위험과 calibration set, `.codex/skills/refactor-agent/pipeline/runner.py:203-216`의 `Eval PASS` 중심 조건을 연결하면 답변 검증성이 더 좋아진다.

- [현재 B-6 사례 claim] “현재 B-6에는 `Eval PASS + Critique high` 충돌이 이미 있으므로”라는 문장은 중요한 근거 claim인데, 초안 안에서는 그 충돌이 어디서 확인되는지 표시되지 않는다. 입력의 Checked Context에 있는 내용인지, 별도 artifact에서 확인한 사실인지 구분해야 한다.

- [표현 범위 과대] “자동화할 수 있는 것은 사실 신호다”는 표현은 너무 넓다. 사실 신호라도 해석이 필요한 경우가 있고, 자동화 가능한 것은 “결정적으로 판정 가능한 신호”에 가깝다. 현재 초안도 뒤에서 테스트, 스키마, 정적 규칙을 예로 들고 있으므로 앞 문장을 좁히는 편이 일관적이다.

- [초안 밖 예시의 근거 약함] “호출처 0 public API” 같은 예시는 입력 맥락에 명시된 근거가 아니며 의미도 다소 압축되어 있다. 자동화 가능한 신호의 예시로 유지하려면 일반 예시임을 분명히 하거나, 입력에 있는 테스트·스키마·정적 규칙 중심으로 줄이는 편이 낫다.

## 확인 필요

- `Eval PASS + Critique high` 충돌이 사용자가 바로 확인할 수 있는 어느 artifact나 파일에 기록되어 있는지 확인하면 좋다.
- 최종 답변이 “slow-loop이 필수”를 어떤 수준의 필수로 말할지 정해야 한다. 모든 실행 중간 승인인지, 조건부 escalaton인지, calibration set 유지인지 구분이 필요하다.

## 수정 제안

- 첫 문단의 결론은 유지하되 “모든 실행 중간 승인”이 아니라 “proxy와 실제 품질의 정렬을 확인하는 조건부 slow-loop”이라고 더 명확히 고정한다.
- 핵심 근거를 짧게 추가한다. 예: `PROBLEM.md:14-37`은 rubric 점수 최적화가 실제 품질 최적화로 오인될 위험을 기록하고, `runner.py:203-216`은 Eval PASS만 최종 PASS 조건으로 삼아 Critique 약점이 gate를 막지 않는 구조라고 연결한다.
- “자동화할 수 있는 것은 사실 신호다”를 “fast-loop은 테스트, 스키마, 정적 규칙처럼 결정적으로 판정 가능한 신호를 처리한다”로 좁힌다.
- 현재 B-6 충돌 문장은 “입력 맥락 기준으로” 또는 구체 파일 경로와 함께 제시해 근거 위치를 분명히 한다.
- 세 가지 운영 방식 비교는 좋으므로 유지하되, 추천안인 위험 기반 slow-loop가 언제 발동되는지 신호 충돌, rubric 변경, 새 유형, 표본 감사, 낮은 신뢰도처럼 조건 목록을 더 명확히 정리한다.

## 요약

초안의 방향은 맞다. Goodhart 위험 때문에 사람의 slow-loop이 필요하다는 결론과 “모든 실행 승인자가 아니라 품질 기준의 소유자”라는 구분도 좋다. 다만 핵심 claim에 파일 근거가 직접 붙어 있지 않고, 자동화 가능한 신호의 범위가 조금 넓게 표현되어 있어 검증 가능성과 경계 설정을 보강해야 한다.
