## 문제 지점

- [외부 사례 근거] draft는 Spring PetClinic, Buckpal, Netflix, Shopify 사례를 근거로 사용하면서 “현재 저장소 구조”, “이 사례는 … 보여준다”처럼 비교적 확정적인 표현을 쓴다. 그러나 input에는 해당 링크를 실제로 확인했다는 컨텍스트가 없다. 최종 답안에서 이 표현을 유지하려면 링크의 해당 파일과 사례가 실제로 그 내용을 담고 있는지 확인한 근거가 필요하다.

- [Jakarta Persistence claim] “Entity를 영속 Domain 객체로 설명하며 업무 메서드를 가지는 것을 금지하지 않는다”는 핵심 근거로 쓰이고 있다. 링크는 있으나 명세의 어느 절 또는 어떤 문장에 기대는지 독자가 바로 따라가기 어렵다. 특히 “금지하지 않는다”는 명시 조항이 아니라 해석일 가능성이 있으므로, 근거 위치를 더 좁히거나 “명세상 엔티티가 업무 메서드를 가져서는 안 된다는 제약은 확인되지 않는다”처럼 추론 경계를 드러내는 편이 안전하다.

- [현장 표의 P 표현] “Legacy Schema 또는 여러 데이터 소스” 행에서 “모델 변환과 변경 전파가 생겨 P가 드러날 가능성이 높다”고 쓰는데, P는 앞에서 “Persistence가 그 규칙을 침범하고 있다는 증거”로 정의되어 있다. 이 행은 D가 없을 때도 P 가능성을 말하는 것처럼 읽힐 수 있어, D와 P의 의존 관계가 약간 흐려진다.

- [저장 전략 설명] 분리 방식 설명에서 “기존 객체라면 Adapter가 관리할 JPA Entity를 조회해 Domain에서 변경된 상태를 반영한 뒤 저장”을 대표 구현으로 제시한다. 실무적으로 가능한 선택지지만, 이 방식은 추가 조회와 변경 병합 책임을 Adapter에 둔다는 비용이 있다. draft 안에서 바로 뒤에 Mapper 비용을 말하긴 하나, 이 저장 전략 자체의 trade-off가 충분히 명시되지는 않았다.

## 확인 필요

- 외부 링크가 실제로 draft의 설명과 일치하는지 확인해야 한다. 특히 Spring PetClinic `Owner`, Buckpal `AccountPersistenceAdapter`, Netflix, Shopify 사례는 현재 링크 기준으로 구조나 내용이 바뀌었을 가능성이 있다.

- Jakarta Persistence 3.2 명세에서 Entity 정의, 생성자 요구, Proxy 또는 persistence lifecycle 관련 제약을 뒷받침할 수 있는 위치를 확인해야 한다.

- Task C-2 제출 환경이 최소 400자만 요구하는지, 아니면 너무 긴 답안이 감점 요인이 될 수 있는지 확인하면 좋다. 현재 draft는 요구를 충족하지만 분량이 꽤 길다.

## 수정 제안

- 외부 사례 문장은 “현재 저장소 구조” 대신 “링크한 코드 기준으로 확인하면” 또는 “예시로 볼 수 있다”처럼 확인 기준을 명확히 하라. 실제 확인하지 않았다면 사례 단락의 단정 강도를 낮추라.

- Jakarta Persistence 문장은 명세의 구체 위치를 추가하거나, “업무 메서드를 금지하지 않는다”를 “업무 메서드 금지를 직접 요구하는 근거는 아니다”처럼 해석임을 드러내라.

- 현장 표의 Legacy Schema 행은 “P가 드러날 가능성이 높다”보다 “D가 있는 영역에서는 저장 모델 차이가 P로 이어질 가능성이 높다”로 바꾸면 앞선 `D AND P` 기준과 더 일관된다.

- 저장 전략 설명에 “기존 JPA Entity를 조회해 반영하는 방식은 ID, Version, 자식 식별자 보존에는 유리하지만 Adapter가 변경 병합 책임을 갖는 비용이 있다”는 한 문장을 추가하라.

## 요약

draft는 사용자가 지적한 D/P 기준 중복 문제를 대부분 해결했다. `나의 분리 기준`이 먼저 나오고, 현장 섹션은 이를 적용하는 역할로 재배치되어 성공 기준과 잘 맞는다. 남은 보완점은 외부 사례와 명세 근거의 확인 가능성을 높이고, 몇몇 단정 표현의 추론 경계를 더 분명히 하는 것이다.
