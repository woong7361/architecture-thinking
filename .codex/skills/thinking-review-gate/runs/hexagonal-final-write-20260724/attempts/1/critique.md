## 문제 지점

- [근거 없는 구체 예시] `ReserveTicketUseCase`, `TicketReservationHttpAdapter`, `ReservationApplicationService`, `LoadTicketPort`, `InMemoryTicketAdapter`, `POST /tickets/T-100/reservations`, `U-10` 같은 식별자와 시나리오가 입력 문맥에 anchor되어 있지 않다. 지금 형태는 실제 코드나 기존 문서에 있는 이름처럼 읽혀서 사용자가 검증하기 어렵다.
- [입력에 없는 업무 규칙 추가] 입력에서 확인된 규칙은 `판매 중지된 티켓은 예약할 수 없다`인데, 초안은 `중복 예약 규칙`까지 함께 넣었다. 새 규칙을 추가하면 설명의 초점이 흐려지고, 근거 없는 확장으로 보일 수 있다.
- [사실과 해석의 경계 불명확] Cockburn 원문과 DIP 원문을 근거로 삼는다고 했지만, 본문 각 claim이 원문에서 직접 오는 원칙인지, 이번 과제 맥락에서의 설계 해석인지 구분되지 않는다. 특히 Port가 어떤 타입을 써야 하는지, Domain과 JPA Entity를 분리하는 방식, 테스트를 어디서 나눠 검증하는지는 권장 설계에 가깝다.
- [Adapter가 왜 인프라인지의 명시성 부족] 초안은 Adapter가 바깥 구현체라는 설명은 했지만, 왜 그것이 인프라로 분류되는지 한 문장으로 못 박지 않았다. 입력 제약에는 구현체라는 점뿐 아니라 인프라인 이유까지 포함되어야 한다.

## 확인 필요

- 초안에 넣은 클래스명과 HTTP 예시가 `task3/assignments/taskC-1.md`나 앞선 답안에 실제로 등장하는지 확인이 필요하다. 없다면 예시라고 밝히거나 일반 명칭으로 바꿔야 한다.
- `중복 예약`을 이 답안에 포함할 근거가 실제 과제 문맥에 있는지 확인이 필요하다. 현재 입력만 보면 확실한 규칙은 `판매 중지 티켓 예약 금지`다.
- 원문 근거를 답안 안에서 더 직접 연결할 수 있는지 확인이 필요하다. 지금은 참고 링크만 있고, 어떤 문장이 어떤 근거에 기대는지 따라가기가 어렵다.

## 수정 제안

- 예시는 입력에서 이미 확인된 재료 중심으로 줄여라. `SaveTicketPort`, `TicketJpaAdapter`, `Ticket.reserveBy(UserId)`, `판매 중지 티켓`만으로도 설명이 충분하다.
- 새로 만든 식별자를 유지할 거면 실제 코드가 아니라 설명용 예시라는 점을 먼저 밝혀라. 그렇지 않으면 역할명 중심의 일반 서술로 바꾸는 편이 낫다.
- `중복 예약 규칙`은 빼거나, 반드시 넣어야 한다면 그 규칙이 어디서 왔는지 근거를 추가하라.
- 핵심 claim마다 성격을 짧게 구분하라. 예를 들어 `이 부분은 Cockburn의 경계/port 관점`, `이 부분은 DIP의 소스 코드 의존 역전`, `이 부분은 이번 티켓 예시에 적용한 해석`처럼 연결하면 검증 가능성이 올라간다.
- Adapter 설명에는 `Adapter는 Core가 정의한 Port를 HTTP, JPA 같은 외부 기술로 연결하는 구현체이기 때문에 인프라에 속한다`는 문장을 직접 넣어라.
- Domain/JPA 분리, In-memory 대체, 통합 테스트 분리는 보편 법칙처럼 쓰지 말고 `이 과제의 목표인 기술 누수 방지와 테스트 비용 절감을 위해 이렇게 배치할 수 있다`는 톤으로 낮춰라.

## 요약

초안의 큰 구조와 설명 흐름은 맞지만, 검증 가능성을 떨어뜨리는 임의 예시와 입력에 없는 규칙 추가가 있다. 새로 만든 이름과 시나리오를 정리하고, 원문 근거와 해석의 경계를 더 분명히 하면 critique 기준에 더 잘 맞는다.
