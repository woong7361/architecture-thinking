## 문제 지점

- [매핑 고위험 기준] `두 개 이상이면 전면 분리 대신...`이라는 임계값이 새로 제안되지만, 왜 2개가 기준인지 근거가 없다. 현재 문맥에서는 휴리스틱으로 볼 수 있으므로 단정형 기준처럼 보이면 사용자가 검증하기 어렵다.
- [P=true 예시] Lazy collection 예시는 방향은 맞지만, 실제로 어떤 문제가 생기는지 조금 더 구체화할 필요가 있다. 예를 들어 영속성 컨텍스트 밖에서의 접근, 암묵적 DB 조회, 단위 테스트가 실제 실행 조건을 가리는 문제처럼 P의 피해가 더 직접적으로 드러나야 한다.
- [추가 용어] `command만 분리`, `query는 projection`은 사용자의 원 질문인 P/M 판단보다 한 단계 뒤의 구현 전략이다. 설명 없이 들어가면 핵심 게이트보다 부가 패턴이 더 어렵게 느껴질 수 있다.
- [사실/선택 구분] `M이라는 이름과 세부 점수표는 제거할 수 있다`, `세 번째 방안을 추천한다`는 답변자의 선택이다. 근거는 있지만, “현재 과제 답안에서는 이렇게 단순화하는 편이 낫다”처럼 선택의 범위를 더 명확히 표시하면 좋다.

## 확인 필요

- `P`의 명칭을 사용자가 이전 답변에서 `Persistence pressure` 또는 `영속성 압력`으로 받아들였는지 확인하면 좋다. 초안은 개념을 설명하지만, 기호 자체의 이름을 다시 고정하지는 않는다.
- 매핑 고위험 질문의 `2개 이상` 기준을 과제용 임시 기준으로 둘지, 더 약하게 “하나라도 크면 경계 재검토”로 표현할지 결정이 필요하다.
- `command/query/projection` 같은 용어를 최종 답변에 유지할지, 사용자의 현재 질문에 맞춰 제거할지 판단이 필요하다.

## 수정 제안

- 매핑 비용 기준은 “정량 규칙”이 아니라 “전면 분리 전에 멈춰서 재설계할 신호”라고 낮춰 표현한다.
- P 예시에서는 Lazy Loading 자체보다 “업무 규칙 실행이 JPA 런타임 조건에 의존하게 되는 순간”을 더 명확히 써라. 단위 테스트에서는 통과하지만 실제 JPA 환경에서는 트랜잭션, 프록시, fetch 전략에 따라 실패하거나 성능 문제가 드러날 수 있다는 식이면 좋다.
- `command만 분리하고 query는 projection` 문장은 삭제하거나, 유지한다면 “조회 모델은 굳이 Domain Entity로 왕복 변환하지 않는다” 정도로 풀어 써라.
- 최종 게이트에서 `M`을 완전히 버린다는 인상을 줄이지 말고, “분리 여부의 원인은 아니지만 분리 범위와 방식의 제약으로 남긴다”로 정리하라.
- 추천안의 성격을 “현재 Task C-2 답안 기준으로는”이라고 제한하면 과도한 일반화가 줄어든다.

## 요약

초안은 사용자의 핵심 질문인 P의 역할과 M의 위치를 대부분 잘 답한다. 보완할 부분은 매핑 위험 임계값의 근거 부족, P=true 예시의 실행상 피해 구체화, 그리고 부가 구현 용어가 답변을 불필요하게 어렵게 만들 수 있는 점이다.
