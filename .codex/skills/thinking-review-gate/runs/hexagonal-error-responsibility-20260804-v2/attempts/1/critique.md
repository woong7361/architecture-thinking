## 문제 지점

- [도메인 불변식 책임과 코드 예시] 본문은 `Ticket`이 자신의 불변식을 직접 강제한다고 말하지만, 예시 코드는 `ticket.ensureReservable()`를 application service가 먼저 호출한 뒤 `ticket.assignTo(...)`를 따로 호출한다. 이 형태만 보면 `assignTo()` 단독 호출 경로에서 불변식이 빠질 수 있어, 주장과 코드가 완전히 맞물리지 않는다.
- [결제 거절 처리 추천의 단정도] 입력에는 "결제 거절이 정상 업무 결과인지 예외 상황인지 확정할 수 없다"는 제약이 있는데, 초안의 도입부와 최종 추천은 혼합형을 사실상 기본 권장안처럼 읽히게 쓴다. 옵션 섹션의 조건이 최종 결론까지 충분히 연결되지 않는다.
- [근거의 적용 범위] Hexagonal 원문과 AWS 문서는 port/adapter 경계 원칙을 설명하지만 `Optional`, `ChargeResult`, `UserNotFoundException` 같은 구체 계약 형태를 직접 권장하지는 않는다. 초안이 이 점을 한 번 언급하긴 하지만, 표와 코드 예시에서는 웹 검색 결과의 정답 패턴처럼 보일 여지가 남아 있다.
- [사용자 질문의 직접성] 사용자의 핵심 질문은 "`if (user == null) throw ...`와 `if (!paymentApi.charge(...)) throw ...`가 각 객체의 예외 책임을 정하는 문제인가"인데, 초안은 패턴 설명은 충분해도 이 질문에 대한 직접 답을 초반에 짧고 명확하게 고정하지 않았다.

## 확인 필요

- 결제 거절을 이 시스템에서 예상 가능한 정상 결과로 다루는지, 아니면 예외 중심으로 단순화해도 되는지 요구사항이나 결제사 계약을 확인해야 한다.
- `Ticket`이 예약 가능 여부 확인과 상태 변경을 하나의 behavior로 묶을 수 있는 현재 도메인 모델인지 확인해야 한다.
- 답변에서 "웹에서 직접 확인된 권장"과 "그 근거를 바탕으로 한 현재 예제용 설계 추천"을 분리해 표현할지 확인해야 한다.

## 수정 제안

- 도입부에 한 문장으로 직접 답을 먼저 고정하라. 예: "이 문제는 모든 `throw`를 각 객체로 밀어 넣는 문제가 아니라, 외부 실패 해석은 adapter, 유스케이스 조율은 application service, 자기 상태 불변식은 domain entity가 맡는 책임 분리 문제다."
- `Ticket` 예시는 `ensureReservable()`와 `assignTo()`를 분리한 채 두지 말고, 불변식이 실제로 엔티티 안에 있다는 점이 드러나도록 behavior를 하나로 묶거나, 최소한 `assignTo()`도 내부에서 같은 검사를 수행한다고 설명하라.
- 혼합형 추천은 조건부 표현으로 낮춰라. 최종 권장 문장에 "결제 거절이 예상 가능한 정상 결과라면"이라는 전제를 다시 붙이고, 전제가 다르면 예외 중심안도 단순하고 타당한 대안이라고 바로 이어서 적는 편이 안전하다.
- 표와 코드 예시 앞에 "아래는 웹 문서가 직접 규정한 정답이 아니라, port/adapter 분리 원칙과 DDD validation guidance를 현재 예제에 적용한 설계안"이라는 경계 문장을 추가하라.
- Microsoft/Fowler 근거는 DDD와 실패 표현의 일반 원칙으로 위치시키고, Hexagonal 자체의 직접 규범처럼 읽히지 않게 문장을 정리하라.

## 요약

초안의 방향은 맞지만, 현재 형태는 "헥사고날이 직접 권장한 패턴"과 "근거를 바탕으로 한 조건부 설계 추천"이 섞여 보인다. 특히 `Ticket` 불변식 책임 주장과 코드 예시의 연결이 약하고, 결제 거절을 result로 둘지 예외로 둘지의 전제가 최종 권장까지 충분히 이어지지 않았다.
