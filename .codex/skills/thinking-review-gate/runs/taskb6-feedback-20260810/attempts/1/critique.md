## 문제 지점

- [근거 앵커] 초안은 `runner.py`, `final.json`, `critique.json`, `comparison-b2-b5.md`, `PROBLEM.md`의 내용을 근거로 쓰지만 본문 안에는 구체 파일·라인 앵커가 거의 없다. `input.md`에는 라인 근거가 정리되어 있으므로, 최종 답변에서도 핵심 claim 옆에 최소한 `runner.py:75-89`, `runner.py:203-216`, `final.json:10-31`, `PROBLEM.md:14-37` 같은 추적 가능한 앵커를 붙이는 편이 좋다.

- [전체 결론] “네 피드백 모두 타당하다”, “현재 파이프라인의 판정 구조에 실제 허점이 있다”는 결론이 강하게 시작된다. 뒤에서 근거를 제시하지만, 첫 문단만 보면 검토 범위 밖의 전체 정답 판정처럼 읽힐 수 있다. “확인한 산출물 기준으로는” 또는 “현재 입력 범위에서는”처럼 판정 범위를 앞에서 제한해야 한다.

- [FB-B6-01] 행위 게이트와 설계 품질 판정을 분리하는 방향은 타당하지만, 초안 일부 표현은 여전히 `PASS`의 의미를 넓게 해석하는 문제를 남긴다. “현재 `PASS`는 품질이 객관적으로 입증됐다는 뜻으로 쓰기 어렵다”는 문장은 좋지만, 이어지는 후보에서는 `behavior=GREEN`, `quality=candidate`, `human review=pending` 같은 새 상태 모델을 제안한다. 이 상태 모델은 초안의 근거에서 직접 나온 사실이 아니라 개선안이므로 “제안”임을 더 분명히 표시해야 한다.

- [FB-B6-02] `Ticket.of()`를 “현재 범위의 실패”로 판단하는 논리는 입력 근거와 맞지만, 실제 저장소 구현이 입력 범위 밖이라는 불확실성이 결론보다 뒤에 배치되어 있다. 이 불확실성은 판단을 바꿀 수 있는 조건이므로 후보 1의 추천 문장에도 같이 붙어야 한다.

- [FB-B6-03] “실제 Git 커밋 대신 되돌릴 수 있는 불변 checkpoint를 써도 된다”는 말은 합리적인 설계 제안이지만, 입력 근거에는 직접적인 구현 방식 근거가 없다. 새 용어인 `checkpoint`의 의미와 검증 조건을 설명하지 않으면, 파울러식 작은 커밋 리듬을 약화시키는 임의 대체안처럼 보일 수 있다.

- [FB-B6-04] proposal preflight 후보는 유용하지만, 어떤 검사는 결정적으로 가능한지와 어떤 검사는 LLM 판단에 남는지가 섞여 있다. 예를 들어 “호출처 0인 새 public API”는 정적 검사에 가깝지만, “기법 하나”, “변경 범위”, “선행 단계”는 규칙 정의가 필요하다. 이를 구분하지 않으면 Gen 품질 개선이 다시 LLM 자기검수로 흐를 위험을 충분히 다루지 못한다.

- [출력 기준] `input.md`의 출력 기준은 각 실질 피드백마다 “피드백의 역할”을 제시하라고 한다. 초안은 “명확화 요구”, “판단 근거 질문”, “설계 대안”, “범위 확장 제안”을 본문에 녹여 쓰고 있지만, 모든 항목에서 독자가 바로 찾을 수 있는 고정 라벨로 드러나지는 않는다.

## 확인 필요

- “동결된 6개 시나리오”라는 숫자가 실제 과제 파일이나 실행 산출물에 근거가 있는지 확인해야 한다. 현재 제공된 `input.md`의 근거 요약만 보면 “6개”를 직접 확인할 수 없다.

- 실제 `TicketRepository` 영속성 구현이 별도로 존재하며 setter 기반 복원에 의존하는지 확인해야 한다. 이 여부에 따라 `Ticket.of()`를 제거해야 할 과설계로 볼지, 저장소 재배선과 함께 완성해야 할 API로 볼지가 달라진다.

- 최종 답변의 목적이 “피드백에 대한 답변 후보 정리”인지, “다음 파이프라인 개선 우선순위 제안”까지 포함하는지 확인하면 좋다. 초안은 종합 판단까지 제시하므로 유용하지만, 과제 제출용 답변 후보가 목적이면 종합 판단의 비중을 줄일 수 있다.

## 수정 제안

- 각 FB 섹션에 `피드백의 역할:` 라인을 추가해 요구 형식을 명확히 맞춘다. 예: `피드백의 역할: 행위 보존 검증과 설계 품질 판정을 분리하라는 명확화 요구`.

- 핵심 claim마다 최소 1개 이상의 evidence anchor를 붙인다. 특히 FB-B6-01의 `PASS` 구조, FB-B6-02의 `Ticket.of()` 지적, FB-B6-03의 단일 매니페스트 문제, FB-B6-04의 Goodhart 위험은 파일·라인 또는 실행 산출물 앵커가 필요하다.

- “네 피드백 모두 타당하다”를 “확인한 과제 답안, 피드백, 파이프라인 산출물 기준으로 네 피드백 모두 실질 쟁점이 있다”처럼 범위를 제한한다.

- “6개 시나리오”가 근거 파일에서 확인되지 않으면 “동결된 경계 테스트”로 바꾸거나, 확인 가능한 원문 앵커를 붙인다.

- `checkpoint`는 “Git 커밋과 같은 사용자 저장소 변경이 아니라, 파이프라인 내부에서 이전 산출물로 되돌릴 수 있는 기준점”처럼 정의하고, 성공 조건을 “행위 게이트 GREEN 후 새 baseline으로 재진단”으로 제한한다.

- FB-B6-04에서는 preflight를 결정적 검사와 LLM 검토로 나눈다. 예를 들어 “호출처 0 public API 차단”은 정적 검사 후보, “변경 범위와 선행 단계 타당성”은 별도 critique 후보로 분리하면 자기평가 순환 문제를 더 정확히 다룰 수 있다.

## 요약

초안은 피드백 4건의 핵심을 잘 분해했고, 각 항목마다 답변 후보와 트레이드오프도 충분히 제시한다. 다만 최종 답변으로 쓰려면 강한 결론의 범위를 더 좁히고, 파일·라인 근거를 본문에 직접 연결하며, 불확실성과 새 설계 제안을 사실처럼 보이지 않게 표시해야 한다.
