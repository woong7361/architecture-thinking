## 문제 지점

- [사용자 요청 충족 여부] 초안은 무엇을 바꿀지 설명하는 계획문에 가깝다. 사용자는 "다 수정해줘"라고 실행을 요청했는데, 초안에는 실제로 8개 파일을 수정했는지와 작업이 끝났는지가 드러나지 않는다.
- [근거 anchor 부족] `8개 파일에 같은 구조가 있다`, `프로젝트 전체 검색에서 참조를 찾지 못했다`, `섹션 경계를 대신할 수 있다` 같은 핵심 claim에 사용자가 따라갈 수 있는 anchor가 없다. 파일 경로, 검색 패턴, diff 요약, 검증 결과 중 최소 하나가 붙어야 한다.
- [검증 결과 부재] `검증 기준`은 적었지만 실제 검증 결과가 없다. `<!--`와 `-->`가 0건인지, 메타데이터 필드가 유지됐는지, 메타데이터 구간 외 본문이 안 바뀌었는지를 사용자가 확인할 수 없다.
- [결론 형식 미흡] 추천안과 trade-off는 비교했지만, 최종 결론이 "그래서 무엇을 실제로 했는가"로 닫히지 않는다. 현재 문서는 변경 설계 메모처럼 읽히고 완료 보고로는 약하다.

## 확인 필요

- 이 초안이 실제 수정 후 최종 응답 초안인지, 아니면 수정 전 작업 계획 초안인지 확인이 필요하다.
- 실제 수정이 끝났다면 어떤 파일이 변경됐는지와 검증 명령 또는 결과 요약이 필요하다.
- HTML을 제거하면 메타데이터가 보이는 Markdown 텍스트가 된다는 점을 실제 결과 보고에서도 분명히 밝혀야 한다.

## 수정 제안

- 첫 문단을 계획 설명이 아니라 완료 보고로 바꿔라. 예: `task2/assignments/taskB-0.md`부터 `taskB-7.md`까지 8개 파일의 HTML 주석을 Markdown 블록 인용 형식으로 바꿨다.
- 핵심 claim마다 evidence anchor를 붙여라. 최소한 변경 대상 경로 패턴, 검색 대상 문자열, 검증 관점은 답변 안에서 바로 추적 가능해야 한다.
- `검증 기준`만 적지 말고 `검증 결과`를 적어라. 예: HTML 주석 패턴 재검색 결과 0건, 메타데이터 5개 필드 유지, diff 확인 결과 메타데이터 구간만 변경.
- `표현 방식 비교`는 유지해도 되지만 길이를 줄이고, 최종 응답에서는 선택 이유를 한두 문장으로 압축해라. 이 답변의 주목적은 설계 토론이 아니라 수정 완료와 검증 가능성 보고다.
- `섹션 경계를 대신할 수 있어 해당 표식은 제거한다`는 문장은 근거가 약하다. 실제 검색 근거를 붙이거나, 더 보수적으로 `참조처를 찾지 못해 제거했다`처럼 사실과 판단을 분리해라.

## 요약

초안은 선택지 비교 자체는 괜찮지만, 사용자의 실행 요청에 대한 완료 응답으로는 부족하다. 실제 수정 여부, 검증 결과, 추적 가능한 근거를 앞에 세워서 계획문이 아니라 작업 완료 보고로 바꿔야 한다.
