# 결론

세 판단 모두 핵심 방향은 맞다. 다만 다음과 같이 경계를 더 정확히 잡는 편이 좋다.

- FB-B2-01: adapter가 외부 응답을 도메인 값으로 번역하는 것은 맞다. 하지만 새로운 업무 판단까지 adapter에 넣으면 core를 보호한 것이 아니라 정책을 바깥으로 유출한 것이다.
- FB-B2-02: 조립 흐름을 인수테스트로 검증하는 것은 맞다. 다만 모든 실제 외부 시스템까지 호출하는 E2E보다, 인바운드 경계부터 실제 서비스와 DB를 묶고 통제 불가능한 외부만 대역으로 바꾸는 컴포넌트 인수테스트가 주력에 가깝다.
- FB-B2-04: 공통 인터페이스를 유지할 수 있다. 다만 다형성의 단위를 `charge()`가 아니라 트랜잭션과 보상까지 소유하는 예매 흐름 전체로 올려야 한다.

## FB-B2-01 · adapter로 변환하면 core를 유지할 수 있지 않은가

그 생각이 기본적으로 맞다. 외부 API의 DTO, 상태 코드, 벤더 용어가 core 안으로 들어오지 않게 adapter가 우리가 소유한 port의 결과 타입으로 번역해야 한다.

```text
외부 API
   ↓
Adapter: 외부 형식과 실패를 변환
   ↓
Outbound Port: core가 정의한 계약
   ↓
Application Service: 필요한 사실을 수집
   ↓
Domain: 그 사실의 업무 의미를 판단
```

예를 들어 외부 응답을 그대로 넘기지 않고 `BlacklistStatus`, `PaymentHistorySummary`, `EligibilityFacts` 같은 도메인 값으로 바꾼 뒤 `ticket.reserve(userId, facts)`에 전달할 수 있다. 그러면 도메인 테스트는 값만 넣어 검증할 수 있고 외부 API는 Mock하지 않아도 된다.

다만 “core는 동일하게 유지된다”는 말에는 조건이 필요하다.

1. 외부 시스템이 기존에 core가 이미 알고 있던 사실의 새로운 공급자라면 core를 그대로 유지할 수 있다.
2. 외부 응답 때문에 새로운 업무 규칙이 생겼다면 core의 정책은 바뀌어야 한다. 변경을 adapter에 숨기면 adapter가 업무 결정을 소유하게 된다.

예를 들어 벤더의 `code=37`을 `BlacklistStatus.BLOCKED`로 바꾸는 것은 adapter의 책임이다. 반면 `BLOCKED 사용자는 VIP라도 예약할 수 없다`는 판단은 domain의 책임이다. adapter가 바로 `canReserve=false`를 반환하면 외부 변환과 업무 판단의 경계가 섞일 가능성이 있다. 외부 서비스 자체가 최종 판정 권한을 가진 계약이라면 `EligibilityDecision`을 반환해도 되지만, 그 권한 관계가 명시돼야 한다.

또한 adapter는 조회와 예약 사이에 판정이 바뀌는 문제를 해결하지 않는다. 실시간성이 강하다면 판정 시각, 만료, 재확인 또는 잠금 정책을 별도로 가져야 한다.

### 이 피드백에 달 답변

> 외부 의존을 도메인 안에서 직접 호출하게 할 필요는 없다고 봅니다. core가 소유한 outbound port를 두고 adapter가 외부 응답을 `EligibilityFacts` 같은 도메인 값으로 변환한 뒤, application service가 그 값을 domain에 전달하면 됩니다. 그러면 core는 외부 프로토콜을 모르고 값 기반 테스트를 유지할 수 있습니다. 다만 외부 응답이 새로운 업무 규칙을 만든다면 그 판단까지 adapter에 숨겨서는 안 됩니다. 외부 형식의 번역은 adapter가, 번역된 사실의 업무 의미 판단은 domain이 맡아야 합니다.

## FB-B2-02 · 조립 흐름은 E2E 인수테스트가 맞지 않은가

방향은 맞다. 조립 흐름은 내부 메서드 호출보다 사용자가 보는 유스케이스 결과로 검증하는 편이 낫다. 다만 `E2E`가 어디까지를 뜻하는지 나누어야 한다.

| 검증 대상 | 적합한 테스트 | 이유 |
| --- | --- | --- |
| 예약 불가, 상태 전이 같은 순수 규칙 | 도메인 단위 테스트 | 빠르고 값만으로 모든 규칙을 검증할 수 있다 |
| 조회 → 결제 → 저장 조립과 트랜잭션 | 컴포넌트 인수테스트 | 인바운드 경계부터 실제 서비스와 DB까지 검증한다 |
| 저장소와 외부 API 변환 | 어댑터 통합·계약 테스트 | 기술별 오류를 경계에서 국소화한다 |
| 배포된 시스템의 핵심 사용자 경로 | 소수의 E2E 테스트 | 실제 설정과 네트워크까지 포함한 최종 신뢰를 준다 |

HTTP/API부터 실제 서비스와 Testcontainers DB까지 부르고 외부 결제만 Stub 서버로 대체한다면, 이를 넓은 의미의 E2E 인수테스트라고 부를 수도 있다. 하지만 테스트 용어를 엄밀히 쓰면 컴포넌트 인수테스트 또는 유스케이스 통합 테스트에 가깝다.

실제 결제 sandbox까지 호출하는 진짜 E2E만으로 모든 조립 분기를 검증하면 느리고 불안정하며 실패 원인을 찾기 어렵다. 따라서 핵심 성공·실패 경로는 컴포넌트 인수테스트로, 실제 외부 연결은 소수의 계약·E2E 테스트로 확인하는 조합이 비용 대비 효용이 높다.

### 이 피드백에 달 답변

> 조립 흐름은 인수테스트로 검증하는 것이 맞다고 봅니다. 다만 모든 실제 외부 시스템까지 호출하는 E2E를 많이 두기보다는, inbound port부터 실제 service와 DB까지 묶고 결제처럼 통제하기 어려운 외부만 Stub으로 바꾼 컴포넌트 인수테스트를 중심에 두겠습니다. 순수 규칙은 단위 테스트로 넓게 검증하고, 실제 외부 연동은 어댑터 계약 테스트와 소수의 E2E로 보완하면 조립 오류와 외부 계약 오류를 더 빠르게 구분할 수 있습니다.

## FB-B2-04 · 공통 인터페이스가 맞는가

### 1번은 조건부로 맞다

공통 인터페이스가 “결제를 수행해 업무 결과를 돌려준다”는 계약만 가진다면 카드와 포인트를 같은 역할로 묶을 수 있다. 하지만 그 인터페이스가 “결제와 티켓 예약이 함께 원자적으로 끝난다”는 의미까지 암묵적으로 약속하면 문제가 생긴다.

- 포인트와 티켓이 같은 DB와 같은 트랜잭션 관리자 안에 있다면 하나의 로컬 트랜잭션으로 묶을 가능성이 있다.
- 외부 카드 API는 로컬 DB 트랜잭션에 참여할 수 없다. 카드 승인 뒤 티켓 저장이 실패하면 롤백이 아니라 승인 취소나 재처리가 필요하다.
- 포인트 구현이 내부 트랜잭션을 먼저 커밋하고 티켓 저장이 나중에 실패한다면 카드와 같은 부분 성공 문제가 생긴다.

따라서 “트랜잭션 경계가 어긋난다”는 말은 인터페이스를 사용할 수 없다는 뜻이 아니다. 같은 메서드가 구현마다 서로 다른 원자성·실패·복구 보장을 제공하는데 계약에는 그 차이가 드러나지 않는 것이 문제다.

### 2번과 3번은 같은 선택지가 아니다

- 2번은 결제 방식별로 조립 책임을 나누는 구조적 분리다. 각 흐름이 한 요청 안에서 동기적으로 끝날 수도 있다.
- 3번은 결제 대기, 승인, 확정, 취소를 시간에 걸친 상태로 저장하는 생명주기 모델이다. 재시도, 비동기 통보, 장시간 처리가 있을 때 필요하다.

두 축은 서로 독립적이다. 결제 방식별 handler를 두면서 모든 흐름을 동기적으로 끝낼 수도 있고, 각 handler가 상태 기반 워크플로를 사용할 수도 있다. 이전 추천을 정확히 고치면 현재 예제에는 2번이 우선이고, 실제 장시간 처리와 재시도가 요구될 때 3번을 추가하는 편이 맞다.

### 상태 기반 워크플로는 절차지향인가

업무에 순서가 있다고 절차지향 설계가 되는 것은 아니다. 예매는 본질적으로 조회, 결제, 상태 변경, 저장 순서를 가진다. 문제는 순서 자체가 아니라 하나의 메서드가 모든 규칙과 외부 의존의 세부를 소유하는 것이다.

OOP에서도 application service는 얇게 순서를 조율할 수 있다. `Ticket`은 허용되는 상태 전이와 불변식을 지키고, 결제 전략은 결제 방식별 실행과 실패 의미를 소유하며, adapter는 외부 기술을 변환한다. 상태 기반 흐름도 aggregate의 메서드나 State 패턴을 통해 다형적으로 구현할 수 있다. 다만 상태가 두세 개뿐이라면 State 클래스까지 만드는 것은 과설계일 수 있다.

### 다형성을 유지하는 추천 구조

`PaymentMethod.charge()`처럼 결제 한 단계만 추상화하지 말고, 트랜잭션·보상 차이가 실제로 생겼다면 예매 시나리오 전체를 전략으로 만든다.

```java
public interface ReservationFlow {
    PaymentType supports();
    ReservationResult reserve(ReservationCommand command);
}

public final class PointReservationFlow implements ReservationFlow {
    @Transactional
    public ReservationResult reserve(ReservationCommand command) {
        // 포인트 행과 티켓을 필요한 방식으로 잠근다.
        // 포인트를 차감하고 Ticket의 예약 불변식을 실행한다.
        // 같은 로컬 트랜잭션으로 저장한다.
    }
}

public final class CardReservationFlow implements ReservationFlow {
    public ReservationResult reserve(ReservationCommand command) {
        // 외부 카드를 승인한다.
        // 티켓 저장 실패 시 승인 취소 또는 재처리 정책을 실행한다.
    }
}
```

진입점은 `Map<PaymentType, ReservationFlow>` 같은 registry에서 구현을 선택한다. 새 결제수단이 추가돼도 중앙 `switch`를 늘리지 않는다. 공통 예약 규칙은 `Ticket.reserve()`에 남기고, 구현마다 다른 트랜잭션과 보상만 각 flow가 소유한다.

이 구조의 핵심은 “트랜잭션을 인터페이스로 감춘다”가 아니라 “서로 다른 일관성 전략을 다형적인 유스케이스 구현으로 캡슐화한다”는 것이다.

### 트레이드오프

- `PaymentMethod.charge()`를 유지하면 구조가 가장 작지만 트랜잭션과 보상 차이를 호출자가 다시 알아야 할 수 있다.
- `ReservationFlow`로 추상화 높이를 올리면 결제 방식별 차이를 온전히 캡슐화할 수 있지만 공통 조회와 저장 코드가 중복될 수 있다.
- 상태 기반 워크플로까지 도입하면 비동기와 재시도에 강하지만 상태, 멱등성, 타임아웃, 운영 관측 비용이 커진다.

### 이 피드백에 달 답변

> 얇은 결제 인터페이스를 유지할 수는 있지만 `charge()`만으로 트랜잭션 의미의 차이까지 없어진다고 보기는 어렵습니다. 포인트는 같은 로컬 트랜잭션에 참여할 수 있지만 외부 카드 승인은 DB와 함께 롤백할 수 없기 때문입니다. 따라서 차이가 결제 구현 내부에서 끝나면 공통 `PaymentMethod`로 충분하고, 티켓 저장의 원자성이나 보상까지 달라지면 다형성의 단위를 `ReservationFlow` 전체로 올리는 편이 맞습니다. `PointReservationFlow`와 `CardReservationFlow`가 각각 트랜잭션·보상 전략을 소유하고 공통 예약 규칙은 `Ticket`에 남기면 중앙 분기 없이 OOP를 유지할 수 있습니다. 상태 기반 워크플로는 이 구조와 같은 것이 아니라 장시간 처리와 재시도가 필요할 때 추가하는 시간 모델입니다.
