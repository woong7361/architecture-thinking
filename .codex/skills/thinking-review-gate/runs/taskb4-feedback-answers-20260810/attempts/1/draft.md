# Proposed feedback answers for taskB-4

## FB-B4-01

**답변:**

맞습니다. 책임 분해 자체를 목표로 삼으면 객체 안의 응집도는 높아져도 협력 전체를 이해하는 비용은 오를 수 있습니다. 그래서 메소드 수나 메시지 호출 수를 기준으로 자르기보다 실제로 독립해서 바뀌는 이유가 있는지를 먼저 보겠습니다. 현재 설계에서는 예약 판단과 상태 전이는 같은 상태와 규칙 때문에 함께 바뀌므로 `Ticket`에 모으고, `TicketService`에는 예매 유스케이스의 순서를 한눈에 읽을 수 있는 조립 흐름을 남깁니다. 한 메소드마다 객체를 만드는 식으로 더 쪼개지는 않겠습니다.

분리가 과했는지는 변경과 테스트에서 추적하겠습니다. 하나의 요구사항 때문에 분리된 여러 객체가 매번 함께 수정되거나, 값만 전달하는 메소드가 연쇄적으로 늘어나거나, 단순한 유스케이스 테스트에도 많은 test double이 필요해지면 경계가 실제 변경 축과 어긋났다는 신호입니다. 이때는 함께 변하는 책임을 다시 합치겠습니다. 반대로 한 객체에 서로 다른 팀이나 정책의 변경이 계속 충돌하면 더 분리할 근거가 됩니다.

전체 흐름은 `TicketService`의 선형적인 조립 코드와 유스케이스 인수테스트를 기준점으로 유지하겠습니다. 비동기 단계와 재시도·보상처럼 흐름 자체가 복잡해질 때만 별도의 프로세스나 상태 머신을 검토하겠습니다. 즉 SRP로 얻는 변경 격리와 협력을 따라가는 인지 비용을 함께 보고, 어느 한쪽을 절대 기준으로 삼지 않겠습니다.

## FB-B4-02

**답변:**

현재 `charge(...): boolean` 포트에는 호출이 끝날 때 결제 성공 여부도 확정된다는 동기 계약이 들어 있습니다. 따라서 "새 벤더는 어댑터만 추가하면 된다"는 제 주장은 같은 동기 완료 계약을 지키는 벤더 범위에서만 성립합니다.

동기와 비동기 벤더를 처음부터 함께 받는 구조는 만들 수 있습니다. 결제를 즉시 성공 여부를 반환하는 호출이 아니라 결제 시도를 시작하고 결과를 나중에 확정하는 과정으로 모델링합니다. 예를 들어 outbound port는 `requestPayment(...)`로 `PaymentAttemptId`를 반환하고, 결과는 별도의 inbound port로 받습니다. 동기 어댑터는 호출 직후 결과를 확정하고, 비동기 어댑터는 웹훅이 왔을 때 확정합니다. 애플리케이션은 결제 대기 상태와 중복 통보에 대한 멱등성, 만료, 재시도와 보상을 함께 책임져야 합니다.

가능하다는 것과 지금 만들어야 한다는 것은 다릅니다. 현재 카타에서 확인되는 계약은 동기 결제뿐이므로 비동기 상태와 웹훅 처리까지 미리 구현하면 아직 오지 않은 복잡도를 선지불하게 됩니다. 지금은 `ChargePort`가 동기 완료형 벤더를 위한 계약임을 명시하고 지원 범위를 정직하게 한정하겠습니다. 반대로 비동기 벤더가 실제 도입 후보이거나 나중에 상태 모델과 외부 계약을 바꾸는 비용이 크다는 근거가 있다면, 비동기 우선 모델은 과설계가 아니라 예상된 변경 비용을 앞당겨 지불하는 선택입니다.

## FB-B4-04

**답변:**

지적된 `UserRepo`가 코어의 `UserRepository` 인터페이스를 뜻한다면, 코어가 정의하고 DB 구현이 구현하므로 구조적으로는 outbound port 역할을 할 수 있다고 보았습니다. 반면 아래쪽의 구체 구현인 `DB UserRepo`를 뜻한다면 `UserPersistenceAdapter`라고 표현하는 편이 맞습니다. 현재 앵커만으로는 어느 쪽인지 확정하기 어려운데, 다이어그램에서 두 역할이 이름으로 분명히 구분되지 않은 것은 맞습니다.

이번 설계도에서는 헥사고날의 역할을 명시적으로 드러내기 위해 코어 인터페이스를 `LoadUserPort`, DB 구현을 `UserPersistenceAdapter`로 표현하겠습니다. `Repository`라는 이름이 틀려서가 아니라 Port는 애플리케이션이 외부에 요구하는 능력이고 Adapter는 그 능력을 특정 기술로 구현한다는 차이를 선명하게 보이기 위한 선택입니다.

## FB-B4-05

**답변:**

`TicketRepository`도 코어가 계약을 소유하고 외부 DB 구현이 이를 구현한다면 outbound port가 될 수 있습니다. Port는 아키텍처상의 역할이므로 모든 인터페이스 이름에 반드시 `Port`가 붙어야 하는 것은 아닙니다. 그래서 처음에는 Repository 역할명만으로도 헥사고날과 객체지향을 함께 지킬 수 있다고 판단했습니다.

다만 N-tier의 `Service -> Repository` 형태로 작업하다 보면 Service가 데이터를 조회해 판단하고 setter로 바꾸는 데이터 중심 흐름으로 기울기 쉽고, 현재 다이어그램도 Port와 Adapter의 구분을 충분히 보여주지 못합니다. 이번 설계에서는 애플리케이션이 필요로 하는 능력을 `LoadTicketPort`와 `SaveTicketPort`로 표현하고, 하나의 `TicketPersistenceAdapter`가 두 Port를 구현하도록 바꾸겠습니다. 작은 코드에서 인터페이스 수가 늘어나는 비용은 있지만, 헥사고날의 경계를 학습하고 설명하는 현재 목적에는 이쪽이 더 명확합니다.

다만 이름을 `Port`로 바꾸는 것만으로 객체지향이 되는 것은 아닙니다. 데이터 중심 설계를 피하는 핵심은 저장 인터페이스의 이름보다 `Ticket`이 예약 가능 여부와 상태 전이를 스스로 책임하는 데 있습니다. 조회와 저장의 소비자와 변경 축이 계속 같다면 실제 제품 코드에서는 `TicketRepository` 하나를 outbound port로 유지하는 선택도 여전히 가능합니다.

## FB-B4-06

**답변:**

파라미터가 세 개라는 사실만으로 나쁜 계약은 아니지만, 현재 시그니처는 의미가 다른 두 `long`의 순서를 바꿔도 컴파일되고 `String paymentInfo`가 무엇을 보장하는지도 드러나지 않습니다. 결제 방식이나 인증 정보가 추가되면 유스케이스 시그니처와 호출자도 함께 계속 바뀔 수 있습니다.

이 예매 요청에서는 `ReserveTicketCommand`로 입력을 묶고 내부 값을 `UserId`, `TicketId`, `PaymentMethodToken` 같은 의미 타입으로 표현하겠습니다. inbound adapter가 인증된 사용자와 외부 요청을 검증해 Command를 만들고, `TicketService`는 전역 보안 컨텍스트를 직접 읽지 않고 명시적인 입력만 받습니다. 이렇게 하면 단순히 파라미터 개수를 하나로 줄이는 것이 아니라 유스케이스 입력 계약과 검증 경계를 한곳에 모을 수 있습니다.

반대로 내부에서만 쓰이고 입력이 더 늘지 않는 메소드라면 의미 타입 세 개를 그대로 받는 편이 더 단순할 수 있습니다. 하지만 현재 메소드는 외부에서 들어오는 예매 유스케이스의 경계이고 결제 정보가 확장될 가능성이 있으므로 Command 객체가 더 적합하다고 판단합니다.
