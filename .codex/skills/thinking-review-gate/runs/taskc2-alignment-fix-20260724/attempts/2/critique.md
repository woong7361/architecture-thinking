## 문제 지점

- [P 기준] `같은 업무 개념을 여러 Persistence Model이나 데이터 소스에서 구성해야 한다`를 `P=true` 조건으로 둔 부분은 입력 제약과 약하게 충돌할 수 있다. 입력은 Legacy Schema, 여러 데이터 소스만으로 분리를 확정하지 말라고 했는데, 이 문장은 업무 규칙 침범 여부 없이 데이터 소스 다양성 자체를 P 증거로 읽힐 여지가 있다.

- [공개 사례 근거] Spring PetClinic, Buckpal, Netflix, Shopify 사례가 답안의 판단을 보조하지만, 각 링크가 실제로 어떤 범위까지만 입증하는지 세부 근거가 충분히 고정되어 있지 않다. 특히 GitHub `main`/`master` 링크는 시간이 지나며 바뀔 수 있으므로 제출 답안에서는 “현재 링크 기준” 또는 “예시로만 사용” 같은 경계가 더 분명해야 한다.

- [분리 구조 설명] 분리 방식의 의존 방향과 런타임 흐름은 잘 제시되어 있지만, `Application Service`가 어느 패키지에 있고 Domain 행위를 호출한 뒤 Save Port로 넘기는 위치가 구조 예시에는 빠져 있다. 성공 기준의 “Load, Domain 행위, Save의 런타임 흐름”은 대부분 충족하지만, 코드/모듈 배치 차이를 더 명확히 하려면 application service 위치가 함께 보여야 한다.

- [Mapper 비용] 기존 Entity 갱신 시 ID, Version, 자식 식별자와 관계 상태를 잃지 않기 위해 기존 JPA Entity를 조회한다고 설명한 점은 좋다. 다만 “기존 객체라면 Adapter가 관리할 JPA Entity를 조회”가 항상 필요한 방식처럼 읽힐 수 있다. 상황에 따라 merge, dirty checking, 명시적 update query, aggregate 재구성 전략이 달라질 수 있으므로 대표 전략이라는 한계를 표시하는 편이 안전하다.

## 확인 필요

- Spring PetClinic `Owner`가 답안에서 말한 메서드와 매핑을 현재 링크에서 실제로 갖고 있는지 확인이 필요하다.

- Buckpal 예시가 “새 활동만 다시 JPA Entity로 바꿔 저장한다”는 설명과 정확히 일치하는지 확인이 필요하다.

- 과제 제출 맥락에서 외부 공개 사례가 필수인지, 아니면 개인 기준과 구조 설명만으로 충분한지 확인하면 답안 길이와 초점을 더 조절할 수 있다.

## 수정 제안

- `P=true` 조건의 여러 Persistence Model/데이터 소스 항목을 “업무 규칙을 실행하기 위해 여러 저장 모델의 차이를 Core가 알아야 하거나, 그 차이 때문에 테스트와 변경 격리가 깨지는 경우”처럼 바꿔라. 이렇게 하면 현장 조건만으로 분리하지 않는다는 제약과 `D AND P` 기준이 더 일관된다.

- 통합/분리 구조 예시에 `application/service`를 추가하고, 런타임 흐름을 `Application Service -> Load Port -> Adapter -> Mapper -> Domain 행위 -> Save Port -> Adapter -> Mapper/Repository` 순서로 한 번 더 정리해라.

- 공개 사례 문단에는 “이 사례는 결정 기준이 아니라 비용 양상을 보여주는 참고”라는 문장을 유지하되, 각 사례의 입증 범위를 한 문장씩 더 제한해라. 최신 링크 변동 가능성이 있는 GitHub 사례는 커밋 고정 링크를 쓰거나 “현재 저장소 구조 기준”이라고 표시하는 것이 좋다.

- 기존 Entity 갱신 설명은 “대표적인 구현은 기존 JPA Entity를 조회해 Domain 상태를 반영하는 방식”처럼 표현해라. 그러면 특정 저장 전략을 유일한 정답처럼 보이는 문제를 줄일 수 있다.

## 요약

초안은 사용자의 핵심 지적인 현장·사이즈 기준과 `D AND P` 기준의 충돌, 그리고 Domain/JPA Entity 분리 구조 누락을 대부분 보완했다. 남은 약점은 데이터 소스 다양성을 다시 P 조건으로 과하게 읽히게 만드는 문장, 외부 사례의 근거 범위, Application Service를 포함한 흐름의 완성도다.
