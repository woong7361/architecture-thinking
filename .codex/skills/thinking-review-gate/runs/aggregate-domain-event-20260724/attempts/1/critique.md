## 문제 지점

- [근거 경계] 5~7절의 실무 권고 중 일부가 출처나 "추론/실무 관례" 표시 없이 단정적으로 제시된다. 예: `조회는 전용 Query/DTO/Projection으로 해결하는 편이 낫다`, `Handler를 멱등하게 만들어야 한다`, `단순 CRUD의 Entity 하나도 개념적으로는 Aggregate Root일 수 있다`, `Domain Event는 결합을 시간/순서/실패 처리 결합으로 바꾸는 도구다`. 방향성은 타당하지만 현재 anchor 목록만으로는 사용자가 어떤 부분이 원문 근거이고 어떤 부분이 작성자 해석인지 구분하기 어렵다.
- [이벤트 처리 시점 설명] 본문 중간의 흐름도는 `커밋 전후에 Event Handler 실행`으로 넓게 적고, 마지막 문단에서 다시 `커밋 전 같은 트랜잭션`과 `커밋 후 별도 트랜잭션`을 언급한다. 하지만 어떤 종류의 후속 작업이 어느 쪽에 적합한지 기준이 본문 안에서 명확히 닫히지 않아, 사용자가 Domain Event 처리 시점을 규칙처럼 오해할 가능성이 있다.
- [예시 코드의 숨은 전제] `pullDomainEvents()`로 이벤트를 꺼내고 비우는 예시를 보여주지만, 저장과 발행의 순서를 어떻게 맞춰야 유실이나 중복을 피하는지 설명이 없다. 개념 설명용 코드라도 이 전제를 한 줄로 밝혀두지 않으면 구현 패턴으로 오해될 수 있다.

## 확인 필요

- 5~7절의 운영·설계 권고 중 어떤 문장을 `출처 기반 사실`로 둘지, 어떤 문장을 `실무적 해석/추천`으로 낮출지 구분할 필요가 있다.
- Domain Event handler를 같은 트랜잭션에서 처리하는 예와 커밋 후 처리하는 예를 각각 무엇으로 둘지 기준을 확정할 필요가 있다. 최소한 `즉시 일관성 필요 여부`와 `외부 부수효과 여부`로 나눠야 한다.
- Java 예시를 유지할지, 유지한다면 `pullDomainEvents()`가 개념 예시라는 점과 실제 구현에서는 transaction/outbox coordination이 필요하다는 문장을 보강할지 결정이 필요하다.

## 수정 제안

- 5~7절의 단정 문장을 두 부류로 나눠 수정하라. 출처가 있는 내용은 해당 문장 옆에 anchor를 붙이고, 출처가 없는 실무 조언은 `실무에서는 보통`, `이 답변에서는 다음 기준으로 권한다`처럼 톤을 낮춰 사실과 추천을 분리하라.
- Domain Event 처리 시점 설명을 한 문단으로 다시 정리하라. `Aggregate 내부 불변식은 메서드 안에서 즉시 보장`, `같은 일관성 경계 안의 후속 처리만 필요하면 같은 트랜잭션 가능`, `다른 Aggregate나 외부 시스템 반응은 커밋 후/outbox 쪽이 안전`처럼 판단 기준을 명시하면 혼선이 줄어든다.
- Java 예시 바로 아래에 한 줄을 추가하라. 예: 이 코드는 개념 설명용이며, 실제 구현에서는 Aggregate 저장과 이벤트 전달을 같은 트랜잭션 경계 또는 outbox로 조정해야 한다.
- 가능하면 마지막 `실무에서 경계를 찾는 질문` 절 앞이나 뒤에 `여기부터는 원문 정의를 바탕으로 한 실무적 판단 기준`이라는 표지를 넣어, 정의·근거와 실무적 해석을 분리하라.

## 요약

초안의 구조와 개념 설명은 좋지만, 후반부의 실무 권고가 근거 기반 사실인지 작성자 해석인지 경계가 흐리고, Domain Event 처리 시점 기준도 한 번 더 명확히 닫아야 한다. 이 두 지점을 정리하면 사용자가 검증 가능한 답변에 더 가까워진다.
