## 문제 지점

- [사실과 전제의 혼재] “사람이 그 mapping을 이 과제의 계약으로 수용한 뒤 input을 고쳤다”는 시간 순서를 확정 사실로 서술하지만, 제공된 문맥은 사람이 mock PG mapping을 권위 있는 기준본으로 지정하거나 검증했음을 입증하지 않는다. 후반부에서는 이를 다시 “사람이 승인했다는 전제”라고 표현해 답변 내부의 사실 상태도 일관되지 않는다.
- [근거 추적성] 현재 input의 HTTP 계약, 테스트의 `PgChargeAdapter` 미실행, 최초 GREEN 이후 사람의 mapping 확인이라는 핵심 판단에 프로젝트 파일 경로와 해당 위치가 연결되어 있지 않다. 결론은 제공된 문맥과 대체로 부합하지만 사용자가 직접 확인하기 어렵다.
- [계약 권한 모델] “사람이 승인한 명세나 기존 fixture”라는 표현은 명세와 fixture를 같은 권위 수준처럼 읽히게 한다. 기존 fixture는 로컬 동작을 보여주는 근거일 뿐, 사람의 명시적 지정 없이는 계약의 기준본이 아니다.
- [검토 상태의 판정 권한] `REVIEW: REQUIRED`를 만드는 “영향이 큰 미확정 계약”의 판정 기준과 판정 주체가 정의되지 않았다. 이 상태로는 AI가 임의로 검토를 요구하거나, 반대로 중요한 불확실성을 `CLEAR`로 분류할 수 있다.
- [자동 게이트와 최종 수용의 관계] `AUTOMATED_GATE: GREEN`이면서 `REVIEW: REQUIRED`인 경우 실행 결과를 수용할 수 있는지, 누가 검토를 종결하는지, 미해결 상태가 후속 단계 진행을 막는지가 명확하지 않다. “두 번째 자동 정답 게이트가 아니다”라는 설명만으로 운영 의미가 고정되지 않는다.
- [대안 범위] 원문에서 제시한 저장과 결제를 별도 슬롯과 게이트로 분리하는 대안을 직접 비교하지 않았다. 현재 구조에서 전용 계약 테스트를 택하는 이유는 제시했지만, 분리안의 실패 격리 효과와 구조 변경 비용이 빠져 있다.
- [검증 기준 부족] 추가할 계약 테스트가 `POST /charge`, `paymentInfo`, `amount`, HTTP 200의 `approved:true/false`를 각각 어떻게 판정해야 하는지 구체적인 완료 조건이 없다. 특히 `approved:false` 시나리오가 `2xx=승인` 구현을 실패시킨다는 연결을 명시하면 제안의 검증 가능성이 높아진다.

## 확인 필요

- 사람이 `charge-approved.json`과 `charge-declined.json`을 C-6 과제의 권위 있는 계약 기준본으로 실제 승인했는지 확인해야 한다.
- 현재 input의 계약이 어떤 사람 승인이나 원래 과제 명세에 근거해 추가되었는지 확인해야 한다. AI가 mapping에서 추론해 넣은 것이라면 아직 확정 계약으로 취급할 수 없다.
- `REVIEW: REQUIRED`가 정보 제공 상태인지, 사람 승인 전 후속 수용을 보류하는 상태인지 운영 규칙을 정해야 한다.
- 중요도를 AI가 제안하고 사람이 확정할지, 사전에 승인된 위험 분류 규칙으로 자동 판정할지 정해야 한다.

## 수정 제안

- 확정되지 않은 시간 순서를 “mapping 확인 후 input이 수정된 것으로 보이지만, 사람이 이를 계약 기준본으로 승인했는지는 제공된 근거만으로 확인되지 않는다”처럼 사실과 추정을 분리한다.
- 핵심 주장마다 확인 가능한 경로를 붙인다. HTTP 계약은 `c6-ticket-skeleton.json`의 해당 위치, 어댑터 미실행은 같은 파일의 `storage`와 `protocol`, 최초 오답의 GREEN과 사람 검토는 `runs/c6/L1/review.md`, fixture 동작은 두 mapping 파일에 연결한다.
- 계약 권한을 “사람이 승인한 명세”, “승인되지 않은 fixture나 코드에서 발견한 후보”, “근거 없는 추측”으로 구분한다. fixture는 승인 전까지 `proposed case`의 근거로만 취급한다고 명시한다.
- 두 상태의 의미를 운영 규칙으로 고정한다. 예를 들어 자동 테스트만 `GREEN/RED`를 결정하고, 미확정 계약은 report에 남기되 사전에 정한 중요도 조건에 해당하면 사람의 수용 결정을 요구한다고 설명한다. 누가 중요도를 확정하고 `REQUIRED`를 해제하는지도 함께 적는다.
- 저장과 결제 게이트 분리안을 네 번째 선택지로 다루거나, 현재 범위에서 보류하는 대안으로 명시한다. 실패 원인 격리는 좋아지지만 구조와 게이트 운영 비용이 커서 현재는 전용 계약 테스트가 더 작은 변경이라는 trade-off를 붙인다.
- C-6의 추천안을 조건부로 표현한다. 사람이 mapping 또는 상위 명세를 기준본으로 승인했다면 전용 HTTP 계약 테스트를 추가하고, 승인되지 않았다면 먼저 report와 사람 확인을 거쳐야 한다.
- 계약 테스트의 완료 조건을 명시한다. 실제 로컬 mock PG에 `POST /charge`가 전송되고 요청 본문 두 필드가 검증되며, HTTP 200에서도 `approved:true`만 승인되고 `approved:false`는 거절되어야 한다.

## 요약

자동 판정은 승인된 테스트의 GREEN/RED로 제한하고, AI가 발견한 미확정 계약은 report와 사람 확인으로 다루자는 핵심 방향은 타당하다. 다만 초안은 사람이 fixture를 이미 승인했다는 사실을 확정할 근거가 없고, `REVIEW: REQUIRED`의 판정·해제 권한과 GREEN 이후의 수용 절차가 모호하다. 이 전제를 분리하고 프로젝트 파일 근거, 계약 테스트의 완료 조건, 게이트 분리 대안의 trade-off를 보강해야 한다.
