## FB-B1-02 답변

**답변:**

그럴 수 있다고 생각합니다. 변경을 한곳에 가둔다는 말이 미래의 변경 축을 정확히 예측해 미리 추상화한다는 뜻은 아니라고 봅니다. 아직 확인되지 않은 축에 인터페이스와 계층을 먼저 만들면, 그 추상화 자체가 새로운 변경 비용이 될 수 있습니다.

그래서 지금은 현재 드러난 결정을 작은 범위에 모으고 테스트로 보호하되, 경계를 확정된 구조가 아니라 수정 가능한 가설로 두는 편이 맞다고 생각합니다. 현재 `RefundProcessor`처럼 정책 분기가 한곳에만 있다면 switch를 유지할 수 있습니다. 같은 분기가 여러 곳에 복제되거나 반복 수정, 독립적인 소유권처럼 실제 변화의 증거가 생겼을 때 역할을 추출하겠습니다. 단순한 구조는 미래 확장성이 낮을 수 있지만 잘못된 추상화를 피할 수 있고, 미리 만든 역할은 같은 변경 축이 실제로 반복될 때만 비용을 회수할 수 있습니다.

결국 정보 은닉은 미래를 맞히는 기술이라기보다, 지금 확인된 결정을 작게 격리하고 새로운 증거가 생겼을 때 경계를 다시 그리기 쉽게 만드는 기술에 가깝다고 생각합니다.

## FB-B1-04 답변

**답변:**

시스템 바깥에서 들어오는 최초의 업무 메시지는 애플리케이션의 inbound port인 유스케이스가 받는 것이 자연스럽다고 생각합니다. HTTP 컨트롤러는 외부 입력을 명령으로 변환하고, 유스케이스는 조회와 외부 호출, 저장의 순서를 조율합니다. 주문 상태와 환불 가능 금액 같은 판단은 그 정보를 가진 `Order`와 `Refund`에 메시지를 보내 위임합니다.

이렇게 보면 최초 메시지를 받는 책임과 도메인 규칙을 판단하는 책임은 다릅니다. 애플리케이션 서비스가 협력을 시작하되 도메인 판단까지 가져가면 다시 facade가 됩니다. 반대로 도메인 객체가 저장소나 외부 API 호출까지 책임지면 순수한 모델의 경계가 무너집니다. 현재와 같은 동기 환불 흐름에서는 유스케이스가 협력을 시작하고 도메인 객체가 판단을 맡는 구성이 적절해 보입니다. 외부 승인과 재시도가 여러 트랜잭션에 걸치는 흐름이 실제로 생긴다면 그때는 프로세스 매니저를 별도로 검토하겠습니다.

## FB-B1-05 답변

**답변:**

private 메서드 자체를 없애야 한다기보다, 그 안에 어떤 책임이 들어 있는지를 확인해야 한다고 생각합니다. 객체의 상태를 보고 항상 지켜야 할 불변식을 판단한다면 그 상태를 가진 객체가 맡아야 합니다. 선택 가능한 계산 방식이라면 정책 객체의 후보이고, 외부 요청 변환이나 호출 순서처럼 도메인 판단이 없는 조율이라면 서비스에 남을 수 있습니다.

현재 `RefundProcessor.validateRefundable()`도 한 덩어리로 옮기기보다 규칙별로 봐야 합니다. 주문 상태와 남은 환불 금액처럼 모든 환불에서 지켜야 하는 규칙은 `Order`의 책임에 가깝습니다. 특정 결제 경로에서만 적용되는 조건은 애플리케이션 정책일 수 있습니다. `manualAmount()`도 로직이 복잡해지거나 여러 곳에서 반복될 때 정책 또는 값 객체로 분리하겠습니다. 지금 단계에서 private 메서드를 기계적으로 모두 객체로 옮기면 작은 클래스만 늘어나는 과설계가 될 수 있습니다.

## FB-B1-06 답변

**답변:**

이 경우에도 `Order`가 외부 API를 직접 호출하게 하지는 않을 것 같습니다. 시스템 바깥의 환불 요청은 inbound port인 유스케이스로 들어오고, 애플리케이션 서비스가 자신이 소유한 `RefundPolicyValidationPort` 같은 outbound port를 호출해 외부 정책을 검증합니다. 실제 API 호출은 outbound adapter가 담당하고, 외부 응답은 `RefundPolicyDecision` 같은 도메인 값으로 변환해 애플리케이션 안으로 가져옵니다. `Order`는 그 값과 환불 금액만 받아 자신의 불변식을 확인하고 상태를 전이합니다.

결국 이 문제는 inbound와 outbound 경계를 분리하는 문제라고 생각합니다. inbound port는 시스템이 제공하는 환불 유스케이스를 정의하고, outbound port는 그 유스케이스가 외부 검증에 요구하는 계약을 우리 언어로 정의합니다. 이 구조라면 `Order`는 외부 API의 프로토콜과 장애 방식을 모르면서도 외부 검증 결과를 협력에 사용할 수 있습니다.

다만 검증 결과에 유효 시간이 있으면 검증 이후 주문 상태가 바뀌는 문제를 함께 다뤄야 합니다. 상태 전이 직전 주문 버전을 확인하거나 필요하면 재검증해야 합니다. 외부 검증이 단순 조회가 아니라 승인 상태를 실제로 변경하는 명령이라면 멱등성과 원격 성공 후 로컬 저장 실패에 대한 복구도 추가로 필요합니다.

## FB-B1-07 답변

**답변:**

그 정도로 문맥이 다르다면 기존 인터페이스에 억지로 맞추지 않는 편이 맞다고 생각합니다. 다형성이 새 타입 추가만으로 변경을 흡수하려면 모든 구현이 같은 사전 조건과 결과 의미를 지켜야 합니다. 필요한 데이터만 조금 다르고 결과가 여전히 확정된 환불 금액이라면 공통 요청과 결과 타입을 조정할 수 있습니다. 하지만 정책별 입력을 하나의 요청에 계속 추가하면 사용하지 않는 nullable 필드가 쌓인 데이터 자루가 될 수 있습니다.

일부 정책끼리만 같은 계약을 지킨다면 즉시 금액을 계산하는 역할과 외부 승인이 필요한 역할처럼 인터페이스를 나누겠습니다. 새 정책이 즉시 금액을 반환하지 않고 별도의 승인 상태와 실패 의미를 가진다면 계산 정책의 새 구현이 아니라 별도 유스케이스로 보겠습니다. 인터페이스 분리는 계약을 정직하게 유지하지만 상위 계층의 라우팅과 중복이 늘고, 유스케이스 분리는 생명주기를 명확히 하지만 통합 비용이 커집니다.

따라서 기존 인터페이스를 유지하는 것 자체를 목표로 두지는 않겠습니다. 같은 사전 조건과 사후 조건을 지키면 계약을 진화시키고, 정책군별로만 같으면 역할을 나누고, 결과와 생명주기까지 다르면 유스케이스 경계를 다시 그리겠습니다.
