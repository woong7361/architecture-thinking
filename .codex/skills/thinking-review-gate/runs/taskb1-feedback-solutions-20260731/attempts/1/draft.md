핵심부터 말하면, 리뷰어는 기존 답이 틀렸다고 한 것이 아닙니다. 기존 답의 세 결론인 “변경을 국소화한다”, “협력과 책임을 먼저 본다”, “다형성으로 분기를 대체한다”가 어디까지 유효한지 경계 조건을 묻고 있습니다. 답변을 보완할 핵심은 “경계는 미래를 맞히는 장치가 아니라, 현재 확인된 지식을 격리하고 틀렸을 때 바꾸기 쉽게 만드는 장치”라는 점입니다.

## 어떤 내용에 어떤 피드백이 담겼나

| 피드백 | 원문에서 다룬 내용 | 피드백의 실제 질문 | 보완해야 할 결론 |
| --- | --- | --- | --- |
| FB-B1-01, 03 | facade에 로직이 몰린 경험, OOP는 변경 파급을 국소화한다는 결론 | 댓글 없는 긍정 리액션 | 별도 해결 과제는 없다. 현재 논지의 강점으로 유지한다. |
| FB-B1-02 | 정보 은닉과 변경 국소화 | 예상한 변경 축이 틀리면 그 추상화가 오히려 장애물이 되지 않는가 | 모든 가능성을 미리 숨기는 것이 아니라, 관찰된 변화와 안정된 규칙을 기준으로 가장 작은 경계를 만든다고 보완해야 한다. |
| FB-B1-04 | 협력, 책임, 역할을 데이터보다 먼저 설계 | 시스템 밖에서 온 최초 메시지는 누가 책임지는가 | 외부 요청의 시작은 보통 애플리케이션 유스케이스가 받고, 도메인 판단은 책임 있는 객체에 메시지로 위임한다고 설명해야 한다. 엔티티가 HTTP나 저장소까지 알게 해서는 안 된다. |
| FB-B1-05 | Tell, Don't Ask와 서비스로 샌 도메인 규칙 | 서비스의 private 메서드는 객체 책임이 빠져나온 신호일 수 있다 | 현재 `RefundProcessor`의 검증·계산 private 메서드를 점검 대상으로 삼되, 모든 private 메서드가 나쁜 것은 아니라는 조건을 붙여야 한다. 변환이나 순수한 흐름 보조는 서비스에 남을 수 있다. |
| FB-B1-06 | `Order.applyRefund` 안에 상태 전이를 캡슐화 | 외부 정책 API 결과가 있어야 상태를 바꿀 수 있다면 순수 도메인 경계를 어떻게 지키는가 | I/O 수행과 도메인 판단을 분리해야 한다. 애플리케이션 서비스가 포트를 호출하고 결과를 도메인 값으로 바꾼 뒤 `Order`에 명령한다. |
| FB-B1-07 | 정책 분기를 인터페이스 뒤로 옮기는 다형성 | 새 정책이 기존 입력·출력과 전혀 맞지 않으면 어떻게 하는가 | 인터페이스를 억지로 늘리지 말고, 공통 의미가 남아 있는지 다시 확인한다. 공통 의미가 없으면 정책군이나 유스케이스를 분리해야 한다. |

한 가지 사실도 바로잡을 필요가 있습니다. 현재 코드의 `RefundPolicy`는 인터페이스가 아니라 enum이고 `RefundProcessor`가 switch로 분기합니다. 과제 본문은 “인터페이스로 바꾼다면”이라는 설계 대안을 설명한 것입니다. 따라서 FB-B1-07은 현재 인터페이스의 결함이라기보다, 앞으로 그 대안을 채택할 때 생길 한계를 묻는 질문입니다.

## 해결 방향 3가지

### 1. 확인된 변화까지만 추상화하고 리팩터링 신호를 정한다

현재 두 정책뿐이고 다음 변화가 불확실하다면 switch를 즉시 범용 인터페이스로 바꾸지 않습니다. 대신 다음과 같은 신호가 생기면 경계를 도입합니다.

- 세 번째 정책이 실제로 들어온다.
- 같은 정책 분기가 계산, 검증, 환불 실행 등 두 곳 이상에 반복된다.
- 정책별 변경 주기나 담당 팀이 달라진다.
- 정책 테스트가 공통 서비스 설정 때문에 계속 무거워진다.

장점은 잘못 예측한 추상화 비용을 피하고 현재 코드를 이해하기 쉽게 유지한다는 것입니다. 단점은 첫 변화가 왔을 때 리팩터링 비용을 한 번 치러야 하고, 신호를 무시하면 switch와 private 도메인 로직이 다시 비대해질 수 있다는 점입니다. 현재 카타처럼 규모가 작고 실제 변화 데이터가 적을 때 기본 선택으로 적합합니다.

### 2. 애플리케이션 서비스가 협력을 시작하고 외부 결과를 값으로 번역한다

외부 정책 검증 API가 필요하다면 다음 흐름이 가장 균형이 좋습니다.

```text
외부 요청
  -> RefundUseCase 또는 RefundApplicationService
      -> Order 조회
      -> RefundEligibilityPort 호출
      -> 응답을 RefundDecision 같은 도메인 값으로 변환
      -> order.applyRefund(amount, decision)
      -> 저장
```

최초 메시지와 I/O 순서는 애플리케이션 서비스가 책임지고, “이 결정과 금액으로 상태 전이가 가능한가”는 `Order`가 책임집니다. 외부 API 클라이언트를 `Order`에 주입하지 않으므로 도메인 객체는 순수하게 테스트할 수 있습니다. 현재 `RefundService`도 PG 호출 뒤 `refund.succeed()`와 `order.applyRefund()`를 호출한다는 점에서 이 형태의 출발점에 가깝습니다.

장점은 책임과 테스트 경계가 분명하고 외부 API 교체가 도메인 모델에 번지지 않는다는 것입니다. 단점은 애플리케이션 서비스가 흐름과 예외 매핑을 떠안아 다시 비대해질 수 있다는 것입니다. 또한 외부 검증 시점과 저장 시점 사이에 결과가 낡을 수 있으므로, 정책 결과의 유효 시간이나 멱등성, 실패 보상은 별도로 설계해야 합니다. 외부 조회가 필요하다는 이유만으로 모든 판단을 서비스에 두지 않는 규율이 필요합니다.

### 3. 계약이 이질적이면 하나의 정책 인터페이스를 버리고 유스케이스를 분리한다

새 정책이 추가 입력 하나를 더 요구하는 정도이고 “주문으로부터 환불 금액을 결정한다”는 의미가 유지된다면 `RefundCalculationContext` 같은 명시적 값 객체로 계약을 한 번 진화시킬 수 있습니다. 그러나 필요한 데이터의 출처, 반환 결과, 트랜잭션 범위, 실패 의미까지 다르면 같은 `RefundPolicy` 구현체로 밀어 넣지 않습니다. 예를 들어 `ProrationRefundUseCase`와 `ManualRefundUseCase`를 나누고, 상위 라우터만 요청 유형에 따라 선택하게 합니다.

장점은 nullable 필드와 거대한 context 객체, 지원하지 않는 메서드 같은 거짓 다형성을 피하고 각 흐름의 트랜잭션과 오류 처리를 명확히 할 수 있다는 것입니다. 단점은 유스케이스 수와 라우팅 코드가 늘고, 공통 저장·감사 흐름이 중복될 수 있다는 것입니다. 이때 공통 부분은 실제 중복이 확인된 뒤 작은 협력 객체로 추출해야 합니다. 단순 입력 차이에는 과한 선택이지만, 업무 의미와 원자성까지 달라진 경우에는 가장 안전합니다.

## 비교와 추천

| 방향 | 적합한 상황 | 얻는 것 | 치르는 비용 |
| --- | --- | --- | --- |
| 1. 추상화 지연 + 신호 기반 도입 | 변화가 아직 가설이고 코드가 작음 | 단순성, 잘못된 변경 축에 대한 가역성 | 첫 실제 변화 때 리팩터링 필요 |
| 2. 애플리케이션 조율 + 도메인 값 | 외부 API가 필요하지만 도메인 규칙은 유지됨 | 순수한 도메인, 명확한 최초 메시지 책임 | 조율 코드, 시점 불일치와 실패 처리 |
| 3. 정책군·유스케이스 분리 | 입력·출력·트랜잭션·실패 의미가 질적으로 다름 | 정직한 모델과 독립적 변화 | 타입·라우팅·중복 증가 |

현재 프로젝트에는 1번을 기본 원칙으로 두고, 리뷰어가 든 외부 정책 API 시나리오가 실제 요구가 되면 2번을 적용하는 것을 추천합니다. 이후 새 정책의 문맥이 기존 계약으로 자연스럽게 표현되지 않을 때는 만능 context로 인터페이스를 연명하지 말고 3번으로 분리해야 합니다. 즉 “미리 완벽한 경계를 예측”하는 것이 아니라 “작게 시작하고, 외부 I/O와 도메인 판단을 분리하며, 의미가 달라지는 순간 경계를 다시 긋는” 순서입니다.

확인 근거는 `task2/assignments/taskB-1.md`의 본문과 FB-B1-02~07, `RefundService.java`, `RefundProcessor.java`, `Order.java`입니다. 실제 정책 API의 일관성 보장 방식과 트랜잭션 요구는 아직 주어지지 않았으므로, 그 부분은 구현 전 확인이 필요합니다.
