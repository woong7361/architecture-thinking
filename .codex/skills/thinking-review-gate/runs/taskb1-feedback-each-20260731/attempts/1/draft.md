맞습니다. 앞에서는 전체 피드백을 세 가지 전략으로 묶었지만, 요청하신 것은 댓글 하나마다 해결책 2~3개를 비교하는 것이었습니다. 아래에서는 댓글이 있는 다섯 건을 각각 독립적으로 다룹니다. FB-B1-01과 FB-B1-03은 댓글 없이 리액션만 있으므로 별도의 해결책은 없습니다.

## FB-B1-02: 예측한 변경 축이 틀리면 추상화가 장애물이 되지 않는가

### 피드백 대상과 의미

대상은 “OOP가 요구사항 변경의 파급을 한 곳에 국소화한다”는 주장이다. 리뷰어는 정보 은닉 자체를 반박하는 것이 아니라, 아직 확인되지 않은 변화를 미리 추상화하면 잘못 만든 인터페이스와 계층이 오히려 이후 변경을 막을 수 있음을 묻는다.

### 해결책 1: 실제 두 번째 변화가 올 때까지 단순한 코드를 유지한다

현재처럼 정책이 두 개이고 분기가 한 곳뿐이라면 switch를 유지한다. 세 번째 정책이나 반복 분기가 실제로 등장할 때 공통점을 보고 추상화한다.

- 장점: 잘못 예측한 인터페이스와 클래스 증가를 피한다. 현재 동작을 읽기 쉽다.
- 단점: 첫 변화가 들어오는 시점에 기존 코드를 리팩터링해야 한다. 팀이 리팩터링 신호를 무시하면 분기가 퍼질 수 있다.
- 적합한 조건: 변화가 로드맵이나 실제 요구가 아니라 가능성 수준일 때.

### 해결책 2: 인터페이스는 만들지 않고 작은 캡슐화 경계만 둔다

분기와 계산을 하나의 concrete 객체나 메서드 안에 모으되, 공개 인터페이스나 플러그인 구조까지 만들지는 않는다. 행동 테스트를 두어 나중에 경계를 옮길 수 있게 한다.

- 장점: 변경 파급은 한 곳에 묶으면서 추상화의 방향을 늦게 결정할 수 있다.
- 단점: 코드 요소가 하나 더 생기고, 그 작은 경계조차 잘못 잡으면 이동 비용이 든다.
- 적합한 조건: 변화 가능성은 보이지만 어떤 방향으로 달라질지는 모를 때.

### 해결책 3: 반복될 축이라는 근거가 있을 때 미리 역할을 추출한다

확정된 로드맵, 이미 존재하는 여러 구현, 외부 계약, 별도 소유 팀처럼 근거가 있다면 인터페이스를 먼저 만든다.

- 장점: 구현 추가가 기존 호출부 수정으로 번지는 것을 일찍 막는다.
- 단점: 근거가 틀리면 인터페이스가 최소공배수 계약이나 범용 context 객체로 변질될 수 있다.
- 적합한 조건: 추상화할 변화 축이 추측이 아니라 관찰된 사실일 때.

### 추천

현재 확인한 `RefundProcessor`에서는 정책 분기가 한 메서드에 있으므로 1번 또는 2번이 적합하다. 답안에는 “정보 은닉은 미래를 정확히 예측하는 기술이 아니라, 현재 확인된 결정을 작게 격리하고 새 증거가 생기면 경계를 다시 그리기 쉽게 만드는 기술”이라고 보완하는 것이 좋다.

## FB-B1-04: 시스템 바깥에서 들어오는 최초 메시지는 누가 책임지는가

### 피드백 대상과 의미

대상은 협력·책임·역할을 먼저 설계한다는 주장이다. 리뷰어는 객체에게 책임을 나누기 전에 외부 요청을 처음 받는 객체를 어떻게 선택하는지 묻는다. 여기서는 시스템 경계의 책임과 도메인 판단의 책임을 나눠야 한다.

### 해결책 1: 애플리케이션 유스케이스가 최초 메시지를 받는다

컨트롤러는 HTTP를 명령으로 변환하고 `RefundUseCase.cancel(command)`을 호출한다. 유스케이스는 조회, 외부 호출, 트랜잭션 순서를 조율하고, 도메인 판단은 `Order`와 `Refund`에 위임한다.

- 장점: 시스템이 제공하는 기능이 유스케이스 단위로 드러난다. 웹이나 메시지 소비자 같은 진입 기술과 도메인이 분리된다.
- 단점: 모든 판단을 유스케이스에 넣으면 다시 거대한 facade가 된다.
- 적합한 조건: 저장소나 외부 API 등 여러 협력자를 조율해야 하는 일반적인 백엔드 유스케이스.

### 해결책 2: 어댑터가 애그리거트에 바로 메시지를 보낸다

요청이 단순하고 이미 메모리에 있는 한 객체의 상태만 바꾸는 경우에는 얇은 어댑터가 `order.cancel()` 같은 메시지를 직접 호출할 수 있다.

- 장점: 계층과 중간 타입이 적고 흐름이 짧다.
- 단점: 조회, 저장, 트랜잭션이 추가되는 순간 어댑터가 애플리케이션 로직을 떠안을 수 있다. 진입 채널마다 흐름이 중복될 수 있다.
- 적합한 조건: I/O 조율이 거의 없는 작은 기능이나 단순한 도메인 연산.

### 해결책 3: 도메인 서비스나 프로세스 매니저가 협력을 이끈다

여러 애그리거트의 규칙을 동시에 판단하거나 장시간 진행되는 흐름이라면 `RefundCoordinator` 같은 도메인 서비스나 프로세스 매니저가 후속 협력을 이끌 수 있다.

- 장점: 어느 한 엔티티에도 자연스럽게 속하지 않는 교차 객체 규칙과 장기 흐름을 표현할 수 있다.
- 단점: 너무 일찍 도입하면 엔티티가 다시 데이터 자루가 되고 서비스가 모든 결정을 가져간다. 상태와 실패 처리가 복잡해진다.
- 적합한 조건: 한 애그리거트의 책임으로 귀속하기 어려운 교차 규칙이나 비동기 흐름.

### 추천

현재 환불 예시는 1번이 가장 자연스럽다. `RefundService.cancel`이 PG를 호출하고 결과에 따라 `refund.succeed()`와 `order.applyRefund()`를 호출하는 흐름이 이미 이 방향에 가깝다. 다만 최초 메시지를 받은 서비스는 협력 순서만 책임지고, 상태 전이 규칙까지 가져가서는 안 된다.

## FB-B1-05: 서비스의 private 메서드는 객체가 해야 할 일인가

### 피드백 대상과 의미

대상은 setter 대신 객체에 행동을 요청해야 캡슐화가 지켜진다는 주장이다. 리뷰어의 말은 private 메서드를 문법적으로 금지한다는 뜻보다는, 서비스 안의 private 메서드가 도메인 판단을 숨기는 장소가 되지 않았는지 점검하라는 휴리스틱으로 해석하는 것이 안전하다.

### 해결책 1: 객체 자신의 불변식을 판단하는 메서드는 엔티티로 옮긴다

자신의 상태를 읽고 유효성을 판단한 뒤 자신의 상태를 바꾸는 규칙은 엔티티가 맡는다. 예를 들어 모든 환불 경로에서 `PAID`나 `PARTIALLY_REFUNDED` 상태만 허용한다면 이 검증은 `Order.applyRefund` 또는 별도 공개 행동 안에 둘 수 있다.

- 장점: 상태와 상태를 지키는 규칙이 함께 있어 변경이 국소화된다. 값 기반 단위 테스트가 쉽다.
- 단점: 특정 채널이나 유스케이스에만 적용되는 조건까지 넣으면 `Order`가 모든 업무 흐름을 아는 거대한 객체가 될 수 있다.
- 판정 기준: “이 규칙은 이 객체가 어떤 경로에서 사용되더라도 항상 참이어야 하는가?”

### 해결책 2: 변하는 계산과 판단은 정책 객체로 옮긴다

수동 환불 금액 검증처럼 특정 정책에만 속하는 규칙은 `ManualRefundPolicy` 같은 객체로 분리한다.

- 장점: 정책별 입력, 계산, 테스트를 독립시킬 수 있다. 서비스에 정책별 private 메서드가 계속 늘어나는 것을 막는다.
- 단점: 정책이 적고 짧은 상황에서는 작은 클래스가 과도하게 늘어난다. 공통 계약을 성급히 만들면 FB-B1-07의 문제가 생긴다.
- 판정 기준: “같은 엔티티 상태를 두고 선택 가능한 여러 판단 방식 중 하나인가?”

### 해결책 3: 조율과 변환을 위한 private 메서드는 서비스에 남긴다

분기 선택, DTO 변환, 로깅 데이터 구성처럼 도메인 결정을 하지 않는 보조 메서드는 서비스에 남길 수 있다.

- 장점: 공개 API를 늘리지 않으면서 긴 유스케이스 흐름을 읽기 쉽게 나눌 수 있다.
- 단점: 이름만 조율일 뿐 내부에 규칙이 계속 들어가면 다시 facade가 된다.
- 판정 기준: “이 메서드를 옮기지 않아도 도메인 규칙을 객체만으로 설명하고 테스트할 수 있는가?”

### 현재 코드에 적용하면

- `validateRefundable`: 주문 상태 검증은 `Order` 후보지만 `WEB_ONLY`가 특정 환불 경로의 제약이라면 유스케이스 정책에 남을 수 있다.
- `manualAmount`: 수동 환불에만 적용되는 계산이므로 정책 객체 후보이다.
- `calculateRefundAmount`: 현재는 enum 분기를 선택하는 조율 메서드다. 분기가 한 곳뿐이라면 당장 옮기지 않아도 되지만 정책별 조건이 늘어나면 분리 신호다.

따라서 현재 추천은 private 메서드 전체를 없애는 것이 아니라 1번, 2번, 3번의 판정 질문으로 각각 분류하는 것이다.

## FB-B1-06: 외부 정책 API가 필요하면 순수 도메인 경계를 어떻게 지키는가

### 피드백 대상과 의미

대상은 `Order.applyRefund`가 상태 전이 규칙을 내부에 가둔 예시다. 리뷰어는 상태 전이에 필요한 정보가 객체 내부에 없고 원격 시스템에 있을 때도 같은 캡슐화를 유지할 수 있는지 묻는다. 이것은 현재 요구사항이 아니라 가상 시나리오다.

### 해결책 1: 애플리케이션 서비스가 API를 호출하고 결과를 도메인 값으로 넘긴다

서비스가 `RefundEligibilityPort`를 호출하고 응답을 `RefundDecision`으로 번역한 뒤 `order.applyRefund(amount, decision)`을 호출한다.

- 장점: `Order`가 HTTP 클라이언트와 장애 처리 방식을 모른다. 외부 응답을 값으로 넣어 순수하게 상태 전이를 테스트할 수 있다.
- 단점: 외부 검증 시점과 저장 시점 사이에 결과가 낡을 수 있다. 서비스의 조율·오류 매핑 책임이 늘어난다.
- 적합한 조건: 외부 시스템이 판단 재료를 제공하고 최종 불변식은 우리 도메인이 결정할 때.

### 해결책 2: 도메인 서비스가 도메인이 소유한 포트에 의존한다

`RefundDomainService`가 `RefundEligibility` 인터페이스를 통해 외부 판정을 얻고 주문과 함께 최종 결정을 내린다. 인터페이스는 인프라가 아니라 도메인 언어로 정의한다.

- 장점: 여러 객체와 외부 판정을 결합한 규칙을 하나의 도메인 개념으로 표현할 수 있다.
- 단점: 도메인 판단이 I/O 시점과 결합되고 테스트에서 포트 대역이 필요하다. 도메인 서비스가 애플리케이션 서비스처럼 비대해질 위험이 있다.
- 적합한 조건: 외부 판정과 여러 도메인 객체를 함께 보아야 하는 규칙이 핵심 도메인 개념일 때.

### 해결책 3: 비동기 프로세스로 분리하고 중간 상태를 모델링한다

원격 검증이 느리거나 재시도가 필요하다면 주문을 `REFUND_VALIDATION_PENDING` 상태로 두고, 정책 승인 이벤트를 받은 뒤 상태를 전이한다.

- 장점: 원격 API의 지연과 장애를 트랜잭션 안에 붙잡지 않는다. 재시도와 감사 이력을 명시적으로 관리할 수 있다.
- 단점: 즉시 일관성을 잃고 중간 상태, 중복 이벤트, 보상 처리, 운영 관측 비용이 생긴다.
- 적합한 조건: 검증이 오래 걸리거나 실패·재시도가 정상적인 업무 흐름일 때.

### 추천

단순 동기 API라는 가정에서는 1번이 가장 작고 테스트하기 쉽다. 외부 판정 자체가 핵심 도메인 규칙이면 2번, 지연과 재시도가 업무적으로 허용되거나 필수이면 3번을 선택한다. 실제 선택 전에는 정책 결과의 유효 시간과 트랜잭션 요구를 확인해야 한다.

## FB-B1-07: 새 정책이 기존 인터페이스의 입력과 결과에 맞지 않는다면

### 피드백 대상과 의미

대상은 새 정책을 기존 코드 수정 없이 구현체 추가로 처리한다는 다형성 설명이다. 리뷰어는 모든 변화를 하나의 인터페이스로 흡수할 수 없으며, 공통 계약이 깨졌을 때는 추상화 자체를 다시 검토해야 한다고 묻는다. 현재 `RefundPolicy`는 enum이므로 미래 인터페이스를 가정한 질문이다.

### 해결책 1: 공통 의미가 유지된다면 명시적인 요청·결과 타입으로 계약을 진화시킨다

모든 정책이 여전히 “환불 가능 금액을 결정한다”는 동일한 사전·사후 조건을 지킨다면 `RefundCalculationRequest`와 `RefundQuote` 같은 값 객체로 필요한 문맥을 표현한다.

- 장점: 하나의 역할과 호출 흐름을 유지하면서 계약을 확장할 수 있다.
- 단점: 정책마다 사용하지 않는 nullable 필드가 늘어나면 범용 context 자루가 된다. 기존 구현과 호출부도 함께 수정해야 한다.
- 적합한 조건: 필요한 데이터만 달라졌고 업무 의미와 결과의 의미는 동일할 때.

### 해결책 2: 능력이나 문맥별로 인터페이스를 나눈다

`AmountRefundPolicy`, `ExternalApprovalRefundPolicy`처럼 공통 사전·사후 조건을 공유하는 정책끼리 별도 계약으로 묶는다.

- 장점: 각 인터페이스가 작고 정직해지며 지원하지 않는 입력이나 메서드를 피할 수 있다.
- 단점: 상위 계층에 어느 정책군을 선택할지 라우팅이 필요하고, 공통 처리의 중복 가능성이 있다.
- 적합한 조건: 일부 정책끼리는 공통점이 있지만 전체를 하나의 계약으로 묶을 수 없을 때.

### 해결책 3: 유스케이스나 경계 자체를 분리한다

새 정책의 트랜잭션, 상태 생명주기, 실패 의미까지 다르다면 `ManualRefundUseCase`와 `ExternalApprovedRefundUseCase`처럼 별도 흐름으로 분리한다. 업무 언어와 소유권까지 다르면 별도 모듈이나 bounded context 후보가 된다.

- 장점: 거짓 다형성을 피하고 각 흐름의 트랜잭션과 오류 처리를 명확히 표현한다.
- 단점: 타입, 라우팅, 저장·감사 코드가 중복될 수 있다. 경계를 너무 크게 나누면 통합 비용이 커진다.
- 적합한 조건: 파라미터 차이가 아니라 업무 의미와 원자성까지 질적으로 다를 때.

### 추천

선택 기준은 “모든 구현이 같은 사전조건과 사후조건을 지킬 수 있는가?”이다. 그렇다면 1번, 정책군별로만 가능하면 2번, 처리 흐름과 결과 의미까지 다르면 3번이 맞다. 기존 인터페이스를 지키는 것 자체가 목표가 되어서는 안 된다.

## 정리

각 피드백의 추천은 서로 다르다.

- FB-B1-02: 현재는 단순 구조나 작은 concrete 경계를 유지한다.
- FB-B1-04: 애플리케이션 유스케이스가 최초 메시지를 받고 도메인 객체에 판단을 위임한다.
- FB-B1-05: private 메서드를 불변식, 정책, 조율로 분류한 뒤 각각 엔티티, 정책 객체, 서비스에 배치한다.
- FB-B1-06: 동기 외부 검증이면 포트 호출 결과를 도메인 값으로 변환해 객체에 전달한다.
- FB-B1-07: 공통 계약이 유지되는 정도에 따라 계약 진화, 인터페이스 분리, 유스케이스 분리 중 선택한다.

외부 API의 실제 일관성 요구와 새로운 정책의 실제 문맥은 제공되지 않았으므로 FB-B1-06과 07의 추천은 조건부 설계안이다.
