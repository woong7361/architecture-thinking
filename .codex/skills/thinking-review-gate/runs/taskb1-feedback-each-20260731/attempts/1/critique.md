## 문제 지점

- [근거 anchor 부족] 초안이 전체적으로 맞는 방향을 잡았지만, 각 섹션의 주요 claim이 `Checked Context`의 어떤 사실에 기대는지 명시되지 않아 검증 가능성이 약하다. 특히 FB-B1-02, 04, 05의 추천은 현재 코드 사실에서 출발한 판단인지 일반 설계 원칙인지가 문장 안에서 바로 드러나지 않는다.
- [근거 없는 구체 예시 삽입] FB-B1-05의 `PAID`, `PARTIALLY_REFUNDED`, `WEB_ONLY`와 FB-B1-04의 `refund.succeed()`는 `input.md`에 없는 구체 요소다. 예시를 들 수는 있지만, 지금 형태는 현재 코드 사실처럼 읽힐 가능성이 있어 금지된 “초안에 없는 근거를 있는 것처럼 만들기”에 가깝다.
- [사실과 가상 시나리오의 경계 흐림] FB-B1-06과 FB-B1-07은 `input.md`에서 이미 가상 설계 질문으로 정리돼 있는데, 초안은 마지막 정리 문단에 가서야 조건부라는 점을 붙인다. 본문 초반부터 “현재 코드 사실”과 “가상 시나리오에서의 선택지”를 나눠야 사용자가 오해하지 않는다.
- [FB-B1-04의 숨은 구조 변경 전제] `RefundUseCase.cancel(command)` 예시는 설명용으로는 괜찮지만, 현재 문맥에는 `RefundService.cancel`만 확인되어 있다. 따라서 “최초 메시지를 누가 받는가”를 설명하는 답변이 “새 계층을 도입해야 한다”는 처방처럼 읽히지 않게 정리해야 한다.
- [FB-B1-05의 현재 코드 적용 파트가 덜 단정적이어야 함] `validateRefundable`, `manualAmount`, `calculateRefundAmount`를 분류하는 접근은 좋지만, 지금은 판정 기준은 제시하면서도 현재 코드에 대한 잠정 결론과 가정이 뒤섞여 있다. 무엇이 확인된 사실이고 무엇이 추가 확인이 필요한 추정인지 더 명확히 표시해야 한다.
- [7개 피드백 커버리지는 충족하지만 식별성이 약함] FB-B1-01과 FB-B1-03을 리액션으로 구분한 점은 맞다. 다만 서두 한 문장에만 묶여 있어 “7개를 빠짐없이 다뤘다”는 확인성이 낮다. 각 ID를 별도 bullet로 짧게 적는 편이 더 분명하다.

## 확인 필요

- `taskB-1` 원문 댓글에 대한 현재 paraphrase가 실제 피드백 의도와 어긋나지 않는지. 지금 초안은 `input.md`의 요약을 잘 따르지만, 비평 대상이 “원문 댓글”이라면 표현 수위를 더 맞출 필요가 있다.
- `RefundService.cancel` 내부의 실제 상태 전이 메서드 명과 흐름이 무엇인지. 현재 입력에는 “PG 호출 뒤 Refund와 Order에 상태 전이 메시지를 보낸다”까지만 있으므로 `refund.succeed()` 같은 이름은 확인 전 사용하면 안 된다.
- `validateRefundable`이 검사하는 구체 조건이 무엇인지. 입력에는 “결제 플랫폼과 주문 상태”만 있으므로 `WEB_ONLY` 같은 조건명은 사실이 아니라 예시로만 써야 한다.
- `Order.applyRefund`가 실제로 어떤 상태 집합을 허용하는지. `PAID`, `PARTIALLY_REFUNDED`는 입력 근거가 없으므로, 상태명을 넣으려면 추가 확인이 필요하다.
- FB-B1-06에서 외부 정책 API의 응답 유효 시간, 재시도 필요, 동기 처리 요구가 실제로 있는지. 이 정보가 없으면 1번, 2번, 3번 추천은 모두 조건부다.

## 수정 제안

- 각 피드백 섹션을 최소한 `현재 코드 사실`, `피드백의 질문`, `대안과 trade-off`, `추천과 조건` 순서로 나눠라. 이렇게 하면 사용자가 “무엇에 대한 피드백인지”와 “어떤 해결책을 비교하는지”를 바로 검증할 수 있다.
- `Checked Context`에 있는 사실은 문장 안에서 직접 anchor를 걸어라. 예를 들어 “현재 문맥에서 확인된 사실은 `calculateRefundAmount`가 enum switch를 사용한다는 점이다”처럼 시작하면 claim과 evidence가 바로 연결된다.
- 입력에 없는 구체 메서드명, 상태명, 정책명을 제거하거나 “예를 들어”와 “가정하면”을 앞에 붙여 명시적 가상 예시로 낮춰라. 특히 `refund.succeed()`, `WEB_ONLY`, `PAID`, `PARTIALLY_REFUNDED`는 그대로 두면 안 된다.
- FB-B1-04는 “`RefundService.cancel`을 애플리케이션 유스케이스로 해석할 수 있다”는 식으로 현재 구조와 연결해 설명하라. 새 이름인 `RefundUseCase`는 필수 설계처럼 보이지 않게 예시임을 분명히 하라.
- FB-B1-05는 세 메서드에 대해 “확인된 사실”과 “가능한 분류”를 분리해 써라. 지금처럼 휴리스틱은 유지하되, 각 메서드에 대한 잠정 판단 옆에 왜 잠정적인지 한 줄로 붙이는 편이 좋다.
- FB-B1-06과 FB-B1-07은 섹션 첫 문장에서 “현재 요구사항이 아니라 가상 시나리오”라고 못 박아라. 마지막 정리에서만 조건부라고 말하면 앞선 강한 문장들이 과도하게 단정적으로 읽힌다.
- FB-B1-01과 FB-B1-03은 서두 문장 하나로 끝내지 말고, ID별로 “리액션만 있어 설계 질문과 해결책 비교 대상이 없음”이라고 짧게 분리 표기하라. 그러면 7건 전부를 독립적으로 확인할 수 있다.

## 요약

구조와 대안 비교는 대체로 맞지만, 현재 초안은 근거 anchor가 약하고 입력에 없는 구체 예시를 몇 군데 사실처럼 섞었다. 각 피드백마다 현재 코드 사실, 질문의 의미, 조건부 대안을 분리하고, 확인되지 않은 상태명·메서드명은 제거하거나 명시적 가정으로 낮추는 수정이 필요하다.
