## 문제 지점

- [트리거 해석] 초안은 “현재 답안의 트리거는 다음처럼 좁혀 쓰는 편이 정확하다”고 말하면서 `v >= 2` 기준을 사실상 “같은 최소 입력과 같은 결과 계약을 공유할 때”로 재정의한다. 방향은 타당하지만, 기존 `refactoring-criteria.md:74-75`의 기준을 대체하는 것인지, 그 기준에 추가되는 보정 조건인지가 분명하지 않다. 사용자는 기존 과제 답안의 판단을 검토하는 중이므로, “개수 기준은 후보 신호이고, 공통 계약 가능성 검토가 실제 적용 조건이다”처럼 관계를 명확히 해야 한다.

- [오케스트레이션 제안] `PricingService`가 등급 조회와 쿠폰 서버 호출을 조정한 뒤 좁은 규칙들을 조합한다는 제안은 합리적이지만, 현재 확인된 코드에는 `PricingService`, 고객 등급, 쿠폰 모델, 외부 서버 호출 경계가 없다. 초안은 이를 “실제 요구가 들어왔을 때의 설계안”으로 읽히게 쓰고 있으나, 근거 없는 현재 구조 설명으로 오해될 여지가 있다.

- [불필요한 입력의 기준] 초안은 공통 `PricingContext`가 비대해지는 경우를 잘 설명하지만, 언제 “비대하다”고 판단할지 기준이 조금 더 명시되면 좋다. 예를 들어 대부분의 구현이 사용하지 않는 필드가 늘어나거나, 컨텍스트 생성 때문에 외부 조회가 항상 발생하면 경계 재검토 신호라는 식으로 확인 가능한 기준을 붙일 수 있다.

## 확인 필요

- 기존 `v >= 2` 트리거를 문서상 그대로 유지하면서 해석만 보완할 것인지, 아니면 기준 문구 자체를 “같은 최소 입력과 결과 계약을 공유할 때”로 수정할 것인지 확인이 필요하다.

- FB-B5-01의 VIP 등급과 외부 쿠폰 서버 응답이 단순 예시인지, 향후 답안에 반영해야 하는 확정 요구인지 확인이 필요하다. 현재 입력 문맥상으로는 확정 요구가 아니라 가정으로 처리하는 것이 맞다.

## 수정 제안

- 마지막 정리 문장을 다음 취지로 바꾸는 것이 좋다: `v >= 2`는 다형성 도입을 검토하게 만드는 신호이고, 실제 도입 여부는 변형들이 같은 최소 입력과 같은 결과 계약을 공유하는지로 결정한다.

- `PricingService`, `CustomerGrade`, `Coupon` 같은 이름은 현재 코드에 있는 구조가 아니라 “요구가 확정될 경우의 예시 설계”라고 명시한다.

- 공통 컨텍스트를 선택해도 되는 조건과 피해야 하는 조건을 더 검증 가능하게 분리한다. 예를 들어 “정책 대부분이 동일 데이터를 이미 필요로 한다면 가능”, “컨텍스트를 만들기 위해 모든 요청에서 VIP 조회나 쿠폰 서버 호출이 필요해진다면 부적절”처럼 적으면 사용자가 판단 기준을 따라가기 쉽다.

## 요약

초안의 핵심 결론은 적절하다. 다형성 자체가 불필요한 데이터를 강제하는 것이 아니라, 공통 계약을 너무 넓게 잡을 때 문제가 생긴다는 설명도 사용자 질문에 잘 답한다. 다만 기존 `v >= 2` 기준과 새 보정 조건의 관계, 현재 코드에 없는 설계 요소의 지위, 비대한 입력 객체를 판정하는 기준을 더 명확히 하면 검증 가능한 답변이 된다.
