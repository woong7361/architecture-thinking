## 1. FB-B1-02 — 잘못 예측한 변경 축

### 내가 한 말

OOP와 정보 은닉은 변경의 파급을 한곳에 국소화한다. 환불 정책도 역할 뒤에 두면 새 정책을 타입 추가로 흡수할 수 있다고 말했다.

### 들어온 피드백

변경 축을 잘못 예측했다면, 그 축을 기준으로 만든 추상화가 오히려 미래 변경의 장애물이 되지 않겠느냐는 질문이다.

**근거:** `task2/assignments/taskB-1.md:87`, 현재 switch는 `task1/task1-4-history-A/src/main/java/com/thinking/payment/RefundProcessor.java:30`

### 가능한 방안

#### 방안 1. 현재 분기를 유지한다

- **예시:** `[현재 코드]` `PRORATION`, `MANUAL` switch를 한곳에 두고 테스트로 보호한다.
- **장점:** 구조가 단순하다. 잘못된 인터페이스를 미리 만들지 않는다.
- **단점:** 변경이 반복되면 기존 코드를 리팩터링해야 한다. 시기를 놓치면 분기가 퍼질 수 있다.

#### 방안 2. 작은 계산 객체로 격리한다

- **예시:** `[제안]` switch와 계산을 concrete `RefundAmountCalculator` 한곳으로 옮긴다.
- **장점:** 변경을 모으면서 추상화 방향은 나중에 정할 수 있다.
- **단점:** 변화가 오지 않으면 클래스만 하나 늘어난다.

#### 방안 3. 관찰된 변경 축에 인터페이스를 만든다

- **예시:** `[제안]` 같은 분기가 여러 위치에 복제되거나 정책별 독립 소유권이 생겼을 때 `RefundAmountPolicy`를 추출한다.
- **장점:** 정책별 확장과 테스트가 쉬워진다.
- **단점:** 공통점이 부족하면 모든 구현이 사용하지 않는 입력을 받는 거대한 계약이 된다.

### 추천

현재 확인된 코드는 분기가 한곳에 있으므로 1번이 가장 작다. 분기가 커지지만 방향이 불명확하면 2번, 반복 수정·분기 복제·독립 소유권이 확인되면 3번으로 전환한다. 정책 개수만으로 결정하지 않는다.

## 2. FB-B1-04 — 시스템 최초 메시지의 책임

### 내가 한 말

객체지향 설계는 데이터보다 협력이 먼저이며, 협력이 책임과 역할을 결정한다고 말했다.

### 들어온 피드백

시스템 바깥에서 들어오는 최초 요구는 누가 받아야 전체 도메인 협력이 자연스럽게 시작되는지 묻는 질문이다.

**근거:** `task2/assignments/taskB-1.md:110`, 현재 협력 흐름은 `task1/task1-3-history/src/main/java/com/thinking/payment/RefundService.java:11`

### 가능한 방안

#### 방안 1. 애플리케이션 유스케이스가 받는다

- **예시:** `[제안]` `RefundController → RefundUseCase.cancel → Order·Refund → PgClient`로 흐른다. 컨트롤러는 입력 변환, 유스케이스는 순서 조율, 도메인 객체는 상태 판단을 맡는다.
- **장점:** 진입 기술, 업무 흐름, 도메인 규칙이 분리된다.
- **단점:** 유스케이스가 도메인 판단까지 가져가면 다시 거대한 facade가 된다.

#### 방안 2. 프로세스 매니저가 받는다

- **예시:** `[가상 상황]` 외부 승인이 비동기로 진행된다면 `RequestRefund → VALIDATING → PG_CANCEL_PENDING → COMPLETED`를 `RefundProcess`가 관리한다.
- **장점:** 장기 상태, 재시도, 실패 복구가 명시된다.
- **단점:** 중간 상태, 중복 메시지, 운영 관측 비용이 크게 늘어난다.

### 추천

확인한 `RefundService.cancel`은 한 메서드 안에서 PG 결과를 받고 상태를 전이한다. 이 흐름에는 1번이 적합하다. 외부 승인과 재시도가 여러 트랜잭션에 걸치는 실제 요구가 생길 때 2번으로 전환한다.

## 3. FB-B1-05 — 서비스 private 메서드에 남은 책임

### 내가 한 말

상태를 외부에서 꺼내 판단하지 말고, 데이터의 주인인 객체에게 행동을 요청해야 캡슐화가 지켜진다고 말했다.

### 들어온 피드백

서비스의 private 메서드가 하는 일도 실제로는 도메인 객체가 맡아야 할 책임일 수 있다는 의견이다.

**근거:** `task2/assignments/taskB-1.md:126`, 현재 private 판단은 `task1/task1-4-history-A/src/main/java/com/thinking/payment/RefundProcessor.java:17`

### 가능한 방안

#### 방안 1. 객체 자신의 불변식은 엔티티로 옮긴다

- **예시:** `[비교 구현]` 다른 이력의 `Order.validateRefundable()`과 `Order.applyRefund()`는 주문 상태와 남은 금액을 직접 검증한다. 위치는 `task1/task1-4-history-B/src/main/java/com/thinking/payment/domain/Order.java:41`이다.
- **장점:** 상태와 규칙이 함께 있어 변경이 국소화된다.
- **단점:** 특정 환불 경로에만 적용되는 규칙까지 넣으면 `Order`가 모든 업무 흐름을 알게 된다.

#### 방안 2. 선택 가능한 계산은 정책이나 값 객체로 옮긴다

- **예시:** `[제안]` 수동 환불 검증이 복잡해지거나 재사용될 때 `ManualRefundAmount.of(requestAmount, refundableAmount)`로 분리한다.
- **장점:** 정책별 테스트와 재사용이 쉬워진다.
- **단점:** 현재처럼 짧고 한곳에서만 쓰면 작은 클래스만 과도하게 늘어난다.

#### 방안 3. 도메인 판단이 없는 조율은 서비스에 남긴다

- **예시:** `[제안]` `toPgCommand()`처럼 외부 요청 형식만 바꾸는 private 메서드는 서비스에 둔다.
- **장점:** 공개 API를 늘리지 않고 흐름을 나눌 수 있다.
- **단점:** 변환 메서드 안에 정책 판단이 들어가면 다시 facade가 된다.

### 추천

private 메서드를 일괄 제거하지 않는다. 현재 `RefundProcessor.validateRefundable()`의 주문 상태 판단과 특정 결제 경로 판단이 같은 책임인지 먼저 구분한다. 모든 환불에서 지켜야 할 불변식은 `Order` 후보이고, 특정 경로 정책은 애플리케이션 계층에 남을 수 있다. `manualAmount()`는 복잡도나 중복이 실제로 늘어날 때 정책 객체 후보로 본다.

## 4. FB-B1-06 — 외부 API가 필요한 상태 전이

### 내가 한 말

`Order` 안에 환불 상태 전이 규칙을 두면 변경을 객체 경계 안에 가둘 수 있다고 말했다.

### 들어온 피드백

상태 변경 전에 외부 환불 정책 API 검증이 반드시 필요하다면, 순수한 도메인 경계를 어떻게 지킬지 묻는 가상 질문이다.

**근거:** `task2/assignments/taskB-1.md:138`, 현재 외부 PG 포트 예시는 `task1/task1-3-history/src/main/java/com/thinking/payment/PgClient.java:3`

### 가능한 방안

#### 방안 1. 애플리케이션 서비스가 외부 API를 호출한다

- **예시:** `[가상 상황]` `RefundEligibilityPort.check()`의 응답을 `RefundDecision`으로 바꾼 뒤 `Order`에 전달한다.
- **장점:** `Order`가 HTTP와 외부 응답 형식을 모르므로 순수하게 테스트할 수 있다.
- **단점:** 판정 후 주문 상태가 바뀌거나 원격 성공 후 로컬 저장이 실패할 수 있다. 주문 버전 확인, 멱등 키, 재검증이 필요할 수 있다.

#### 방안 2. 도메인 서비스가 도메인 소유 포트를 사용한다

- **예시:** `[가상 상황]` `RefundApprovalService`가 `RefundEligibility` 포트와 여러 도메인 객체를 함께 사용한다.
- **장점:** 외부 판정과 여러 객체를 결합한 규칙을 하나의 도메인 개념으로 표현할 수 있다.
- **단점:** 도메인 서비스가 I/O와 결합되고 비대해질 위험이 있다.

#### 방안 3. 비동기 프로세스와 중간 상태를 둔다

- **예시:** `[가상 상황]` `VALIDATION_PENDING → PG_CANCEL_PENDING → SUCCEEDED`를 이벤트로 진행한다.
- **장점:** 지연과 재시도, 원격 성공 후 로컬 실패를 복구하기 쉽다.
- **단점:** 즉시 일관성을 잃고 중복 이벤트와 보상 처리 비용이 생긴다.

### 추천

외부 검증이 단일 요청 안에서 끝나고 판정 유효 시간이 충분하다면 1번이다. 외부 판정과 여러 객체를 결합하는 행위 자체가 핵심 도메인 개념이면 2번, 장기 실행과 재시도가 업무의 일부면 3번이다. 실제 API 요구가 없으므로 현재 추천은 조건부다.

## 5. FB-B1-07 — 기존 인터페이스로 표현할 수 없는 정책

### 내가 한 말

다형성을 사용하면 새 환불 정책을 기존 코드 수정이 아니라 새 구현 타입 추가로 처리할 수 있다고 말했다.

### 들어온 피드백

새 정책이 기존 인터페이스의 입력과 반환 타입으로 표현할 수 없는 완전히 다른 문맥을 요구하면 어떻게 할지 묻는 가상 질문이다.

**근거:** `task2/assignments/taskB-1.md:152`, 현재 정책은 인터페이스가 아니라 `task1/task1-4-history-B/src/main/java/com/thinking/payment/domain/RefundPolicy.java:5`의 enum이다.

### 가능한 방안

#### 방안 1. 결과 의미가 같다면 공통 계약을 진화시킨다

- **예시:** `[제안]` 모든 정책이 공통 `RefundFacts`를 받아 확정된 `RefundQuote`를 반환하고 반올림 방식만 다르다면 같은 역할을 유지한다.
- **장점:** 하나의 호출 흐름을 유지할 수 있다.
- **단점:** 정책별 입력을 모두 공통 요청에 추가하면 nullable 필드가 쌓인 데이터 자루가 된다.

#### 방안 2. 능력별로 인터페이스를 나눈다

- **예시:** `[제안]` 즉시 금액을 계산하는 `ImmediateRefundPolicy`와 외부 승인을 요청하는 `ApprovalRequiredRefundPolicy`를 분리한다.
- **장점:** 각 계약이 필요한 입력과 결과만 가진다.
- **단점:** 상위 계층의 라우팅과 공통 처리 중복이 늘어난다.

#### 방안 3. 생명주기까지 다르면 유스케이스를 나눈다

- **예시:** `[제안]` 즉시 취소하는 `ImmediateRefundUseCase`와 외부 심사를 기다리는 `PartnerApprovalRefundUseCase`를 분리한다.
- **장점:** 서로 다른 트랜잭션과 실패 의미가 명확해진다.
- **단점:** 저장, 감사, 라우팅 코드가 중복될 수 있다.

### 추천

모든 정책이 같은 사전 조건과 결과 의미를 가지면 1번이다. 일부 정책군만 같은 계약을 지키면 2번, 결과와 생명주기까지 다르면 3번이다. 실제 새 정책 문맥이 제공되지 않았으므로 조건부 판단이다.
