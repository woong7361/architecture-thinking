# 첫 번째 피드백은 어떤 문제인가

결론부터 말하면, 리뷰어의 문제 제기는 맞습니다. 다만 “LLM이 자기 코드를 채점하니 전부 무효다”가 핵심은 아닙니다. 더 정확히는 서로 다른 세 문제가 겹쳐 있습니다.

## 1. 알기 쉬운 비유

자동차를 정비한 뒤 두 가지 검사를 한다고 생각해 보겠습니다.

- 제동 시험기에 올려 제동거리를 재는 것은 기계적 검사입니다. 정해진 조건에서 브레이크가 기준 안에 들어왔는지는 재현 가능하게 확인할 수 있습니다.
- 정비사가 “전체적으로 더 좋은 차가 됐다”고 평가하는 것은 종합 판단입니다. 체크리스트가 있어도 정비사의 해석이 들어갑니다.

worktree 행위 게이트는 전자입니다. 동결된 테스트가 모두 GREEN인지는 기계적으로 판정합니다. Eval은 후자입니다. 루브릭은 기준을 고정하지만, 각 축에 몇 점을 줄지는 LLM이 판단합니다.

따라서 “브레이크 시험을 자동화했으니 차 전체가 객관적으로 더 좋아졌다”라고 말하면 측정 범위를 넘어섭니다. 원래 답안도 완성도는 B-5가 더 낫다고 유보했지만, 객관성이라는 단어가 행위 보존을 넘어 전체 비교의 근거처럼 읽힐 여지가 있습니다.

## 2. 정확히 어떤 문제가 있는가

### 문제 1. 객관성의 범위가 섞였다

행위 게이트가 확인하는 명제는 다음입니다.

> 이 변경을 baseline에 적용했을 때, 지정된 경계 테스트가 모두 통과했다.

확인하지 못하는 명제는 다음입니다.

> 모든 기존 행위가 보존됐다.
> 설계가 더 단순해졌다.
> 과설계가 없다.
> B-5보다 더 좋은 리팩토링이다.

테스트가 보지 않는 행위는 GREEN이어도 깨질 수 있습니다. 설계 품질은 테스트 통과만으로 결정되지도 않습니다. 따라서 “객관적”은 동결된 테스트가 관찰하는 행위 보존에만 붙일 수 있습니다.

### 문제 2. 결정적인 계산과 객관적인 평가를 혼동했다

`score_eval()`은 LLM이 낸 네 축의 점수를 가중합하고 임계값과 비교합니다. 이 계산은 같은 입력이면 같은 결과가 나오는 결정적 계산입니다.

하지만 `diagnosis_accuracy=4`, `change_minimality=4` 같은 입력 점수는 LLM의 해석입니다. 계산기가 정확히 더한다고 해서 설문 응답 자체가 객관적이 되는 것은 아닙니다.

즉 구조는 다음과 같습니다.

```text
LLM의 해석적 점수
        ↓
Python의 결정적 합산
        ↓
PASS 또는 FAIL
```

마지막 두 단계가 결정적이어도 첫 단계가 독립된 사실 측정으로 바뀌지는 않습니다.

### 문제 3. 자기평가 편향과 Goodhart 위험이 있다

Gen과 Eval을 새 세션으로 분리하면 Eval이 Gen의 대화를 그대로 이어받는 정보 누출은 줄어듭니다. 이 분리는 가치가 있습니다.

그러나 같은 LLM 계열은 코드 생성 때와 평가 때 비슷한 선호와 맹점을 공유할 가능성이 있습니다. 사람이 쓴 정답이나 동결된 외부 판정과 비교하지 않으므로, Eval은 독립 증거라기보다 내부 리뷰입니다.

여기서 “순환”은 두 수준으로 구분해야 합니다.

- 한 번의 Gen→Eval에서는 엄밀한 논리적 순환이라기보다 자기평가 편향과 오류 상관관계 문제입니다. LLM Eval이 무가치하다는 뜻은 아닙니다.
- Eval의 약한 축을 다시 Gen에 넣어 반복하면 rubric이 곧 최적화 목표가 됩니다. 실제 품질보다 rubric에서 높은 점수를 받는 방향으로 고쳐질 수 있습니다. 이때는 Goodhart식 피드백 순환이 분명해집니다.

숫자 자체를 Gen에 주지 않고 약한 축 이름만 전달하는 방식은 노골적인 점수 맞추기를 줄입니다. 하지만 같은 rubric의 통과를 목표로 반복한다는 구조는 남습니다.

### 문제 4. Critique가 발견한 위험이 최종 판정에 연결되지 않는다

이것이 현재 코드에서 가장 구체적인 문제입니다.

실행 결과는 다음 세 가지를 동시에 기록합니다.

- 행위 게이트: 6개 시나리오 GREEN
- Eval: 4.0, PASS
- Critique: high 행위 위험 1건, `of()` 과설계 등 추가 약점

그런데 `runner.py`는 Eval이 통과하면 Critique의 severity와 관계없이 최종 `PASS`를 반환합니다. Critique는 문제를 발견했지만 게이트가 아니라 메모에 가깝습니다.

Critique의 high 지적도 LLM 판단이므로 항상 옳다고 단정할 수는 없습니다. 그러나 파이프라인이 Critique를 위험 탐지 단계로 채택했다면 다음 중 하나는 정해야 합니다.

- high 지적이 있으면 FAIL 또는 사람 검토 대기로 보낸다.
- Critique는 참고 정보일 뿐이며 PASS에는 영향을 주지 않는다고 명시한다.

현재는 Critique를 품질 단계라고 소개하면서 실제 PASS에서는 무시하므로 의미가 일치하지 않습니다.

## 3. 피드백이 원래 주장을 어디까지 무너뜨리는가

원래 주장 전체가 틀린 것은 아닙니다.

- “자동 테스트가 사람의 수동 실행보다 반복 가능하고 재현 가능하다”는 주장은 유지할 수 있습니다.
- “행위 보존이 객관적으로 검증됐다”는 표현은 “동결 경계 테스트가 관찰하는 행위가 보존됐다”로 좁혀야 합니다.
- “코드가 더 좋아졌다는 판정도 객관적이다”라는 의미로는 방어하기 어렵습니다. Eval은 내부 품질 검사이지 외부 검증이 아니기 때문입니다.
- 현재의 최종 `PASS`는 행위 GREEN과 LLM rubric 통과를 뜻할 뿐, Critique가 지적한 위험까지 해소됐다는 뜻은 아닙니다.

그래서 이 피드백은 단순한 문구 수정 요청이 아니라 결과 상태의 의미와 gate 연결을 다시 보라는 피드백입니다.

## 4. 대응 수준과 트레이드오프

1. **문구만 좁힌다**: “사람보다 객관적”을 “동결 경계 테스트 범위에서 더 재현 가능하다”로 바꿉니다.
   - 얻는 것: 원래 비교의 과장을 빠르게 바로잡습니다.
   - 비용과 한계: Eval PASS와 Critique high가 충돌하는 구현 문제는 그대로 남습니다.

2. **추천 · 판정 상태를 분리한다**: `behavior=GREEN`, `quality_eval=PASS`, `critique=REVIEW_REQUIRED`처럼 사실과 LLM 판단을 분리합니다. Critique high가 있으면 최종 상태를 사람 검토 대기로 보냅니다.
   - 얻는 것: 각 신호가 무엇을 증명하는지 명확해지고, 알려진 위험을 품은 결과가 단순 PASS로 소비되는 것을 막습니다.
   - 비용과 한계: Critique 오탐 때문에 자동 통과율이 떨어질 수 있어 severity 기준과 사람 override 정책이 필요합니다.

3. **외부 기준으로 품질을 보정한다**: 사람이 판정한 과거 리팩토링을 동결하고 Gen이나 rubric 변경 전후가 사람 verdict와 얼마나 일치하는지 검증합니다.
   - 얻는 것: “품질이 좋아졌다”는 주장을 자기 점수가 아닌 외부 기준과 연결할 수 있습니다.
   - 비용과 한계: 사람 판정 데이터가 쌓이는 속도에 개선 속도가 묶이고, 작은 캘리브레이션 셋에 과최적화될 수 있습니다.

## 5. 한 문장으로 정리

첫 번째 피드백이 짚은 핵심은 “자동 테스트가 객관적이지 않다”가 아니라, **행위 테스트의 객관성을 LLM 기반 설계 품질 판정까지 확장했고, 그 LLM 판정과 Critique가 충돌해도 최종 PASS가 나는 구조를 구분하지 않았다**는 것입니다.
