## 문제 지점

- [핵심 판단] 초안은 Level 1/2/3의 역할을 요약하지만, 사용자 질문인 “이 설계가 적절한가?”에 대한 명시적 판단이 약하다. “적절하다/조건부로 적절하다/부적절하다” 중 어떤 결론인지 먼저 밝혀야 한다.
- [근거 앵커] 초안의 주요 claim이 `SKILL.md`, `PROBLEM.md`, `rubric.yaml`, `validate.py` 동작 같은 확인 가능한 근거와 연결되어 있지 않다. 현재 문맥에는 각 Level의 정의, 레벨 분리 목적, PROBLEM.md의 임시 결정, rubric 축과 validation 기준이 있으므로 이를 근거로 연결해야 한다.
- [사용자 요청 누락] 사용자는 runner/validation 결과 기준으로 “약한 축과 수정 방향”을 요청했지만, 초안에는 validation 결과, weak axes, 수정 방향이 없다. critique artifact 자체는 eval/validation을 읽지 않지만, main agent의 최종 답변에는 runner 결과를 반영해야 한다.
- [대안과 trade-off 부족] 초안은 3단계 설계를 유일한 답처럼 제시한다. 설계 판단 답변이므로 최소한 `2단계로 단순화`, `현재 3단계 유지`, `항상 artifact 기반 검토` 같은 대안을 비교하고 왜 현재 3단계가 적절한지 설명해야 한다.
- [불확실성 경계] “모든 답변을 Level 3로 보내면 생산성이 떨어진다”, “검토가 없으면 재작업이 늘 수 있다”는 타당한 방향의 claim이지만, 프로젝트의 실제 실행 시간, 실패율, 재작업 빈도 같은 측정 근거는 없다. 따라서 정책적 판단 또는 설계 가정임을 표시해야 한다.
- [일관성/범위] Level 2 조건과 Level 3 조건의 경계가 초안에서는 너무 짧게 표현되어 있다. `file artifact`, `pass/fail gate`, `schema validation`, `CI/hook 후보 검증`처럼 Level 3를 결정하는 조건을 분명히 써야 Level 2와 중복되는 오해를 줄일 수 있다.

## 확인 필요

- runner가 생성한 `validation.json`의 `weak_axes`와 총점/통과 여부를 main agent가 실제 최종 답변에 반영해야 한다.
- `eval.json`의 축별 이유를 사용자에게 어느 정도 노출할지 확인해야 한다. 현재 `PROBLEM.md`의 임시 결정은 일반 verifier 출력에서 축 점수를 노출하지 않는 방향이므로, 최종 답변은 점수 나열보다 약한 축과 수정 방향 중심이 더 일관적이다.
- Level 3가 “사용자 명시 요청 또는 artifact/gate 필요 시”로 제한되는 현재 정책이 실제 사용 흐름에서 과도하거나 부족하지 않은지는 아직 운영 데이터가 없으므로, 운영 후 조정 가능성을 남겨야 한다.

## 수정 제안

- 결론을 먼저 쓰도록 수정한다: “현재 목적에는 3단계 분리가 조건부로 적절하다. 이유는 검토 비용과 품질 보증 강도를 분리할 수 있기 때문이다.”
- 근거를 문맥 파일에 연결한다. 예: `SKILL.md`의 Level 정의, `PROBLEM.md`의 점수 노출 제한 임시 결정, `rubric.yaml`의 평가 축, `validate.py`의 weak_axes 산출 방식을 각각 claim 근거로 사용한다.
- 사용자 요청에 맞춰 validation 기준의 약한 축을 별도 섹션으로 정리한다. 단, 점수 자체를 과하게 전면화하지 말고 “근거 앵커 부족”, “대안/trade-off 부족”, “불확실성 경계 부족”처럼 수정 가능한 문제로 표현한다.
- 대안 비교를 추가한다. 최소 3개 대안을 짧게 비교하면 된다: `Level 1/2만 유지`, `현재 3단계 유지`, `모든 검토를 Level 3로 통일`. 각 대안의 장점, 비용, 실패 가능성을 붙인다.
- Level 2와 Level 3의 경계를 더 엄격히 적는다. “설계/추천/구현 방향이면 Level 2, 재현 가능한 artifact/gate/schema validation/CI 후보 검증이 필요하면 Level 3”처럼 결정 규칙을 명확히 제시한다.
- 불확실한 claim에는 운영 데이터가 없다는 한계를 붙인다. 예: “생산성 저하는 합리적 설계 가정이지만, 실제 임계값은 run 기록이 쌓인 뒤 조정해야 한다.”
- 최종 수정 방향은 “3단계 구조는 유지하되, Level 3 진입 조건과 사용자-facing 출력 정책을 더 명시한다”로 정리하는 것이 현재 문맥과 가장 잘 맞는다.

## 요약

초안의 방향은 프로젝트 문맥과 대체로 맞지만, 답변으로 쓰기에는 근거 앵커, validation 기반 약한 축, 대안 비교, 불확실성 표시가 부족하다. main agent는 3단계 설계를 조건부로 지지하되, Level 3의 진입 조건과 runner/validation 결과 기반 수정 방향을 명확히 보강해야 한다.
