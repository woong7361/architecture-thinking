## 문제 지점

- [Spring PetClinic 사례] `Owner`가 `addPet()`과 `addVisit()`을 한 클래스에 둔다는 설명은 확인이 필요하다. 공개 코드 기준으로 `Owner`에는 `addPet()`이 있고, 방문 추가 행위는 보통 `Pet` 쪽에 있다. 이 문장이 틀리면 통합 Rich JPA Entity 사례의 근거 신뢰도가 떨어진다.

- [근거 연결 방식] 참고 링크는 충분하지만, 본문 주요 claim과 출처가 직접 연결되어 있지 않다. 특히 Jakarta Persistence, Netflix의 약 두 시간 전환, Shopify의 점진적 경계 강화는 독자가 어느 문단이 어느 근거에서 나온 말인지 추적하기 어렵다.

- [예시 2의 결론 강도] Lazy Collection에 업무 규칙이 결합된 예시는 분리 후보로 적절하지만, 제목이 “분리하는 경우”라서 분리가 유일한 해결처럼 읽힐 수 있다. Fetch 전략 조정, Repository 쿼리로 사전 조회, Aggregate 범위 축소 같은 대안과 비교한 뒤 분리로 간다는 흐름이 더 정확하다.

- [사후 확인 기준] Mapper가 단순 값 변환인지 DB 상태 판단인지 확인한다는 기준은 들어가 있지만, “구현 후 무엇을 보면 비용이 감당 가능한지”가 조금 더 명시되면 Task C-2의 개인 기준으로 더 강해진다. 예를 들어 매핑 테스트 수, 자식 ID와 Version 보존 여부, 삭제와 순서 결정 책임 발생 여부를 체크 항목으로 분리할 수 있다.

## 확인 필요

- Spring PetClinic의 현재 `Owner` 클래스가 실제로 어떤 업무 메서드를 갖는지 확인해야 한다.
- Netflix Studio Workflows 글의 “약 두 시간” 전환 사례가 어떤 범위의 변경이었는지 본문 표현과 맞는지 확인해야 한다.
- Shopify 사례가 JPA 사례가 아니라는 한계 표시는 충분하지만, 제출물에서 요구하는 “실제 사용 사례”로 받아들여질 수 있는지 과제 맥락상 확인하면 좋다.

## 수정 제안

- Spring PetClinic 문장을 `Owner`의 `addPet()` 사례와 `Pet`의 방문 관련 행위처럼 실제 코드에 맞게 고친다.
- 주요 사례 문단마다 출처명을 문장 안에 붙인다. 예를 들어 “Jakarta Persistence 명세 기준으로...”, “Netflix Tech Blog 사례에서는...”처럼 연결한다.
- 예시 2 제목을 “JPA 의존 피해 때문에 분리를 검토하는 경우”로 낮추고, 분리 외 대안을 한두 문장으로 언급한 뒤 D/P 기준에 따라 분리 후보가 된다고 정리한다.
- Mapper 비용 기준 마지막에 사후 점검 문장을 추가한다. “Mapper가 DB 조회, 기존 자식 비교, 삭제 판정, 순서 보존을 맡기 시작하면 분리 범위를 줄인다”처럼 실행 가능한 체크로 쓰면 좋다.

## 요약

초안은 Task C-2 요구를 대부분 충족한다. 다만 PetClinic 사례의 메서드 사실관계와 사례별 근거 연결을 보강해야 한다. 또한 Lazy Loading 예시는 “분리 확정”보다 “분리 후보와 대안 비교”로 표현하면 결론이 더 방어 가능해진다.
