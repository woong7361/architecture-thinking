먼저 현재 코드 기준 추천을 압축하면 다음과 같습니다.

| 피드백 | 현재 추천 | 전환 신호 |
| --- | --- | --- |
| 잘못 예측한 변경 축 | 분기를 한곳에 두고 추상화를 늦춘다 | 같은 축의 세 번째 변화나 반복 수정이 확인됨 |
| 최초 메시지의 책임 | 애플리케이션 유스케이스가 받고 도메인에 판단을 위임한다 | 장기·비동기 협력으로 발전함 |
| 서비스 private 메서드 | 불변식, 정책, 조율로 분류해 각 책임의 주인에게 보낸다 | private 판단이 늘거나 여러 유스케이스에서 중복됨 |
| 외부 API가 필요한 상태 전이 | 애플리케이션 서비스가 포트를 호출하고 결과를 값으로 전달한다 | 지연·재시도·장기 상태가 업무의 일부가 됨 |
| 기존 인터페이스에 안 맞는 정책 | 같은 계약인지 먼저 확인하고, 아니면 역할이나 유스케이스를 나눈다 | 입력 차이를 넘어 결과와 생명주기까지 달라짐 |

## 1. 잘못 예측한 변경 축의 위험

현재 `RefundProcessor`에는 `PRORATION`, `MANUAL` 두 정책을 선택하는 switch가 한 곳에만 있다. 아직 반복되는 변경 축이 확인됐다고 보기는 어렵다.

### 방안 A: 두 번째 실제 변화가 올 때까지 단순한 분기를 유지한다

예시는 현재 switch를 유지하되 정책별 행동 테스트를 두는 것이다. `PARTNER_SPECIAL` 같은 세 번째 정책이 실제 요구로 들어오거나 동일한 분기가 다른 위치에도 복제될 때 추상화를 검토한다.

```java
return switch (request.policy()) {
    case PRORATION -> RefundCalculator.calculate(...);
    case MANUAL -> manualAmount(...);
};
```

- 장점: 잘못 예측한 인터페이스와 클래스 증가를 피한다. 현재 흐름이 한눈에 보인다.
- 비용: 새 변화가 들어오는 시점에는 기존 코드를 수정하고 리팩터링해야 한다. 팀이 그 시점을 놓치면 분기가 퍼질 수 있다.
- 적합한 조건: 변화가 로드맵이나 실제 요구가 아니라 가능성에 머물러 있을 때다.

### 방안 B: 인터페이스 없이 작은 concrete 경계만 만든다

예를 들어 switch와 계산을 `RefundAmountCalculator` 한 객체로 옮긴다. 공개 인터페이스나 플러그인 구조는 만들지 않는다.

```java
long amount = refundAmountCalculator.calculate(order, request);
```

- 장점: 분기와 계산을 한곳에 가두면서 추상화 방향의 결정은 미룰 수 있다. 나중에 객체를 없애거나 역할을 추출하기도 쉽다.
- 비용: 클래스가 하나 늘어난다. 변화가 오지 않으면 단순한 메서드를 옮긴 것에 그칠 수 있다.
- 적합한 조건: 변경 가능성은 보이지만 무엇이 어떻게 달라질지는 아직 모를 때다.

### 방안 C: 관찰된 변경 축이 있을 때만 역할을 추출한다

예를 들어 실제로 세 정책이 존재하고 각각 독립 배포나 별도 테스트가 필요해지면 `RefundAmountPolicy`를 도입한다.

```java
interface RefundAmountPolicy {
    RefundQuote calculate(RefundContext context);
}
```

- 장점: 새 정책 추가가 기존 계산기의 수정으로 번지는 것을 줄인다. 정책별 테스트와 소유권이 분명해진다.
- 비용: 잘못된 공통 계약을 만들면 모든 구현이 사용하지 않는 입력을 받거나 인터페이스가 계속 커진다.
- 적합한 조건: 여러 구현, 확정된 로드맵, 반복 수정처럼 변경 축을 뒷받침하는 증거가 있을 때다.

현재 추천은 A 또는 B다. 정보 은닉은 미래를 정확히 예측하는 기술이라기보다, 현재 확인된 결정을 작게 격리하고 새 증거가 생겼을 때 경계를 다시 그리기 쉽게 만드는 기술로 보는 편이 안전하다.

## 2. 시스템 최초 메시지의 책임

최초 메시지의 책임은 HTTP를 받는 책임과 업무 협력을 시작하는 책임을 구분해야 한다.

### 방안 A: 애플리케이션 유스케이스가 최초 업무 메시지를 받는다

컨트롤러는 HTTP를 명령으로 바꾸고 `RefundUseCase.cancel(command)`을 호출한다. 유스케이스는 주문 조회, PG 호출, 저장 순서를 조율하고 상태 판단은 `Order`와 `Refund`에 위임한다.

```text
POST /refunds
  -> RefundController
  -> RefundUseCase.cancel(command)
  -> Order.validateRefundable()
  -> PgClient.cancelPayment(...)
  -> Order.applyRefund(amount)
```

- 장점: 웹, 메시지 소비자 같은 진입 기술과 업무 흐름이 분리된다. 시스템이 제공하는 기능이 유스케이스 이름으로 드러난다.
- 비용: 유스케이스가 모든 판단까지 가져가면 다시 거대한 facade가 된다.
- 적합한 조건: 저장소, 외부 API, 트랜잭션 등 여러 협력자를 조율하는 일반적인 백엔드 기능이다.

### 방안 B: 진입 어댑터가 도메인 객체를 직접 호출한다

조회나 외부 호출 없이 이미 가진 객체의 상태만 바꾸는 매우 작은 기능이라면 어댑터가 `order.applyRefund(amount)`를 바로 호출할 수 있다.

- 장점: 중간 계층과 타입이 적고 흐름이 짧다.
- 비용: 조회, 저장, 권한, 트랜잭션이 추가되는 순간 어댑터가 업무 흐름을 떠안을 수 있다. HTTP와 메시지 진입점에 같은 흐름이 중복될 수도 있다.
- 적합한 조건: I/O 조율이 거의 없고 단일 객체의 원자적 행동으로 끝날 때다.

### 방안 C: 프로세스 매니저가 장기 협력을 시작한다

외부 승인, PG 취소, 재시도, 보상 처리가 여러 단계에 걸치면 `RefundProcess`가 명령을 받고 상태와 후속 메시지를 관리한다.

```text
RequestRefund
  -> RefundProcess: VALIDATING
  -> PolicyApproved
  -> PgCancellationRequested
  -> RefundCompleted
```

- 장점: 비동기 단계와 실패 복구가 명시된다. 어느 한 엔티티에 속하지 않는 장기 협력을 표현할 수 있다.
- 비용: 중간 상태, 중복 메시지, 재시도, 운영 관측이 필요해진다. 단순한 동기 흐름에는 과도하다.
- 적합한 조건: 협력이 한 트랜잭션 안에서 끝나지 않고 실패와 재시도가 정상 흐름일 때다.

현재 환불 예시에는 A가 가장 자연스럽다. 현재 `RefundService.cancel`도 PG를 호출한 뒤 `Refund`와 `Order`에 메시지를 보내므로 이 방향에 가깝다. 핵심은 서비스가 순서를 조율하되 도메인 규칙까지 소유하지 않는 것이다.

## 3. 서비스 private 메서드에 남은 도메인 책임

private 메서드는 문법 자체가 문제가 아니다. 그 안의 판단이 누구의 책임인지가 기준이다. 현재 `RefundProcessor`의 private 메서드는 서로 다른 세 부류로 나눌 수 있다.

### 방안 A: 객체 자신의 불변식은 엔티티로 이동한다

주문 상태와 환불 가능 금액처럼 `Order`가 자신의 상태만으로 판단할 수 있는 규칙은 `Order`가 맡는다.

```java
order.validateRefundable();
order.applyRefund(refundAmount);
```

- 장점: 상태와 상태를 지키는 규칙이 함께 있어 변경이 국소화된다. 실제 객체만으로 단위 테스트할 수 있다.
- 비용: 특정 채널에서만 적용되는 규칙까지 넣으면 `Order`가 웹 경로나 운영 정책까지 아는 거대한 객체가 될 수 있다.
- 판정 질문: 이 규칙은 주문이 어떤 경로에서 사용되더라도 항상 참이어야 하는가?

현재 코드의 `PAID` 또는 `PARTIALLY_REFUNDED` 상태 검증과 환불 가능 금액 검증은 이 후보에 가깝다. 반면 `WEB_ONLY`는 특정 환불 경로의 제약이라면 애플리케이션 정책일 수 있다.

### 방안 B: 선택 가능한 계산 규칙은 정책 객체나 값 객체로 이동한다

수동 환불 금액 검증은 `ManualRefundPolicy` 또는 `ManualRefundAmount`가 맡을 수 있다.

```java
ManualRefundAmount amount = ManualRefundAmount.of(
    request.manualAmount(),
    order.refundableAmount()
);
```

- 장점: 수동 정책의 입력 검증과 계산을 독립적으로 테스트할 수 있다. 서비스의 정책별 private 메서드 증가를 막는다.
- 비용: 정책이 두 개뿐이고 로직이 짧다면 작은 클래스가 과도하게 늘 수 있다. 성급한 공통 인터페이스는 다섯 번째 피드백의 문제를 만든다.
- 판정 질문: 같은 주문을 두고 선택 가능한 여러 판단 방식 중 하나인가?

### 방안 C: 도메인 결정을 하지 않는 조율 메서드는 서비스에 남긴다

PG 명령 변환, 로그 필드 구성, 응답 DTO 조립처럼 도메인 규칙이 없는 private 메서드는 서비스에 둘 수 있다.

```java
private PgCancelCommand toPgCommand(Order order, long amount) { ... }
```

- 장점: 공개 API를 늘리지 않으면서 긴 유스케이스 흐름을 읽기 쉽게 나눈다.
- 비용: 이름은 변환이나 조율이지만 내부에 정책 판단이 들어가기 시작하면 다시 facade가 된다.
- 판정 질문: 이 메서드를 서비스에 남겨도 도메인 규칙을 도메인 객체만으로 설명하고 테스트할 수 있는가?

현재 추천은 private 메서드를 일괄 제거하는 것이 아니다. `validateRefundable`은 불변식과 경로 정책으로 분해하고, `manualAmount`는 정책 후보로 본다. 단순한 흐름 조율만 서비스에 남기는 방식이 적합하다.

## 4. 외부 API가 필요한 상태 전이

이 피드백은 현재 구현이 아니라 외부 환불 정책 검증 API가 새로 필요하다는 가상 상황이다.

### 방안 A: 애플리케이션 서비스가 포트를 호출하고 결과를 도메인 값으로 전달한다

서비스가 `RefundEligibilityPort`를 호출한 뒤 외부 응답을 `RefundDecision`으로 번역한다. `Order`는 HTTP나 외부 응답 형식을 모르고 도메인 값만 받는다.

```java
RefundDecision decision = eligibility.check(order.id(), request);
order.applyRefund(refundAmount, decision);
```

- 장점: 도메인 객체가 순수하게 유지된다. 외부 응답을 값으로 넣어 상태 전이를 빠르게 테스트할 수 있다.
- 비용: 외부 검증과 주문 저장 사이에 시간이 흐르면 판정 결과가 낡을 수 있다. 서비스의 오류 변환과 조율 책임이 늘어난다.
- 적합한 조건: 동기 API가 판단 재료를 제공하고 최종 불변식은 우리 도메인이 결정할 때다.

### 방안 B: 도메인 서비스가 도메인이 소유한 포트에 의존한다

여러 객체와 외부 판정을 함께 봐야 하는 핵심 규칙이라면 `RefundApprovalService`가 `RefundEligibility` 역할을 사용해 결정을 내릴 수 있다.

```java
refundApprovalService.approve(order, request);
```

- 장점: 외부 판정과 여러 도메인 객체를 결합하는 규칙을 하나의 도메인 개념으로 표현한다. 인터페이스 언어도 외부 벤더가 아니라 우리 업무 언어로 통제할 수 있다.
- 비용: 도메인 판단이 I/O 시점과 결합되고 테스트에서 포트 대역이 필요하다. 도메인 서비스가 애플리케이션 서비스처럼 비대해질 위험이 있다.
- 적합한 조건: 외부 판정과 여러 객체를 결합하는 행위 자체가 핵심 도메인 개념일 때다.

### 방안 C: 비동기 프로세스로 분리하고 중간 상태를 모델링한다

원격 검증이 느리거나 재시도가 필요하다면 `REFUND_VALIDATION_PENDING` 상태를 두고 승인 이벤트를 받은 뒤 상태를 바꾼다.

```text
refund.request() -> VALIDATION_PENDING
PolicyApproved -> PG_CANCEL_PENDING
PgCancelled -> SUCCEEDED
```

- 장점: 외부 API의 지연과 장애를 한 트랜잭션 안에 붙잡지 않는다. 재시도와 감사 이력을 명시적으로 다룰 수 있다.
- 비용: 즉시 일관성을 잃는다. 중복 이벤트, 중간 상태, 보상 처리, 운영 관측 비용이 생긴다.
- 적합한 조건: 검증 지연과 재시도가 예외가 아니라 정상적인 업무 흐름일 때다.

단순한 동기 API라는 가정에서는 A를 추천한다. 외부 판정 자체가 핵심 도메인 규칙이면 B, 장기 실행과 재시도가 필요하면 C로 전환한다. 선택 전에는 판정의 유효 시간과 트랜잭션 요구를 확인해야 한다.

## 5. 기존 인터페이스로 표현할 수 없는 새 정책

현재 `RefundPolicy`는 enum이므로 이 피드백은 미래의 인터페이스를 가정한 질문이다. 판단 기준은 새 정책도 기존 구현과 같은 사전 조건과 사후 조건을 지키는지다.

### 방안 A: 업무 의미가 같다면 명시적인 요청과 결과 타입으로 계약을 진화시킨다

새 정책도 여전히 환불 가능 금액을 계산하고 `RefundQuote`를 반환한다면 필요한 문맥을 값 객체로 표현할 수 있다.

```java
RefundQuote calculate(PartnerRefundRequest request);
```

예를 들어 제휴사 등급이 추가로 필요하지만 결과는 여전히 확정된 환불 금액이라면 같은 역할로 볼 여지가 있다.

- 장점: 하나의 계산 역할과 호출 흐름을 유지할 수 있다. 입력의 의미를 타입으로 드러낼 수 있다.
- 비용: 모든 정책 입력을 하나의 `RefundContext`에 계속 추가하면 사용하지 않는 nullable 필드가 늘어난다. 기존 호출부와 구현을 함께 수정해야 할 수 있다.
- 적합한 조건: 필요한 데이터만 달라지고 계산의 의미와 결과 계약은 같을 때다.

현재 `RefundCalculationRequest`의 nullable `manualAmount`는 범용 요청이 커질 때 생길 수 있는 위험을 이미 일부 보여준다.

### 방안 B: 능력이나 문맥별로 인터페이스를 나눈다

즉시 금액을 계산할 수 있는 정책과 외부 승인이 필요한 정책을 서로 다른 역할로 둔다.

```java
interface ImmediateRefundPolicy {
    RefundQuote calculate(RefundFacts facts);
}

interface ApprovalRequiredRefundPolicy {
    ApprovalRequest requestApproval(RefundFacts facts);
}
```

- 장점: 각 인터페이스가 작고 정직해진다. 지원하지 않는 입력이나 반환값을 억지로 구현하지 않아도 된다.
- 비용: 상위 계층에서 어느 정책군을 사용할지 라우팅해야 한다. 공통 검증과 후처리가 중복될 수 있다.
- 적합한 조건: 전체 정책은 하나로 묶이지 않지만 일부 정책끼리는 같은 계약을 공유할 때다.

### 방안 C: 처리 흐름과 생명주기까지 다르면 유스케이스를 분리한다

새 정책이 즉시 금액을 반환하지 않고 외부 심사 후 며칠 뒤 승인되는 구조라면 계산 정책의 새 구현이 아니라 별도 업무 흐름이다.

```text
ImmediateRefundUseCase.calculateAndCancel()
PartnerApprovalRefundUseCase.requestAndWait()
```

- 장점: 거짓 다형성을 피한다. 각 흐름의 트랜잭션, 상태, 실패 의미를 명확히 표현한다.
- 비용: 라우팅과 저장, 감사 코드가 중복될 수 있다. 너무 일찍 나누면 통합 비용만 커진다.
- 적합한 조건: 파라미터 차이를 넘어 결과의 의미, 원자성, 생명주기까지 질적으로 다를 때다.

추천 기준은 간단하다. 모든 구현이 같은 사전 조건과 사후 조건을 지키면 A, 정책군별로만 같으면 B, 처리 결과와 생명주기까지 다르면 C다. 기존 인터페이스를 유지하는 것 자체가 목표가 되어서는 안 된다.

## 종합 의견

다섯 피드백은 서로 다른 문제처럼 보이지만 같은 판단 순서를 요구한다.

1. 먼저 실제 협력과 현재 확인된 변경을 본다.
2. 판단에 필요한 정보를 가장 잘 아는 객체에 책임을 둔다.
3. 같은 계약으로 교체할 근거가 있을 때만 역할을 추출한다.
4. 전제가 깨지면 기존 추상화를 확장하기보다 경계를 다시 그린다.

현재 코드에는 대규모 전략 패턴이나 비동기 프로세스를 즉시 도입할 근거가 없다. 우선 `RefundProcessor`의 private 판단을 불변식, 정책, 조율로 분류하고, 한곳에 있는 switch는 테스트로 보호하며 유지하는 작은 개선이 적절하다. 외부 검증 API나 이질적인 정책이 실제 요구로 들어올 때 네 번째와 다섯 번째 피드백의 선택 기준을 적용하면 된다.
