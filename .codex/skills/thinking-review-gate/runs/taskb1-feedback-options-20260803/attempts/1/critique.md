## 문제 지점

- [피드백 식별] 다섯 주제를 다루지만 `FB-B1-02` 같은 식별자와 피드백 요지가 본문에 없다. 앞선 대화를 보지 않은 독자는 각 답변이 어느 피드백에 대응하는지 추적하기 어렵다.
- [근거 추적성] `RefundProcessor`, `RefundService`, `RefundCalculationRequest`를 근거로 사용하지만 전체 상대 경로와 메서드 또는 필드 위치가 없다. 현재 구현에 관한 주요 판단을 사용자가 직접 확인하기 어렵다.
- [현재 사실과 예시의 구분] `RefundUseCase.cancel`, `Order.validateRefundable`, `RefundService.cancel`, `WEB_ONLY` 등이 실제 코드인지 설명용 가상 명칭인지 불분명하다. 특히 `WEB_ONLY`는 `input.md`에서 확인된 현재 문맥에 없다.
- [변경 축 판단] “두 번째 실제 변화”, “세 번째 정책”을 추상화 전환 기준처럼 사용하지만 현재 스냅샷만으로 과거 변경 횟수나 확정된 로드맵은 알 수 없다. 정책 개수 자체도 변경 축이 검증됐다는 충분조건은 아니다.
- [최초 메시지 방안 B] 진입 어댑터가 도메인 객체를 직접 호출하는 예시는 HTTP 어댑터가 이미 로드된 도메인 객체를 어떻게 얻고 저장하는지 설명하지 않는다. 현재 백엔드 문맥에서는 애플리케이션 계층을 우회해 트랜잭션과 저장 책임이 어댑터로 새어 나갈 가능성이 크다.
- [private 메서드 판단] 표의 “각 책임의 주인에게 보낸다”와 종합 의견의 “작은 개선이 적절하다”는 실제 메서드별 이동을 확정한 것처럼 읽힌다. 제공된 근거만으로는 수동 금액 검증을 별도 정책 객체로 옮길 만큼 복잡하거나 반복되는지 확인되지 않았다.
- [새 정책 방안 A] 공통 계약을 유지한다는 설명과 `calculate(PartnerRefundRequest request)` 예시가 맞지 않는다. 제휴사 전용 입력 타입은 기존 구현이 공유할 계약이라기보다 특정 구현의 계약으로 보이며, 모든 정책이 같은 역할로 대체 가능하다는 주장을 약화한다.
- [외부 API 협력] 판정 유효 시간은 언급하지만 상태 전이 직전 동시 변경, 중복 요청, 원격 성공 후 로컬 저장 실패 같은 경계 조건이 빠져 있다. 이 조건들은 동기 호출과 비동기 프로세스 중 무엇을 추천할지 바꿀 수 있다.
- [의견과 사실의 구분] “정보 은닉은 … 기술로 보는 편이 안전하다”, “A가 가장 자연스럽다” 같은 설계 의견은 타당할 수 있으나 현재 코드 사실과 같은 어조로 제시된다.

## 확인 필요

- 각 섹션과 `FB-B1-02`, `FB-B1-04`, `FB-B1-05`, `FB-B1-06`, `FB-B1-07`의 정확한 대응 관계.
- 현재 구현을 설명하는 클래스의 전체 상대 경로, 실제 메서드명과 필드명.
- `RefundService.cancel`, `WEB_ONLY`가 실제 코드에 존재하는지, 아니면 설명을 위한 가상 예시인지.
- 정책 변경 이력, 확정된 추가 정책, 같은 분기의 복제 여부. 확인할 수 없다면 추상화 전환 기준을 조건부 의견으로 유지해야 한다.
- 가상 외부 정책 API의 동기성, 판정 유효 기간, 장애 및 재시도 요구, 멱등성, 트랜잭션 경계.
- 새 정책이 기존 정책과 동일한 결과 의미와 실패 모델을 가지는지, 외부 승인이나 장기 상태를 요구하는지.

## 수정 제안

- 각 섹션 제목에 피드백 ID와 한 문장 요약을 추가해 입력의 다섯 피드백과 직접 연결한다.
- 현재 코드에 관한 주장에는 전체 상대 경로와 확인할 심볼을 붙인다. 정확한 위치를 제공할 수 없다면 “`input.md`의 확인 문맥 기준”이라고 근거 범위를 제한한다.
- 모든 코드 블록에 `현재 코드`, `개념 예시`, `가상 시나리오` 중 하나를 표시한다. 확인되지 않은 `WEB_ONLY`는 제거하거나 명시적인 가상 예시로 바꾼다.
- “세 번째 정책이면 추상화”를 결정 규칙으로 쓰지 말고 반복 수정, 분기 복제, 독립 테스트·배포 요구, 확정된 로드맵을 전환 증거로 제시한다. 정책 개수는 관찰 신호 중 하나로만 둔다.
- 최초 메시지의 방안 B는 인메모리 객체를 이미 보유한 내부 호출처럼 매우 제한된 조건으로 좁히거나, 현재 HTTP 흐름에는 부적합하다고 명시한다. 조회·저장·트랜잭션이 생기면 방안 A로 전환하도록 한다.
- private 메서드는 먼저 불변식, 선택 정책, 조율로 분류하되 실제 이동은 규칙의 보편성, 중복, 복잡도가 확인된 경우에만 추천한다. 현재 근거로 확정할 수 없는 이동은 후보로 표현한다.
- 새 정책 방안 A의 예시는 모든 구현이 공유할 수 있는 최소 입력과 결과 계약으로 교체한다. 정책별 입력이 필수라면 타입별 인터페이스 분리 또는 유스케이스 분리 방안으로 보내 설명과 예시를 일치시킨다.
- 외부 API 선택 기준에 판정 만료, 낙관적 잠금 또는 재검증, 멱등 키, 원격 성공 후 로컬 실패 복구를 추가한다.
- 종합 추천을 “현재 확인된 사실”, “조건부 추천”, “전환 신호”로 나눠 설계 의견과 구현 사실을 구분한다.

## 요약

초안은 다섯 피드백마다 세 가지 방안과 장점·비용·적용 조건을 제공해 요청 범위를 충실히 다룬다. 다만 근거 위치가 추적 가능하지 않고, 실제 코드와 가상 예시가 일부 섞여 있으며, 정책 개수를 추상화 기준처럼 사용하는 부분과 공통 계약 예시의 불일치를 수정해야 한다.
