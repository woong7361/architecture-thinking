단순 리액션과 칭찬·동의 문장은 제외하면, 실질적인 피드백은 다음 5건입니다. 아래의 `피드백이 나온 이유`는 댓글 문맥을 바탕으로 한 해석입니다.

## 1. 잘못 예측한 변경 축의 위험 — FB-B1-02

- **대상 내용:** OOP와 정보 은닉은 변경의 파급을 한 곳에 국소화한다는 주장
- **피드백 요지:** 처음부터 변경 축을 잘못 예측했다면, 그 축을 기준으로 만든 은닉 경계가 오히려 미래 변경을 방해하지 않겠느냐는 질문입니다.
- **피드백이 나온 이유:** 답안은 변경 국소화의 이점만 다루고, 잘못된 예측으로 만든 추상화의 비용은 다루지 않았습니다. 추상화를 언제 만들고 언제 다시 허물어야 하는지까지 생각해 보라는 피드백입니다.

## 2. 시스템 최초 메시지의 책임 — FB-B1-04

- **대상 내용:** 데이터보다 협력이 먼저이고, 협력이 책임과 역할을 결정한다는 설명
- **피드백 요지:** 시스템 바깥에서 들어오는 최초의 요구는 누가 받아야 전체 도메인 협력이 자연스럽게 시작되는지 묻습니다.
- **피드백이 나온 이유:** 답안은 시스템 내부 객체의 책임 분배는 설명했지만, 협력을 시작하는 시스템 진입점의 책임은 다루지 않았습니다. 컨트롤러, 애플리케이션 유스케이스, 도메인 객체 사이에서 최초 책임을 어떻게 나눌지 확장해 보라는 피드백입니다.

## 3. 서비스 private 메서드에 남은 도메인 책임 — FB-B1-05

- **대상 내용:** 객체의 데이터를 외부에서 판단하지 말고 데이터의 주인에게 행동을 요청해야 한다는 설명
- **피드백 요지:** 서비스의 private 메서드가 수행하는 로직은 보통 도메인 객체가 맡아야 할 책임일 수 있으므로 가급적 지양해야 한다는 의견입니다.
- **피드백이 나온 이유:** 비즈니스 로직을 서비스의 private 메서드로 나눠도 객체 사이의 책임은 분리되지 않았을 수 있습니다. 서비스 내부의 판단을 상태와 정보를 가진 객체로 이동시킬 수 있는지 확인하라는 피드백입니다. 모든 private 메서드를 금지한다는 의미는 아닙니다.

## 4. 외부 API가 필요한 상태 전이 — FB-B1-06

- **대상 내용:** 환불 상태 전이 규칙을 `Order` 안에 두어 변경을 객체 경계 안에 가둔 예시
- **피드백 요지:** 상태를 바꾸기 전에 외부 환불 정책 검증 API를 반드시 호출해야 한다면, 순수한 도메인 객체의 경계를 유지하면서 어떻게 협력할지 묻습니다.
- **피드백이 나온 이유:** 예시는 상태 전이에 필요한 정보를 객체가 모두 가지고 있다는 전제를 둡니다. 외부 I/O가 필요할 때 외부 호출을 조율하는 책임과 상태를 판단하는 도메인 책임을 어떻게 분리할지도 설명할 필요가 있기 때문입니다.

## 5. 기존 인터페이스로 표현할 수 없는 새 정책 — FB-B1-07

- **대상 내용:** 다형성을 사용하면 새 정책을 기존 코드 수정이 아니라 새 타입 추가로 처리할 수 있다는 설명
- **피드백 요지:** 새로운 정책이 기존 인터페이스의 파라미터와 반환 타입으로 표현할 수 없는 완전히 다른 문맥을 요구하면 어떻게 할지 묻습니다.
- **피드백이 나온 이유:** 답안은 새로운 변화가 기존 역할의 계약 안에 들어온다는 전제를 둡니다. 입력, 결과, 처리 흐름의 의미까지 다르면 기존 인터페이스에 억지로 맞추지 말고 역할이나 유스케이스 경계를 다시 나눠야 할 수 있음을 짚은 피드백입니다.

다섯 피드백의 공통 주제는 **객체지향 원칙을 적용하는 방법보다, 그 원칙의 전제가 깨졌을 때 기존 경계를 어떻게 다시 설계할 것인가**입니다.
