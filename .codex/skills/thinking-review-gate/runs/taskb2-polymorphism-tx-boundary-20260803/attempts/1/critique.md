## 문제 지점

- `[근거 앵커 부족]` 현재 추천의 핵심 결론인 `지금은 ReservationFlow까지 올리지 않는다`가 입력의 확인된 사실과 직접 묶여 있지 않다. `현재 task에서는 공통 reserveTicket 흐름이 있고, 확인된 차이는 결제 방식의 내부 처리뿐이며, Spring 설정·DB 배치·전파 속성은 주어지지 않았다`는 문맥을 전면에 세워야 사용자가 왜 이 결론이 나왔는지 검증할 수 있다.
- `[예시 코드의 오해 가능성]` `TicketReservationService.reserve()` 예시는 `pay -> reserve -> save`를 사실상 추천 순서처럼 보이게 만든다. 그런데 뒤에서는 결제 방식에 따라 잠금 순서와 저장 순서가 달라질 수 있다고 설명한다. 설명용 코드가 핵심 주장과 충돌하는 인상을 준다.
- `[PaymentMethod 계약 정의 부족]` 답변의 분기 기준이 `같은 PaymentMethod 계약을 지킬 수 있다면`인데, 여기서 말하는 계약이 무엇인지 불명확하다. 단순히 `pay()` 시그니처만 공유하면 된다는 뜻으로 읽히면, 피드백이 문제 삼은 얇은 인터페이스 한계를 다시 반복하게 된다.
- `[사실과 일반론의 경계 흐림]` `DB commit 실패는 proxy 밖에서 발생할 수 있다` 같은 문장은 현재 task에서 확인된 사실이 아니라 Spring 일반론 또는 가능성이다. 이런 문장은 보조 예시로는 괜찮지만, 현재 시스템에 대한 판단처럼 들리지 않게 경계를 더 분명히 해야 한다.

## 확인 필요

- 포인트 차감 데이터와 티켓 데이터가 실제로 같은 DB와 같은 transaction manager에 묶이는가.
- 포인트 결제와 카드 결제가 현재 정말로 다른 잠금 순서, 완료 상태, 보상 정책을 요구하는가. 아니면 아직 피드백 차원의 가정인가.
- 외부 카드 API에 취소, void, 멱등성 계약이 있는가.
- 예약 도메인이 `PENDING` 같은 중간 상태를 허용하는가.
- 이 답변이 실제 Spring 구현 판단인지, 과제 수준의 설계 원칙 답변인지 범위를 어디까지 둘 것인지.

## 수정 제안

- 서두에서 판단 근거를 먼저 고정하라. `현재 확인된 사실만 보면 공통 reserveTicket 흐름은 하나이고, 결제 방식 차이가 전체 유스케이스 분리까지 확정할 증거는 없다`는 식으로 결론을 입력 문맥에 직접 연결하는 편이 낫다.
- 예시 코드는 제거하거나 `순서를 확정한 예시가 아니라 인터페이스 위치만 보여주는 의사코드`라고 명시하라. 지금 형태는 사용자가 실제 추천 순서로 읽기 쉽다.
- `PaymentMethod` 계약이 최소한 무엇을 포함해야 하는지 한 줄로 정의하라. 예를 들면 `성공/실패뿐 아니라 pending 여부, 취소 가능성, 보상에 필요한 식별자까지 공통 의미로 다룰 수 있어야 한다`는 수준의 설명이 필요하다.
- `이 조건을 만족하지 못하면 ReservationFlow로 올린다`는 승격 기준을 더 선명하게 적어라. 지금도 신호 목록은 있지만, `결제 방식이 순서·상태·복구정책까지 바꾸면 payment polymorphism이 아니라 flow polymorphism 문제다`처럼 한 문장으로 압축하는 편이 좋다.
- Spring-specific caveat은 유지하더라도 `현재 시스템에서 확인된 사실은 아니고, 실제 구현에서는 이런 추가 확인이 필요하다`고 표시해 사실과 추정을 분리하라.

## 요약

초안의 방향은 맞다. 다만 지금 상태는 `왜 아직 Flow 분리가 과한지`에 대한 근거 연결이 약하고, 예시 코드가 오히려 순서 결정을 암시한다. 결론을 입력 문맥에 더 단단히 고정하고, `PaymentMethod 계약`의 의미와 `Flow로 올리는 전환 조건`을 더 명확히 쓰면 사용자가 검증 가능한 답변이 된다.
