> 맞습니다. 할인 계산이 복잡해진다고 곧바로 모든 할인을 하나의 `DiscountPolicy` 다형성으로 묶는 것은 적절하지 않습니다. 현재의 단순 비율 할인은 구체 클래스로 유지합니다. 이후 같은 최소 입력과 같은 결과 계약을 공유하는 대체 할인 중 하나를 선택해야 할 때 Strategy 인터페이스를 도입하고, 구체 구현은 서비스 내부가 아니라 Composition Root에서 생성해 주입하겠습니다. 반대로 VIP와 외부 쿠폰처럼 입력과 협력이 다르면 가격 계산 서비스가 좁은 규칙들을 명시적으로 조합합니다. 여러 정책의 집합이나 순서가 실제로 동적일 때만 공통 컨텍스트와 목록 순회를 검토하겠습니다.

이 답변은 현재 구조를 유지하면서도 “복잡해지면 인터페이스”라는 단순한 결론을 피한다.

## FB-B5-02 · 유예의 한계와 조기 스멜

**원문 앵커**: `task2/assignments/taskB-5.md:34-35` · FB-B5-02

### 내가 주장한 내용

현재 할인은 한 종류이고 변경도 두 production 파일에 갇혀 있으므로 가격 축을 더 추상화하지 않는다. 두 번째 할인이 확정되는 `v = 2` 시점을 `DiscountPolicy` 인터페이스 도출 트리거로 기록했다.

### 피드백이 날아온 내용

피드백은 현재 결론을 바로 부정하지 않는다. 요구는 두 번째 정책으로 명확하게 등장하기 전에 입력, 조건, 외부 협력이 점진적으로 늘어난다는 점을 지적한다. 따라서 `v = 2` 이전에 관찰할 수 있는 준비 신호와 YAGNI를 지키는 준비 범위를 구체화하라는 요구다.

### 핵심 판단

기존 답안은 **준비 리팩토링**과 **다형성 추상화 도입**을 같은 시점으로 묶었다. 둘을 분리하는 편이 낫다.

```text
현재 스멜 발생
  -> 기존 책임 정리와 외부 경계 분리
  -> 대체 구현과 공통 계약 확인
  -> 그때 인터페이스 도입
```

`v >= 2`는 인터페이스를 검토하는 신호로 유지할 수 있다. 그보다 앞선 미세한 스멜은 인터페이스를 미리 만들라는 신호가 아니라, 현재 구체 코드를 응집시키고 변경 비용을 낮추라는 신호로 본다.

관찰 가능한 신호는 다음과 같다.

| 신호 | 코드에서 보이는 모습 | 먼저 할 준비 |
|---|---|---|
| 입력 증가 | `finalAmount`에 등급, 쿠폰, 채널 등이 계속 추가됨 | 관련 값의 책임과 규칙 경계 재검토 |
| 외부 협력 유입 | `TicketService`가 가격 계산 때문에 쿠폰 API나 등급 조회를 직접 수행함 | 외부 I/O를 포트로 분리하고 계산에는 검증된 값 전달 |
| 변경 이유 증가 | 한 `DiscountPolicy`가 임계 금액, 등급, 쿠폰 장애 대응 때문에 각각 바뀜 | 서로 다른 이유로 변하는 구체 규칙을 분리 |
| 조건 분기 반복 | 같은 할인 타입 `if` 또는 `switch`가 둘 이상의 호출부에 나타남 | 공통 계약을 확인한 뒤 Strategy 검토 |
| 변경 전파 | 가격 규칙 하나가 서비스, 계산 클래스, 외부 연동 여러 곳을 함께 수정하게 함 | Shotgun Surgery 위치로 책임 이동 |
| 테스트 팽창 | 단순 가격 규칙 검증에 저장소와 외부 API mock이 필요해짐 | 순수 계산과 오케스트레이션 분리 |

### 답변·변론 후보

1. **추천 · 준비와 추상화를 단계적으로 분리한다**

   > `v = 2`를 기다리는 동안 아무것도 하지 않는 것은 아닙니다. 입력 증가, 외부 I/O 유입, 반복 분기, 변경 전파, 테스트 mock 증가가 현재 변경에서 관찰되면 먼저 구체 규칙의 응집도와 경계를 정리하겠습니다. 다만 이 단계에서 사용되지 않는 인터페이스나 Factory는 만들지 않습니다. 같은 최소 입력과 결과 계약을 가진 대체 구현이 확인될 때 Strategy를 도입하고, 구체 구현은 Composition Root에서 조립하겠습니다.

   - **얻는 것**: 현재 문제에 근거해 준비하면서 잘못된 미래 인터페이스를 피한다.
   - **비용**: `v` 하나만 세는 기존 게이트보다 판단 항목이 늘어난다.
   - **적합 조건**: 요구는 아직 하나지만 현재 변경 경로에서 실제 마찰이 관찰될 때 적합하다.

2. **기존 `v >= 2` 게이트를 엄격하게 유지한다**

   > 요구가 확정되기 전에는 현재 구체 클래스와 테스트만 유지하고, 두 번째 정책이 승인된 변경 범위에 들어오면 기능 구현 전에 인터페이스를 추출하겠습니다.

   - **얻는 것**: 가장 단순하고 결정적인 YAGNI 기준을 유지한다.
   - **비용**: 할인 종류는 하나인 채 외부 I/O와 입력만 복잡해지는 FB-B5-01의 반례를 놓친다.
   - **적합 조건**: 변경이 작고 되돌리기 쉬우며 가격 정책의 변화 빈도가 낮을 때 적합하다.

3. **인터페이스와 Factory를 미리 도입한다**

   > 가격 정책이 핵심 변동 축이라는 제품 로드맵이 이미 확인됐다면 구현이 하나여도 Strategy와 조립 경계를 먼저 둡니다.

   - **얻는 것**: 다음 구현을 추가할 때 구조 변경이 작다.
   - **비용**: 공통 계약이 확인되기 전에 잘못된 인터페이스를 고정할 수 있고 현재 코드가 복잡해진다.
   - **적합 조건**: 두 번째 정책이 막연한 가능성이 아니라 가까운 일정으로 확정됐을 때만 적합하다.

### 추천 답변

> 말씀하신 것처럼 `v = 2`만을 유일한 트리거로 두면 요구가 점진적으로 스며드는 과정을 놓칠 수 있습니다. 그래서 준비 리팩토링과 다형성 도입을 분리해서 보겠습니다. 입력이 늘거나, 가격 계산 때문에 외부 I/O가 서비스에 들어오거나, 같은 조건 분기가 반복되거나, 가격 변경이 여러 파일로 전파되거나, 단순 계산 테스트에 여러 mock이 필요해지는 순간은 준비 신호입니다. 이때는 현재 구체 규칙을 응집시키고 외부 경계를 분리하되 사용되지 않는 인터페이스와 Factory까지 만들지는 않겠습니다. 이후 같은 최소 입력과 결과 계약을 가진 대체 구현이 실제로 확인될 때 Strategy를 도입하고 Composition Root에서 구현을 조립하겠습니다. 현재 문제를 줄이는 준비는 YAGNI 위반이 아니지만, 미래 가능성만을 위해 사용되지 않는 확장 구조를 만드는 것은 과잉 대응이라고 봅니다.

이렇게 답하면 YAGNI를 “아무 준비도 하지 않는다”가 아니라 “현재 증거가 없는 미래 구조를 만들지 않는다”로 정의할 수 있다.
