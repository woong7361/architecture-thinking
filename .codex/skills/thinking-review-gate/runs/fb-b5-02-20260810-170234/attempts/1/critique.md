## 문제 지점

- [근거 앵커] 초안은 `task2/assignments/taskB-5.md:34-35`만 직접 앵커로 제시한다. 하지만 핵심 claim인 `v >= 2` 기준, `refactoring-criteria.md`, `change-resilience-test.md`, FB-B5-01에서 합의한 Composition Root 기준은 사용자가 바로 따라갈 수 있는 파일·라인 근거가 부족하다.

- [용어 일관성] 스멜 표의 “한 `DiscountPolicy`가 임계 금액, 등급, 쿠폰 장애 대응 때문에 각각 바뀜”은 `v = 2` 이전에는 아직 `DiscountPolicy` 인터페이스를 만들지 않는다는 결론과 살짝 충돌해 보일 수 있다. 이 항목은 “할인 계산 구체 클래스” 또는 “가격 계산 규칙”처럼 현재 구조 기준 용어로 바꾸는 편이 안전하다.

- [준비 리팩토링 범위] “외부 I/O를 포트로 분리”는 YAGNI를 지키는 준비로 제시되지만, 포트 분리도 추상화이므로 조건을 더 좁혀야 한다. 외부 협력이 실제로 유입됐고 계산 테스트나 변경 전파를 악화시키는 경우에만 분리한다고 명시해야 한다.

- [불확실성 경계] 초안은 현재 코드에서 실제로 해당 스멜이 관찰됐는지, 아니면 FB-B5-02에 대한 일반 대응 기준인지가 일부 섞여 있다. “현재 확인된 사실”과 “앞으로 관찰할 신호”를 더 분리하면 검증 가능성이 높아진다.

## 확인 필요

- `refactoring-criteria.md`에서 `v = 기존 구체 변형 수 + 확정 예정 변형 수`와 `v >= 2` 판단이 적힌 정확한 위치.
- `change-resilience-test.md`와 과제 본문에서 두 번째 할인 종류 등장 시 인터페이스 도출을 설명하는 정확한 위치.
- 현재 코드 또는 과제 맥락에서 외부 I/O 유입, mock 증가, 반복 분기 같은 스멜이 실제로 이미 보이는지 여부.

## 수정 제안

- `원문 앵커`를 하나만 두지 말고, 핵심 claim별로 파일 근거를 짧게 붙인다. 예: `refactoring-criteria.md`는 `v >= 2` 기준, `change-resilience-test.md`는 두 번째 할인 등장 시 인터페이스 도출 기준, `taskB-5.md`는 FB-B5-02 피드백 위치로 나눈다.

- 스멜 표의 `DiscountPolicy` 표현을 현재 구조 기준 표현으로 바꾼다. 예: “할인 계산 구체 클래스가 임계 금액, 등급, 쿠폰 장애 대응 때문에 각각 바뀜”.

- “외부 I/O를 포트로 분리” 앞에 조건을 붙인다. 예: “가격 계산이 외부 조회에 직접 의존하기 시작해 순수 계산 테스트가 어려워질 때”.

- 추천 답변에서 “준비 리팩토링”의 범위를 더 명확히 제한한다. 현재 증거가 있는 응집도 정리, 테스트 분리, 외부 협력 격리는 허용하고, 사용되지 않는 Strategy, Factory, 정책 목록, 공통 컨텍스트는 보류한다고 대비시키면 좋다.

- “현재 관찰된 스멜”과 “앞으로 관찰할 조기 신호”를 문장상 분리한다. 지금은 FB-B5-02에 답하기 위한 기준 제안이므로, 실제 코드에서 이미 관찰된 것처럼 읽히는 표현은 줄이는 편이 낫다.

## 요약

초안의 결론과 대응 방향은 입력 제약에 대체로 맞다. 다만 핵심 근거의 파일 앵커가 부족하고, `v = 2` 이전 단계 설명에서 아직 만들지 않을 `DiscountPolicy` 용어를 사용해 약한 모순이 생긴다. 준비 리팩토링과 추상화 도입을 분리한다는 핵심 메시지는 유지하되, 근거 위치와 적용 조건을 더 좁히면 더 검증 가능한 답변이 된다.
