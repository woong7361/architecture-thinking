현재 열린 질문 5개는 모두 같은 뿌리를 갖는다. 테스트와 규칙은 자동차의 차선 유지 장치처럼 이미 정한 방향 안에서 이탈을 막아주지만, 목적지를 고르고 낡은 지도를 버리고 관할 경계를 나누는 결정까지 대신하지는 못한다.

결론부터 말하면 현재 프로젝트에는 다음 조합이 맞다.

1. 인수 시나리오는 애플리케이션 입출력 계약에 고정하고, 실행 glue의 변경은 테스트 어댑터 한곳으로 격리한다.
2. 작업 시작 전에 짧은 문제 정의 리뷰를 추가하고, 구현 중에는 지금처럼 작은 변경 단위를 유지한다.
3. 자동화 여부는 결정의 가역성과 영향 범위로 나누고, 큰 결정은 ADR과 작은 실험으로 사람이 승인한다.
4. 기존 테스트를 불변식·호환 계약·우연한 quirk로 분류하고, 패러다임 변경은 점진 교체한다.
5. 현재 카타는 분산 시스템으로 나누지 않는다. 필요하면 먼저 모듈 경계를 만들고 실제 변경 결합도를 측정한다.

## 1. 테스트는 어디까지 바깥에서 관측해야 하는가

대상은 `taskB-0.md:59-66`의 Cucumber glue 문제다. Gherkin은 유지됐지만 `setReserved`와 `PaymentApi` 같은 코드 이름이 바뀌자 glue가 깨졌다. 현재 step도 상태 준비는 개선됐지만, 단언은 여전히 저장소에서 `Ticket`을 꺼내 getter를 읽고 `RecordingPaymentApi`를 직접 조회한다.

문제는 테스트 코드가 조금도 바뀌지 않아야 한다는 데 있지 않다. 순수한 구조 변경 때 비즈니스 시나리오와 기대 결과는 유지되고, 필요한 수정이 경계 어댑터에만 국소화되어야 한다. 또한 인수테스트는 동작을 보존하지만 규칙이 어느 객체에 놓였는지는 보장하지 못하므로 설계 품질 게이트와 역할을 분리해야 한다.

| 대안 | 장점 | 비용·위험 |
| --- | --- | --- |
| 애플리케이션 포트 기반 인수테스트 + 전용 test adapter + 소수 E2E | Gherkin은 `reserveTicket`, 예약 조회, 결제 완료 메시지 같은 안정된 계약만 알고 내부 타입 개명은 adapter에서 흡수한다. 빠른 인수테스트와 실제 배선 검증을 함께 얻는다. | 테스트 adapter와 포트 계약 테스트를 관리해야 한다. fake가 실제 adapter와 달라질 수 있어 소수 E2E가 필요하다. |
| HTTP·메시지·실DB를 통과하는 완전한 black-box E2E 중심 | 사용자 관측과 가장 가깝고 실제 배선 오류까지 잡는다. | 느리고 실패 원인 진단이 어렵다. 환경·데이터 때문에 불안정해질 수 있으며 모든 경우를 이 층에 두면 피드백이 늦어진다. |
| 현재처럼 in-process glue가 저장소와 test double을 직접 읽음 | 빠르고 실패 위치가 명확하며 기존 카타에는 구현 비용이 작다. | 저장소·도메인 타입·double 이름에 계속 결합되고, adapter가 실제 외부 계약과 달라져도 알기 어렵다. |

추천은 첫 번째다. `Then 티켓이 예약된다`는 `ReservationQuery` 같은 안정된 조회 계약으로 확인하고, `Then 결제가 청구된다`는 outbound port에 기록된 최종 청구 메시지로 확인한다. 포트 이름이 바뀌면 glue 전체가 아니라 test adapter의 배선만 고친다. 구조 품질은 B-7에서 만든 규칙·리뷰 게이트로 별도 확인한다. Ports and Adapters의 원문도 유스케이스를 외부 기술이 아니라 애플리케이션 경계에 대해 작성해야 안정적이라고 설명한다.

## 2. 짧게 공유하는 것 외에 혼자 오래 끄는 습관을 어떻게 바꿀까

대상은 `taskB-0.md:82`의 v0.1·v0.2 공유 방식이다. 작은 배치는 잘못된 방향에서 생기는 매몰 비용을 낮추지만, 출발 전에 문제를 잘못 정의하거나 리뷰어가 핵심 가정을 보지 않으면 작은 오답을 여러 번 만드는 문제가 남는다.

| 대안 | 장점 | 비용·위험 |
| --- | --- | --- |
| 구현 전 문제 정의 체크포인트 | 문제, 성공 기준, 하지 않을 것, 선택지 2개, 가장 불확실한 가정을 먼저 공유해 구현 전에 방향 오류를 잡는다. | 동료의 응답을 기다릴 수 있고 작은 일에도 적용하면 절차가 무거워진다. |
| 고불확실성 구간만 페어·모브 작업 | 질문과 답이 실시간으로 오가며 암묵지와 설계 의도를 공유한다. | 두 사람 이상의 시간을 동시에 쓰며 익숙한 작업에는 과하다. |
| 시간 제한 spike + 중단 조건 + 결정 기록 | 혼자 탐색할 자유를 유지하면서도 정해진 시점에 증거와 질문을 들고 나온다. | 제한 시간 안에서도 잘못된 가정을 탐색할 수 있고, 최종 방향 확인은 여전히 필요하다. |

추천은 “문제 정의 체크포인트 → 시간 제한 spike → 작은 변경 리뷰”의 조합이다. 예를 들어 반나절 이상 예상되는 작업은 구현 전에 5줄짜리 문제 정의를 공유하고, 가장 불확실한 부분만 60~90분 탐색한 뒤 계속할지 묻는다. 시간 수치는 팀 반응 속도에 맞춰 조정할 운영 기준이다. Google의 코드 리뷰 지침도 작은 변경이 리뷰 속도·깊이·롤백에는 유리하지만, 리뷰 대기를 줄이기 위해 페어 프로그래밍이나 즉시 가능한 리뷰어 같은 보완책이 필요하다고 설명한다.

## 3. 자동화 뒤에도 인간이 책임져야 하는 거시적 결단은 무엇인가

대상은 페이지 총평의 첫 질문이다. B-7의 숫자 규칙은 주어진 목표 안에서 과설계를 억제했지만, 무엇을 목표로 삼을지와 어떤 손실을 감수할지는 정하지 못한다. 예를 들어 자동화는 “포트 145줄로 변경 4줄을 아꼈다”를 계산할 수 있지만, 벤더 독립성이 규제·협상력·사업 지속성 때문에 그 비용보다 중요한지는 사람이 결정해야 한다.

| 대안 | 장점 | 비용·위험 |
| --- | --- | --- |
| 가역성·영향 범위에 따른 결정 등급 | 되돌리기 쉽고 영향이 작은 결정은 자동화하고, 데이터·계약·조직 경계처럼 되돌리기 어려운 결정은 사람이 승인한다. 속도와 책임 경계가 명확하다. | 위험 등급을 잘못 분류하면 자동화가 큰 결정을 통과시킬 수 있다. |
| ADR에 맥락·대안·사업 결과·책임자 기록 | 왜 선택했는지와 버린 대안, 재검토 조건을 남겨 나중에 전제를 검증할 수 있다. | 기록이 승인 의식으로 변하면 느려지고, 갱신하지 않으면 낡은 문서가 된다. |
| 작은 실험으로 결정을 지연하는 real-option 방식 | 실제 비용·사용자 반응·장애 위험을 보고 결정해 추측을 줄인다. | 실험 기간과 이중 운영 비용이 들며 보안·법률·데이터 손실처럼 실험할 수 없는 결정도 있다. |

추천은 세 가지를 계층으로 쓰는 것이다. 자동화가 결정 등급을 분류하고 근거를 계산한다. 되돌리기 어렵거나 영향 범위가 큰 결정은 사람이 ADR로 승인한다. 되돌릴 수 있지만 불확실한 결정은 작은 실험으로 증거를 만든다. 인간의 최종 책임은 목적, 허용 위험, 경계, 예외, 피해를 누가 부담하는지를 정하는 데 있다.

## 4. 기존 도메인 지식과 테스트가 부채가 되면 어떻게 경계를 다시 그을까

대상은 페이지 총평의 두 번째 질문이다. 현재 특성화 테스트는 널 참조 종료와 결제 후 저장 실패 시 미보상도 기존 quirk로 보존한다. 리팩토링 중에는 유효한 안전망이지만, 새로운 정책이 정상 오류 처리와 보상을 요구하면 같은 테스트가 변화를 막는 낡은 계약이 된다.

| 대안 | 장점 | 비용·위험 |
| --- | --- | --- |
| 테스트를 불변식·호환 계약·quirk로 분류하고 폐기 조건 지정 | 무엇을 영구 보존하고 무엇을 임시 보존하는지 드러난다. 새 정책이 오면 quirk 테스트를 의도적으로 교체할 수 있다. | 분류가 틀릴 수 있고 owner·재검토 시점 관리가 필요하다. |
| Strangler Fig 또는 Branch by Abstraction으로 신구 모델 병행 | 새 경계를 일부 트래픽부터 검증하고 비교·롤백하면서 점진 전환할 수 있다. | 이중 구현, 데이터 동기화, 임시 추상화와 운영 복잡도가 생긴다. |
| 별도 bounded context + Anti-Corruption Layer로 새 모델 보호 | 새 모델이 낡은 용어와 규칙에 오염되지 않고 필요한 호환만 번역한다. | 변환 계층과 중복 모델을 유지해야 하며 경계를 잘못 잡으면 복잡성만 늘어난다. |

추천은 먼저 테스트를 세 종류로 분류하고, 큰 전환이면 두 번째와 세 번째를 결합하는 것이다. 새 비즈니스 계약을 먼저 테스트로 고정한 뒤 신구 구현을 병행하고, 트래픽과 데이터의 기준 시스템을 단계적으로 옮긴다. 낡은 테스트는 새 계약 승인과 전환 완료 조건이 충족됐을 때 제거한다. 대규모 변경을 추상화 뒤에서 점진적으로 수행하고 항상 동작 가능한 상태를 유지하는 방식은 Branch by Abstraction의 핵심과 맞는다.

## 5. 풍부한 도메인 모델은 언제 분산된 컨텍스트로 나눌까

대상은 페이지 총평의 세 번째 질문이다. 객체가 크거나 협력자가 많다는 사실만으로 bounded context나 마이크로서비스 분리를 결정하면, 현재 카타에서 포트 145줄을 쓰고 4줄을 아낀 것과 같은 과설계가 더 큰 규모로 반복될 수 있다. 먼저 “하나의 객체가 너무 큰 문제”, “한 컨텍스트 안 aggregate 경계 문제”, “서로 다른 비즈니스 모델이 섞인 문제”를 구분해야 한다.

| 대안 | 적합한 상황 | 비용·위험 |
| --- | --- | --- |
| 같은 컨텍스트 안에서 객체·aggregate 책임만 재분배 | 언어, 정책 소유자, 배포 주기는 같고 특정 객체만 비대할 때 | 가장 싸고 트랜잭션이 단순하지만 컨텍스트 수준의 결합은 그대로다. |
| 모듈러 모놀리스 안에서 bounded context 후보를 모듈로 분리 | 비즈니스 언어·변경 이유가 갈리기 시작했지만 독립 배포·확장이 아직 필요 없을 때 | 운영비가 낮고 경계를 시험하기 쉽다. 한 프로세스라 경계 위반을 도구와 리뷰로 막아야 한다. |
| bounded context를 독립 서비스로 추출 | 독립 팀·배포 주기·확장·장애 격리가 실제로 필요하고 경계 간 강한 동기 트랜잭션이 드물 때 | 자율성과 격리를 얻지만 분산 트랜잭션, 지연, 관측성, 데이터 소유권과 운영 비용을 떠안는다. |

분리 신호는 라인 수가 아니라 다음처럼 관찰해야 한다. 같은 용어가 영역마다 다른 뜻과 규칙을 갖는지, 서로 다른 비즈니스 책임자와 팀이 소유하는지, 변경 이력이 서로 독립적인지, 독립 배포·확장·장애 격리가 필요한지, 경계를 넘는 강한 일관성 트랜잭션을 줄일 수 있는지다. 이 신호가 반복해서 함께 나타나면 먼저 모듈 경계를 만들고 변경 결합도를 측정한 뒤 서비스 추출을 검토한다.

현재 카타에는 분산 분리를 권하지 않는다. 프로젝트 보고서 자체가 이 규모에서는 포트도 본전을 못 뽑았다고 한계를 명시한다. 우선 `Reservation`, `Payment`, `Member` 같은 후보 모듈의 공개 계약과 의존 방향만 제한하고, 이후 실제 변경이 한 모듈 안에 갇히는지 측정하는 편이 맞다. Microsoft는 bounded context마다 독립 모델을 두되 서비스 크기는 aggregate보다 작지 않고 bounded context보다 크지 않게 보라는 일반 원칙을 제시하고, AWS는 비즈니스 역량 기반 분해가 안정적일 수 있지만 깊은 비즈니스 이해와 추가 운영 비용이 필요하다고 설명한다.

## 우선순위

지금 바로 적용할 것은 1번과 2번이다. 테스트 포트와 test adapter의 역할을 분리하고, 구현 전 문제 정의 체크포인트를 추가한다. 3번은 자동화 파이프라인의 승인 규칙으로 발전시킬 수 있다. 4번과 5번은 현재 카타에 구조를 더 만드는 일이 아니라, 회사 코드에서 패러다임 전환이나 컨텍스트 분리 신호가 실제로 나타날 때 사용할 판단 기준으로 보관하는 것이 적절하다.
