맞습니다. 핵심은 Goodhart의 법칙이고, 사람의 slow-loop이 필요하다는 결론입니다. 다만 “모든 실행 중간에 사람이 승인해야 한다”보다는 “자동 평가가 실제 품질과 계속 정렬되는지 사람이 주기적·조건부로 교정해야 한다”가 더 정확합니다.

구조를 나누면 다음과 같습니다.

```text
Fast-loop
Gen → 테스트·스키마·정적 규칙 → 자동 통과/재시도

Slow-loop
사람 verdict → rubric/Gen과의 불일치 확인 → calibration set 갱신 → 규칙 개선
```

자동화할 수 있는 것은 사실 신호다. 테스트 GREEN, 컴파일 성공, 호출처 0 public API, 스키마 위반처럼 기계적으로 확인할 수 있는 것은 fast-loop에서 처리해도 된다.

사람이 필요한 것은 품질 proxy를 교정하는 지점이다. 예를 들어 Eval PASS와 Critique high가 충돌하거나, rubric을 바꾸려 하거나, 기존 calibration set에 없는 사례가 나오거나, 일정 비율을 표본 감사할 때 slow-loop로 올린다.

세 가지 운영 방식이 있다.

1. 모든 run을 사람이 승인한다.
   - 가장 안전하지만 사람이 병목이 되어 자동화 가치가 크게 줄어든다.
2. 위험 기반 slow-loop를 둔다. 추천한다.
   - 평상시에는 fast-loop를 쓰고, 신호 충돌·새 유형·rubric 변경·표본 감사 때만 사람이 판정한다. 안전성과 처리량의 균형이 가장 좋다.
3. 정기 표본만 사람이 본다.
   - 비용은 가장 작지만 개별 high-risk 결과가 표본에 잡히기 전까지 통과할 수 있다.

따라서 사람은 매 실행의 승인자라기보다 품질 기준의 소유자다. 사람 verdict를 동결 캘리브레이션 셋으로 쌓고, LLM Eval이 그 verdict와 계속 일치하는지 확인해야 Goodhart 위험을 줄일 수 있다. 사람을 완전히 빼면 rubric 점수 상승을 실제 품질 상승으로 착각할 수 있고, 모든 실행에 넣으면 확장성이 사라진다.

현재 B-6에는 `Eval PASS + Critique high` 충돌이 이미 있으므로, 이 경우는 slow-loop로 보내는 대표 트리거가 된다.
