# Task B-2 피드백 분석

전체 피드백 4건이 모두 실질적인 질문이나 반례를 포함하므로 4건을 분석했다. 리액션·단순 동의로 제외한 항목은 0건이다. 댓글 앞부분의 칭찬은 덜어내고 새로 제기된 쟁점만 다뤘다.

## FB-B2-01 · 외부 사실에 의존하는 규칙도 순수하게 테스트할 수 있는가

### 내가 주장한 내용

생성자 주입만으로 테스트하기 좋은 설계가 되지는 않는다. 현재 코드는 예약 규칙과 조회·결제·저장이 한 메서드에 섞여 있어 규칙 하나를 검증할 때도 모든 외부 의존을 준비해야 한다. 예약 결정은 도메인 객체로 옮기고 외부 입출력은 얇은 서비스에 남기면, 규칙은 값 기반으로 테스트하고 외부 의존만 별도로 격리할 수 있다고 주장했다.

### 피드백이 날아온 내용

이 피드백은 원래 진단을 부정하기보다 적용 범위를 넓히는 질문이다. 예약 가능 여부가 과거 결제 이력이나 실시간 외부 판정처럼 도메인 객체가 혼자 알 수 없는 사실에 좌우된다면, 결정과 입출력을 어떻게 나눠야 다시 Mock 중심 테스트로 돌아가지 않는지 묻는다.

### 답변·변론 후보

1. **외부 사실을 먼저 수집해 값으로 전달한다**: 애플리케이션 서비스가 필요한 사실을 포트에서 조회해 `ReservationFacts` 같은 불변 값으로 만들고, 도메인 정책은 `decide(ticket, user, facts)`처럼 그 값만 받아 판단하게 한다. 외부 조회와 결과의 최신성은 서비스가 책임지고, 규칙의 조합은 여전히 Mock 없이 테스트한다.
   - **트레이드오프**: 순수 규칙 테스트와 외부 연동 테스트가 깔끔히 갈린다. 반면 조회 시점과 상태 변경 시점 사이에 사실이 바뀔 수 있다. 실시간성이 강할수록 타임스탬프, 버전, 재확인, 잠금 같은 일관성 장치가 추가된다. 외부 사실을 한 번의 관측값으로 다뤄도 되는 경우에 적합하다.

2. **도메인 정책이 좁은 조회 포트에 의존하게 한다**: 규칙이 실제 조회 순서나 실패 의미까지 소유해야 한다면 도메인 서비스가 `PaymentHistoryQuery`, `BlacklistQuery` 같은 역할을 호출하게 한다. 테스트에서는 호출 검증 중심 Mock 대신 의미 있는 시나리오 데이터를 가진 Fake를 사용한다.
   - **트레이드오프**: 규칙의 흐름과 외부 판정의 의미를 한곳에서 읽을 수 있고 실시간 조회도 직접 표현한다. 대신 도메인 테스트가 완전히 순수하지 않으며 외부 실패와 지연까지 테스트 조합에 들어온다. 조회 자체가 규칙의 일부이고 그 순서가 중요할 때 적합하다.

3. **외부 판정과 예약을 두 단계의 의사결정으로 모델링한다**: 먼저 외부 시스템이 승인 결과를 만들고, 도메인은 유효기간과 근거가 포함된 승인 값을 받아 예약 상태를 전이한다. 판정이 오래 걸리면 `PENDING`, `APPROVED`, `REJECTED` 같은 상태로 흐름을 드러낸다.
   - **트레이드오프**: 외부 판정과 핵심 상태 전이를 각각 독립적으로 테스트하고 재시도나 감사 이력을 명확히 만들 수 있다. 대신 중간 상태, 만료, 중복 요청, 보상 처리가 필요해진다. 외부 판정의 지연과 실패가 정상적인 업무 흐름인 경우에 적합하다.

핵심 변론은 “외부 사실이 필요한 규칙 전체를 순수 함수로 만들 수 있다”가 아니다. 순수하게 유지할 수 있는 것은 관측된 사실을 받아 결정을 내리는 부분이며, 사실의 수집과 최신성 보장은 입출력 경계에 남는다.

## FB-B2-02 · 얇은 서비스의 조립 흐름은 어떻게 검증할 것인가

### 내가 주장한 내용

규칙은 도메인 객체에서 값 기반으로 테스트하고, 서비스에는 조회·결제·저장 순서를 조립하는 역할만 남긴다고 주장했다. 저장소는 실제 데이터베이스 의미가 중요하므로 Testcontainers 같은 실제 인프라에 가까운 테스트를, 외부 결제 호출은 Mock 또는 Fake를 사용하자고 제안했다.

### 피드백이 날아온 내용

순수 로직을 분리해도 서비스에는 여러 입출력을 잇는 흐름이 남는다. 이 흐름을 어느 테스트 수준에서 얼마나 검증해야 비용 대비 결함 탐지 효과가 가장 높은지 구체적인 전략을 요구한다.

### 답변·변론 후보

1. **서비스 단위 테스트를 소수의 대표 흐름에만 둔다**: 저장소와 외부 호출을 Fake로 바꾸고 성공 흐름, 결제 실패, 저장 전 중단처럼 순서가 의미 있는 분기만 검증한다. 내부 메서드 호출을 모두 복제하지 말고 반환 결과, 저장된 상태, 외부로 나간 명령만 확인한다.
   - **트레이드오프**: 빠르고 실패 원인을 찾기 쉬우며 조립 순서의 회귀를 값싸게 잡는다. 실제 트랜잭션, 쿼리 매핑, 제약조건은 증명하지 못한다. 서비스 흐름이 단순하고 어댑터 테스트가 별도로 있을 때 적합하다.

2. **인바운드 경계부터 실제 데이터베이스까지 묶는 컴포넌트 테스트를 중심에 둔다**: 서비스와 저장소는 실제 구성으로 실행하고 외부 시스템만 제어 가능한 Fake 서버나 Stub으로 대체한다. 내부 상호작용보다 최종 데이터 상태와 외부 요청을 단언한다.
   - **트레이드오프**: 트랜잭션과 저장소 의미까지 한 번에 검증해 조립 흐름의 주요 위험을 잘 잡는다. 실행 시간이 늘고 데이터 준비와 격리 비용이 생기며 실패 원인이 넓다. 데이터베이스 경계가 핵심 위험일 때 비용 대비 효용이 높다.

3. **계층별 계약 테스트를 조합하고 서비스 테스트를 최소화한다**: 도메인 규칙 테스트, 저장소 통합 테스트, 외부 어댑터 계약 테스트를 각각 두고 서비스에는 한두 개의 대표 경로만 남긴다. 같은 분기를 여러 수준에서 반복하지 않는다.
   - **트레이드오프**: 테스트 중복과 전체 실행 비용을 줄이고 각 실패를 빠르게 국소화한다. 개별 계약이 모두 맞아도 실제 조립 설정이나 트랜잭션 경계의 오류가 빠질 수 있다. 구성 검증용 컴포넌트 테스트를 최소 한 개는 유지해야 한다.

현재 예제라면 두 번째 전략을 소수의 핵심 흐름에 적용하고, 도메인 규칙은 빠른 단위 테스트로 넓게 덮는 조합이 가장 균형적이다. 이것은 모든 서비스 분기를 통합 테스트하자는 뜻이 아니라, 데이터베이스와 외부 호출이 만나는 경계의 대표 위험만 선택하자는 제안이다.

## FB-B2-03 · YAGNI를 지키면서 추상화 시점을 어떻게 판단할 것인가

### 내가 주장한 내용

결제수단이 하나뿐이고 추가 가능성이 확인되지 않았다면 구체 호출을 곧바로 추상화하지 않는 선택도 합리적이라고 주장했다. 포인트 결제라는 실제 두 번째 변형이 들어온 시점에는 분기와 새 의존이 기존 예매 흐름을 열게 되므로, 그때 결제 역할을 추출하는 투자가 정당해진다고 봤다.

### 피드백이 날아온 내용

확장 요구가 올지 확신할 수 없는 현실에서 “두 번째 변형이 왔을 때”만으로는 팀의 결정 기준이 부족하다고 지적한다. 추상화를 도입할 구체적인 신호는 무엇인지, 미리 다형성을 만들지 않으면서도 변경하기 쉬운 구조는 어떤 모습인지 묻는다.

### 답변·변론 후보

1. **두 번째 실제 사례 또는 확정된 근시일 요구를 문턱으로 삼는다**: 이미 구현할 두 번째 사례가 있거나 가까운 계획에 소유자와 일정이 잡힌 경우에만 공통 역할을 추출한다. 같은 분기가 두 곳 이상 복제되거나 한 변경이 여러 모듈을 여는 현상이 먼저 나타나도 문턱을 넘은 것으로 본다.
   - **트레이드오프**: 근거 없는 추상화를 줄이고 실제 차이를 본 뒤 올바른 인터페이스를 만들 수 있다. 첫 확장 시점에는 기존 코드를 리팩터링해야 하므로 단기 납기 압박을 받는다. 변경이 되돌릴 수 있고 테스트 안전망이 있는 경우에 적합하다.

2. **다형성은 미루되 변경 지점은 응집시킨다**: 인터페이스를 미리 만들지 않아도 결제 입력을 값으로 묶고, 결제 호출과 결과 해석을 한 작은 경계에 모으며, 예약 규칙과 분리된 테스트를 둔다. 목표는 확장 기능을 미리 구현하는 것이 아니라 나중에 추출할 한 곳을 만드는 것이다.
   - **트레이드오프**: YAGNI를 크게 해치지 않으면서 첫 변경의 비용을 낮춘다. 작은 메서드나 구체 협력자도 현재 요구만 보면 간접 계층이므로, 경계가 자주 바뀌지 않으면 불필요한 구조가 된다. 외부 의존이라는 자연스러운 경계가 이미 보일 때 적합하다.

3. **변경 가능성과 변경 비용을 함께 기록해 결정한다**: 팀이 확장 가능성, 예상 시점, 변경 파급 범위, 데이터 마이그레이션이나 공개 계약처럼 되돌리기 어려운 요소를 짧게 평가한다. 예상 확장 비용이 추상화를 유지하는 비용보다 명백히 클 때만 선투자하고, 판단 근거와 재검토 시점을 기록한다.
   - **트레이드오프**: “느낌상 필요하다”는 논쟁을 비교 가능한 근거로 바꾸고 고비용 변경을 일찍 다룰 수 있다. 확률과 비용은 추정치라 거짓 정밀성을 만들 수 있고 작은 변경마다 기록하면 의사결정 비용이 커진다. 실패 비용이 크거나 여러 팀의 계약이 걸린 변경에 적합하다.

따라서 YAGNI와 확장성은 “아무 준비도 하지 않기”와 “인터페이스를 미리 만들기”의 양자택일이 아니다. 현재 요구에 맞는 단순한 구현을 유지하되, 관련 책임을 한곳에 모으고 관찰 가능한 테스트를 두어 다음 변경이 왔을 때 안전하게 추출할 수 있게 하는 것이 중간 지점이다.

## FB-B2-04 · 결제 방식마다 트랜잭션 경계가 다르면 얇은 인터페이스로 충분한가

### 내가 주장한 내용

결제수단을 하나의 역할로 추출하고 카드와 포인트를 각 구현으로 두면, 새 수단 추가를 기존 예약 메서드의 수정이 아니라 새 구현 추가로 바꿀 수 있다고 주장했다. 이 주장은 결제수단들이 서비스 관점에서 같은 계약과 비슷한 실행 의미를 가진다는 전제를 암묵적으로 두고 있었다.

### 피드백이 날아온 내용

포인트 결제는 외부 API 호출이 아니라 내부 데이터베이스 행에 잠금을 걸고 차감해야 하므로 카드 결제와 원자성, 실패, 복구 방식이 다르다. 이런 구조적 차이까지 단순한 `charge` 인터페이스 뒤에 숨기면 추상화가 현실을 왜곡하지 않는지 묻는 반례다.

### 답변·변론 후보

1. **공통 인터페이스를 유지하되 업무 결과만 계약으로 삼는다**: 호출자는 “결제 승인을 얻는다”는 결과만 알고, 각 구현이 필요한 잠금과 트랜잭션을 내부에서 관리하게 한다. 단 티켓 저장과 결제 사이의 일관성 수준, 실패 의미, 재시도 가능성도 계약에 명시해야 한다.
   - **트레이드오프**: 예약 서비스는 단순하고 결제 구현 추가도 쉬워진다. 그러나 서로 다른 원자성과 보상 책임을 같은 반환값 뒤에 숨기면 호출자가 필요한 제어를 할 수 없다. 두 방식이 동일한 실패 의미와 일관성 약속을 실제로 제공할 수 있을 때만 적합하다.

2. **결제 방식별 애플리케이션 흐름을 나누고 순수한 예약 규칙만 공유한다**: `CardReservationHandler`와 `PointReservationHandler`처럼 유스케이스 조립을 분리한다. 포인트 흐름은 포인트 차감과 티켓 예약을 하나의 로컬 트랜잭션으로 묶고, 카드 흐름은 외부 결제 성공 뒤 저장 실패에 대한 보상 정책을 명시한다.
   - **트레이드오프**: 트랜잭션 경계와 실패 처리가 코드에 드러나 잘못된 공통화를 피한다. 대신 조회와 검증 같은 흐름이 일부 중복되고 진입점에서 결제 방식에 맞는 핸들러를 선택해야 한다. 실행 의미가 본질적으로 다른 결제 방식이 소수일 때 적합하다.

3. **예약을 상태 기반 워크플로로 승격한다**: 예약을 즉시 완료하지 않고 결제 대기, 결제 승인, 예약 확정, 취소 같은 상태 전이로 모델링한다. 포인트는 하나의 로컬 트랜잭션으로 빠르게 확정하고, 외부 결제는 재시도와 보상 또는 메시지 기반 후속 처리를 사용한다.
   - **트레이드오프**: 동기·비동기 방식, 재시도, 장애 복구를 같은 업무 흐름 안에서 명시적으로 다룰 수 있다. 반면 상태 수, 멱등성, 타임아웃, 운영 관측 부담이 크게 늘어난다. 결제 방식이 계속 늘고 장시간 처리나 부분 실패가 정상적으로 발생할 때 적합하다.

이 반례에서는 원래 주장을 그대로 방어하기 어렵다. 인터페이스는 구현체 이름의 차이는 흡수할 수 있지만 트랜잭션과 일관성 의미의 차이까지 자동으로 없애지는 못한다. 현재 규모라면 두 번째 안이 가장 정직하고, 장시간 흐름과 재시도가 실제 요구가 될 때 세 번째 안으로 확장하는 편이 타당하다.
