## 1. 잘못 예측한 변경 축

### 내가 한 말

OOP와 정보 은닉은 요구사항 변경의 파급을 한곳에 국소화한다. 환불 정책도 인터페이스 뒤에 두면 새 정책을 타입 추가로 흡수할 수 있다고 설명했다.

### 들어온 피드백

처음부터 변경 축을 잘못 예측했다면, 그 축을 기준으로 만든 추상화가 오히려 미래 변경의 장애물이 되지 않겠느냐는 질문이다.

### 가능한 방안

1. **현재 분기를 유지한다.**
   - 예시: 현재 `RefundProcessor`의 `PRORATION`, `MANUAL` switch를 한곳에 두고 테스트로 보호한다.
   - 트레이드오프: 구조가 단순하고 잘못된 인터페이스를 피할 수 있다. 반면 변화가 실제로 반복되면 기존 코드를 리팩터링해야 하고, 시기를 놓치면 분기가 퍼질 수 있다.

2. **인터페이스 없이 작은 계산 객체로 격리한다.**
   - 예시: switch와 계산을 concrete `RefundAmountCalculator` 한곳으로 옮긴다.
   - 트레이드오프: 변경은 모으되 추상화 방향은 나중에 정할 수 있다. 반면 변화가 오지 않으면 클래스만 하나 늘어난다.

3. **변경 축이 관찰된 뒤 인터페이스를 만든다.**
   - 예시: 같은 분기가 여러 위치에 복제되거나 정책별 독립 소유권이 생기면 `RefundAmountPolicy`를 추출한다.
   - 트레이드오프: 정책별 확장과 테스트가 쉬워진다. 반면 공통점이 부족하면 사용하지 않는 입력을 모두 받는 거대한 계약이 된다.

### 추천

현재는 1번이다. 분기가 커지지만 방향이 불명확하면 2번, 반복 수정·분기 복제·독립 소유권이 확인되면 3번으로 전환한다. 정책 개수만으로 추상화 여부를 결정하지 않는다.

## 2. 시스템 최초 메시지의 책임

### 내가 한 말

객체지향 설계는 데이터보다 협력이 먼저이며, 협력이 책임과 역할을 결정한다고 설명했다.

### 들어온 피드백

시스템 바깥에서 들어오는 최초 요구는 누가 받아야 전체 도메인 협력이 자연스럽게 시작되는지 묻는 질문이다.

### 가능한 방안

1. **애플리케이션 유스케이스가 최초 업무 메시지를 받는다.**
   - 예시: `RefundController → RefundUseCase.cancel → Order·Refund → PgClient` 순서로 흐른다. 컨트롤러는 입력 변환, 유스케이스는 조회와 외부 호출 순서, 도메인 객체는 상태 판단을 맡는다.
   - 트레이드오프: 진입 기술과 업무 흐름, 도메인 규칙이 분리된다. 반면 유스케이스에 모든 판단을 넣으면 다시 거대한 facade가 된다.

2. **장기 협력은 프로세스 매니저가 받는다.**
   - 예시: `RequestRefund → VALIDATING → PG_CANCEL_PENDING → COMPLETED` 상태를 `RefundProcess`가 관리한다.
   - 트레이드오프: 비동기 승인과 재시도, 실패 복구가 명시된다. 반면 중간 상태, 중복 메시지, 운영 관측 비용이 크게 늘어난다.

### 추천

현재 동기 환불 흐름에는 1번이 맞다. 외부 승인과 재시도가 여러 트랜잭션에 걸치는 실제 요구가 생길 때만 2번으로 전환한다.

## 3. 서비스 private 메서드에 남은 책임

### 내가 한 말

상태를 외부에서 꺼내 판단하지 말고, 데이터의 주인인 객체에게 행동을 요청해야 캡슐화가 지켜진다고 설명했다.

### 들어온 피드백

서비스의 private 메서드가 하는 일도 실제로는 도메인 객체가 맡아야 할 책임일 수 있다는 의견이다.

### 가능한 방안

1. **객체 자신의 불변식은 엔티티로 옮긴다.**
   - 예시: 주문 상태와 남은 환불 가능 금액은 `Order.validateRefundable()`과 `Order.applyRefund()`가 검증한다.
   - 트레이드오프: 상태와 규칙이 함께 있어 변경이 국소화된다. 반면 특정 환불 채널에만 적용되는 규칙까지 넣으면 `Order`가 모든 업무 흐름을 알게 된다.

2. **선택 가능한 계산은 정책이나 값 객체로 옮긴다.**
   - 예시: 수동 환불 검증이 복잡해지거나 재사용되면 `ManualRefundAmount.of(requestAmount, refundableAmount)`로 분리한다.
   - 트레이드오프: 정책별 테스트와 재사용이 쉬워진다. 반면 현재처럼 짧고 한곳에서만 쓰는 규칙이라면 작은 클래스만 과도하게 늘어난다.

3. **도메인 판단이 없는 조율 메서드는 서비스에 남긴다.**
   - 예시: `toPgCommand()`처럼 외부 요청 형식만 변환하는 private 메서드는 서비스에 둔다.
   - 트레이드오프: 공개 API를 늘리지 않고 흐름을 읽기 쉽게 나눌 수 있다. 반면 변환 메서드 안에 정책 판단이 들어가기 시작하면 다시 facade가 된다.

### 추천

private 메서드를 일괄 제거하지 않는다. 현재 `validateRefundable()`은 주문 불변식과 특정 경로 정책으로 나눠 판단한다. `manualAmount()`는 복잡도나 중복이 실제로 늘어날 때만 별도 정책 후보로 본다.

## 4. 외부 API가 필요한 상태 전이

### 내가 한 말

`Order` 안에 환불 상태 전이 규칙을 두면 변경을 객체 경계 안에 가둘 수 있다고 설명했다.

### 들어온 피드백

상태 변경 전에 외부 환불 정책 API의 검증이 반드시 필요하다면, 순수한 도메인 객체의 경계를 어떻게 지킬지 묻는 가상 질문이다.

### 가능한 방안

1. **애플리케이션 서비스가 외부 API를 호출한다.**
   - 예시: `RefundEligibilityPort.check()`의 응답을 `RefundDecision`으로 변환한 뒤 `order.applyRefund(amount, decision)`을 호출한다.
   - 트레이드오프: `Order`가 HTTP와 외부 응답 형식을 모르므로 순수하게 테스트할 수 있다. 반면 판정 이후 주문 상태가 바뀌거나 원격 성공 후 로컬 저장이 실패할 수 있다. 주문 버전 확인, 멱등 키, 재검증이 필요할 수 있다.

2. **도메인 서비스가 도메인 소유 포트를 사용한다.**
   - 예시: `RefundApprovalService`가 `RefundEligibility` 포트와 여러 도메인 객체를 함께 사용해 승인 여부를 결정한다.
   - 트레이드오프: 외부 판정과 여러 객체를 결합한 규칙을 도메인 개념으로 표현할 수 있다. 반면 도메인 서비스가 I/O와 결합되고 비대해질 위험이 있다.

3. **비동기 프로세스와 중간 상태를 도입한다.**
   - 예시: `VALIDATION_PENDING → PG_CANCEL_PENDING → SUCCEEDED` 상태를 저장하고 이벤트로 진행한다.
   - 트레이드오프: 지연과 재시도, 원격 성공 후 로컬 실패를 복구하기 쉽다. 반면 즉시 일관성을 잃고 중복 이벤트와 보상 처리 비용이 생긴다.

### 추천

단순 동기 API라면 1번이다. 외부 판정과 여러 객체를 결합하는 행위 자체가 핵심 도메인 개념이면 2번, 장기 실행과 재시도가 업무의 일부면 3번을 선택한다.

## 5. 기존 인터페이스로 표현할 수 없는 정책

### 내가 한 말

다형성을 사용하면 새로운 환불 정책을 기존 코드 수정이 아니라 새 구현 타입 추가로 처리할 수 있다고 설명했다.

### 들어온 피드백

새 정책이 기존 인터페이스의 입력과 반환 타입으로 표현할 수 없는 완전히 다른 문맥을 요구한다면 어떻게 할지 묻는 가상 질문이다.

### 가능한 방안

1. **결과 의미가 같다면 공통 계약을 진화시킨다.**
   - 예시: 모든 정책이 동일한 `RefundFacts`를 받아 확정된 `RefundQuote`를 반환하고, 반올림 방식만 다르다면 같은 인터페이스를 유지한다.
   - 트레이드오프: 하나의 호출 흐름을 유지할 수 있다. 반면 정책별 입력을 모두 공통 요청에 추가하면 nullable 필드가 쌓인 데이터 자루가 된다.

2. **능력별로 인터페이스를 나눈다.**
   - 예시: 즉시 금액을 계산하는 `ImmediateRefundPolicy`와 외부 승인을 요청하는 `ApprovalRequiredRefundPolicy`를 분리한다.
   - 트레이드오프: 각 계약이 필요한 입력과 결과만 가져 정직해진다. 반면 상위 계층의 라우팅과 공통 처리 중복이 늘어난다.

3. **생명주기까지 다르면 유스케이스를 나눈다.**
   - 예시: 즉시 취소하는 `ImmediateRefundUseCase`와 외부 심사를 기다리는 `PartnerApprovalRefundUseCase`를 분리한다.
   - 트레이드오프: 서로 다른 트랜잭션과 실패 의미를 명확하게 표현한다. 반면 저장, 감사, 라우팅 코드가 중복될 수 있다.

### 추천

모든 정책이 같은 사전 조건과 결과 의미를 가지면 1번이다. 일부 정책군만 같은 계약을 지키면 2번, 결과와 생명주기까지 다르면 3번이다. 기존 인터페이스를 유지하는 것 자체를 목표로 두지는 않는다.

## 한 줄 정리

현재는 작은 구조를 유지하고, 반복 변경·외부 협력·서로 다른 생명주기가 실제로 확인될 때만 다음 단계의 추상화나 경계 분리를 선택하는 것이 적절하다.
