# FB-B6-02 · 불필요한 `of()`를 어떻게 봐야 하는가

제 판단은 분명합니다. 현재 kata 범위에서 `Ticket.of()`는 허용 가능한 준비 작업이 아니라 파이프라인의 실패입니다. 다만 실패의 핵심은 “호출처 0인 메서드를 만들었다” 한 줄보다 깊습니다. Critique가 확인되지 않은 가능성을 제기했고, refine이 그것을 확인된 요구처럼 구현한 것이 본질입니다.

## 알기 쉬운 비유

건물 도면을 검토하던 사람이 “나중에 지하 창고가 생기면 별도 출입문이 필요할 수 있다”고 말했습니다. 다음 작업자는 지하 창고가 실제로 있는지 확인하지 않고 출입문부터 만들었습니다. 완성 검사에서 “이 문은 연결된 공간이 없다”고 발견했지만 건물은 최종 승인됐습니다.

문 자체가 나쁜 것은 아닙니다. 실제 지하 창고가 있고 문이 연결된다면 필요합니다. 문제는 존재하지 않는 요구를 가정해 공개 구조물을 만들고, 실제 연결까지 하지 않은 상태를 완성으로 판정한 것입니다.

## 실행에서 무슨 일이 있었나

```text
1차 Critique
"setter를 없애면 DB 복원 경로가 깨질 수 있다"
                 ↓ 확인 없이 전달
2차 Diagnose
"그러면 Ticket.of()를 먼저 만들자"
                 ↓
Implement
호출처 0인 public Ticket.of() 생성
                 ↓
2차 Critique
"실제 재배선이 없고 호출처가 0이다"
                 ↓
최종 결과
Critique 약점을 포함한 채 PASS
```

1차 Critique의 우려는 일반적인 시스템에서는 가능한 이야기다. ORM이나 persistence adapter가 DB row를 `Ticket`으로 복원한다면 setter를 제거하기 전에 별도 재구성 경로가 필요할 수 있다.

그러나 이 run의 입력에는 저장소 구현이 없었다. baseline repository 전체에서 setter 호출처는 `TicketService`뿐이고, 테스트 저장소는 같은 `Ticket` 객체를 Map에 넣었다가 반환한다. `TicketService`의 setter 호출을 `reserveBy()`로 바꾸면 알려진 호출처는 모두 사라진다.

따라서 “DB 복원 경로가 필요하다”는 것은 확인된 사실이 아니라 입력 밖의 추정이었다.

## 어떤 종류의 실패인가

### 1. 근거 경계 실패

Critique는 “실제 코드에 이런 복원 경로가 있다”가 아니라 “일반적으로 있을 수 있다”는 가능성을 제시했다. 이 가능성을 코드 검색이나 추가 입력으로 확인하지 않고 high 결함으로 올렸다.

모르는 외부 adapter가 있을 가능성은 다음 행동 중 하나를 요구한다.

- repository 전체에서 호출처를 검색한다.
- adapter를 입력 범위에 포함한다.
- 범위 밖 위험이라고 표시하고 사용자에게 확인한다.

미사용 public API를 먼저 추가할 근거가 되지는 않는다.

### 2. 추정의 세탁

1차 Critique의 추정이 `REVISION_FEEDBACK`으로 넘어가자 2차 Diagnose에서는 “저장 상태 복원 통로”라는 확정된 설계 요구가 됐다. 어느 단계에서도 새로운 증거는 추가되지 않았다.

즉 다음 변환이 일어났다.

```text
가능성 → high 지적 → refine 입력 → 구현 요구 → 코드
```

중간 단계를 많이 거쳤지만 근거의 강도는 높아지지 않았다. 이것이 단순 환각보다 위험한 부분이다. 파이프라인의 이전 출력이 다음 단계의 입력이 되면서 추정이 사실처럼 굳어졌다.

### 3. 변경 단위와 완료 조건 실패

Diagnose는 `추가 → 재배선 → 제거` 순서를 제안했지만 실제로는 다음만 수행했다.

- `of()` 추가
- setter 제거
- 저장소 재배선 없음

만약 factory가 정말 필요했다면 실제 adapter 호출처까지 같은 완료 단위에 포함하거나, 중간 migration 상태로 남기고 최종 PASS를 주지 말았어야 한다.

### 4. 탐지와 차단의 분리

2차 Critique는 `of()`가 호출처 0인 과설계임을 정확히 발견했다. 그러나 최종 PASS는 Eval 점수만 보므로 이 발견은 결과를 막지 못했다.

따라서 “파이프라인이 과설계를 잡았다”는 말은 맞지만 “파이프라인이 과설계를 막았다”는 말은 틀리다.

## `of()`가 항상 나쁜가

아니다. 다음 조건이 모두 있다면 정당화될 수 있다.

- 실제 persistence adapter가 존재한다.
- 저장 상태에서 `Ticket`을 복원해야 한다.
- setter 없이 복원할 명시적 생성 경로가 필요하다.
- 같은 변경 또는 확정된 바로 다음 단계에서 adapter가 `of()`를 호출한다.
- 복원된 객체의 불변식을 검증하는 테스트가 있다.

현재 산출물은 이 조건을 만족하지 않는다. 주석으로만 “저장소 복원 통로”라고 설명할 뿐 실제 호출자는 없다.

## 답변 후보

1. **추천 · 현재 범위의 명확한 실패로 인정한다**

   > 저는 `of()` 생성을 파이프라인의 실패라고 봅니다. 정적 팩토리 자체가 나쁜 것이 아니라, 현재 입력에는 저장소 재구성 구현이나 호출처가 없는데 Critique의 가능성만 근거로 public API를 만들었기 때문입니다. repository 기준으로 setter 호출처는 서비스뿐이어서 `reserveBy()`로 대체한 뒤 `of()` 없이 setter를 제거할 수 있었습니다. 더 큰 문제는 다음 Critique가 이를 과설계로 잡았는데도 최종 PASS를 막지 못한 점입니다.

   - 트레이드오프: 현재 근거와 YAGNI에 가장 충실하다. 다만 repository 밖에 실제 persistence adapter가 있다면 적용 전에 그 adapter를 별도로 확인해야 한다.

2. **완료되지 않은 migration 단계로 해석한다**

   > `of()`의 방향 자체는 저장 상태 복원이라는 후속 작업이 확정돼 있었다면 이해할 수 있습니다. 하지만 adapter 재배선 없이 `of()`만 추가한 상태는 완성된 리팩토링이 아니라 중간 migration 상태입니다. 따라서 이 단계에는 PASS가 아니라 다음 단계 필요 상태가 붙어야 했습니다.

   - 트레이드오프: 실제 운영 adapter가 별도 작업으로 존재할 때 단계적 전환을 허용한다. 반면 다음 작업이 보장되지 않으면 미사용 API가 영구히 남으므로 만료 조건과 연속 작업이 필요하다.

3. **범위를 확장해 factory를 실제로 완성한다**

   > setter 제거가 실제 운영 저장소까지 포함한 목표라면 adapter를 입력과 변경 범위에 추가하고, 그 adapter를 `Ticket.of()`로 재배선한 뒤 setter를 제거했어야 합니다.

   - 트레이드오프: 재구성 경로와 캡슐화를 함께 완성한다. 대신 변경 범위와 테스트 부담이 커지며, 작은 리팩토링 단위라는 규율과 충돌할 수 있다.

## 한 문장 결론

`of()` 문제는 미사용 메서드 한 개의 문제가 아니라, **근거 없는 가능성이 critique→refine을 거치며 확정 요구로 바뀌고, 실제 사용처 없이 구현된 뒤, 다시 과설계로 탐지됐는데도 PASS한 문제**다.

현재 kata라면 `of()`와 전용 private constructor를 제거하고 setter 제거는 유지하는 것이 맞다. 외부 persistence adapter가 실제로 있다면 미리 API를 추측할 것이 아니라 그 adapter를 입력에 포함해 함께 판단해야 한다.
