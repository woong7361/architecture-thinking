# 검토 문맥

- 대상: `task2/assignments/taskB-2.md`의 FB-B2-04 후속 논의.
- 원래 task는 하나의 `reserveTicket` 메서드가 사용자 조회, 티켓 조회, 외부 결제, 티켓 상태 변경과 저장을 순차 실행한다.
- 원래 답안은 결제수단을 하나의 역할로 추출해 카드와 포인트를 다형적으로 교체하자고 주장했다.

- 실제 Spring 설정, 데이터베이스 배치, 트랜잭션 관리자, 전파 속성, 외부 카드 API의 멱등성·취소 계약은 제공되지 않았다.
- 성공 기준: `ReservationFlow` 분리가 항상 필요한지 직접 답한다. OOP의 장점과 과도한 다형성의 비용을 구분한다. workflow와 transaction boundary의 관계를 설명한다. 현재 task에 맞는 단계적 추천과 전환 조건을 제시한다.
- 원본 task와 구현 코드는 수정하지 않는다.
