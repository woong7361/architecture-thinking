# Task B-6 피드백 분석

전체 피드백 4건 중 실질 피드백 4건을 분석했다. 리액션·단순 동의로 제외한 항목은 0건이다.

먼저 결론부터 말하면 네 피드백 모두 타당하다. 특히 FB-B6-01은 문구 보완을 넘어 현재 파이프라인의 판정 구조에 실제 허점이 있음을 짚는다. FB-B6-03은 다음 실험 방향으로 가장 구체적이지만, 한 번에 한 기법을 적용하는 것과 함께 성공 결과를 새 기준선으로 승격해 재진단해야 2차 정리 문제까지 풀 수 있다.

## FB-B6-01 · 행위 게이트의 객관성과 LLM 자기평가 순환

**원문 앵커**: 답안 2절 L52–L54 · FB-B6-01

### 내가 주장한 내용

완성도와 규율은 손 리팩토링이 더 낫지만, 파이프라인은 동결된 경계 테스트를 worktree에서 자동 실행하므로 행위 보존 검증 방식은 사람의 수동 확인보다 객관적이고 재현 가능하다고 주장했다. 원문은 전체 설계 품질까지 파이프라인이 더 객관적이라고 명시하지는 않았지만, 같은 문단에서 진단·YAGNI·행위 안전을 함께 비교해 범위가 넓게 읽힐 여지가 있다.

### 피드백이 날아온 내용

피드백은 두 층을 구분하라는 명확화 요구다. 테스트 결과의 객관성은 행위 보존에만 성립하며, 코드가 더 나아졌다는 품질 판정은 LLM Eval에 의존한다. 생성과 평가를 세션으로 분리해도 LLM이 만든 결과를 LLM이 채점하고 그 결과를 다시 Gen 개선에 쓰면 자기평가 순환이 남는다는 지적이다.

실제 구현도 이 우려를 강화한다. `runner.py`는 LLM 축 점수의 합산만 결정적으로 계산하고, 최종 PASS는 Eval 통과만 본다. 실제 최종 산출물은 Eval PASS와 동시에 Critique의 high 행위 위험 및 `of()` 과설계 지적을 포함한다. 즉 현재 `PASS`는 품질이 객관적으로 입증됐다는 뜻으로 쓰기 어렵다.

### 답변·변론 후보

1. **추천 · 지적을 수용하고 판정의 층을 분리한다**: “맞습니다. 객관적이라는 표현은 동결된 6개 시나리오가 확인하는 행위 보존에만 한정해야 합니다. 설계 품질은 LLM 루브릭 기반의 일관성 검사이지 독립적인 객관 판정이 아닙니다. 더구나 현재는 Critique가 high 위험과 과설계를 잡아도 Eval 점수만 넘으면 PASS하므로, 결과를 `behavior=GREEN`, `quality=candidate`, `human review=pending`처럼 나누는 편이 맞습니다.”
   - **트레이드오프**: 주장의 정확성과 결과 해석 가능성을 얻는다. 반면 기존 `PASS` 표현을 낮추고 상태 모델과 게이트 연결을 바꿔야 한다. 현재 실행 로그와 가장 잘 맞는 답이다.

2. **원래 의도를 좁혀 방어한다**: “제가 말한 객관성은 더 좋은 설계라는 판정이 아니라 동일 테스트를 매번 자동 실행한다는 행위 보존 방식에 한정했습니다. Eval 숫자를 Gen에 직접 돌려주지 않고 Critique와 Eval도 분리해 직접적인 점수 맞추기는 줄였습니다. 다만 이것이 공유 모델 편향과 루브릭 과최적화까지 제거하지는 않으므로 Eval은 객관적 증명보다 고정 기준에 따른 보조 검사라고 표현하겠습니다.”
   - **트레이드오프**: 기존 설계의 가치와 의도를 보존하면서 과장을 걷어낸다. 그러나 독립된 정답과 비교하지 않는 한 품질 판정의 순환성 자체는 해결하지 못한다.

3. **외부 기준으로 Eval을 보정한다**: “장기적으로는 사람이 판정한 과거 리팩토링을 동결 캘리브레이션 셋으로 만들고, Gen이나 rubric 변경 전후가 사람 판정과 얼마나 일치하는지 회귀 검증하겠습니다. 모델 또는 세션 분리만으로 독립성을 주장하지 않겠습니다.”
   - **트레이드오프**: 품질 개선을 실제 사람 기준과 연결해 순환을 줄인다. 대신 사람 verdict가 쌓이는 속도에 개선 속도가 묶이고, 작은 데이터셋에서는 일반화가 약하다. `PROBLEM.md`의 열린 문제를 푸는 중장기 답변에 적합하다.

## FB-B6-02 · 호출처가 없는 `of()`를 어떻게 판단할 것인가

**원문 앵커**: 답안 2절 L55–L61 · FB-B6-02

### 내가 주장한 내용

2차 refine에서 호출처가 없는 `Ticket.of()` 팩토리를 만든 것을 Type C 과설계이자 파이프라인의 과교정 사례로 기록했다. 다만 왜 이런 결과가 나왔는지와 작성자 본인의 평가를 충분히 풀지 않았다.

### 피드백이 날아온 내용

반박이라기보다 판단 근거와 개인 의견을 묻는 질문이다. 단순히 “과설계가 있었다”는 관찰을 넘어, 이 실패를 허용 가능한 준비 작업으로 보는지, 제거해야 할 잘못으로 보는지, 파이프라인 설계에서 무엇을 바꿔야 하는지 설명해 달라는 요구다.

현재 근거로는 `source_files`에 저장소 구현이 없고 `of()`의 실제 호출처도 없다. Critique가 “setter를 없애면 저장 상태 복원 경로가 필요할 수 있다”고 가정해 팩토리를 제안했지만, 그 경로를 같은 변경에서 재배선하지 않았다. 따라서 현재 범위에서는 미래 사용처를 미리 만든 실패로 보는 것이 타당하다. 다만 실제 저장소가 setter에 의존한다면 복원 API의 필요성은 별도 확인해야 한다.

### 답변·변론 후보

1. **추천 · 파이프라인 실패로 명확히 평가한다**: “저는 `of()` 생성을 실패라고 봅니다. 동작을 당장 깨지 않더라도 호출처 0인 public API는 현재 리팩토링 목표를 완성하지 않고 미래 변경을 추측해 만든 것입니다. 더 중요한 문제는 Critique가 이를 잡았는데도 파이프라인이 PASS했다는 점입니다. 저장소가 입력 범위 밖이라면 `of()`와 setter 제거를 함께 DEFER했어야 합니다.”
   - **트레이드오프**: YAGNI와 변경 최소성 기준이 명확해지고 현재 근거에 충실하다. 반면 setter 제거라는 목표 달성을 미루며, 실제 영속성 복원 문제는 남는다.

2. **변경 범위를 넓혀 실제 사용처까지 완성한다**: “setter 제거가 이번 목표에서 꼭 필요하다면 저장소 구현을 입력과 변경 범위에 포함하고, `Ticket.of()`로 실제 재배선한 뒤 setter를 제거했어야 합니다. 그 경우 팩토리는 더 이상 호출처 0 과설계가 아닙니다.”
   - **트레이드오프**: 복원 경로와 불변식 캡슐화를 함께 완성한다. 대신 변경 범위와 테스트 부담이 커지고, 원래의 작은 리팩토링 단위를 넘을 수 있다. 실제 저장소 구현을 확인할 수 있을 때 적합하다.

3. **일시적 확장 지점으로 허용한다**: “다음 단계에서 즉시 저장소를 재배선할 계획이 확정돼 있다면 짧은 기간의 준비 변경으로 남길 수 있습니다. 다만 같은 변경 묶음이나 바로 다음 단계에 실제 호출처가 생기지 않으면 실패로 되돌려야 합니다.”
   - **트레이드오프**: 단계적 마이그레이션이 쉬워진다. 반면 ‘곧 쓸 것’이라는 추정이 쉽게 영구 미사용 API가 되므로 만료 조건과 연속된 작업 보장이 필요하다. 현재 과제처럼 호출처 작업이 범위에 없는 경우에는 적합하지 않다.

## FB-B6-03 · 파울러의 작은 리팩토링 리듬을 게이트로 강제하기

**원문 앵커**: 답안 4절 L77–L97 · FB-B6-03

### 내가 주장한 내용

현재 파이프라인은 원본을 한 번 진단하고 여러 기법을 한 매니페스트로 구현하므로, 추출 뒤에 생긴 중복처럼 성공한 리팩토링 이후 나타나는 2차 정리를 잡지 못한다고 분석했다. 해결 후보로 제안과 구현 루프 분리, 또는 Eval 결과에 따라 원본 재시도와 새 baseline 진행을 나누는 방식을 제시했다.

### 피드백이 날아온 내용

피드백은 루프 수를 늘리기 전에 작업 보폭부터 줄이자는 설계 대안이다. 한 번에 파울러 기법 하나만 적용하고, 그 단위를 커밋과 행위 게이트로 강제하면 2차 정리 문제와 큰 변경 단위 문제를 함께 줄일 수 있다는 제안이다.

핵심 방향은 타당하다. 다만 “한 기법 한 단계”만으로 새 냄새가 자동 발견되지는 않는다. 각 단계가 GREEN이면 그 산출물을 새 baseline으로 승격하고, 변경된 코드에 Diagnose를 다시 실행해야 한다. 실제 Git 커밋 대신 되돌릴 수 있는 불변 checkpoint를 써도 리듬의 목적은 유지된다.

### 답변·변론 후보

1. **추천 · 작은 단계와 재진단을 결합한다**: “좋은 지적입니다. 2차 정리 문제는 단일 패스뿐 아니라 한 번에 다섯 기법을 묶은 큰 보폭의 문제이기도 합니다. 다음 실험은 `기법 하나 선택 → 구현 → 행위 게이트 → checkpoint 승격 → 변경된 코드 재진단`으로 바꾸겠습니다. 실패하면 현재 단계만 버리고, 성공하면 다음 진단이 새 중복을 볼 수 있게 하겠습니다.”
   - **트레이드오프**: 실패 위치, 리뷰 단위, 롤백 범위가 작아지고 2차 냄새를 실제로 관찰할 수 있다. 대신 LLM 호출과 테스트 횟수가 늘고, 기법 순서 선택과 종료 조건이 필요하다. 현재 문제를 가장 직접적으로 검증하는 실험이다.

2. **작은 단위만 먼저 도입한다**: “우선 한 매니페스트 한 기법과 단계별 행위 게이트만 강제하고, 재진단 루프는 다음 단계로 미루겠습니다.”
   - **트레이드오프**: 구현이 단순하고 큰 배치의 위험을 빠르게 줄인다. 그러나 변경된 코드를 다시 진단하지 않으므로 원래 고민인 2차 정리 발견은 아직 해결되지 않는다. granularity 효과만 분리해 측정하고 싶을 때 적합하다.

3. **제안 계획을 먼저 수렴시킨 뒤 원자적으로 실행한다**: “전체 의존 순서를 먼저 계획해 `추가 → 재배선 → 제거` 같은 단계 목록을 만들고, 실행은 한 기법씩 게이트하겠습니다.”
   - **트레이드오프**: 순서 의존성이 있는 리팩토링을 안전하게 다룬다. 반면 원본만 보고 만든 계획은 적용 후 새로 생기는 냄새를 예측하지 못하며, 사전 계획 비용이 커진다. 실행 중 재계획 조건을 별도로 둬야 한다.

## FB-B6-04 · Gen 자체의 품질과 내부 검수 강화

**원문 앵커**: 답안 4절 L96–L97 · FB-B6-04

### 내가 주장한 내용

답안은 주로 품질 미달 이후의 refine 분기와 baseline 재승격을 고민했다. Gen이 처음부터 더 작은 범위와 더 정확한 근거를 가진 제안을 내도록 만드는 상류 품질 관리 방법은 구체화하지 않았다.

### 피드백이 날아온 내용

후처리 루프만 늘리지 말고 Gen의 최초 출력 품질과 구현 전 내부 검수를 개선하라는 범위 확장 제안이다. 구체 수단은 제시하지 않았으므로, 답변에서는 검수 목표와 측정 방법을 나눠 제안하는 편이 좋다.

### 답변·변론 후보

1. **추천 · 구현 전 결정적 proposal preflight를 둔다**: “동의합니다. Gen 뒤에 바로 구현하지 않고 먼저 제안 계약을 검사하겠습니다. 각 제안은 현재 코드의 심볼 근거, 실제 호출처, 기법 하나, 변경 범위, 선행 단계, 검증할 관측 행위를 가져야 합니다. 호출처 0인 새 public API나 범위 밖 재배선을 전제로 한 제거는 구현 전에 DEFER합니다.”
   - **트레이드오프**: `of()` 같은 범위 불일치와 큰 변경 묶음을 LLM 재호출 전에 싸게 차단한다. 반면 정적 규칙으로 의미적 타당성을 모두 판정할 수 없고, 규칙이 지나치면 필요한 준비 변경도 막을 수 있다.

2. **Gen과 독립된 제안 Critique를 구현 전에 둔다**: “Diagnose 결과를 별도 세션이 반례 중심으로 검토하고, 누락·과설계·순서 오류를 고친 뒤에만 Implement로 넘기겠습니다.”
   - **트레이드오프**: 코드 생성 전에 잘못된 방향을 고쳐 구현 비용을 줄인다. 그러나 LLM 호출 비용이 늘고 같은 모델 계열이면 자기평가 편향이 남으며, 실제 diff에서만 보이는 문제는 잡지 못한다.

3. **동결 캘리브레이션 셋으로 Gen 변경을 회귀 검증한다**: “사람 verdict가 붙은 과거 코드와 기대 진단을 고정하고, prompt나 규칙 변경 전후에 누락·오진·과설계율이 실제로 나아졌는지 측정하겠습니다.”
   - **트레이드오프**: ‘Gen 품질이 높아졌다’는 주장을 재현 가능한 외부 기준에 연결한다. 대신 데이터 구축 비용이 들고, 캘리브레이션 사례에 과최적화될 수 있어 새로운 사례의 사람 검토도 계속 필요하다.

## 종합 판단

우선순위는 다음이 적절하다.

1. FB-B6-01을 수용해 행위 GREEN과 설계 품질 판정을 분리하고, Critique의 high 위험이 있어도 PASS하는 현재 의미를 바로잡는다.
2. FB-B6-03의 작은 보폭을 채택하되, 각 성공 checkpoint를 새 baseline으로 삼아 재진단한다.
3. FB-B6-04의 proposal preflight를 앞단에 추가하고, 장기적으로는 사람 verdict 기반 캘리브레이션 셋으로 Gen과 Eval을 함께 검증한다.
4. FB-B6-02에는 `of()`를 현재 범위의 실패로 본다는 의견을 분명히 밝히고, 저장소까지 범위를 넓힐지 setter 제거를 미룰지 선택 기준을 제시한다.

이 검토는 현재 저장된 코드와 실행 산출물을 기준으로 한다. 실제 `TicketRepository` 영속성 구현이 별도로 존재하고 setter 복원에 의존하는지는 입력 범위 밖이라 확인이 필요하다.
