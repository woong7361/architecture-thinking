## 확인한 구현과 실험 제약

- `task2/task7-history/code/variance/with-rule-r3/Holding.java`의 `take()`는 보유 수를 숨기고 제한 판단을 객체 내부에 둔다. 다만 `held`는 불변 스냅샷이며 메서드가 값을 갱신하지 않는다.
- `task2/task7-history/code/variance/with-rule-r4/infra/RegisteredMembers.java`는 요청마다 `tickets.countByUserId()`로 `Member` 스냅샷을 복원한다.
- `task2/task7-history/code/B-rule-full/ticket-limit/TicketHolder.java`도 자신을 저장하지 않는 스냅샷임을 명시한다. 순차 요청에서는 티켓 저장 뒤 다음 요청이 새 개수를 읽지만, 같은 스냅샷 재사용이나 동시 요청의 원자성은 이 객체만으로 보장되지 않는다.
- 인수테스트는 `task2/task7-history/harness/net/resources/features/ticket_reservation.feature`의 현재 행위 4개를 검증한다. 내부 책임 배치, 다음 변경 비용, 동시성은 검증하지 않는다.
- 무제약 4회 중 2회와 원칙 적용 4회 중 4회가 도메인 객체 배치를 택했다. 표본 4회로 일반적인 확률 50%를 추정했다고 단정할 수는 없다.
- 약한 규칙과 전량 규칙은 30줄 대 189줄이며 숫자 게이트 외에도 여러 내용이 다르다. 따라서 결과 차이를 형용사 대 숫자라는 단일 원인으로 확정하기 어렵다.
- 파일 수와 코드 줄 수는 변경 비용의 대리 지표다. 리뷰 시간, 생성 재시도 수, 결함률, 토큰과 실행 시간은 측정하지 않았다.
- `PROBLEM.md`에서 Task B-7과 직접 연결된 열린 문제는 찾지 못했다.

## 성공 기준

- 각 실질 피드백을 정확히 한 번 다룬다.
- 원래 주장의 범위와 피드백의 역할을 과장하지 않는다.
- 각 피드백에 실제 댓글로 사용할 수 있는 서로 다른 후보를 2~3개 제시한다.
- 모든 후보에 얻는 것, 비용, 적합 조건을 연결한다.
- 추천은 분석자의 판단임을 표시한다.
- 실험으로 확인된 사실과 해석, 외삽의 한계를 구분한다.
