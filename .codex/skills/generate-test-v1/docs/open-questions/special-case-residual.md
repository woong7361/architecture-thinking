# 열린 질문 — 특수해(명세를 통과하는 틀린 구현)는 정적 명세로 막을 수 있는가

> 상태: **열림(토론 중)**. rules 모드에 삼각측량→불변식→반례를 쌓은 뒤에도 남는 잔여 특수해에 대한 기록.
> 자매 문서: [unit-test-lock-in.md](unit-test-lock-in.md) · [feature-altitude-coupling.md](feature-altitude-coupling.md).
> 관련 구현: gen_rules(∀ 불변식) · rules.rubric(`invariant_generality` 축, coverage 구현-반례 캡) · critique_rules(반례 도전).

## 질문

받은 피드백:
> *"삼각측량도 같은 방식으로 깨질 수 있어요. 예제가 둘이면 AI는 if 분기 두 개로 그 둘만 통과시킬 수 있죠.
> 일반화를 강제하는 건 예제의 개수일까요, 아니면 다른 무엇일까요? … '어떤 입력이든 환불액은 결제액을
> 넘지 않는다'처럼 속성 자체를 단언하는 property-based testing이요. 삼각측량이 못 막는 특수해를 이
> 방식은 막을 수 있을까요? 못 막는 특수해도 여전히 남을까요?"*

**특수해 = 명세(예시표·불변식)를 전부 통과하면서도 정책 의도와 다른 구현.** 이걸 유한한 정적 명세로
완전히 배제할 수 있는가가 이 문서의 질문이다.

## 지금까지 쌓은 층 — 하나의 특수해로 따라가기

규칙: `경과일 ≤ 7 → 전액, ≥ 8 → 반액`. 특수해 하나를 각 층에 통과시켜 본다.

```
특수해: refund(p, d) = if d==3: 10000; if d==8: 5000; else 0

① 삼각측량 (안/밖 짝 예시표)         → 통과   표 두 줄(d=3,8)을 그대로 외움
② ∀ 불변식  0 ≤ 환불액 ≤ 결제액       → 통과   0 ≤ 0 ≤ p 를 만족(else 0이라도)
③ 반례 찾기  d=5 → 환불액=결제액       → 탈락   구간 값을 못박는 행/불변식이 강제됨
④ 잔여      ①②③ 다 통과하는 절사 off-by-one → 정적으론 못 잡음
```

층별로 **무엇을 막고 무엇이 새는가**:

| 층 | 구현 위치 | 막는 것 | 새는 것(다음 층이 담당) |
|---|---|---|---|
| 삼각측량 | `gen_rules`(안/밖 짝) | 경계의 **정확한 값** 고정 | 그 점만 외운 lookup 특수해 |
| ∀ property | `gen_rules`(불변식) + `invariant_generality` 축 | 무한 입력의 **위반 클래스**(예: 초과 환불) | property-만족-but-틀린 구현(항상 0) |
| 반례 | `critique_rules` 반례 도전(생성) + rules.rubric coverage **구현-반례 캡**(게이트) | property-만족-but-틀린 구현을 **능동 사냥** → 행/불변식 강제 | 정책도 비평자도 예상 못 한 틀림 |
| 잔여 | — | — | 셋 다 통과하는 틀린 구현 |

**교훈:** ①→② = *일반화를 강제하는 건 예제의 개수가 아니라 전칭 명제(∀)*. 개수는 특수해의 비용만
올린다. ②→③ = property는 *틀린 답의 공간을 좁힐 뿐 한 점으로 고정하지 못한다*("항상 0"이 통과) →
반례가 그 구멍을 능동으로 찌른다. 그래도 ④가 남는다.

## 검토 — 결국 특수해는 못 막는가

**일반적으로 정적·유한 명세로는 못 막는다. 이건 도구 결함이 아니라 이론적 한계다.** 유한한 예시(점
유한개) + 유한한 property(입력공간 위 술어 유한개)를 만족하는 함수는 무한히 많고, 그중엔 틀린 함수도
있다. 명세가 함수를 *유일하게 결정*하지 않는 한 특수해는 존재한다. 다만 세 갈래로 갈린다:

1. **등식형 ∀ = 잔여 0.** property가 *경계(bound `r ≤ k`)* 가 아니라 *등식(`r = 산식`)* 이면 그
   규칙의 잔여는 0이 된다 — ∀가 곧 함수 정의라서 특수해가 존재할 수 없다. rules의 **계산 규칙은 이미
   `산식 + 재검산 witness` 형태**라 사실상 이 등식형이고, 그래서 **계산 규칙의 잔여는 닫혀 있다.**
   남는 건 등식으로 못 적는 **순수 관계 불변식**(`0 ≤ r ≤ k` 류)뿐이고, 여기엔 잔여가 필연이다.
2. **필연 잔여의 처리 = test-time으로 이월.** 순수 관계 불변식의 잔여는 삼각측량(값 고정) + 반례(구멍
   사냥)로 얇게 만들고, 마지막 얇은 층은 **test-time PBT(무작위 생성 + shrink)** 로 넘긴다. 그리고
   **그 PBT의 property는 명세에 써둔 ∀ 그대로**다 — 앞 층이 뒷 층의 재료를 만든다. PBT도 표본이라
   완전하진 않고, 완전 폐쇄는 형식검증인데 그건 *완전한 명세*를 요구 → 같은 문제가 재귀한다.
3. **재프레이밍 = 제거가 아니라 비용.** 목표는 애초에 "특수해 제거"(정적 유한 명세로는 불가능)가
   아니라 **"명세를 통과하는 틀린 구현의 비용을, 정직하게 올바로 구현하는 비용보다 높이는 것"**이다.
   게이밍이 정직 구현보다 비싸지면 특수해는 *존재하더라도 최소 저항 경로가 아니게* 되어 실무에서
   패배한다. 4층(삼각측량·∀·반례·캡)은 정확히 그 비용을 올린다.

**잠정 답:** 특수해는 원리상 못 막는다. 대신 (a) 등식형 ∀로 계산 규칙의 잔여를 0으로 닫고, (b) 순수
관계 불변식의 필연 잔여는 얇게 만들어 test-time PBT로 이월하며, (c) "게이밍 비용 > 정직 비용"을 만들어
실무적으로 무력화한다.

**정정(2026-07-21 후속 검토) — "규칙 종류가 열린다"는 틀렸다.** 위에서 "순수 관계 불변식엔 잔여가
필연"이라 했으나, 후속 검토에서 반례가 계속 무너졌다:
- **외부입력(MANUAL):** 지정값도 입력이므로 `출력 = 입력` 등식으로 닫힌다. "열림"은 명세가 그 등식을
  안 쓴 spec gap이었다.
- **다치(정답 여럿):** 정답 기준이 '집합 소속'이면 `출력 ∈ 집합` 멤버십이 완전한 명세라 닫힌다. "항상 1번
  좌석"은 그 명세상 정답이지 특수해가 아니다 — 열려 보이는 건 '공정 분배' 같은 **미명시 의도**가 있을 때뿐이고,
  그건 property 하나 더 붙이면 되는 또 다른 spec gap이다.
- **순수 관계 불변식(`r ≤ k`):** 값 `r`은 발동 정책의 등식으로 이미 닫혀 있고, `r ≤ k`는 교차 안전 불변식
  (cross-check)이지 값을 미결정으로 남기는 게 아니다.

→ **결론 갱신: 어떤 규칙 '종류'도 본질적으로 열려 있지 않다. 모든 '열림'은 아직 안 쓴 명세(spec gap)다.**

**재정정(2번째 후속) — "두 벽"도 부정확했다. 진짜 축은 관찰가능성(observability)이다.** 위에서 진짜 벽을
"(1) 형식화 못 하는 의도, (2) 진짜 무작위"라 했으나 둘 다 무너진다: **무작위**는 정답 기준이 곧 분포
property라 표본으로 닫히고(`return 42`는 균등성 위반으로 걸림), **불형식화 의도**는 spec gap이거나(예시로
근사) 질문이 성립 안 하는 것(틀림의 기준 부재)이라 깔끔한 벽이 아니다. 관통하는 진짜 기준:
> **특수해는 "관찰상 구별 불가능한 두 구현이 정답 여부에선 다를 때"만 살아남는다.**
그래서 닫히느냐는 규칙 종류가 아니라 **정답 기준이 어떤 관찰 채널에 드러나느냐**다:
- 입출력으로 결정 → 완전한 행동 명세로 닫힘(함수형·MANUAL·다치).
- 입출력엔 없지만 다른 채널로 관찰 → 그 채널을 재면 닫힘: 성능 O(n²)은 **시간 측정**, 타이밍 side-channel은
  **타이밍 분포**, Dual_EC 백도어는 **설계·상수 검토(white-box)** 로 잡힘(단 비기능 요구를 명시해야 "틀림"이 됨).
- **어떤 관찰로도 안 드러남 → 진짜 못 닫음.** 유일한 절대 벽: **암호학적으로 검출 불가능한 적대적 백도어**
  (Goldwasser et al., FOCS 2022 — white-box로도 계산적으로 검출 불가). 악의적 구현자 + 무거운 암호가 필요한 극단.

즉 비적대적 개발에선 **"잔여 = 아직 안 잰 관찰 채널"** 이고 채널을 늘리면 계속 닫힌다. "게이밍 비용 > 정직
비용" 재프레이밍은 여전히 유효 — 목표는 완전 폐쇄가 아니라 필요한 관찰 채널만큼 spec gap을 싸게 메우는 것.

## 후보 방향 (아직 결정 아님)

> **실제 run + 후속 검토가 처방을 바꾼다(2026-07-21):** 생성된 환불 명세를 분류하니 규칙 10개 중 9개
> (함수형)가 이미 등식으로 닫혔다. MANUAL은 처음 '열림'으로 봤으나 **오판** — 지정값도 입력이라
> `출력 = 입력` 등식으로 닫힌다(명세가 그 등식을 빠뜨린 spec gap이었을 뿐). 나아가 **다치조차 정답 기준이
> '집합 소속'이면 `출력 ∈ 집합` 멤버십으로 닫힌다.** 결론: **어떤 규칙 '종류'도 본질적으로 열려 있지 않다 —
> 모든 '열림'은 아직 안 쓴 명세(spec gap)다.** 진짜 못 닫는 건 (1) 형식화 못 하는 의도(spec↔intent 간극),
> (2) 진짜 무작위(표본·통계로만 닫힘, per-call 불가) 둘뿐. 그래서 처방은 **"닫을 수 있는 건(대부분) 정적으로
> 닫고 — 반례 층이 spec gap을 메우게 —, 미명시 의도·무작위 규칙만 골라 test-time으로"** 다.

- **D1. test-time PBT 연결.** 명세의 ∀ 불변식을 그대로 실행 가능한 property로 내보내는 어댑터(사람의
  구현 단계에서 jqwik/Hypothesis 등에 바인딩). 스킬은 명세만 내지만 "이 ∀는 PBT property다"를 기계가
  읽을 형태로 표시. → 필연 잔여를 실제로 얇게 만드는지 실측.
- **D2. 반례 캡의 수렴/환각 튜닝.** eval 구현-반례 캡이 (i) 환각 반례로 영원히 REJECT하지 않는지,
  (ii) 반례가 많은 도메인에서 max_iter 안에 수렴하는지 실측. 필요하면 "정책 명시 위반"의 판정을 더
  결정적으로(정책 인용 필수 필드 등).
- **D3. 등식형 ∀ 유도 — 전면이 아니라 좁은 체크로.** 실제 run에서 함수형 규칙은 이미 등식으로 나왔다.
  그러니 D3의 일은 "모두 등식화"가 아니라 **"등식으로 적을 수 있는데 bound로만 적은 규칙을 잡아 등식으로
  올리는"** 좁은 감점 규칙이다(`invariant_generality`가 그런 규칙에만 캡). 잔여 0 영역을 놓치지 않기 위함.
- **D4. critique↔eval 반례 정합.** 두 스테이지가 서로 다른 반례를 잡을 때 refine에서만 만나는 현재
  구조를 유지할지, 아니면 반례를 구조화 필드로 승격해 정합을 앞당길지.
- **D5. 규칙 종류 분류·표시(신규, 실제 run이 촉발).** 각 규칙을 **함수형(정적 닫힘 가능) vs 관계·외부입력·
  다치(정적으론 불가, test-time 필요)** 로 분류해 명세에 표시한다. 그러면 (a) 어느 규칙이 등식으로 정적
  검증 완료이고 어느 게 실행 검증 대상인지 명확해지고, (b) D1(PBT)을 **열린 규칙에만** 집중시킬 수 있고,
  (c) 함수형인데 bound로 적힌 규칙(D3 대상)을 자동으로 드러낸다. 열린 규칙엔 "출력을 외부값/관계에 묶는
  test-time 의무"를 함께 남긴다(예: MANUAL은 '지정값 X를 넣으면 출력이 X' 예시/property).

## 트레이드오프 / 남은 리스크

- **반례 캡(현행)의 수렴 리스크:** eval이 반례를 지어내면(환각) 영원히 REJECT → max_iter 소진. "정책
  원문에 명시된 위반만"으로 묶었으나, 이 경계 판단 자체가 LLM 주관이라 완충이 완전치 않다.
- **critique↔eval 커플링:** 반례를 *찾는 것*(critique)과 *고치게 만드는 것*(eval REJECT→refine)이
  분리돼, eval이 놓치면 critique 반례가 기록만 되고 안 쓰인다(실제 run에서 관측 → coverage 캡으로 보완).
- **test-time PBT는 이 스킬 밖**(사람의 사이클). 스킬은 명세만 내고 실행 안 함 — 다만 ∀로 재료를 댄다.
- 함께 드러난 하네스 잔여: claude provider 무재시도(일회성 파싱 실패가 run을 죽임), gen 자리표시자 글리치.

  **다음: D5로 규칙을 분류한 뒤 D1(PBT)을 열린 규칙에 적용, D2(반례 캡 튜닝) 병행 실측.** rules 실증 쌓이면 closed 이관.
- (2026-07-21) **정정 — "규칙 종류가 열린다"는 오판.** MANUAL(외부입력)은 `출력=입력` 등식으로, 다치는
  `출력∈집합` 멤버십으로 닫힌다. 지금까지의 모든 '열림'은 규칙 종류의 벽이 아니라 **spec gap**(안 쓴 명세)이었다.
  진짜 벽은 (1) 형식화 못 하는 의도, (2) 진짜 무작위(통계로만 닫힘) 둘뿐. → D5는 "함수형/관계/외부/다치"가
  아니라 **"정적으로 닫힘(등식·멤버십) / 미명시 의도·무작위라 실행 검증 필요"** 로 분류하도록 재정의.
- (2026-07-22) **재정정 — "두 벽"도 부정확, 진짜 축은 관찰가능성.** 무작위는 분포 명세로 닫히고 불형식화
  의도는 spec gap/질문불성립이라 벽이 아니다. 특수해는 **관찰상 구별 불가능한데 정답이 다를 때만** 생존 →
  닫힘은 규칙 종류가 아니라 **정답 기준이 어느 관찰 채널(입출력→시간·타이밍·메모리→white-box 설계검토)에
  드러나느냐**. 유일한 절대 벽 = **암호학적 검출불가 백도어**(Goldwasser 2022). 비적대적 개발에선 "잔여 =

  한 수단으로 위치.
