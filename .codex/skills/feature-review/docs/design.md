# feature-review 설계

> 상태: 설계 초안. 구현 전이다. 15절의 열린 결정이 닫히면 구현을 시작한다.
> 이 문서는 설계 기록으로 이 저장소에 둔다. skill 본체는 11.1절대로 사용자 전역 위치에 설치한다.

## 1. 목적

이 skill은 새로 추가된 기능이 기획한 대로 동작하는지 판정하고, 그 과정에서 결함, 보안 위험, 설계 개선점을 함께 찾아 리포트 하나로 낸다. 일반적인 코드 리뷰는 코드가 안전한지를 묻는다. 이 skill은 여기에 코드가 요청자가 원한 동작을 하는지, 그리고 요청자가 정하지 않은 동작을 코드가 스스로 정하지는 않았는지를 더 묻는다.

판정 기준은 기획서가 있으면 기획서다. 기획서가 없으면 사용자가 intake에서 말한 기능 설명, 커밋 기록 같은 코드 밖의 흔적, 기존 코드 관례에서 기준을 모은다. 기준이 약할수록 코드가 근거 없이 정한 동작이 많아진다. 그래서 이 skill은 추가된 기능이 지금 어떻게 동작하는지를 기획서 형식으로 정리한 동작 명세를 리포트에 싣고, 요청자에게 그 동작이 의도와 맞는지 확인을 요청한다. 기획서가 없으면 이 동작 명세가 기획 리뷰의 중심 결과물이 된다.

## 2. 배경

위험만 보는 리뷰로는 기획과 어긋난 구현을 잡지 못한다. 이 판단은 이전 작업에서 관찰한 실패 세 가지에 근거한다.

첫째, 명세가 비어 있는 자리는 구현자가 가정으로 채우고, 그 가정은 테스트를 통과한다. 한 과제에서 자동 게이트 4단과 인수테스트 21개가 모두 통과했지만 결과가 틀렸다. 명세에 엔드포인트와 승인 판정 기준이 없었고, 생성기가 그 자리를 그럴듯한 가정으로 채웠기 때문이다. 테스트도 같은 가정 위에서 쓰였으니 틀린 것을 잡을 수 없었다. 이 skill이 코드에서 명세로 거꾸로 추적하는 단계를 두는 이유다.

둘째, LLM이 매긴 점수는 판정 근거로 믿기 어렵다. 근거 없는 문장이 네 건 있는 초안이 그런 문장이 없는 초안보다 높은 점수를 받은 사례가 있었다. 그래서 이 skill은 점수를 매기지 않는다. 대신 항목마다 코드 위치와 근거를 붙이고, 그 근거가 실제 코드와 맞는지를 결정적으로 검사한다.

셋째, 같은 세션에서 AI가 자기 결과를 평가하면 맥락 편향이 생긴다. 그래서 검증은 분석과 맥락을 공유하지 않는 새 세션에서 한다.

## 3. 범위

이 skill은 구현이 끝난 코드를 리뷰한다. 네 관점에서 결과를 내며, 관점별 내용은 7절에 있다.

- 기획 정합성
- 결함과 에러 위험
- 보안 위험
- 설계 개선 제안

다음은 이번 범위에 넣지 않는다.

- 구현 전에 기획의 빈자리를 채우는 일. 질문을 만드는 로직은 같지만 입력과 출력이 다르다. 15절에 열린 문제로 남긴다.
- 코드를 직접 고치는 일. 이 skill은 리포트만 낸다.
- 테스트 실행. 기존 테스트가 무엇을 검증하는지는 읽어서 판단하지만, 빌드와 실행은 하지 않는다.

## 4. 전체 흐름

사람과 주고받는 단계는 intake 하나뿐이고, 그 뒤는 runner가 사람 개입 없이 끝까지 실행한다. intake를 skill에 두고 나머지를 스크립트로 분리한 이유는 두 가지다. subprocess로 실행되는 단계는 사용자와 대화할 수 없고, 사용자와 대화하지 않는 단계는 코드로 순서를 고정해야 매번 같은 절차로 돈다.

```
[skill] intake ─ 리뷰할 기능을 자연어로 넓게 받는다. 전부 선택
   │  python runner.py [--feature "..."] [--spec ...] [--decisions ...]
[runner]  작업 디렉터리 = skill을 호출한 워크스페이스
 준비 1. 수집 ─ git 기록과 변경분을 스크립트로 모은다
 준비 2. 기능 범위 확정 ─ 이번에 추가된 기능과 그 코드를 LLM이 찾는다
 준비 3. 판정 기준 확정 ─ 기준마다 출처와 강도를 붙인다
   │
   ├─ 1. 기획 관점 → 결정적 검사 → LLM 검증 ─┐
   ├─ 2. 에러 관점 → 결정적 검사 → LLM 검증 ─┤ 관점마다 따로 진행
   ├─ 3. 보안 관점 → 결정적 검사 → LLM 검증 ─┤
   └─ 4. 설계 관점 → 결정적 검사 → LLM 검증 ─┘
   │
 5. 병합
 6. 리포트 작성
```

네 관점은 서로의 결과를 읽지 않으므로 병렬로 실행한다. 한 관점이 끝나면 다른 관점을 기다리지 않고 바로 그 관점의 검증을 시작한다. 병합은 네 관점의 검증이 모두 끝난 뒤에 한다.

## 5. intake

intake는 사용자에게서 "어떤 기능을 리뷰할지"를 넓게 받는 일만 한다. 사용자는 "알림 신청 기능 리뷰해줘"처럼 말하면 되고, 파일 목록이나 커밋 범위를 줄 필요는 없다. 그 설명을 실제 코드 범위로 바꾸는 일은 runner가 6.2절에서 한다.

| 항목 | 필수 | 설명 |
|---|---|---|
| 리뷰할 기능 | 선택 | 자연어로 받는다. 기능 이름만이어도 되고, 그 기능이 무엇을 해야 하는지까지 말했다면 그 부분은 명시된 판정 기준으로 쓴다. 없으면 최근 추가된 기능을 리뷰한다. |
| 기획서 경로 | 선택 | 있으면 받는다. 여러 개일 수 있고 형식은 제한하지 않는다. |
| 이전 결정 파일 | 선택 | 이전 리뷰의 확인사항에 답한 파일. 10절 참조 |
| provider | 선택 | 기본값인 Claude가 아닌 provider로 실행할 때만 받는다. 11.3절 참조 |

intake는 사용자에게 한 번만 묻고, 사용자가 준 것만 runner에 넘긴다. 아무것도 주지 않아도 리뷰는 진행한다. 다만 판정 기준이 약해지므로 기획 위반 대신 확인사항이 늘어나고, 이 사실을 리포트 첫머리에 밝힌다.

## 6. 준비 단계

### 6.1 수집

수집은 LLM 없이 스크립트가 한다. 같은 저장소 상태에서는 항상 같은 결과가 나와야 하는 작업이기 때문이다.

- git 저장소 최상위 경로, 현재 브랜치, 기본 브랜치
- 커밋하지 않은 변경분과 그 파일 목록
- 작업 단위 후보 목록. 6.2절이 이 후보 중에서 리뷰할 작업 단위를 고른다.
  - 커밋하지 않은 변경 전체
  - 병합 커밋마다, 그 병합으로 들어온 브랜치 이름과 커밋 목록, 커밋별 변경 파일
  - 병합되지 않은 최근 커밋마다, 메시지와 변경 파일
- 사용자가 준 기획서와 이전 결정 파일의 내용

작업 단위 후보는 현재 브랜치가 기본 브랜치에 이미 병합되었는지와 관계없이 최근 기록에서 만든다. 기본 브랜치에서 갈라진 뒤의 커밋만 보면, 이미 병합된 브랜치에서는 목록이 비어 범위를 정할 재료가 사라진다.

git 저장소가 아니면 변경 기록을 쓸 수 없으므로, 리뷰할 기능 설명만으로 범위를 찾는다.

### 6.2 기능 범위 확정

리뷰 범위는 기능 단위이고, 대상은 이번에 추가된 기능이다. 이전부터 있던 코드는 리뷰 대상이 아니다. 새로 추가된 기능이 요청대로 동작하는지를 보는 것이 이 skill의 목적이기 때문이다.

범위는 git 기록의 작업 단위로 정한다. 작업 단위는 한 번에 함께 만들어진 변경의 묶음이다. 병합된 브랜치 하나, 커밋하지 않은 현재 작업, 또는 이어진 커밋 몇 개가 작업 단위가 된다. LLM은 6.1의 작업 단위 후보 중 intake의 기능 설명에 맞는 것을 고르고, 기능 설명이 없으면 가장 최근의 작업 단위를 고른다. 고른 작업 단위와 같은 파일이나 같은 저장 구조를 건드리는 커밋하지 않은 변경은 함께 포함한다.

리뷰 대상 파일은 고른 작업 단위가 바꾼 파일 전체다. 기능 설명은 어느 작업 단위를 고를지 정하는 데만 쓰고, 작업 단위 안에서 파일을 덜어내는 데는 쓰지 않는다. 코드 호출 관계로 "독립적"이라고 판단해 덜어내면, 같은 결과를 만드는 데이터 흐름의 다른 부분이 빠진다. 설정 파일이나 무관한 파일처럼 기능과 관계없는 파일은 뺄 수 있지만, 뺀 파일과 이유를 기록한다.

> 예시. 한 병합에 이벤트 수집 API, 그 이벤트를 묶는 여정 기록, 집계 배치, 관리자 통계 조회가 함께 들어왔다면 네 가지 모두 리뷰 대상이다. 수집 API를 지워도 집계 배치 코드가 남는다는 이유로 집계를 빼지 않는다.

추가된 기능이 이전부터 있던 코드를 호출하거나 그 위에 얹혀 있으면, 이전 코드도 읽는다. 다만 그 목적은 추가된 기능의 동작을 이해하고 기존 관례를 파악하는 데 있다. 이전 코드 자체의 결함은 올리지 않는다. 예외는 이전 코드의 동작 때문에 추가된 기능이 요청대로 동작하지 않는 경우다. 이 경우는 추가된 기능의 결함으로 올리고, 원인 위치로 이전 코드를 적는다.

범위 확정은 틀릴 수 있다. 고른 작업 단위와 그렇게 판단한 근거를 리포트 첫머리에 짧게 적어서 사용자가 바로 알아볼 수 있게 한다. runner는 사람 개입 없이 끝까지 가므로, 확신이 낮을 때도 멈추지 않고 가장 가능성이 높은 범위로 진행한 뒤 이 사실을 리포트에 밝힌다.

### 6.3 판정 기준 확정

판정 기준은 출처에 따라 강도가 다르고, 어긴 기준의 강도에 따라 판정이 달라진다.

| 강도 | 출처 | 이 기준을 어긴 코드 |
|---|---|---|
| 명시 | 기획서, intake에서 사용자가 말한 기능 설명, 이전 결정 파일 | 기획 위반 |
| 추정 | 커밋 메시지, 브랜치 이름, 저장소 안의 관련 문서 | 기획 확인사항. 추정한 의도와 다르다고 적는다. |
| 관례 | 기존 코드가 같은 문제를 처리하는 방식 | 관례와 다르게 한 이유가 보이지 않으면 확인사항 |

추정 기준을 어긴 코드를 기획 위반으로 판정하지 않는 이유는 추정이 틀렸을 수 있어서다. 커밋 메시지도 구현자가 쓰므로, 구현자의 가정이 그대로 담겨 있을 수 있다.

리뷰 대상 코드 자체에서 의도를 추정하지는 않는다. 코드를 보고 "이 코드는 이렇게 하려는 것"이라고 추정하면 그 추정은 항상 코드와 일치하고, 모든 요구사항이 `구현됨`으로 판정된다. 2절에서 본, 가정으로 채운 자리가 통과하는 실패가 리뷰 안에서 다시 일어나는 것이다. 테스트 코드도 같은 이유로 의도의 출처로 쓰지 않고, 구현이 무엇을 검증하는지 보여 주는 증거로만 쓴다.

기획서 형식은 제한하지 않는다. 요구사항 표, API 스키마, 인수테스트 시나리오처럼 형식이 달라도 공통 형식인 "요구사항 문장 목록"으로 바꾸고, 문장마다 출처와 강도를 붙인다.

### 6.4 관점에 넘기는 입력

네 관점은 6.2절의 범위 결과와 6.3절의 판정 기준을 받아 코드를 직접 읽는다. 범위 결과에는 작업 단위, 대상 파일 전체, 진입점, 저장 구조가 들어 있다. 네 관점이 같은 범위 결과를 받으므로 서로 다른 범위를 보지 않는다. 관점 사이에 코드 요약을 따로 만들어 넘기지 않는 이유는 14절에 있다.

## 7. 네 관점

각 관점은 6.4절의 입력을 받아 대상 코드를 직접 읽고 결과 항목 목록을 낸다. 항목의 공통 형식은 13절에 있다.

### 7.1 기획 관점

기획 관점은 요구사항과 코드를 양방향으로 추적한다.

요구사항에서 코드로 갈 때는 요구사항 문장마다 `구현됨`, `어긋남`, `없음`, `명세가 모호함` 중 하나로 판정하고 코드 위치를 붙인다. `구현됨`으로 판정한 문장은 그 동작이 깨졌을 때 실패할 테스트가 있는지도 확인하고, 없으면 `미검증`으로 표시한다.

코드에서 요구사항으로 갈 때는 대상 코드에서 코드가 내린 결정을 직접 찾는다. 분기 조건, 기본값, 실패 처리, 중복·재시도 처리, 상태 전이 규칙, 저장 구조의 제약이 결정에 해당하고, 조건이 다르면 따로 센다. 결정마다 근거를 찾아 출처를 붙인다.

- `요구사항`: 6.3절의 요구사항 문장 목록에 근거가 있는 결정. 근거 문장의 강도가 추정이면 확인사항 판정에 그 사실을 함께 적는다.
- `관례`: 기존 코드가 이미 같은 방식으로 하고 있는 결정
- `코드가 정함`: 위 두 가지 어디에도 근거가 없는 결정

`어긋남`과 `없음`은 기획 위반으로, `코드가 정함`과 `명세가 모호함`은 기획 확인사항으로 올린다. `코드가 정함`이라도 모두 올리지는 않는다. 사용자에게 보이는 동작이 달라지거나, 되돌리기 어렵거나, 데이터나 금전이 걸린 결정만 대안과 함께 확인사항으로 올린다. 나머지는 아래의 동작 명세에서 확인 대상으로 보여 준다.

> 예시. 기능 설명이 "같은 조건의 신청은 하나만 유지한다"뿐인데 코드가 두 번째 신청을 에러로 거절한다면, 이는 `코드가 정함`이다. 기존 신청을 그대로 돌려주는 방식도 요청을 만족하기 때문이다. 요청자가 보는 동작이 달라지므로 확인사항으로 올린다.

#### 동작 명세

기획 관점은 결과 항목과 별도로 동작 명세를 낸다. 동작 명세는 추가된 기능이 지금 어떻게 동작하는지를 기획서 형식으로 다시 쓴 것이다. 기획서가 없는 기능은 코드가 곧 기획이므로, 코드에 들어 있는 기획 사항을 요청자가 읽을 수 있는 문장으로 꺼내 "이렇게 되어 있는데 의도와 맞는가"를 확인받는 것이 기획 리뷰의 실체가 된다.

동작 명세의 문장은 "조건 → 현재 동작" 형식이고, 문장마다 코드 위치와 근거 출처를 붙인다. 근거 출처는 6.3절의 명시, 추정, 관례에 `코드가 정함`을 더한 네 가지다. 문장은 기능 흐름에 따라 묶는다.

- 정상 흐름: 기능이 성공할 때 무엇을 받고 무엇을 돌려주며 무엇이 바뀌는가
- 입력 검증과 거절: 어떤 입력을 어떤 응답으로 거절하는가
- 실패와 재시도: 저장소나 외부 시스템이 실패하면 어떻게 되는가
- 중복과 동시 요청: 같은 요청이 두 번 오거나 동시에 오면 어떻게 되는가
- 상태와 전이: 어떤 상태가 있고, 어떤 조건에서 바뀌며, 되돌아갈 수 있는가
- 경계값과 기본값: 한도, 기간, 기본 설정이 어떻게 정해져 있는가

문장에는 호출하는 쪽에서 관찰할 수 있는 동작만 쓴다. 호출하는 쪽은 사용자일 수도, 다른 시스템일 수도 있다. 관찰할 수 있는 동작은 입력, 출력, 상태 변화, 외부로 나가는 부수 효과를 말한다. 내부 구현 방식까지 쓰면 명세가 길어지고, 요청자가 확인해야 할 결정이 그 안에 묻힌다.

동작 명세는 6.3절의 "코드에서 의도를 추정하지 않는다"는 규칙과 부딪히지 않는다. 동작 명세는 코드가 무엇을 하는지만 적고, 그것이 의도인지는 요청자가 판단한다.

기획서가 있으면 명시 기준으로 덮인 문장은 "기획서와 일치"로 접어서 짧게 보여 주고, 기획서가 다루지 않는 문장만 펼쳐서 확인 대상으로 둔다. 기획서가 없으면 모든 문장이 확인 대상이다.

### 7.2 에러 관점

에러 관점은 코드가 의도한 동작을 하지 못하는 경로를 찾는다. 직접 드러나는 예외와 잘못된 값뿐 아니라 동시 실행, 부분 실패, 재시도, 외부 시스템 지연처럼 특정 조건에서만 드러나는 간접 위험도 포함한다. 항목마다 그 경로에 도달하는 조건을 적는다. 조건을 적을 수 없는 항목은 올리지 않는다.

### 7.3 보안 관점

보안 관점은 외부 입력이 닿는 경로를 범위 결과의 진입점에서 출발해 따라간다. 인증과 인가 누락, 입력 검증 누락, 민감 정보 노출, 다른 사용자의 자원 접근을 본다. 항목마다 공격자가 어떤 입력을 제어해야 하는지를 적는다.

### 7.4 설계 관점

설계 관점은 SOLID 위반, code smell, 아키텍처 경계 위반을 찾아 개선을 제안한다. 이 관점의 결과는 결함이 아니라 제안이므로, 리포트에서 결함 뒤에 따로 둔다.

설계 제안은 변경 축을 근거로 댈 수 있을 때만 올린다. 변경 축은 실제로 바뀔 가능성이 있는 요구나 구현 방식을 말한다. 추상화를 제안하면서 변경 축을 댈 수 없으면 과설계로 보고 올리지 않는다. 기존 코드베이스의 관례와 부딪히는 제안도 올리지 않는다. 개수에는 상한을 둔다. 상한이 없으면 리포트가 제안으로 가득 차서 결함이 그 사이에 묻히기 때문이다.

## 8. 검증

검증은 병합 전에 관점마다 한다. 병합한 뒤에 검증하면 어느 관점이 어떤 기준으로 올린 항목인지 흐려지고, 오탐이 중복 제거 과정에서 다른 항목과 섞인다. 검증은 두 층으로 나눈다.

### 8.1 결정적 검사

첫 층은 `validate.py`가 LLM 없이 한다. 다음 중 하나라도 실패하면 그 항목을 기각하고 사유를 기록한다.

- 결과 JSON이 스키마에 맞는가
- 근거 위치가 하나인가. 항목 하나는 원인이 되는 코드 한 곳만 인용한다. 문제가 여러 곳에 걸치면 항목을 나누고 `관련 항목`으로 잇는다. 한 곳의 인용이 틀려도 다른 항목까지 함께 버려지지 않게 하기 위해서다.
- 인용한 파일과 줄 번호가 실제로 있는가
- 인용한 코드 조각이 그 위치의 실제 내용과 일치하는가. 공백 차이는 무시한다.
- 분류별 필수 필드가 채워졌는가. 결함에는 도달 조건, 기획 위반에는 어긴 요구사항, 확인사항에는 현재 동작과 대안, 설계 제안에는 변경 축이 필요하다.

위치나 코드를 지어낸 항목은 LLM을 쓰기 전에 걸러진다.

### 8.2 LLM 검증

둘째 층은 새 세션의 검증자가 항목마다 두 가지를 판정한다.

- 사실성: 코드가 정말 항목이 주장하는 대로 동작하는가
- 적절성: 그 관점에 속하는 문제이고, 분류와 심각도가 맞는가

적절성 기준은 관점마다 다르다.

| 관점 | 적절성 기준 |
|---|---|
| 기획 | 요구사항이나 관례로 이미 정해진 결정이 아닌가. 확인할 만큼 동작 차이가 큰가 |
| 에러 | 적힌 도달 조건이 실제로 성립하는가. 다른 곳에서 이미 처리하고 있지 않은가 |
| 보안 | 공격자가 그 입력을 실제로 제어할 수 있는가. 프레임워크나 상위 계층이 이미 막고 있지 않은가 |
| 설계 | 변경 축이 실제로 있는가. 기존 관례와 부딪히지 않는가 |

검증자에게는 항목의 주장, 위치, 인용 코드, 분류별 필수 필드만 넘긴다. 관점 단계의 추론 과정과 확신도는 넘기지 않는다. 추론을 읽으면 검증자가 그 결론을 따라가기 쉽다.

검증자는 적절성을 두 질문으로 나눠 판정한다. 첫째, 이 항목이 문제인가. 문제가 아니면 기각한다. 둘째, 문제라면 지금 분류가 맞는가. 분류가 틀렸으면 기각하지 않고 맞는 분류로 옮긴다. 사실이고 문제인 항목을 관점이 맞지 않다는 이유로 버리면, 그 문제는 어느 관점에서도 올라오지 않는다. 사실이지만 어느 분류에서도 문제가 아닌 기획 관점 항목은 동작 명세 문장으로 옮긴다.

심각도는 사실이 틀렸을 때만 바꾼다. 도달 조건이 성립하지 않거나 영향 범위를 잘못 적은 경우가 여기에 해당한다. 검증자가 "이 정도는 감수할 만하다"는 가치 판단으로 심각도를 낮추지 않는다. 그 판단은 리포트를 읽는 사람이 한다. 설계 제안에는 심각도가 없으므로 심각도를 바꾸지 않는다.

판정은 `확정`, `기각`, `수정` 중 하나다. `수정`은 분류나 심각도를 바꾸는 경우이고, 바꾼 값과 이유를 함께 낸다. 수정 이유는 실행 기록에만 남기고 리포트에는 수정된 결과만 싣는다. 기각된 항목은 리포트에서 빼되 실행 기록에는 남긴다. 관점별 오탐률을 보고 프롬프트를 고치는 재료로 쓴다.

비용을 줄이기 위해 검증은 항목마다가 아니라 관점마다 한 번 호출한다.

## 9. 병합

병합은 검증을 통과한 항목을 모아 중복을 없애고 분류를 확정한다. 규칙은 결정적으로 적용하고, 규칙으로 판단할 수 없을 때만 LLM을 쓴다.

- 같은 문제인지는 위치로 판단한다. 같은 파일에서 두 항목의 줄 범위가 같거나 한쪽이 다른 쪽을 포함하고, 분류 계열이 같으면 같은 문제다. 분류 계열은 위험, 기획 위반, 확인사항, 설계 넷이다. 관점이 같아도 합친다. 범위가 일부만 겹치면 합치지 않고 `관련 항목`으로 잇는다.
- 합칠 때 문장을 새로 쓰지 않는다. 검증을 통과한 항목 하나를 대표로 남기고 문장은 원문 그대로 둔다. 대표는 분류 우선순위, 심각도나 결정 시점이 가장 높은 항목이다. 나머지 항목은 "같은 문제로 합친 항목"으로 ID, 제목, 위치 한 줄씩 대표 아래에 붙인다. LLM에게 합친 문장을 쓰게 하면 그 문장은 검증을 거치지 않은 채 리포트에 실린다.
- 위치가 겹치지 않는데 뜻이 같은 중복은 아직 합치지 않는다. 이런 중복이 실행 기록에서 두 번 이상 나오면, LLM이 항목의 ID, 제목, 주장, 위치만 보고 같은 문제의 묶음과 대표만 고르게 하는 단계를 더한다. 이때도 문장은 쓰지 않게 하고, 합치는 일은 위 규칙대로 코드가 한다.
- 기각되거나 합쳐져 사라진 항목을 가리키는 `관련 항목` 연결은 지우거나 남은 항목으로 바꾼다.
- 어긴 기준이 있으면 결함이나 기획 위반이다. 어긴 기준 없이 코드가 고른 동작이면 확인사항이다.
- 에러 관점과 보안 관점이 같은 문제를 올리면 보안으로 분류한다.
- 확인사항에 대한 답에 따라 결함 여부가 달라지는 항목은 두 항목을 `관련 항목`으로 잇는다.

병합 뒤에는 결과 항목, 동작 명세, 요구사항 추적이 서로 맞는지 한 번 더 맞춘다.

- 동작 명세 문장이 결과 항목과 같은 위치를 인용하면 그 문장은 싣지 않는다. 같은 결정을 요청자가 두 곳에서 판단하게 된다.
- 검증에서 동작 명세로 옮겨 온 문장이 기존 동작 명세 문장과 같은 위치를 인용하면 기존 문장을 남긴다.
- 요구사항 추적은 기획 관점이 연결한 결과 항목의 최종 상태로 다시 정한다. 추적 판정은 관점 단계에서 한 번 적히지만, 그 뒤 검증과 병합에서 항목이 기각되거나 옮겨지거나 합쳐질 수 있기 때문이다.

| 연결된 항목의 최종 상태 | 추적 표시 |
|---|---|
| 기획 위반으로 남음 | 어긋남 또는 없음, 그 항목 ID |
| 확인사항으로 남음 | 명세가 모호함, 그 항목 ID |
| 동작 명세로 옮겨짐 | 동작 명세에서 확인, 그 문장 ID |
| 합쳐짐 | 대표 항목 기준으로 위 규칙을 따른다 |
| 사실이 아니어서 기각됨 | 판정 없음 |

기획 관점은 "어긋남", "없음", "명세가 모호함"으로 판정한 요구사항마다 근거가 된 결과 항목 ID를 적는다. 연결된 항목이 없으면 병합 뒤 정합성 단계에서 그 추적 판정을 "판정 없음"으로 바꾸고 실행 기록에 남긴다.

## 10. 리포트

리포트는 요청자가 코드를 열지 않고도 읽고 결정할 수 있게 쓴다. 리포트와 모든 단계의 출력은 한국어로 쓴다. 코드 식별자와 인용한 코드는 원문 그대로 둔다.

리포트에는 결정에 필요한 것만 싣는다. 항목의 주장은 한두 문장으로 쓰고 도달 조건과 겹치는 설명을 반복하지 않는다. 검증 사유, 검증에서 수정되었다는 표시, 합쳐진 관점 목록, 대상 파일 전체 목록처럼 과정을 설명하는 내용은 실행 기록에만 둔다. 검증을 거치지 못한 항목에만 "검증 안 됨"을 표시한다. 이 표시는 과정이 아니라 그 항목을 얼마나 믿을지에 관한 정보라서 읽는 사람의 판단에 필요하다. 동작 명세의 근거는 명시나 관례일 때만 표시하고, 표시가 없으면 코드가 정한 것으로 읽는다. 요구사항 추적은 요구사항마다 상태와 요청자가 판단할 곳의 ID를 한 줄로 쓴다. 상태는 구현됨, 구현됨 · 미검증, 어긋남, 없음, 명세가 모호함, 동작 명세에서 확인, 판정 없음 중 하나다.

섹션 순서는 다음과 같다.

1. 범위와 판정 기준: 고른 작업 단위, 진입점과 저장 구조 요약, 판단 근거 두세 줄, 사용한 판정 기준의 출처와 강도. 범위나 기준을 추정했다면 그 사실을 밝힌다. 대상 파일 전체 목록은 실행 기록에만 둔다.
2. 결함과 위험: 기획 위반, 에러, 보안. 심각도 높음, 중간, 낮음 순서로 둔다.
3. 기획 확인사항: `배포 전 결정 필요`와 `나중에 결정` 두 단계로 나눈다.
4. 동작 명세: 7.1절의 동작 명세. 요청자가 문장마다 의도와 맞는지 표시한다. 기획서가 없을 때는 이 섹션이 리포트에서 가장 길다.
5. 설계 제안
6. 기각 요약: 관점별로 기각된 항목 수와 사유별 개수

확인사항 항목에는 현재 동작, 대안, 영향, 관련 항목, 답을 적을 자리를 둔다.

```markdown
### Q-1 [배포 전 결정 필요] <결정 이름>
- 현재 동작: <코드가 지금 하는 일> (<file>:<line>)
- 대안: <요청을 만족하는 다른 동작>
- 영향: <현재 동작일 때 요청자가 겪는 차이>
- 관련 항목: <답에 따라 결함이 되는 항목 ID, 없으면 없음>
- 답:
```

동작 명세는 흐름별로 묶고, 문장마다 의도 확인 칸을 둔다.

```markdown
### 실패와 재시도
- B-7 외부 조회가 실패하면 → 이전 조회 결과를 유지하고 실패를 기록하지 않는다 (<file>:<line>)
  - 근거: 코드가 정함
  - 의도와 맞음: [ ] 맞음  [ ] 다름 →
- B-8 발송이 실패하면 → 3번까지 다시 보낸 뒤 포기한다 (<file>:<line>)
  - 근거: 관례
  - 의도와 맞음: [ ] 맞음  [ ] 다름 →
```

"다름"에는 원하는 동작을 한 줄로 적게 한다. 확인사항과 동작 명세의 차이는 선택지의 유무다. 확인사항은 영향이 커서 대안을 함께 제시하고 고르게 하는 항목이고, 동작 명세는 현재 동작을 보여 주고 맞는지만 표시하게 하는 문장이다.

요청자가 답을 적은 리포트는 다음 리뷰의 "이전 결정 파일"로 넘긴다. 답이 달린 결정은 다음 리뷰에서 명시 기준으로 취급하므로, 같은 확인사항이 다시 올라오지 않는다. 그 대신 답과 어긋나는 코드는 기획 위반으로 판정된다. 동작 명세도 같다. "맞음"으로 표시한 문장은 그대로, "다름"으로 표시한 문장은 요청자가 적은 동작으로 명시 기준이 된다. 기획서 없이 시작한 기능도 리뷰를 한 번 거치면 확인된 동작 명세가 남고, 이것을 기능의 기획서로 쓸 수 있다.

## 11. 실행 구조

### 11.1 설치 위치

skill은 특정 프로젝트가 아니라 사용자 전역에 둔다. 어느 프로젝트에서든 같은 skill로 리뷰할 수 있어야 하고, skill이 리뷰 대상 워크스페이스 밖에 있어야 12절의 정보 차단이 성립하기 때문이다.

본체는 `~/.agents/skills/feature-review/`에 두고, `~/.claude/skills/feature-review`는 본체를 가리키는 디렉터리 연결로 만든다. 이 컴퓨터의 다른 전역 skill이 이미 이 방식을 쓰고 있어서 따른다. 본체가 하나이므로 Claude와 Codex가 같은 프롬프트와 스크립트를 쓴다. Codex가 `~/.agents/skills/`를 전역 skill 위치로 읽는지는 구현 전에 확인한다.

### 11.2 파일 구성

```
~/.agents/skills/feature-review/
  SKILL.md             # intake 후 runner 실행
  pipeline/
    runner.py          # 단계 순서, 병렬 실행, 실행 기록
    clients/           # 공통 인터페이스, Claude 클라이언트, Codex 클라이언트
    prompts/           # 범위, 판정 기준, 관점 4종, 검증 4종
    schemas/           # collect, scope, criteria, finding, verdict, report
    validate.py        # 8.1 결정적 검사
    render_report.py   # 병합 결과 JSON을 리포트 markdown으로 변환
  runs/                # 실행 기록과 최종 리포트. 11.4 참조
```

### 11.3 실행 모드

LLM 클라이언트는 기존 skill의 공통 인터페이스 구조를 가져온다. 단계는 프롬프트와 출력 스키마만 넘기고, 어느 provider가 실행하는지는 모른다.

기존 클라이언트는 정보를 차단하려고 파일 도구를 막고 빈 디렉터리에서 실행한다. 이 skill의 단계는 코드를 읽어야 하므로 실행 모드를 하나 더 둔다.

| 모드 | 파일 접근 | 작업 디렉터리 | 쓰는 단계 |
|---|---|---|---|
| `isolated` | 없음 | 빈 임시 디렉터리 | 병합 중 LLM이 필요한 경우 |
| `repo-read` | 읽기와 검색만 | skill을 호출한 워크스페이스의 git 최상위 | 기능 범위 확정, 판정 기준 확정, 네 관점, 검증 |

Claude CLI에서 허용 도구를 지정하는 플래그와 Codex CLI의 읽기 전용 sandbox 동작은 구현 전에 실제 CLI 버전에서 확인한다.

작업 디렉터리는 skill을 호출한 워크스페이스다. skill은 리뷰할 프로젝트 안에서 호출되므로 저장소 경로를 따로 받지 않고, 각 단계의 LLM이 그 디렉터리에서 코드를 직접 탐색한다. 기준 경로는 호출한 위치가 아니라 git 저장소 최상위로 잡는다. 하위 디렉터리에서 호출해도 커밋 기록과 다른 모듈의 관례를 볼 수 있어야 하기 때문이다.

Claude CLI와 Codex CLI는 작업 디렉터리의 프로젝트 지침 파일을 자동으로 읽을 가능성이 있다. 그렇다면 기존 관례를 파악하는 데는 도움이 되지만, 파일 기록처럼 리뷰와 무관한 지시가 섞일 수 있다. 실제 동작은 구현 전에 두 CLI에서 확인한다.

기본값은 모든 단계를 provider 하나로 실행하는 것이고, 그 provider는 Claude다. 모델은 그 provider의 최신 모델을 쓰고, 추론 강도는 high로 둔다. 검증은 분석과 같은 모델이 하더라도 새 세션에서 하므로 맥락 편향은 막힌다. 같은 모델이라서 생기는 판단 편향은 남지만, 처음부터 provider를 섞으면 결과가 나빠졌을 때 원인이 모델 차이인지 프롬프트인지 가르기 어렵다. 그래서 하나로 시작하고, 실행 기록에서 검증이 관점의 오탐을 걸러내지 못하는 경향이 보이면 그때 검증 provider를 바꿔 본다.

provider, 모델, 추론 강도는 skill 본체의 설정 파일 한 곳에 둔다. 코드에 박아 두지 않는 이유는 최신 모델이 계속 바뀌기 때문이다. 설정 파일의 값은 provider별로 따로 두어서, intake나 runner 인자로 provider만 바꾸면 그 provider의 모델과 추론 강도가 따라온다. 단계별로 provider를 다르게 지정하는 것도 설정 구조로는 허용하되, 기본값으로 쓰지는 않는다.

| provider | 기본 모델 | 추론 강도 |
|---|---|---|
| Claude | 설계 시점 최신 모델 `claude-opus-5` | high |
| Codex | 설계 시점 사용자 설정 모델 `gpt-5.6-luna` | high |

모델 ID는 설계 시점인 2026-09 기준이다. CLI가 별칭으로 항상 최신 모델을 가리키게 할 수 있으면 별칭을 쓰고, 그렇지 않으면 설정 파일의 ID를 손으로 바꾼다. Claude CLI에서 추론 강도를 지정하는 방법도 구현 전에 확인한다.

### 11.4 실행 기록과 리포트 위치

실행 중에 생기는 파일은 모두 워크스페이스 밖에 둔다. 워크스페이스에 두면 리뷰 대상 저장소에 리뷰와 무관한 파일이 섞이고, 12절의 정보 차단도 깨진다.

실행 기록은 skill 본체 아래 `runs/<워크스페이스 식별자>/<실행 시각>/`에 둔다. 기존 skill들도 실행 기록을 skill 디렉터리의 `runs/` 아래에 두므로 같은 방식을 따른다. 워크스페이스 식별자는 저장소 이름에 저장소 최상위 경로의 해시를 붙여 만든다. 이름이 같은 저장소가 여러 곳에 있어도 기록이 섞이지 않게 하기 위해서다.

실행 기록 디렉터리에는 수집 결과, 범위와 판정 기준, 관점별 결과, 검증 결과, 기각 항목, 병합 결과, 최종 리포트를 단계별 파일로 남긴다. 최종 리포트도 이 디렉터리에 두고, skill은 실행이 끝나면 리포트 경로와 요약을 사용자에게 보여 준다. 요청자가 확인 칸을 채운 리포트는 그 경로 그대로 다음 리뷰의 이전 결정 파일로 넘긴다.

## 12. 정보 차단

`repo-read` 모드의 단계는 워크스페이스의 모든 파일을 읽을 수 있다. 실행 기록이 워크스페이스 안에 있으면 검증자가 관점 단계가 남긴 추론을 읽을 수 있고, skill의 프롬프트가 워크스페이스 안에 있으면 관점 단계가 검증 기준을 먼저 읽고 거기에 맞춰 항목을 쓸 수 있다. skill을 전역에 두고 실행 기록을 skill 아래에 두는 것은 이 두 경로를 막기 위해서다.

워크스페이스 밖에 둔다고 해서 읽을 수 없게 되는 것은 아니다. 읽기 전용 sandbox는 쓰기를 막을 뿐 절대 경로 읽기까지 막지는 않을 가능성이 있다. 그래서 단계에 넘기는 프롬프트에는 실행 기록이나 skill 디렉터리의 경로를 넣지 않고, 필요한 내용은 프롬프트 본문에 직접 담는다. 경로를 모르면 찾아 읽을 이유도 없다. 두 CLI가 작업 디렉터리 밖의 읽기를 실제로 어디까지 허용하는지는 구현 전에 확인한다.

skill이 들어 있는 저장소 자체를 리뷰하는 경우에는 이 차단이 성립하지 않는다. 드문 경우이므로 차단하지 않고, 리포트 첫머리에 그 사실을 밝힌다.

## 13. 결과 항목 형식

모든 관점은 같은 형식으로 항목을 낸다. 필드별 필수 여부는 분류에 따라 다르고, 8.1의 결정적 검사가 이를 확인한다.

| 필드 | 설명 |
|---|---|
| `id` | 관점 접두어와 번호 |
| `lens` | `spec`, `error`, `security`, `design` |
| `category` | `spec_violation`, `spec_question`, `defect`, `security`, `design` |
| `severity` | 결함류는 `high`, `medium`, `low`. 확인사항은 `before_release`, `later` |
| `title` | 한 줄 요약 |
| `location` | 원인이 되는 코드 한 곳의 파일, 시작 줄, 끝 줄, 인용 코드 |
| `claim` | 코드가 어떻게 동작한다는 주장 |
| `violated_criterion` | 어긴 기준의 출처, 강도, 원문. 출처는 `spec`, `request`, `decision`, `commit`, `doc`, `convention` 중 하나이고, 강도는 6.3절의 `explicit`, `inferred`, `convention` 중 하나 |
| `reach_condition` | 에러와 보안 항목에서 그 경로에 도달하는 조건 |
| `current_behavior`, `alternative`, `impact` | 확인사항에서 요청자가 고르는 데 필요한 정보 |
| `change_axis` | 설계 제안의 근거가 되는 변경 축 |
| `related` | 관련 항목 ID 목록 |

검증 결과는 항목 ID, 사실성 판정, 적절성 판정, 최종 결정, 바뀐 필드, 이유로 이루어진다.

동작 명세는 결과 항목과 형식이 달라서 따로 낸다. 문장마다 `id`, 흐름 묶음, 조건, 현재 동작, `location`, 근거 출처와 강도, 관련 결과 항목 ID를 가진다. 동작 명세 문장도 8.1의 위치·인용 검사와 8.2의 사실성 검증을 거친다. 동작 명세가 틀리면 요청자는 실제와 다른 동작을 보고 "맞음"을 표시하게 되고, 그 문장이 다음 리뷰의 명시 기준이 되기 때문이다. 적절성 판정은 하지 않는다.

## 14. 고려했다가 버린 안

**front와 back으로 나눈 리뷰.** 기획 정합성은 명세와 코드의 대조라서 계층과 관계가 없다. 한 요구사항이 서버 처리와 화면 표시에 걸쳐 있으면, 계층별 리뷰는 양쪽 모두 자기 몫이 아니라고 보고 넘길 수 있다. 계층은 관점 안의 점검 항목으로 다룬다. 파이프라인을 계층별로 나누는 것은 판정 기준 문서가 계층마다 다를 때만 의미가 있다.

**기획 확인사항을 대화 중 질문으로 받는 방식.** 리뷰가 중간에 멈추고, 요청자는 버그와 기획 결정을 따로 봐야 한다. 리포트에 모으면 한 번에 보고 필요한 것만 골라 답할 수 있다. 답할 압력이 약해지는 문제는 결정 단계 구분과 이전 결정 파일로 보완한다.

**영향이 큰 결정만 확인사항으로 올리고 나머지는 가정 목록으로 두는 방식.** 기획서가 없으면 코드가 내린 결정 전체가 사실상 기획인데, 가정 목록은 흐름 없이 나열되어 기능 전체를 읽기 어렵다. 확인 칸도 없어서 요청자가 훑어보고 지나가면 다음 리뷰의 기준으로 이어지지 않는다. 동작 명세로 바꿔 흐름별로 묶고 문장마다 확인 칸을 두었다.

**관점 앞에 기능 지도를 만드는 단계.** 처음에는 네 관점이 같은 범위를 보게 하고 코드 탐색을 한 번으로 줄이려고, 진입점, 흐름, 상태, 코드가 내린 결정을 요약한 기능 지도를 먼저 만들었다. 실제 실행에서 이 요약은 정보를 잃었고 관점은 요약에 기댔다. 컬럼마다 갱신 조건이 다른 저장 쿼리가 결정 한 줄로 뭉개져 그 차이에서 생긴 결함을 어느 관점도 찾지 못했고, 스키마에 칸이 없던 저장 구조의 제약과 배포 설정은 지도에서 빠져 관점에서도 보이지 않았다. 대상 파일 109개 중 88개는 지도에 한 번도 나오지 않았다. 같은 기능을 요약 없이 코드에서 직접 읽은 리뷰가 결함을 더 많이 찾았고, 지도 단계는 네 관점이 모두 기다리는 가장 긴 단계였다. 범위를 맞추는 일은 범위 결과가 이미 하므로 지도를 없앴다. 네 관점이 각자 코드를 탐색하므로 토큰 사용량은 늘어난다.

**subagent만으로 구성한 skill.** 사용자와 대화하는 단계를 다루기는 쉽지만, 실행 순서가 프롬프트 지시에 의존하고 provider를 바꿔 끼울 수 없다. 실행 기록도 따로 만들지 않으면 남지 않는다.

**기획 관점을 먼저 실행하고 그 결과를 에러 관점에 넘기는 순서.** 에러 판정에 영향을 주는 것은 확인사항에 대한 요청자의 답인데, 그 답은 리포트가 나온 뒤에 온다. 실행 중에는 두 관점이 서로의 결과를 쓰지 않으므로 순서를 둘 이유가 없다.

**병합 후 검증.** 8절 참조.

**모든 항목을 개별 호출로 검증.** 항목 수만큼 호출이 늘어난다. 관점별로 묶어도 검증자가 항목을 하나씩 판정하는 데는 문제가 없다고 본다. 묶었을 때 판정 품질이 떨어지는지는 실행 기록으로 확인해야 한다.

**내장 코드 리뷰와 보안 리뷰 skill 재사용.** 바로 쓸 수 있지만 프롬프트를 고칠 수 없어서, 실행 기록을 보고 skill을 개선하는 루프를 만들 수 없다.

## 15. 열린 결정

- **실행 기록 정리.** 실행 기록은 계속 쌓인다. 보존 기간은 기록이 쌓인 뒤에 정한다.
- **설계 제안 상한.** 초기값을 정하고 실행 기록을 보며 조정한다.
- **구현 전 모드.** 요청만 있고 코드가 없을 때 같은 로직으로 기획의 빈자리를 먼저 묻는 모드를 이 skill에 넣을지, 별도 skill로 뺄지 정해야 한다.
- **추가된 기능의 경계.** 6.2절의 "이번에 추가된 기능"을 어디까지로 볼지 정해야 한다. 기본 브랜치에서 바로 작업하고 커밋하는 흐름이면 기능의 시작 커밋을 git 기록만으로 알기 어렵다. 기능 설명과 커밋 메시지로 LLM이 판단하게 둘지, intake에서 시작 지점을 선택적으로 받을지 정해야 한다.
- **CLI 동작 확인.** 구현 전에 다음 CLI 동작을 확인한다. Codex가 `~/.agents/skills/`를 전역 skill 위치로 읽는지, 두 CLI가 읽기 전용 모드에서 작업 디렉터리 밖의 파일 읽기를 허용하는지, 허용 도구와 추론 강도를 지정하는 플래그가 무엇인지, 최신 모델을 가리키는 별칭이 있는지.
- **CLI의 프로젝트 지침 파일 로딩.** 두 CLI가 작업 디렉터리의 지침 파일을 자동으로 읽는지, 읽는다면 끌 수 있는지 확인해야 한다. 11절 참조.

## 16. 확인 방법

이 skill이 목적대로 동작하는지는 다음 평가 케이스로 확인한다. 케이스는 스킬 규칙 본문이 아니라 평가 입력에만 둔다.

- **명세 공백 재현 케이스.** 명세가 비어 있는 자리를 구현자가 가정으로 채운 이전 과제 코드를 넣고, 그 가정이 기획 확인사항으로 올라오는지 본다. 2절의 첫 번째 실패를 이 skill이 잡는지 확인하는 케이스다.
- **결함 주입 케이스.** 기획서가 있는 기능에 요구사항 위반, 동시성 결함, 인가 누락을 하나씩 심고, 각각이 맞는 관점에서 올라오는지 본다.
- **오탐 케이스.** 결함이 없는 코드를 넣고, 검증 단계가 관점의 오탐을 얼마나 기각하는지 본다.
- **기획서 없음 케이스.** 기획서 없이 실행해, 동작 명세의 문장이 실제 코드 동작과 맞는지, 내부 구현이 아니라 관찰할 수 있는 동작만 담는지 본다. 이어서 문장 몇 개에 "다름"을 표시해 다시 실행하고, 그 문장들이 기획 위반으로 판정되는지 본다.
- **입력 없음 케이스.** intake에서 아무것도 주지 않고 실행해, 찾은 기능이 실제로 최근 추가된 기능과 맞는지, 추정 기준만으로 기획 위반이 나오지 않는지 본다.
- **이전 코드 제외 케이스.** 이전부터 있던 코드에 결함을 심고 그 위에 새 기능을 추가해, 새 기능과 무관한 결함은 올라오지 않고 새 기능의 동작을 깨는 결함만 올라오는지 본다.
- **결정 반영 케이스.** 확인사항에 답을 적은 파일을 넣고 다시 실행해, 같은 확인사항이 사라지고 답과 어긋나는 코드가 기획 위반으로 바뀌는지 본다.
