# feature-review 판정 기준

## 이 문서의 쓰임

이 문서는 네 관점과 검증자가 무엇을 문제로 보고 언제 올리지 않는지를 정한 기준의 원본이다. 관점 프롬프트는 절차와 출력 형식만 정하고 판정 기준은 거의 담고 있지 않아서, 같은 코드를 두고도 실행마다 올라오는 항목이 달랐다. 그래서 판정 기준을 원칙 단위로 정리하고, 그중 모델이 놓치기 쉬운 것만 골라 프롬프트에 넣었다.

프롬프트에는 원칙의 결론만 들어간다. 원칙 ID, 출처, 예시는 이 문서에만 있고, 프롬프트에는 각 관점의 `역할`, `판정의 잣대`, `위반 신호`, `올리지 않는 경우` 네 절로 들어간다. 검증자 프롬프트에는 `역할`과 함께 검증할 관점의 `올리지 않는 경우` 목록이 그대로 들어가서, 관점이 올리지 말았어야 할 항목을 검증자가 같은 기준으로 걸러 낸다. 이 목록이 두 프롬프트에서 똑같은지는 `tests/test_prompts.py`가 확인한다. 문장의 최종 표현은 프롬프트가 기준이고, 이 문서는 각 문장이 왜 들어갔는지와 어디서 왔는지를 추적하는 데 쓴다.

아래 원칙 표의 "반영" 열은 원칙이 프롬프트의 어느 절에 들어갔는지를 적는다. "신호"는 `위반 신호`, "제외"는 `올리지 않는 경우`, "할 일"은 기존 `할 일` 절이다. 반영이 "삭제"인 원칙은 기록으로만 남는다.

이 문서는 여러 기능과 여러 저장소에 공용으로 쓴다. 규칙 본문에는 특정 업무 영역의 명사, 아키텍처 스타일, 프레임워크의 이름을 쓰지 않고, 구체 사례는 각 절 끝의 예시에만 둔다. 예시를 지워도 규칙의 의미는 달라지지 않아야 한다.

새 원칙은 실행 기록에서 같은 문제가 두 번 관찰될 때만 추가한다. 한 번 관찰된 문제는 그 실행의 기록에만 남기고 두 번째 사례를 기다린다. 한 번의 실패에 맞춰 원칙을 늘리면 프롬프트가 길어지는 만큼 모델이 핵심 기준을 덜 따르게 되기 때문이다.

## 공통 기준

네 관점 프롬프트 모두에 `판정의 잣대` 절로 들어간다.

판정의 잣대는 대상 저장소 자신의 구조와 관례다. 계층 구분, 오류 응답 형식, 동시성 제어, 테스트 방식 모두 저장소가 이미 쓰는 방식을 기준으로 삼고, 다른 구조나 방식으로 옮기자는 제안은 올리지 않는다. 관례보다 나은 방식이라도 이 기능만 다르게 만들면 일관성이 깨진다.

심각도 정의는 심각도가 high, medium, low인 기획, 에러, 보안 프롬프트에만 들어간다. 설계 제안은 심각도가 null이라 설계 프롬프트에는 넣지 않았다.

- high: 정상 사용 범위의 입력이나 흔한 타이밍에서 도달하고, 결과가 데이터 손실, 잘못된 상태의 영구 저장, 권한 없는 접근이나 변경처럼 되돌리기 어렵거나 호출하는 쪽이 알아챌 수 없다.
- medium: 동시 요청, 외부 장애, 특정 권한처럼 운영 중 실제로 생기는 조건이 있어야 도달한다. 또는 흔히 도달하지만 결과가 호출하는 쪽에 드러나고 재시도나 수동 조치로 되돌릴 수 있다.
- low: 도달 조건이 드물고 결과가 드러나며 되돌릴 수 있다. 또는 기능은 맞게 끝나지만 응답 코드나 메시지처럼 계약의 품질만 떨어진다.

초안의 다른 공통 규칙은 프롬프트에 이미 있어서 넣지 않았다. 근거 위치를 한 곳만 인용하는 규칙, 도달 조건이 없으면 올리지 않는 규칙, 이전 코드의 문제를 올리지 않는 규칙, 점수를 매기지 않는 규칙은 각 관점의 출력 규칙과 금지 사항에 있고, 심각도를 사실로만 바꾸는 규칙은 검증자 프롬프트의 할 일에 있다. 테스트 통과가 반증이 아니라는 규칙은 SP7로 옮겼다.

ER1부터 ER3은 기존 할 일 2번이 이미 동시 호출, 부분 성공, 재요청, 외부 지연을 차례로 따지게 하므로 판정 원칙 대신 코드에서 보이는 신호만 남겼다. 비평 방식에 있던 "두 요청이 어떤 순서로 끼어드는지 적는다" 같은 내용은 기존 출력 규칙의 도달 조건과 겹친다.

ER7과 SE6은 같은 자원 고갈을 다루고, 경계는 누가 크기와 횟수를 정하는가다. 공격자가 크기나 횟수를 제어해야 도달하면 보안 관점이, 정상 사용에서 데이터가 늘어 생기면 에러 관점이 맡는다. 두 관점 모두 반대쪽 경우를 `올리지 않는 경우`에 한 줄로 적었다.

ER8에서 초안의 "기본값이 코드의 기본값과 다르다"는 뺐다. 이 경우는 null 허용이나 타입 불일치로 드러날 때만 문제가 되고, 그 신호는 이미 남아 있다.

DE2의 제외 조건 두 줄은 책임을 나누자는 제안이 근거 없이 늘어나는 것을 막는다. private 메서드로 나눈 것은 가독성 정리라서 책임 분리의 근거로도 반대 근거로도 쓰지 않고, 늘 함께 바뀌는 책임은 나누자고 제안하지 않는다.

DE5의 변경 축은 셀 수 있어야 한다. "언젠가", "아마" 같은 표현이나 코드 주석은 근거가 아니고, 테스트 대역은 테스트가 실제로 그 자리에 대역을 끼울 때만 변형으로 센다.

## 검증자

검증자 네 프롬프트 모두 역할과 해당 관점의 `올리지 않는 경우` 목록을 받는다. 역할은 회의적인 스태프 엔지니어이고, 리포트에 실린 항목이 모두 코드로 다시 확인할 수 있는 사실인지를 책임진다. 그래서 항목의 주장을 믿지 않고 반례부터 찾으며, 기각에도 확정과 똑같이 코드 위치를 근거로 댄다.

| ID | 판정하는 성질 | 반영 | 출처 |
|---|---|---|---|
| VE1 | 사실성은 호출 경로를 따라 확인한다 | 삭제. 기존 할 일 1번과 같다 | design.md 8.2절, verify_error.md, verify_security.md |
| VE2 | 도달 조건은 막는 장치를 찾아 시험한다 | 한 문장만 에러와 보안 검증자의 할 일 2번에 추가했다. 막는 장치를 찾지 못했다면 어디까지 찾아봤는지 이유에 적고 도달 조건이 성립한다고 본다 | design.md 8.2절, verify_error.md, verify_security.md |
| VE3 | 관점의 "올리지 않는 경우"를 판정 근거로 쓴다 | `올리지 않는 경우` 절로 추가. 관례를 근거로 삼으면 그 관례의 코드 위치를 검증자가 직접 찾아 적는다 | lens_design.md 금지 사항, task2/assignments/taskB-7.md 4절 |
| VE4 | 분류는 문제의 성격으로 정한다 | 삭제. 기존 할 일 3번과 같다 | design.md 8.2절과 9절 |
| VE5 | 심각도는 사실이 틀렸을 때만 바꾼다 | 삭제. 기존 할 일 4번과 금지 사항과 같다 | design.md 8.2절, task1/CLAUDE.md 결정론적 게이트 |

VE2의 한 문장은 에러와 보안 검증자에만 넣었다. 두 관점의 항목에만 막는 장치를 찾아야 하는 도달 조건이 있기 때문이다.

기획 검증자에서는 `올리지 않는 경우`에 해당하는 항목을 기각하지 않고 동작 명세로 옮긴다. 기획 검증자는 사실이지만 문제가 아닌 항목을 버리지 않고 요청자에게 동작 명세로 보여 주는 규칙을 이미 따르기 때문이다.

## 예시

이 절은 규칙을 이해하기 위한 예시이며 지워도 규칙은 그대로다. 프롬프트에는 들어가지 않는다.

- SP2: 요청이 "같은 조건의 신청은 하나만 유지한다"뿐인데 코드가 두 번째 신청을 409로 거절한다. 기존 신청을 돌려주는 동작도 요청을 만족하므로 코드가 정한 결정이다.
- SP3: 목적이 "고객이 금액의 근거를 알 수 있게 한다"인데 외부 취소가 시간 초과로 끝나면 500을 돌려준다. 고객은 처리 여부를 알 수 없어 목적과 어긋난다.
- SP7: 외부 결제 호출을 모든 테스트 구성에서 대역으로 바꿔서, 거절 응답을 승인으로 읽는 코드가 인수테스트 21개를 통과했다.
- ER4: 외부 예약처 조회가 실패하면 빈 목록을 돌려주고, 감시 작업은 그 빈 목록을 "빈자리 없음"으로 저장한다. 조회 실패 동안에는 알림 대상이 사라진다.
- ER5: 결제 응답을 `is2xxSuccessful()`로만 판정했는데 외부는 거절도 200과 `approved:false`로 돌려준다.
- ER9: `UPDATE ... SET status = ?, detail = COALESCE(detail, ?)`에서 status는 매번 바뀌고 detail은 처음 값에 머물러, 재처리 뒤 상태와 상세가 서로 다른 시도를 가리킨다.
- SE3: `GET /subscriptions/{id}`가 `findById(id)` 결과를 그대로 돌려주어, 로그인한 사용자가 번호를 바꿔 가며 남의 신청을 볼 수 있다.
- SE6: 갱신 요청마다 외부 예약처를 조회해서, 한 사용자가 초당 수십 번 갱신하면 예약처가 서비스 전체의 조회를 막는다.
- DE1: 저장소가 포트와 어댑터 구조를 따르고 기존 기능은 모두 저장 어댑터 안에서 영속화 예외를 도메인 예외로 바꾸는데, 새 기능의 웹 예외 처리기가 `OptimisticLockingFailureException`을 직접 잡는다. 반대로 계층형 구조 저장소에 포트와 어댑터를 도입하자는 제안은 올리지 않는다.
- DE5: 결제 수단이 카드 하나이고 기준에 다른 수단이 없는데 `PaymentMethod` 인터페이스와 구현 하나를 새로 만들었다. 변형 수가 1이라 제안 대상이다.
