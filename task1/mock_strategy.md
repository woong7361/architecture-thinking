# A-2: 상태 검증 vs 행위 검증, 그리고 가짜 객체 전략

> 결제 환불 도메인(DoDo Class)을 코드 맥락으로 삼아 정리한다.
> 핵심 질문: "무엇을 검증할 것인가"와 "어디에 가짜를 끼울 것인가".

---

## 1. 고전파 TDD vs 런던파 TDD

### 두 관점의 차이

**고전파(Classical / Detroit)** 는 **상태**를 검증한다. 객체에 입력을 주고, 그 결과로 나온 값이나 객체의 최종 상태가 기대와 맞는지 확인한다. 협력 객체는 가능하면 진짜를 쓰고, Mock은 외부 의존처럼 어쩔 수 없을 때만 쓴다. 테스트의 관심사는 "이 로직이 올바른 답을 내는가"다.

**런던파(London / Mockist)** 는 **행위**를 검증한다. 대상 객체가 협력 객체의 어떤 메서드를, 몇 번, 어떤 인자로 호출했는지를 확인한다. 협력 객체를 전부 Mock으로 대체하고 대상 객체만 고립시켜 테스트한다. 테스트의 관심사는 "이 객체가 협력자와 올바르게 상호작용하는가"다.

### 장단점

| 관점 | 테스트 용이성 | 유연성(리팩토링 내성) |
|------|------------|---------------------|
| 고전파 | 진짜 객체를 엮어야 해 셋업이 무거울 수 있음 | **강함** — 내부 구현이 바뀌어도 결과만 같으면 통과 |
| 런던파 | Mock으로 고립이 쉬워 셋업이 가벼움 | **약함** — 호출 순서/방식이 바뀌면 결과가 같아도 깨짐 |

런던파의 핵심 약점은 **테스트가 구현 구조에 묶인다**는 것이다. `verify(svc).calculate()` 같은 단언은 "calculate를 호출했다"는 구현 사실을 박제한다. 리팩토링으로 호출 구조가 바뀌면, 동작이 멀쩡해도 테스트가 빨갛게 된다. 이게 바로 "리팩토링하면 다 깨지는 가짜 테스트"다.

### 내가 더 끌리는 쪽: 고전파 (단, 경계는 런던파)

나는 **순수 도메인 로직에는 고전파**가 맞다고 본다. 이유는 명확하다. 결제 환불에서 진짜 중요한 건 "일할 계산이 15000원을 정확히 내는가"라는 **결과**지, "calculator를 한 번 호출했는가"라는 **절차**가 아니다. 결과를 검증하면 내부 구현을 자유롭게 바꿔도 테스트가 살아남고, 그 테스트가 진짜 회귀 안전망이 된다.

다만 **외부 의존을 엮는 오케스트레이션 계층(Facade)** 에서는 런던파가 불가피하다. DB 트랜잭션, PG API 호출, 구독 취소를 진짜로 돌릴 수 없으니 Mock으로 대체하고, "성공 시 환불을 SUCCEEDED로, 실패 시 TIMED_OUT으로 전이시키는가" 같은 흐름(행위)을 검증할 수밖에 없다. 그래서 내 입장은 "기본은 고전파, 외부 경계에서만 런던파"다.

## 2. 가짜 객체를 언제 쓰고 언제 피하는가 — 내 기준

### 쓴다: 외부 시스템 경계

다음은 Mock/Stub으로 격리한다. 공통점은 **느리거나, 비결정적이거나, 부작용이 있거나, 통제 불가능**하다는 것이다.

- DB (TxManager, Repository) — 느리고 환경 의존적
- 외부 API (PortOne PG 호출) — 네트워크 비결정성, 실제 결제 부작용
- 시계/랜덤 (`time.Now()`, UUID 생성) — 같은 입력에 다른 출력
- 메시지 큐, 이메일 발송 등 부작용

이런 경계는 가짜로 끼워야 테스트가 **Fast / Repeatable** 해진다. 특히 PG 호출은 실패/타임아웃 분기를 진짜로 재현할 수 없으므로, Stub으로 "거부 응답", "타임아웃"을 주입해야만 그 분기를 검증할 수 있다.

### 피한다: 순수 도메인 로직

다음은 절대 Mock으로 감싸지 않는다. **외부 의존이 없어 진짜로 실행해도 빠르고 결정론적**이기 때문이다.

- 값 객체 (환불 금액, 일할 계산 결과)
- 계산 규칙 (`CalculateProration`)
- 상태 전이 (`ApplyRefund`: PAID → REFUNDED / PARTIALLY_REFUNDED)

이걸 Mock으로 감싸면 "진짜 계산"이 사라지고 "내가 정한 정답"만 남는다. 테스트가 검증할 게 없어진다.

### 한 줄 기준

> **"진짜로 실행했을 때 느리거나, 비결정적이거나, 부작용이 있는가?"** — 그렇다면 가짜를 끼운다. 아니라면 진짜를 쓴다.

도메인 로직은 이 질문에 전부 "아니오"다. 그래서 가짜를 끼울 이유가 없다.

## 3. 가짜를 쓰면 안 되는 경우 — 내 코드 맥락 분석

### 실제 사례: Facade 테스트가 일할 계산을 Stub으로 덮었다

DoDo Class의 환불 Facade 테스트(`order_refund_test.go`)는 이렇게 되어 있다.

```go
// success_refund_full 시나리오
CalculateRefundAmountFunc: func(...) (int64, []byte, error) {
    return 5000, []byte("detail"), nil   // ← 환불 금액 계산을 Stub이 박제
}
```

`CalculateRefundAmount`는 일할 계산(`결제금액 / 총일수 × 잔여일수`)을 수행하는 **순수 도메인 로직**이다. 그런데 이 테스트는 그 계산을 진짜로 돌리지 않고 Stub이 그냥 `5000`을 반환하게 만들었다.

### 무엇이 망가지는가

**첫째, 계산이 틀려도 테스트가 초록색이다.** 일할 단가 절사를 `round`로 잘못 바꾸든, 잔여일수 부호를 반대로 쓰든, Stub은 변함없이 5000을 반환하므로 테스트는 통과한다. 돈이 걸린 가장 중요한 규칙에 **회귀 안전망이 없다.**

**둘째, 테스트가 검증하는 건 계산이 아니라 "호출했다는 사실"뿐이다.** 이 테스트는 "Facade가 calculate를 호출하고, 그 반환값으로 환불 레코드를 만든다"는 흐름만 확인한다. 이건 Facade 테스트로서는 정당하다 — 문제는 **순수 계산을 따로 상태 검증하는 테스트가 어디에도 없다**는 점이다. 실제로 `proration_test.go`도, `order_entity_test.go`도 존재하지 않는다.

### 올바른 분리

- **일할 계산 / 상태 전이** → Stub 없이 진짜 실행 + 결과 단언 (고전파)
  - `assertEquals(15000, calculate(30000, 30, 15))`
  - `order.applyRefund(30000); assertEquals(REFUNDED, order.status)`
- **Facade** → 위 계산은 진짜로 두거나 별도 테스트로 커버하고, DB/PG/구독만 Stub (런던파)

핵심은 **"가짜로 덮은 그 자리가 사실은 검증했어야 할 핵심 로직이 아닌가?"** 를 항상 되묻는 것이다. 외부 의존이라서 덮는 건 정당하지만, 계산이 귀찮아서 덮으면 그 순간 테스트는 게이트가 아니라 장식이 된다.

이 분석이 task1 Java 환불 도메인 작업의 설계 근거가 된다.
