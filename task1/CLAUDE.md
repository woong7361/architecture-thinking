# task1 AGENTS.md

> 이 파일은 루트 AGENTS.md를 상속하며, Phase 1 · Station 1-1(Test-Driven Foundation) 작업에만 적용되는 추가 규칙이다.

## 스프린트 목적

요구사항을 실행 가능한 테스트로 고정하는 것. 단위테스트(JUnit5/Mockito/AssertJ)와 BDD 인수테스트(Cucumber-JVM)를 직접 작성하고, 그 인수테스트가 "AI가 짠 코드가 맞는가"를 판정하는 결정론적 게이트임을 체감한다.

---

## 스택 규칙

- 언어: Java 17 이상 (원래 목표는 Java 24였으나, 로컬에 설치된 JDK가 corretto-17이라 17로 맞춘다. 일할계산 등 순수 도메인 로직에는 17로 충분하다.)
- 단위테스트: JUnit 5 + Mockito + AssertJ
- 인수테스트: Cucumber-JVM (Gherkin)
- 빌드: Maven — Cucumber-JVM 공식 레퍼런스가 Maven 기준이라 학습 마찰 최소화
- 다른 언어/프레임워크 맥락이 있으면 "이전에는 이렇게, 여기서는 이렇게"를 한 줄로 병기한다.

---

## TDD 사이클 규칙

- Red → Green → Refactor 순서를 반드시 지킨다.
- Green 단계에서 코드는 테스트를 통과시키는 최소한만 작성한다. 과도한 선행 구현을 하지 않는다.
- 각 사이클은 커밋 또는 메모로 단계가 드러나야 한다. 커밋 메시지에 `[Red]`, `[Green]`, `[Refactor]` 접두어를 붙인다.
- 순수 도메인 로직을 먼저 단위테스트로 고정한 뒤, 외부 의존이 있는 로직으로 넘어간다.

---

## 테스트 설계 규칙

### 테스트 범위

- 단위테스트: 외부 의존 없이 실행 가능한 순수 도메인 로직. 빠르고 독립적이어야 한다.
- 통합테스트: DB, 외부 API 등 실제 의존이 연결되는 경계. 느리고 비싸므로 꼭 필요한 경우만 작성한다.
- 인수테스트: 완제품이 요구사항을 만족하는지 검증. Gherkin Feature 파일로 작성하며 사람과 기계 모두 읽을 수 있어야 한다.

### Mock 사용 기준

- 외부 시스템(DB, 외부 API, 메시지 큐)은 Mock/Stub으로 격리한다.
- 순수 도메인 로직(값 객체, 계산 규칙, 상태 전이)은 Mock으로 감싸지 않는다. 감쌀 경우 구현을 그대로 베끼는 테스트가 된다.
- Mock을 사용할 때는 "이 의존이 외부 시스템이기 때문에"라는 이유를 주석 한 줄로 남긴다.
- Mockito `verify`는 행위가 중요한 경우(예: 이벤트 발행, 외부 호출 횟수)에만 사용한다. 상태로 검증할 수 있으면 상태 검증을 우선한다.

### FIRST 원칙 자가 점검

테스트를 작성한 뒤 아래를 확인한다.

- Fast: 단위테스트 1개가 수십 ms 이내로 실행되는가
- Independent: 다른 테스트에 의존하거나 순서에 영향받지 않는가
- Repeatable: 같은 입력에 항상 같은 결과가 나오는가
- Self-validating: 실행 결과가 Pass/Fail로 명확히 구분되는가
- Timely: 구현 코드보다 먼저(또는 동시에) 작성되었는가

## Gherkin 작성 규칙

- Given/When/Then 구조를 지킨다. And/But은 중복 구조를 줄일 때만 사용한다.
- Happy Path와 Unhappy Path(경계값, 실패, 거절 시나리오)를 모두 포함한다.
- Then 절은 검증 가능한 단언이어야 한다. "should work"처럼 모호한 표현은 금지한다.
- 각 Scenario는 독립적으로 실행 가능해야 한다. 시나리오 간 상태 공유를 피한다.
- Feature 파일은 도메인 언어로 작성한다. 구현 세부사항(클래스명, 메서드명)을 노출하지 않는다.

---

## 결정론적 게이트 원칙

인수테스트는 AI가 생성한 코드의 정합성을 판정하는 게이트다.

- AI에게 구현을 맡긴 뒤 반드시 인수테스트로 판정한다. 같은 세션 내 AI의 자기 평가("잘 짰어?")는 맥락 편향이 있으므로 판정 근거로 삼지 않는다.
- 테스트가 통과해도 "이 변경을 잡아낼 수 있는가"를 확인한다. 일부러 결함을 하나 심어 테스트가 Red가 되는지 검증한다.
- 테스트가 Red가 되지 않으면 그 테스트는 결함 탐지 능력이 없는 것이다. 빠진 단언을 추가한다.

---


## 코드 생성 시 AI 행동 규칙

- 테스트 코드를 생성할 때 경계값과 예외 케이스를 먼저 묻는다. Happy Path만 있으면 보완을 제안한다.
- 도메인 로직을 Mock으로 감싸는 코드가 생성되려 하면 이유를 먼저 확인한다.
- TDD 사이클을 건너뛰고 구현 먼저 작성하는 방향으로 유도하지 않는다.
- 생성한 테스트는 FIRST 원칙 자가 점검 결과를 함께 제시한다.
- Gherkin의 Then 절에 모호한 표현이 있으면 구체적인 단언으로 교체를 제안한다.
- **Refactor 단계마다 단일 책임(SRP)을 자가 점검한다.** 서로 다른 축(계산 규칙 vs 정책 판단, 상태 전이 vs 영속성 등)이 한 클래스에 뭉쳐 있는지 확인한다. **private 메서드 분리는 가독성 정리일 뿐 책임 분리가 아니다** — 책임 분리는 클래스/파일 경계가 갈라져야 성립한다. 뭉침을 발견하면 즉시 분리를 제안하되, 지금 분리할지 미룰지는 도메인 판단(그 축의 향후 변경 가능성)에 근거를 남기고 결정한다.
