(Grit's Why): 시니어는 'TDD를 할 줄 아는 사람'이 아니라 '왜 테스트가 이 비용을 감수할 가치가 있는지'를 아는 사람입니다. 테스트의 종류와 비용 구조를 모르면 '커버리지 100%'를 자랑하면서 정작 가치 없는 테스트만 쌓게 됩니다.

### 교본 (3축)

- 기술: 테스트 주도 개발(켄트 벡), 객체 지향 설계와 실천(프리먼·프라이스). A-0 필수 도서이니 그쪽 안내를 따르세요.
- 마인드셋: 함께 자라기(김창준). A-0 안내를 따르세요.
- 팀그릿: ai-native-development-guide Ch7(AI 테스트 3함정, 뮤테이션 테스트, 구현 테스트 vs 행동 테스트).

### 수행 내용

1. 테스트의 역사를 짧게 정리해 주세요. 수동 검증에서 시작해 단위테스트와 xUnit 계열(켄트 벡의 SUnit, 이어서 JUnit), 2000년대 초 TDD, 그 이후 BDD와 인수테스트로 확장되는 흐름입니다. 연도 암기가 목적이 아니라, 각 단계가 '직전 단계의 무엇이 아쉬워서' 등장했는지를 중심으로 적어 주세요.

```
테스트의 역사는 피드백을 더 빠르고, 작고, 명확하게 만들려는 흐름으로 볼 수 있다. 처음에는 사람이 직접 프로그램을 실행하며 확인했지만, 수동 검증은 반복 비용이 크고 변경 때마다 같은 확인을 다시 해야 했다. 이를 자동화하려는 초기 시도(대화형 실행, 캡처-리플레이 도구)는 화면이나 실행 흐름이 조금만 바뀌어도 깨져서, 작은 코드 단위를 코드로 검증하는 방향이 필요해졌다. Smalltalk용으로 등장한 SUnit은 테스트 케이스·단언·fixture·러너라는 구조를 패턴으로 정립했고, 이것이 JUnit을 거쳐 언어마다 이식되는 xUnit 계열의 뿌리가 되었다. 덕분에 자동화 테스트는 일상적인 개발 도구가 되었다. 하지만 테스트를 코드 작성 후에 붙이면 이미 설계가 굳어버린다는 문제가 남았다. TDD는 새로 발명된 기법이라기보다, 실패하는 테스트를 먼저 쓰고 최소 구현으로 통과시킨 뒤 리팩터링하는 오래된 방식을 재발견해 Red-Green-Refactor 리듬으로 체계화한 것이다. 다만 단위테스트가 모두 통과해도 '만들라고 한 것을 제대로 만들었는가'와 '옳은 것을 만들었는가'는 별개의 문제였고, 'test'라는 단어 자체가 검증의 초점을 흐린다는 문제의식도 있었다. 그래서 BDD는 이름을 의도적으로 'test'에서 'behavior'로 옮겼고, 이후 ATDD·인수테스트로 이어지며 테스트의 초점이 개발자 내부 구현에서 사용자의 행동과 실행 가능한 인수 기준으로 확장되었다.
```

2. 테스트의 종류(Unit, Integration, E2E)를 목적과 범위, 비용 대비 효용 관점으로 비교해 주세요. 'Unit은 왜 빠르고 저렴하며, E2E는 왜 느리고 비싸지만 어떤 가치를 주는가'에 답할 수 있어야 합니다.

```
테스트의 종류는 결국 '얼마나 넓은 범위를 확인하는가'로 갈린다. 그리고 이 범위가 비용과 효용을 동시에 결정한다.

단위테스트(Unit)는 한 객체나 함수를 외부 의존 없이 검증한다. DB도 네트워크도 없이 메모리 안에서 끝나므로 실행이 수 ms로 빠르고, 작성과 유지 비용도 낮다. 실패하면 원인이 그 좁은 범위 안에 있으니 진단도 즉각적이다. 대신 부분이 맞다고 전체가 맞다는 보장은 없다. 각 조각이 서로 연결될 때 생기는 문제는 잡지 못한다.

통합테스트(Integration)는 모듈과 실제 의존(DB, 외부 API 등)이 만나는 경계를 검증한다. 실제 I/O가 붙으므로 셋업·teardown 비용이 생기고 단위테스트보다 느리다. 그 대신 '내가 짠 코드가 실제 의존과 약속한 대로 주고받는가(계약)'를 확인해 준다. 단위테스트가 못 보는 연결 지점을 메우는 자리다.

E2E는 완제품을 사용자 관점에서 통째로 실행한다. 브라우저·네트워크·DB 전 스택을 깨우기 때문에 가장 느리고, 환경 의존성 탓에 간헐적으로 실패(flaky)하기 쉬우며, 실패해도 원인이 어디인지 넓어 진단 비용이 크다. 그럼에도 값어치가 있는 이유는, 실제 사용자가 밟는 경로가 처음부터 끝까지 작동한다는 '가장 진짜에 가까운 확신'을 주기 때문이다. 설정, 통합 지점, 실행 환경까지 포함해 검증하는 것은 E2E뿐이다.

정리하면 세 축이 같은 방향으로 움직인다. 범위가 넓어질수록 확신은 커지지만, 실행·유지·진단 비용도 함께 커진다. 그래서 좋은 전략은 셋 중 하나를 고르는 게 아니라, 확신 대비 비용이 가장 좋은 지점에 무게를 어떻게 배분할지의 문제가 된다.

```

3. 테스트 전략 모델 한 가지 이상(테스트 피라미드 또는 테스팅 트로피)을 리서치하고, '어떤 종류의 테스트에 집중해야 하는가'에 대한 본인 입장을 본인 언어로 정리해 주세요.

```
피라미드는 단위테스트를 많이 두고 E2E는 적게 둔다. 낮은 층일수록 빠르고 싸고 덜 깨지기 때문이다(속도·비용 최적화). 트로피는 통합테스트에 무게를 둔다. 실제 사용에 가까울수록 더 믿을 수 있기 때문이다(신뢰 최적화). 겉보기엔 "단위를 더 할까, 통합을 더 할까"의 선택처럼 보인다.

그런데 이 비교 자체가 어긋난다. 단위테스트는 로직을 재고, 통합테스트는 경계, 즉 외부 의존과의 접점을 잰다. 서로 다른 것을 재는데 "무엇을 더 하느냐"로 저울질하는 게 애초에 이상하다. 두 축이 같은 선 위에 있지 않다. 이 불일치는 설계로 풀린다. 단위와 통합의 비율은 고르는 게 아니라 경계를 어떻게 그었느냐에서 따라 나온다. 순수 로직을 어댑터 밖으로 밀어내면 그만큼 단위테스트로 싸게 덮이고, 외부 의존을 얇은 어댑터로 가두면 통합테스트는 그 얇은 층만 덮으면 된다(헥사고날). 만약 로직인데 통합테스트로 내몰린다면, 그건 전략의 문제가 아니라 경계를 잘못 그은 설계 신호다.

그래서 내 입장은, 어떤 테스트에 집중하느냐가 타입 선택이 아니라 설계 문제라는 것이다. 순수 로직은 단위테스트로 촘촘히 덮고, 외부 경계는 얇은 어댑터로 뽑아 그것만 통합테스트한다. 예를 들어 환불이라면 일할 계산 같은 순수 로직은 단위테스트, 단순 조회는 테스트하지 않고, 같은 주문이 두 번 환불되지 않도록 막는 유니크 제약·락이 실제로 작동하는지처럼 진실이 DB에 있는 부분만 실DB로 통합테스트한다. 결국 어떤 테스트에 집중할지는 아키텍처가 정한다.
```

4. 본인이 Phase 0에서 만든 validate 단계를 이 지형도 위에 올려놓아 보세요. 그것이 단위테스트였는지, 통합테스트였는지, 아니면 계약(contract) 검증이었는지 적어 주세요.

```
Phase 0의 validate는 각 단계가 다음 단계로 넘기는 JSON 산출물이 약속한 형식과
규약을 지켰는지 검사하는 게이트다. 스키마로 구조·필드를 확인하고, 같은
brief_hash·iteration에서 나온 게 맞는지, 남의 권한을 침범하지 않았는지를
본다. 통과하면 PASS, 아니면 REJECT로 멈춘다.

이건 테스트가 아니다. 테스트는 개발 시점에 내 코드가 맞는지 재는 도구지만,
validate는 런타임에 방금 생성된 산출물이 규약을 지켰는지 막는 가드다.
판정 대상이 '내 코드'가 아니라 '데이터'다.

경계에 앉아 있어서 통합테스트처럼 보이지만 그것도 아니다. 통합테스트는 실제 컴포넌트
둘을 붙여 돌려서 그 상호작용을 관찰하는데, validate는 옆 단계를 실행하지 않는다.
이미 만들어진 산출물 하나를 약속한 스키마·규약에 비춰볼 뿐이다. 컴포넌트를 통합해
돌려보는 게 아니라, 단계와 단계 사이 인터페이스가 지켜야 할 계약을 강제한다.

그래서 이건 계약 검증이다. 비결정적인 생산자(LLM)가 내놓은 출력을,
단계 간에 미리 합의한 계약(스키마·필드 규약·해시 일치·임계값)에 맞는지 결정론적
규칙으로 판정하는 자리다. 런타임에서 도는 가드라는 점에서 '테스트'보다 '검증'에 가깝다.
```

5. A-3에서 다룰 도메인에서 어느 부분을 단위테스트로, 어느 부분을 통합테스트로 검증할지 간단한 테스트 전략을 세워 주세요.

```
환불(구독 일할 환불) 도메인을 순수 로직과 경계로 나눠 배치한다.

단위테스트 — 외부 의존 없는 순수 도메인 로직. 일할 환불금 계산(남은 일수 비율 × 결제액에서 수수료 차감)을 첫날·마지막날·0일·반올림 경계 예제로 고정하고, 환불 가능 여부 판정(환불 기한 초과, 이미 환불됨)과 상태 전이(결제완료→환불완료, 이미 환불된 주문의 재환불 거부)를 검증한다. 이 계산·규칙은 Mock 없이 값으로 확인하며, 정답 예제는 내가 직접 만든다.

통합테스트 — 진실이 DB·트랜잭션에 있는 얇은 조각만. 첫째, 이중 환불 방지: 같은 주문에 환불을 두 번 저장하면 유니크 제약(또는 버전 락)이 두 번째를 거부하는지 확인한다. 단일 스레드 결정론적 테스트 하나면 되고 부하테스트가 아니다. 둘째, 원자성: 환불 이력 저장과 주문 상태 변경이 한 트랜잭션으로 묶여 중간 실패 시 둘 다 롤백되는지 확인한다. 유니크 제약·락·트랜잭션은 Mock이나 H2로 정확히 재현되지 않으므로 실제 DB(Testcontainers)로 확인한다.

테스트하지 않음 — 주문·회원 단순 조회(findById)처럼 로직 없는 조회는 프레임워크를 신뢰하고 통합테스트로 덮지 않는다.
```
