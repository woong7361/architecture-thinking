(Grit's Why): 여기가 테스트 사고의 가장 깊은 지점입니다. '상태를 검증할 것인가, 행위를 검증할 것인가'를 다룹니다. 이걸 모르면 가짜 객체(Mock)를 남발해 구현을 그대로 베낀, 리팩토링하면 다 깨지는 가짜 테스트를 만들게 됩니다.

### 수행 내용

1. 고전파 TDD(상태 기반, Mock에 보수적)와 런던파 TDD(행위 기반, Mock에 적극적)의 관점 차이를 본인 언어로 정리해 주세요. 각각이 테스트 용이성과 유연성 측면에서 갖는 장단점도 함께.
2. 가짜 객체(Mock, Stub)를 언제 쓰고 언제 쓰지 말아야 하는지 본인 기준을 세워 주세요. 외부 시스템(DB, 외부 API)과 순수 도메인 로직 중 어디에 가짜를 끼우는 것이 맞는지 근거를 적어 주세요.
3. 'Mock을 쓰면 안 되는 경우'를 하나 본인 코드 맥락으로 제시해 주세요. 값 객체나 순수 도메인 로직을 Mock으로 감싸면 무엇이 망가지는지 설명해 주세요.

> (개인화 포인트) 신뢰할 수 없는 검증은 형태만 다를 뿐 같은 병입니다. 가짜 객체에 너무 기대는 테스트는 구현이 조금만 바뀌어도 깨지고, 비결정적 평가는 같은 입력에 다른 답을 냅니다. 둘 다 '믿을 수 없는 게이트'입니다.
>
