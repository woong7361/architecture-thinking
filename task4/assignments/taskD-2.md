# Task D-2: 기술 에세이 (데이터 기반 4-Step)

(Grit's Why): 좋은 기술 글은 교과서 요약이 아니라 '문제를 어떻게 풀었나'의 서사입니다. 면접관은 '추정 → 소거 → 확신 → 검증'이 글에 드러날수록 그 사람의 논리력을 봅니다.

### 수행 내용

1. 1-1~1-3에서 본인이 실제로 한 작업 하나(예: 헥사고날로 어댑터 교체를 무수정으로 만든 일, 또는 인수테스트로 AI 코드를 판정한 일)를 골라, 4-Step으로 기술 에세이를 쓰세요. (1) 문제 정의 (2) 증거/관찰 (3) 대안 분석과 의사결정(왜 이 선택인가, 트레이드오프) (4) 검증.
2. 가능하면 Before/After를 정량(또는 구조 변화)으로 보여 주세요. 교과서식 개념 나열은 금지.
3. 초안을 완성하세요. D-5 하네스를 통과시킨 퇴고본을 발행하고 링크를 제출합니다.

### 4-Step 자가 점검 메모

**(1) 문제 정의 — 출발점은 분명하지만 두 문제의 연결은 약하다.** AI가 짠 코드를 내 인상으로 판정할 수 없다는 문제에서 시작했고, 반복해서 실행할 수 있는 게이트의 조건도 제시했다. 다만 생성한 테스트가 구현의 모양을 고정한다는 다음 문제와의 관계는 독자가 연결해야 한다. 결국 필요했던 것은 **구현의 모양은 고정하지 않으면서 반복해서 실행할 수 있는 판정 기준**이었다.

**(2) 증거와 관찰 — 실제로 확인한 결과를 충분히 보여줬다.** AI 평가가 놓친 실패 두 건, 생성된 테스트의 서로 다른 호출 방식, 리팩터링 뒤에도 남은 환불 정책, 18개 시나리오의 실행 결과를 글에 담았다. 다만 테스트를 고치기 어려워질 수 있다는 점과 AI가 만든 기준이 구현에 끌려갈 수 있다는 위험은 직접 확인한 결과가 아니라 내가 예상한 부분이다. 이를 더 구체적으로 보았으면 좋았을것 같다.

**(3) 대안 분석과 의사결정 — 대안은 보이지만 선택 과정은 약하게 드러난다.** AI에게 직접 묻는 방법, 생성한 테스트 코드를 실행하는 방법, 승인한 도메인 명세를 실행하는 방법을 비교하고 각각의 비용도 적었다. 그러나 채택안을 먼저 설명하고 버린 안을 나중에 제시해, 같은 기준으로 저울질해 선택한 순간보다 결론을 사후에 정리한 모습에 가깝다.

**(4) 검증 — 결함을 직접 넣어 테스트가 실패하는 데까지 확인했다.** 동결한 18개 시나리오는 새 구현에서 빠진 정책 두 건을 드러냈다. 무료 환불 기준을 7일에서 6일로 바꾸자 해당 시나리오가 추가로 실패했고, 구현을 복원하자 원래 결과로 돌아왔다. 한 규칙만 시험했다는 한계는 있지만, 계획에 그치지 않고 테스트가 실제 결함을 잡는지 확인했다는 점에서 검증은 있다.
