# Task D-4: 스피치 &amp; 딜리버리 (GritTalk 프리퀄)

(Grit's Why): 글로 정리한 것을 말로도 꺼낼 수 있어야 진짜 본인 것입니다. 면접과 발표는 결국 '짧은 시간에 핵심을 전달하는' 같은 근육입니다.

### 수행 내용

1. 기본기 3주(테스트/OOP/헥사고날) 중 하나를 3~5분 오디오 또는 영상으로 스스로 설명해 녹화하세요. 대본을 외워 읽지 말고, 설명 구조(도입-핵심-예시-마무리)를 잡아서 말하세요.
2. 1분 엘리베이터 피치를 따로 만드세요: '나는 어떤 문제를 푸는 백엔드 개발자인가'를 1분 안에.
3. 녹화를 본인이 다시 보고, 공감대를 만드는 프레이밍(청자가 왜 들어야 하는지)이 도입에 있는지 점검하세요. (가능하면 D-2 기술 에세이와 다른 각도로: 글이 '무엇을 어떻게'였다면 말은 '왜 그게 중요한지'를 청자 눈높이로.)
4. 위 설명을 녹화한 뒤, 본인 AI에게 그 내용을 주고 시니어가 던질 법한 꼬리질문 2개를 뽑아달라고 하세요. 그다음 대본이나 노트 없이 그 질문에 즉석으로 답하는 모습을 한 번 더 짧게 녹화하세요. 막히는 질문이 있으면 그게 아직 말로는 안 꺼내지는 지점입니다. 그 질문과 다시 정리한 답을 적어 주세요.

### 제출물

- [ ] 3~5분 스피치 녹화 링크 + 1분 엘리베이터 피치 스크립트.
- [x] 녹화 자가 점검(설명 구조/공감대 프레이밍 관점). (최소 300자)
- [x] 꼬리질문 2개와 무대본 답변 녹화. 막혔던 질문 1개와 다시 정리한 답.

### 2. 녹화 자가 점검

이 절은 두 부분이다. 앞은 녹음을 다시 들으며 내가 직접 느낀 점이고, 뒤는 전사 타임스탬프로 계산한 수치다.

#### AI 시대의 테스트 — 다시 들으며 점검한 것

**1. 말을 많이 전다.** 문장 중간에 말을 더듬는 지점이 반복해서 나온다. 내용을 몰라서가 아니라 다음 문장을 고르기 전에 입이 먼저 나가서 생기는 것으로 보인다. 연습이 많이 필요하다.

**2. 너무 단정적으로 말한다.** 다른 정답이 있을 수 있는 지점인데도 `이렇게 되는 것은 옳지 않습니다`처럼 확정적으로 끝낸다. 내 판단이 유일한 답인 것처럼 들린다. 어떤 조건에서 그렇게 판단했는지를 함께 말하고, 다른 선택지가 가능한 지점은 그렇게 말해야 한다.

**3. 생각이 실시간으로 정리되지 않는다.** 대본 없이 말하다 보니 머릿속 정리가 끝나기 전에 문장이 시작된다. 그래서 한 문장에 판단이 여러 개 붙고 문장이 길어진다. 말하면서 동시에 구조를 잡는 능력이 필요하다.

**4. 하나의 화제가 드리프트된다.** 서론에서 핵심, 결론으로 하나의 화제를 이어가야 하는데 말을 해나가는 사이에 화제가 조금씩 옆으로 밀린다. 대본이 없으니 말을 해나가면서 생각한 결론이 있었는데, 중간 사례를 지나는 동안 그 결론에서 점점 멀어졌다. 그래서 마지막에 결론을 내리는 것이 힘들었고, 처음 잡았던 결론과 실제로 말한 결론이 완전히 같지는 않다.

네 가지는 따로가 아니다. 실시간 정리가 안 되니(3) 말을 더듬고(1), 정리되지 않은 상태에서 문장을 닫으려니 단정적인 어미로 끊어버리고(2), 그 결과 화제가 드리프트된다(4). 다음 녹음에서는 대본을 외우는 대신 서론·핵심·결론 세 문장만 먼저 고정해 두고, 사례를 하나 말할 때마다 그 세 문장으로 돌아오는 방식으로 연습한다.

#### 구간별 속도와 수치

`AI 시대의 테스트`는 전체 311.6초, 공백 기준 446토큰, 분당 85.87이었다. 내용 블록별로 묶으면 다음과 같다.


| 블록                     | 시간       | 블록 평균(분당 토큰) | 블록 내 최저–최고 |
| ---------------------- | -------- | ------------ | ---------- |
| 도입(경험 제시 → 핵심 질문)      | 0–59초    | 92.5         | 66.7–150   |
| 문제 제기(테스트가 없다면)        | 59–120초  | 85.6         | 60–150     |
| 사례 비교(AI 검토 vs 인수 테스트) | 120–193초 | 88.8         | 60–120     |
| 반례(초록인데 규칙이 틀린 경우)     | 195–236초 | 74.6         | 60–90      |
| 결론                     | 236–260초 | 90.0         | 60–110     |
| 행동 제안과 마무리             | 261–311초 | 87.6         | 60–150     |


블록 평균은 74.6에서 92.5 사이로 비교적 고르다. 문제는 블록 안이다. 개별 구간은 60에서 150까지 2.5배 차이가 난다. 32–36초 `이거 진짜 괜찮아 라고 다시 한 번 검토를 하게 됩니다`가 150인 반면, 68–81초 `AI의 판정, AI가 위험도 2개...`는 60이다. 마지막도 300–304초에서 150으로 몰아붙이다가 304–311초 마지막 문장에서 60으로 떨어진다. 위 자가 점검의 (1)(3)과 같은 지점이다. 정리가 된 문장은 빠르게 지나가고, 정리가 덜 된 문장은 늘어진다.

필러는 전사에서 `한번` 4회, `이제` 2회가 확정됐다. 빈도 자체는 크지 않지만 도입과 전환에 몰려 있어 문장 시작을 약하게 만든다.

`1분 엘리베이터 피치`는 전체 66.7초, 110토큰, 분당 98.9였고 필러는 `한번` 1회였다.


| 블록         | 시간     | 구간별 분당 토큰        |
| ---------- | ------ | ---------------- |
| 도입 정의      | 0–12초  | 72 → 111.4       |
| 로컬 브레인 사례  | 12–30초 | 100 / 60 / 112.5 |
| 콘텐츠 자동화 사례 | 30–45초 | 96 / 105 / 90    |
| 테니스 코트 사례  | 45–57초 | 120 / 120        |
| 마무리        | 57–66초 | 120 → 80         |


45초부터 60초까지 세 구간이 연속으로 120이다. 테니스 코트 사례와 결론 진입이 한 호흡에 붙어 빨라졌고, 마지막 문장에서만 80으로 떨어진다. 사례 사이와 마지막 `저는` 앞에서 멈추는 연습이 필요하다.

이 수치는 전사 텍스트와 세그먼트 타임스탬프만으로 계산했다. 음높이, 음량, 억양, 정확한 무음 길이는 측정하지 않았고, 자동 전사가 놓친 필러나 더듬은 지점은 집계되지 않았다. 위 자가 점검 (1)의 더듬음은 수치가 아니라 녹음을 직접 들으며 확인한 것이다.

##### 자동 전사 원문

> 테스트가 항상 같은 결과를 낸다고 했는데 시간, 안수, 동시성, 데이터베이스, 웹, API 같이 비결정적 요소는 어떻게 통제했나요에 대한 질문에 대한 답변입니다.
>
> 보통 웹 요소 같은 경우 경리를 해서 코어 비즈니스 명역만 따로 인수 테스트로 진행을 하고요.
>
> 이런 외부 같은 경우 따로 통합 테스트나 그런 것들을 통해 진행하고 그것들이 아닌 경우 정말 통째로 이제 미디처럼 유저플로우를 테스트하고 싶다라고 한다면 이제 데이터베이스들 같은 경우에는 이제 테스트 데이터베이스 같은 걸 어프치기도 하고
>
> 그리고 외부 API 같은 경우 그런 응답, 리퀘스트 리스펀스를 흉내는 아예 목서버를 두고 아예 통합으로 검증을 진행하기도 합니다.
>
> 그리고 동시성의 경우, 앤수나 동시성의 경우 이런 특수한 그런 케이스이기 때문에 그런 것들을 이제 단위 테스트나 혹은 인수 테스트에서 여러 번 테스트를 하거나 특별한 케이스 테스트 슈트를 만들어서 진행합니다.
>
> 그리고 이번 팀이 합의한 테스트 규칙 자체가 올바른 지는 누가 어떤 근거에 절차로 점증하는 가에 대한 질문에 대한 답변인데요.
>
> 사실 테스트는 누가 이제 올바르다 올바르지 않다 그런 게 아니라 이제 팀이 어떤 이런 테스트가 있었겠다 혹은 괜히 어떤 이런 테스트가 계약이라고 하죠. 내가 이런 응답을 줬을 때 이러한 응답이 왔으면 좋겠다 혹은 이러한 것을 설정했을 때 이러한 것들이 돌아와야 된다라는 그런 계약의 의거에서 팀이나 혹은 그런 개인이 답하는 계약을 그렇게 진행을 하는 거기 때문에 올바른지 어떤지는 이제 팀이 결정한다고 볼 수 있겠습니다.

`안수`, `경리를`, `명역만`, `미디처럼`, `어프치기도`, `앤수나`, `점증하는`은 자동 전사 오류일 가능성이 있다. 원래 발화는 녹음을 다시 들으며 확인해야 하므로 원문에서는 임의로 고치지 않았다.

#### 답변 점검

전체 속도는 공백 기준 분당 92.64토큰이었다. 전사에서 필러로 확정된 `이제`는 7회였다. 첫 답변에서는 데이터베이스, 외부 API, 동시성 사례가 정리 문장 없이 이어졌고 `이런`, `그런`, `경우`처럼 참조 범위가 넓은 표현이 반복됐다. 그래서 청중이 사례를 직접 묶어 핵심 원칙을 추론해야 한다. 다음에는 질문을 그대로 다시 읽기보다 결론을 먼저 한 문장으로 말하고, 범주명을 전환어로 사용해 한 범주를 한 문장씩 끝낸다.

내용 측면에서 데이터베이스에는 테스트 데이터베이스, 외부 API에는 목 서버를 사용한다고 답했다. 하지만 무엇을 고정했고 같은 결과가 나오는지 어떻게 확인했는지는 말하지 않았다. 2번 질문에서는 테스트를 팀이 합의한 계약이라고 설명했지만, 질문이 요구한 근거와 검증 절차 대신 `팀이 결정한다`는 결론으로 끝났다. 요구사항, 사용자 시나리오, 운영 중 발견된 결함 같은 근거와 계약을 제안·검토·수정하는 주체를 구분할 필요가 있다.

#### 가장 막혔던 질문

1번 질문에서 시간은 실제로 답하지 못했다. 난수와 동시성은 `여러 번 테스트한다`, `특별한 테스트 스위트를 만든다`고 답했지만 이는 비결정성을 없애는 통제가 아니라 간헐적인 실패를 발견할 가능성을 높이는 탐지에 가깝다. 질문의 핵심인 `같은 조건을 어떻게 재현하는가`에 답하려면 통제와 탐지를 먼저 구분해야 한다.

#### 답변 구성 선택지

- **원칙과 대표 요소를 연결하는 방식:** 통제와 탐지의 차이를 먼저 밝히고 시간·난수·동시성을 각각 설명한다. 질문에서 막힌 지점을 직접 보완하면서도 답변 길이를 관리할 수 있어 다음 녹음에 가장 적합하다.
- **모든 요소를 차례로 설명하는 방식:** 시간·난수·동시성·데이터베이스·외부 API를 모두 같은 깊이로 다룬다. 빠짐은 적지만 무대본 답변이 다시 길어지고 사례 나열로 흐를 가능성이 크다.
- **실제 사례 하나를 깊게 설명하는 방식:** 가장 경험이 많은 사례에서 무엇을 고정했고 어떻게 검증했는지 보여준다. 구체성과 신뢰도는 높지만 질문에 포함된 다른 비결정적 요소에는 답하지 못한다.

#### 어떻게 보완할 것인가

답변을 `원칙 → 요소별 통제 → 통제할 수 없는 부분의 탐지` 순서로 말한다.

1. **원칙:** 테스트가 저절로 같은 결과를 내는 것은 아니다. 입력과 외부 의존성, 실행 환경을 같은 조건으로 만들었을 때 정해진 범위에서 반복 가능한 판정이 된다.
2. **시간:** 현재 시간을 직접 읽지 않고 시간 제공자를 주입한다. 테스트에서는 고정된 시각을 반환하게 해 만료 전후 같은 경계 조건을 재현한다.
3. **난수:** 난수 생성기를 주입하고 고정된 시드나 미리 정한 값의 순서를 사용한다. 무작위 탐색 테스트에서 실패했다면 시드를 기록해 같은 실패를 다시 실행할 수 있게 한다.
4. **동시성:** 모든 스케줄을 완전히 고정할 수 있다고 말하지 않는다. 배리어나 래치처럼 실행 지점을 맞추는 장치로 검증하려는 경쟁 조건을 만들고, 특정 실행 순서보다 중복 처리 방지나 최종 상태 같은 불변 조건을 검증한다.
5. **탐지:** 반복 실행과 스트레스 테스트는 남은 경쟁 조건을 발견하는 보조 수단으로 둔다. 이것을 결정성을 보장하는 통제라고 표현하지 않는다.
6. **데이터베이스와 외부 API:** 테스트마다 초기 데이터를 고정하고 상태를 격리한다. 외부 API는 고정 응답을 반환하는 대역으로 코어 흐름을 검증하되, 실제 연동과의 차이는 별도의 계약 테스트와 통합 테스트로 확인한다.

#### 다시 정리한 답

`테스트가 항상 같은 결과를 낸다`고 단정한 것은 범위가 너무 넓었습니다. 제가 말하려던 것은 비결정적 요소를 경계 밖으로 격리하거나 같은 조건으로 제어한 테스트는 반복 가능한 판정이 된다는 뜻입니다. 시간은 시간 제공자를 주입해 테스트에서 시각을 고정하고, 난수는 생성기와 시드를 주입해 같은 값의 순서를 재현합니다. 동시성은 모든 실행 순서를 완전히 고정하기 어려우므로 실행 지점을 맞춘 뒤 중복 처리 방지나 최종 상태 같은 불변 조건을 검증합니다. 반복 실행과 스트레스 테스트는 남은 문제를 발견하는 수단이지 결정성을 보장하는 수단은 아닙니다. 데이터베이스는 초기 상태를 격리하고, 외부 API는 고정된 대역으로 코어 흐름을 검증한 뒤 실제 연동은 별도의 계약 테스트와 통합 테스트로 확인합니다.
