# Task D-3: 성장 에세이 (설계의 언어화)

(Grit's Why): 기술 에세이가 '무엇을 했나'라면, 성장 에세이는 '그 3주에 내 사고가 어떻게 바뀌었나'입니다. 발행되지 않은 사고는 존재하지 않습니다.

### 수행 내용

1. 1-1~1-3을 지나며 '왜'를 3겹 이상 파고든 지점 하나를 골라, 사고 전환을 성장 에세이로 쓰세요. (예: '테스트는 귀찮은 것' → '테스트는 AI 코드를 판정하는 게이트'로 바뀐 과정.)
2. 회고에 본인만의 성장 정의를 담으세요. 무엇을 어디까지 했고, 다음에 무엇을 더 할지.
3. 초안을 완성하세요. D-5 하네스를 통과시킨 퇴고본을 발행하고 링크를 제출합니다.

### 제출물

- [ ] 발행된 성장 에세이 링크 + 사고가 바뀐 지점을 짚은 메모. (최소 300자)

### 사고가 바뀐 지점 (메모)

나는 반복되는 작업을 어디까지 자동화할 수 있을지 고민했다. AI에게 묻고 코드를 작성하게 했지만 결과를 그대로 믿지는 못했다. 결국 내가 다시 자료를 찾고 레퍼런스와 대조했다. 처음에는 AI의 답이 더 정확해지면 해결될 문제라고 생각했다. 하지만 같은 코드를 두 번 평가시켰을 때 지적의 개수와 심각도가 달라지는 것을 보고, 문제는 결과를 만드는 능력보다 그 결과를 판정하는 방식에 있다고 생각하게 됐다.

그래서 결정적인 판정과 정성적·정량적 평가의 차이를 찾아보고, 판정을 어디까지 자동화할 수 있는지 밀어봤다. 코드 자체에 하나의 정답이 있는 것은 아니었다. 다만 테스트 결과, 형식, 금지 규칙처럼 기준을 실행 가능한 규칙으로 고정할 수 있는 부분은 기계에 넘길 수 있었다. 주관적인 품질은 채점표를 통해 평가 항목과 출력 형식을 맞출 수 있었지만, 숫자로 표현했다고 같은 답이 보장되지는 않았다. 채점표의 통과는 최종 승인이 아니라 사람이 검토할 후보가 됐다는 뜻으로만 읽어야 했다.

이 과정에서 내 자리에 대한 생각도 바뀌었다. 결정적으로 만들 수 없는 모든 곳에 내가 서 있어야 하는 것은 아니었다. 정해진 기준을 적용하고, 후보를 만들고, 실패를 반영해 고치는 일은 AI에게 더 넘길 수 있었다. 내가 개입해야 할 때는 무엇을 좋은 결과로 볼지 아직 정하지 못했을 때, 기존 기준을 바꿔야 할 때, 그리고 비결정적 판정을 거친 후보를 최종 승인할 때였다. 질문은 "어떤 일을 AI에게서 지켜야 하는가"에서 "어디에 내가 개입해야 결과의 가치가 달라지는가"로 바뀌었다.
