# 헥사고날 컨벤션 (ticket-reservation)

이 프로젝트에서 코드를 만들거나 고칠 때 지켜야 하는 규약이다. 레이어 단위 작업 시 컨텍스트로 주어진다.

규칙은 임의로 정한 것이 아니라 이 저장소에 이미 있는 판단에서 끌어왔다. 각 절 끝에 출처를 적었다.

## 1. 무엇을 지키려는 것인가

헥사고날의 핵심은 육각형 모양이 아니라 **안쪽과 바깥쪽이 대화하는 경계를 명시하는 것**이다.
안쪽은 업무 규칙과 유스케이스, 바깥쪽은 HTTP·DB·메시지 브로커 같은 기술이다.
판정 기준은 하나다 — **UI와 DB 없이 업무 규칙을 실행하고 테스트할 수 있는가.**

이 구조가 변경을 없애 주지는 않는다. **기술 변경이 업무 정책으로 번지는 범위를 줄일 뿐이다.**
Port의 계약이 바뀌거나 업무 규칙이 바뀌면 Core도 바뀐다. 그건 실패가 아니라 정상이다.

> 출처: `task3/assignments/taskC-1.md` 답안 3 — Cockburn 원문 해석

## 2. 구조와 의존 방향

```
com.thinking.ticket
├─ core                      ← 안쪽. 기술을 모른다
│  ├─ domain                 업무 규칙. 상태와 불변식을 스스로 소유
│  ├─ application            유스케이스. 규칙들을 엮는 순서를 소유
│  └─ port
│     ├─ in                  Core가 바깥에 제공하는 계약
│     └─ out                 Core가 바깥에 요구하는 계약
├─ adapter                   ← 바깥. 기술 세부
│  ├─ in                     외부 표현을 Command로 번역
│  └─ out                    Outbound Port를 특정 기술로 구현
└─ config                    조립 지점
```

**의존은 항상 안쪽을 향한다.** `adapter → port → core`. Core는 어떤 Adapter도 import하지 않는다.

**소스 코드 의존 방향과 실행 순서는 다른 개념이다.** 런타임에는 Application이 주입된 Adapter를
호출하지만, 소스 코드에서는 Adapter가 Core의 Port를 구현한다. 화살표를 뒤집는 것이 DIP다.

> 출처: `taskC-1.md` "DIP로 의존 방향을 뒤집는다" · `taskC-3.md` 목표 헥사고날 설계

## 3. 규칙은 Domain에, 절차는 Application에

Core는 두 겹이다. 이 구분이 흐려지면 Application이 비대해지고 Domain이 빈약해진다.

| | 소유하는 것 | 예 |
|---|---|---|
| `core/domain` | **판단과 상태 전이** — 예약 가능한가, 할인 후 금액은 얼마인가 | 불변식 검사, 상태 전이, 값 계산 |
| `core/application` | **순서** — 조회하고, 도메인에 판단을 위임하고, 결제를 요청하고, 저장한다 | 포트 호출 순서, 결과 조립 |

Application은 **판단하지 않는다.** 조건 분기로 업무 규칙을 흉내내고 있다면 그 규칙은 Domain으로 가야 한다.

> 출처: `taskC-3.md` — "규칙 자체는 Domain에, 규칙을 엮는 절차는 Application에 둔다"

## 4. Port는 업무 언어로 쓴다

Port를 인터페이스로 쓴다는 것이 본질이 아니다. 본질은 **계약의 소유권과 사용하는 언어**다.

- Port는 `HttpServletRequest`, `JpaEntity`, `saveAndFlush` 같은 기술 세부가 아니라
  `ReserveTicketCommand`, `Ticket`, `save`처럼 **유스케이스에 필요한 업무 개념**을 쓴다.
- **Inbound Port는 Core가 제공하는 계약**이고, **Outbound Port는 Core가 요구하는 계약**이다.
  방향은 다르지만 **둘 다 Core가 소유하고 정의한다.**
- Outbound Port는 "무엇이 필요한가"만 드러내고 "어떻게 하는가"는 모른다.
  저장 계약은 저장 기술을 몰라야 한다.

> 출처: `taskC-1.md` 답안 3 · `taskC-3.md` Port 설명

## 5. Domain 모델과 영속 모델은 분리한다

이 프로젝트는 분리를 택했다. 따라서 **도메인 객체와 영속 모델은 다른 클래스이고, 변환은 Outbound
Adapter 안에서 일어난다.** Core에는 순수 도메인 객체만 오간다.

분리 자체가 항상 옳아서가 아니다. 보호할 업무 규칙이 있고(D), 그 규칙의 테스트나 변경 격리가
영속 기술 때문에 깨질 때(P) 분리한다. 이 프로젝트는 예약 불변식과 상태 전이를 가지므로 그 기준을 만족한다.

**분리를 택한 이상 그 대가도 지킨다** — 도메인 객체에 영속 애노테이션을 붙이지 않고,
Core Port가 영속 타입을 노출하지 않는다.

> 출처: `task3/assignments/taskC-2.md` "나의 기준" (D·P 판단)

## 6. 금지 규칙

**import 금지** — `HexagonalBoundaryTest`가 자동으로 검사한다. 위반하면 빌드가 실패한다.

- `core/**` → `com.thinking.ticket.adapter.**` : 의존 방향 역전
- `core/**` → `org.springframework.**` : 프레임워크 침투
- `core/**` → `jakarta.persistence.**`, `org.hibernate.**` : 영속 기술 침투
- `adapter/in/**` → `adapter/out/**` : 유스케이스를 건너뛴 우회 경로

**경로 금지**

- 지정받은 작업 범위 밖의 파일을 만들거나 고치지 않는다.
- `src/test/**` 는 어떤 이유로도 수정하지 않는다. 테스트는 심판이다.

## 7. 계약을 바꾸고 싶을 때

Port 시그니처가 불편하더라도 **직접 바꾸지 않는다.** 바꿔야 한다고 판단하면 고치는 대신 이유를 보고한다.

Port는 여러 Adapter와 여러 테스트 구성이 함께 의존하는 계약이라, 한쪽 사정으로 바꾸면 다른 쪽이
조용히 깨진다. 계약 변경은 사람의 판단 영역이다.

## 8. 테스트는 심판이다

- 인수 시나리오와 스텝 정의는 요구사항의 고정된 표현이다. 통과시키려고 고치지 않는다.
- 테스트가 빨간불이면 프로덕션 코드를 고친다. 반대가 아니다.
- 심판이 요구하는 타입 이름·스키마 이름·프로토콜 계약은 별도로 전달된다. 그 이름을 정확히 따른다.
- **Gherkin의 `When` 한 문장은 Inbound Port 메서드 하나와 1:1로 대응한다.**

> 출처: `taskC-3.md` "When ↔ Inbound Port 1:1 매핑"

## 9. 코드 관례

- 생성자 주입만 사용한다. 필드 주입·세터 주입을 쓰지 않는다.
- DTO는 `record`로 만든다.
- **도메인 객체에 public setter를 만들지 않는다.** 상태 변경은 의미 있는 이름의 전이 메서드로 한다.
  객체는 스스로 불변식을 지키는 자율적인 존재여야 하고, 캡슐화가 변경 용이성을 만든다.
- 예외는 도메인 예외 타입으로 던진다. 프로토콜 응답으로의 번역은 Inbound Adapter가 한다.
- 주석은 한글로 `/* ... */` 형식. **무엇을 하는지가 아니라 왜 그렇게 했는지**를 남긴다.
- **새 추상화를 임의로 추가하지 않는다.** 교체 축이 실제로 둘 이상일 때만 인터페이스를 만든다.
  자율성을 올리면 의존성도 함께 올라갈 수 있다 — 전부 트레이드오프다.
