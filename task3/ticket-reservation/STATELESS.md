# Stateless 설계 메모 — 무엇을 왜 외부화했는가 (Task C-4 제출물 3)

## 한 줄 정의

"상태 외부화"는 **서버를 여러 개 띄우는 것**이 아니라, **앱 프로세스가 요청과 요청 사이에 상태를 들고 있지 않게 만드는 것**이다. 그 빼낸 상태를 담을 곳(백킹 서비스)이 별도 컨테이너로 뜨는 것은 결과일 뿐이다. 그래서 별도로 뜨는 컨테이너가 전부 "외부화된 상태"인 것도 아니다 — 이 프로젝트에서 컨테이너가 갈라지는 이유는 **두 개의 서로 다른 축**이다.

## 축 A — 상태 외부화: 예약/티켓/회원 데이터 → MySQL

| 무엇 | 어디로 | 왜 |
| --- | --- | --- |
| 티켓의 예약 여부·소유자, 회원, 예약 결과 | **MySQL 컨테이너(`db`)** | 리팩토링 전에는 이 상태가 앱 메모리(in-memory Map)에 있었다. 앱이 상태를 들고 있으면 인스턴스마다 데이터가 갈라져 **수평 확장 자체가 성립하지 않는다.** 상태를 앱 밖의 단일 진실원(SoR)으로 빼야 어느 인스턴스가 어떤 요청을 받아도 같은 데이터를 본다. |
| 설정·비밀(DB 접속 정보, PG 주소) | **환경변수(`.env`)** | 코드/이미지에 값을 박지 않는다(12-factor config). 이미지 1개를 환경만 바꿔 dev/운영에 재사용한다. |
| HTTP 세션 | **(만들지 않음)** | 세션 상태를 앱에 두지 않으므로 sticky session도, 세션 저장용 Redis도 필요 없다. "무상태"를 애초에 상태를 만들지 않는 방식으로 달성했다. |

`db`는 stateful이라 함부로 복제할 수 없다 — **scale-out 대상이 아니라 단일 진실원**이다.

## 축 B — 외부 의존 격리: 결제사(PG) → Mock 서버

`mock-pg`(WireMock 컨테이너)는 **상태 외부화가 아니다.** 결제사는 원래부터 우리 시스템 밖의 서버이고, 로컬/재현 환경에서 진짜 PG를 호출할 수 없으니 **가짜로 대체해 띄운 것**이다. 우리 앱의 결제 아웃바운드 어댑터(`PaymentHttpAdapter`)가 `ChargePort`(Outbound Port)를 구현해 이 mock 서버를 HTTP로 호출한다. 진짜 PG로 바꿔도 이 어댑터만 교체되고 Core는 무수정이다 — 헥사고날의 "어댑터 교체" 논지를 실물로 증명하는 장치다.

## 무상태 앱과 수평 확장(scale-out)

축 A 덕분에 앱(`app`)은 로컬 상태가 0이다. 따라서 **동일 이미지를 여러 개 띄워도** 모두 같은 MySQL을 보고 아무 인스턴스나 아무 요청을 처리할 수 있다.

```
docker compose -f docker-compose.yml -f docker-compose.scale.yml up -d --scale app=3
```

세 인스턴스가 같은 `db`/`mock-pg` 를 공유하며 각자 독립적으로 뜬다.

### 무상태만으로는 부족한 지점 — 정합성 가드

무상태라고 정합성이 저절로 보장되지는 않는다. 인스턴스 2개가 **같은 티켓을 동시에** 예약하면 이중 예약이 날 수 있다. 그래서 예약 확정을 DB의 **단일 원자 UPDATE**로 처리한다(`TicketJpaRepository.reserveIfFree`):

```sql
UPDATE tickets SET reserved = true, user_id = ?
WHERE id = ? AND reserved = false AND suspended = false
```

`WHERE reserved = false` 조건이 이중 예약을 DB 계층에서 막는다 — 여러 인스턴스가 동시에 시도해도 실제로 행을 바꾸는 건 **정확히 하나**뿐이고, 영향 행 수 0이면 충돌로 판정해 `409 Conflict`를 돌려준다. 이것이 "무상태 + 수평 확장이 안전하다"는 주장을 참으로 만드는 최소 장치다.

> 남은 quirk(범위 밖): 경합에서 진 요청이 이미 결제를 청구했다면 그 결제의 보상(취소)은 이 skeleton에서 다루지 않는다. 이는 기존 안전망이 박제한 "결제 후 실패 시 보상 없음" quirk와 같은 성질이며, 보상/재시도는 C-5의 몫이다.

## 왜 cache/queue를 넣지 않았나

과제는 "필요 시" cache/queue를 허용하지만, 이 walking skeleton에는 **정당화할 변경 축이 없다.** 세션이 없어 세션 캐시가 불필요하고, 예매는 동기 요청-응답으로 충분해 비동기 큐가 필요 없다. 근거 없는 인프라 추가는 과설계이므로 MySQL + mock-pg 로 최소화했다(필요가 확정되면 그때 도입).

## 헬스 체크로 정상 기동 확인

- 엔드포인트: `GET /actuator/health` (Spring Boot Actuator). `db` 헬스 인디케이터가 포함되어 **DB 연결까지** 검사한다 → `{"status":"UP","components":{"db":{"status":"UP"},...}}`.
- compose 레벨: `app`은 이 엔드포인트를 `curl -f` 로 헬스체크하고, `db`가 `service_healthy` 된 뒤에만 기동한다. `docker compose ps` 의 `STATUS` 가 `healthy` 로 뜨면 정상 기동이다.
