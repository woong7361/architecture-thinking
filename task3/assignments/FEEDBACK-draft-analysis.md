# Station 1-3 피드백 답변 후보 분석

전체 디스커션 16건 중 실질 피드백이 있는 13개 스레드를 분석했다. 본문 없는 리액션 3건은 제외했다. 페이지 총평 한 스레드에는 서로 다른 질문 세 개가 있어 한 섹션 안에서 쟁점을 나누었다.

## FB-C0-01 · Core 경계를 더 나눌 시점

**원문 앵커**: `taskC-0.md` L24 · Core가 바깥 기술을 모른 채 유스케이스를 유지해야 한다는 주장

### 내가 주장한 내용

헥사고날의 핵심은 레이어 이름이 아니라 Core와 외부 기술 사이의 의존 방향이다. 다만 현재 답안은 Core 내부의 업무 경계를 언제 더 나눌지는 다루지 않았다.

### 피드백이 날아온 내용

티켓 예매보다 큰 시스템에서 Core 경계를 하나 더 그어야 한다는 관찰 가능한 신호를 구체화해 달라는 질문이다.

### 답변·변론 후보

1. **추천 · 언어와 변화의 불일치를 근거로 점진적으로 분리한다**: 같은 용어가 문맥마다 다른 뜻을 갖거나, 규칙·데이터·변경 주기·담당자가 따로 움직이는데 한 모델 때문에 함께 수정하고 배포해야 할 때 경계 후보로 본다. 먼저 같은 배포 단위 안의 모듈로 나누고 독립 배포 필요가 확인될 때 서비스로 분리한다.
   - **트레이드오프**: 조기 분산 시스템 비용을 피하면서 실제 변화 증거를 사용할 수 있다. 대신 분리 신호를 늦게 알아차리면 한동안 결합 비용을 감수해야 한다.

2. **팀과 운영 소유권을 먼저 기준으로 분리한다**: 독립된 팀, 데이터 소유권, 가용성 목표가 생기는 순간 별도 경계를 만든다.
   - **트레이드오프**: 책임과 장애 범위가 선명해진다. 업무 언어가 아직 충분히 갈라지지 않았다면 네트워크 호출과 분산 정합성만 늘어날 수 있다.

## FB-C0-02 · Core 계약과 인프라 현실이 충돌할 때

**원문 앵커**: `taskC-0.md` L26 · Core가 필요한 능력을 자기 언어의 Port로 정의한다는 주장

### 내가 주장한 내용

Port의 소유자는 Core이며 Adapter가 그 계약을 구현해야 한다. 원래 주장은 인프라가 계약을 완전하게 제공하지 못하거나 구현 비용이 과도한 경우까지 다루지는 않았다.

### 피드백이 날아온 내용

Core 계약을 현실에 맞춰 바꿀지, Adapter가 성능과 복잡도를 감수하면서 계약을 지킬지 판단 기준을 묻는다.

### 답변·변론 후보

1. **추천 · 업무 의미와 기술 편의를 구분한다**: 업무상 반드시 지켜야 하는 의미는 Core 계약에 남기고 페이지네이션, 재시도, 프로토콜 변환 같은 기술 차이는 Adapter가 흡수한다. 다만 요구 성능이나 일관성을 현실적으로 제공할 수 없다면 그 제약을 숨기지 않고 비동기 처리나 부분 결과처럼 유스케이스 계약에 명시한다.
   - **트레이드오프**: Core가 거짓 약속을 하지 않으면서도 기술 세부의 누수를 막는다. 어디까지가 업무 제약인지 합의하는 비용이 필요하다.

2. **Adapter가 계약을 항상 보존한다**: Core는 이상적인 계약을 유지하고 Adapter가 캐시, 병렬 조회, 추가 저장소로 부족한 기능을 보완한다.
   - **트레이드오프**: Core는 단순하고 안정적이다. 보완 비용과 장애 지점이 Adapter에 쌓이고 성능 목표를 못 맞출 위험이 있다.

## FB-C0-05 · Walking skeleton 다음 기능의 우선순위

**원문 앵커**: `taskC-0.md` L34 · 실제 HTTP부터 DB까지 통과하는 가장 얇은 경로를 만들었다는 주장

### 내가 주장한 내용

Walking skeleton은 기능 수보다 실제 경로를 먼저 검증하는 골격이다. 그 위에 어떤 기능부터 붙일지는 정하지 않았다.

### 피드백이 날아온 내용

골격 다음에 기능을 확장할 때 무엇을 우선해야 하는지 묻는다.

### 답변·변론 후보

1. **추천 · 가장 큰 미검증 위험을 세로 조각으로 추가한다**: 결제 Adapter가 자동 판정에서 빠졌던 경험을 근거로 실제 PG 계약, 타임아웃, 중복 요청, 결제 후 저장 실패처럼 손실이 크고 불확실한 경로부터 끝에서 끝까지 붙인다.
   - **트레이드오프**: 큰 실패를 일찍 발견하고 아키텍처 가정을 검증한다. 사용자가 바로 체감하는 기능 수는 천천히 늘 수 있다.

2. **사용자 가치가 높은 정상 기능부터 넓힌다**: 조회, 취소, 예약 내역처럼 사용 빈도가 높은 기능을 우선해 제품 가치를 빠르게 만든다.
   - **트레이드오프**: 눈에 보이는 진척이 빠르다. 이미 드러난 결제와 정합성 위험을 뒤로 미루면 나중에 구조를 다시 바꿀 수 있다.

## FB-C1-01 · 모델을 모두 분리할 때의 임계점

**원문 앵커**: `taskC-1.md` L20 · 한 엔티티가 API·업무·영속성 역할을 함께 맡으면 결합이 생긴다는 주장

### 내가 주장한 내용

기술 모델이 여러 계층의 공용 계약이 되면 테스트 비용과 변경 전파가 커진다. 모든 모델을 항상 분리해야 한다고 주장한 것은 아니다.

### 피드백이 날아온 내용

API, 업무, 영속성 모델을 모두 분리해 클래스와 Mapper가 크게 늘 때 분리 편익이 비용을 넘는 기준을 요구한다.

### 답변·변론 후보

1. **추천 · 독립적으로 바뀌는 경계만 분리한다**: 외부 API 호환성, 도메인 불변식, 저장 스키마의 변경 이유가 실제로 다르거나 타입 노출이 장애·보안 위험을 만들 때 분리한다. 같은 모양과 생명주기가 오래 유지되는 단순 CRUD 내부 기능은 통합을 허용한다.
   - **트레이드오프**: Mapper 폭증을 피하면서 중요한 경계는 보호한다. 팀이 변화 신호를 계속 관찰해야 하며 기준 적용이 균일하지 않을 수 있다.

2. **공개 API와 영속성 모델은 기본적으로 분리한다**: 향후 변경 비용을 옵션 비용으로 보고 초기에 세 모델을 분리한다.
   - **트레이드오프**: 외부 계약과 DB 변경의 독립성이 높다. 단순 기능도 클래스와 매핑 테스트가 늘고 모든 변경을 여러 모델에 반복할 수 있다.

## FB-C1-02 · 외부 시스템이 핵심 규칙을 지배할 때

**원문 앵커**: `taskC-1.md` L75 · 보호할 대상은 업무 언어와 규칙을 담은 도메인 모델이라는 주장

### 내가 주장한 내용

DDD는 외부 의존성 0 자체보다 무엇을 보호할지 먼저 정하며, 헥사고날은 그 모델을 기술 세부에서 격리한다.

### 피드백이 날아온 내용

외부 결제망의 상태 전이처럼 통제할 수 없는 제약이 핵심 업무의 성립 조건이라면 순수한 내부 모델과 외부 현실 중 어디서 출발할지 묻는다.

### 답변·변론 후보

1. **추천 · 외부 사실은 인정하고 업무 의미는 내부가 소유한다**: 외부 시스템이 실제로 제공하는 상태와 보장을 먼저 확인한 뒤 Adapter가 이를 내부의 `승인됨`, `확인 중`, `실패` 같은 의미로 번역한다. 외부 제약 자체가 사업 규칙이라면 기술 타입을 끌어들이지 말고 도메인 개념으로 명시한다.
   - **트레이드오프**: 현실과 동떨어진 모델을 피하면서 공급자 교체 여지를 남긴다. 번역 계층과 `UNKNOWN` 같은 중간 상태가 늘어난다.

2. **외부 상태 모델을 내부 표준으로 채택한다**: 공급자 모델이 사실상 업계 표준이고 교체 가능성이 낮다면 내부도 같은 상태 전이를 사용한다.
   - **트레이드오프**: 변환이 적고 구현이 빠르다. 공급자 정책 변경과 교체 비용이 Core 전체로 전파될 수 있다.

## FB-C2-01 · 미래 분리 비용 때문에 처음부터 나눌 것인가

**원문 앵커**: `taskC-2.md` L18 · 분리 편익과 지속적인 매핑 비용을 비교해야 한다는 주장

### 내가 주장한 내용

업무 규칙이 존재하고 JPA 때문에 테스트나 변경 격리가 깨진 증거가 함께 있을 때 분리를 검토한다. 단순히 미래 가능성만으로 두 모델을 만들지는 않는다.

### 피드백이 날아온 내용

통합 엔티티가 시스템 전반에 퍼진 뒤 분리하면 마이그레이션이 비싸므로 처음부터 분리하는 편이 낫지 않은지 묻는다.

### 답변·변론 후보

1. **추천 · 모델은 통합하되 누수 방지용 이음새를 먼저 만든다**: 엔티티를 API에 직접 노출하지 않고 저장 접근을 Adapter에 모아 참조 범위를 제한한다. 분리 신호가 생기면 한 Aggregate씩 새 Domain 모델과 Mapper를 넣어 점진적으로 옮긴다.
   - **트레이드오프**: 매 변경마다 이중 모델을 유지하는 비용을 피하고 미래 마이그레이션 범위도 제한한다. 이음새 규율이 무너지면 뒤늦은 분리가 다시 비싸진다.

2. **변화 가능성이 높은 핵심 Aggregate는 처음부터 분리한다**: 규칙 증가와 저장 기술 변화가 이미 로드맵에 있다면 선행 비용을 지불한다.
   - **트레이드오프**: 미래 전환 위험이 줄고 테스트가 단순해진다. 예측이 빗나가면 사용하지 않은 유연성에 계속 매핑 비용을 낸다.

## FB-C3-01 · 결제 확인 중 사용자에게 보여줄 상태

**원문 앵커**: `taskC-3.md` L137 · 결제 후 저장 실패를 즉시 보상하지 않고 별도 대사 유스케이스로 닫겠다는 주장

### 내가 주장한 내용

외부 결제와 DB 저장은 하나의 로컬 트랜잭션으로 묶을 수 없으므로 타임아웃과 저장 실패를 별도 원장과 대사 흐름으로 처리한다.

### 피드백이 날아온 내용

대사가 끝나기 전 사용자가 보는 상태와 문구를 지금 설계해 보라는 요구다.

### 답변·변론 후보

1. **추천 · 성공과 실패가 아닌 확인 중 상태를 노출한다**: 예약을 `결제 확인 중`으로 표시하고 중복 결제를 피하도록 안내한다. 상태 조회와 알림 경로를 함께 제공하며, 완료 시 예약 확정 또는 결제 취소 결과를 알린다.
   - **트레이드오프**: 불확실성을 정직하게 전달하고 중복 결제를 줄인다. 상태 모델, 조회 화면, 알림, 운영 응대가 추가로 필요하다.

2. **승인 즉시 임시 예약으로 보여준다**: 사용자에게 좌석을 확보한 것처럼 보이고 뒤에서 복구한다.
   - **트레이드오프**: 경험은 단순하다. 나중에 취소될 수 있는 결과를 성공처럼 보여 신뢰와 보상 비용이 커질 수 있다.

## FB-C4-01 · DB 외에 외부화해야 할 상태

**원문 앵커**: `taskC-4.md` L55 · 예약·티켓·회원 데이터를 MySQL로 옮겨 앱을 무상태로 만들었다는 주장

### 내가 주장한 내용

현재 walking skeleton의 영속 상태를 DB로 옮겨 여러 앱 인스턴스가 같은 결과를 보게 했다. 현재 코드에는 로그인 세션, 로컬 파일, 애플리케이션 캐시, 스케줄러가 없다.

### 피드백이 날아온 내용

실서비스에서 자주 남는 세션, 로컬 파일, 인메모리 캐시, 중복 스케줄러 실행까지 stateless 판단에 포함하라는 요구다.

### 답변·변론 후보

1. **추천 · 현재 범위를 한정하고 상태별 외부화·중복 방지 원칙을 명시한다**: 세션은 토큰이나 공유 저장소, 파일은 객체 저장소, 필수 캐시는 공유 저장소나 재생성 가능한 로컬 캐시, 스케줄은 큐·DB 소유권과 멱등성으로 다룬다.
   - **트레이드오프**: 수평 확장과 장애 복구 기준이 명확해진다. Redis, 객체 저장소, 락이나 큐 같은 운영 구성요소가 늘어난다.

2. **인스턴스 로컬 상태를 허용하되 소실 가능한 상태로 제한한다**: 성능용 캐시나 임시 파일은 언제든 버려져도 결과가 같다는 조건으로 로컬에 둔다.
   - **트레이드오프**: 외부 인프라와 네트워크 비용이 줄어든다. 캐시 일관성과 디스크 용량, 재시작 후 성능 저하를 관리해야 한다.

## FB-C6-01 · Report에서 자동 게이트로 넘길 항목

**원문 앵커**: `taskC-6.md` L136 · 미검증 가정과 위험을 report로 제출하고 사람이 승인한다는 제안

### 내가 주장한 내용

AI가 발견한 테스트 밖 위험을 임의로 계약에 넣지 않고 구조화된 report로 사람에게 넘기려 했다.

### 피드백이 날아온 내용

모든 report를 사람이 읽으면 병목이 되므로 관측 사실부터 자동화하고, 최종적으로 사람에게 남길 판단을 구분하라는 질문이다.

### 답변·변론 후보

1. **추천 · 관측과 판단을 분리한 2단 게이트를 둔다**: 실제 실행된 프로덕션 Adapter, 테스트 더블로 치환된 Port, 계약 출처 유무, 새 의존성 위반처럼 기계가 확인할 수 있는 사실은 자동 판정한다. 업무 의미, 허용 위험, 상충하는 계약의 우선순위만 사람에게 올린다.
   - **트레이드오프**: 사람은 예외와 결정에 집중한다. 관측 스키마와 자동 규칙 자체를 유지하고 오탐을 관리해야 한다.

2. **위험 점수로 사람 검토량을 줄인다**: 모든 report를 보존하되 영향도와 근거 수준을 점수화해 높은 항목만 사람에게 보낸다.
   - **트레이드오프**: 단계적으로 도입하기 쉽다. 점수 기준이 틀리면 중요한 위험이 낮게 분류될 수 있고 판단 과정이 불투명해진다.

## FB-C6-02 · 실제 외부 계약의 근거

**원문 앵커**: `taskC-6.md` L136 · 사람이 승인한 case만 계약과 테스트에 반영한다는 제안

### 내가 주장한 내용

AI가 만든 가정을 사람이 승인하면 계약으로 승격하려 했다. 하지만 사람의 승인 자체가 올바르다는 근거는 제시하지 않았다.

### 피드백이 날아온 내용

실제 PG라면 무엇을 근거로 엔드포인트, 상태 코드, 응답 의미를 확정할지 묻는다.

### 답변·변론 후보

1. **추천 · 출처가 있는 증거 묶음으로 계약을 승인한다**: 버전이 명시된 공식 문서와 스키마, Sandbox 실행, 공급자 지원 확인, 실제 통신 기록을 우선순위와 확인 시각과 함께 묶는다. 근거가 충돌하거나 없으면 성공으로 추정하지 않고 `UNKNOWN`으로 처리해 대사한다.
   - **트레이드오프**: 기억이나 단일 스텁에 의존하지 않고 계약 변경도 추적할 수 있다. 공급자 환경과 계약 테스트를 유지하는 비용이 든다.

2. **공급자 SDK를 계약의 기준으로 삼는다**: 공식 SDK 타입과 동작을 Adapter 계약 테스트의 근거로 사용한다.
   - **트레이드오프**: 구현과 검증이 빠르고 타입 오류를 줄인다. SDK 버그나 문서와의 차이, 버전 종속성을 별도로 확인해야 한다.

## FB-INT-01 · 어댑터 교체를 넘어 서비스 안정성을 증명하는 방법

**원문 앵커**: `FEEDBACK-interview.md` · 모의 면접 질문 3 답변

### 내가 주장한 내용

두 Adapter 조합에서 Core 무수정과 같은 인수테스트 통과를 확인했고, 새로운 트랜잭션 의미가 생기면 경계를 다시 그어야 한다고 답했다.

### 피드백이 날아온 내용

구조적 교체 가능성만 말하지 말고 실제 서비스 안정성까지 판단 범위를 넓히라는 조언이다.

### 답변·변론 후보

1. **추천 · 구조 증거와 운영 안정성 증거를 분리해 답한다**: 현재 실험은 의존 방향만 증명한다. 실서비스에서는 Adapter 계약 테스트, 실제 프로토콜 통합 테스트, 동시성·멱등성·타임아웃·재시도·부분 실패 테스트, 부하와 관측성을 추가해야 한다고 한계를 밝힌다.
   - **트레이드오프**: 증명한 것과 아직 모르는 것을 정직하게 구분한다. 테스트 계층과 운영 검증 비용이 커진다.

2. **Core 무수정을 안정성의 중심 근거로 방어한다**: 교체 시 Core가 바뀌지 않는 것이 회귀 위험을 줄이므로 대규모에서도 원리는 성립한다고 강조한다.
   - **트레이드오프**: 아키텍처 설명은 간결하다. 분산 장애, 용량, 정합성 같은 실제 안정성 질문에는 충분히 답하지 못한다.

## FB-INT-02 · 팀 관례를 사용자·비즈니스 관점에서 판단하기

**원문 앵커**: `FEEDBACK-interview.md` · 모의 면접 질문 5 답변

### 내가 주장한 내용

팀 규칙을 기본으로 따르되 분리 편익이 있다고 판단하면 별도 구현과 분석을 통해 제안하겠다고 답했다.

### 피드백이 날아온 내용

기술적 선호만 비교하지 말고 기존 관례의 이유를 존중하며 사용자와 사업 결과에 미치는 영향을 근거로 대화하라는 조언이다.

### 답변·변론 후보

1. **추천 · 관례의 이유와 관측된 비용부터 확인한다**: 장애, 기능 출시 시간, DB 변경 전파, 고객 오류처럼 사용자·사업에 드러난 문제가 없다면 기존 방식을 따른다. 문제가 있다면 작은 변경 영역에서 실험해 리드타임과 결함 차이를 비교한 뒤 팀에 제안한다.
   - **트레이드오프**: 개인 취향이 아니라 팀과 사용자 성과로 설득할 수 있다. 충분한 관측 데이터와 실험 시간이 필요하다.

2. **기술 부채 예방을 근거로 선제 분리를 제안한다**: 미래 마이그레이션 비용을 줄이기 위해 일관된 분리 규칙을 요청한다.
   - **트레이드오프**: 장기 구조 일관성을 얻을 수 있다. 현재 사용자 가치와 연결되지 않으면 과설계나 개인 취향으로 보일 수 있다.

## 페이지 총평 · 설계를 버릴 때, 인간의 결정권, 미래 변경 여지

**원문 앵커**: `FEEDBACK-overall.md` · 페이지 레벨 총평의 질문 세 개

### 내가 주장한 내용

명시적 경계, 자동 게이트, 사람의 계약 승인으로 AI 생성 코드를 통제할 수 있다고 주장했다. 성능과 속도를 위해 경계를 완화하는 조건, 인간이 끝까지 소유할 판단, 현재 설계를 미래에 쉽게 해체할 방법은 충분히 다루지 않았다.

### 피드백이 날아온 내용

설계를 원칙으로만 방어하지 말고 버릴 조건을 정하고, 자동화 이후 인간의 책임을 정의하며, 후임자가 구조를 안전하게 교체할 수 있도록 무엇을 고정하지 않을지 묻는다.

### 답변·변론 후보

1. **추천 · 세 질문 모두 증거와 책임의 경계로 답한다**: 프로파일링과 사업 손실로 병목이 확인될 때만 국소적으로 경계를 합치고, 인간은 목표·불변식·허용 위험·증거 기준을 소유한다. 미래 변경을 위해 공개 계약은 작게 유지하고 Adapter와 조립부를 교체 가능하게 두며 결정 근거와 회귀 테스트를 남긴다.
   - **트레이드오프**: 현재 효율과 미래 변경 가능성을 함께 다룬다. 측정, 기록, 회귀 테스트를 지속적으로 관리해야 한다.

2. **아키텍처 원칙을 강하게 보존한다**: 성능은 캐시와 인프라 최적화로 해결하고 경계는 유지하며, 인간은 모든 최종 승인을 담당한다.
   - **트레이드오프**: 구조적 일관성과 통제가 강하다. 극단적인 지연 목표에서 불필요한 간접 비용을 유지하고 사람 병목도 남을 수 있다.
