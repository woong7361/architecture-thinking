## FB-INT-01 · 모의 면접 질문 3 답변

- **질문**: 같은 Cucumber 인수테스트를 in-memory와 Testcontainers MySQL 두 방식으로 돌려서 Core를 한 줄도 고치지 않고 초록불을 받으셨습니다. "그건 어댑터가 두 개뿐이라 가능한 것 아닌가요? 실제 서비스 규모에서도 그게 성립하나요?" 라는 질문을 받으시면 어떻게 답하실 건가요?
- **지적된 답변**: core가 outbound에 의존하지 않는다면 일반적으로 가능하다고 생각합니다. 하지만 힘들 경우도 있다고 생각합니다.  예를 들어 내부 포인트로만 결제를 하다가, 새롭게 외부 결제 API가 도입된다면 새롭게 tx경계가 생깁니다. 그렇다면 기존 경계는 너무 좁거나 넓어 새로운 outbound를 도입할 수 없고, 경계를 새로 정의해야하는 일이 생깁니다. 하지만 이런 식으로 미리 경계를 보수적으로 잡는 일은 서비스 유지보수성을 떨어뜨리고, 복잡성을 올릴 수 있기에 새로 요구사항이 들어왔을 때 경계를 새로 긋는 것이 맞다고 생각합니다.
- **작성자 / 시각**: 그릿 · 2026-08-10 16:11 KST
- **피드백 원문**:

```
이 부분에서는 인수테스트 이상으로 서비스의 안정성을 생각하시는 방향에 대해 고민해주시면 좋을 것 같습니다 
```

**답변 초안:**

현재 실험이 증명한 것은 저장 Adapter를 바꿔도 Core의 소스 의존성과 같은 업무 시나리오가 유지된다는 점까지입니다. Adapter가 두 개뿐인 작은 환경에서 얻은 결과이므로, 이것만으로 실제 서비스 규모의 안정성을 증명했다고 말할 수는 없습니다. 규모가 커져도 Core가 구체 기술을 모르게 한다는 원리는 유효하지만, Adapter 수와 외부 호출이 늘수록 각 구현이 같은 계약과 운영 특성을 지키는지는 별도로 검증해야 합니다.

실서비스에서는 모든 Adapter에 같은 계약 테스트를 적용하고, 실제 프로토콜을 쓰는 통합 테스트를 추가하겠습니다. 여기에 동시 요청, 멱등성, 타임아웃, 재시도, 부분 실패와 대사, 부하 한계, 장애 시 관측 가능성까지 확인해야 합니다. 새로운 결제 수단이 단순 구현 교체가 아니라 트랜잭션 의미와 사용자 상태를 바꾼다면 Core 무수정을 고집하지 않고 Port와 유스케이스 경계를 다시 그어야 합니다. 따라서 `Core를 안 고쳤다`는 것은 구조 증거이고, 서비스 안정성은 실패 조건과 운영 환경을 포함한 별도의 증거로 답하겠습니다.

## FB-INT-02 · 모의 면접 질문 5 답변

- **질문**: Domain Entity와 Persistence Entity를 나누면 매핑 비용이 생기는데 이번에는 그 비용을 감수하셨습니다. 반대로 나누지 않는 편이 낫다고 판단할 프로젝트는 어떤 조건일까요? 면접관이 "우리 팀은 그렇게 안 나눕니다"라고 하면 그 대화를 어떻게 이어가실 건가요?
- **지적된 답변**: 그리고 팀의 규칙이 그렇게 나누지 않는다고 한다면 당연히 기본적으로 팀의 컨벤션을 따라야하는 것이 맞다고 생각하고, 제가 생각하기에 정말 entity를 분리하는 것이 이점이 있다고 생각한다면 해당 사항 보고 후 개별적으로 분리한 소스를 만들고, 분석하고, 기획을 작성해 따로 제안해보는 것을 고려할것 같습니다.
- **작성자 / 시각**: 그릿 · 2026-08-10 16:13 KST
- **피드백 원문**:

```
네 이런 답변 플로우 괜찮다고 생각합니다. 추가로 더 들어가볼 수 있는 점은, 유저, 그리고 실제 서비스 관점에 대한 생각입니다. 팀에서 관습적으로 해온 것에 기술적인 근거가 있을 것이라는 인정을 밝히고, 본질적으로 유저 관점에서 혹은 비즈니스 관점에서 맞는 점에 대한 감각이 있다는 점을 밝혀주셔도 좋을 것 같아요. 
```

**답변 초안:**

면접관이 `우리 팀은 그렇게 나누지 않는다`고 말하면 먼저 그 관례가 생긴 이유를 묻겠습니다. 한 DB의 단순 CRUD가 대부분이라 매핑 비용이 더 컸는지, JPA 기능을 적극 활용해 개발 속도를 얻고 있는지, 과거 분리 시도에서 어떤 문제가 있었는지 확인하겠습니다. 팀이 운영 경험을 통해 만든 기준을 제 설계 선호만으로 틀렸다고 판단하지 않겠습니다.

그다음 사용자와 사업 결과를 보겠습니다. 통합 엔티티 때문에 장애가 반복되는지, DB 변경이 API까지 번져 출시가 늦어지는지, 반대로 분리로 생긴 매핑 오류와 개발 지연이 더 큰지를 근거로 비교하겠습니다. 관측된 문제가 없다면 팀 방식을 따르겠습니다. 문제가 있다면 승인 없이 별도 구조를 병행하지 않고, 변화가 잦은 Aggregate 하나에서 작은 실험을 제안해 변경 범위, 테스트 시간, 결함 수를 비교하겠습니다. 제안의 목적도 `헥사고날이 더 옳다`가 아니라 사용자 오류와 출시 비용을 실제로 줄일 수 있는지 확인하는 데 두겠습니다.
