## Scenario B. 티켓 예매 시스템 문제 해결 시나리오

### 1. 문제 정의

상황: 오픈 1분 만에 10만 명 동시 접속 예상, 1만 석 한정. 중복 차감(Overbooking) 없이 1만 명에게만 정확히 판매해야 함.

#### 1.1 상황 요약

- 동시 접속 규모: 10만 명
- 판매 수량: 1만 석
- 반드시 보장해야 하는 조건: 중복 차감이나 초과 판매 없이 정확히 1만 명에게만 티켓 판매

#### 1.2 핵심 기술적 문제

- 핵심 문제 한 문장 정의: 짧은 시간에 대량의 동시 요청이 몰리는 상황에서, 시스템 전체가 판매 가능 수량과 주문 상태의 정합성을 잃지 않도록 제어하는 문제

#### 1.3 문제를 나누어 보는 관점

- 대기열 / 트래픽 제어 문제: 10만 명의 요청을 순서대로 보내되 한꺼번에 핵심 트랜잭션 구간으로 보내지 않는 문제
- 동시성 제어 문제: 같은 재고 또는 좌석에 대한 경쟁 요청 중 하나만 성공시키는 문제
- 결제와 좌석 확정의 원자성 문제: 외부 결제 시스템과 내부 주문/좌석 상태를 최종적으로 일관되게 맞추는 문제

---

### 2. 핵심 엔지니어링 요구사항

#### 2.1 재고 정합성 보장

- 전체 판매 수량은 반드시 1만 석을 초과하지 않아야 한다.
- 동일 좌석이 두 명 이상에게 중복 배정되지 않아야 한다.

#### 2.2 원자적 처리 보장

- 좌석 확인, 재고 차감, 주문 생성, 좌석 확정은 중간 상태 불일치 없이 처리되어야 한다.
- 내부 DB 변경은 가능한 하나의 트랜잭션 안에서 묶는다.

#### 2.3 동시 요청 제어

- 동시에 많은 구매 요청이 들어와도 재고 차감 로직은 안전하게 제어되어야 한다.
- 같은 사용자의 중복 요청이나 재시도가 중복 구매로 이어지지 않아야 한다.

#### 2.4 순서 보장

- 선착순 예매라면 먼저 진입한 사용자가 먼저 구매 기회를 얻도록 서버 기준의 순서를 관리해야 한다.
- 순서 대기가 너무 길다면 명시적인 순서 및 예상 대기시간을 보여주어 사용자 경험을 향상 시킨다.

#### 2.5 트래픽 제어

- 오픈 직후 10만 명의 요청이 한꺼번에 핵심 처리 구간으로 몰리지 않도록 제어해야 한다.
- 대기열이나 요청 제한을 통해 시스템이 감당 가능한 수준으로 요청을 흘려보내야 한다.

---

### 3. 10만 명의 요청 쏠림을 제어하고, 요청 순서를 유지하는 전략

#### 3.1 주요 목표

이 장의 목표는 오픈 직후 10만 명이 동시에 들어오는 상황에서 구매 플로우에 진입할 수 있는 권한을 시스템 처리량에 맞춰 배분하는 것이다.
여기서 구매 플로우는 좌석 조회, 좌석 점유, 주문 생성, 결제 요청으로 이어지는 무거운 처리 구간을 의미한다. 

구매 기회는 정책에 따라 명확하게 배분되어야 한다. 선착순 예매라면 먼저 진입한 사용자에게 먼저 기회를 주고, 이탈, 결제 실패, 타임아웃으로 구매 기회가 반환되면 다음 대상에게 순서대로 기회를 넘긴다.

#### 3.2 비교 기준

아래 방식들은 "오픈 1분 만에 10만 명이 몰리고, 1만 석만 판매해야 하며, 서버가 발급한 순번 기준으로 구매 기회를 배분해야 하는 상황"에서 다음 기준으로 비교한다.

- 순서 보장: 서버 기준 선착순으로 다음 입장자를 선별할 수 있는가
- 진입 제어: DB, 좌석 점유, 결제 API가 감당 가능한 처리량에 맞춰 구매 플로우 진입을 처리량에 맞게 제한할 수 있는가
- 사용자 UX: 사용자가 자신의 대기 상태, 입장 가능 여부, 다음 행동을 이해할 수 있는가
- 운영 복잡도: 인프라 운영 복잡도, 장애 복구, 비용이 감당 가능한가

#### 3.3 대기열 구현 방식 비교

##### 3.3.1 Redis INCR 기반 대기열 서버

###### 이 시나리오에서의 장점

- Redis `INCR`로 단조 증가하는 순번을 발급하고, 현재 입장 가능한 최대 순번만 관리하면 되므로 구조가 단순하고 비용이 낮다.
- 구매 단계로 통과시킬 순번 범위를 조절하면, 10만 명이 동시에 접속해도 핵심 구매 API로 들어가는 인원을 제한할 수 있다.
- 순번 발급 자체는 원자적으로 처리되므로, 서버가 여러 대로 늘어나도 같은 이벤트 안에서 순번이 중복 발급될 위험이 낮다.

###### 이 시나리오에서의 단점

- Redis `INCR` 자체가 요청을 받아 쌓아두는 구조는 아니므로, 결제 API까지 도달하는 트래픽을 제어하지 못한다.
- 별도 대기 상태를 저장하지 않는 순번 기반 제한 접속에 가까우므로, 이탈자, 결제 실패자, 타임아웃 사용자가 생겼을 때 다음 순번 사용자를 공정하게 입장시키기 어렵다.
- Redis 장애나 데이터 유실이 발생하면 순번 상태가 사라질 수 있으므로 persistence, replication, failover 설정이 필요하다.

---

##### 3.3.2 Redis Sorted Set 기반 대기열 서버

###### 이 시나리오에서의 장점

- 사용자 ID를 기준으로 중복 없이 순번을 저장하므로, 실제 대기 중인 사용자 집합과 순서를 명시적으로 관리할 수 있다.
- `ZRANK`, `ZRANGE`, `ZREM` 같은 연산으로 현재 대기 위치를 조회하고, 앞 순번 사용자를 선별하여, 입장 완료나 만료 상태를 대기열에 반영하기 쉽다.
- 사용자별 순번 조회와 앞 순번 선별을 Redis 자료구조로 직접 표현할 수 있어, 대기 화면에 필요한 상태 조회를 구현하기 쉽다.

###### 이 시나리오에서의 단점

- Redis Sorted Set은 대기 상태 저장소에 가깝고, MQ처럼 요청을 직접 쌓아두고 후단이 가져가는 방식은 아니므로 트래픽 흡수에는 한계가 있다.
- Waiting Room API가 대기 등록, 순번 조회, 입장 가능 여부 확인 요청을 계속 받아야 하므로, polling 주기, rate limit, cache 전략을 별도로 설계해야 한다.
- INCR 단독 방식보다 구현이 복잡하고, 사용자 상태, 대기 상태, 입장 상태, 만료 처리를 함께 관리해야 한다.
- Redis 장애, failover, TTL 만료 정책을 잘못 설계하면 대기 순서나 입장 상태가 어긋날 수 있다.

---

##### 3.3.3 Kafka / Message Queue 기반 대기열

###### 이 시나리오에서의 장점

- 대량의 진입 요청을 durable log나 message queue에 쌓고 consumer가 처리량에 맞춰 순차적으로 소비할 수 있다.
- queue에 쌓인 요청을 consumer가 후단 결제 서버의 처리량에 맞춰 가져가 처리 속도를 조절할 수 있어, 결제 서버로 흘러가는 요청량을 제한할 수 있다.
- Kafka나 MQ는 메시지 처리 이력, consumer offset, ack/retry 같은 메커니즘을 제공하므로 장애 후 재처리와 처리 추적에는 더 적합하다.

###### 이 시나리오에서의 단점

- Kafka나 MQ는 메시지를 저장하고 소비하는 흐름에는 강하지만, 사용자별 현재 순번, 예상 대기 시간, 입장 가능 여부처럼 Waiting Room에 필요한 실시간 상태 조회에는 별도 상태 저장소가 필요하다.
- 처리량을 높이기 위해 partition이나 consumer를 늘리면 전체 사용자 기준 FIFO 보장이 어려워지고, 전역 순서를 강하게 유지하면 처리량이 제한된다.
- Redis도 운영 복잡도가 없지는 않지만, Kafka나 MQ는 대기 상태 관리 외에 consumer, offset 또는 ack, 재처리, 중복 소비 방지 같은 메시지 소비 파이프라인까지 설계해야 하므로 주 대기열로 쓰기에는 구조가 무거워질 수 있다.


---

##### 3.3.4 DB sequence table 기반 대기열

###### 이 시나리오에서의 장점

- DB sequence나 auto increment를 사용하면 중복을 방지하고 순번 발급 규칙을 명확하게 구현 가능하다. 
- 대기 등록, 입장 허용, 만료, 이탈 같은 상태 변화를 DB row와 트랜잭션으로 관리할 수 있어 장애 후 복구나 감사 로그 관점에서 이해하기 쉽다.
- 별도 추가적인 인프라 없이 기존 DB만으로 구현할 수 있다면 초기 구조는 단순하다.

###### 이 시나리오에서의 단점

- 10만 명의 순번 발급과 순번 조회가 DB에 몰리면, 구매 전 단계에서부터 DB 병목이 생길 수 있다.
- 대량 사용자의 대기 등록과 순번 발급이 DB write로 몰리고, 이후 대기 화면에서 반복적으로 순번과 입장 가능 상태를 조회하면 DB read 부하도 크게 증가한다.
- 핵심 재고 차감과 주문 생성도 DB가 맡아야 하는데, 대기열까지 DB에 두면 보호해야 할 DB에 부하를 더 얹는 구조가 된다.
- 수평 확장이 어렵고, 부하를 버티려면 DB 스케일업이나 read replica 같은 비용이 커질 수 있다.

---

#### 3.4 이 시나리오에서의 선택 방향

비용/운영 편의성: DB보다는 복잡하지만 Kafka/MQ보다는 Waiting Room 목적에 직접적이고 간편함
부하 처리: DB read/write 집중을 Redis로 분산
순서 유지: Sorted Set score 기반으로 대기 순서 표현 가능
사용자 편의성: 현재 순번, 입장 가능 여부 조회 구현이 쉬움
후단 보호: admitter/token으로 구매 API 진입량 제한 가능

이 시나리오에서는 Redis Sorted Set 기반 대기열을 중심으로 선택하는 것이 가장 적합하다. Redis INCR로 서버 기준 순번을 발급하고, Sorted Set에 사용자와 순번을 저장한다. 이후 별도의 admitter가 DB, 결제, 좌석 확정 API가 감당 가능한 처리량에 맞춰 앞 순번 사용자를 batch 단위로 선별하고, 구매 단계에 진입할 사용자에게 짧은 TTL의 admission token을 발급한다.

입장량은 HTTP 서버가 연결을 붙잡고 있다가 흘려보내는 방식이 아니라, Waiting Room에서 초당 또는 주기별로 입장 가능 상태로 바꿀 사용자 수를 제한하는 방식으로 제어한다. 예를 들어 처음에는 초당 500명처럼 보수적인 값으로 시작하고, 입장 token TTL, 구매 API latency, DB connection 사용률, DB lock wait, 결제 API error rate 같은 지표를 보면서 입장률을 조정한다. 정확한 활성 세션 수를 완벽히 알기는 어렵기 때문에, TTL 기반의 활성 사용자 추정과 시스템 부하 지표를 함께 사용한다.

최종 구조는 다음과 같이 역할을 분리한다.

1. Waiting Room: 사용자를 구매 API 앞에서 대기시킨다. 사용자는 대기 화면에서 순번과 입장 가능 여부를 조회한다.
2. 순번 저장소: Redis INCR과 Redis Sorted Set으로 순서와 대기 상태를 관리한다.
3. Admitter: 시스템 처리량에 맞춰 앞 순번 사용자 일부를 입장 가능 상태로 바꾸고 admission token을 발급한다.
4. Admission Token / Cookie: 입장 허가를 받은 사용자만 구매 API에 접근할 수 있도록 검증한다.
5. Protected API: token 또는 cookie를 검증한 뒤 좌석 점유, 주문 생성, 결제 같은 구매 단계를 처리한다.

Kafka나 message queue는 대량 이벤트를 안정적으로 저장하고 소비하는 데는 강하지만, 사용자별 현재 순번을 보여주고 앞 순번 사용자를 입장시키는 Waiting Room 대기열에는 별도 상태 조회 모델이 필요해진다. 또한 Waiting Room 뒤에 MQ를 두고 결제 API 앞에서 다시 트래픽을 흡수하는 구조는 가능하지만, 구매 단계가 비동기화되어 처리 대기 상태, 좌석 점유 TTL, 결제 실패와 재시도 처리를 추가로 관리해야 한다. 따라서 이 시나리오에서는 MQ를 주력 대기열로 두기보다, 결제 완료 이벤트, 알림, 로그, 보상 처리 같은 후속 비동기 처리에 사용하는 편이 적합하다.

DB sequence table은 영속성은 좋지만, 10만 명의 진입 요청과 순번 조회를 DB로 보내면 핵심 DB를 보호하려는 목적과 충돌한다.

---

#### 3.5 선택한 조합의 Trade-off

- Redis Sorted Set은 대기 순서와 상태 관리는 편하지만, MQ처럼 요청을 직접 쌓아두고 consumer가 가져가는 구조는 아니다.
  - 보완: Waiting Room API를 수평 확장하고, 상태 조회 polling 주기를 조절해 앞단 API 부하를 줄인다.
- 10만 명이 짧은 주기로 status API를 polling하면 Waiting Room API와 Redis read 부하가 커질 수 있다.
  - 보완: 대기 순번이 먼 사용자는 긴 주기로 조회하고, 입장이 가까운 사용자만 짧은 주기로 조회하게 한다. 대기 화면과 정적 리소스는 CDN/cache를 사용한다.
- Redis 장애나 failover 과정에서 대기열 상태가 유실되거나 순서가 어긋날 수 있다.
  - 보완: Redis replication, persistence, failover 구성을 두고, admission token 발급 기록이나 최소한의 순번 발급 로그를 별도로 남긴다.

### 4. 재고와 결제 상태의 정합성 유지를 위한 동시성 전략

#### 4.1 주요 목표

이 장의 목표는 대기열을 통과한 구매 요청이 실제 좌석 점유, 주문 생성, 결제 상태 변경을 수행할 때 재고와 주문 상태의 정합성을 잃지 않도록 만드는 것이다.

이 단계에서는 단순히 요청을 많이 처리하는 것보다, 전체 판매 수량이 1만 석을 넘지 않고 동일 좌석이 두 명 이상에게 배정되지 않는 것이 우선이다. 또한 사용자의 중복 클릭, 네트워크 재시도, 결제 webhook 중복 수신, 예약 만료 worker 실행처럼 같은 주문이나 좌석 상태를 여러 흐름이 동시에 변경하려는 상황도 안전하게 처리해야 한다.

#### 4.2 비교 기준

아래 방식들은 "대기열을 통과한 사용자가 좌석 점유, 주문 생성, 결제 요청을 수행하는 상황"에서 다음 기준으로 비교한다.

- 최종 정합성 보장: 전체 판매 수량이 1만 석을 초과하지 않고, 동일 좌석이 중복 배정되지 않도록 최종적으로 보장할 수 있는가
- 경합 제어와 처리량: 오픈 직후 특정 공연이나 좌석에 요청이 몰려도 DB row lock, connection 대기, 재시도 폭증을 감당 가능한 수준으로 제한할 수 있는가
- 중복 요청 방어: 사용자 중복 클릭, API 재시도, 결제 webhook 중복 수신, worker 재처리가 중복 구매나 중복 상태 변경으로 이어지지 않게 막을 수 있는가
- 운영 복잡도: 추가 구성 요소를 도입했을 때 얻는 이점이 장애 대응과 운영 비용을 감당할 만큼 큰가

#### 4.3 재고/주문 상태 변경을 제어하는 동시성 전략

##### 4.3.1 Pessimistic Lock, 비관적 락

###### 이 시나리오에서의 장점

- DB가 동시 변경 순서를 직접 제어하므로, 재고나 주문 상태처럼 틀어지면 안 되는 데이터의 정합성을 강하게 보장할 수 있다.
- Redis, queue 같은 추가 인프라 없이 DB 트랜잭션만으로 구현할 수 있어 초기 구현 비용과 운영 복잡도가 낮다.
- 실패 후 재시도를 반복하는 방식보다 처리 흐름이 단순해, 작은 임계 구역에서는 장애 분석과 롤백 범위를 파악하기 쉽다.
- 좌석 최종 확정, 주문 상태 확정처럼 짧고 중요한 상태 전이 구간에서는 제한적으로 유효하다.


###### 이 시나리오에서의 단점

- 특정 공연의 재고 row 하나에 10만 명이 몰리면 DB row lock이 병목이 된다.
- 대기 중인 요청이 DB 커넥션을 오래 잡으면, 구매 API뿐 아니라 같은 DB를 쓰는 다른 기능까지 영향을 받을 수 있다.
- 트래픽이 몰릴수록 락 타임아웃과 데드락 대응이 필요해지고, 사용자는 구매 실패나 긴 대기를 경험할 가능성이 커진다.
- 재고 차감 전체를 비관적 락으로 처리하면 DB row lock과 커넥션 대기가 커져 오픈 직후 병목이 될 가능성이 높다.

---

##### 4.3.2 외부 분산 락, Redis Lock 등

###### 이 시나리오에서의 장점

- 여러 애플리케이션 서버가 같은 재고 차감이나 주문 확정 로직에 동시에 진입하는 것을 애플리케이션 레벨에서 제어할 수 있다.
- DB에 도달하기 전에 경쟁 요청을 줄일 수 있어, DB row lock 경합과 조건부 update 충돌을 완화할 수 있다.
- 락 키를 공연, 좌석, 주문, 사용자 구매 시도 단위로 나눌 수 있어 보호 범위를 비교적 유연하게 설계할 수 있다.

###### 이 시나리오에서의 단점

- Redis 락은 임계 구역 진입만 제어할 뿐, 재고 차감이나 주문 상태 변경의 성공을 보장하지 않으므로 DB에서 최종 조건을 다시 검증해야 한다.
- TTL 만료, Redis 장애, 네트워크 지연이 생기면 락 상태와 실제 DB 상태가 어긋날 수 있다.
- 특정 공연이나 좌석 구역을 하나의 락 키로 크게 묶으면, Redis 락 자체가 병목이 되어 처리량이 제한될 수 있다.
- Redis가 장애 나면 구매 흐름 전체의 병목이나 SPOF가 될 수 있으므로, Redis Cluster/Sentinel 같은 고가용성 구성이 필요해 비용이 크다.
- Redis 락 상태와 DB의 재고/주문 상태가 어긋날 수 있으므로, 최종 초과 판매 방지는 DB 조건부 update와 unique constraint가 맡고, 불일치가 생기면 상태 재확인과 복구 처리 전략이 필요해 구조가 복잡해진다.

---

##### 4.3.3 Optimistic Lock, 낙관적 락

###### 이 시나리오에서의 장점

- 결제 webhook, 예약 만료 worker, 재처리 worker가 같은 주문 상태를 중복 변경하는 것을 막기 좋다.
- 사용자별 주문 row처럼 경합이 낮은 데이터에서는 DB 락 대기를 크게 만들지 않고 상태 전이를 보호할 수 있다.

###### 이 시나리오에서의 단점

- 오픈 직후 특정 공연 재고 row에 요청이 집중되면 version 충돌이 폭발적으로 늘어난다.
- 재고 차감 방식으로 사용시 실패 요청이 재시도되면서 DB update 시도가 반복되면, 재시도 부하가 커질 수 있다.

---

##### 4.3.4 Redis Atomic Counter / Lua Script

###### 이 시나리오에서 1차 선택으로 보기 어려운 이유

- Redis에서 재고 확인과 차감을 원자적으로 처리할 수는 있지만, Redis 값과 DB의 주문/좌석 상태가 어긋날 수 있다. 최종 정합성을 DB에서 다시 보장해야 한다면, Redis를 재고의 단일 진실 공급원처럼 두는 방식은 이 시나리오에서 부담이 크다.
- Redis 장애, persistence 설정 문제, failover 과정에서 재고 값 유실이나 중복 처리 가능성을 고려해야 한다.
---

#### 4.4 이 시나리오에서의 선택 방향

정확히 1만 명에게만 판매하려면 10만 명의 요청을 모두 DB 락 경합으로 보내면 안 된다. 재고 차감이나 좌석 점유 같은 짧은 임계 구역은 Redis 같은 외부 분산 락으로 보호하고, 최종 정합성은 DB 조건부 update와 unique constraint로 다시 보장하는 방향이 적합하다.

```
Redis lock 획득
  -> DB transaction 짧게 시작
    -> 좌석/재고 가능 여부 확인
    -> 주문 PENDING 생성
    -> 좌석/재고를 expires_at 있는 임시 예약 상태로 변경
  -> DB transaction 종료
Redis lock 해제

외부 결제 API 호출

결제 완료 webhook
  -> order 상태가 PENDING이고 예약이 유효할 때만 PAID/CONFIRMED 전이
  -> 중복 webhook은 idempotency key로 무시
```

DB pessimistic lock은 특정 좌석 확정처럼 좁은 구간에는 쓸 수 있지만, 재고 차감의 주력 방식으로 쓰면 DB 커넥션과 row lock 대기 시간이 길어질 수 있다. Optimistic lock은 재고 차감처럼 충돌이 집중되는 구간에는 재시도 비용이 커지지만, 결제 상태나 예약 상태처럼 개인 주문 단위로 나뉘는 row에는 보조적으로 쓰기 좋다.

즉, 동시성 전략만 놓고 보면 다음 조합이 가장 균형이 좋다.

1. Redis 외부 분산 락으로 짧은 재고 임계 구역 보호
2. DB 조건부 update로 1만 석 초과 차감 방지
3. 좌석 단위 unique constraint로 중복 배정 방지
4. idempotency key로 중복 요청 방지
5. 결제/예약/주문 상태는 optimistic lock으로 중복 webhook과 재처리 방어

외부 결제 API가 포함된 흐름에서는 DB transaction이나 lock을 외부 API 호출까지 길게 유지하지 않는다.
외부 API는 지연, 타임아웃, 중복 응답, 응답 유실이 발생할 수 있으므로 transaction 안에 넣으면 DB connection과 row lock을 오래 점유하게 된다. 

그래서 외부 API 결제 호출은 tx1과 tx2사이의 트랜잭션 경계에 위치해 있으며 이는 lock이 아니라 version check, snapshot, 상태 전이 조건으로 막고 감사하는 것이 좋다.

```
1. TX1: balance 상태와 금액을 검증한다.
2. TX1: 사용할 금액을 `available_balance`에서 `held_balance`로 이동한다.
3. TX1: hold/payment row에 `PENDING`, `expires_at`, `balance_version`, 주요 상태 snapshot을 저장한다.
4. TX1: commit한다.
5. 외부 결제 API를 호출한다.
6. TX2: hold/payment row가 여전히 유효한지 확인한다.
7. TX2: version 또는 snapshot 기반으로 확정 가능한 상태인지 다시 검증한다.
8. TX2: 성공이면 `CONFIRMED`, 실패/만료면 `RELEASED`로 상태 전이한다.
9. TX2: commit한다.
```

#### 4.5 선택한 조합의 Trade-off

- Redis 락도 특정 공연 전체를 하나의 락 키로 잡으면 병목이 될 수 있다.
  - 보완: 락 범위를 좌석 점유나 재고 차감 같은 최소 임계 구역으로 제한한다.
- Redis 장애, TTL 만료, 네트워크 지연으로 락과 DB 상태가 어긋날 수 있다.
  - 보완: DB 조건부 update, unique constraint, idempotency key로 최종 정합성을 한 번 더 보장한다.
- 분산 락은 공정한 순서 보장 장치가 아니다.
  - 보완: 선착순 순서가 중요하다면 3번의 대기열이나 순번 발급 전략에서 별도로 보장해야 한다.
- Optimistic lock은 주문/결제 상태 보호에는 적합하지만, 중복 webhook이나 재처리가 몰리면 실패와 재시도 처리가 필요하다.
  - 보완: 재시도 횟수, 상태 전이 조건, 멱등 처리 결과 저장 정책을 함께 둔다.
- 앞단에 queue를 두더라도 여러 API 서버가 동시에 같은 재고 차감 요청을 처리하면 DB 부하가 다시 집중될 수 있다.
  - 보완: queue에서 방출하는 속도를 DB 처리량 기준으로 제한하거나 DB 요청이 가기전 queue를 추가적으로 도입할 수 있다.
