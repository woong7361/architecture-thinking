## 핵심 엔지니어링 요구사항별 해결 방식 초안

### 2.1 재고 정합성 보장

해결 방식:
- DB의 재고 테이블에서 조건부 업데이트를 사용한다.
  - 예: `remaining_count > 0`일 때만 차감
- 좌석 단위 예매라면 좌석 ID에 대해 unique constraint를 둔다.
  - 예: `seat_id`가 이미 확정된 주문에 중복 연결되지 않도록 제약
- 최종 판매 성공 상태의 주문 수가 1만 건을 넘지 않도록 DB 레벨에서 검증한다.

핵심:
- 애플리케이션 로직만 믿지 않고, DB의 원자적 연산과 제약조건으로 마지막 방어선을 둔다.

### 2.2 원자적 처리 보장

해결 방식:
- 좌석 임시 점유, 주문 생성, 재고 차감은 하나의 DB 트랜잭션 안에서 처리한다.
- 결제는 외부 시스템이므로 DB 트랜잭션에 직접 묶기보다 주문 상태를 단계적으로 관리한다.
  - 예: `PENDING_PAYMENT -> PAID -> CONFIRMED`
- 결제 성공 후 좌석 확정에 실패하는 경우를 대비해 보상 로직을 둔다.
  - 예: 결제 취소, 좌석 점유 해제, 주문 실패 처리

핵심:
- 내부 DB 상태 변경은 트랜잭션으로 묶고, 외부 결제 연동은 상태 전이와 보상 처리로 일관성을 맞춘다.

### 2.3 동시 요청 제어

해결 방식:
- DB Lock, Redis Lock, 또는 원자적 재고 차감 연산을 사용한다.
- 동일 좌석이나 동일 재고에 대해 여러 요청이 동시에 접근해도 하나의 요청만 성공하도록 제어한다.
- 같은 사용자의 중복 클릭이나 재시도는 idempotency key로 한 번만 처리한다.

가능한 대안:
- DB Lock:
  정합성은 강하지만 트래픽이 많으면 병목이 될 수 있다.
- Redis Lock:
  빠르지만 락 만료, Redis 장애, 네트워크 문제를 신중히 다뤄야 한다.
- Atomic Update:
  `UPDATE inventory SET count = count - 1 WHERE count > 0` 같은 방식으로 단순 재고 차감에는 효과적이다.

핵심:
- 동시에 들어온 요청을 모두 병렬로 성공시키는 것이 아니라, 재고 차감 구간만큼은 안전하게 직렬화하거나 원자적으로 처리해야 한다.

### 2.4 트래픽 제어

해결 방식:
- 대기열을 두어 모든 사용자가 한 번에 구매 API로 들어오지 않게 한다.
- Queue 또는 Waiting Room을 통해 처리 가능한 수만 순차적으로 통과시킨다.
- API 서버는 수평 확장하고, 정적 리소스는 CDN으로 분산한다.
- 구매/결제 같은 핵심 구간에는 rate limit을 적용한다.

핵심:
- 10만 명의 요청을 모두 핵심 트랜잭션 구간으로 보내지 않고, 시스템이 감당 가능한 속도로 흘려보낸다.

### 2.5 실패 복구

해결 방식:
- 주문과 좌석에 명확한 상태값을 둔다.
  - 주문: `PENDING`, `PAID`, `CONFIRMED`, `FAILED`, `CANCELED`
  - 좌석: `AVAILABLE`, `HELD`, `SOLD`
- 임시 점유 좌석에는 만료 시간을 둔다.
  - 결제가 일정 시간 안에 완료되지 않으면 좌석을 다시 해제한다.
- 결제 성공 후 좌석 확정 실패 같은 불일치는 보상 트랜잭션으로 처리한다.
- 메시지 큐를 사용한다면 outbox pattern으로 이벤트 유실을 방지한다.

주의:
- 외부 결제 시스템까지 포함한 2-phase commit은 현실적으로 복잡하고 잘 쓰기 어렵다.
- 보통은 Saga 패턴, 상태 전이, 보상 처리로 최종 일관성을 맞춘다.

핵심:
- 실패를 예외 상황으로만 보지 않고, 주문/좌석/결제 상태를 추적 가능한 상태 머신으로 설계해야 한다.

## 요약 매핑

- 재고 정합성 보장:
  DB 원자적 update, unique constraint, 재고/좌석 상태 검증
- 원자적 처리 보장:
  DB transaction, 주문 상태 전이, 결제 후 보상 처리
- 동시 요청 제어:
  DB Lock, Redis Lock, atomic update, idempotency key
- 트래픽 제어:
  대기열, rate limit, queue 기반 순차 진입, 서버 수평 확장
- 실패 복구:
  주문/좌석 상태 스키마, TTL 기반 좌석 점유 만료, Saga, outbox pattern, 보상 트랜잭션




### 핵심 엔지니어링 요구사항을 기술적 축으로 재정리

#### 1. 정합성 보장

목표:
- 1만 석을 초과해서 판매되지 않아야 한다.
- 동일 좌석이 중복 배정되지 않아야 한다.
- 결제 성공과 좌석 확정 상태가 어긋나지 않아야 한다.

해결 방향:
- DB Lock
- Optimistic Lock
- Atomic Update
- Redis Atomic Counter / Lua

보조 안전장치:
- DB Transaction
- Unique Constraint
- Idempotency Key


#### 2. 트래픽 제어

목표:
- 10만 명의 요청이 한 번에 핵심 처리 구간으로 들어오지 않게 해야 한다.
- DB, 결제, 좌석 확정 API에 부하가 집중되지 않게 해야 한다.
- 사용자가 대기 상태를 예측 가능하게 인지할 수 있어야 한다.

해결 방향:
- Waiting Room
- Queue
- Rate Limit
- 서버 수평 확장
- CDN / Cache
- 구매 단계 진입 제한
md


#### 3. 실패 복구와 상태 관리

목표:
- 결제 실패, 타임아웃, 서버 장애가 발생해도 좌석과 주문 상태를 복구할 수 있어야 한다.
- 중간 상태가 남더라도 최종적으로 일관된 상태로 수렴해야 한다.

해결 방향:
- 주문/좌석 상태 머신
- 좌석 임시 점유 TTL
- Saga Pattern
- 보상 트랜잭션
- Outbox Pattern
- 재처리 worker




##### 1.2 프로세스 정합성 / 분산 트랜잭션 정합성
질문:
- 좌석 점유는 성공했는데 결제가 실패하면 어떻게 할 것인가?
- 결제는 성공했는데 주문 확정이 실패하면 어떻게 할 것인가?
- 메시지 발행은 실패했는데 DB 상태만 바뀌면 어떻게 할 것인가?
- 서버 장애 후 중간 상태를 어떻게 복구할 것인가?

주요 방식:
- 주문/좌석 상태 머신
- Saga Pattern
- 보상 트랜잭션
- Outbox Pattern
- 재처리 Worker
- TTL 기반 임시 점유
