# Task 6-1. 멱등성(Idempotency)

## 1. 멱등성의 정의

멱등성이란 같은 요청을 한 번 보내든 여러 번 보내든 시스템의 최종 결과가 동일하게 유지되는 성질이다.

백엔드 API 관점에서는 특히 "같은 요청이 재시도되더라도 주문, 결제, 재고, 쿠폰 같은 상태 변화가 중복으로 발생하지 않게 하는 것"으로 이해할 수 있다. 예를 들어 결제 승인 요청이 네트워크 문제로 두 번 들어오더라도 실제 결제는 한 번만 성공해야 한다.

주의할 점은 멱등성이 이론적으로는 응답 본문이 아니라 시스템 상태에 대한 효과가 동일한지를 중심으로 판단된다는 것이다. 다만 결제 API처럼 클라이언트가 응답을 기준으로 후속 동작을 결정하는 경우에는, 같은 멱등성 키와 같은 요청 내용에 대해 가능하면 이전과 같은 성공 응답을 반환하도록 설계하는 것이 안전하다.

## 2. 왜 사용하는가

결제와 주문 시스템에서는 요청이 한 번만 온다고 가정하면 위험하다. 실제 운영 환경에서는 다음 상황이 자주 발생한다.

- 사용자가 결제 버튼을 여러 번 누른다.
- 모바일 네트워크가 불안정해서 클라이언트가 같은 요청을 재시도한다.
- 서버가 결제 처리는 완료했지만 응답을 보내기 전에 장애가 난다.
- PG사 웹훅이 같은 결제 성공 이벤트를 여러 번 보낸다.
- 메시지 큐에서 같은 이벤트가 중복 소비된다.

멱등성을 사용하지 않으면 같은 주문에 대해 결제가 두 번 승인되거나, 재고가 두 번 차감되거나, 쿠폰과 포인트가 중복 사용될 수 있다. 결제/주문 도메인에서 이런 문제는 단순한 버그가 아니라 정산 오류, 고객 문의, 환불 처리, 법적 분쟁으로 이어질 수 있다.

따라서 멱등성은 "중복 요청을 없애는 기능"이라기보다, 중복 요청이 오더라도 비즈니스 결과가 망가지지 않도록 막는 백엔드의 방어 설계라고 보는 것이 맞다.

## 3. 보통 어떤 경우에 사용하는가

멱등성은 모든 연산에 대해 이야기할 수 있는 성질이지만, 실무에서는 주로 서버의 비즈니스 상태를 변경하거나 외부 시스템에 부작용을 일으키는 요청에 명시적으로 적용한다. 단순 조회 API는 보통 이미 멱등적인 성격을 가지므로 별도의 중복 방지 설계를 추가하지 않는 경우가 많다.

멱등적인 성질을 가지는 일반적인 API 예시는 다음과 같다.

- 특정 리소스를 조회하는 `GET` API
- 특정 리소스를 같은 값으로 전체 갱신하는 `PUT` API
- 특정 리소스를 삭제하는 `DELETE` API

다만 `GET`은 보통 서버의 비즈니스 상태를 변경하지 않는 안전한 조회 요청이므로, 추가 구현 방식보다 HTTP 메서드 자체의 성질로 이해하는 경우가 많다.

결제/주문 도메인에서 멱등성을 더 신경 써서 설계해야 하는 대표적인 사용 사례는 다음과 같다.

- 주문 생성 API
- 결제 승인 API
- 결제 취소 또는 환불 API
- 재고 차감 API
- PG사 웹훅 처리
- 메시지 큐 이벤트 소비

특히 결제/주문 도메인에서는 "돈, 재고, 혜택"처럼 한 번만 처리되어야 하는 자원에 멱등성을 적용해야 한다.

## 4. 멱등성을 구현하는 큰 방향과 대표 방법

멱등성 구현은 크게 두 축으로 나눠 볼 수 있다.

첫째, 중복 요청을 식별하는 방식이다. 같은 요청이나 같은 이벤트를 구분할 수 있는 고유 식별자를 저장하고, 이미 처리한 식별자가 다시 들어오면 새로 처리하지 않는다.

대표 예시는 다음과 같다.

- `Idempotency-Key`
- PG 거래 ID
- 웹훅 `event_id`
- 메시지 `event_id`
- `request_id`
- `inbox_events` 테이블

둘째, 비즈니스 효과가 중복 반영되지 않도록 상태와 연산을 설계하는 방식이다. 중복 요청이 들어오더라도 현재 상태와 비즈니스 규칙을 확인해 결제, 주문, 재고, 쿠폰 같은 효과가 한 번만 반영되도록 한다.

대표 예시는 다음과 같다.

- 연산 자체를 멱등적으로 설계
- 상태 전이 조건 검사
- 이미 처리된 상태면 재반영하지 않기
- 조건부 `UPDATE`
- 성공 결제는 주문당 하나만 허용
- 필요 시 락이나 optimistic lock으로 동시성 보조

DB 유니크 제약은 어떤 컬럼에 거느냐에 따라 두 축 모두에 사용될 수 있다. `event_id`나 `request_id`에 걸면 식별자 기반 중복 제거이고, `order_id`와 성공 결제 상태에 걸면 비즈니스 규칙을 DB에서 강제하는 방식이다.

실제 결제/주문 시스템에서는 이 두 축을 따로 선택하기보다 함께 사용한다. 예를 들어 결제 승인 API는 `Idempotency-Key`로 중복 요청을 식별하고, DB 유니크 제약과 상태 전이 조건으로 실제 결제 성공 처리가 중복 반영되지 않게 막는다.

이 두 축을 기준으로 결제/주문 도메인에서 특히 자주 쓰는 대표 구현 방법은 다음 3가지다.

### 4-1. Idempotency-Key 방식

클라이언트가 요청마다 고유한 `Idempotency-Key`를 보내고, 서버가 이 키와 처리 결과를 저장하는 방식이다.

예를 들어 결제 승인 요청에서 다음과 같은 키를 보낼 수 있다.

```http
POST /payments
Idempotency-Key: order-123-payment-attempt-1
```

서버는 요청을 처리하기 전에 해당 키가 이미 저장되어 있는지 확인한다.

- 처음 들어온 키라면 처리 상태를 `PROCESSING`으로 저장한 뒤 결제를 진행한다.
- 이미 성공한 키라면 결제를 다시 하지 않고 기존 성공 응답을 반환한다.
- 아직 처리 중인 키라면 `409 Conflict` 또는 "처리 중" 응답을 반환한다.
- 실패한 키라면 실패 유형에 따라 재시도 가능 여부를 판단한다.

이 방식에서는 키만 저장하면 부족할 수 있다. 같은 키가 이전과 같은 비즈니스 요청을 의미하는지 확인할 수 있어야 하기 때문이다. 이를 위해 요청 본문 해시를 저장하거나, 주문 ID, 금액, 통화, 결제 수단, API 종류 같은 핵심 필드를 함께 저장해 비교하는 정책을 둘 수 있다. 같은 키인데 요청 의미가 다르면 잘못된 재사용으로 보고 거절하는 것이 안전하다.

### 4-2. DB 유니크 제약 조건 방식

중복되면 안 되는 비즈니스 키에 DB 유니크 제약을 거는 방식이다. 예를 들어 같은 웹훅 이벤트를 두 번 처리하지 않기 위해 `event_id`를 유니크하게 저장하거나, 같은 PG 거래가 두 번 저장되지 않도록 `pg_transaction_id`에 유니크 제약을 둘 수 있다.

또한 "한 주문에는 성공 결제가 하나만 있어야 한다"는 규칙도 DB 제약으로 보호할 수 있다. 다만 모든 결제 시도에 단순히 `order_id` 유니크 제약을 걸면 실패 후 재시도까지 막을 수 있으므로, 실제로는 성공 결제 기준으로만 중복을 막도록 설계해야 한다.

이 방식의 장점은 애플리케이션 코드에서 실수하더라도 DB가 마지막 방어선 역할을 한다는 점이다. 단순히 조회 후 저장하는 방식만으로는 동시 요청을 막기 어렵기 때문에, 유니크 제약과 충돌 시 기존 데이터 조회를 함께 사용하는 것이 안전하다.

### 4-3. 상태 전이 조건 검사 방식

주문과 결제는 상태 머신으로 관리하는 것이 좋다.

예를 들어 주문 상태가 다음과 같다고 하자.

```text
CREATED -> PAYMENT_PENDING -> PAID
```

이미 `PAID`인 주문에 결제 성공 이벤트가 다시 들어오면 결제를 다시 반영하지 않고 "이미 처리된 이벤트"로 다뤄야 한다. 이를 위해 상태 변경 시 현재 상태 조건을 함께 확인한다.

```sql
UPDATE orders
SET status = 'PAID'
WHERE id = :order_id
  AND status = 'PAYMENT_PENDING';
```

영향받은 row가 1개라면 이번 요청이 상태 변경에 성공한 것이다. 0개라면 이미 다른 요청이 처리했거나 현재 상태가 결제 완료로 바뀔 수 없는 상태라는 뜻이다.

이 방식은 중복 웹훅, 중복 이벤트 소비, 동시 요청 처리에서 특히 중요하다.

## 5. 사용 시 주의점

첫째, 멱등성 키는 요청의 의미 단위와 맞아야 한다. 같은 주문의 같은 결제 시도에는 같은 키를 사용해야 하지만, 다른 결제 시도나 다른 금액의 요청까지 같은 키를 쓰면 안 된다.

둘째, 같은 `Idempotency-Key`로 다른 요청 내용이 들어오는 경우를 막아야 한다. 이를 위해 요청 본문 해시, 주문 ID, 금액, 결제 수단 같은 핵심 값을 함께 저장하고 비교해야 한다.

셋째, 처리 중 상태에 대한 정책이 필요하다. 첫 번째 요청이 아직 끝나지 않았는데 같은 키의 요청이 다시 들어오면 기다리게 할지, `409 Conflict`를 반환할지, 현재 처리 상태를 반환할지 결정해야 한다.

넷째, 멱등성 기록의 보관 기간을 정해야 한다. 보관 기간이 너무 짧으면 늦게 도착한 재시도 요청이나 웹훅 중복을 막지 못한다. 결제 도메인에서는 정산, 환불, 고객 문의까지 고려해 충분한 기간을 두는 것이 좋다.

다섯째, 멱등성은 "정확히 한 번 실행"을 자동으로 보장하지 않는다. 외부 PG 호출, 내부 DB 저장, 메시지 발행 사이에서 장애가 날 수 있으므로 트랜잭션 경계와 복구 절차를 함께 설계해야 한다.

## 6. 멱등성이 보장하지 않는 것

멱등성은 요청이 반드시 성공한다는 뜻이 아니다. 같은 요청을 여러 번 보내도 계속 실패할 수 있다.

또한 외부 PG사가 결제를 정확히 한 번만 처리한다는 뜻도 아니다. 우리 시스템은 PG 거래 ID 조회, 결제 상태 확인 API, 웹훅 이벤트 중복 방지 등을 통해 외부 시스템과의 불일치를 복구할 수 있어야 한다.

그리고 멱등성만으로 모든 동시성 문제가 해결되지는 않는다. 동시에 두 요청이 들어오는 상황에서는 DB 유니크 제약, 조건부 업데이트, 트랜잭션 같은 동시성 제어가 필요하다.

## 7. 결제 요청 예시 시나리오

예를 들어 사용자가 주문 `order-123`에 대해 결제 요청을 보냈다고 하자.

```text
1. 클라이언트가 Idempotency-Key와 함께 결제 승인 요청을 보낸다.
2. 서버가 멱등성 키를 PROCESSING 상태로 저장한다.
3. 서버가 PG사에 결제 승인을 요청한다.
4. PG 결제는 성공했지만 서버 응답이 클라이언트에 도착하기 전에 타임아웃이 발생한다.
5. 클라이언트가 같은 Idempotency-Key로 다시 요청한다.
6. 서버는 기존 결제 성공 결과를 조회하고, PG 결제를 다시 호출하지 않은 채 기존 성공 응답을 반환한다.
```

이 흐름이 없으면 클라이언트의 정상적인 재시도가 중복 결제로 이어질 수 있다.

## 8. 실무 설계 요약

결제/주문 도메인에서는 하나의 방법만으로 멱등성을 완성하기 어렵다. 보통 다음 방식을 조합한다.

- 결제 승인 API에는 `Idempotency-Key`를 사용한다.
- 결제 테이블에는 `pg_transaction_id`를 유니크하게 관리하고, 주문별 성공 결제는 부분 유니크 제약이나 별도 성공 결제 기록으로 하나만 허용한다.
- 웹훅 이벤트는 `event_id`를 저장해 중복 처리를 막는다.
- 주문과 결제 상태는 조건부 업데이트로 전이시킨다.
- 재고, 쿠폰, 포인트처럼 중복 처리되면 안 되는 자원도 별도의 중복 방지 키나 이력 테이블을 둔다.

결론적으로 멱등성은 프론트엔드에서 버튼을 비활성화하는 정도로 해결할 문제가 아니다. 프론트엔드 처리는 사용자 경험을 개선할 수는 있지만, 최종적으로 중복 결제와 중복 주문을 막는 책임은 백엔드 API, DB 제약 조건, 상태 전이 설계가 함께 가져야 한다.
