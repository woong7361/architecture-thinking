# 단계 1 — 세 run을 묶은 결과

세 run 모두 통과했고, 세 run 모두 자기 평가의 예측 숫자가 결과와 정확히 일치했다. **기대했던 모양의
어긋남은 0건이다.** 테스트가 빨간불인데 AI가 맞다고 우긴 자리는 없었다.

| run | 모델 | 기준선 | 방식 | 결과 | 예측 일치 |
| --- | --- | --- | --- | --- | --- |
| 1 | 기본 | 보조 메서드 남아 있음 | 사용자 행 잠금 + 유니크 제약 + 재시도 | 10/10 통과 | 5/5 |
| 2 | sonnet | 보조 메서드 남아 있음 | 사용자 행 잠금 한 줄 | 10/10 통과 | 5/5 |
| 3 | 기본 | 보조 메서드 제거 | 사용자 행 잠금 + 유니크 제약 + 재시도 | 10/10 통과 | 5/5 |

## 셋이 같은 자리로 갔고, 힌트 때문이 아니었다

세 run 모두 `kata_users` 행을 `PESSIMISTIC_WRITE`로 잠그고, 그 잠금을 조회 앞에 뒀다.

run 1과 2는 기준선에 남아 있던 `lockUserForUpdate`를 호출했다. 그 미사용 메서드가 힌트였을 수 있어서
run 3은 그것을 제거한 기준선에서 같은 모델과 같은 지시문으로 돌렸는데, `lockSubscriber`를 직접 만들어
같은 일을 했다. **구멍을 막아도 답이 바뀌지 않았다.**

그래서 수렴의 이유는 문제의 구조로 보인다. 막아야 하는 것이 "아직 없는 행을 둘이 따로 만드는 일"이라
잠글 대상이 없고, 두 요청이 공통으로 쥐는 행은 사용자뿐이다. 이것은 F-3에서 사람이 내린 판단과 같은
결론이기도 하다.

## 어긋난 자리는 극성이 달랐다

제출물이 요구하는 "AI의 자기 평가와 재현 테스트 결과가 어긋난 지점"을 극성 그대로 찾으면 0건이다.
대신 세 run에서 반복된 다른 어긋남이 있다. **자기 평가가 보장한다고 적은 범위가 테스트가 판정한 범위보다
넓다.**

run 1과 3은 자기 평가 1·2절에 "줄 세우기가 실패하면 유니크 제약이 INSERT를 거부하고 재시도가 새
트랜잭션에서 다시 읽는다"를 적었다. 그 문장은 구현의 절반을 설명한다. 그런데 **그 절반은 한 번도 실행되지
않았다.**

근거는 둘이다. 로그에 `1062` 중복 키 위반과 교착이 0건이고, 반환 ID가 조건마다 최솟값부터 최댓값까지
정확히 100칸이다. 실패한 INSERT도 AUTO_INCREMENT를 소비하므로 회차마다 INSERT가 한 번씩만 일어났다는
뜻이다.

run 2가 그것을 뒤에서 확인한다. 안전망 없이 잠금 하나만 두고도 10/10 통과했다. 같은 테스트가 안전망이
있는 구현과 없는 구현을 구별하지 못한다는 뜻이다.

그래서 세 run의 초록불은 셋 다 같은 것을 말한다. "사용자 행 잠금이 이 조건에서 중복을 막았다"까지다.
자기 평가가 말한 "줄 세우기가 실패해도 안전하다"는 테스트 밖에 있다.

## 테스트가 판정하지 않은 주장 목록

세 run의 자기 평가에서, 구현이 기대고 있지만 이 테스트가 참·거짓을 가르지 않은 문장을 모았다. 단계 2의
주장 후보이고, 주장 목록은 하네스가 뽑으므로 하네스가 같은 자리를 뽑는지 대조하는 데 쓴다.

| 문장 | 어느 run이 적었나 | 테스트가 가르는가 |
| --- | --- | --- |
| InnoDB의 읽기 뷰는 트랜잭션의 첫 일반 읽기에서 만들어지고, 잠금 읽기는 읽기 뷰를 만들지 않는다 | 1, 2, 3 | 간접. 통과가 이것과 모순되지 않을 뿐 |
| `PESSIMISTIC_WRITE`가 한 문장의 `SELECT ... FOR UPDATE`로 나간다 | 1 | 아니다 |
| 조회를 `FOR UPDATE`로 하면 빈 인덱스 구간의 갭 잠금이 다른 사용자끼리 교착을 만든다 | 3 | 아니다. 그 경로를 피했다 |
| 이미 커밋된 행을 잠그면 갭 잠금이 생기지 않는다 | 3 | 아니다 |
| 유니크 인덱스는 NULL을 중복으로 보지 않는다 | 1, 3 | 아니다. run 1이 별도 컨테이너로 따로 확인했다 |
| `Propagation.NOT_SUPPORTED`는 기존 트랜잭션을 보류하고 트랜잭션 없이 실행한다 | 1, 3 | 아니다 |
| IDENTITY 전략은 `persist` 시점에 INSERT를 보낸다 | 1, 3 | 아니다 |
| 1062가 `DataIntegrityViolationException`으로 변환된다 | 1, 3 | 아니다. 예외 경로가 실행되지 않았다 |
| 인스턴스가 몇 개여도 된다 | 1 | 아니다. 테스트는 한 인스턴스다 |
| `MAX_ATTEMPTS = 3` | 1, 3 | 아니다. 구현자가 근거 없이 골랐다고 적었다 |

마지막 둘이 선택 주장이고 나머지는 사실 주장이다. 열 줄 중 테스트가 직접 가르는 것은 하나도 없다.
이것이 단계 2가 필요한 이유다.

## 내가 틀린 것 둘

**가림을 파일 단위로만 했다.** `AlertRepository`가 F-3의 보조 메서드 셋을 들고 있었고 run 1과 2가 그것을
호출했다. run 3으로 결과가 바뀌지 않는 것을 확인했지만, 확인하기 전까지 두 run의 전제는 내가 적은 것과
달랐다. 가림 목록은 파일이 아니라 식별자 단위로 훑어야 했다.

**원본 해시로 판정하려 했다.** 체크아웃의 줄 끝 변환만으로 멀쩡한 run이 탈락한다. `git status`의 변경
목록과 줄 끝을 정규화한 해시를 함께 보는 방식으로 고쳤다. 같은 허점이 하네스의 인용 대조에도 있어
설계의 `citation_absent`에 정규화를 넣어야 한다.
