# 자기 평가 양식

구현을 마친 뒤, **테스트를 돌리기 전에** 채운다. 이 순서가 이 단계의 전부다. 실패 로그를 보고 쓰면 평가가
결과에 맞춰지고, 자기 평가와 테스트가 어긋난 자리가 사라진다.

모르는 칸은 모른다고 적는다. 확신이 낮은 것을 단정하면 어긋남이 어디서 생겼는지 가릴 수 없다.

## 1. 무엇을 막았는가

어떤 경합을 코드의 어느 자리에서 막는지 적는다. 두 요청이 어떤 순서로 들어왔을 때 무엇이 한쪽을 멈추게
하는지가 드러나야 한다.

## 2. 어느 전제에 기대는가

| 전제 | 값 |
| --- | --- |
| DB와 격리 수준 | |
| 애플리케이션 인스턴스 수 | |
| 커넥션 풀 크기 | |
| 그 밖에 기대는 것 | |

## 3. 테스트가 어떻게 나올 것인가

조건마다 숫자를 미리 적는다. 조건 이름은 `AlertSubscriptionTest`의 것을 그대로 쓴다.

| 조건 | 중복 회차 | 요청 오류 회차 |
| --- | ---: | ---: |
| `NEW_SEQUENTIAL` | | |
| `NEW_TOGETHER` | | |
| `NEW_UNCOORDINATED` | | |
| `EXISTING_TOGETHER` | | |
| `DIFFERENT_USERS` | | |

요청 오류 칸을 비우지 않는다. 중복을 0으로 만들면서 요청을 실패시키는 구현이 있고, 그 경우 중복 숫자만으로는
통과와 실패가 갈리지 않는다.

## 4. 막지 못하는 것

이 구현이 보장하지 않는 범위를 적는다. 없으면 없다고 적되, 어떤 조건에서도 깨지지 않는다는 뜻으로 적는
것인지 확인한다.

## 5. 확신이 낮은 자리

구현 중 근거 없이 고른 것, 문서를 확인하지 않고 그렇게 동작한다고 가정한 것을 적는다.
