## 변경이 한 줄이다

`subscribe`의 첫 줄에 `repository.lockUserForUpdate(command.userId())`를 넣은 것이 전부다. 스키마는
고치지 않았다.

run 1은 사용자 행 잠금과 유니크 제약 둘을 뒀는데 run 2는 잠금 하나만 뒀다. 두 run이 같은 자리를 골랐고
run 2는 그 자리를 최소 변경으로 닫았다.

## 두 run이 같은 자리로 간 이유가 내 가림의 구멍일 수 있다

`AlertRepository`에 `lockUserForUpdate`가 미사용 상태로 남아 있었다. `PESSIMISTIC_WRITE`로 사용자 행을
잠그는 한 줄짜리 메서드이고, 기준선에서 이것을 쓰는 코드는 내가 제거한 F-3의 서비스뿐이었다. 낙관적 락의
재료인 `currentUserVersion`과 `advanceUserVersion`도 함께 남아 있었다.

파일 단위로만 가려서 메서드 단위의 흔적을 못 봤다. 그래서 두 run이 조건 없이 그 자리를 찾아낸 것인지,
호출만 하면 되는 메서드가 있어서 간 것인지 이 두 run으로는 가를 수 없다. [blocked-paths.md](../blocked-paths.md)의
`놓친 것` 절에 기록했다.

run 3은 그 셋을 제거한 기준선에서 같은 모델에 같은 지시문으로 돌린다. 모델과 지시문을 고정했으니 달라진
것은 구멍 하나다.

## 자기 평가에서 확신이 낮다고 적은 자리

InnoDB의 MVCC 상호작용이다. 잠금 읽기가 스냅샷을 만들지 않으므로 뒤따르는 일반 읽기가 잠금 대기 후에
새 스냅샷을 잡는다는 것을, 일반적으로 알려진 InnoDB 동작에서 추론했고 문서의 특정 구절로 확인하지 않았다고
적었다. 100회 관찰이 뒷받침하지만 문서로 확정된 것은 아니라고 스스로 적었다.

run 1의 자기 평가도 같은 자리를 가장 불안한 곳으로 꼽았다. 두 run이 독립으로 같은 문장에 걸렸으므로
단계 2의 사실 주장 1번 후보다.
