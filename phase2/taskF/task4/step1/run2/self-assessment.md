## 1. 무엇을 막았는가

`AlertService.subscribe`에서 기존 신청 조회(`findActive`)보다 앞에 `repository.lockUserForUpdate(command.userId())`를 추가했다. 이 호출은 `kata_users` 테이블의 해당 사용자 행을 `SELECT ... FOR UPDATE`로 잠근다.

두 요청이 같은 `userId`로 거의 동시에 들어왔을 때: 먼저 커밋을 시작한 트랜잭션이 사용자 행의 쓰기 잠금을 얻고, 뒤의 트랜잭션은 같은 행에 쓰기 잠금을 요청하는 순간 DB 레벨에서 멈춘다(블로킹). 앞선 트랜잭션이 `findActive` → (없으면) `save` → 커밋을 마치고 잠금을 풀 때까지 뒤의 트랜잭션은 그 자리에서 대기하므로, 두 트랜잭션의 "조회 후 삽입" 구간이 겹치지 않는다. 뒤의 트랜잭션이 깨어난 뒤 수행하는 `findActive`는 앞선 트랜잭션이 막 커밋한 행을 보게 되므로 중복 삽입 대신 기존 ID를 반환한다.

막는 자리는 정확히 `AlertService.subscribe` 메서드의 첫 줄(잠금 호출)이다. 그 뒤의 `findActive`/`save`는 코드 변경 없이 그대로 둔다.

## 2. 어느 전제에 기대는가

- **격리 수준**: MySQL InnoDB, `REPEATABLE READ` (현재 `application.properties` 설정 그대로). 잠금 조회(`SELECT ... FOR UPDATE`)는 항상 최신 커밋 데이터를 읽는다는 InnoDB 문서의 동작에 기댄다. 또한 한 트랜잭션에서 "일반(비잠금) 조회"의 스냅샷은 그 트랜잭션 안에서 처음 수행되는 일반 조회 시점에 뜬다는 동작에 기댄다 — `lockUserForUpdate`가 잠금 조회라 스냅샷을 소비하지 않으므로, 잠금이 풀린 뒤 실행되는 `findActive`(이 트랜잭션의 첫 일반 조회)가 그 시점의 최신 커밋을 스냅샷으로 뜬다.
- **DB 엔진**: InnoDB (schema.sql에 이미 지정됨). 행 단위 잠금을 지원해야 한다.
- **잠금 대상 행의 존재**: `kata_users`에 해당 `userId` 행이 이미 있어야 한다. 테스트의 `@BeforeEach`가 사용자 1, 2를 항상 미리 넣어 두므로 이 과제의 테스트 범위 안에서는 성립한다. 신규 가입 등 사용자 행이 없는 경로는 다루지 않는다.
- **애플리케이션 인스턴스 수**: 잠금이 DB 행 잠금이라 애플리케이션 인스턴스 수와 무관하게 동작한다 (단일 인스턴스를 가정하지 않는다).
- **커넥션 풀 크기**: 동시에 대기해야 하는 커넥션 수만큼 풀이 있어야 한다. 테스트는 워커 2개, 풀 크기 4(`application.properties`)이므로 충분하다. 풀이 동시 요청 수보다 작으면 잠금 대기가 아니라 커넥션 획득 대기가 먼저 걸려 타임아웃으로 이어질 수 있다.
- **트랜잭션 전파**: `AlertService.subscribe`가 `@Transactional`이고 그 메서드 안에서만 잠금과 조회·삽입이 일어난다(테스트 쪽에 별도 트랜잭션이 없음을 `@BeforeEach`에서 확인하고 있다). 잠금과 조회·삽입이 같은 트랜잭션, 같은 커넥션에서 실행된다는 전제에 기댄다.
- **데드락 없음**: 한 트랜잭션이 잠그는 행은 항상 하나(`command.userId()`에 해당하는 사용자 행)뿐이라 교차 대기(circular wait)가 생기지 않는다는 전제.

## 4. 막지 못하는 것

- 사용자 행이 애초에 없는 경우(신규 사용자 생성과 알림 신청 사이의 경합)는 다루지 않는다. 이 과제의 스키마와 테스트는 사용자 행이 항상 미리 존재한다고 가정하므로 범위 밖이다.
- 같은 사용자가 **다른 코트/날짜/시간대**로 동시에 신청하는 경우도 모두 같은 사용자 행 하나로 직렬화된다. 업무 규칙상 문제는 없지만(다른 조건은 중복 신청이 아니므로 성능상 과도한 직렬화일 뿐), 서로 다른 조건 간의 동시성까지 세밀하게 허용하지는 않는다.
- DB가 여러 개로 샤딩되어 사용자 행이 복제·분산되는 구조에서는 이 잠금이 전역 직렬화를 보장하지 못한다. 단일 MySQL 인스턴스(테스트 환경과 동일) 전제에서만 유효하다.
- 애플리케이션 재시작 중 커넥션이 끊기며 잠금이 풀리는 경우의 복구 절차는 다루지 않는다(InnoDB가 커넥션 종료 시 잠금을 자동 해제하는 기본 동작에만 기댄다).

## 5. 확신이 낮은 자리

- "잠금 조회가 트랜잭션의 첫 조회일 때, 그 뒤의 일반 조회가 잠금 대기가 풀린 시점을 기준으로 새 스냅샷을 뜬다"는 InnoDB MVCC 동작은 MySQL 문서의 일반 서술(잠금 조회는 항상 최신 커밋을 읽고, 일반 조회의 스냅샷은 트랜잭션 내 첫 일반 조회 시점에 확정된다)을 조합해 추론한 것이다. 이 조합 동작을 공식 문서의 한 문장으로 직접 확인하지는 못했다 — Hibernate가 `entityManager.find(..., PESSIMISTIC_WRITE)`를 실제로 `SELECT ... FOR UPDATE` 하나로, 그리고 그 즉시(지연 없이) DB로 보낸다는 점도 Hibernate 내부 동작을 문서로 재확인하지 않고 일반적으로 알려진 동작으로 가정했다.
- `lockUserForUpdate`가 이미 `AlertRepository`에 준비돼 있었던 이유를 "이 경합을 막기 위한 용도"로 해석했는데, `KataUser`의 주석은 이 필드를 "F-3에서 충돌 감지용"이라고만 적어 두었다. 두 메서드(`lockUserForUpdate`, `currentUserVersion`/`advanceUserVersion`)가 서로 다른(낙관적 잠금) 용도로 준비된 것일 수도 있는데, 이번 수정에서는 비관적 잠금 메서드만 쓰고 낙관적 잠금 메서드 둘은 그대로 미사용 상태로 남겨 두었다. 이것이 과제가 기대한 조합인지는 확신이 낮다.
- 동시성 수치(중복 회차 0, 요청 오류 회차 0)는 실제 실행 전에 적은 예측이다. 타이밍이나 테스트 컨테이너 환경에 따라 실제 수치가 예측과 다를 수 있다.

## 실행 후 메모

- 실제 결과가 3절의 예측과 정확히 일치했다 (5개 조건 모두 중복 0회, 요청 오류 0회, `Tests run: 10, Failures: 0, Errors: 0`).
- 5절에서 확신이 낮다고 적었던 "잠금 조회 뒤 일반 조회가 새 스냅샷을 뜬다"는 추론은 이번 실행 결과(NEW_TOGETHER, NEW_UNCOORDINATED 모두 중복 0)로 간접적으로 뒷받침됐다. 다만 이것은 100회 반복에서 재현된 경합 실패가 없었다는 경험적 확인이고, 문서상 근거를 직접 확인한 것은 아니므로 확신 수준 자체는 바꾸지 않는다.
