# 알림 신청 동시성 자가 점검

## 1. 무엇을 막았는가

막는 자리는 두 곳이다. `AlertService.registerOnce` 의 첫 줄이 사용자 행을 잠가 요청을 줄 세우고,
`schema.sql` 의 유니크 제약이 그 줄 세우기가 실패했을 때 두 번째 행의 INSERT 자체를 거부한다.

요청 A와 B가 같은 사용자·코트·날짜·시간대로 거의 동시에 들어온 경우를 따라가면 이렇게 된다.

1. A가 트랜잭션을 열고 `SELECT ... FROM kata_users WHERE id = 1 FOR UPDATE` 로 사용자 행을 잠근다.
2. B도 트랜잭션을 열고 같은 행을 잠그려다 **여기서 멈춘다.** B는 아직 기존 신청을 조회하지 않았다.
3. A는 기존 신청을 조회해 없음을 확인하고 INSERT 한 뒤 커밋한다. 커밋으로 사용자 행 잠금이 풀린다.
4. B가 잠금을 얻어 진행한다. B의 기존 신청 조회는 B의 트랜잭션에서 처음 수행하는 일반 읽기이므로
   이 시점에 스냅숏이 잡히고, A가 커밋한 행이 보인다. B는 INSERT 하지 않고 A가 만든 ID를 반환한다.

3과 4 사이에 끼어들 수 있는 요청은 없다. 조회와 생성이 한 트랜잭션 안에 있고, 그 트랜잭션에
들어가는 입구를 사용자 행 잠금이 하나로 좁혔기 때문이다.

줄 세우기가 기대대로 동작하지 않으면 두 번째 자리가 받는다. 4에서 B가 A의 행을 못 보고 INSERT 하면
`uq_watching_subscription` 이 1062 로 거절하고, B의 트랜잭션은 되돌아간다. `subscribe` 의 재시도
루프는 트랜잭션 밖에 있으므로(`Propagation.NOT_SUPPORTED`) 되돌린 뒤 새 트랜잭션에서 다시 읽는다.
새 트랜잭션의 스냅숏은 A의 커밋 이후에 잡히니 이번에는 A의 행이 보이고, B는 그 ID를 반환한다.
그래서 중복도 남지 않고 요청도 실패하지 않는다.

유니크 제약은 `status = 'WATCHING'` 인 행에만 1을 주고 나머지는 NULL 로 두는 가상 생성 컬럼
`watching_marker` 위에 걸었다. NULL 은 유니크 검사에서 빠지므로 종료된 신청은 같은 조건으로 여러 건
남을 수 있고, 감시 중인 신청만 조건당 한 건으로 제한된다.

## 2. 어느 전제에 기대는가

**DB와 격리 수준.** MySQL 8.4.8 InnoDB, REPEATABLE READ(Hikari 가 설정하고 테스트가 확인한다).
1번의 4단계는 "InnoDB 의 읽기 뷰는 트랜잭션의 첫 *일반* 읽기에서 만들어지고, 잠금 읽기는 읽기 뷰를
만들지 않는다"는 동작에 기댄다. 이 전제가 깨지면 중복 INSERT 가 발생하지만 유니크 제약과 재시도가
받아내므로 업무 규칙 자체는 유지된다. 유니크 제약은 격리 수준과 무관하게 성립한다.

**애플리케이션 인스턴스 수.** 몇 개여도 된다. 두 방어선 모두 DB 안에 있고 JVM 안에 상태를 두지 않았다.

**커넥션 풀 크기.** 요청 하나가 동시에 잡는 커넥션은 한 개다. 재시도 루프를 `NOT_SUPPORTED` 로 둬서
루프 자신은 트랜잭션도 커넥션도 잡지 않고, 시도마다 `REQUIRES_NEW` 로 하나를 열고 닫는다.
풀이 4이고 작업 스레드가 2, 테스트 스레드가 1이므로 3을 쓴다. 다만 사용자 행 잠금 대기는 커넥션을
붙잡은 채로 기다리므로, 같은 사용자의 동시 요청 수가 풀 크기를 넘는 환경에서는 대기가 풀을 말린다.

**그 밖에.**
- 잠글 `kata_users` 행이 존재한다. 없으면 `entityManager.find` 가 null 을 주고 잠금은 걸리지 않는다
  (그 경우 INSERT 는 외래 키에서 어차피 실패한다).
- Hibernate 가 IDENTITY 전략이라 `persist` 시점에 INSERT 를 보내므로, 제약 위반이 시도 트랜잭션
  안에서 드러난다.
- 1062 가 `DataIntegrityViolationException` 으로 변환되거나, 최소한 원인 사슬에
  `SQLIntegrityConstraintViolationException` 이 들어 있다. 코드는 사슬 전체를 훑어 둘 다 받는다.
- `ddl-auto=validate` 는 엔티티에 매핑되지 않은 `watching_marker` 컬럼을 문제 삼지 않는다.

## 3. 테스트가 어떻게 나올 것인가

| 조건 | 중복 회차 | 요청 오류 회차 |
| --- | ---: | ---: |
| NEW_SEQUENTIAL | 0 | 0 |
| NEW_TOGETHER | 0 | 0 |
| NEW_UNCOORDINATED | 0 | 0 |
| EXISTING_TOGETHER | 0 | 0 |
| DIFFERENT_USERS | 0 | 0 |

NEW_TOGETHER 와 NEW_UNCOORDINATED 는 기준선에서 100회 모두 중복이었다. 사용자 행 잠금이 두 요청을
줄 세우므로 0이 되어야 한다. DIFFERENT_USERS 는 사용자 1과 2가 서로 다른 행을 잠그니 대기 없이 통과한다.
EXISTING_TOGETHER 는 두 요청 모두 조회만 하고 끝나므로 INSERT 가 없다.

요청 오류는 모든 조건에서 0으로 본다. 잠금 대기는 오류가 아니고(기본 `innodb_lock_wait_timeout` 50초,
테스트 한 회차는 그보다 훨씬 짧다), 유니크 제약에 걸린 시도는 재시도가 삼켜서 ID를 반환한다.

## 4. 막지 못하는 것

- **감시 중이 아닌 상태로의 전이는 조율하지 않는다.** 한쪽이 `status` 를 ENDED 로 바꾸는 동안 다른 쪽이
  같은 조건으로 신청하면, 두 요청의 순서는 정해지지 않는다. 결과가 "기존 ID 반환"일지 "새 신청 생성"일지
  타이밍에 달려 있다. 지금 코드에는 종료 경로가 없어 드러나지 않는다.
- **종료된 신청의 중복은 허용한다.** 같은 조건으로 ENDED 가 여러 건 쌓일 수 있다. 설계상 그렇게 뒀다.
- **교착은 재시도하지 않는다.** InnoDB 가 교착을 감지해 한쪽을 되돌리면 `DeadlockLoserDataAccessException`
  이고, 이것은 제약 위반이 아니므로 그대로 호출자에게 올라간다. 지금 구조에서 교착이 생기는 경로를
  찾지는 못했지만 재시도가 덮어 주지도 않는다.
- **세 번을 넘는 충돌은 오류가 된다.** 제약 위반이 3회 연속이면 마지막 예외를 던진다.
- **같은 사용자의 모든 신청이 한 줄로 선다.** 코트와 시간대가 달라도 사용자 행을 공유하므로 직렬화된다.
  정확성은 지키지만 한 사용자의 처리량은 제한된다.
- **잠금 대기 시간에 상한을 두지 않았다.** DB 기본값에 맡겼다. 대기가 길어지면 커넥션을 붙잡는다.

## 5. 확신이 낮은 자리

- **읽기 뷰가 만들어지는 시점.** 1번의 4단계가 여기에 걸려 있는데, 이번 작업에서 MySQL 문서를 다시
  확인하지 않고 "잠금 읽기는 읽기 뷰를 만들지 않는다"고 가정했다. 더 불안한 쪽은 Hibernate 다.
  `entityManager.find(..., PESSIMISTIC_WRITE)` 가 `SELECT ... FOR UPDATE` 한 문장으로 나가는지,
  아니면 일반 SELECT 로 엔티티를 먼저 읽고 잠금 문장을 따로 보내는지 확인하지 않았다. 후자라면 읽기 뷰가
  대기 전에 잡혀 줄 세우기만으로는 중복을 막지 못한다. 유니크 제약과 재시도를 넣은 이유가 이것이다.
- **예외 타입.** 제약 위반이 `persist` 에서 올라오는지 커밋에서 올라오는지, Spring 의 변환이 어느 경계에서
  일어나는지 확인하지 않았다. 그래서 타입을 특정하지 않고 원인 사슬을 훑는 방식으로 피해 갔다.
  이건 확신이 있어서가 아니라 확신이 없어서 넓게 잡은 것이다.
- **가상 생성 컬럼 위의 유니크 인덱스.** NULL 이 유니크 검사에서 빠지는 것은 확신한다. MySQL 8.4 에서
  VIRTUAL 생성 컬럼에 유니크 인덱스를 거는 데 제약이 있는지는 문서를 보지 않았다.
- **MAX_ATTEMPTS = 3.** 근거 없이 골랐다. 측정하지 않았다.
- **`idx_active_lookup` 을 남긴 판단.** 새 유니크 인덱스의 앞 네 컬럼이 조회를 덮으므로 중복일 수 있다.
  실행 계획을 바꾸지 않으려고 그냥 뒀고, 어느 쪽이 나은지 확인하지 않았다.

## 실행 후 메모

1~5절은 실행 전 상태로 둔다. 실행 결과로 달라진 것만 여기 적는다.

**3절 예측은 다섯 조건 모두 맞았다.** `Tests run: 10, Failures: 0, Errors: 0, Skipped: 0`, 전 조건
`duplicates=0 requestErrors=0 contractViolations=0 normal=100`. `overlappingCalls` 는 NEW_SEQUENTIAL 만
0이고 나머지 네 조건은 100이므로, 두 요청이 실제로 겹친 상태에서 통과했다.

**5절의 가장 큰 불안이 해소됐다.** "Hibernate 가 잠금 전에 일반 SELECT 를 보내 읽기 뷰를 먼저 잡는가"가
걱정이었는데, 로그가 그렇지 않다고 말한다. NEW_TOGETHER·NEW_UNCOORDINATED·EXISTING_TOGETHER 는 100회
동안 반환 ID 가 최솟값부터 최댓값까지 정확히 100 구간이고(106~205, 206~305, 306~405), DIFFERENT_USERS
는 사용자 둘이라 회차당 2씩 증가한다. AUTO_INCREMENT 가 한 칸도 건너뛰지 않았다는 뜻이고, 실패한
INSERT 도 값을 소비하므로 **회차마다 INSERT 가 정확히 한 번씩만 일어났다**. 1062 로그도 한 줄 없다.
즉 유니크 제약과 재시도는 한 번도 발동하지 않았고, 1번의 4단계(잠금 대기 후의 읽기가 상대의 커밋을
본다)가 실제로 성립했다. 사용자 행 잠금만으로 다 막은 것이다.

**유니크 제약은 테스트가 건드리지 않으므로 따로 확인했다.** 일회용 MySQL 8.4.8 컨테이너에 같은 DDL 을
적용하고 직접 INSERT 해 봤다. 같은 조건의 두 번째 WATCHING 은
`ERROR 1062 (23000) Duplicate entry '1-10-2026-10-10-09:00-10:00-1' for key
'alert_subscriptions.uq_watching_subscription'` 으로 거절됐고, 같은 조건의 ENDED 두 건은 함께 남았다
(ENDED 2, WATCHING 1). `SHOW INDEX` 로 다섯 컬럼 유니크 인덱스가 생성된 것도 확인했다. 5절에서 문서를
보지 않았다고 적은 "VIRTUAL 생성 컬럼 위의 유니크 인덱스" 는 이 실측으로 대체한다.

**남은 불확실성.** 재시도 경로와 `isWatchingConflict` 의 예외 타입 판별은 **한 번도 실행되지 않았다.**
동작을 확인한 것이 아니라 발동하지 않은 것뿐이니, 5절의 "예외 타입" 항목은 그대로 미검증이다.
`MAX_ATTEMPTS = 3` 과 `idx_active_lookup` 유지 판단도 근거가 생기지 않았다. 4절의 한계는 모두 그대로다.
