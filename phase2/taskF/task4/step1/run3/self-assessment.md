# 알림 신청 동시성 자기평가

## 1. 무엇을 막았는가

조회와 INSERT 사이에 다른 요청이 끼어드는 경합을 **신청자 행 쓰기 잠금**으로 막고,
그 잠금을 거치지 않은 경로까지 **유일 제약**으로 막는다.

같은 사용자·코트·날짜·시간대로 두 요청 T1, T2가 들어왔을 때 순서는 이렇게 결정된다.

1. `AlertRegistrar.register` 가 트랜잭션을 열고 가장 먼저 `AlertRepository.lockSubscriber(userId)` 를 호출한다.
   이것은 `kata_users` 의 해당 행을 `SELECT ... FOR UPDATE` 로 잠근다
   (`src/main/java/com/thinking/tennis/kata/AlertRepository.java`).
2. T1이 먼저 잠금을 얻으면 T2는 이 한 줄에서 멈춘다. 조회도 INSERT도 아직 하지 않은 상태로 멈춘다.
3. T1은 기존 신청을 조회하고, 없으므로 INSERT 하고 커밋한다. 커밋과 함께 잠금이 풀린다.
4. T2가 잠금을 얻는다. T2의 트랜잭션은 잠금을 얻은 뒤에야 첫 일관된 읽기를 수행하므로
   읽기 스냅샷이 T1 커밋 이후에 만들어지고, 조회는 T1이 넣은 행을 본다.
   그래서 T2는 INSERT 하지 않고 같은 ID를 반환한다.

잠금 대기 지점이 조회 앞이라는 것이 핵심이다. 조회 뒤에 잠그면 두 요청 모두 "없음"을 읽은 뒤에 줄을 서게 되어 의미가 없다.

이 잠금을 쓰지 않는 쓰기 경로가 생겨도 중복 행은 남지 않는다.
`src/test/resources/schema.sql` 의 `uq_watching_subscription` 이
`(user_id, court_id, play_date, time_slot, watching_marker)` 를 유일하게 묶고,
`watching_marker` 는 `status = 'WATCHING'` 일 때만 1이고 그 밖에는 NULL인 생성 컬럼이다.
MySQL 유일 인덱스는 NULL을 서로 다른 값으로 보므로, 감시 중인 신청만 하나로 제한되고 종료된 신청은 같은 조건으로 여러 건 남을 수 있다.

유일 제약이 걸리면 그 요청이 실패로 끝나지 않게 `AlertService.subscribe` 가 받아낸다.
제약 위반·교착·잠금 대기 초과는 경쟁의 결과이므로 최대 3회까지 **새 트랜잭션**에서 다시 판단한다.
재시도를 트랜잭션 밖에 둔 이유는 두 가지다. 실패한 시도의 롤백이 다음 시도를 오염시키지 않아야 하고,
REPEATABLE READ에서는 같은 트랜잭션에서 다시 조회해도 같은 스냅샷을 볼 뿐이기 때문이다.
그래서 시도 단위 메서드는 `REQUIRES_NEW` 로 분리된 빈(`AlertRegistrar`)에 두었다. 자기 호출은 프록시를 타지 않는다.

## 2. 어느 전제에 기대는가

- **DB**: MySQL 8.4 InnoDB. `FOR UPDATE` 행 잠금, 생성 컬럼, 유일 인덱스의 NULL 중복 허용에 기댄다.
  유일 제약을 MySQL 방식(NULL 구분)으로 쓰기 때문에 다른 DB로 옮기면 부분 인덱스 등으로 다시 써야 한다.
- **격리 수준**: REPEATABLE READ (`spring.datasource.hikari.transaction-isolation`).
  잠금 획득이 트랜잭션의 첫 문장이고, 읽기 스냅샷은 첫 **일관된** 읽기에서 만들어진다는 InnoDB 동작에 기댄다.
  이 전제가 틀려 스냅샷이 더 이르게 잡히더라도 유일 제약이 중복 INSERT를 거부하고 재시도가 새 트랜잭션에서 수습한다.
  READ COMMITTED로 낮춰도 동작은 유지된다.
- **애플리케이션 인스턴스 수**: 제한 없다. 잠금과 제약이 모두 DB에 있고 JVM 안의 락이나 캐시를 쓰지 않는다.
- **커넥션 풀 크기**: 4. 한 요청은 트랜잭션 동안 커넥션 하나를 붙잡고, 잠금 대기 중에도 붙잡고 있다.
  테스트는 작업 스레드 2개와 준비 SQL용 1개를 쓰므로 여유가 있다. 같은 사용자의 동시 요청 수가 풀 크기를 넘으면 커넥션 획득에서 먼저 막힌다.
- **그 밖**: `kata_users` 에 신청자 행이 미리 커밋되어 있어야 한다(FK가 요구하는 것과 같다).
  없으면 잠글 대상이 없어 요청이 실패한다. 테스트 픽스처는 사용자 1, 2를 미리 넣는다.
- Spring이 MySQL 중복 키 오류(1062)를 `DataIntegrityViolationException` 으로 번역한다는 것(`@Repository` 예외 번역).

## 3. 테스트가 어떻게 나올 것인가

| 조건 | 중복 회차 | 요청 오류 회차 |
| --- | ---: | ---: |
| NEW_SEQUENTIAL | 0 | 0 |
| NEW_TOGETHER | 0 | 0 |
| NEW_UNCOORDINATED | 0 | 0 |
| EXISTING_TOGETHER | 0 | 0 |
| DIFFERENT_USERS | 0 | 0 |

요청 오류를 0으로 적는 근거는 둘이다. 잠금으로 줄을 세우므로 정상 경로에서는 제약 위반 자체가 나지 않고,
나더라도 `subscribe` 가 새 트랜잭션에서 재시도해 같은 ID를 반환한다.
DIFFERENT_USERS는 서로 다른 `kata_users` 행을 잠그므로 기다리지 않고 각자 한 건씩 만든다.
교착은 예상하지 않는다. 잠그는 대상이 이미 존재하는 PK 행 하나뿐이고, 비어 있는 인덱스 구간에 갭 잠금을 걸지 않기 때문이다.
(조회를 `FOR UPDATE` 로 했다면 사용자가 달라도 같은 갭을 잠가 교착이 났을 것이다. 그래서 조회는 잠금 없는 읽기로 두었다.)

## 4. 막지 못하는 것

- **같은 사용자의 서로 다른 조건까지 직렬화된다.** 사용자 행 하나로 줄을 세우므로 한 사용자가 코트·시간대를 바꿔 동시에 신청해도 순차 처리된다. 정확성은 지키지만 처리량은 포기했다.
- **종료된 신청의 중복은 제한하지 않는다.** 유일 제약은 감시 중인 행만 본다. 같은 조건의 `ENDED` 행은 몇 건이든 쌓인다. 업무 규칙이 감시 중인 신청만 말하므로 의도한 범위다.
- **상태 전이는 조정하지 않는다.** 종료된 신청을 다시 감시로 되돌리는 경로나 상태를 바꾸는 다른 코드는 이 잠금을 타지 않는다. 그 경로가 중복 감시 행을 만들려 하면 유일 제약이 막지만, 수습 없이 오류로 끝난다.
- **재시도는 3회로 끝난다.** 그 안에 수렴하지 않으면 예외를 그대로 올린다. 두 요청 경합에서는 1회로 끝나지만, 경합 폭이 커지면 실패하는 요청이 생길 수 있다.
- **잠금을 기다리는 동안 커넥션을 붙잡는다.** 한 사용자에게 요청이 몰리면 풀이 마르고, 다른 사용자의 요청까지 영향을 받는다.
- `KataUser.version` 은 쓰지 않는다. 비관적 잠금으로 선점하므로 낙관적 충돌 감지가 필요하지 않았다.

## 5. 확신이 낮은 자리

- **InnoDB 읽기 스냅샷 생성 시점.** 잠금 읽기가 스냅샷을 만들지 않고, 스냅샷은 첫 일관된 읽기에서 만들어진다고 전제했다. 기억하는 매뉴얼 문구에 기댔고 이번 작업에서 8.4 문서를 다시 확인하지는 않았다. 틀릴 경우를 대비해 유일 제약과 재시도를 함께 넣었다.
- **예외 번역 형태.** IDENTITY 키라 `persist` 시점에 INSERT가 나가고 중복 키가 `DataIntegrityViolationException` 으로 번역된다고 보았다. 커밋 시점에 다른 형태로 올라오면 재시도가 걸리지 않는다. 그래서 `ConcurrencyFailureException` 까지 함께 받지만, 번역되지 않은 예외는 잡지 못한다.
- **`em.find(..., PESSIMISTIC_WRITE)` 가 `@Version` 컬럼을 건드리지 않는다는 가정.** 강제 증가는 `PESSIMISTIC_FORCE_INCREMENT` 의 일이라고 알고 있지만 문서로 확인하지 않았다.
- **Hibernate `validate` 가 매핑에 없는 생성 컬럼을 문제 삼지 않는다는 가정.** 매핑된 컬럼의 존재만 검사한다고 보았다.
- **STORED 생성 컬럼이 UPDATE 때 재계산된다는 가정.** 상태를 `ENDED` 로 바꾸면 marker가 NULL이 되어 같은 조건의 새 신청이 가능해진다고 보았다.
- **재시도 3회라는 숫자.** 두 요청 경합에서 1회면 수렴한다는 판단에서 여유를 둔 값이고, 측정해서 고른 값이 아니다.

## 실행 후 메모

결과는 3절에 적은 대로 나왔다. `Tests run: 10, Failures: 0, Errors: 0, Skipped: 0`,
다섯 조건 모두 `completed=100 normal=100 duplicates=0 requestErrors=0 contractViolations=0`.
NEW_SEQUENTIAL만 `overlappingCalls=0` 이고 나머지 네 조건은 100으로, 호출이 실제로 겹친 상태에서 통과했다.

1~5절에서 고치지 않고 여기 남기는 것은 세 가지다.

**재시도 경로는 한 번도 실행되지 않았다.** 로그에 중복 키, 제약 위반, 교착, 잠금 대기 초과가 하나도 없다
(`duplicate entry|ConstraintViolation|DataIntegrityViolation|Deadlock|Lock wait timeout` 검색 결과 0건).
사용자 행 잠금만으로 500회가 모두 정리되었다는 뜻이고, 2절에 적은 읽기 스냅샷 전제가 이 환경에서는 성립했다는 뜻이다.
동시에 5절에 적은 예외 번역 형태와 재시도 동작은 **이번 실행으로 검증되지 않았다.** 확신도는 실행 전과 같다.
그 경로를 확인하려면 잠금을 뺀 상태로 따로 돌려 봐야 한다.

**잠금과 유일 제약 중 어느 쪽이 통과를 만들었는지는 이 실행만으로 가릴 수 없다.** 둘을 같이 넣었고 둘 다 통과한다.
위의 0건을 근거로 잠금이 먼저 막았다고 읽었지만, 유일 제약만 두었을 때의 결과는 측정하지 않았다.

**잠금 대기가 응답 시간에 얼마를 더하는지 재지 않았다.** 테스트는 정확성만 보고 지연은 보지 않는다.
4절에 적은 "같은 사용자의 서로 다른 조건까지 직렬화된다"는 비용도 수치로는 모르는 상태다.
