# run 3 판정

2026-10-28. **통과했고, 자기 평가와 테스트가 어긋난 자리는 없었다.** 다섯 조건의 예측이 결과와 전부
일치했다. 세 run 모두 같은 결과다.

판정 규칙은 지켜졌다. 추적 파일의 변경 목록은 `AlertRepository.java`, `AlertService.java`,
`schema.sql` 셋이고 신규는 `AlertRegistrar.java` 하나다. 테스트 파일의 정규화 해시가 단계 0의 동결값과
같다.

이 run은 `AlertRepository`에서 F-3의 보조 메서드 셋을 제거한 기준선에서 돌렸다. 모델과 지시문은 run 1과
같다. 달라진 것은 그 구멍 하나다.

## 구멍을 막아도 같은 자리로 갔다

`lockSubscriber(long userId)`를 **직접 만들어** 사용자 행을 `PESSIMISTIC_WRITE`로 잠갔다. 이름만 다르고
run 1·2가 호출한 `lockUserForUpdate`와 같은 일을 한다.

그래서 수렴의 이유가 내 가림의 구멍이 아니었다. 미사용 메서드가 없어도 같은 자리를 찾았으므로, 세 run이
같은 방식을 고른 것은 문제의 구조 때문으로 보인다. 잠글 신청 행이 아직 없으니 두 요청이 공통으로 쥐는
다른 행을 잠그는 수밖에 없고, 그 행이 사용자다. 다만 구멍이 있던 두 run과 없던 한 run을 비교한 것이라
표본은 여전히 작다.

## 이 run만 낸 설계 근거 둘

**잠금을 조회 앞에 둔 이유를 명시했다.** 조회 뒤에 잠그면 두 요청이 모두 "없음"을 읽은 뒤 줄을 서므로
의미가 없다고 적었다.

**조회 자체를 `FOR UPDATE`로 하지 않은 이유를 적었다.** 빈 인덱스 구간에 갭 잠금이 걸려
`DIFFERENT_USERS`에서 교착이 생긴다는 것이다. 이것은 설계를 가른 근거인데 **테스트가 판정하지 않았다.**
그 경로를 택하지 않았으므로 교착이 실제로 났을지는 이 run으로 알 수 없다. 단계 2의 사실 주장 후보다.

주석에 "이미 커밋되어 존재하는 행을 잠그므로 갭 잠금이 생기지 않는다"고도 적었다. 같은 주장의 뒷면이고
역시 테스트 밖이다.

## 안전망이 또 실행되지 않았다

run 1과 같다. 유니크 제약과 `REQUIRES_NEW` 재시도를 뒀는데 로그에 중복 키 위반과 교착이 0건이라 재시도
경로가 한 번도 돌지 않았다. 구현자가 "안전망의 동작은 이번 실행으로 검증되지 않았다"고 스스로 적었다.

세 run에서 안전망을 둔 것은 run 1과 run 3이고, 둘 다 실행되지 않았다. run 2는 안전망 없이 잠금 하나로
통과했다. 즉 이 테스트에서 안전망은 통과에 기여하지 않았고, 있는지 없는지를 테스트가 구별하지 못한다.
