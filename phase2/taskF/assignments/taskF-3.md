# Task F-3: 격리 수준과 락으로 막기 (Isolation Level · 비관/낙관 락 · 99명의 패배자)

(Grit's Why): 막는 방법은 여러 가지이고, 각각 무엇을 보장하고 무엇을 비용으로 치르는지가 다릅니다. "되게 만들기"가 아니라 "왜 이 방식인지 판단하기"가 이번 Task의 핵심입니다.

### 수행 내용

1. DB Isolation Level을 본인 DB 기준으로 관찰하세요. 격리 수준을 바꿔 가며 F-2의 버그가 어떻게 달라지는지(Dirty Read / Non-Repeatable Read / Phantom 중 본인 케이스에 해당하는 현상)를 실제로 확인하고, 기본 격리 수준이 무엇이고 왜 그게 기본인지 적습니다.
2. F-2의 버그를 최소 두 가지 방식으로 막고 비교하세요.
  - 비관적 락(SELECT ... FOR UPDATE 등)과 낙관적 락(version 컬럼)을 둘 다 적용해 보고, 각각 언제 유리하고 언제 불리한지(충돌 빈도, 대기, 재시도 비용)를 본인 재현 테스트로 확인.
  - 재현 테스트가 두 방식 모두에서 초록불이 되는 것을 증명.
3. 99명의 패배자(대기열 처리)를 설계하세요. 선착순 1명만 이기고 99명은 정확히 패배 처리되어야 하는 상황에서, Spin Lock(계속 재시도하며 점유 확인)과 Pub/Sub(락 해제 신호를 구독해 대기) 방식을 비교하고, 어느 쪽이 왜 자원을 덜 태우는지 설명하세요. (분산 환경에서의 함정은 2-3에서 심화하므로 여기서는 단일 인스턴스 기준 원리까지.)

## 답안

### 막으려는 문제

코트에 빈자리가 나면 알려 주는 신청 기능이다. 규칙은 하나, 같은 사용자·코트·날짜·시간대로 몇 번을 신청하든 알림을 기다리는 신청은 한 건만 남아야 한다. 서비스는 이 규칙을 조회로 지킨다. 같은 조건의 신청이 있는지 먼저 찾고, 없을 때만 저장한다.

두 요청이 겹치면 둘 다 빈 조회 결과를 받는다. 뒤 요청이 조회할 때 앞 요청의 저장이 아직 끝나지 않았기 때문이다. 그래서 둘 다 새로 저장해 신청이 두 건이 된다. F-2에서 겹치는 요청 두 개를 100번 보내 100번 모두 중복을 확인했다.

이 글은 그 중복을 막는 수단을 차례로 대 본 기록이다. 수단마다 무엇이 막혔는지와 그 대가로 무엇을 내주었는지를 함께 적는다.

### 제출물 1: 격리 수준별 관찰 결과와 기본 격리 수준의 의미

#### 1. 격리 수준을 올려도 맨 위 단계 전까지는 중복이 그대로였다

가장 먼저 떠오르는 수단은 DB 설정을 바꾸는 것이다. 격리 수준은 동시에 도는 트랜잭션이 서로의 작업을 어디까지 볼 수 있는지 정하는 설정이고, MySQL은 네 단계를 제공한다. 네 단계를 각각 설정해 F-2의 버그가 달라지는지 확인했다.

두 요청이 모두 새 신청을 만들려는 상황만 수준별로 100번씩 돌렸다. 두 요청은 출발 신호를 맞추지 않고 잇따라 보냈다. 세 번째 열은 두 요청의 처리 구간이 실제로 겹쳤는지 확인한 횟수로, 모든 수준에서 100번 다 겹쳤으니 조건은 매번 성립했다.

| 격리 수준 | 중복 발생 회차 | 요청 오류 회차 | 호출 구간이 겹친 회차 |
|---|---:|---:|---:|
| READ UNCOMMITTED | 100/100회 | 0/100회 | 100/100회 |
| READ COMMITTED | 100/100회 | 0/100회 | 100/100회 |
| REPEATABLE READ | 100/100회 | 0/100회 | 100/100회 |
| SERIALIZABLE | 0/100회 | 100/100회 | 100/100회 |

아래 세 수준에서는 격리 수준을 올려도 중복이 한 번도 줄지 않았다. 격리 수준은 조회 결과가 저장할 때까지 유효하다고 보장하지 않기 때문이다. "조회해 보니 없다"와 "그래서 만든다"를 한 덩어리로 묶는 일은 격리 수준이 하는 일이 아니다.

#### 2. SERIALIZABLE은 중복 대신 실패를 만들었다

가장 높은 SERIALIZABLE에서는 중복이 한 건도 생기지 않았다. 이 수준에서는 평범한 조회도 잠금과 함께 실행되기 때문이다. 대신 100번 모두 요청이 오류로 끝났다. 두 트랜잭션이 INSERT에 필요한 잠금을 서로 기다리다 교착 상태에 빠졌다. 교착 상태는 둘이 서로가 쥔 잠금이 풀리기를 기다려 양쪽 다 진행하지 못하는 상태이고, DB는 한쪽을 실패시켜 이를 푼다.

그러니 이 결과를 성공으로 읽으면 안 된다. 중복은 0건이지만 신청에 성공한 사용자도 0명이다. 동시성 대책은 저장 결과와 요청 성공 여부를 함께 봐야 판정할 수 있다. 이 수준을 실제로 쓰려면 실패한 요청을 다시 실행하는 재시도 정책까지 갖춰야 기능이 성립한다.

#### 3. 더티 리드도 팬텀 리드도 아니었다

과제가 고르라고 한 세 현상이 실제로 일어나는지는 따로 확인해야 했다. 중복 재현 테스트는 요청 두 개를 겹쳐 보내기만 해서, 각 현상의 정의가 요구하는 조회 순서를 만들지 못하기 때문이다. 그래서 세션 두 개를 열고 조회와 저장의 순서를 코드로 고정한 프로브를 돌렸다. 조회 조건은 서비스가 쓰는 것과 같고, 네 수준에서 20회씩 반복했다. 결과는 수준마다 20회가 모두 같았다.

더티 리드는 READ UNCOMMITTED에서만 보였다. 아직 커밋되지 않은 값을 읽어서 생기는 문제인데, 서비스가 쓰는 REPEATABLE READ에서는 다른 트랜잭션의 커밋 전 INSERT가 한 번도 보이지 않았다. 이 중복은 반대다. 커밋되지 않은 다른 요청의 INSERT가 보이지 않아서 생긴다. 비반복 읽기도 아니다. 같은 행을 두 번 읽었는데 값이 달라지는 현상인데, 서비스는 같은 행을 두 번 읽지 않는다.

팬텀 리드는 READ UNCOMMITTED와 READ COMMITTED에서 보였고 REPEATABLE READ에서는 보이지 않았다. 첫 조회가 뜬 스냅숏이 트랜잭션 끝까지 유지되어, 그 사이에 다른 트랜잭션이 커밋한 행조차 두 번째 조회에 나타나지 않았다. 넓게 보면 다른 트랜잭션의 조회 범위에 행이 끼어든 상황이지만, 팬텀 리드라는 이름이 가리키는 "다시 조회하니 없던 행이 나타난다"는 이 수준에서 일어나지 않는다.

#### 4. 팬텀이 보이지 않는 것이 중복을 만들었다

프로브에서 두 번째 조회 뒤 "없으니 만든다"까지 수행하게 했더니, REPEATABLE READ에서만 행이 두 건 남았다. 두 번째 조회가 여전히 0을 돌려주니 판단이 그대로 서서, 이미 커밋된 행 위에 한 건을 더 만든 것이다. 팬텀이 보이는 READ COMMITTED에서는 두 번째 조회가 1을 보여 줘 만들지 않았다. 보여 주지 않는 쪽이 안전해 보이지만 이 기능에서는 반대였다.

그렇다고 READ COMMITTED가 이 버그를 막지는 않는다. 프로브의 조회는 두 번이고 서비스의 조회는 한 번이다. 조회가 한 번이면 그 결과가 낡는 구간은 READ COMMITTED에도 그대로 있고, 실제로 1절 표에서 READ COMMITTED도 100번 모두 중복이었다.

그래서 이 중복의 이름은 ANSI 세 현상 쪽이 아니라 애플리케이션 쪽에 있다. 조회로 확인한 결과를 믿고 저장하는 사이에 틈이 생기는 check-then-act 경합이고, F-1의 갱신 유실과 깨지는 자리가 같다. 격리 수준이 정하는 것은 무엇을 보여 줄 것인가이지, 내가 본 것이 쓸 때까지 유효한가가 아니다. 프로브에서도 그 쓰기를 막은 것은 SERIALIZABLE뿐이었고, 그 대가는 2절에서 봤다.

#### 5. 기본값 REPEATABLE READ는 절충이지 방어선이 아니다

MySQL InnoDB의 기본 격리 수준은 REPEATABLE READ다. 한 트랜잭션 안에서 같은 조회가 같은 결과를 주도록 보장하지만, 조회와 INSERT를 자동으로 한 덩어리로 묶지는 않는다. 설정을 건드리지 않은 F-2에서 중복이 난 이유가 이것이다.

MySQL 문서는 왜 이 값을 기본으로 골랐는지 직접 설명하지 않는다. 다만 위 표를 보면 자리가 보인다. SERIALIZABLE처럼 대기와 교착 상태를 만들지 않으면서 일관된 읽기는 제공하는 중간 지점이다. 기본값은 대부분의 기능이 무리 없이 돌아가게 하는 선택이지, 조회 결과를 믿고 쓰는 코드를 지켜 주지는 않는다.

### 제출물 2: 비관적 락과 낙관적 락 비교

#### 1. 잠글 신청 행이 아직 없어서 사용자 행을 잠갔다

락을 걸려면 두 요청이 공통으로 쥐는 대상이 있어야 하는데, 이 버그에는 그게 없다. 막으려는 것이 "아직 없는 신청을 둘이 따로 만드는 일"이라서 정작 잠글 신청 행이 존재하지 않는다.

그래서 두 요청이 반드시 함께 보는 `kata_users` 행, 즉 신청자 자신을 잠금 대상으로 삼았다. 중복은 같은 사용자의 요청끼리만 생기므로, 한 사용자의 요청에 순서를 세우면 중복도 막힌다.

#### 2. 두 방식은 같은 문제를 반대 순서로 푼다

비관적 락은 먼저 잠그고 다른 요청을 기다리게 한다. 사용자 행을 `PESSIMISTIC_WRITE`로 잠근 뒤 기존 신청을 조회하고, 없을 때만 저장한다. 뒤에 온 요청은 앞 요청이 트랜잭션을 끝낼 때까지 조회를 시작하지 못하므로, 조회하는 시점에는 앞 요청이 만든 신청이 이미 보인다.

낙관적 락은 일단 진행하고 충돌을 나중에 감지한다. version은 행이 바뀔 때마다 1씩 올라가는 숫자다. 내가 읽은 version일 때만 갱신되도록 조건을 걸면, 늦게 도착한 쪽은 갱신에 실패하면서 자기가 밀렸다는 사실을 알게 된다. 실패한 트랜잭션은 되돌리고 새 트랜잭션에서 처음부터 다시 실행한다. 다시 실행할 때는 앞 요청의 신청이 보이므로 새로 만들지 않는다.

#### 3. 두 방식 모두 재현 테스트를 통과했다

같은 사용자에게 겹치는 요청 두 개를 100번씩 보내고, 이를 세 번 반복해 측정했다. 두 방식 모두 모든 회차에서 중복 0건, 요청 오류 0건이었고, 최종적으로 활성 신청 1건과 두 요청이 받은 동일한 신청 번호를 확인했다. F-2에서 빨간불이던 재현 테스트가 두 구현 모두에서 통과한다.

#### 4. 비관이 빨랐던 것은 충돌이 100%였기 때문이다

| 측정 항목 | 비관적 락 | 낙관적 락 |
|---|---:|---:|
| 요청 하나의 시간 중앙값 | 11.831ms | 15.569ms |
| 한 회차 전체 시간 중앙값 | 12.963ms | 18.561ms |
| 중복 발생 | 0/100회 | 0/100회 |
| 요청 오류 | 0/100회 | 0/100회 |
| 충돌 후 재시도 | 0회 | 100회 |

낙관적 락이 느린 이유는 마지막 줄에 있다. 두 요청을 매번 겹치게 만든 테스트라 충돌률이 100%였고, 그래서 100번 모두 트랜잭션을 두 번 실행했다. 한 번에 끝난 비관적 락보다 느린 것이 당연하다.

그러므로 이 수치는 두 방식의 성능 우열이 아니라 충돌이 잦을 때의 모습이다. 충돌이 드문 조건에서는 낙관적 락의 재시도가 거의 일어나지 않아 순서가 뒤집힐 수 있다.

#### 5. 속도 말고 달라지는 것들

| 비교 기준 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 충돌 처리 | 먼저 잠그고 다른 요청은 대기한다. | 먼저 진행하고 version 충돌을 감지한다. |
| 대기와 재시도 | DB 연결이 잠금 해제까지 대기하지만 재시도 코드는 거의 없다. | 잠금 대기는 줄일 수 있지만 충돌마다 트랜잭션을 다시 실행한다. |
| 코드 복잡도 | 잠금 순서와 대상을 정하면 비교적 단순하다. | version 갱신, 롤백, 새 트랜잭션, 최대 재시도와 실패 처리가 필요하다. |
| 영향 범위 | 사용자 행을 잠그므로 같은 사용자의 다른 조건 요청도 기다린다. | 충돌한 요청만 다시 실행한다. |
| DB·인프라 | 공유 DB의 잠금 기능만 쓰며 별도 인프라가 필요 없다. | 공유 DB의 version 컬럼만 쓰며 별도 인프라가 필요 없다. |
| 주의할 점 | 잠금 순서가 다르면 교착 상태가 생길 수 있다. | 재시도가 모두 실패했을 때의 응답과 과도한 재시도를 정해야 한다. |

#### 6. 그래서 선택 기준은 충돌 빈도다

두 방식은 서로 다른 자리에서 비용을 낸다. 비관적 락은 기다리는 동안, 낙관적 락은 다시 실행하는 동안 낸다. 같은 자원에 요청이 자주 몰리고 대기 시간이 짧게 예측된다면 기다리는 편이 싸므로 비관적 락이 단순한 선택이다. 충돌이 드물다면 대기 없이 진행하고 가끔 다시 하는 편이 싸다.

다만 낙관적 락을 고르려면 충돌률과 재시도 횟수를 실제로 관찰할 수 있어야 한다. 충돌이 예상보다 잦으면 비용 계산이 뒤집히는데, 측정하지 않으면 그 사실을 모른다.

### 제출물 3: 99명의 패배자 — Spin 대기와 Pub/Sub 비교

#### 1. 셋 다 정확했으므로 비교 축은 기다리는 비용이다

100명이 같은 자원에 동시에 달려들어 한 명만 이겨야 하는 상황이다. 승자는 자기 일을 처리하고, 진 99명은 자기가 졌다는 결과를 정확히 받고 끝나야 한다.

승자를 정하는 방법은 세 방식 모두 똑같이 CAS로 했다. CAS는 값이 내가 읽은 그대로일 때만 바꾸는 연산이라, 100명이 동시에 시도해도 성공은 한 명뿐이다. 그래서 "1명 승리, 99명 패배"는 세 방식 모두 만족한다. 실제로 150회 전부 통과했다. 정확성으로는 셋을 가를 수 없다는 뜻이다.

갈리는 것은 나머지 99명이 결과를 기다리는 방법이다.

- **Spin 대기**: 결과가 나왔는지 상태를 계속 다시 읽어 확인한다.
- **JVM Condition**: 스레드를 재워 두고 승자가 보내는 신호에 깨어난다. 신호는 같은 프로그램 안에서만 닿는다.
- **Redis Pub/Sub**: 대기자가 Redis 채널을 구독하고, 승자가 결과를 발행하면 받는다. 신호가 프로세스와 서버를 넘어 닿는다.

과제가 지정한 것은 Spin과 Pub/Sub 둘이지만 Condition을 함께 넣었다. 둘만 비교하면 재웠다 깨우는 방식의 비용이 "재운다"에서 오는지 "브로커를 거친다"에서 오는지 가를 수 없기 때문이다. Condition은 재우되 네트워크를 쓰지 않으므로 그 둘을 분리해 준다.

#### 2. 같은 입력을 세 방식에 넣고 대기 자원만 쟀다

각 방식마다 100명이 50회씩 겨루는 묶음을 세 번 돌려, 방식당 150회 15,000개 요청을 처리했다. 승자는 세 방식 모두 똑같이 20ms의 모의 처리 지연 뒤에 결과를 알렸다. Redis 연결 100개와 발행용 연결 1개는 측정 전에 만들어 재사용했고, 연결 준비 시간은 처리 시간에서 뺐다. 모든 회차에서 승자 1명, 패배자 99명, 결과 관찰 100건을 확인했다.

| 측정 항목 | Spin 대기 | JVM Condition 대기 | Redis Pub/Sub |
|---|---:|---:|---:|
| 회차 시간 중앙값 | 29.965ms | 22.258ms | 24.193ms |
| 회차 p95 중앙값 | 124.089ms | 24.069ms | 26.467ms |
| 정규화 CPU 사용률 중앙값 | 92.356% | 0.505% | 2.246% |
| 대기 중 관찰 | 약 33억 회 | 14,850회 await | 메시지 15,000건 수신 |
| 네트워크 사용 | 없음 | 없음 | 입력 약 10.8KB, 출력 약 1.10MB |
| 정확성 | 150/150회 통과 | 150/150회 통과 | 150/150회 통과 |

p95는 측정값을 빠른 순으로 줄 세웠을 때 95번째 백분위, 즉 느린 쪽 5%가 시작되는 지점이다. 표의 값은 각 회차 p95의 중앙값이므로, 매 회차에서 가장 오래 기다린 축에 속한 요청이 얼마나 걸렸는지를 보여 준다.

정규화 CPU 사용률은 각 50회 묶음에서 Java 프로세스의 CPU 시간과 Redis의 `used_cpu_user + used_cpu_sys` 증가량을 더한 뒤, 측정 경과 시간과 호스트의 논리 CPU 20개로 나눈 값이다. 그래서 92.356%는 작업 관리자에 뜨는 컴퓨터 전체 사용률이 아니라, 두 프로세스가 논리 CPU 20개분의 용량 중 쓴 비율이다. Docker 가상화 계층과 다른 프로세스의 CPU는 빠져 있다. 묶음 세 번의 범위는 Spin 91.966~92.429%, Condition 0.295~0.921%, Redis 1.980~4.001%로 묶음끼리 크게 흔들리지 않았다.

#### 3. 계속 확인하는 대기는 CPU를 거의 다 태운다

Spin은 15,000개 요청을 처리하는 동안 상태를 약 33억 회 다시 읽었고, CPU를 92.356% 썼다. 기다리는 쪽은 실제로 아무 일도 하지 않는데 비용은 세 방식 중 가장 크다. 회차 시간도 가장 길었고, 느린 쪽 꼬리인 p95는 124.089ms로 나머지 둘의 다섯 배였다.

브로커가 필요 없어 구조는 가장 단순하다. 그러나 비용이 늘어나는 자리가 "기다리는 일" 자체라서, 99명을 기다리게 하는 이 상황과는 맞지 않는다.

#### 4. 재웠다 깨우는 대기는 거의 쓰지 않는다

Condition은 0.505%, Redis Pub/Sub는 2.246%로 Spin의 50분의 1 아래였다. 재워 둔 스레드는 CPU를 쓰지 않고, 깨우는 작업은 대기자 수만큼만 일어나기 때문이다. Condition은 14,850회 깨어났고 Redis는 메시지 15,000건을 받았다. 33억 회와 비교하면 확인 횟수 자체가 다른 자릿수다.

둘 사이의 차이는 신호가 어디까지 가느냐에서 온다. Condition은 같은 JVM 안에서 재우고 깨우므로 가장 짧았다. Redis Pub/Sub는 메시지를 직렬화해 보내고 브로커가 받아 돌려주는 과정이 더해져 Condition보다 느렸고, 출력 약 1.10MB의 네트워크를 썼다. 이것이 Pub/Sub가 더 내는 대가이고, 대신 얻는 것은 신호가 프로세스 밖으로 나간다는 점이다.

#### 5. 단일 인스턴스면 Condition, 여러 인스턴스면 Pub/Sub

애플리케이션 인스턴스가 하나라면 Condition을 쓴다. 가장 빠르고 CPU도 가장 적게 쓰며, 따로 운영할 것이 없다.

여러 인스턴스가 같은 신호를 받아야 한다면 Redis Pub/Sub를 검토한다. 다만 Pub/Sub는 그 순간 연결된 구독자에게만 메시지를 전달하고 다시 재생하지 않는다. 구독이 끊긴 사이에 발행된 결과는 영영 받지 못한다는 뜻이다. 그래서 승자의 결과는 Redis 키나 DB에 저장해 두고, Pub/Sub는 대기자를 깨우는 신호로만 쓰는 편이 안전하다. 깨어난 대기자가 저장된 결과를 읽으면 메시지를 놓쳐도 결과는 남는다. 여기에 연결 관리와 브로커 장애 대응까지 함께 설계해야 한다.

#### 6. 이 결과를 어디까지 말할 수 있나

한 대의 호스트에서 연결이 정상인 상태로 반복한 측정이다. 네트워크가 끊기거나 브로커가 죽는 상황, 메시지가 유실되는 상황은 검증하지 않았다. 분산 환경에서의 함정은 Station 2-3에서 다룬다.

승자의 처리 시간을 20ms로 고정한 것도 결과에 영향을 준다. 처리가 길어지면 기다리는 시간이 늘어 Spin의 CPU 소모는 더 커지고, 짧아지면 세 방식의 차이가 줄어든다. 표의 수치는 20ms 조건에서의 비교다.
