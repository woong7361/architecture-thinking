# Task F-3: 격리 수준과 락으로 막기 (Isolation Level · 비관/낙관 락 · 99명의 패배자)

(Grit's Why): 막는 방법은 여러 가지이고, 각각 무엇을 보장하고 무엇을 비용으로 치르는지가 다릅니다. "되게 만들기"가 아니라 "왜 이 방식인지 판단하기"가 이번 Task의 핵심입니다.

### 수행 내용

1. DB Isolation Level을 본인 DB 기준으로 관찰하세요. 격리 수준을 바꿔 가며 F-2의 버그가 어떻게 달라지는지(Dirty Read / Non-Repeatable Read / Phantom 중 본인 케이스에 해당하는 현상)를 실제로 확인하고, 기본 격리 수준이 무엇이고 왜 그게 기본인지 적습니다.
2. F-2의 버그를 최소 두 가지 방식으로 막고 비교하세요.
  - 비관적 락(SELECT ... FOR UPDATE 등)과 낙관적 락(version 컬럼)을 둘 다 적용해 보고, 각각 언제 유리하고 언제 불리한지(충돌 빈도, 대기, 재시도 비용)를 본인 재현 테스트로 확인.
  - 재현 테스트가 두 방식 모두에서 초록불이 되는 것을 증명.
3. 99명의 패배자(대기열 처리)를 설계하세요. 선착순 1명만 이기고 99명은 정확히 패배 처리되어야 하는 상황에서, Spin Lock(계속 재시도하며 점유 확인)과 Pub/Sub(락 해제 신호를 구독해 대기) 방식을 비교하고, 어느 쪽이 왜 자원을 덜 태우는지 설명하세요. (분산 환경에서의 함정은 2-3에서 심화하므로 여기서는 단일 인스턴스 기준 원리까지.)

## 답안

### 제출물 1: 격리 수준별 관찰 결과와 기본 격리 수준의 의미

F-2의 알림 신청 코드는 먼저 같은 사용자·코트·날짜·시간대의 `WATCHING` 신청을 조회하고, 없으면 새 행을 저장한다. 이 조회와 저장 사이를 다른 요청이 통제하지 않기 때문에, 두 요청이 모두 빈 조회 결과를 받은 뒤 각각 INSERT하면 같은 조건의 신청이 두 건으로 늘어날 수 있다. 이 동작이 DB 격리 수준에 따라 달라지는지 확인하기 위해 Testcontainers의 MySQL 8.4.8/InnoDB에서 네 수준을 각각 설정하고, `NEW_UNCOORDINATED` 조건만 100회씩 실행했다. 두 작업을 ExecutorService에 연속 제출했으며 작업 내부에서 CountDownLatch를 기다리지 않았다.

| 격리 수준 | 중복 발생 회차 | 요청 오류 회차 | 호출 구간이 겹친 회차 |
|---|---:|---:|---:|
| READ UNCOMMITTED | 100/100회 | 0/100회 | 100/100회 |
| READ COMMITTED | 100/100회 | 0/100회 | 100/100회 |
| REPEATABLE READ | 100/100회 | 0/100회 | 100/100회 |
| SERIALIZABLE | 0/100회 | 100/100회 | 100/100회 |

READ UNCOMMITTED, READ COMMITTED, REPEATABLE READ에서는 격리 수준을 바꿔도 중복이 사라지지 않았다. 조회가 비어 있다는 사실과 새 행을 만드는 작업을 한 덩어리로 묶지 않았기 때문이다. 반면 SERIALIZABLE에서는 일반 조회가 더 강한 잠금과 함께 실행되면서 중복 행은 생기지 않았지만, 두 트랜잭션이 INSERT 잠금을 얻으려다 교착 상태에 빠져 요청 오류가 100회 발생했다. 따라서 “중복이 0건”만으로 기능이 성공했다고 판단할 수 없으며, 저장 결과와 요청 성공 여부를 함께 확인해야 한다.

이번 실험에서 직접 확인한 현상은 더티 리드나 비반복 읽기가 아니라 **빈 조회 뒤 동시에 INSERT하는 동시 삽입 경합**이다. 같은 트랜잭션에서 두 번 조회해 새 행이 보이는지를 확인한 실험은 아니므로, 이 결과를 팬텀 리드로 단정하지 않았다. 팬텀 리드 자체는 첫 조회와 두 번째 조회 사이에 다른 트랜잭션이 행을 커밋하는 별도 실험으로 확인해야 한다.

MySQL InnoDB의 기본 격리 수준은 REPEATABLE READ다. 이 수준은 일반 SELECT에서 일관된 읽기를 제공하지만, 조회와 INSERT를 자동으로 원자화하지 않는다. 그래서 이번 기능에서는 기본 격리 수준을 사용해도 중복이 발생했다. MySQL 문서가 기본값을 선택한 정책 이유를 직접 설명하지는 않지만, REPEATABLE READ는 SERIALIZABLE보다 잠금으로 인한 대기를 줄이면서도 일관된 읽기를 제공하는 절충안으로 이해할 수 있다. SERIALIZABLE은 충돌을 줄이는 대신 대기와 교착 상태를 만들 수 있으며, 실패한 요청을 다시 실행하는 재시도 정책까지 있어야 최종적으로 모든 요청의 계약을 판단할 수 있다. [MySQL 격리 수준 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html)

실행 명령과 전체 로그는 [래치 없는 격리 수준 관찰 기록](../alert-kata/evidence/uncoordinated-isolation-results.md)에 정리했다.

### 제출물 2: 비관적 락과 낙관적 락 비교

F-2의 중복을 막기 위해 두 요청이 공통으로 접근할 수 있는 `kata_users` 행을 조정 대상으로 선택했다. [비관적 락 코드](../alert-kata/src/main/java/com/thinking/tennis/kata/PessimisticAlertService.java)는 사용자 행을 `PESSIMISTIC_WRITE`로 먼저 잠근 뒤 기존 신청을 조회하고, 없을 때만 저장한다. [낙관적 락 코드](../alert-kata/src/main/java/com/thinking/tennis/kata/OptimisticAlertService.java)는 사용자 `version`을 조건부로 증가시키고, 충돌한 트랜잭션을 [새 트랜잭션](../alert-kata/src/main/java/com/thinking/tennis/kata/OptimisticSubscriptionAttempt.java)에서 다시 실행한다. 두 구현은 [동일한 재현 테스트](../alert-kata/src/test/java/com/thinking/tennis/kata/LockComparisonTest.java)로 비교했다.

먼저 같은 사용자에게 두 요청을 겹쳐 보내 100회씩 실행했다. 세 번 반복한 측정 결과는 다음과 같다.

| 측정 항목 | 비관적 락 | 낙관적 락 |
|---|---:|---:|
| 요청 시간 중앙값 | 11.831ms | 15.569ms |
| 한 회차 처리 시간 중앙값 | 12.963ms | 18.561ms |
| 중복 발생 | 0/100회 | 0/100회 |
| 요청 오류 | 0/100회 | 0/100회 |
| 충돌 후 재시도 | 0회 | 100회 |

이번 조건에서는 낙관적 락이 매회 충돌 후 재시도했기 때문에 비관적 락보다 느렸다. 이 수치는 Testcontainers MySQL 8.4.8에서 측정한 값이므로 모든 환경의 성능 우열을 뜻하지 않는다. [측정 로그](../alert-kata/evidence/lock-comparison-results.md)

속도 외의 차이는 다음과 같다.

| 비교 기준 | 비관적 락 | 낙관적 락 |
|---|---|---|
| 충돌 처리 | 먼저 잠그고 다른 요청은 대기한다. | 먼저 진행하고 version 충돌을 감지한다. |
| 대기와 재시도 | DB 연결이 잠금 해제까지 대기하지만 재시도 코드는 거의 없다. | 잠금 대기는 줄일 수 있지만 충돌마다 트랜잭션을 다시 실행한다. |
| 코드 복잡도 | 잠금 순서와 대상을 정하면 비교적 단순하다. | version 갱신, 롤백, 새 트랜잭션, 최대 재시도와 실패 처리가 필요하다. |
| 영향 범위 | 사용자 행을 잠그므로 같은 사용자의 다른 조건 요청도 기다린다. | 충돌한 요청만 다시 실행한다. |
| DB·인프라 | 공유 DB의 잠금 기능만 사용하며 별도 인프라가 필요 없다. | 공유 DB의 version 컬럼만 사용하며 별도 인프라가 필요 없다. |
| 주의할 점 | 잠금 순서가 다르면 교착 상태가 발생할 수 있다. | 재시도가 모두 실패했을 때의 응답과 과도한 재시도를 정해야 한다. |

두 방식 모두 최종적으로 활성 신청 1개와 동일한 신청 ID를 보장했다. 같은 자원에 요청이 자주 몰리고 짧은 대기가 예측 가능하면 비관적 락이 단순한 선택이 될 수 있다. 충돌이 드물고 대기보다 재시도가 유리한 환경에서는 낙관적 락을 고려할 수 있지만, 충돌률과 재시도 횟수를 관찰할 수 있어야 한다. [MySQL 잠금 조회 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html), [Jakarta Persistence 낙관적 잠금 명세](https://jakarta.ee/specifications/persistence/3.1/jakarta-persistence-spec-3.1)

### 제출물 3: 99명의 패배자 — Spin 대기와 Pub/Sub 비교

이번 비교는 같은 입력을 세 방식에 넣어 대기 자원만 비교하도록 다시 설계했다. 각 방식은 100명의 작업자와 50회 반복을 사용했고, 모든 회차에서 100명이 동시에 출발해 CAS로 한 명만 승자를 정했다. 승자는 같은 20ms의 모의 처리 지연 뒤 자신의 결과를 알렸고, 나머지 99명은 그 결과를 받아 종료했다. 세 방식 모두 150회, 15,000개 요청을 처리했으며 모든 회차에서 승자 1명, 패배자 99명, 결과 관찰 100건을 확인했다. Redis 연결 100개와 발행 연결 1개는 측정 전에 만들어 재사용했고 연결 준비 시간은 처리 시간에서 분리했다.

| 측정 항목 | Spin 대기 | JVM Condition 대기 | Redis Pub/Sub |
|---|---:|---:|---:|
| 회차 시간 중앙값 | 29.965ms | 22.258ms | 24.193ms |
| 회차 p95 중앙값 | 124.089ms | 24.069ms | 26.467ms |
| 정규화 CPU 사용률 중앙값 | 92.356% | 0.505% | 2.246% |
| 대기 중 관찰 | 약 33억 회 | 14,850회 await | 메시지 15,000건 수신 |
| 네트워크 사용 | 없음 | 없음 | 입력 약 10.8KB, 출력 약 1.10MB |
| 정확성 | 150/150회 통과 | 150/150회 통과 | 150/150회 통과 |

CPU 사용률은 각 50회 묶음에서 Java 프로세스 CPU 시간과 Redis의 used_cpu_user + used_cpu_sys 증가량을 더한 뒤, 측정 경과 시간과 호스트의 논리 CPU 20개로 나눈 값이다. 따라서 표의 92.356%는 컴퓨터 전체 작업 관리자 사용률이 아니라 두 프로세스가 20개 논리 CPU 용량 중 사용한 비율이다. Docker 가상화 계층과 다른 프로세스의 CPU는 포함하지 않는다. 세 번의 묶음 결과에서 Spin은 91.966~92.429%, Condition은 0.295~0.921%, Redis는 1.980~4.001% 범위였다. 측정 정의와 원시 로그 재집계는 [공정 비교 기록](../alert-kata/evidence/fair-queue-resources.md)과 [재집계 결과](../alert-kata/evidence/fair-queue-resources-summary.json)에서 확인할 수 있다.

이번 조건에서 Condition이 가장 짧고 CPU도 적게 사용했다. 같은 JVM 안에서 대기자를 재우고 신호를 보낼 수 있기 때문이다. Redis Pub/Sub는 네트워크 직렬화와 브로커 처리가 추가되어 Condition보다 느렸지만, 여러 애플리케이션 인스턴스가 같은 신호를 받아야 할 때 사용할 수 있다. Spin은 별도 브로커가 없어 구조가 단순하지만, 결과를 기다리는 동안 상태를 계속 읽어 CPU를 대부분 소모했다.

따라서 단일 JVM의 대기라면 Condition을 선택한다. 인스턴스 사이에 실시간 신호를 전달해야 한다면 Redis Pub/Sub를 검토하되, 연결 관리와 브로커 장애를 함께 설계해야 한다. Redis Pub/Sub는 연결된 구독자에게만 메시지를 전달하고 재생하지 않으므로, 승자 결과를 Redis 키나 DB에 저장하고 Pub/Sub는 대기자를 깨우는 신호로 사용하는 편이 안전하다. 이 실험은 정상적으로 연결된 단일 호스트의 대기 비용을 비교한 것이며, 분산 장애 복구나 메시지 유실까지 검증한 결과는 아니다. [Redis Pub/Sub 공식 문서](https://redis.io/docs/latest/develop/pubsub/)
