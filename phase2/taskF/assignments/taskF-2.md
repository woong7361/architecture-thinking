# Task F-2: 동시성 버그 직접 재현하기 (The Kata)

(Grit's Why): 1-1에서 죽은 코드를, 2-1에서 죽은 기획서를 비평했다면, 여기서는 멀쩡해 보이는 코드를 본인 손으로 깨뜨립니다. 재현하지 못한 버그는 이해한 버그가 아닙니다.

### 수행 내용

1. 동시성 결함이 있는 기능 1개를 고르세요. 본인 시그니처 프로젝트의 재고 차감, 쿠폰 발급, 좌석 예매, 포인트 적립 중 하나면 좋습니다(없으면 단순 카운터로 시작).
2. 그 기능을 동시 요청으로 깨뜨리는 재현 테스트를 직접 작성하세요. ExecutorService와 CountDownLatch(또는 JMeter/k6)로 N개의 동시 요청을 보내고, 기대값과 실제값이 어긋나는 것을 테스트로 증명합니다. (예: 재고 100개에 100명이 동시 주문했는데 재고가 음수가 되거나, 쿠폰 1장이 여러 명에게 발급되는 것을 빨간불로 고정.)
3. 깨진 결과를 로그/스크린샷으로 남기고, "왜 이 숫자가 나왔는가"를 F-1의 메커니즘과 연결해 설명하세요.

### 제출물

- [x] 동시성 재현 테스트 코드를 GitHub에(동시 요청 수, 기대값, 실제값이 드러나게).
- [x] 깨진 관찰 결과(로그/스크린샷) + 왜 그 숫자가 나왔는지 메커니즘 연결 설명. (최소 300자)

## 답안

### 제출물 1: 알림 신청 기능과 재현 테스트

테니스 코트에 빈자리가 나면 알려 주는 기능이다. 사용자가 코트와 날짜, 시간대를 골라 신청해 두면 그 자리가 났을 때 알림을 받는다. 여기에는 지켜야 할 규칙이 하나 있다. 같은 사용자가 같은 코트·날짜·시간대로 몇 번을 신청하든, 알림을 기다리는 신청은 한 건만 남아야 한다. 두 건이 남으면 자리 하나에 알림이 두 번 갈 수 있다. taskE에서 이 규칙만 떼어 내 작은 서비스로 옮겼다.

서비스는 이 규칙을 조회로 지킨다. 신청이 들어오면 같은 사용자·코트·날짜·시간대의 신청이 DB에 이미 있는지 먼저 찾는다. 있으면 새로 만들지 않고 그 신청의 번호를 돌려주고, 없을 때만 새 신청을 저장한다. 이미 끝난 신청은 찾는 대상에서 빼, 같은 자리에 다시 신청할 수 있게 했다. 그래서 요청이 몇 개 들어오든 결과는 하나로 정해진다. 기다리는 신청은 사용자마다 한 건이고, 같은 내용으로 들어온 요청은 모두 같은 신청 번호를 받는다. 이것이 테스트가 확인할 기대값이다.

요청이 하나씩 차례로 들어오면 이 코드는 규칙을 지킨다. 문제는 두 요청이 같은 순간에 처리될 때다. 앞으로 "겹친다"는 말은 한 요청의 처리가 끝나기 전에 다른 요청의 처리가 시작된다는 뜻으로 쓴다. 재현 테스트가 묻는 것은 하나다. 요청이 겹쳐도 기대값이 지켜지는가.

겹치는 요청만 돌리면 중복이 나와도 겹침 때문인지 코드가 원래 틀린 것인지 가릴 수 없다. 그래서 겹치는 상황과 겹치지 않는 상황을 함께 다섯 가지 준비했다. 상황마다 요청 두 개를 100번씩, 모두 1,000개 요청을 보냈다. DB는 실제 MySQL을 띄워 썼고, 읽기 방식은 MySQL이 기본으로 쓰는 REPEATABLE READ 그대로 두었다. 이 설정이 무엇을 막아 주고 무엇을 막지 못하는지는 제출물 2의 2절에서 다룬다. 매번 DB에 남은 신청 건수와 각 요청이 돌려받은 번호를 기대값과 맞춰 본다.

### 제출물 2: 관찰 결과와 원인

#### 1. 겹친 두 상황에서만 100번 모두 중복이 생겼다

두 요청이 겹치면서 둘 다 새 신청을 만들려 할 때만 중복이 나왔다. 다섯 상황을 100번씩 돌린 결과는 다음과 같다.

| 상황 | 두 요청을 보낸 방식 | 중복이 생긴 횟수 | 요청이 실패한 횟수 |
|---|---|---:|---:|
| 차례로 신규 | 앞 요청의 저장이 끝난 뒤 뒤 요청을 보냄 | 0 / 100 | 0 |
| 동시 신규 | 두 요청을 같은 신호에 맞춰 동시에 보냄 | 100 / 100 | 0 |
| 신호 없는 신규 | 신호를 맞추지 않고 두 요청을 잇따라 보냄 | 100 / 100 | 0 |
| 이미 있는 신청 | 같은 내용의 신청 한 건을 미리 저장해 두고 동시에 보냄 | 0 / 100 | 0 |
| 다른 사용자 | 코트·날짜·시간대는 같고 사용자만 다른 두 요청을 동시에 보냄 | 0 / 100 | 0 |

동시에 보냈는데도 멀쩡한 상황이 둘 있다. 사용자가 다른 경우에는 서비스가 신청을 찾을 때 사용자까지 조건에 넣으므로 두 요청이 서로의 신청을 볼 일이 없고, 각자 한 건씩 만든 것은 규칙대로다. 이미 신청이 있는 경우에는 두 요청의 조회에 그 신청이 잡혀 둘 다 같은 번호를 돌려줬다. 기대값을 어긴 것은 새 신청을 함께 만들려 한 두 상황뿐이고, 그 두 상황의 테스트는 실패로 남았다.

#### 2. 조회는 아직 저장되지 않은 신청을 보지 못한다

왜 겹치면 두 건이 될까. 서비스는 "없으면 만든다"를 조회 한 번으로 판단하는데, 그 조회는 보는 순간의 DB만 보여 준다. A가 없다고 확인한 그 순간에 B도 같은 조회를 할 수 있다. B가 볼 때 A의 신청은 아직 저장이 끝나지 않아 보이지 않는다. 그래서 둘 다 자기가 처음이라고 판단하고 각자 저장한다.

| 단계 | 요청 A | 요청 B |
|---|---|---|
| 1 | 같은 조건의 신청이 없다고 조회 | |
| 2 | | A의 저장이 끝나기 전에 조회해, 역시 없다고 판단 |
| 3 | 새 신청을 저장 | 새 신청을 저장 |

조회와 저장은 하나의 트랜잭션으로 묶여 있다. 트랜잭션은 여러 DB 작업을 한 덩어리로 처리해 중간에 실패하면 전부 되돌리는 단위다. 그런데 한 덩어리로 묶는 것과 다른 요청을 기다리게 하는 것은 다르다. 트랜잭션은 중간 상태를 남기지 않을 뿐, 같은 시간에 다른 트랜잭션이 도는 것을 막지 않는다.

둘이 겹치지 않게 하려면 두 가지 중 하나가 필요한데 지금은 둘 다 없다. 하나는 락이다. 조회할 때 그 자리를 잠가 두면 뒤에 온 요청은 앞 요청이 끝날 때까지 기다린다. 그런데 MySQL 문서에 따르면 지금 쓰는 REPEATABLE READ에서 평범한 조회는 아무것도 잠그지 않는다. 다른 요청이 그 사이에 저장하는 것을 막지 않는다는 뜻이다. 다른 하나는 UNIQUE 제약이다. 같은 사용자·코트·날짜·시간대의 행이 두 개 생기면 DB가 거부하도록 테이블에 걸어 두는 규칙인데, 이 테이블에는 걸려 있지 않다. 그래서 두 저장이 모두 성공한다.

#### 3. F-1에서 본 재고 문제와 깨지는 자리가 같다

F-1에서는 재고 10개를 두 스레드가 동시에 하나씩 줄이는 경우를 봤다. 둘 다 10을 읽고 각자 9를 계산해 저장하는 바람에, 두 번 줄였는데 재고는 9에서 멈췄다. 차감 한 번이 사라진 것이다. 이번 중복은 결과가 반대다. 하나가 사라진 것이 아니라 하나가 늘었다.

결과는 달라도 깨지는 자리는 같다. 둘 다 값을 읽어 판단하는 일과 그 판단대로 쓰는 일이 떨어져 있고, 그 사이에 다른 요청이 들어왔다. 읽은 내용이 쓸 때까지 그대로일 것이라고 가정한 코드는 요청이 겹치는 순간 그 가정이 깨진다. 

#### 4. 100번 모두 깨진 것은 테스트가 매번 겹치게 만들었기 때문이다

동시성 문제는 실행 순서에 따라 생겼다 말았다 한다. 그렇다면 중복도 100번 중 몇 번만 나와야 할 것 같은데 두 상황 모두 100번 다 나왔다. 시간을 재 보니 이유가 있었다. 두 요청이 출발한 시각의 차이는 중간값으로 0.002ms인데, 요청 하나를 처리하는 데는 6.6ms가 걸렸다. 출발 간격이 처리 시간의 수천 분의 일이니 뒤 요청은 앞 요청이 한창 처리되는 중에 시작한다. 100번 모두 겹친 이유다. 신호를 맞추지 않은 상황도 다르지 않았다. 두 작업을 잇따라 보내면 신호가 없어도 출발 간격은 그대로 짧기 때문이다.

그러므로 100/100은 이 결함이 언제나 일어난다는 뜻이 아니라, 이 테스트가 결함이 드러나는 조건을 매번 만들어 냈다는 뜻이다.

#### 5. 이 결과를 어디까지 말할 수 있나

한 대의 PC에서 같은 프로그램과 DB를 켜 둔 채 반복한 관찰이다. 실제 사용자들이 요청을 보내는 간격을 흉내 낸 것이 아니므로, 100/100을 운영 환경에서 중복이 생길 확률로 읽으면 안 된다. 중복이 0번인 상황도 안전하다는 증명은 아니다. 이번 실행에서 발견되지 않았다는 뜻일 뿐이다.

시간은 서비스를 부르기 직전과 직후에 쟀고, DB 안에서 조회와 저장이 정확히 언제 실행됐는지는 기록하지 않았다. 그래서 2절의 단계 순서는 코드와 최종 결과를 맞춰 본 설명이다.
