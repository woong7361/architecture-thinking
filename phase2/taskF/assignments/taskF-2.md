# Task F-2: 동시성 버그 직접 재현하기 (The Kata)

(Grit's Why): 1-1에서 죽은 코드를, 2-1에서 죽은 기획서를 비평했다면, 여기서는 멀쩡해 보이는 코드를 본인 손으로 깨뜨립니다. 재현하지 못한 버그는 이해한 버그가 아닙니다.

### 수행 내용

1. 동시성 결함이 있는 기능 1개를 고르세요. 본인 시그니처 프로젝트의 재고 차감, 쿠폰 발급, 좌석 예매, 포인트 적립 중 하나면 좋습니다(없으면 단순 카운터로 시작).
2. 그 기능을 동시 요청으로 깨뜨리는 재현 테스트를 직접 작성하세요. ExecutorService와 CountDownLatch(또는 JMeter/k6)로 N개의 동시 요청을 보내고, 기대값과 실제값이 어긋나는 것을 테스트로 증명합니다. (예: 재고 100개에 100명이 동시 주문했는데 재고가 음수가 되거나, 쿠폰 1장이 여러 명에게 발급되는 것을 빨간불로 고정.)
3. 깨진 결과를 로그/스크린샷으로 남기고, "왜 이 숫자가 나왔는가"를 F-1의 메커니즘과 연결해 설명하세요.

### 제출물

- [ ] 동시성 재현 테스트 코드를 GitHub에(동시 요청 수, 기대값, 실제값이 드러나게).
- [x] 깨진 관찰 결과(로그/스크린샷) + 왜 그 숫자가 나왔는지 메커니즘 연결 설명. (최소 300자)

## 답안

### 제출물 1: 알림 신청 기능과 동시 테스트

taskE의 알림 신청에서 중복 여부를 확인하고 저장하는 부분을 작은 서비스로 옮겼다. 같은 사용자가 같은 코트·날짜·시간대로 다시 신청해도 감시 중인 신청은 하나만 남아야 하므로, [현재 서비스](../alert-kata/src/main/java/com/thinking/tennis/kata/AlertService.java)는 DB에서 기존 신청을 먼저 찾는다. 있으면 새로 저장하지 않고 기존 신청 ID를 반환하며, 없으면 새 신청을 저장한다. 종료된 신청은 이 조회에서 제외해 같은 조건으로 다시 신청할 수 있게 했다.

이 조회 후 저장 방식이 동시 요청에서도 신청을 하나만 남기는지 확인했다. Testcontainers로 실제 MySQL 8.4.8을 실행하고 InnoDB의 REPEATABLE READ 격리 수준을 사용했으며, 먼저 단일·순차 신청과 다른 사용자·시간대의 신청, 종료 후 재신청을 검사하는 기본 테스트 5개가 통과하는 것을 확인했다.

[반복 테스트](../alert-kata/src/test/java/com/thinking/tennis/kata/AlertSubscriptionTest.java)는 두 요청이 겹치는 상황과 그렇지 않은 상황을 비교한다. ExecutorService로 작업을 실행하고, 동시 시작 조건에서만 CountDownLatch로 서비스 호출 직전의 출발 신호를 맞췄다. 시작 신호 없이 두 작업을 연달아 제출하는 조건도 포함했으며, 서비스의 조회·저장 사이에는 대기나 지연을 넣지 않았다.

아래 다섯 조건을 각각 두 요청씩 100회 실행했다. 매회 신청 데이터를 비우되, 기존 신청을 재사용하는 조건만 1건을 미리 저장했다. 이후 두 요청의 처리가 끝나면 DB의 신청 건수와 반환 ID를 대조했다. 준비용 호출을 제외한 실험 요청은 총 1,000개다.

기본 테스트는 `mvn test`, 다섯 조건의 반복 테스트를 함께 실행하려면 `mvn -Pkata-red test`를 사용한다. [실행 방법과 코드](../alert-kata/README.md), [작업 계획·완료 조건](../../../.omx/plans/taskf-2-kata.md)을 정리했으며 GitHub 게시 전이다.

### 제출물 2: 관찰 결과와 원인

중복은 같은 조건의 신규 신청 두 개를 겹쳐 실행했을 때 발생했다. 2026-10-06 실행에서 이 조건은 출발 신호 유무와 관계없이 각각 100회 모두 신청이 2건 남았지만, 순차 요청과 기존 신청의 재사용에서는 중복이 없었다. [원본 로그](../alert-kata/evidence/review-rerun.log)

| 요청 조건 | 중복이 발생한 회차 |
|---|---:|
| 신청 없음, A의 저장이 확정된 뒤 B 호출 | 0 / 100 |
| 신청 없음, 두 요청에 같은 출발 신호 | 100 / 100 |
| 신청 없음, 출발 신호 없이 두 작업을 연달아 제출 | 100 / 100 |
| 기존 신청 1건이 있음, 두 요청에 같은 출발 신호 | 0 / 100 |
| 서로 다른 사용자, 두 요청에 같은 출발 신호 | 0 / 100 |

> **검토 메모 — 왜 100/100회가 나왔을까?**
>
> 처음에는 동시성의 실행 순서가 비결정적이라면 중복도 10/100회나 50/100회처럼 일부만 발생해야 한다고 생각했다. 확인해 보니 `NEW_TOGETHER`는 두 작업을 준비시킨 뒤 `CountDownLatch`의 출발 신호를 보내는 조건이었다. `NEW_UNCOORDINATED`는 래치로 기다리지 않았지만, 두 작업을 2개 스레드에 연속 제출했다. 이 환경에서는 요청 시작 간격의 중앙값이 0.002ms이고 서비스 호출 시간은 약 6.6ms여서 두 호출 구간이 100회 모두 겹쳤다. 따라서 100/100은 동시성의 비결정성이 없다는 뜻이 아니라, 이번 테스트 조건에서 결함을 일으키는 겹침이 매회 만들어졌다는 뜻이다. 운영 환경에서 중복이 발생할 확률이 100%라는 의미로 확대할 수는 없다.

기대값은 사용자·조건별로 감시 중인 신청 1건이므로, 서로 다른 사용자가 각각 1건씩 만든 것은 중복으로 세지 않았다. 모든 요청은 오류 없이 처리를 마쳤고, 기존 신청이 있는 조건에서는 두 요청 모두 그 신청의 ID를 반환했다. 반면 신규 생성이 겹친 두 조건은 기대값을 어겼으므로, 기본 테스트 5개와 조건별 반복 테스트 5개 중 2개가 실패했다.

중복의 원인은 기존 신청을 조회하는 것만으로는 동시에 만들어지는 신청까지 막을 수 없다는 점이다. A가 신청이 없음을 확인해도 아직 저장이 확정되지 않았다면 B 역시 없다고 조회할 수 있다. 그러면 두 요청 모두 새 신청을 만들기로 판단한다. 다음은 코드와 결과로 설명할 수 있는 실행 순서이며, SQL 실행 시점을 직접 기록한 것은 아니다.

| 단계 | 요청 A | 요청 B |
|---|---|---|
| 1 | 기존 신청이 없다고 조회 | |
| 2 | | A의 저장이 확정되기 전에 조회해 신청이 없다고 판단 |
| 3 | 새 신청을 저장하고 확정 | 새 신청을 저장하고 확정 |

조회와 저장을 하나의 트랜잭션으로 묶었지만, 이것만으로 두 요청의 처리가 차례대로 진행되지는 않는다. MySQL 공식 문서에 따르면 REPEATABLE READ의 일반 SELECT는 다른 트랜잭션의 쓰기를 막는 락을 설정하지 않는다. 여기에 현재 DB에는 같은 사용자·조건의 중복을 거부하는 UNIQUE 제약도 없어, 두 요청의 저장이 모두 확정될 수 있다. 즉, 기존 신청을 재사용하는 처리는 있지만 동시에 생성되는 중복까지 막는 구조는 아니다. [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

F-1의 갱신 유실과는 결과가 다르지만, 여러 단계의 처리 사이에 다른 요청이 끼어든다는 원리는 같다. 재고 예시에서는 같은 값을 덮어써 한 번의 차감이 사라졌고, 이번에는 두 요청이 각각 ‘없음’을 확인한 뒤 별도의 행을 추가했다. 이런 ‘확인 후 실행’ 사이의 경합은 MIT 강의의 잔액 확인 후 출금 예시에서도 설명한다. [MIT 6.005](https://web.mit.edu/6.005/www/fa16/classes/19-concurrency/#message_passing_example)

출발 신호를 없앤 조건에서도 두 작업을 연달아 제출하자 호출 구간이 100회 모두 겹쳤다. 두 호출의 시작 차이는 중앙값 0.002ms였고, 호출 시간은 중앙값 약 6.6ms였다. 따라서 출발 신호가 없다는 이유만으로 두 요청이 차례로 처리된다고 볼 수는 없다. 다만 이 값은 서비스 호출 직전·직후를 측정한 것이므로 정확한 SQL 실행 순서까지 보여주지는 않는다. [측정 결과와 검토](../alert-kata/evidence/review-results.md)

이번 결과는 같은 로컬 환경에서 반복한 관찰이며 운영 환경의 발생 확률을 뜻하지 않는다. F-2에서는 기존 신청을 확인한 뒤 생성하는 구현의 결함을 확인했고, 중복 방지 수정은 F-3에서 같은 기준으로 비교할 대상으로 남겨 두었다.
