# 사전 검토 후 재시험 결과

요구사항·구현·테스트 조건을 먼저 검토하고 판정 기준을 보완한 뒤, 다섯 조건을 각각 100회 실행했다. 현재 코드의 문제는 같은 조건의 새 신청이 함께 만들어질 때 중복을 막지 못한다는 점으로 확인됐다. 기존 신청을 찾아 반환하는 기능이 항상 실패하거나, 테스트가 모든 조건에서 중복을 만드는 결과는 아니었다.

## 실행 결과

2026-10-06, MySQL 8.4.8/InnoDB/REPEATABLE READ, Spring Boot 3.5.16, Testcontainers 2.0.5, JDK 25.0.4.1에서 `mvn -B -ntp -Pkata-red test`를 실행했다. [원본 로그](review-rerun.log), [JUnit 결과](review-rerun-junit.txt), [집계 JSON](review-rerun-summary.json).

| 조건 | 완료 회차 | 중복 발생 | 요청 오류 | 호출 구간이 겹친 회차 |
|---|---:|---:|---:|---:|
| 신청 없음, A 커밋 후 B 호출 | 100 | 0 | 0 | 0 |
| 신청 없음, 같은 시작 신호 | 100 | 100 | 0 | 100 |
| 신청 없음, 시작 신호 없이 두 작업 제출 | 100 | 100 | 0 | 100 |
| 신청 1건을 미리 커밋, 같은 시작 신호 | 100 | 0 | 0 | 100 |
| 서로 다른 사용자, 같은 시작 신호 | 100 | 0 | 0 | 100 |

매회 두 요청을 보내 총 1,000개 요청을 관찰했다. 기존 신청을 준비하는 100번의 호출은 별도이며 실험 요청 수에 포함하지 않는다. JUnit은 기본 테스트 5개와 조건별 집계 테스트 5개를 실행해 총 10개 중 2개가 실패했다. 오류와 건너뜀은 0개였다. 실패한 두 조건은 각각 중복 발생 회차 0이라는 기대값에 실제 100이 나왔다.

서로 다른 사용자 조건의 기대값은 사용자마다 1건, 전체 2건이다. 이를 중복으로 세지 않았다. 기존 신청 조건에서는 DB 건수뿐 아니라 미리 만든 신청 ID를 두 요청이 그대로 반환하는지도 통과했다.

## 왜 100회 모두 중복됐는가

시작 신호를 없애도 두 작업을 같은 실행기에 연달아 제출하므로 요청 시작 간격이 길어지는 것은 아니다. 이번 `NEW_UNCOORDINATED` 조건의 시작 차이 중앙값은 2μs, 서비스 호출 시간 중앙값은 6.589ms였다. 두 요청의 호출 구간은 100회 모두 겹쳤다. `NEW_TOGETHER`는 시작 차이 중앙값 3μs, 호출 시간 중앙값 7.266ms였다.

시작 차이의 중앙값은 조건별 100쌍, 호출 시간의 중앙값은 조건별 실험 요청 200개를 기준으로 계산했다. 기존 신청 준비 호출은 이 집계에서 제외했다.

현재 서비스는 일반 SELECT로 신청을 찾고, 없으면 INSERT한다. 두 요청이 각각 빈 조회 결과를 얻으면 각자 생성하며 이를 조율하는 락이나 업무 UNIQUE 제약이 없다. 최종 DB 행과 반환 ID를 보면 같은 조건에 두 신청이 커밋됐다. 조회 후 생성 사이의 경합이라는 설명은 코드와 최종 결과를 연결한 해석이다. 호출 구간 계측으로 정확한 SELECT 시각이나 DB 트랜잭션 구간을 직접 관측했다고 주장하지 않는다.

MySQL은 REPEATABLE READ의 일반 SELECT가 스냅샷을 읽으며 다른 트랜잭션의 쓰기를 막는 락을 설정하지 않는다고 설명한다. [MySQL 공식 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html)

## 재시험 전에 보완한 점

- 실제 저장소가 하나만 등록됐는지와 서비스 프록시를 검사해 이전의 테스트용 저장소가 끼어들지 않게 했다. 서비스·저장소·스키마의 동작은 이번 재시험에서 변경하지 않았다.
- 반환 ID를 해당 사용자·조건·감시 상태의 실제 행과 대조하고, 기존 신청이 있으면 준비한 ID도 확인했다.
- 요청 오류·중복·계약 위반을 독립 기록했다. 이 지표는 겹칠 수 있으므로 합산해 회차 수로 읽지 않는다.
- 다섯 조건은 독립된 JUnit 호출이라 한 조건의 단언 실패 후에도 나머지 조건을 실행했다.
- 순차 호출과 준비 호출에도 제한 시간을 적용했다. 실행기가 종료되지 않으면 다음 테스트의 데이터 정리를 금지한다. 이번 실행에는 중단 회차가 없었다.

## 해석의 범위

이 결과는 taskE 전체 기능을 검증한 것이 아니라 유효한 요청의 중복 신청 규칙을 분리한 F-2 실습이다. 지원 코트·시간대·만료 검증, HTTP, 인증, 재시도 키는 구현 범위 밖이다. 현재 구현이 동시 중복까지 보장하는 정상 기능이라는 표현은 사용하지 않는다.

같은 JVM·DB·연결 풀을 재사용한 100회 반복이며, 실제 사용자들의 요청 도착 분포를 측정한 것이 아니다. 공통 시작 신호 유무만으로 운영 트래픽과 같아지지 않는다. 100/100을 운영 발생 확률로 일반화하거나, 낮은 비율을 얻기 위해 임의 지연을 추가하지 않았다.

중복 방지 수정은 아직 하지 않았다. 기존 F-2/F-3 구분을 유지해 이번에는 구현 결함과 테스트 타당성을 확인했으며, F-3에서 이 기대값을 유지한 채 수정 전후를 비교할 수 있다.

사전 검토와 비교 조건은 [재시험 전 검토](review-before-rerun.md)에 있다. 검토 과정에서는 `thinking-review-gate`의 독립 검토를 사용했으며, 그 의견에 따라 반환 ID 판정과 오류 집계, 종료 실패 후 정리 차단을 보완했다.
