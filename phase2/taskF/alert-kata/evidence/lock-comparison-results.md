# 비관적 락과 낙관적 락 비교 결과

F-2의 `NEW_UNCOORDINATED`와 같은 방식으로 두 요청을 `ExecutorService`에 연속 제출했다. 각 전략은 같은 조건에서 100회 반복했고, 매회 활성 알림 행이 1개인지와 두 요청이 같은 ID를 반환하는지를 확인했다. 낙관적 락은 충돌한 트랜잭션을 새 트랜잭션으로 재시도했으며, 비관적 락은 사용자 행을 먼저 잠근 뒤 조회·저장했다.

실행 명령:

```text
mvn -B -ntp -Dtest=LockComparisonTest test
```

환경은 Testcontainers MySQL 8.4.8/InnoDB, Java 25, Spring Boot 3.5.16이며, 동일한 컨테이너 조건에서 실행을 세 번 반복했다. 요청 시간은 두 요청 각각의 서비스 프록시 호출 구간, 회차 시간은 두 요청을 제출한 시점부터 결과를 받은 시점까지 측정한 중앙값이다.

| 실행 | 비관적 요청 중앙값 | 비관적 회차 중앙값 | 낙관적 요청 중앙값 | 낙관적 회차 중앙값 | 낙관적 충돌·재시도 |
|---:|---:|---:|---:|---:|---:|
| 1 | 9.765ms | 11.517ms | 14.024ms | 16.971ms | 100회 |
| 2 | 11.831ms | 12.963ms | 16.070ms | 20.053ms | 100회 |
| 3 | 11.888ms | 13.816ms | 15.569ms | 18.561ms | 100회 |

세 번의 중앙값을 다시 비교하면 비관적 락은 요청 11.831ms, 회차 12.963ms였고 낙관적 락은 요청 15.569ms, 회차 18.561ms였다. 이번처럼 같은 사용자에게 두 요청이 항상 겹치는 조건에서는 낙관적 락이 매회 한 번 충돌하고 트랜잭션을 다시 실행하므로 더 느렸다. 이 값은 특정 하드웨어와 컨테이너의 측정값이며 모든 부하에서 같은 순서가 된다는 뜻은 아니다.

두 전략 모두 중복 0회, 요청 오류 0회, 활성 행 1개, 두 요청의 반환 ID 일치로 테스트를 통과했다. [비관적 락 구현](../src/main/java/com/thinking/tennis/kata/PessimisticAlertService.java)은 항상 존재하는 사용자 행에 `PESSIMISTIC_WRITE` 잠금을 먼저 걸어 같은 사용자의 요청을 직렬화한다. 따라서 별도 재시도 코드가 필요하지 않고 구현이 단순하지만, 잠금을 얻을 때까지 DB 연결을 점유하며 같은 사용자에 대한 다른 조건의 신청도 기다리게 된다. 모든 생성 경로가 같은 사용자 행을 같은 순서로 잠그지 않으면 교착 상태를 관리해야 한다. [MySQL 잠금 조회 문서](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html)

[낙관적 락 구현](../src/main/java/com/thinking/tennis/kata/OptimisticAlertService.java)은 사용자 `version`을 조건부로 증가시키는 SQL과 별도 `REQUIRES_NEW` 트랜잭션, 최대 재시도 횟수를 함께 사용한다. 충돌한 시도는 전체 트랜잭션을 롤백하고 새 트랜잭션에서 기존 신청을 다시 조회하므로 코드와 테스트가 더 복잡하다. 반면 충돌이 드문 환경에서는 요청을 오래 잠그지 않고 진행할 수 있으며, 재시도 횟수와 최대 시도 초과 시의 처리 정책을 애플리케이션에서 조절할 수 있다. 추가 Redis나 분산 락 인프라는 필요하지 않고, 모든 인스턴스가 공유하는 DB의 version 컬럼만 있으면 된다. [Jakarta Persistence 낙관적 잠금 명세](https://jakarta.ee/specifications/persistence/3.1/jakarta-persistence-spec-3.1)

따라서 같은 자원에 요청이 자주 몰리고 재시도보다 짧은 대기가 예측 가능하면 비관적 락이 단순하다. 충돌이 드물고 잠금으로 인한 대기를 줄이는 것이 중요하면 낙관적 락을 고려할 수 있지만, 충돌 예외·재시도·최대 시도 초과를 포함한 코드와 관측 지표가 필요하다. 어느 쪽이 항상 빠르다고 결론 내리지 않고, 실제 요청 분포와 충돌률을 측정해 선택해야 한다.
