# 재시험 전 검토

## 목적과 범위

같은 사용자·코트·날짜·시간대의 감시 중 신청이 하나여야 한다는 taskE FR-1·V-1을 기준으로 구현과 시험을 검토한다. 조회 후 대기로 실패를 만드는 방식은 사용하지 않으며, 100회 중 몇 회에서 규칙을 위반했는지를 관찰한다. 결과가 100회 모두 실패하거나 모두 통과하더라도 원하는 숫자가 나올 때까지 조건을 조정하지 않는다.

이번 검토의 기본 범위는 F-2의 결함과 테스트 타당성 확인이다. 동시 중복까지 수정하는 범위는 별도로 사용자에게 질문했으며, 답이 없으면 기존 F-2/F-3 구분을 유지한다. F-2의 이 구현을 완성된 정상 기능으로 표현하지 않는다.

## 확인한 문제

1. **업무 규칙을 보장하지 않는 구현**: AlertService.subscribe는 트랜잭션 안에서 findActive 후 없으면 INSERT한다. 저장소 조회에는 락이 없고 스키마에는 업무 조건의 UNIQUE가 없다. 같은 조건의 두 생성이 조율되지 않는다. KataUser.version은 읽거나 갱신하지 않아 중복을 막지 못한다.
2. **실험 조건이 한쪽으로 제한됨**: 기존 100회는 매회 신청이 없는 상태에서 같은 조건의 두 요청을 함께 출발시켰다. 생성 경합의 관찰에는 유효하지만 일반 요청을 대표하지 않는다. 100/100이 시험 조작을 입증하는 것도, 운영 발생 확률이 100%라는 뜻도 아니다.
3. **반례 비교 부족**: 순차 요청과 기존 신청 재사용은 기본 테스트에서만 확인했다. 동일한 100회 실험 틀에서 시작 방식과 초기 상태를 비교해야 시험이 항상 중복을 만드는지 구분하기 쉽다.
4. **관찰 범위의 한계**: 원본 로그에는 최종 건수와 반환 ID만 있으므로 정확한 SELECT 시점, DB 연결 ID, SQL 사이의 순서를 직접 측정했다고 말할 수 없다. 서비스 호출 구간이 겹쳤는지는 호출 직전·직후 시각으로 별도 관찰할 수 있지만 SQL 구간의 겹침과는 구분해야 한다.
5. **판정의 빈틈**: 기존 반복 시험은 건수만 집계해 기존 ID 반환까지 검사하지 않았다. 회차별 DB의 실제 ID와 반환 ID도 대조해야 한다. 서로 다른 사용자가 각각 한 건을 만든 결과를 중복으로 집계하면 안 된다.
6. **시간 초과 뒤의 정리**: 작업이 남아 있는데 다음 회차나 다른 테스트가 DELETE를 실행해서는 안 된다. 작업을 취소하고 실행기 종료를 확인하며, 종료하지 못하면 이후 준비 단계도 실패하게 해야 한다. 불완전한 실행은 100회 합계로 출력하지 않는다.
7. **전체 기능과 실습 범위의 구분**: taskE에는 지원 코트·시간대·만료 검증과 HTTP 재시도 키 계약도 있다. 현재 Kata는 유효한 요청의 중복 신청 규칙만 분리한 실습이며 전체 taskE 구현을 검증하는 것이 아니다.

## 재시험 설계

모든 비교는 같은 서비스·저장소·MySQL 8.4.8/InnoDB/REPEATABLE READ에서 실행한다. 비밀번호는 이미 사용자가 지정한 폐기용 값을 사용한다. 각 조건은 100회, 회차당 서비스 요청 2개이며, 기존 신청 준비 호출은 요청 수에 포함하지 않는다.

| 조건 | 시작 전 신청 | 요청 방식 | 기대 |
|---|---|---|---|
| 순차 신규 | 없음 | A 커밋 후 B 호출 | 같은 ID, 감시 중 1건 |
| 동시 신규 | 없음 | 서비스 호출 전 공통 시작 신호 | 같은 ID, 감시 중 1건 |
| 시작 신호 없는 신규 | 없음 | 실행기에 두 작업을 차례로 제출, 완료는 나중에 수집 | 같은 ID, 감시 중 1건 |
| 동시 기존 신청 | 미리 1건 커밋 | 공통 시작 신호 | 준비한 ID 반환, 감시 중 1건 |
| 서로 다른 사용자 | 없음 | 공통 시작 신호 | 사용자마다 1건, 총 2건 |

서비스 내부에는 대기·sleep·가짜 반환·관찰용 SQL을 넣지 않는다. 호출 직전과 프록시 반환 직후의 시간만 기록해 시작 차이와 호출 구간 겹침을 보조 지표로 삼는다. 이는 운영 트래픽의 도착 분포를 재현하는 것이 아니다.

매회 모든 호출의 반환을 수집한 뒤 DB 건수를 업무 조건별로 세고, 반환 ID가 해당 조건의 실제 행에 속하는지도 확인한다. 준비한 ID가 있다면 그 ID도 확인한다. 오류·중복·그 외 규칙 위반을 구분하고, 실제 위반을 감싸서 성공으로 만들지 않는다. 첫 실패 후에도 완전한 회차는 모두 수집하고 마지막에 위반 0회라는 기대값을 판정한다. 시간 초과는 실험 중단으로 표시한다.

## 선택지와 판단

- **비교 조건을 추가해 F-2를 먼저 검증**: 같은 구현에서 초기 상태와 요청 시작 방식을 비교할 수 있고 F-3의 수정 전 기록도 남는다. 단, 동시 중복 결함 자체는 남는다. 현재 작업의 기본 선택이다.
- **지금 중복 방지까지 수정해 전후 비교**: 업무 규칙 충족까지 확인할 수 있지만 F-3의 설계 선택과 구현이 이번 범위에 들어온다. 사용자가 이 범위를 선택하면 같은 시험으로 전후를 비교한다.
- **원래의 100회 시험만 재실행**: 비용은 작지만 기존 결과의 원인을 구분할 비교가 부족해 선택하지 않는다.

## 재시험 전에 반영한 검토 의견

별도 검토에서 요청 오류와 DB 중복이 함께 발생할 수 있다는 점을 확인했다. 새 테스트는 요청 오류·중복·전체 계약 위반을 독립적으로 기록하므로 지표를 더해 회차 수로 해석하지 않는다. 정상 회차는 요청 오류와 계약 위반이 모두 없는 경우다.

다섯 조건은 JUnit의 독립적인 매개변수 테스트로 실행해 한 조건의 건수 단언 실패가 나머지 조건을 막지 않게 한다. `safeToReset`은 실행기 종료가 확인될 때만 복구하므로 이전 작업이 남아 있으면 다음 준비 단계의 데이터 정리도 금지한다. 시간 초과는 Future 취소와 실행기 종료를 거쳐 `ABORT`와 완료 회차를 기록한다.

서비스 호출 구간은 `System.nanoTime()`으로 기록하고 `max(시작) < min(종료)`일 때 겹쳤다고 판정한다. 서비스 내부는 계측하지 않는다. 같은 JVM·컨테이너·연결 풀을 재사용한 반복 관찰이므로 독립 표본으로 가정한 통계적 확률 추정을 하지 않는다.

실행 시 실제 AlertRepository가 하나만 등록됐는지와 서비스가 Spring 프록시인지도 검사한다. 기존 대기용 저장소 설정이 끼어들면 실험을 진행하지 않는다.

검토용 CLI는 로컬 버전과 모델의 호환성 문제로 실행되지 않아, 같은 critique/eval 지침을 내장 검토 에이전트로 수행했다. 저장된 검토 결과와 schema validation은 [검토 기록](../../../../.codex/skills/thinking-review-gate/runs/taskf2-rerun-review-20261006/attempts/1/critique.md)에 남겼다.
