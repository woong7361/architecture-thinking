# Task E-4: API Contract 설계 (스키마 우선, 에러 체계, 멱등성 기초)

(Grit's Why): E-3에서 못 박은 요구사항을 이제 기계와 동료가 함께 읽는 계약으로 만듭니다. 명세가 곧 계약입니다.

### 수행 내용

1. E-3의 기능을 스키마 우선(OpenAPI 또는 Protobuf)으로 API 계약으로 작성하세요. 요청과 응답 스키마, 필수와 선택 필드, 제약 조건을 명시합니다.
2. 에러 코드 체계를 세우세요. 4xx(클라이언트 잘못)와 5xx(서버 잘못)를 구분하고, 비즈니스 에러(예: 재고 없음)와 시스템 에러(예: DB 타임아웃)를 분리하세요. 각 에러의 의미와 클라이언트가 어떻게 대응해야 하는지 적습니다.
3. 멱등성 기초. 재시도가 안전해야 하는 엔드포인트 1개를 골라 Idempotency-Key를 설계하세요. 키를 어떻게 만들고, 어디에 저장하며, 중복 요청이 오면 어떤 응답을 돌려줄지 정합니다. (분산 환경 멱등성은 Station 2-4에서 심화합니다.)

### 제출물

- [ ] OpenAPI 또는 Protobuf 계약 파일을 GitHub에.
- [ ] 에러 코드 체계표(비즈니스 에러와 시스템 에러 분리).
- [ ] 멱등성 설계 메모(Idempotency-Key의 생성, 저장, 중복 응답 흐름). (최소 300자)

### 1. 계약은 경계마다 따로 쓴다

약속해야 할 경계가 둘이라 계약 파일도 둘로 나눴다. 하나는 클라이언트가 우리에게 요청을 보내고 응답을 받는 HTTP 표면이고, 다른 하나는 우리가 만들어 단말로 내보내는 알림 메시지다. 상대도 방향도 다른 둘을 한 파일에 넣으면 한쪽의 어휘로 다른 쪽을 적게 된다.

### 2. 에러 코드 체계표

코드는 클라이언트의 대응이 갈리는 자리에만 둔다. 상황을 잘게 나눌수록 표는 촘촘해지지만, 대응이 같은 두 코드는 클라이언트가 분기할 일이 없어 무시되고 결국 상태 코드로 돌아간다. 그래서 필수 멱등 키 헤더가 없는 경우를 따로 두지 않고 `VALIDATION_FAILED`에 넣었다. 헤더를 채워 다시 보내야 풀리는 실패라 다른 형식 위반과 고치는 방법이 같고, 어느 헤더가 비었는지는 `detail`이 지목한다. 같은 키의 앞선 요청이 아직 처리 중인 경우도 `CONCURRENT_UPDATE_CONFLICT`에 넣었다. 그 판정은 잠금 대기가 제한 시간을 넘긴 것이고 대응은 기다렸다 같은 요청을 다시 보내는 것이라, 저장소 경합에 밀린 것과 다르지 않다.

멱등성 전용 코드는 그래서 `IDEMPOTENCY_KEY_REUSED` 하나다. 이 키는 탔으니 새 키로 만들라는 지시는 다른 어떤 코드도 대신 하지 못한다. 덕분에 표의 409는 전부 재시도 불가가 되어, 상태 코드로 분기하는 클라이언트도 이 자리에서 틀리지 않는다.

재시도 가능 여부는 계약에 직접 적는다. 모든 실패 응답에 `retryable`이 들어가고, 재시도해도 되는 실패에는 `retryAfterSeconds`와 표준 `Retry-After` 헤더가 함께 온다. 이 값이 없으면 클라이언트가 상태 코드를 제 식대로 해석해, 재시도하면 풀릴 실패를 포기하거나 영영 같은 실패가 날 요청을 계속 보낸다. 다만 이 조건은 스키마로 적을 수 없어 검사 스크립트가 대신 판정한다.


| 코드                               | HTTP    | 분류    | 언제 나는가                                            | 재시도 |
| -------------------------------- | ------- | ----- | ------------------------------------------------- | --- |
| `VALIDATION_FAILED`              | 400     | 요청 검증 | 요청의 형식이나 값이 스키마를 만족하지 않는다. 멱등 키 헤더의 누락도 여기에 든다   | 불가  |
| `UNAUTHENTICATED`                | 401     | 요청 검증 | 토큰이 없거나 유효하지 않다                                   | 불가  |
| `COURT_NOT_SUPPORTED`            | 404·422 | 비즈니스  | 서비스가 지원하지 않는 코트다. 경로에서 받으면 404, 본문에서 받으면 422로 나간다 | 불가  |
| `SLOT_NOT_SUPPORTED`             | 422     | 비즈니스  | 그 코트가 그 날짜에 운영하지 않는 시간대다                          | 불가  |
| `ALERT_WINDOW_CLOSED`            | 422     | 비즈니스  | 만료 시각이 이미 지난 조건이다                                 | 불가  |
| `ALERT_NOT_FOUND`                | 404     | 비즈니스  | 그런 신청이 없거나 본인의 것이 아니다                             | 불가  |
| `IDEMPOTENCY_KEY_REUSED`         | 409     | 비즈니스  | 같은 키가 내용이 다른 요청에 이미 쓰였다                           | 불가  |
| `UPSTREAM_TIMEOUT`               | 504     | 시스템   | 예약처가 제때 응답하지 않았고 마지막 성공 결과도 없다                    | 가능  |
| `UPSTREAM_UNAVAILABLE`           | 503     | 시스템   | 예약처에 닿지 못했거나 예약처가 실패를 돌려줬다                        | 가능  |
| `UPSTREAM_RESPONSE_UNREADABLE`   | 502     | 시스템   | 예약처의 응답은 왔지만 읽지 못했다                               | 가능  |
| `STORAGE_TIMEOUT`                | 503     | 시스템   | 저장소가 제때 응답하지 않았다                                  | 가능  |
| `CONCURRENT_UPDATE_CONFLICT`     | 503     | 시스템   | 같은 자원을 동시에 고치려다 경합에 밀렸다. 같은 멱등 키를 기다리다 물러난 경우를 포함한다 | 가능  |
| `INTERNAL_ERROR`                 | 500     | 시스템   | 위 어디에도 해당하지 않는 서버 내부 실패다                          | 가능  |


### 3. 멱등성 설계 메모

재시도가 안전해야 하는 엔드포인트로 `POST /alerts`를 골랐다. 같은 요청이 두 번 들어오면 신청이 둘 생기는 API가 이것뿐이고, NFR-1대로 예약 오픈 시각에 가입자가 한꺼번에 몰리는 자리다. 응답이 늦으면 사용자는 버튼을 다시 누르고 앱은 답을 받지 못한 요청을 다시 보낸다.

#### 키를 어떻게 만드는가

키는 클라이언트가 신청 하나마다 UUID로 만들고, 재시도에는 처음 보낸 값을 그대로 다시 보낸다. 서버가 요청 조건에서 키를 파생시키면 같은 조건의 새 요청과 재시도가 구분되지 않는다. 키가 유효한 범위는 `(user_id, endpoint, idempotency_key)`라, 다른 사용자가 같은 UUID를 써도 서로의 응답을 받지 않는다.

#### 어디에 무엇을 저장하는가

기록은 `idempotency_record` 한 행이고, 신청과 같은 트랜잭션에서 커밋한다. 따로 커밋하면 신청은 생겼는데 기록은 없는 창이 열리고, 그 창에 들어온 재시도가 두 번째 신청을 만든다. 한 행에 담는 값은 넷이다.

- `(user_id, endpoint, idempotency_key)`에 걸린 유니크 제약. 중복 판정과 동시 요청 직렬화를 이 제약이 맡는다.
- 요청 본문 해시. 같은 키에 다른 본문이 왔는지 가린다. 필드 순서만 바뀐 같은 요청이 409를 받지 않도록 정규화한 뒤 해시한다.
- 돌려준 상태 코드와 응답 본문. 재시도에 재생할 답이다. 2xx만 기록하고, 요청을 고쳐야 풀리는 4xx는 같은 키로 다시 와도 조건을 다시 판정한다. 계약도 재시도 안전을 응답을 받지 못했거나 5xx를 받은 경우로 한정해 적었다.
- 만료 시각. 수명은 24시간이다. 요구사항에 없어 여기서 정했고, 오프라인이었다가 다음 날 돌아온 앱의 재시도까지 덮는 길이다.

#### 중복 요청에 무엇을 돌려주는가

| 들어온 요청                | 응답                                                        | `Idempotency-Replayed` |
| --------------------- | --------------------------------------------------------- | ---------------------- |
| 처음 보는 키               | 201, 새로 만든 신청                                             | false                  |
| 기록이 있고 본문이 같다         | 기록한 상태 코드와 본문을 그대로 재생 (201 또는 200)                        | true                   |
| 기록이 있고 본문이 다르다        | 409 `IDEMPOTENCY_KEY_REUSED`                              | —                      |
| 같은 키의 앞선 요청이 처리 중     | 잠금을 기다려 재생. 못 얻으면 409 `IDEMPOTENT_REQUEST_IN_PROGRESS`      | 재생하면 true               |
| 기록이 만료된 뒤 온 재시도       | 새 요청으로 처리. 같은 조건을 아직 감시 중이면 200으로 그 신청을 돌려준다             | false                  |

재생은 상태 코드까지 그대로 돌려준다. 201이 200으로 바뀌면 클라이언트가 그 차이로 재시도 여부를 분기하게 된다. 본문이 다른 요청에 앞선 결과를 주지 않는 이유도 같은 자리다. 보낸 적 없는 조건의 신청을 자기 것으로 믿는다.

처리 중은 상태 컬럼 없이 유니크 제약의 잠금으로 판정한다. 같은 키가 동시에 들어오면 두 번째 삽입이 첫 트랜잭션을 기다렸다가, 커밋됐으면 기록을 읽어 재생하고 롤백됐으면 처음 온 요청처럼 처리한다.

#### 신청 테이블의 유니크 제약과 나누는 일

두 장치는 다른 실패를 막는다. 신청 테이블의 유니크 제약이 막는 것은 같은 조건을 두 번 신청하는 일이라, FR-1대로 제약 위반을 잡아 기존 신청을 200으로 돌려준다. 동시에 들어온 중복도 여기서 처리해, 진 쪽이 받는 제약 위반을 500으로 흘리지 않는다. 멱등 키가 막는 것은 재시도가 처음과 다른 응답을 받는 일이다. 조건으로만 찾아 돌려주면 그사이 알림이 나간 신청은 다른 상태로 돌아와, 클라이언트는 자기 요청이 무엇을 했는지 알 수 없다.

#### 검증

Testcontainers로 띄운 MySQL에 스레드 둘이 같은 키로 보내, 신청이 하나인지와 두 응답의 본문이 같은지를 함께 본다(V-1). 1-1에서 전략만 쓰고 실행 로그를 남기지 않은 이중 방지 테스트와 대상이 같으니, 그 로그를 E-5의 계약 테스트와 함께 남긴다.
