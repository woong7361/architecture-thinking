# Task E-4: API Contract 설계 (스키마 우선, 에러 체계, 멱등성 기초)

(Grit's Why): E-3에서 못 박은 요구사항을 이제 기계와 동료가 함께 읽는 계약으로 만듭니다. 명세가 곧 계약입니다.

### 수행 내용

1. E-3의 기능을 스키마 우선(OpenAPI 또는 Protobuf)으로 API 계약으로 작성하세요. 요청과 응답 스키마, 필수와 선택 필드, 제약 조건을 명시합니다.

### 1. 계약은 경계마다 따로 쓴다

약속해야 할 경계가 둘이라 계약 파일도 둘로 나눴다. 하나는 클라이언트가 우리에게 요청을 보내고 응답을 받는 HTTP 표면이고, 다른 하나는 우리가 만들어 단말로 내보내는 알림 메시지다. 상대도 방향도 다른 둘을 한 파일에 넣으면 한쪽의 어휘로 다른 쪽을 적게 된다.

### 2. 에러 코드 체계표

| ------------------------------ | ------- | ----- | --------------------------------------------------- | ---------------------------------------------------------- | --- |
| `VALIDATION_FAILED`            | 400     | 요청 검증 | 요청의 형식이나 값이 스키마를 만족하지 않는다. 멱등 키 헤더의 누락도 여기에 든다      | `detail`의 필드와 값을 고쳐 같은 요청을 다시 보낸다. 멱등 키는 유효한 UUID로 채운다.    | 불가  |

### 3. 멱등성 설계 메모

재시도가 안전해야 하는 엔드포인트로 `POST /alerts`를 골랐다. 조회는 상태를 바꾸지 않고 해제는 몇 번 불러도 결과가 같지만, 신청은 요청 한 번에 신청 한 건을 만든다. 응답을 받지 못한 사용자가 버튼을 다시 누르면 서버는 그 요청이 재시도인지 새 신청인지 구분할 수 없다.

#### 키를 어떻게 만드는가

키는 클라이언트가 신청 하나마다 UUID로 만들고, 재시도할 때는 처음 보낸 값을 그대로 다시 보낸다. 서버가 요청 조건으로 키를 만들면 같은 조건의 새 신청과 앞선 요청의 재시도가 같은 키를 갖게 되어 둘을 구분할 수 없다.

#### 어디에 무엇을 저장하는가

기록은 `idempotency_record` 테이블에 한 행으로 저장하고, 신청과 같은 트랜잭션에서 커밋한다. 트랜잭션을 나누면 신청은 저장됐는데 기록은 없는 구간이 생기고, 그 사이에 온 재시도는 신청을 하나 더 만든다. 한 행의 컬럼은 다음과 같다.

- `user_id`, `endpoint`, `idempotency_key`: 키를 식별하는 범위이며, 세 컬럼에 유니크 제약을 건다. 사용자를 범위에 넣었으므로 다른 사용자가 같은 UUID를 써도 서로의 기록을 읽지 않는다.
- `request_hash`: 정규화한 요청 본문의 해시. 같은 키로 온 요청이 처음과 같은 내용인지 비교하는 데 쓴다.
- `expires_at`: 저장 후 24시간. 요구사항에 없는 값이라 여기서 정했고, 오프라인이던 기기가 다음 날 보내는 재시도까지 받을 수 있는 길이로 잡았다.

#### 중복 요청에 무엇을 돌려주는가

같은 키로 요청이 다시 오면 본문이 처음과 같은지 확인한다. 같으면 응답을 못 받은 클라이언트가 다시 보낸 것이므로 처음 결과를 돌려준다. 다르면 클라이언트가 키를 다른 요청에 잘못 쓴 것이므로 409로 거부한다. 이때 처음 결과를 돌려주면 클라이언트는 자기가 보내지 않은 신청을 자기 결과로 착각한다. 본문은 정규화한 해시로 비교하므로 필드 순서만 다른 요청은 같은 본문으로 본다.


| 들어온 요청               | 응답                                                                    | `Idempotency-Replayed` |
| -------------------- | --------------------------------------------------------------------- | ---------------------- |
| 처음 보는 키              | 201, 새로 만든 신청. 같은 조건을 감시 중인 신청이 이미 있으면 200, 그 신청                      | false                  |
| 기록이 있고 해시가 같다        | 처음 요청의 결과                                                             | true                   |
| 기록이 있고 해시가 다르다       | 409 `IDEMPOTENCY_KEY_REUSED`                                          | —                      |
| 같은 키의 앞선 요청이 아직 처리 중 | 끝날 때까지 기다린 뒤 위 규칙대로 응답한다. 제한 시간을 넘기면 503 `CONCURRENT_UPDATE_CONFLICT` | 결과를 돌려주면 true          |
| 기록이 만료된 뒤에 온 재시도     | 처음 보는 키로 처리                                                           | false                  |


재시도에는 상태 코드까지 처음과 똑같이 돌려준다. 201이 200으로 바뀌면 클라이언트는 신청이 새로 만들어지지 않았다고 판단하는데, 그 차이는 재시도 때문에 생긴 것이라 판단이 틀린다.

처리 중인지는 상태 컬럼을 따로 두지 않고 유니크 제약으로 판정한다. 같은 키가 동시에 들어오면 두 번째 삽입이 첫 트랜잭션이 끝날 때까지 기다리고, 첫 트랜잭션이 커밋됐으면 그 결과를 돌려주며 롤백됐으면 처음 보는 요청으로 처리한다.
