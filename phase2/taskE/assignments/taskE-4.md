# Task E-4: API Contract 설계 (스키마 우선, 에러 체계, 멱등성 기초)

(Grit's Why): E-3에서 못 박은 요구사항을 이제 기계와 동료가 함께 읽는 계약으로 만듭니다. 명세가 곧 계약입니다.

### 수행 내용

1. E-3의 기능을 스키마 우선(OpenAPI 또는 Protobuf)으로 API 계약으로 작성하세요. 요청과 응답 스키마, 필수와 선택 필드, 제약 조건을 명시합니다.
2. 에러 코드 체계를 세우세요. 4xx(클라이언트 잘못)와 5xx(서버 잘못)를 구분하고, 비즈니스 에러(예: 재고 없음)와 시스템 에러(예: DB 타임아웃)를 분리하세요. 각 에러의 의미와 클라이언트가 어떻게 대응해야 하는지 적습니다.
3. 멱등성 기초. 재시도가 안전해야 하는 엔드포인트 1개를 골라 Idempotency-Key를 설계하세요. 키를 어떻게 만들고, 어디에 저장하며, 중복 요청이 오면 어떤 응답을 돌려줄지 정합니다. (분산 환경 멱등성은 Station 2-4에서 심화합니다.)

### 제출물

- [ ] OpenAPI 또는 Protobuf 계약 파일을 GitHub에.
- [ ] 에러 코드 체계표(비즈니스 에러와 시스템 에러 분리).
- [ ] 멱등성 설계 메모(Idempotency-Key의 생성, 저장, 중복 응답 흐름). (최소 300자)

### 1. 계약은 경계마다 따로 쓴다

약속해야 할 경계가 둘이라 계약 파일도 둘로 나눴다. 하나는 클라이언트가 우리에게 요청을 보내고 응답을 받는 HTTP 표면이고, 다른 하나는 우리가 만들어 단말로 내보내는 알림 메시지다. 상대도 방향도 다른 둘을 한 파일에 넣으면 한쪽의 어휘로 다른 쪽을 적게 된다.

### 2. 에러 코드 체계표

이 표는 클라이언트의 다음 행동이 달라지는 경우만 코드로 나눈다. 4xx는 `detail`을 보고 요청이나 조건을 고친 뒤 다시 보내고, 5xx는 `retryable`과 `Retry-After`를 따른다. 필수 멱등 키 누락은 `VALIDATION_FAILED`, 같은 키로 다른 본문을 보낸 경우는 `IDEMPOTENCY_KEY_REUSED`, 동시 갱신 경합은 `CONCURRENT_UPDATE_CONFLICT`로 구분한다.

`retryable`이 true이면 `retryAfterSeconds` 또는 `Retry-After`만큼 기다린 뒤 같은 요청을 다시 보낸다. `POST /alerts`는 재시도할 때 같은 `Idempotency-Key`를 유지한다. 예약 상태 확인 실패는 빈자리 없음으로 해석하지 않고 잠시 후 다시 조회하며, 마지막 성공 결과가 있으면 갱신 실패를 함께 표시한다([FR-3], [EF-1]).

| -------------------------------- | ------- | ----- | ------------------------------------------------- | ------------------------------------------------------------------ | --- |
| `VALIDATION_FAILED`              | 400     | 요청 검증 | 요청의 형식이나 값이 스키마를 만족하지 않는다. 멱등 키 헤더의 누락도 여기에 든다   | `detail`의 필드와 값을 고쳐 같은 요청을 다시 보낸다. 멱등 키는 유효한 UUID로 채운다. | 불가  |

### 3. 멱등성 설계 메모

재시도가 안전해야 하는 엔드포인트로 `POST /alerts`를 골랐다. 계약의 다섯 오퍼레이션 중 같은 요청을 두 번 보냈을 때 응답이 달라지는 것이 이것뿐이다. 조회는 상태를 바꾸지 않고 해제는 몇 번 불러도 같은 답이 나오는데, 신청만 요청 한 번에 신청 한 건을 만든다. 응답을 받지 못한 사용자는 버튼을 다시 누르고, 서버는 그 재시도를 처음 보내는 요청과 구분할 수단이 없다.

#### 키를 어떻게 만드는가

키는 클라이언트가 신청 하나마다 UUID로 만들고, 재시도할 때는 처음 보낸 값을 그대로 다시 보낸다. 서버가 요청 조건에서 키를 만들어 쓰면 안 된다. 그렇게 하면 같은 조건으로 새로 신청하는 요청과 앞선 요청의 재시도가 같은 키를 갖게 되어 서버가 둘을 구분할 수 없다. 키를 비교하는 범위는 `(user_id, endpoint, idempotency_key)`다. 그래서 다른 사용자가 같은 UUID를 쓰더라도 서로의 응답을 받지 않는다.

#### 어디에 무엇을 저장하는가

기록은 `idempotency_record` 테이블의 한 행이고, 신청과 같은 트랜잭션에서 커밋한다. 트랜잭션을 나누면 신청은 저장됐는데 기록은 아직 없는 짧은 구간이 생긴다. 그 구간에 재시도가 들어오면 서버는 처음 보는 키로 판단해 신청을 하나 더 만든다. 한 행에 담는 값은 넷이다.

- `(user_id, endpoint, idempotency_key)`에 걸린 유니크 제약. 중복인지 판정하는 일과 같은 키의 동시 요청을 한 줄로 세우는 일을 이 제약 하나가 맡는다.
- 요청 본문의 해시. 같은 키로 다른 내용이 왔는지 알아내는 데 쓴다. 필드 순서만 다른 같은 요청이 409를 받지 않도록, 본문을 정규화한 뒤에 해시한다.
- 돌려준 상태 코드와 응답 본문. 재시도에 다시 돌려줄 답이다. 2xx만 기록한다. 4xx는 요청을 고쳐야 풀리는 실패라 기록하지 않고, 같은 키로 다시 와도 조건을 처음부터 다시 판정한다. 계약에도 재시도가 안전한 경우를 응답을 받지 못했거나 5xx를 받은 경우로 한정해 적었다.
- 만료 시각. 기록의 수명은 24시간이다. 요구사항에 없는 값이라 여기서 정했고, 기기가 오프라인이었다가 다음 날 돌아와 보내는 재시도까지 받아 줄 수 있는 길이로 잡았다.

#### 중복 요청에 무엇을 돌려주는가

| 들어온 요청                 | 응답                                                               | `Idempotency-Replayed` |
| --------------------- | ---------------------------------------------------------------- | ---------------------- |
| 처음 보는 키               | 201, 새로 만든 신청                                                    | false                  |
| 기록이 있고 본문도 같다         | 기록해 둔 상태 코드와 본문을 그대로 다시 돌려준다 (201 또는 200)                        | true                   |
| 기록이 있고 본문이 다르다        | 409 `IDEMPOTENCY_KEY_REUSED`                                     | —                      |
| 같은 키의 앞선 요청이 아직 처리 중  | 잠금을 기다려 그 결과를 그대로 돌려준다. 제한 시간 안에 얻지 못하면 503 `CONCURRENT_UPDATE_CONFLICT` | 기록을 돌려주면 true         |
| 기록이 만료된 뒤에 온 재시도      | 처음 보는 키로 처리한다. 같은 조건을 아직 감시 중이면 200으로 그 신청을 돌려준다                 | false                  |

다시 돌려줄 때는 상태 코드까지 처음과 똑같이 한다. 201이 200으로 바뀌면 클라이언트는 그 차이를 보고 신청이 새로 만들어졌는지를 판단하게 되는데, 그 값은 재시도 때문에 달라진 것이라 판단이 틀린다. 본문이 다른 요청에 앞선 응답을 돌려주지 않는 이유도 같다. 그렇게 하면 클라이언트는 자기가 보낸 적 없는 조건의 신청을 자기 요청의 결과로 받아들인다.

처리 중인지는 따로 상태 컬럼을 두지 않고 유니크 제약의 잠금으로 판정한다. 같은 키가 동시에 들어오면 두 번째 삽입이 첫 트랜잭션이 끝날 때까지 기다린다. 첫 트랜잭션이 커밋됐으면 기록을 읽어 그 응답을 그대로 돌려주고, 롤백됐으면 처음 보는 요청처럼 처리한다.
