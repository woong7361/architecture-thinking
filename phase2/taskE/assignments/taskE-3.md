# Task E-3: 죽은 기획서를 살아있는 요구사항으로 (요구사항 명세 + NFR + 엣지케이스)

(Grit's Why): 모호한 기획은 기술 부채의 뿌리입니다. 코드를 짜기 전에 모호함을 명확함으로 바꾸는 요구사항 설계부터 합니다. 1-1에서 죽은 코드를 비평했다면, 여기서는 죽은 기획서를 비평합니다.

> 현웅님 메모: E-3의 예시 기획서가 이미 하신 일과 겹칩니다
>
> E-3 1번의 예시 기획서가 티켓 예매 대기열입니다. 현웅님은 Phase 0 Task 5에서 같은 시나리오를 직접 고르셔서 Redis INCR 순번 발급과 Sorted Set 대기열, admitter의 batch 입장, 짧은 TTL의 admission token까지 이미 설계하셨고, 1-2와 1-3의 코드베이스도 티켓 예매입니다. 이 예시를 처음 보는 기획서처럼 비평하시면 이미 하신 일을 두 번 세게 됩니다.
>
> 그래서 1번은 이렇게 하십시오. 컨셉 부재와 NFR 부재 비평은 Phase 0에서 이미 쓰신 요구사항 위에서 시작하시되, 그때 안 쓰신 것을 겨눠 주세요. Phase 0에서 처음에는 초당 500명처럼 보수적인 값으로 시작한다고 적으셨지만 그 숫자를 어디서 얻을지는 적지 않으셨습니다. NFR 세 가지 중 하나는 그 숫자를 어떻게 정해야 했는지에 쓰시면 됩니다. 엣지 케이스도 같습니다. 같은 사용자의 중복 요청이나 재시도가 중복 구매로 이어지지 않아야 한다까지 요구사항으로는 세우셨지만 그것을 계약으로 옮기지는 않으셨습니다. 그 간극이 비평의 대상입니다.
>
> 2번의 본인 기능은 환불 요청 하나로 좁히시길 권합니다. 정확히는 1-1에서 짜신 구독 일할 환불을 HTTP 표면으로 올리는 것입니다. 근거가 셋 있습니다. 첫째, 요구사항 재료가 이미 손에 있습니다. 이미 전액 환불된 주문, 아직 결제 대기중인 주문, 앱스토어나 구글 플레이처럼 이 경로로 환불하면 안 되는 결제 수단을 각각 거절 시나리오로 두셨고 수동 금액 한도 초과와 0원 이하와 구독 기간 0일 이하까지 조건을 세워 두셨습니다. E-4 2번의 에러 코드 체계표는 그 표를 HTTP로 번역하는 일입니다. 둘째, 실패 분기를 이미 셋으로 나눠 두셨습니다. PG 취소 결과를 SUCCEEDED와 REJECTED와 TIMED_OUT으로 모델링하셨는데, 이 셋을 4xx와 5xx 중 어디에 놓을지가 E-4 2번의 진짜 질문입니다. 특히 TIMED_OUT은 클라이언트가 재시도해도 되는 상태인지를 계약에 적어야 합니다. 셋째, E-4 3번의 재시도가 안전해야 하는 엔드포인트가 바로 환불 요청입니다. 1-1에서 같은 주문에 환불을 두 번 저장하면 유니크 제약이나 버전 락이 두 번째를 거부하는지 확인한다고 쓰셨는데, 그때는 DB 안에서 막는 데까지 가셨습니다. Idempotency-Key는 그 방어선을 요청 경계 밖으로 올리는 일이고, 1-3에서 결제 원장과 보정 대기 상태와 멱등 키가 생기는 시점에는이라고 미뤄 두신 그 시점이 지금입니다.

## 답안

### 1. 기획서 비평

#### 간단 기획: 테니스 코트 검색 및 빈자리 알림 서비스
```
테니스 코트 정보와 예약 경로를 한 곳에서 찾고, 원하는 시간에 빈자리가 생기면 알림을 받는 서비스다. 여러 예약 사이트를 반복해서 확인하는 부담을 줄이는 것이 목적이다.

사용자는 원하는 날짜로 코트를 검색하고 예약 가능 여부를 확인한다. 조회 결과를 갱신해 예약 상태를 다시 확인하고, 원하는 자리가 있으면 해당 예약 사이트로 이동해 직접 예약한다.

원하는 자리가 없으면 코트·날짜·시간대를 지정해 빈자리 알림을 신청한다. 서비스는 해당 조건의 예약 상태를 주기적으로 확인하고, 빈자리를 발견하면 코트 정보와 예약 링크를 담은 알림을 보낸다. 사용자는 자신이 등록한 빈자리 알림 조건을 확인하거나 알림을 해제할 수 있다.

서비스는 검색과 빈자리 알림, 예약 화면 연결까지 제공한다. 실제 예약은 사용자가 외부 예약 사이트에서 진행하며, 이 서비스에서는 개인의 예약 내역을 조회하거나 예약을 취소할 수 없다. 알림이 예약 성공을 보장하지는 않는다.
```

#### 컨셉 부재 비평

현재 기획에는 반복 확인 부담을 줄인다는 목적이 있다. 다만 고객이 궁극적으로 원하는 결과와 서비스가 만들어 주려는 경험은 더 명확히 할 필요가 있다. 이를 확인하기 위해 다음 두 가지를 묻는다.

**1. 고객이 진정으로 원하는 것은 무엇인가?**

> 고객이 원하는 것은 ‘특정 코트의 빈자리를 기다리는 것’인가, ‘원하는 시간에 테니스를 칠 수 있는 곳을 찾는 것’인가?

**고객이 특정 코트를 기다리는 이유를 확인하기 위한 질문이다.** 원하는 시간에 테니스를 치는 것이 목적이라면, 특정 코트의 취소를 기다리는 것은 여러 방법 중 하나다. 예를 들어 A코트가 모두 예약되어 있어도, 근처 B코트에 같은 시간대의 빈자리가 있다면 B코트를 선택할 수 있다. 이 경우 서비스는 고객이 원하는 시간에 이용할 수 있는 다른 코트도 찾아 선택할 수 있도록 돕는 방향으로 기획할 수 있다.

**2. 이 서비스에서 고객에게 정말 주고 싶은 효용은 무엇인가?**

> ‘**대신 지켜봐 줄게요**’는 빈자리가 날 때까지 계속 확인해야 하는 귀찮음을 없애 주는 것인가, 테니스를 칠 수 있게 예약까지 잡아 주는 것인가?

**서비스가 어디까지 해 줄지 정하기 위한 질문이다.** 귀찮음을 없애 주는 것이라면 빈자리가 났다고 알려 주는 데서 서비스의 역할이 끝나고, 예약은 고객이 직접 한다. 예약을 잡아 주는 것이라면 알림을 받고도 예약하지 못한 경우까지 서비스가 책임져야 한다. 지금 기획은 알림이 예약 성공을 보장하지 않는다고 적어 두어 앞쪽에 가깝지만, 고객이 기대하는 것이 뒤쪽이라면 이 슬로건과 서비스가 고객에게 효용이 있을지를 고민해봐야한다.

#### NFR 부재 비평

현재 기획에는 얼마나 많은 요청을 처리할지, 예약처를 얼마나 자주 확인할지, 빈자리를 얼마나 빨리 알릴지가 없다. 서비스를 열기 전이라 실제 사용자 데이터가 없으므로, 아래 수치는 오픈채팅방 인원이나 예약 오픈 시각처럼 지금 확인할 수 있는 사실을 근거로 정했다. 

**1. 목표 처리량(초당 요청 건수, TPS)이 없다.**

처리할 요청 규모를 모르면 서버 사양과 대수를 정할 근거가 없다. 게다가 갱신 요청은 외부 예약처 조회로 이어질 수 있어, 요청량은 우리 서버만이 아니라 예약처에도 부하가 된다.

기준값은 초기 유입 경로에서 역산한다. 방 전체 인원에게 가입률을 바로 곱하지 않고, `방 인원 → 서비스 방문자 → 가입자`로 나누어 계산한다. 내가 가입해 있는 코트를 구하는 사람 1,000명이 모인 오픈채팅방에서 방 인원의 **5%인 50명**이 홍보 링크를 방문하고, 방문자의 최대 **20%가 가입**한다고 가정하면 초기 가입자는 **10명**이다. 5% 방문률과 20% 가입률은 카카오 오픈채팅의 확정된 평균이 아니라 초기 용량을 계산하기 위한 가정이다. 커뮤니티 광고 자료에서도 관리자 게시물의 링크 클릭률을 2~6% 범위로 제시하지만, 카카오 오픈채팅에 직접 적용할 수 있는 공식 통계는 아니므로 출시 후 실제 방문·가입 데이터를 측정해 갱신한다. [참고: Torchly 커뮤니티 광고 benchmark](https://torchlyhq.com/community-advertising-benchmarks)

요청은 예약처가 예약을 여는 시각에 몰린다. 서울시 공공서비스예약의 테니스장은 매달 정해진 날 오전 10시처럼 시설마다 여는 시각을 공지하고, 인기 있는 자리는 이때 마감되므로 가입자 일부가 같은 시각에 들어와 새로고침한다. 초기 부하 시나리오는 이 가입자 10명 중 **최대 10명이 동시에** 1초에 한 번씩 갱신하는 **초당 10건**으로 잡는다. 이는 가입자 수에서 자동으로 도출되는 평균 부하가 아니라, 예약 오픈 시각의 피크를 확인하기 위한 상한 가정이다. 

**2. 외부 예약처를 얼마나 자주 확인할지 정하지 않았다.**

이 서비스의 정보는 전부 외부 예약처에서 가져오므로, 자주 확인할수록 정보는 최신이지만 조회량이 늘고 예약처가 우리 요청을 막을 수 있다. 막히면 검색과 알림이 함께 멈추므로, 확인 주기가 없으면 예약처에 보내는 조회량이 안전한지 판단할 수 없다. 조회는 기본적으로 사람이 아닌 코트·날짜 단위로 묶어 한 번만 가져오고, 그러면 이용자가 늘어도 조회량은 확인 주기 하나로 제한된다.

초기값은 **20초**로 둔다. 예약처가 허용하는 조회량은 공개돼 있지 않으니 차단당하지 않을 만큼 보수적으로 시작하고, 조회가 막히면 주기를 늘리고 20초 사이에 났다 사라지는 불일치가 많다면 시간을 줄인다.

**3. 빈자리를 발견하고 알림이 도착하기까지의 시간 목표가 없다.**

예약은 선착순이라 빈자리 알림은 다른 사람보다 먼저 받을수록 유리하고, 늦게 받은 알림은 받아도 쓸모가 없다. 그래서 목표는 **발견 후 3초 안에 도착**으로 둔다. 발송 대기에서 1초마다 꺼내면 대기 시간은 1초 안이고, 나머지는 푸시 서비스가 기기에 전달하는 시간이다. 다만 빈자리가 난 뒤 우리가 발견하기까지는 확인 주기(20초)만큼 더 늦을 수 있어, 알림을 더 빨리 받게 하려면 발송보다 확인 주기를 줄이는 편이 효과가 크다. 서비스를 연 뒤에는 알림을 받고 예약 화면에 들어갔을 때 이미 자리가 나가 있던 비율을 재서, 이 비율이 높으면 확인 주기부터 줄인다. 새벽에 난 빈자리는 사용자가 알림을 신청할 때 새벽에도 받을지 고르게 한다. 특정 코트를 기다리는 사람은 새벽 알림이라도 원하겠지만, 그렇지 않은 사람에게는 방해가 되기 때문이다.

#### 엣지 케이스 부재 비평

이 서비스는 자기 데이터를 갖고 있지 않다. 코트의 예약 상태는 전부 남의 예약처에 있고, 우리는 갱신 요청이 들어올 때 20초에 한 번씩 가져와 알림으로 내보낸다. 그래서 실패는 잘못된 입력에서 오지 않고, 이 경로가 끊기거나 한꺼번에 몰리는 자리에서 온다.

| 상황                      | 계약                                                                                                                                                   |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| **예약 상태를 가져오지 못함**      | ‘빈자리 없음’이 아니라 일시적인 확인 실패로 표시하고, 마지막 확인 시각과 함께 잠시 후 다시 확인해 달라고 안내한다. 응답은 오지만 내용을 읽지 못하는 경우도 확인 실패로 본다. 알림 신청자에게 따로 연락하지 않고, 앱의 신청 목록에 ‘확인 지연’으로 보여준다. |

| 상황                   | 계약                                                                                                  |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| **발송이 실패하거나 결과를 모름** | 최대 3번까지 다시 보낸다. 결과를 모르는 경우도 다시 보내, 누락 대신 중복을 감수한다. 3번 모두 실패하면 DLQ로 옮겨 사용자에게 다시 보내지 않고 원인 확인에만 쓴다.   |
| **발송이 밀려 정보가 오래됨**   | 같은 자리에 더 최신 조회 결과가 나오면 그 전 결과로 만든 알림은 낡은 것으로 보고 보내지 않는다. 기준은 조회 주기(20초)이며, 발송 직전에 예약처를 다시 조회하지 않는다. |
| **같은 자리를 반복해서 발견**   | 알림은 한 건만 보낸다. 이후의 상태 변화는 알림으로 보내지 않고, 앱과 웹에서 최신 정보로 보여준다.                                           |
