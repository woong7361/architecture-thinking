# Task E-5: AI 파이프라인 (API Contract 검증) + 명세를 판정 기준으로

(Grit's Why): 이것이 이번 Station의 진짜 산출물입니다. Phase 1의 Gen/Eval 하네스를 API 도메인으로 확장해, AI가 짠 구현이 계약을 지키는지 본인이 판정합니다.

> 현웅님 메모: E-5는 1-3에서 겪으신 일의 정면입니다
>
> 1-3 C-6에서 L1 1차 산출물이 게이트 4단을 전부 통과했고 인수테스트 21개가 초록불이었는데 틀렸습니다. 원인을 이렇게 적으셨습니다. 엔드포인트와 승인 판정 기준이 없었기 때문에 생성기는 그 빈자리를 /payments 와 2xx 승인이라는 가정으로 채웠다. 입력 누락은 오답을 만들었고, 게이트 공백은 그 오답에 GREEN을 줬다. 모의면접에서는 계약이 비어있는 부분이 있다는 것을 확인하였고 그 계약의 시작은 제가 주어준 기획문서가 잘못되었기 때문이라고 정리하셨습니다.
>
> 이번 Station의 E-3과 E-4와 E-5가 그 문장의 순서를 그대로 따라갑니다. 기획문서를 요구사항 명세로 고치고(E-3), 그 명세를 계약으로 확정하고(E-4), 그 계약을 판정 기준으로 돌립니다(E-5). 그때 비어 있던 자리가 정확히 엔드포인트와 요청 본문과 응답 본문의 approved와 거절도 HTTP 200이었으니, E-4에서 스키마를 쓰실 때 그 네 가지가 스키마 안에 다 있는지부터 확인해 주세요.
>
> 그때 현웅님은 이것은 이번 결과를 확인한 수동 스모크이지 같은 실수를 다음 실행에서 자동으로 막는 게이트는 아니라고 닫으셨습니다. 이번에는 자동 게이트까지 가 주세요. E-5 2번의 계약 테스트는 현웅님이 직접 쓰시고, AI 구현을 그 테스트의 통과와 실패로만 판정하십시오. PgChargeAdapter 가 어느 자동 판정에서도 실행되지 않았다고 진단하신 그 커버리지 공백은 이번 계약 테스트에서 함께 메워 주세요. 대역으로 빠진 경로가 하나 있으면 초록불의 뜻이 그만큼 줄어듭니다. 모의면접에서 순수한 자바쪽은 archUnit으로 대역이 아닌 테스트를 강제해야겠다고 하신 그 생각을 여기서 실행해 보셔도 좋습니다.
>
> 1번은 이식 모드로 가십시오. 현웅님은 Phase 0의 writing-harness-pipeline부터 1-1의 generate-test, 1-2의 refactor-agent, 1-3의 skeleton-agent, 1-4의 blog-draft와 speech-rehearsal까지 여섯 개를 이미 굴려 보셨습니다. 이식하는 방법도 1-2에서 직접 정리해 두셨습니다. 루프 제어 구조, 스키마 검증과 역할경계 금지필드, 금지패턴 가드와 refine 배관, 루브릭 로더, 파일 매니페스트 승격, 정보 차단, LLM 클라이언트를 그대로 가져오시면 됩니다. 새로 만드실 것은 Validate 자리 하나입니다. 1-2의 behavior_gate.py는 worktree에서 행위 보존을 판정했고 1-3의 게이트는 경로 규약과 컴파일과 경계 규칙과 인수테스트를 봤는데, 이번 판정 대상은 계약의 호환성입니다. 무엇을 Breaking으로 볼지(필수 필드 추가, 응답 필드 삭제, 에러 코드 제거, 타입 축소)를 먼저 정하시고 게이트를 만드십시오.
>
> 루브릭은 1-1의 방식을 이으시되 축을 갈아 주세요. 1-1에서 behavioral_altitude 축으로 gherkin에 enum과 UTC 같은 기술 용어가 새어 나온 것을 잡아내셨듯이, 이번에는 계약 적합성 축(누락 필드, 타입 불일치, 빠진 에러 코드)이 그 자리에 옵니다. 다만 1-4에서 직접 관찰하신 것도 같이 기억해 주세요. 근거 없는 문장이 네 건 있는 초안이 4.8점을 받고 그런 문장이 없는 초안이 4.5점을 받은 역전이 있었습니다. 계약 적합성은 점수로 재는 것보다 결정적 대조 검사로 판정하시는 편이 안전하고, 그 방법은 이미 1-4에서 현웅님이 쓰신 것입니다. AI의 자기 평가와 계약 테스트 결과가 어긋난 지점을 적으실 때는 1-4에서 세우신 기준을 그대로 쓰시면 됩니다. AI는 후보를 넓히는 데까지, 채택과 서열은 내가 한다.

### 수행 내용

1. Phase 1 하네스를 재사용해 API Contract 검증 파이프라인으로 확장하세요. 명세(스키마)를 입력하면 구현 초안을 뽑고(Gen), 새 세션에 시니어 리뷰어 역할을 주고 계약 위반(누락 필드, 타입 불일치, 빠진 에러 코드)을 지적하게 하고(Critique), 계약 적합성을 루브릭으로 평가하고(Eval), 스키마 diff와 Breaking Change를 탐지해 미달 시 REJECT합니다(Validate). 어디를 재사용했고 무엇을 새로 만들었는지 적어 주세요.
2. 명세 먼저, 구현은 나중. 이번 Station의 핵심 의식입니다.
   - E-4에서 만든 API 계약을 먼저 확정하고, 그 계약에서 계약 테스트(또는 인수테스트) 몇 개를 본인이 직접 쓰세요.
   - 그다음 구현을 AI에게 맡기세요.
   - AI가 만든 구현을 본인이 쓴 계약 테스트로만 판정하세요. AI에게 스펙대로 짰어라고 묻지 말고, 계약 테스트의 통과와 실패로 판정합니다. 테스트는 실패라는데 AI는 맞다고 한 지점이 있으면 그 지점을 적어 주세요.
