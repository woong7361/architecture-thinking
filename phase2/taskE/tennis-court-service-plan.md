# 빈자리 알림 기능 요구사항 명세서

관련 과제: [Task E-3 — 제출물 2](https://github.com/woong7361/architecture-thinking/blob/main/phase2/taskE/assignments/taskE-3.md)

## 목적과 범위

사용자가 지정한 코트·날짜·시간대에 빈자리가 생기면 알려, 외부 예약 사이트에서 예약을 시도할 수 있게 한다. 범위는 알림 신청과 조회와 해제, 예약 상태 확인, 알림 발송, 만료까지다. 실제 예약과 취소는 외부 사이트에서 이뤄지고, 이 서비스는 고객이 예약을 마쳤는지 알지 못한다.

이 명세의 수치는 전부 초기값이다. 서비스가 아직 공개되지 않아 실제 수요도 외부 예약처의 허용 조회량도 측정된 적이 없으므로, 각 값이 어디서 나왔는지와 무엇을 보고 고칠지를 함께 적는다.

전제는 셋이다. 사용자를 구분하고 알림을 보낼 경로가 확보되어 있다고 본다. 신청 단위는 예약처가 제공하는 코트 하나, 날짜 하나, 시간대 하나다. 만료 시각은 이용 시작 시각으로 두되, 더 이른 예약 마감 시각이 확인되면 그 시각을 쓴다.

## 기능 요구사항

| 번호 | 기능 | 요구사항 |
|---|---|---|
| FR-1 | 알림 신청 | 지원하는 코트·시간대이고 만료 전이면 신청을 저장하고, 신청 식별자와 조건과 만료 시각과 감시 중 상태를 돌려준다. 같은 사용자의 같은 조건에 감시 중인 신청이 있으면 기존 신청을 돌려준다. 응답을 받지 못해 재시도해도 감시 중인 신청은 하나만 남는다. |
| FR-2 | 신청 조회와 해제 | 사용자는 자신의 신청 조건과 상태, 마지막으로 확인에 성공한 시각, 최근 확인 실패 여부, 최근 발송 결과를 볼 수 있다. 해제하면 그 시점부터 확인과 새로운 발송을 멈춘다. 다른 사용자의 신청은 조회할 수도 해제할 수도 없다. |
| FR-3 | 예약 상태 확인 | 감시 중이고 만료 전인 조건의 예약 상태를 확인한다. 확인은 사용자마다 하지 않고 코트·날짜 단위로 묶어, 마지막 확인에서 20초가 지나지 않았으면 저장해 둔 결과를 쓴다. 확인에 실패한 경우는 빈자리 없음으로 다루지 않고 마지막 성공 결과와 그 시각을 유지한다. |
| FR-4 | 알림 대상 생성 | 신청 후 첫 확인에서 빈자리이면 알림 대상을 하나 만든다. 그 뒤로는 빈자리 없음이 확인된 다음 다시 빈자리가 확인된 경우에만 새 대상을 만든다. 같은 자리가 계속 비어 있어도 대상을 늘리지 않는다. |
| FR-5 | 알림 발송 | 알림 대상은 만들어지는 즉시 발송 대기로 기록하고, 발송은 확인 작업과 분리된 작업이 맡는다. 확인과 대기 기록은 한 트랜잭션으로 저장해 발견한 빈자리가 사라지지 않게 한다. 발송 서비스가 요청을 접수하면 접수됨으로 기록하며, 이를 고객의 수신이나 예약 성공으로 표시하지 않는다. |
| FR-6 | 알림 내용 | 코트와 날짜·시간대, 빈자리를 확인한 시각, 외부 예약 링크, 예약을 보장하지 않는다는 안내를 담는다. 발송 직전에 예약 상태를 다시 확인하지 않으므로, 확인 시각을 알림에 드러내 사용자가 판단할 수 있게 한다. |
| FR-7 | 만료 | 만료 시각이 되면 확인과 새로운 발송을 멈춘다. 해제되거나 만료된 신청은 저절로 되살아나지 않는다. 종료 직전에 시작된 발송으로 알림이 뒤늦게 도착할 수 있음을 안내한다. |

FR-4의 기준은 확인 실패를 상태 변화로 보지 않는다는 뜻이다. 빈자리 있음 다음에 확인 실패가 오고 다시 빈자리 있음이 확인됐다면 같은 자리로 다룬다. 확인하지 못한 사이에 예약됐다가 취소된 경우까지는 알 수 없다.

## 정상 흐름

1. 사용자가 A코트 토요일 10~11시 알림을 신청하고, 서비스는 감시 중 상태와 만료 시각을 돌려준다.
2. 확인 작업이 그 코트·날짜의 예약 상태를 20초 간격으로 확인한다. 같은 코트·날짜를 감시하는 다른 신청이 있어도 외부 조회는 한 번이다.
3. 빈자리가 확인되면 알림 대상을 만들고, 같은 트랜잭션에서 발송 대기로 기록한다.
4. 발송 작업이 대기를 꺼내 알림을 보내고, 접수 결과를 기록한다. 사용자는 링크로 이동해 직접 예약한다.
5. 같은 자리가 계속 비어 있어도 다시 알리지 않는다. 사용자가 해제하거나 만료될 때까지 확인을 이어간다.

## 비기능 요구사항

| 번호 | 기준 | 초기값 | 근거와 조정 |
|---|---|---|---|
| NFR-1 | 처리 규모 | 가입자 200명, 감시 중인 신청 500건. 예약이 열리는 시각에 200명이 모두 접속해 1초에 한 번씩 갱신하는 초당 200건을 기준으로 서버를 구성한다. | 홍보 경로인 오픈채팅방 1000명에 가입 전환 20%를 적용했다. 공개 직후 실제 가입자 수를 가장 먼저 확인하고, 200명을 넘으면 피크도 비례해 늘어나므로 미리 증설 기준을 정해 둔다. |
| NFR-2 | 검색·갱신 응답시간 | 위 피크에서 95%를 1초 이내에 응답한다. 요청을 받은 때부터 응답을 완료할 때까지 잰다. | 응답이 갱신 간격보다 길면 다음 요청이 앞 요청을 기다리며 쌓인다. 갱신 간격 1초는 가정이므로 실제 간격을 측정해 함께 조정한다. 대부분의 요청은 저장해 둔 결과로 답하니 실제 응답은 이보다 짧다. |
| NFR-3 | 예약 상태 확인 간격 | 코트·날짜마다 20초. 같은 코트·날짜를 여러 사용자가 보거나 여러 신청이 감시해도 외부 조회는 한 번이다. | 자주 확인할수록 최신이지만 예약처가 우리 요청을 막을 수 있고, 막히면 검색과 알림이 함께 멈춘다. 허용량이 공개돼 있지 않아 보수적인 값에서 시작한다. 조회가 막히거나 오류가 늘면 늘리고, 20초 사이에 났다 사라지는 자리를 자주 놓치면 줄인다. |
| NFR-4 | 알림 발송 시점 | 빈자리를 발견하면 모으지 않고 즉시 보낸다. 발견한 작업이 직접 보내지 않고 대기 기록을 거친다. | 빈자리는 금방 사라지므로 모아 보내면 그사이 나간다. 발견 작업이 발송까지 맡으면 발송 서비스가 느린 동안 NFR-3의 20초가 밀리므로 두 작업을 나눈다. 한 사람이 짧은 시간에 몇 건을 받는지 측정해 묶음 발송이 필요한지 다시 판단한다. |
| NFR-5 | 알림 유효기간 | 빈자리를 확인한 시점부터 20초. 넘긴 대상은 보내지 않는다. | 20초가 지나면 다음 확인 결과가 나와 있으므로, 오래된 정보를 보내는 대신 새 결과로 다시 판단하는 편이 낫다. 확인 간격을 바꾸면 이 값도 함께 바꾼다. |

## 실패 흐름

| 상황 | 기대 동작 |
|---|---|
| 예약 상태를 가져오지 못함 | 확인 실패로 표시하고 마지막 성공 시각과 결과를 유지한다. 화면에서 확인 실패와 빈자리 없음을 구분해 보여주고, 성공한 예약처의 결과는 먼저 보여준다. 실패만으로는 알림 대상을 만들지 않는다. 조회는 되는데 응답을 읽지 못하는 상태가 이어지면 그 예약처를 지원 목록에서 빼고 운영자에게 알린다. |
| 여러 사람이 같은 때에 갱신을 누름 | 같은 코트·날짜에 대해 한 요청만 외부를 확인하고, 나머지는 그 결과를 기다린다. 확인이 1초 안에 끝나지 않으면 기다리던 요청에는 저장해 둔 직전 결과와 그 확인 시각을 준다. 확인이 실패하면 기다리던 요청도 확인 실패로 답한다. 서버가 여러 대이므로 확인 중이라는 표시는 공유 저장소에 둔다. |
| 발송이 실패하거나 결과를 모름 | 5초 뒤에 다시 보내고 추가 시도는 최대 2회다. 유효기간 20초 안에 끝나도록 시도 간격과 횟수를 맞췄다. 응답이 끊겨 접수 여부를 모르는 경우에도 재시도한다. 알림이 두 번 가는 것보다 자리를 놓치는 쪽이 이 서비스에서 더 나쁘기 때문이다. 발송 요청에는 알림 대상 식별자를 실어, 발송 수단이 중복 제거를 지원하면 그것으로 걸러지게 한다. |
| 발송이 밀려 정보가 오래됨 | 유효기간을 넘긴 대상은 보내지 않고 취소로 기록한다. 보내기 전에 예약 상태를 다시 확인하지는 않는다. 그 확인이 NFR-3의 조회량에 그대로 더해지기 때문이고, 대신 확인 시각을 알림에 표시한다. 발송 전에 빈자리 없음이 확인되면 대기 중인 대상을 취소하고, 다시 비어도 되살리지 않고 새 대상을 만든다. |
| 같은 자리를 반복해서 발견 | 빈자리 없음이 확인된 다음 다시 빈자리가 확인돼야 새 대상을 만든다. 앞선 대상이 접수됐든 실패했든 마찬가지다. |

## 검증 시나리오

- 같은 사용자가 같은 조건으로 동시에 두 번 신청해도 감시 중인 신청은 하나다.
- 빈자리 없음에서 있음으로 바뀌면 대상이 하나 생기고, 있음이 이어지는 동안은 늘지 않는다. 없음을 거쳐 다시 있음이 되면 하나가 더 생긴다.
- 빈자리 있음에서 확인 실패를 거쳐 다시 있음이 확인되면 새 대상을 만들지 않는다.
- 같은 코트·날짜에 200건의 갱신 요청을 동시에 보내도 외부 조회는 20초에 한 번이다.
- 확인한 지 20초가 지난 대상은 발송하지 않고 취소로 기록한다.
- 발송이 실패하면 5초 간격으로 최대 2회 더 시도하고, 유효기간을 넘기면 멈춘다.
- 해제하거나 만료된 뒤에는 새 발송이 시작되지 않는다. 먼저 시작된 요청의 늦은 응답이 신청을 되살리지 않는다.
- NFR-1의 피크 요청량과 감시 500건의 확인 작업을 함께 재현해 NFR-2의 응답시간을 측정한다.

## 남은 확인 사항

- **예약처가 허용하는 조회량.** NFR-3의 20초는 이 값을 모르는 상태에서 정한 보수적인 초기값이다. 지원할 예약처를 확정할 때 코트·날짜 조합 수를 세어 실제 조회량을 계산해야 한다.
- **예약처별 예약 마감 기준.** 만료 시각을 이용 시작으로 둘지 그보다 이른 마감으로 둘지가 여기서 갈린다.
- **알림 수단.** 중복 제거와 접수 결과 확인을 지원하는지에 따라 실패 흐름의 재시도 정책이 달라진다.
- **갱신 간격.** NFR-2의 1초는 가정이다. 공개 후 예약이 열리는 시각의 실제 갱신 간격을 재야 응답시간 목표가 근거를 갖는다.

이 값들을 확인하기 전에는 외부 연동을 포함한 목표 달성을 검증했다고 볼 수 없다.
