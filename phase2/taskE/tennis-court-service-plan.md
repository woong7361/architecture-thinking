# 빈자리 알림 기능 요구사항 명세서

관련 과제: [Task E-3 — 제출물 2](https://github.com/woong7361/architecture-thinking/blob/main/phase2/taskE/assignments/taskE-3.md)

## 목적과 범위

**사용자가 원하는 코트·날짜·시간대의 빈자리를 발견하면 알림을 보내, 외부 예약 사이트에서 예약을 시도할 수 있도록 돕는다.**

범위는 알림 신청, 내 신청 목록 조회, 예약 상태 감시, 알림 발송, 해제와 만료까지다. 실제 예약과 예약 취소는 외부 사이트에서 진행하며, 이 서비스는 고객의 예약 완료 여부를 확인하지 않는다.

**아래 정책과 수치는 검토용 초안 제안이다.** 기존 기획에서 확정되지 않은 동작을 구체화했으며, 검증된 운영 성능을 뜻하지 않는다. 알림 수단과 외부 서비스의 지원 범위는 마지막의 확인 사항으로 남긴다.

- 사용자를 구분하고 알림을 보낼 수신 경로가 확보되어 있다는 전제에서 작성한다. 인증 방식과 알림 수단의 선택은 별도다.
- 신청 단위는 예약처가 제공하는 **코트 하나·날짜 하나·예약 시간대 하나**다. 날짜와 시간은 코트의 현지 시각을 기준으로 표시한다.
- **만료 시각**은 이용 시작 시각으로 제안한다. 더 이른 예약 마감 시각이 확인된 경우에는 그 시각을 적용한다.
- 신청 상태는 **감시 중·해제됨·만료됨**으로 구분한다. 조회 실패와 알림 발송 결과는 신청 상태와 별도로 표시한다.

## 기능 요구사항

**신청 조건과 감시 상태를 유지하면서, 확인된 빈자리만 알림 대상으로 만든다.**

| 번호 | 기능 | 요구사항 |
|---|---|---|
| FR-1 | 알림 신청 | 지원하는 코트와 예약 시간대이며 만료 전이면 신청을 저장한다. 저장이 완료된 뒤 신청 식별자, 조건, 만료 시각, 감시 중 상태를 반환한다. |
| FR-2 | 중복 신청 | 동일 사용자의 같은 코트·날짜·시간대에 감시 중인 신청이 있으면 기존 신청을 반환한다. 동시에 요청하거나 응답을 받지 못해 재시도해도 감시 중인 신청은 하나만 유지한다. |
| FR-3 | 내 신청 조회 | 사용자는 자신의 신청 조건, 신청 상태, 마지막 성공 조회 시각, 최근 조회 실패 여부, 최근 알림 발송 결과를 확인할 수 있다. 다른 사용자의 신청은 조회하거나 해제할 수 없다. |
| FR-4 | 예약 상태 감시 | 감시 중이며 만료 전인 조건을 주기적으로 확인한다. 성공적으로 확인한 결과는 빈자리 있음과 없음으로 구분한다. 실패한 조회는 빈자리 없음으로 간주하지 않으며 마지막 성공 결과를 보존한다. 오래된 확인 결과가 최신 결과를 덮지 않도록 한다. |
| FR-5 | 알림 대상 생성 | 신청 후 첫 성공 조회에서 빈자리이면 알림 대상을 만든다. 이후에는 빈자리 없음이 확인된 뒤 다시 빈자리가 확인된 경우에 새 알림 대상을 만든다. 같은 빈자리가 계속 확인되면 대상은 추가하지 않는다. |
| FR-6 | 알림 내용과 결과 | 코트, 날짜·시간대, 빈자리 확인 시각, 외부 예약 링크와 예약 성공을 보장하지 않는다는 안내를 보낸다. 발송 서비스가 요청을 접수하면 접수됨으로 기록하며, 이를 고객의 실제 수신이나 예약 성공으로 표시하지 않는다. |
| FR-7 | 감시 유지와 재신청 | 알림 발송 후에도 감시를 유지한다. 해제되거나 만료된 신청은 자동으로 다시 활성화하지 않는다. 해제 후 같은 조건으로 재신청하면 만료 전인 경우 새 신청으로 처리한다. |
| FR-8 | 해제와 만료 | 해제가 완료되거나 만료 시각이 되면 감시와 새로운 발송 시도를 중단한다. 이미 해제된 신청을 다시 해제해도 같은 종료 상태를 반환한다. 종료 전에 시작된 발송으로 알림이 뒤늦게 도착할 수 있음을 안내한다. |

**조회 실패만으로 새로운 빈자리가 생겼다고 판단하지 않는다.** 빈자리 있음 → 조회 실패 → 빈자리 있음 순서로 확인됐다면 같은 빈자리로 취급한다. 관측하지 못한 사이에 예약됐다가 취소된 경우까지 감지할 수는 없다.

**알림을 보내는 시도와 발송 결과를 분리한다.** 각 신청에서 발견한 하나의 빈자리 발생에 대해 알림 대상을 하나만 만들고, 재시도는 같은 대상의 후속 시도로 기록한다. 같은 대상의 발송 시도를 동시에 중복해서 시작하지 않는다. 접수됨·실패·결과 미확인·발송 취소를 구분한다.

**빈자리 없음이 확인되면 이전 빈자리의 미발송 대상과 재시도 대기를 취소한다.** 이후 다시 빈자리가 확인돼도 취소한 대상을 되살리지 않고 새 대상을 만든다. 이미 시작된 발송은 회수를 보장하지 않으며 결과만 기록하고 추가 시도는 하지 않는다.

## 정상 흐름 — Happy Path

**신청한 조건에서 빈자리가 확인되면 알림을 보내고, 사용자는 외부 사이트에서 예약을 시도한다.**

1. 사용자가 아직 예약 가능한 시점인 A코트의 토요일 10~11시 알림을 신청한다.
2. 서비스는 신청을 저장하고 감시 중 상태와 만료 시각을 반환한다.
3. 첫 조회에서 빈자리가 없으면 감시를 계속한다. 이후 빈자리를 확인하면 알림 대상을 만든다.
4. 발송 직전에 신청이 감시 중인지, 알림이 아직 유효한지 확인하고 알림을 보낸다.
5. 발송 서비스의 접수를 확인하면 발송 결과를 기록한다. 사용자는 받은 링크로 이동해 직접 예약을 시도한다.
6. 같은 자리가 계속 비어 있으면 반복해서 알리지 않는다. 사용자가 해제하거나 만료 시각이 될 때까지 감시를 유지한다.

## 비기능 요구사항 — NFR

**처리 규모, 응답시간, 감시 주기, 발송 지연을 각각 측정한다.** 아래 수치는 초기 설계를 검증하기 위한 목표이며, 실제 수요와 외부 서비스의 허용량을 확인해 조정한다.

| 번호 | 기준 | 초안 목표 | 검증 방법 |
|---|---|---|---|
| NFR-1 | 처리 규모 | 동시 이용자 200명, 서로 다른 감시 조건 100개를 기준으로 한다. 사용자당 신청 5개를 가정해 감시 중인 신청 1,000개로 시험한다. 사용자 조회는 평균 초당 40건이며 1초에 200건이 몰리는 경우도 포함한다. | 감시 작업과 사용자 요청을 함께 실행한다. 빈자리 100개가 동시에 발견되고 조건별 신청자 10명에게 총 1,000건의 알림이 생기는 상황도 재현한다. |
| NFR-2 | 신청·목록·해제 응답시간 | NFR-1의 부하에서 유효한 요청의 95%를 1초 이내에 성공 응답한다. 서비스가 요청을 받은 시점부터 응답을 완료한 시점까지 측정한다. | 요청별 결과와 소요 시간을 기록한다. 오류 응답과 응답하지 못한 요청도 목표 미충족으로 집계한다. |
| NFR-3 | 정보 확인 주기 | 정상 조회가 가능한 예약처는 감시 시작 후 첫 성공 조회까지, 이후 연속된 성공 조회 사이의 간격을 각각 60초 이내로 한다. | 조건별 감시 시작 시각과 성공 조회 시각을 비교한다. 외부 조회 장애 구간과 정상 구간을 분리해 기록하며, 실제 예약처의 허용 조회량 안에서 가능한지 확인한다. |
| NFR-4 | 알림 발송 지연 | 발송 대상 생성의 근거가 된 빈자리 확인 시점부터 발송 서비스 접수까지 95%를 10초 이내로 한다. | NFR-1의 동시 발송 상황에서 측정한다. 신청과 빈자리가 유지되고 외부 발송 서비스가 정상 응답하는 조건으로 시험한다. 실패·결과 미확인·처리 지연으로 취소된 건도 목표 미충족에 포함한다. |

200명·감시 조건 100개·60초는 [초기 기획의 NFR 비평](https://github.com/woong7361/architecture-thinking/blob/main/phase2/taskE/assignments/taskE-3.md#nfr-%EB%B6%80%EC%9E%AC-%EB%B9%84%ED%8F%89)에서 제안한 초기 가정을 이어 사용한다. 신청 1,000개와 발송 10초는 이번 초안의 추가 제안이다. 발송 목표는 내부 대기 시간을 짧게 유지하려는 시작값이며, 사용하는 알림 수단을 정한 뒤 실측해야 한다. 발송 서비스 접수 이후 고객 단말까지 걸리는 시간은 별도 측정 대상이다.

## 실패·예외 흐름 — Unhappy Path

**실패하면 신청 상태와 발송 결과를 구분해 남기고, 중복 신청과 불필요한 알림을 막는다.**

**1. 신청과 감시**

| 상황 | 기대 동작과 확인 기준 |
|---|---|
| 지원하지 않는 조건 또는 이미 만료된 조건으로 신청 | 신청을 거절하고 이유를 반환한다. 신청과 감시 작업을 생성하지 않는다. |
| 신청 저장 실패 또는 응답 유실 | 저장 실패가 확인되면 성공으로 안내하지 않는다. 저장 후 응답만 유실됐다면 같은 조건의 재시도에 기존 신청을 반환하며 감시 중인 신청 수는 하나다. |
| 신청 직전에 빈자리가 생김 | 첫 성공 조회가 빈자리이면 알림 대상을 하나 만든다. 이후 같은 상태를 반복 조회해도 추가하지 않는다. |
| 예약처 조회 실패 | 해당 조건을 확인 실패로 표시하고 마지막 성공 조회 시각과 결과를 유지한다. 다른 조건의 감시는 계속하며, 실패한 조건은 다음 예정 조회에서 다시 확인한다. 실패 자체로 새 알림을 만들지 않는다. |
| 조회 결과가 뒤늦게 도착 | 동일 조건의 실제 확인 시각을 비교해 오래된 결과는 반영하지 않는다. 사용자가 화면의 조회 조건을 바꾼 경우 이전 조건의 응답으로 현재 화면을 덮지 않는다. |
| 같은 빈자리를 반복 확인 | 접수됨·실패·결과 미확인·발송 취소가 된 대상도 같은 빈자리라는 이유로 새로 생성하지 않는다. 빈자리 없음이 성공적으로 확인된 뒤 다시 빈자리가 확인돼야 새 대상이 된다. |

**2. 발송과 종료**

| 상황 | 기대 동작과 확인 기준 |
|---|---|
| 발송 대기 중 정보가 오래됨 | 빈자리 확인 후 60초가 지났거나 신청이 종료됐으면 발송을 취소한다. 그 전에 빈자리 없음이 확인되면 기존 대상은 즉시 취소하며, 다시 빈자리가 돼도 되살리지 않는다. 발송 직전 추가 외부 조회는 하지 않고 마지막 확인 시각을 알림에 표시한다. |
| 발송 서비스가 미접수를 명확히 응답 | 일시 오류라면 명확한 미접수 응답을 받은 시점부터 5초 뒤에 재시도하며, 추가 시도는 최대 2회다. 앞선 시도의 결과를 기다리는 중에는 재시도하지 않는다. 각 시도 직전에 신청 상태, 해당 빈자리의 유효 여부, 알림 유효기간을 다시 확인한다. 영구 거절 또는 시도 횟수 소진은 실패로 기록한다. |
| 발송 응답이 끊겨 접수 여부를 모름 | 접수 여부를 알 수 없는 연결 단절이 발생하거나, 시도 시작 후 10초 이내에 결과를 확인하지 못하면 결과 미확인으로 기록하고 자동 재시도하지 않는다. 중복 전송을 줄이는 대신 일부 알림이 누락될 수 있다. 뒤늦게 결과를 확인해도 기록만 갱신하고 추가 시도는 하지 않는다. |
| 해제·만료와 발송이 겹침 | 해제 완료 또는 만료 이후에는 첫 발송과 재시도를 새로 시작하지 않는다. 그 전에 시작된 요청은 결과를 기록하되 감시를 다시 활성화하지 않는다. |
| 알림을 받은 뒤 다른 사람이 예약 | 예약 가능 상태가 달라질 수 있다는 안내와 확인 시각을 제공한다. 이 서비스에서 예약 성공으로 기록하지 않으며, 해제·만료 전까지 감시는 계속한다. |
| 다른 사용자의 신청 조회·해제 시도 | 요청을 거절하고 다른 사용자의 신청 내용은 반환하지 않는다. 해당 신청 상태도 바뀌지 않는다. |

**발송 목표 10초와 알림 유효기간 60초는 서로 다른 기준이다.** 목표 시간을 넘었어도 유효기간 안이면 발송할 수 있다. 유효기간은 해당 알림을 만든 빈자리 확인 시점부터 계산하며, 이후 같은 빈자리를 다시 확인해도 기존 알림의 유효기간은 연장하지 않는다. 만료 경계인 60초부터는 발송하지 않는다.

알림 유효기간 60초는 NFR-3의 정보 확인 주기 60초를 바탕으로 발송에도 적용한 제안이다. 미접수 후 5초 대기와 추가 2회 시도는 일시 오류의 복구 기회를 주면서 반복 요청을 제한하기 위한 시작값이며, 응답 대기 제한 10초는 결과를 모르는 요청을 계속 붙잡지 않기 위한 제안이다. 알림 수단의 특성과 실측 결과에 따라 조정해야 한다.

이 초안은 매 발송 직전의 재확인보다 주기적인 조회 결과를 활용하는 안을 택했다. 외부 조회량과 발송 지연은 줄지만 실제로는 이미 예약된 자리를 알릴 수 있다. 또한 발송 결과가 불명확할 때는 중복 방지를 우선해 자동 재시도를 하지 않는다. 결과 조회나 중복 방지 기능을 제공하는 발송 수단을 선택하면 이 정책을 재검토할 수 있다. 같은 빈자리에서 실패한 대상을 계속 새로 만들지 않는 정책은 반복 발송을 제한하지만, 아직 남아 있는 예약 기회를 다시 알리지 못할 수 있다.

## 검증 시나리오와 남은 확인 사항

**정상 흐름과 예외 흐름의 결과를 재현해 명세 충족 여부를 확인한다.**

- 같은 사용자가 같은 조건으로 동시에 두 번 신청해도 감시 중인 신청은 하나다.
- 빈자리 없음 → 있음 → 있음 순서에서는 알림 대상이 하나이고, 다시 없음 → 있음이 확인되면 하나가 추가된다.
- 최초 조회가 빈자리이면 알림 대상을 하나 만든다. 빈자리 있음 → 조회 실패 → 있음은 새 대상을 만들지 않는다.
- 발송 목표 10초를 넘겨도 유효기간 전이면 발송할 수 있다. 확인 후 60초부터는 발송하지 않는다.
- 해제 완료나 만료 이후에는 새 발송 시도가 시작되지 않는다. 먼저 시작된 요청의 뒤늦은 결과는 신청을 다시 활성화하지 않는다.
- 발송 대기 중 빈자리 있음 → 없음 → 있음이 확인되면 이전 미발송 대상은 취소하고 새 대상만 발송한다.
- 명확한 일시 거절을 받은 뒤 5초가 지나야 재시도하며, 첫 시도를 포함해 최대 3회까지만 시도한다. 응답이 늦어도 기다리는 중에 중첩 재시도하지 않는다.
- 시도 시작 후 10초 이내에 결과를 확인하지 못하면 결과 미확인으로 남기고 추가 시도하지 않는다. 뒤늦은 응답도 새로운 발송을 유발하지 않는다.
- NFR 표의 부하를 함께 재현하고 응답시간·성공 조회 간격·발송 지연을 각각 기록한다.

구현 전에 확인할 사항은 **알림 수단과 수신 경로 확보 방식**, **발송 서비스의 허용량과 오류·접수 결과 구분 방법**, **예약처별 마감 정보와 실제 조회 가능 주기**다. 확인 전에는 외부 연동을 포함한 목표 달성을 검증했다고 볼 수 없다.
