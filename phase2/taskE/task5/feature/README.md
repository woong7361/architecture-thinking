# 계약 테스트 시나리오 — 무엇을 골랐고 무엇을 뺐는가

E-4에서 확정한 계약([tennis-alert-api.yaml](../../api/tennis-alert-api.yaml))을 AI 구현의 판정 기준으로 돌리기 위한 시나리오다.
하네스가 만든 후보에서 골라 단언을 조이고 근거를 붙였다. 채택과 서열은 내가 정했다.

## 판정을 세 층으로 나눈다

**필드와 타입은 스키마 검증이 판정한다.** `Alert`의 required가 12개고 `additionalProperties`가 닫혀 있어, 응답 하나를 손으로 단언하면
테스트가 필드 수만큼 길어지고 계약이 바뀔 때마다 전부 고쳐야 한다. 모든 응답을 그 오퍼레이션의 응답 스키마로 통과시키는 검증을
공통 자리에 걸면 필드 누락·타입 불일치·계약에 없는 필드가 한 곳에서 잡힌다. 그래서 형식 위반 케이스는 이 feature에 넣지 않았다.

**계약이 스키마로 적을 수 없다고 밝힌 것은 불변식 검사가 판정한다.** 계약의 `Problem` 설명이 두 조건을 그렇게 적었다.
`retryable`이 true면 `retryAfterSeconds`와 `Retry-After` 헤더가 함께 오고, `traceId`는 5xx에만 실린다.
여기에 하나를 더한다. 각 응답의 `code`는 그 오퍼레이션이 `x-error-codes`로 선언한 값이어야 한다.
`check_contract.py`는 문서끼리만 대조하므로 실제 응답에 대해서는 판정하는 것이 없다.

**분기 시나리오만 이 feature가 고정한다.** 단언은 경계에서 관찰되는 것으로만 쓴다. 상태 코드·에러 코드·헤더 이름은 여기 적지 않고
step 바인딩에서 계약을 보고 대응시킨다. feature가 무엇이 일어나는지를 고정하고, step이 그것이 HTTP로 어떻게 보이는지를 고정한다.

## 고른 것

| 파일 | 오퍼레이션 | 시나리오 | 판정하는 계약 조항 |
| --- | --- | --- | --- |
| `alert-request.feature` | `POST /alerts` | 14개(Examples 펼치면 21건) | 멱등 네 갈래, 표식 보관 경계와 사용자 격리, 동시 신청 두 갈래, 4xx 비보관, 요청 거절 다섯 가지 |
| `court-availability.feature` | `GET /courts/{courtId}/availability` | 9개(펼치면 15건) | 확인 간격 경계, 확인 실패 시 신선도와 실패의 갈림, 동시 조회, 미개방 날짜, 미지원 코트, 비인증 조회 |
| `alert-lifecycle.feature` | `GET /alerts`, `GET·DELETE /alerts/{alertId}` | 13개(펼치면 17건) | 소유권과 존재 은폐, 저장된 상태 기준 거르기, 확인 밀림 경계, 해제의 멱등과 발송 대기 폐기, 상태와 발송 결과의 동반 관계 |

고른 기준은 넷이다.

- **계약이 값이나 결말을 정한 자리만 넣는다.** 계약이 정하지 않은 것을 단언하면 게이트가 계약이 아닌 것을 판정한다.
- **한 시나리오는 하나의 조항을 판정한다.** 여러 조항이 한 시나리오에 얽히면 실패했을 때 무엇이 깨졌는지 좁혀지지 않는다.
- **경계는 안과 밖을 짝으로 둔다.** 확인 간격 ±1초, 이용 시작 시각 전후가 그렇다. 한 점만 두면 특수해 구현이 통과한다.
- **대역으로 우회되는 경로를 남기지 않는다.** 예약처 실패 세 갈래와 동시 조회는 스텁의 실제 요청으로 태운다.

계약이 결말을 둘로 열어 둔 자리는 택일을 허용하되 불변식으로 봉인했다. 같은 표식의 동시 신청에서 한쪽이 물러나는 것도,
두 요청이 같은 신청을 받는 것도 계약은 허용한다. 그래서 둘 다 통과시키되 신청이 1건이라는 단언으로 갈랐다.

## 뺀 것과 이유

- **요청 형식 위반**(날짜 형식, UUID가 아닌 표식, 본문 스키마 위반) — 스키마 검증이 판정하는 층이다.
- **저장소 실패와 내부 실패**(`STORAGE_TIMEOUT`, `CONCURRENT_UPDATE_CONFLICT`, `INTERNAL_ERROR`) — 재현하려면 저장소에 장애를 주입해야 한다.
  낙관적 락 경합은 1-3에서 번역만 해 두고 적용하지 않은 그 예외이므로, 주입 수단을 정한 뒤 2차에 넣는다.
- **알림 발송 경로**(AsyncAPI) — 이 세 파일은 HTTP 표면의 계약만 판정한다. 발송 지시와 단말 메시지, 네 번의 시도와 보관 채널은
  메시지 계약이 따로 정하므로 별도 feature로 다룬다.

시계에 기대는 경계는 미루지 않고 넣었다. 표식의 24시간 보관과 확인 밀림의 세 배 경계가 그것이다.
시계는 어차피 주입해야 하고, 장애 주입과 달리 추가 수단이 필요 없다.

`지민의 신청은 N건이다`는 목록 조회로 관찰한다. 그 오퍼레이션이 `alert-lifecycle.feature`의 판정 대상이기도 하므로,
관찰 수단과 판정 대상이 같은 자리를 쓴다. 목록 조회가 깨지면 두 파일이 함께 빨간불이 되고, 그건 의도한 것이다.

## 단언을 고친 자리

하네스 후보를 그대로 쓰지 않은 이유가 여기 있다.

- **계약보다 강한 약속을 되돌렸다.** 한 후보는 같은 표식의 동시 신청에서 두 요청 모두 같은 신청을 받는다고 단언했다.
  계약은 한쪽이 처리 중이라는 이유로 물러날 수 있다고 적었으므로, 그대로 두면 계약을 지킨 구현이 실패한다.
- **저장 상태 단언을 관찰 가능한 형태로 바꿨다.** `새 신청은 만들어지지 않는다`를 `지민의 신청은 N건이다`로 바꿔 목록으로 셀 수 있게 했다.
- **느슨한 단언을 봉인했다.** `실패 결과가 반환된다`나 `알 수 있다`처럼 무엇이 돌아오는지 정하지 않은 문장은 사유와 값으로 바꿨다.
  하네스의 루브릭도 세 번의 반복 내내 이 축만은 하한을 넘기지 못했다.
- **사용자 격리 경계를 열어 두었다.** 계약은 표식을 사용자와 오퍼레이션 단위로 보관한다고 적었는데, 후보는 사용자가 하나뿐이라
  다른 사용자가 같은 표식을 써도 서로의 응답을 받지 않는다는 경계가 없다. 2차에 넣는다.
