# [Phase 2] 2-1(API 설계) - 현웅님

## Phase 2 (설계 역량) · Station 2-1 (API 설계 & 실전 엔지니어링)

Phase 1에서 "이 코드가 맞는가"를 테스트로, "변화에 강한가"를 객체와 아키텍처로 잡았습니다. Phase 2는 "무엇을 왜 만드는가"부터 다시 시작합니다. 이번 Station은 모호한 기획을 동료가 즉시 개발할 수 있는 설계도로 바꾸고, 그 설계를 깨지지 않는 API 계약으로 못 박습니다.

# 왜 지금 이 과제를 드리는가

기능을 나열하는 사람은 코더에 머무릅니다. 무엇을 왜 만드는지(컨셉)를 설계하고, 그 컨셉을 판단 기준으로 삼아 기술 결정을 내리는 사람이 프로덕트 엔지니어(PE)입니다. 컨셉이 없으면 모든 의사결정이 일반적인 합리성(그냥 다들 쓰니까)이나 비용(제일 싼 거)으로만 귀결되고, 이력서는 채워도 고객 문제는 못 푸는 짝짝이 시스템이 남습니다.

이건 취향이 아니라 시장의 요구입니다. 서비스 기업 공고는 기획 의도를 이해하고 요구사항을 구체화하는 능력, API 설계 및 운영 경험을 자격이나 우대로 적습니다. 모호함을 명확함으로 바꾸고 계약으로 못 박는 일이 백엔드 엔지니어의 출발선이라는 뜻입니다.

AI가 코드를 빠르게 쏟아내는 시대에 이 토대는 오히려 더 중요해집니다. 컨셉이 분명해야 무엇을 만들지 흔들리지 않고, 명확한 API 계약(스키마 + 에러 체계 + 멱등성)이 있어야 AI가 짠 구현이 계약을 지키는지 사람의 눈이 아니라 계약 테스트로 즉시 판정할 수 있습니다. 여기서 1-1의 인수테스트가 API 계약 검증으로 이어집니다.

> 핵심 원칙(리마인드): 이번 Station의 진짜 산출물은 API 명세서 한 장이 아니라, 컨셉에서 출발해 요구사항과 엣지케이스를 명세로 못 박고, 그 명세를 AI 구현의 판정 기준으로 돌린 기록입니다.

# 언어와 스택

- Phase 1과 같은 구성을 그대로 잇습니다. Java(1-1과 1-2를 corretto-17로 돌리셨으니 JDK 17 그대로 두셔도 됩니다), Spring Boot(web, jpa, actuator), Maven(./mvnw), MySQL과 JPA입니다. 판정 장치는 1-3에서 세우신 Cucumber와 Testcontainers와 ArchUnit을 그대로 쓰시면 됩니다.
- API 명세는 스키마 우선으로 작성합니다 (OpenAPI 또는 Protobuf 중 선택). 왜 그것을 골랐는지도 한번 생각해 보세요.
- 현웅님은 회사에서 결제 도메인을 맡고 계시고 Apple 인앱 구독 서버 검증과 PortOne 연동을 다뤄 보셨습니다. 지금까지는 남이 쓴 계약을 읽고 거기에 맞추는 자리에 계셨고, 이번 Station은 그 계약을 직접 쓰는 자리로 옮깁니다. 회사에서 외부 결제 계약에 기능을 붙이실 때 무엇을 먼저 확인하셨는지, 그 순서와 여기서 스키마를 먼저 확정하는 순서가 어떻게 다른지 한 줄 적어 주세요.

> 현웅님 메모: 이번 계약이 붙는 자리
>
> 이번 계약은 1-3 헥사고날의 인바운드 쪽에 붙습니다. C-6에서 POST /api/reservations 요청이 ReservationController를 지나 ReserveTicketUseCase로 들어가게 만드셨는데, 그 사이를 지금까지는 자바 시그니처로만 표현하셨습니다. E-4에서 하실 일은 그 시그니처를 기계가 읽는 스키마로 올려서, 인바운드 어댑터가 무엇을 받고 무엇을 돌려줄지 코드 밖에서 확정하는 것입니다.
>
> 에러 체계도 출발점이 이미 있습니다. 1-3에서 ProblemDetail과 problem+json을 쓰셨고 결제 거절을 402로, 이미 예약된 티켓을 409로 매핑하셨습니다. E-4 2번은 그 매핑을 비즈니스 에러와 시스템 에러로 갈라 넓히는 작업입니다.
>
> 스키마 우선 도구는 OpenAPI와 Protobuf 중에 고르시면 됩니다. 지금까지 현웅님의 계약은 Gherkin Feature와 자바 인터페이스로만 표현돼 있고 스키마 파일은 한 건도 없습니다. 1-3에서 WireMock 스텁 매핑 파일을 계약의 원천으로 삼아 직접 열어 보신 적이 있으니, OpenAPI를 고르시면 그 스텁을 스키마에서 파생시키는 데까지 이어 보실 수 있습니다.
>
> 하나 더 있습니다. 1-2에서 DIP는 의존의 방향을 다루고 ISP는 그 추상의 너비를 다룬다고 정리하시면서 PaymentApi를 ChargePort와 RefundPort와 HistoryPort로 자르셨습니다. 자바 인터페이스에 적용하신 그 기준을 HTTP 엔드포인트에도 그대로 적용할 수 있는지, 적용하기 어렵다면 무엇이 다른지 한 줄 적어 주세요.

# 제출 방식과 기한

- 문서, 명세, 다이어그램은 Notion에, 코드와 명세 파일(OpenAPI/Proto)은 본인 GitHub 레포에 정리해 주세요.
- 강제 마감은 없습니다. 본인 페이스로 평균 1.5주를 권장합니다.
- Phase 1에서 열어 두신 항목 중 셋이 이번 Station과 같은 자리에 있습니다. 따로 시간을 내지 마시고 E-4와 E-5 안에서 함께 닫아 주세요. (1) 1-3의 결제 어댑터 실경로 자동 게이트입니다. 수동 스모크에서 멈춘다고 직접 적으셨고, E-5의 계약 테스트에 이 경로를 포함시키시면 그때 열어 두신 구멍이 함께 메워집니다. (2) 1-3의 OptimisticLockingFailureException 번역입니다. 개선 코드까지 써 두시고 적용은 하지 않으셨는데, E-4 2번에서 비즈니스 에러와 시스템 에러를 가르실 때 첫 사례가 됩니다. (3) 1-1의 이중 환불 방지 통합테스트입니다. 전략은 쓰시고 실행 로그는 남기지 않으셨는데, E-4 3번의 멱등성 설계와 대상이 같으므로 Testcontainers로 한 번 돌리시면 두 항목이 한 번에 닫힙니다.
