## 답안

### 제출물 1. 좀비락 발생 메커니즘과 TTL · Lease Time

#### 좀비락

소유자가 죽어도 락은 죽지 않는다. 좀비락은 해제 코드를 빼먹어서 생기는 버그가 아니라, 락 상태를 프로세스 밖에 두면 생기는 일이다. 락에 필요한 세 가지가 저장소와 인스턴스로 갈라지기 때문이다. 락 상태는 외부 저장소에 있고, 누가 그 락을 쥐고 있는지는 인스턴스의 메모리에만 있고, 그 락을 지우는 명령도 그 인스턴스만 보낸다.

저장소는 락 상태만 들고 있다. 누가 걸었는지도, 그 프로세스가 살아 있는지도 추적하지 않는다. 락을 만든 연결과 묶지도 않아서 연결이 끊어져도 그대로 둔다. 자바 프로세스 하나 안에서만 쓰는 `synchronized`는 앞의 세 가지가 모두 같은 프로세스 메모리에 있다. 그래서 프로세스가 죽으면 락도 함께 사라진다. 밖에 둔 락만 혼자 남는다.

그래서 락은 소유자가 스스로 지울 때만 풀린다. 그런데 그 소유자는 죽음과 멈춤과 끊김에 그대로 노출돼 있다. 소유자가 그 명령을 보내지 못하면 락은 그대로 남는다.

#### 좀비락의 세 경우

죽음과 멈춤과 끊김, 셋 다 락이 남는 것으로 끝나지만 남는 시간이 다르다. 그사이에 임계 구역에 아무도 못 들어가거나, 둘이 동시에 들어간다. 아래 타임라인은 알림 신청 락 하나를 두고 각 경우를 따라간다. 이 락은 한 사용자가 같은 코트·시간대에 알림 신청을 두 번 만들지 못하게 막는다. 저장소 명령은 동작으로만 적었다. 어느 저장소를 쓰든 같은 일이 벌어지기 때문이다.

##### 죽음

프로세스가 아예 사라지는 경우다.

```
t=0.0  인스턴스 A: 락 저장 시도(없을 때만) → 성공. 락 획득
t=0.1  A: 알림 신청 중복 검사와 INSERT 시작
t=0.3  A: OOMKill. 또는 kill -9, 컨테이너 강제 종료, 호스트 전원 차단
       → JVM 소멸. finally 블록도 셧다운 훅도 실행되지 않음
t=0.3  저장소: 락 그대로 존재. A의 죽음을 알 방법이 없음
t=1.0  인스턴스 B: 락 저장 시도 → 이미 있음. 실패
t=2.0  인스턴스 C: 락 저장 시도 → 이미 있음. 실패
 ...   운영자가 직접 지울 때까지 계속 실패
```

`finally { unlock() }`은 이 경우를 막지 못한다. `finally`는 프로세스가 살아 있을 때만 실행되므로, 강제 종료와 전원 차단에서는 건너뛴다. 그래서 해당 코트·시간대의 알림 신청이 영구히 막힌다. 되던 일이 아예 안 되는 가용성 사고다. 증상이 분명해서 비교적 빨리 발견된다.

##### 멈춤

프로세스는 살아 있는데 실행만 멈추는 경우다. 애플리케이션 스레드를 전부 세워 두는 Stop-the-world GC가 대표적이고, 세 경우 중 가장 위험하다.

```
t=0.0   A: 락 획득. TTL 10초
t=0.5   A: 작업 시작
t=1.0   A: Stop-the-world GC 시작. 애플리케이션 스레드 전부 정지
        → A는 죽지 않았다. 실행만 멈췄고, 멈춘 줄도 모른다
t=10.0  저장소: TTL 만료. 락 삭제
t=10.1  B: 락 저장 시도 → 성공. B가 락 획득하고 작업 시작
t=12.0  A: GC 종료. 깨어남
        → 여전히 "나는 락을 쥐고 있다"고 믿는다
t=12.1  A: INSERT 실행     ← B와 동시 실행. 상호배제 위반. 중복 신청 생성
t=12.5  A: finally → 락 삭제 ← B의 락을 지운다
t=12.6  C: 락 저장 시도 → 성공. 세 번째 인스턴스까지 진입
```

`t=10.1`에서 B의 획득은 막히지 않는다. Redis는 만료 시각이 지난 키를 접근 시점에 지우고 처음부터 없었던 것처럼 다룬다. 아직 지우지 않았어도 다음 저장 시도에는 없는 키로 응답하므로 B는 성공한다.

여기서 세 가지가 함께 벌어진다.

첫째, 고장 나는 방식이 바뀐다. 죽음은 "아무도 못 들어간다"는 가용성 사고지만, 멈춤은 "두 명이 들어갔다"는 정확성 사고다. 데이터가 조용히 깨지고 로그에는 두 요청 모두 성공으로 남는다.

둘째, A는 쓰기를 하기 전에 소유권을 잃었다는 사실을 알 수 없다. TTL 만료는 저장소 안에서 혼자 일어난다. Redis에 키 만료 알림이 있긴 하지만, 그 알림을 보내는 발행·구독(Pub/Sub)은 지금 연결된 구독자에게 한 번 보내고 끝이라 전달을 보장하지 않는다. 알림이 소켓까지 도착해도 그것을 읽을 스레드가 GC에 함께 멈춰 있다. 깨어난 뒤 그 스레드가 쓰기보다 먼저 실행된다는 보장도 없다. 깨어난 뒤 `isLocked()` 같은 확인을 넣어도, 확인과 실제 쓰기 사이에 또 멈추면 그동안 만료될 수 있다.

셋째, 깨어난 A의 해제가 B의 락을 지운다. 소유자를 확인하지 않는 해제는 락이 있는지만 보고 지운다. 그래서 A가 한 번 멈추면 B의 상호배제까지 깨진다.

원인은 GC만이 아니다. 페이지 폴트로 디스크에서 메모리를 읽는 동안의 정지, CPU 스케줄러 경쟁, `SIGSTOP`, 네트워크 스토리지의 동기 I/O 지연이 같은 효과를 낸다. VM이나 컨테이너를 일시 정지하거나 다른 호스트로 옮기는 동안에도 같다.

그리고 이 사고는 실제로 났다. 『Designing Data-Intensive Applications』의 저자 Martin Kleppmann은 분산 데이터베이스 HBase의 사례를 든다. 긴 GC로 멈춘 노드가 분산 코디네이터 ZooKeeper와의 세션을 잃었다. 다른 노드가 그 데이터 구역을 넘겨받았는데, 멈췄던 노드가 깨어나 계속 저장소에 썼다. 위 타임라인의 TTL 자리에 세션 만료가 들어가면 같은 일이 된다.

##### 끊김

프로세스와 저장소 사이의 통신이 끊기는 경우다. 어느 방향이 끊기느냐에 따라 두 가지로 갈리고, 둘 다 락이 남는다.

**해제 명령이 못 가는 경우**

```
t=0.0   A: 락 획득. 작업 시작
t=1.0   A와 저장소 사이 단절. A는 계속 작업 중
t=3.0   A: 작업 완료 → 락 삭제 요청 → 타임아웃. 실패
        → 저장소의 락은 남고, A는 더 이상 손쓸 수 없다
t=3.0~  B, C: 획득 실패. TTL이 없으면 영구 좀비락
```

**획득 응답이 유실되는 경우**

```
t=0.0   A: 락 저장 시도 전송(TTL 10초)
t=0.1   저장소: 락 생성 성공. 응답 전송
t=0.2   응답 유실 → A는 타임아웃을 받고 "획득 실패"로 판단
t=0.3   A: 포기하거나 재시도. 어느 쪽이든 그 락을 지우지 않는다
        → 아무도 소유하지 않은 락이 남는다
t~10.0  B, C: 그때까지 전부 획득 실패
```

앞의 경우는 소유자가 살아 있어도 손쓸 수 없으니 결과가 죽음과 같다. 뒤의 경우는 소유자가 아예 없는 락을 만든다. 소유자가 없으니 자발적 해제도 일어날 수 없고, 재시도 로직을 아무리 정교하게 만들어도 이 상태는 풀리지 않는다. 시간으로 푸는 길밖에 없다.

#### 바깥에서는 죽음과 멈춤과 끊김을 구별할 수 없다

저장소가 가진 정보는 "A에게서 연락이 없다" 하나뿐이다. A가 죽었는지, GC로 멈췄는지, 선이 끊겼는지, 그냥 느린지 판정할 방법이 없다. 구현을 고쳐서 될 일이 아니라, 분산 시스템에서 원리적으로 구별되지 않는다.

#### 해결책 TTL과 Lease Time

소유자가 살아 있는지 알 수 없으니, 소유자만 해제하는 방식을 버려야 한다. 시간이 지나면 저장소가 스스로 락을 지우게 만들면 된다. TTL과 Lease Time이 그 방식이다.

##### TTL

TTL은 소유자 말고 저장소도 락을 지우게 만든다. 락을 저장할 때 만료 시각을 함께 걸면, 소유자가 사라져도 시간이 되면 저장소가 지운다.

```
SET lock:alert:court7:2026-09-04:10 <랜덤토큰> NX PX 3000
```

`NX`는 키가 없을 때만 쓰고, `PX 3000`은 3초 뒤 자동 삭제다. 이 한 줄이 해제 조건을 두 개로 늘린다. 소유자가 지우거나, 시간이 지나면 풀린다.

TTL은 Redis 문서가 드는 분산 락 세 요건 중 하나만 채운다. 상호배제, 교착 없음, 장애 내성 가운데 교착 없음이다. 락을 쥔 클라이언트가 죽거나 끊겨도 다른 쪽이 결국 다시 락을 잡는다는 뜻이다. 죽음과 끊김이 만드는 좀비락은 이것으로 사라진다.

##### Lease Time

Lease Time은 소유권을 시간 제한부 임대로 바꾼다. TTL과 거의 같은 값이지만 읽는 쪽이 다르다. TTL은 "Redis가 언제 이 키를 지우는가"를 보고, Lease Time은 "내가 언제까지 이 자원을 내 것이라 주장해도 되는가"를 본다.

그래서 소유자가 남은 임대 시간을 알고 작업해야 한다. 작업을 시작하기 전에 남은 시간으로 끝낼 수 있는지 판단하고, 아니면 시작하지 않거나 갱신해야 한다. Redis 문서가 제시하는 다중 노드 락 절차인 Redlock도 남은 유효 시간을 획득에 걸린 시간만큼 깎아서 계산하고, 그 값이 음수면 락을 포기한다.

#### 그 대가로 생기는 새 위험 넷

해제를 시간에 맡기는 순간, 소유자가 자기도 모르는 사이에 락을 잃는 일이 생긴다. 거기서 위험 넷이 나온다. 둘은 TTL 값을 어떻게 잡아도 남는다. 하나는 해제 코드를 함께 바꿔야 막히고, 나머지 하나는 Redis의 시각이 바뀔 때 생긴다.

##### 새 위험 1. TTL이 작업 시간보다 짧으면 정상 작업 중에 풀린다

이 위험은 장애가 하나도 없어도 발생한다. 작업이 TTL보다 1밀리초라도 오래 걸리면 그 틈에 다음 인스턴스가 락을 다시 잡고, 둘이 같은 임계 구역에 들어간다. 그런데 평소에는 안 터진다. 평균 작업 시간 200밀리초에 TTL 3초면 넉넉해 보인다. 그러나 DB 커넥션 풀이 고갈되거나 외부 조회가 느려지면 100번 중 99번이 끝나는 시간(p99)이 5초로 뛴다. 터지는 순간은 그때다.

##### 새 위험 2. TTL이 길면 좀비락이 그만큼 오래 산다

TTL을 60초로 잡으면 위험 1은 줄지만, 인스턴스가 죽을 때마다 해당 코트·시간대의 신청이 60초간 전부 실패한다. 위험 1과 2를 함께 없앨 수 없다.

| | TTL을 늘리면 | TTL을 줄이면 |
|---|---|---|
| 정상 작업 중 만료 | 줄어든다 | 늘어난다 |
| 장애 시 자원 잠김 시간 | 늘어난다 | 줄어든다 |
| 내주는 것 | 가용성 | 상호배제 |

TTL의 하한은 작업의 최악 실행 시간이고 상한은 장애 시 허용 가능한 중단 시간이다. 작업이 허용 중단 시간보다 오래 걸리면 하한이 상한을 넘는다. 어떤 값을 골라도 둘 중 하나를 어긴다. 그때는 작업을 쪼개거나 다른 장치를 더해야 한다.

##### 새 위험 3. 만료된 뒤의 해제가 남의 락을 지운다

멈춤 타임라인에서 깨어난 A가 B의 락을 지운 `t=12.5`가 이 위험이다. 락을 모르는 사이에 잃을 수 있으니, 해제도 소유자를 확인한 뒤 지우도록 함께 바뀌어야 한다. 값에 클라이언트마다 다른 랜덤 토큰을 넣고 조건부로 원자적으로 지운다.

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
    return redis.call("del", KEYS[1])
else
    return 0
end
```

값 검증 없는 `DEL`은 분산 락에서 틀린 코드다. TTL을 걸고도 토큰을 검증하지 않으면 위험 3이 그대로 남는다. Redis 8.4부터는 `DELEX key IFEQ <토큰>` 한 명령으로 된다.

##### 새 위험 4. 만료 판정이 벽시계에 기댄다

Redis의 만료는 단조 증가 시계가 아니라 벽시계 기준이다. NTP 보정이나 수동 변경으로 시각이 갑자기 바뀌면 만료 시점이 당겨지거나 밀려서 두 프로세스가 동시에 락을 쥘 수 있다. Redis 공식 문서도 이 점을 일관성 주의사항으로 적어 두었다.

#### 갱신

TTL을 짧게 잡고, 작업하는 동안 별도 스레드가 주기적으로 만료 시각을 뒤로 늦추면 위험 1과 2를 함께 줄일 수 있다. 자바용 Redis 클라이언트 Redisson의 watchdog이 이 방식이다. 문서 기준으로 `lockWatchdogTimeout` 기본값은 30000밀리초이고, 갱신은 그 3분의 1 주기로 일어난다. 단, `leaseTime`을 지정하지 않고 `lock()`을 호출할 때만 동작한다. 안전하게 하려고 `leaseTime`을 명시하면 자동 갱신이 꺼져서 "작업 중 만료" 위험이 되살아난다.

갱신은 멈춤을 막지 못한다. Stop-the-world GC는 갱신 스레드까지 같이 멈추므로 멈춘 사이 갱신이 끊기고 TTL이 만료된다. 갱신은 작업이 오래 걸릴 때를 대비하는 장치이고, 프로세스가 멈출 때를 막는 장치가 아니다.

#### 정리

TTL은 가용성을 복구하고 상호배제는 복구하지 않는다.

| 적용한 장치 | 죽음 | 멈춤 | 끊김 |
|---|---|---|---|
| TTL 없는 락 | 영구 좀비락 | 멈춘 시간만큼 나머지 획득 실패. 깨어나면 정상 해제 | 영구 좀비락 |
| TTL | 해결 | **상호배제 위반으로 전환** | TTL만큼 지연 후 해결 |
| TTL + 토큰 서명 해제 | 해결 | 연쇄 붕괴는 막음. 중복 실행은 남음 | 해결 |
| TTL + 자동 갱신 | 해결 | 여전히 위반 | 해결 |
| TTL + 토큰 서명 + 자원 쪽 최종 판정 | 해결 | 해결 | 해결 |

TTL은 멈춤을 고치지 않고 고장 나는 방식을 바꾼다. 표의 첫 행과 둘째 행의 '멈춤' 칸이 그 차이다. 눈에 띄는 가용성 사고가 조용한 정확성 사고로 바뀐다. 죽음과 끊김이 멈춤보다 잦은 환경이면 이 맞바꿈은 이득이다. 이득인 것과 안전해진 것은 다르다.

#### 남은 멈춤은 자원 쪽에서 막는다

남은 멈춤은 락 쪽에서 원리적으로 막을 수 없다. 락을 쥐었다고 믿는 상태와 실제 소유권이 어긋나는 순간이 반드시 있고, 그 순간이 언제인지 획득 시점에는 알 수 없다. 그래서 최종 판정을 락이 아니라 자원 쪽으로 옮겨야 한다. Kleppmann은 획득할 때마다 단조 증가하는 번호를 발급하고, 자원이 지금까지 본 가장 큰 번호보다 작은 쓰기를 거부하자고 제안한다. 멈췄던 A는 작은 번호를 들고 오므로 자원 쪽에서 걸러진다.

자원 쪽 판정을 넣을 자리는 이 도메인에 이미 있다. 알림 신청의 업무 조건을 묶은 UNIQUE 제약과 낙관적 락의 `version`이 단조 증가 번호와 같은 일을 한다. 그러면 Redis 락의 역할이 "상호배제를 보장하는 장치"에서 "제약 위반 예외와 재시도를 줄이는 장치"로 내려간다. 역할을 내리는 것은 타협이 아니라 올바른 설계다. 상호배제를 자원 쪽에서 보장하므로 Redlock처럼 여러 노드에 락을 걸 필요도 없다.

#### 한정 DB 비관적 락

"DB 락은 서버가 소유권을 추적하므로 좀비락이 없다"는 설명은 조건부로만 맞다. 클라이언트가 깨끗하게 끊기면 DB 서버가 연결 종료를 보고 트랜잭션을 롤백해 락을 놓는다. 그러나 한쪽만 끊긴 half-open 상태에서는 서버가 클라이언트의 부재를 알지 못해 트랜잭션과 락이 유지된다. 클라이언트는 사라졌는데 서버 쪽 TCP 연결은 그대로 살아 있는 상태다. 이때는 유휴 세션을 끊는 `wait_timeout`이 지나야 세션이 닫힌다. MySQL 기본값은 여덟 시간(28800초)이다. 설정을 손대지 않았다면 좀비 보유 시간이 Redis TTL보다 오히려 길다.

좀비락이 생기는지 아닌지가 차이가 아니다. 차이는 두 가지다. 첫째, DB 락은 멈춤에서 상호배제를 깨지 않고 대기만 늘린다. 둘째, 좀비 보유 시간이 서버 설정값으로 통제된다. 락 전략은 처리량과 지연에 고장 나는 방식까지 더해 비교한다. 그러면 이 차이가 선택의 근거가 된다.

#### 결론

알림 신청 중복 방지에는 락을 세 겹으로 둔다. 이 락은 정확성 목적이다. 락이 깨지면 같은 사용자에게 같은 코트·시간대의 알림이 중복 발송된다. Redis 락에 TTL과 토큰 서명을 함께 적용해 죽음과 끊김에서 생기는 좀비락을 없앤다. 작업 시간이 TTL에 근접하면 갱신으로 위험 1을 줄인다. 멈춤이 만드는 중복 실행은 DB의 UNIQUE 제약으로 최종 차단한다.

TTL 값은 안전 여유가 아니라 측정값으로 정한다. 작업의 p99 실행 시간과 장애 시 허용 중단 시간을 먼저 재고, 그 두 수 사이에서 고른다. 제출물 2에서 그 측정을 한다.
