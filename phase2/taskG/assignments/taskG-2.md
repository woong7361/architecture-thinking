## 답안

### 제출물 1. 데드락 발생 구조와 본인 도메인 재현 시나리오

#### 데드락은 대기 관계가 사이클을 이루어 양쪽 모두 작업을 끝내지 못하는 상태다

두 주체가 각자 이미 획득한 락을 해제하지 않은 상태에서 상대가 획득한 락을 요청하면 양쪽이 모두 멈춘다. 락을 해제하는 코드는 요청한 락을 획득한 다음에 실행되는데, 그 획득이 상대의 해제를 기다리기 때문이다. 그래서 A의 해제는 B의 해제를 기다리고, B의 해제는 다시 A의 해제를 기다린다. 이렇게 대기 관계가 출발점으로 돌아오는 사이클을 이루면 어느 쪽도 자기 해제 코드에 도달하지 못한다. 데드락이라고 부르는 것은 락이라는 장치의 결함이 아니라 이 대기 사이클이다.

```
   보유·대기 관계

        ┌───── 보유 ─────▶ [자원 1] ◀───── 대기 ─────┐
        │                                            │
       ( A )                                      ( B )
        │                                            │
        └───── 대기 ─────▶ [자원 2] ◀───── 보유 ─────┘

   자원을 지우고 대기 관계만 남긴 대기 그래프

        ┌──── A는 B가 보유한 자원 2를 기다린다 ────┐
        │                                          ▼
       ( A )                                    ( B )
        ▲                                          │
        └──── B는 A가 보유한 자원 1을 기다린다 ────┘
```

#### 네 조건이 동시에 성립할 때만 생기고, 하나만 깨면 사라진다

대기 사이클은 아무 조건에서나 생기지 않는다. 데드락이 성립하려면 네 가지 조건이 동시에 충족되어야 하고, 이 네 조건은 1971년에 정리된 뒤 지금까지 같은 형태로 인용된다. 조건이 네 개이므로 해결 방법도 네 가지로 나뉜다. 네 조건 가운데 하나만 성립하지 않게 만들면 나머지 세 조건이 모두 충족되어도 데드락은 발생하지 않는다.

| 조건 | 뜻 | 이 조건을 깨는 장치 | 대가 |
|---|---|---|---|
| 상호배제 | 한 자원을 한 시점에 하나의 주체만 점유한다 | 자원을 분할하거나 불변으로 만들어 락을 사용하지 않는다 | 락이 지키던 규칙을 다른 수단으로 지켜야 한다 |
| 점유 후 대기 | 이미 획득한 락을 유지한 채 다음 락을 기다린다 | 필요한 락을 한 번에 모두 획득하고, 하나라도 실패하면 전부 해제한다 | 필요한 락을 미리 모두 알아야 하고, 락을 거는 범위가 넓어진다 |
| 비선점 | 다른 주체가 획득한 락을 빼앗을 수 없다 | 기한이 만료되면 회수하거나, 사이클을 탐지한 뒤 한쪽을 되돌린다 | 작업이 끝나기 전에 소유권을 잃는 주체가 생긴다 |
| 순환 대기 | 대기 그래프에 사이클이 있다 | 모든 락 획득이 하나의 전역 순서를 따르도록 강제한다 | 순서를 미리 정해야 하고, 그 순서를 따르는 락에만 효력이 있다 |

기한이 있는 락은 세 번째 조건인 비선점을 깨는 장치다. 기한이 지나면 저장소가 락을 삭제하므로 소유자의 동의 없이 락이 회수되고, 그 대가로 작업이 끝나기 전에 소유권을 잃는 위험이 생긴다. 제출물 2에서 만들 Facade는 네 번째 조건인 순환 대기를 깨는 장치다. 순환 대기만 제거하므로 다른 주체의 소유권을 빼앗지 않지만, 어떤 락을 어떤 순서로 획득할지 미리 정해 두어야 한다.

#### 순환 대기는 경로마다 획득 순서가 어긋날 때 생긴다

앞의 세 조건은 락을 사용하기로 결정한 시점에 이미 충족된다. 한 시점에 하나의 주체만 점유하게 하는 것이 락의 정의이고, 이미 획득한 락을 유지한 채 다음 락을 요청하는 것이 일반적인 작성 방식이며, 다른 주체가 획득한 락을 빼앗지 못하는 것이 일반적인 락의 동작이다. 반면 순환 대기는 여러 실행 경로가 자원을 획득하는 순서가 서로 어긋날 때에만 생긴다. 순서가 어긋나는 원인은 실수가 아니라 입력이다. 각 경로는 자기가 입력으로 받은 자원을 먼저 획득하고 그 자원을 읽어서 알아낸 자원을 나중에 획득하므로, 입력이 다른 경로는 획득 순서도 달라진다. 그래서 경로를 하나씩 읽으면 모두 자연스럽고, 여러 경로의 획득 순서를 모아서 비교할 때에만 사이클이 드러난다.

#### 재현 시나리오는 두 경로가 서로 다른 자원 두 개를 엇갈려 잡는 것이다

- 빈자리락: 외부 예약처에서 빈자리를 가져와 저장하는 구간을 잠근다. 코트와 날짜 단위이고, 중복 호출을 막으려고 배타로 잡는다.
- 신청락: 알림 신청 한 건의 상태를 고치는 구간을 잠근다. 신청 단위이고, 두 락 모두 기한이 3초인 Redis 락이다.
- 두 경로가 락을 두 개씩 쥐는 구성은 재현을 위해 그렇게 짰다.

갱신 경로는 코트와 날짜를, 발송 경로는 신청을 입력으로 받는다. 각자 자기 입력을 먼저 잠그므로 획득 순서가 반대가 되고, 같은 코트와 날짜의 같은 시간대를 동시에 처리하면 사이클이 닫힌다.

```
세로선은 그 락을 보유하고 있는 구간이다.

갱신 경로                                입력: 코트, 날짜
  ┌─ 획득 빈자리락
  │    외부 예약처를 조회해 빈자리 현황을 덮어쓴다
  │      ┌─ 획득 신청락        ← 발송 경로가 보유 중이므로 대기
  │      │    감시 중인 신청을 발송 대기에 넣는다
  │      └─ 해제 신청락
  └─ 해제 빈자리락

발송 경로                                입력: 신청
  ┌─ 획득 신청락
  │      ┌─ 획득 빈자리락      ← 갱신 경로가 보유 중이므로 대기
  │      │    저장된 빈자리 현황을 읽는다
  │      └─ 해제 빈자리락
  │    빈자리가 남아 있으면 알림을 발송한다
  └─ 해제 신청락

대기 그래프가 갱신 ─▶ 발송 ─▶ 갱신 으로 닫혀 양쪽 모두 해제 지점에 도달하지 못한다.
```

멈춤은 기한이 만료될 때까지 이어진다. 그래서 두 경로의 응답 시간이 락 기한만큼 늘어나고, 데드락 전용 오류가 없으므로 대기 시간 말고는 원인을 추적할 단서가 없다. 기한이 만료된 뒤에는 두 경로가 소유권을 잃은 채로 같은 신청을 동시에 바꾸므로 알림이 두 번 발송될 수 있다.

#### 테스트로 고정하니 다섯 회차 모두 데드락이 났다

두 경로를 서비스로 만들고 같은 순간에 호출했다. 테스트가 맞춘 것은 출발 시점뿐이고 획득 순서는 각 경로의 입력에 맡겼다. 순서까지 고정하면 전역 순서로 같은 결함을 푸는 것을 보일 수 없다.

기한을 1초로 두고 다섯 회차를 돌렸다. 다섯 회차 모두 두 경로가 서로를 기다렸고, 두 번째 획득 대기는 981에서 999밀리초 사이였으며, 모든 회차에서 첫 락의 소유권을 잃은 상태로 임계 구역을 이어서 실행했다. 대기가 기한에 붙었다는 것은 상대의 해제가 아니라 기한 만료로 풀렸다는 뜻이다.

두 경로는 `phase2/taskF/alert-kata`의 `AvailabilityRefreshService`와 `AlertDispatchService`이고, 테스트는 `CrossResourceDeadlockTest`, 측정 기록은 `evidence/lock-order-deadlock.md`에 있다.

### 제출물 2. Lock 순서 Facade와 데드락 제거 증명과 한계

#### 모든 락 획득은 Facade를 거치고, 순서는 Facade가 정한다

경로마다 획득 코드를 들고 있으면 순서도 경로마다 달라진다. 그래서 획득하는 코드를 두 경로에서 모두 제거하고 Facade 한 곳으로 옮겼다. 순서를 정하는 데 필요한 것은 락마다 매겨 둔 전역 순위뿐이다.

```java
enum LockKind { AVAILABILITY, ALERT }              // 전역 순위는 선언 순서다
record LockRequest(LockKind kind, String key)      // 비교와 동일성 모두 이 쌍으로 판정한다
enum LockOrder { AS_REQUESTED, GLOBAL }            // 전후를 비교하려고 남겼다

LockedOutcome OrderedLockFacade.inOrder(List<LockRequest> requests, LockedWork work)
EscalateResult LockSession.escalate(LockRequest request)
```

호출자는 필요한 락의 목록과 락을 쥔 동안 할 일만 넘기고, 어느 락을 먼저 획득할지는 지정하지 않는다.

```java
// 발송 경로. 신청을 받으면 두 키를 모두 알 수 있으므로 집합을 선언한다
facade.inOrder(List.of(LockRequest.alert(신청), LockRequest.availability(코트, 날짜)),
        session -> 현황을_읽고_발송한다());

// 갱신 경로. 조회한 뒤에야 어느 신청을 잠글지 알게 되므로 작업 도중에 추가한다
facade.inOrder(List.of(LockRequest.availability(코트, 날짜)), session -> {
    외부예약처를_조회해_현황을_덮어쓴다();
    if (session.escalate(LockRequest.alert(신청)) == EscalateResult.ACQUIRED) {
        감시중인_신청을_발송대기에_넣는다();
    }
});
```

Facade는 다섯 단계를 수행한다.

```
1  같은 종류와 같은 키가 겹치면 하나로 줄인다
2  종류의 순위를 먼저 비교하고, 같으면 키를 비교해 정렬한다
3  집합 전체에 하나의 제한 시간을 두고 차례로 획득한다
   하나라도 획득하지 못하면 이미 획득한 것을 전부 해제하고 실패를 돌려준다
4  할 일을 수행한다
5  역순으로 해제한다. 해제 하나가 실패해도 나머지는 전부 해제한다
```

1번은 재진입을 허용하지 않는 락에서 이미 획득한 키를 다시 요청해 기한까지 대기하는 것을 막는다. 5번의 역순 해제는 순환 대기와 관계가 없다. 해제는 대기 관계를 만들지 않기 때문이고, 역순으로 해제하는 이유는 먼저 획득한 락이 지키는 범위가 나중 작업을 포함하기 때문이다. `escalate`는 이미 획득한 락보다 뒤 순위인 요청만 허용하고, 앞 순위를 요청하면 획득하지 않고 위반으로 돌려준다.

#### 순위는 빈자리락을 앞에 둔다

신청락을 앞에 두면 갱신 경로가 외부 예약처를 호출하는 동안 신청락을 계속 보유하는데, 외부 호출은 이 도메인에서 가장 느린 구간이다. 그리고 갱신 경로가 뒤늦게 알게 되는 것이 신청락이므로, 신청락이 뒤 순위여야 작업 도중에 추가할 수 있다. 그 대가로 발송 경로가 빈자리락을 발송이 끝날 때까지 보유하므로 같은 코트와 날짜의 갱신이 더 오래 기다린다.

이 순위에서는 두 경로가 모두 빈자리락을 먼저 요청한다. 늦게 도착한 경로는 어떤 락도 획득하지 못한 상태로 기다리고, 그 상태에서는 상대가 요청할 신청락을 아무도 보유하지 않으므로 대기 관계가 사이클을 이루지 못한다.

#### 결과는 전역 순서에서 멈춤과 소유권 상실이 모두 0이다

사이클이 없다는 것은 논증으로 닫힌다. 이미 획득한 락보다 뒤 순위만 획득하면 대기 관계가 순위가 높아지는 방향으로만 생기므로 출발점으로 돌아오지 못한다. 측정은 그 전제가 실제로 성립하는지만 확인한다. 재현에 쓴 `CrossResourceDeadlockTest`를 그대로 두고 `LockOrder`만 바꿔 두 조건을 돌렸다.

| 획득 순서 | 멈춘 회차 | 소유권 상실 회차 | 순서 위반 | 끝까지 수행한 경로 | 가장 긴 대기 |
|---|---|---|---|---|---|
| 호출자가 넘긴 대로 | 5/5 | 5/5 | 0 | 10/10 | 981~1019ms |
| 전역 순서 | 0/5 | 0/5 | 0 | 10/10 | 0.9~66ms |

전역 순서에서 남은 대기 44에서 66밀리초는 먼저 도착한 경로가 임계 구역에 머문 시간이다. 순서 위반이 0인 것은 갱신 경로가 추가하는 신청락이 이미 획득한 빈자리락보다 뒤 순위이기 때문이고, 순위를 반대로 정하면 같은 추가가 위반이 되어 전부 해제하고 재시작해야 한다.

두 조건이 한 테스트에 함께 있으므로 데드락과 그 제거를 한 번에 확인할 수 있다. 코드는 `phase2/taskF/alert-kata`의 `OrderedLockFacade`와 두 경로 서비스이고, 측정 기록은 `evidence/lock-order-deadlock.md`에 있다.

#### 한계

이 방식은 한 경로가 락을 여럿 보유한다는 전제를 유지한 채 고르는 해법이다. 락 범위를 다시 정해 한 경로가 락을 하나만 보유하게 하거나, 여러 키를 한 번에 원자적으로 획득하면 순서를 맞출 필요가 없다. 아래 다섯 가지는 그 선택의 대가다.

- **적용 범위.** Facade를 거치지 않은 획득은 순서를 따르지 않는다. 직접 호출, 데이터베이스가 스스로 획득하는 갭과 인덱스와 외래 키 락, 커넥션을 보유한 채 락을 기다리는 사이클이 밖에 있다. 지금 구현은 Facade를 만든 데까지이고, 모든 획득이 Facade를 거치도록 강제하려면 락 획득 함수의 공개 범위를 줄이고 그 경계를 테스트로 고정해야 한다.
- **키 사전 확정.** 앞 순위 락이 뒤늦게 필요해지면 전부 해제하고 재시작하는 방법만 남는다. 그러려면 첫 락만 보유한 구간에 되돌릴 수 없는 작업이 없어야 하고, 재시작이 반복되는 라이브락을 막을 상한과 간격 흔들기가 필요하다.
- **기한 만료 위험이 커진다.** 첫 락을 보유한 채 나머지를 획득하므로 한 작업이 필요로 하는 기한이 늘어나고, 락이 여러 개면 그중 하나라도 만료될 확률이 합쳐진다. 순환 대기를 없앤 대가로 비선점 쪽 위험을 더 받는다.
- **순위표의 전역 동일성.** 순위를 재배치한 버전과 이전 버전이 함께 실행되면 전역 순서가 둘로 갈려 사이클이 되살아나고, 깨져도 알려 주는 신호가 없다. 순위는 뒤에만 덧붙이고 재정렬은 두 단계로 배포해야 한다.
- **실패 모드가 바뀌고 경합이 한 곳으로 모인다.** 정렬 때문에 모든 경로가 같은 첫 락을 먼저 요청하므로 그 락이 직렬화 지점이 되고, 제한 시간에 걸려 물러나는 요청이 새로운 실패 모드가 된다. 평균 대기는 줄지만 특정 키의 꼬리 지연은 늘어날 수 있다.
