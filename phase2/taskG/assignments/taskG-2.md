## 답안

### 제출물 1. 데드락 발생 구조와 본인 도메인 재현 시나리오

#### 데드락은 대기 관계가 사이클을 이루어 양쪽 모두 작업을 끝내지 못하는 상태다

두 주체가 각자 이미 획득한 락을 해제하지 않은 상태에서 상대가 획득한 락을 요청하면 양쪽이 모두 멈춘다. 락을 해제하는 코드는 요청한 락을 획득한 다음에 실행되는데, 그 획득이 상대의 해제를 기다리기 때문이다. 그래서 A의 해제는 B의 해제를 기다리고, B의 해제는 다시 A의 해제를 기다린다. 이렇게 대기 관계가 출발점으로 돌아오는 사이클을 이루면 어느 쪽도 자기 해제 코드에 도달하지 못한다. 데드락이라고 부르는 것은 락이라는 장치의 결함이 아니라 이 대기 사이클이다.

G-1에서 다룬 좀비락도 락이 풀리지 않는 상태이지만 멈추는 원인이 다르다. 좀비락은 락을 획득한 주체가 사라져서 해제 요청이 아예 오지 않는 상태다. 데드락은 락을 획득한 주체가 살아 있고 해제 요청을 보내는 코드도 그대로 있는데, 실행이 그 코드까지 진행되지 못하는 상태다. 원인이 다르므로 해결 방법도 다르다. 좀비락은 소유자가 살아 있는지 의심해서 락을 회수하고, 데드락은 대기 사이클을 끊어서 해소한다.

```
   보유·대기 관계

        ┌───── 보유 ─────▶ [자원 1] ◀───── 대기 ─────┐
        │                                            │
       ( A )                                      ( B )
        │                                            │
        └───── 대기 ─────▶ [자원 2] ◀───── 보유 ─────┘

   자원을 지우고 대기 관계만 남긴 대기 그래프

        ┌──── A는 B가 보유한 자원 2를 기다린다 ────┐
        │                                          ▼
       ( A )                                    ( B )
        ▲                                          │
        └──── B는 A가 보유한 자원 1을 기다린다 ────┘
```

#### 네 조건이 동시에 성립할 때만 생기고, 하나만 깨면 사라진다

대기 사이클은 아무 조건에서나 생기지 않는다. 데드락이 성립하려면 네 가지 조건이 동시에 충족되어야 하고, 이 네 조건은 1971년에 정리된 뒤 지금까지 같은 형태로 인용된다. 조건이 네 개이므로 해결 방법도 네 가지로 나뉜다. 네 조건 가운데 하나만 성립하지 않게 만들면 나머지 세 조건이 모두 충족되어도 데드락은 발생하지 않는다.

| 조건 | 뜻 | 이 조건을 깨는 장치 | 내주는 것 |
|---|---|---|---|
| 상호배제 | 한 자원을 한 시점에 하나의 주체만 점유한다 | 자원을 분할하거나 불변으로 만들어 락을 사용하지 않는다 | 락이 지키던 규칙을 다른 수단으로 지켜야 한다 |
| 점유 후 대기 | 이미 획득한 락을 유지한 채 다음 락을 기다린다 | 필요한 락을 한 번에 모두 획득하고, 하나라도 실패하면 전부 해제한다 | 필요한 락을 미리 모두 알아야 하고, 락을 거는 범위가 넓어진다 |
| 비선점 | 다른 주체가 획득한 락을 빼앗을 수 없다 | 기한이 만료되면 회수하거나, 사이클을 탐지한 뒤 한쪽을 되돌린다 | 작업이 끝나기 전에 소유권을 잃는 주체가 생긴다 |
| 순환 대기 | 대기 그래프에 사이클이 있다 | 모든 락 획득이 하나의 전역 순서를 따르도록 강제한다 | 순서를 미리 정해야 하고, 그 순서를 따르는 락에만 효력이 있다 |

G-1에서 적용한 TTL은 세 번째 조건인 비선점을 깨는 장치다. 기한이 지나면 저장소가 락을 삭제하므로 소유자의 동의 없이 락이 회수되고, 그 대가로 작업이 끝나기 전에 소유권을 잃는 위험이 생겼다. 제출물 2에서 만들 Facade는 네 번째 조건인 순환 대기를 깨는 장치다. 순환 대기만 겨냥하므로 다른 주체의 소유권을 빼앗지 않지만, 어떤 락을 어떤 순서로 획득할지 미리 정해 두어야 한다.

#### 획득 순서가 어긋나는 것은 실수가 아니라 경로마다 입력이 달라서 생긴다

네 조건 가운데 앞의 세 조건은 락을 사용하기로 결정한 시점에 이미 충족된다. 한 시점에 하나의 주체만 점유하게 하는 것이 락의 정의이고, 이미 획득한 락을 유지한 채 다음 락을 요청하는 것이 일반적인 작성 방식이며, 다른 주체가 획득한 락을 빼앗지 못하는 것이 일반적인 락의 동작이다. 반면 순환 대기는 저절로 충족되지 않고, 여러 실행 경로가 자원을 획득하는 순서가 서로 어긋날 때 발생한다. 두 경로가 두 자원을 반대 순서로 획득하는 경우가 가장 단순한 형태이고, 세 경로 이상이 차례로 이어져 대기 관계가 처음 경로로 돌아오는 경우도 같은 사이클이다. 모든 경로가 자원을 같은 순서로 획득하면, 나중에 도착한 경로는 첫 번째 자원에서 대기하므로 어떤 자원도 점유하지 않고 따라서 다른 경로를 막지도 않는다.

```
   엇갈린 순서                              같은 순서
   A: 자원 1 → 자원 2                       A: 자원 1 → 자원 2
   B: 자원 2 → 자원 1                       B: 자원 1 → 자원 2

   A ─▶ [자원 1]      [자원 2] ◀─ B         A ─▶ [자원 1] ◀─ B 가 여기서 대기한다
          ↘ 기다림     기다림 ↙                    B 는 자원 2 를 점유한 적이 없다
             사이클 완성                     A ─▶ [자원 2] 는 비어 있으므로 통과한다
```

순서가 어긋나는 데에는 각 경로 나름의 이유가 있다. 각 경로는 자기가 입력으로 받은 자원을 먼저 잠그고, 그 자원을 읽어서 알아낸 다른 자원을 나중에 잠근다. 경로마다 입력으로 받는 자원이 다르면 잠그는 순서도 달라진다. 두 경로를 따로 읽으면 각각 자연스러운데 두 경로를 함께 놓고 보면 순서가 반대인 상황이 이렇게 만들어진다. 그래서 데드락은 한 파일만 읽어서는 발견하기 어렵고, 여러 경로의 획득 순서를 모아서 비교해야 드러난다.

#### 데드락을 탐지하는 락과 탐지하지 않는 락은 같은 사이클을 다르게 드러낸다

사이클이 생겼을 때 무슨 일이 일어나는지는 자원의 종류가 아니라 락을 관리하는 주체가 결정한다. 관계형 DB 엔진은 락을 직접 획득하고, 어느 트랜잭션이 어느 락을 기다리는지도 엔진 안에 기록한다. 그래서 대기 관계를 한곳에 모아 사이클을 찾아내고, 사이클에 포함된 트랜잭션 가운데 하나를 골라 되돌린 다음 데드락 전용 오류를 반환한다. 애플리케이션이 데드락을 멈춤이 아니라 오류로 마주하는 이유가 이것이다. Redis 기반 분산 락은 사정이 다르다. 저장소에는 키가 존재한다는 사실만 있고 어느 클라이언트가 그 키를 기다리는지는 클라이언트의 재시도 루프 안에만 있으므로, 저장소가 참조할 수 있는 대기 그래프 자체가 없다. 사이클이 생겨도 저장소는 평소와 똑같이 키가 이미 존재한다고 응답하며, 전용 오류도 로그도 남기지 않는다.

| 락 관리자 | 사이클이 생기면 | 알아차릴 수 있는 신호 |
|---|---|---|
| 관계형 DB 엔진의 락 | 사이클에 포함된 트랜잭션 하나를 되돌려 해소한다 | 전용 오류 번호와 엔진이 남기는 데드락 기록 |
| 기한이 있는 Redis 락 | 기한이 만료될 때까지 양쪽이 멈춘다 | 락 획득 대기 시간이 기한만큼 늘어나는 것이 유일한 신호다 |
| 기한이 없는 Redis 락 | 운영자가 키를 삭제할 때까지 영구히 멈춘다 | 없다 |
| 두 종류가 섞인 경로 | 두 락 관리자 모두 사이클 전체를 보지 못한다 | 없다 |

기한이 있는 Redis 락에서 대기가 풀리는 것은 데드락이 해결된 결과가 아니다. 기한이 먼저 만료된 쪽의 락이 저장소에서 삭제되고, 그 락을 기다리던 쪽이 자원을 획득하는 것이다. 이때 기한이 만료된 쪽은 자기 락이 사라진 사실을 알지 못한 채 임계 구역을 계속 실행한다. 그러면 같은 자원을 두 주체가 동시에 변경하므로, G-1에서 정리한 위험 3인 상호배제 위반이 데드락에 이어서 발생한다.

#### 본인 도메인에서는 예약 상태와 알림 신청을 두 경로가 엇갈려 잡는다

이 도메인에서 사용하는 락은 두 개 모두 Redis에 있으므로, 앞의 표에서 기한이 있는 Redis 락에 해당한다. 순서가 어긋났을 때 나타나는 결과가 오류가 아니라 멈춤이고, 사이클에서 되돌릴 쪽을 골라 주는 주체도 없으므로 획득 순서는 전부 애플리케이션이 책임져야 한다. 락을 거는 자원은 두 종류인데 락 키를 구성하는 단위가 다르다. 예약 상태는 코트와 날짜로 묶이고, 알림 신청은 코트와 날짜와 시간대로 묶인다. 이 단위 차이가 아래에서 두 경로의 획득 순서를 어긋나게 만드는 원인이다.

| 자원 | 락 키 | 왜 잠그는가 |
|---|---|---|
| 예약 상태 | `lock:availability:court{C}:{D}` | EF-2가 동시 갱신 요청 가운데 한 건만 외부 예약처를 조회하라고 정했다 |
| 알림 신청 | `lock:alert:court{C}:{D}:{T}` | FR-1이 같은 조건의 중복 신청을 막고, FR-4가 신청 하나에 알림 한 건만 보내라고 정했다 |

두 자원을 모두 사용하는 경로도 두 개다. 확인 경로는 코트와 날짜를 입력으로 받는다. FR-7의 조회 요청이 들어왔을 때 저장된 결과가 확인 간격보다 오래되었으면 FR-3의 확인이 실행되고, 그 확인에서 빈자리를 발견하면 FR-4에 따라 해당 시간대를 감시하는 신청을 발송 대기에 넣어야 한다. 그래서 예약 상태를 먼저 잠그고, 확인 결과에서 알아낸 시간대의 신청을 나중에 잠근다.

발송 경로는 신청을 입력으로 받는다. 발송 대기에서 꺼낸 신청에 FR-4의 알림 한 건 제한을 적용하려면 그 신청을 먼저 잠가야 한다. 그 다음 EF-4가 요구하는 최신성 비교를 하려고 같은 코트와 날짜에 저장된 확인 결과를 읽는다. 갱신 중인 중간 상태를 읽지 않으려면 예약 상태 락을 획득해야 하는데, G-1에서 구현한 락에는 배타 모드만 있으므로 읽기만 하는 이 경로도 같은 배타 락을 획득한다. 그래서 두 자원을 획득하는 순서가 확인 경로와 반대가 된다.

```
자원
  R1 = 예약 상태      키 lock:availability:court{C}:{D}
  R2 = 알림 신청      키 lock:alert:court{C}:{D}:{T}

경로 X  확인이 알림을 깨운다                        입력 코트 C, 날짜 D
  획득 R1(C, D)
  결과 ← 외부예약처_조회(C, D)
  저장(결과)
  결과의 빈 시간대 T 마다:
      획득 R2(C, D, T)                             ← 두 번째 자원
      감시중인_신청을_발송대기에_넣고_알림완료로_표시
      해제 R2(C, D, T)
  해제 R1(C, D)

경로 Y  발송이 최신성을 확인한다                    입력 신청 S
  획득 R2(S.C, S.D, S.T)
  S 가 감시중이 아니면 해제하고 끝낸다
  획득 R1(S.C, S.D)                                ← 두 번째 자원
  최신 ← 저장된_예약상태(S.C, S.D)
  해제 R1(S.C, S.D)
  최신에 S.T 의 빈자리가 있으면 발송하고 알림완료로 표시
  없으면 감시중으로 남긴다
  해제 R2(S.C, S.D, S.T)
```

두 경로가 같은 코트와 날짜와 시간대를 동시에 처리하면 아래와 같이 대기 사이클이 생긴다.

```
t=0.00  X: 획득 R1(코트7, 11-20) 성공          Y: 획득 R2(코트7, 11-20, 19:00) 성공
t=0.02  X: 외부 예약처 조회 시작               Y: S 는 감시중. 통과
t=0.35  X: 빈 시간대 19:00 발견
t=0.36  X: 획득 R2(코트7, 11-20, 19:00) 요청 → Y 가 보유 중. 대기 시작
t=0.37  Y: 획득 R1(코트7, 11-20) 요청        → X 가 보유 중. 대기 시작
        → 사이클 완성. X 는 Y 의 해제를, Y 는 X 의 해제를 기다린다
t=0.37~ 양쪽 모두 자기 해제 지점에 도달하지 못한다. 저장소는 아무 이상도 보고하지 않는다
t=기한  먼저 기한이 만료된 쪽의 락이 삭제되고, 기다리던 쪽이 그 자원을 획득한다
        기한이 만료된 쪽은 소유권을 잃은 사실을 모른 채 임계 구역을 이어서 실행한다
```

이 사이클이 운영에서 드러나는 결과는 네 가지다. 첫째로 두 경로의 응답 시간이 락 기한만큼 늘어나므로, G-1에서 선택한 기한 3초에서는 NFR-2가 정한 피크 95분위 1초 기준을 넘긴다. 둘째로 알림 발송이 그만큼 지연되어 NFR-4가 정한 3초 기준도 넘긴다. 셋째로 데드락 전용 오류가 없으므로, 락 획득 대기 시간이 늘어나는 것 말고는 원인을 추적할 단서가 없다. 넷째로 기한이 만료된 다음에는 두 경로가 같은 신청을 동시에 변경할 수 있어 알림이 두 번 발송되고, FR-4의 알림 한 건 제한과 EF-5가 함께 깨진다.

이 시나리오를 테스트로 고정할 때는 두 경로의 첫 번째 획득이 반드시 겹치도록 만들어야 한다. 실제 실행 타이밍에 맡기면 사이클이 생기는 회차와 생기지 않는 회차가 섞여 테스트가 불안정해진다. 그래서 두 스레드가 각자 첫 번째 자원을 획득한 사실을 신호로 서로 확인한 다음에 두 번째 자원을 요청하도록 순서를 고정한다.

```
테스트: 사이클을 결정적으로 만든다
  스레드 X: 획득 R1 → 신호1 올림 → 신호2 기다림 → 획득 R2 요청
  스레드 Y: 획득 R2 → 신호2 올림 → 신호1 기다림 → 획득 R1 요청
  단언: 두 번째 획득은 양쪽 모두 기한이 만료되기 전에는 성공하지 못한다
        또는 두 경로의 획득 대기 시간이 기한 이상이다
```

테스트 실행 시간을 줄이려면 락 기한을 짧게 설정해야 한다. 다만 기한을 짧게 설정하면 기한 만료로 대기가 풀리는 시점도 함께 당겨진다. 그래서 멈춤이 기한까지 이어지는지 확인하는 단언과 기한 만료 후에 소유권을 잃는지 확인하는 단언은 서로 다른 기한 설정에서 측정해야 한다.
