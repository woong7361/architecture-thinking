# My Design — 이 유스케이스의 객체 설계도

`rules.md`의 순서(협력 → 책임 → 역할 → 생성)를 밟아 미리 그려 둔 설계도다.
**확정 스펙이 아니라 구현이 검증할 가설이다.** 뒤에서 앞이 틀렸음을 발견하면 되돌아온다.

## ① 협력 — 예매가 성립하려면 *무슨 일*이 일어나야 하나

객체가 아니라 행위에서 출발한다. **여기엔 객체 이름이 하나도 없다. 행위만, 수신자는 전부 미정(?).**

```
"예매하라"가 올바르게 끝나려면 —
  a. 예매 요청을 받아들인다                          → ?
  b. 요청자가 실재하는(예매 자격 있는) 사람인지 확인 → ?
  c. 예매 대상을 확보한다                            → ?
  d. 그 대상이 지금 예약 가능한 상태인지 판단한다      → ?   (이미 팔렸으면 거부)
  e. 대가를 청구한다                                → ?
  f. 대상을 '예약됨'으로 전이한다(누구 것인지 기록)   → ?
  g. 그 전이를 영구히 확정한다                       → ?
  h. b~g가 도중 실패해도 모순 상태를 안 남기게 묶는다  → ?   (돈만 받고 예약 안 됨 방지)
```

여기서 **행위 수준의 결정** 하나: `d(가능 판단)`를 `e(청구)` 앞에 둔다 — 못 파는 자리에 돈부터 걷으면
안 되니까(fail-fast). 아직 "누가"는 없다.

## ② 책임 배정 — 정보 전문가로 수신자를 붙인다 → *여기서 객체가 태어난다*

- **d, f (예약 가능 판단 · 상태 전이).** 필요한 정보 = 대상의 **예약 상태**. 그걸 소유한 자에게 준다
  → **`Ticket`** 이라는 도메인 객체가 태어난다. d·f가 같은 정보(상태)에 붙으니 한 객체로 모인다(높은 응집).
- **e (청구).** 필요한 정보 = 결제 수단·외부 결제 시스템과 통신하는 법 → **결제 담당**이 태어난다.
- **c, g (확보 · 영속화).** 필요한 정보 = 대상이 어디 저장돼 있는지 → **`TicketRepository`**.
- **b (요청자 실재 확인).** 필요한 정보 = 유저가 어디 저장돼 있는지 → **`UserRepository`**.
  - ⟳ *되돌아오기(정상):* "이거 예매의 책임 맞아? 인증 앞단 일 아냐?" 잠깐 ①로 되돌아가 묻는다.
    → **존치.** "실재하는 유저에게만 예매"는 예매의 **업무 전제조건**이고, 이를 저장소 제약(FK)에
    떠넘기면 정책이 저장 세부로 새고 `UserNotFound`라는 도메인 의미가 저수준 제약 위반 예외로 뭉개진다.
- **a, h (요청 수신 · 원자성 경계 · 조립).** 필요한 정보 = 협력 전체의 순서와 원자성. 개별 도메인 객체는
  그걸 모른다 → 협력을 **조정하는 자**가 태어난다: **`TicketService`**.
  - `h`의 근거: `e(청구)`는 외부라 되돌릴 수 없다. "청구 성공 + 확정 실패"의 모순을 막는 경계는
    순서를 아는 조정자만 질 수 있다. `Ticket`은 순수 불변식만, 경계는 서비스가 진다 — 그래야 도메인이
    순수하게 남아 Mock 0개로 검증된다.

**책임표 (변경 이유 하나 = SRP):**

| 행위 | 태어난 객체 | 정보 전문가 근거 | 변경 축 |
|---|---|---|---|
| d·f 예약 판단·전이 | **`Ticket`** (도메인) | 예약 상태(`reserved`,`userId`)를 소유 | 예약 규칙 |
| e 청구 | **결제 담당** (ChargePort 구현) | 외부 결제 통신을 앎 | 결제 방식 |
| c·g 확보·영속화 | **`TicketRepository`** | 저장 매체를 앎 | 저장 방식 |
| b 유저 실재 확인 | **`UserRepository`** | 유저 저장소를 앎 | 저장 방식 |
| a·h 조립·**원자성 경계** | **`TicketService`** | 협력 순서·원자성을 앎 | 유스케이스 흐름 |

**이제 수신자가 붙은 협력:**

```
Client → TicketService.reserve(userId, ticketId, payInfo)   ┐ 원자성/보상 경계
  ├─ b  userRepo.findById(userId)          없으면 UserNotFound     │  = TicketService 소유
  ├─ c  ticketRepo.findById(ticketId)      대상 확보               │
  ├─ d·f ticket.reserve(userId)            가능 판단+전이(거부 가능) │
  ├─ e  chargePort.charge(payInfo, price)  청구                    │
  └─ g  ticketRepo.save(ticket)            확정(실패 시 e 보상)      ┘
```

## ③ 역할 — 갈아끼울 축만 인터페이스로

②에서 태어난 객체 중 **구현이 교체되는 축**만 포트로 뽑는다. 축 없으면 안 뽑는다(과설계 경계).
`rules.md` §4의 게이트를 통과한 것만 만든다.

- **결제 담당 → `ChargePort`.** **방향(DIP):** 벤더 API가 아니라 내가 통제하는 `ChargePort`에 의존.
  **너비(ISP):** `refund`·`queryHistory` 없이 `charge`만. **OCP:** 결제수단 추가 = 어댑터 한 장.
- **저장 → `TicketRepository` / `UserRepository`** (포트): DB 교체 + 테스트 대체 축(DIP·테스트 격리).
- **`Ticket`은 역할화하지 않는다** — 예약 규칙이 다형으로 갈리는 축이 아직 없다(과설계 경계).

## ④ 생성 — 맨 마지막, 최소만

`TicketService`는 포트들을 **생성자 주입**으로 받는다. 실제 구현체를 만들어 꽂는 건 바깥(구성 루트)의
몫 — 사용 책임과 생성 책임을 분리한다.

## 객체 설계도

**화살표 = 의존 방향.** 정책(서비스)과 세부(어댑터)가 서로를 모른 채 가운데 포트에서 만난다(DIP).

```
                ┌──────────────── 도메인 ────────────────┐
      d·f 전이   │  Ticket  「예약 불변식의 주인」          │
   ┌────────────►│  - reserved / userId                    │
   │             │  + reserve(userId) … 이미 예약이면 거부 │
   │             └─────────────────────────────────────────┘
 ┌─┴───────────────────────────────────────────────────────┐
 │                     TicketService                        │  ← 고수준 정책(유스케이스)
 │   reserve(userId, ticketId, payInfo)                     │    조립 · 원자성 경계 소유
 └───┬───────────────────┬───────────────────────┬─────────┘
 의존(추상)│               │                       │
       ▼                 ▼                       ▼
 ┌──────────────────┐ ┌──────────────────┐ ┌──────────────────┐
 │ «port» ChargePort│ │«port»            │ │«port»            │
 │  charge(info,amt)│ │ TicketRepository │ │ UserRepository   │   ← 역할(이음매)
 │                  │ │  findById / save │ │  findById        │
 └────────▲─────────┘ └────────▲─────────┘ └────────▲─────────┘
          │ 구현                │ 구현                │ 구현
 ┌────────┴─────────┐ ┌────────┴─────────┐ ┌────────┴─────────┐
 │ CardPaymentAdapter│ │  DB TicketRepo   │ │  DB UserRepo     │  ← 저수준 세부(어댑터)
 │  (OCP: 추가만)   │ │  (테스트: Fake)  │ │  (테스트: Fake)  │
 └──────────────────┘ └──────────────────┘ └──────────────────┘
```

**읽는 법.** 정책과 세부가 가운데 포트에서 만난다. 결제수단 추가는 왼쪽 아래 어댑터 한 장 추가, 테스트는
어댑터 자리에 Fake를 꽂는 일 — 서비스·도메인은 한 줄도 안 열린다. `UserRepository`·`TicketRepository`는
**행위 b·c·g의 정보 전문가라서** 등장했다 — 도출 경로가 (행위→객체)로 뒤집혀 있다.
