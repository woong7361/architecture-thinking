# task2 AGENTS.md — 객체 설계 공용 규칙

> 루트 AGENTS.md를 상속한다. 아래는 객체지향 설계·SOLID 작업 전반에 적용되는 공용 규칙이다.

## 설계 순서 규칙 (책임 주도 설계 · 『오브젝트』)

설계의 **driver는 협력이다.** "협력이 책임을 결정하고, 책임이 객체를 결정한다."
객체·데이터·생성부터 시작하면 절차적 한 덩어리가 된다.

아래 ①~④는 **순차 워터폴이 아니라 사고의 기본 흐름(가설)**이다. 뒤 단계에서 앞이 틀렸음을
발견하면 되돌아간다 — 되돌아오는 것이 정상이다(RDD도 CRC 카드처럼 지우고 다시 쓰는 탐색이다).

1. **협력** — 유스케이스의 메시지 흐름을 먼저 그린다 (누가 누구에게 무엇을 요청하나).
2. **책임** — 각 메시지를 **그 정보를 가장 잘 아는 객체(정보 전문가)**에게 할당한다.
   여기서 객체가 태어난다. 변경 이유 하나 = SRP. 도메인 규칙은 그 상태를 소유한 도메인 객체에 준다.
3. **역할** — 갈아끼울 수 있는 책임은 인터페이스(역할)로 추상화한다 → DIP/ISP 관계, 포트/어댑터.
4. **생성** — 누가 조립·주입하나는 **맨 마지막**에 정의한다. 생성 책임은 사용 책임과 분리한다(DI/Factory).

- 책임을 객체에 할당할 때마다 "왜 이 객체가?"를 정보 전문가로 한 줄 정당화한다.
- private 메서드로 쪼개는 건 책임 분리가 아니다. 책임 분리는 객체 경계가 갈라져야 성립한다.
- **설계도는 확정 스펙이 아니라 구현·테스트가 검증할 가설이다.** 코드 전에 전부 상세히 그리지 않는다(BDUF 경계).
  선행 설계는 헤맴(thrashing)을 줄이는 밑그림이고, 그림의 오류는 구현 단계의 테스트·리팩터링이 잡는다.

## SOLID 적용 규칙

- **SRP** = 변경 이유 하나. "기능 하나"가 아니라 "바뀔 이유 하나".
- **DIP = 의존의 *방향*** (벤더 구체가 아니라 내가 통제하는 추상에 의존).
  **ISP = 추상의 *너비*** (역할 단위로 좁혀라). 둘을 같은 예로 뭉뚱그리지 않는다.
- **OCP** 추상화(다형성/Port)는 **그 축이 실제로 늘어남을 아는 지금에만** 정당하다.
  변경이 오지 않을 곳을 미리 추상화하는 것은 과설계다 — YAGNI를 항상 병기한다.

## AI 행동 규칙

- 설계를 **객체 목록이나 데이터부터** 시작하려 하면 협력(①)으로 되돌린다.
- **생성/DI부터** 고민하도록 유도하지 않는다. 협력·책임이 서기 전엔 생성은 미룬다.
- 책임을 특정 객체에 몰아주려 하면 정보 전문가 기준으로 재배치를 제안한다.
- 추상화(Port·인터페이스)를 제안할 때는 **어떤 변경 축이 그것을 정당화하는지**를 함께 댄다. 축이 없으면 과설계로 표시한다.
- ISP/DIP를 한 예로 설명하지 않는다 — 방향(DIP)과 너비(ISP)를 분리해 보인다.
- 설계도를 코드 전에 **전부 상세화**(BDUF)하도록 유도하지 않는다. 가설 수준의 밑그림에서 멈추고 검증은 구현 단계로 넘긴다.
- 설계도를 **확정 계약**처럼 굳히려 하면 가설로 되돌린다. 뒤 단계에서 앞 단계로 되돌아가는 것을 막지 않는다.
