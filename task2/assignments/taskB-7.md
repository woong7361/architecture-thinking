## 답안

### 한 줄로

**AI에게 "잘 설계해줘"라고 말하는 방식은 소용이 없었다. 세어서 판정할 수 있는 규칙을 줬을 때만 통했다.**
그리고 내가 세운 규칙을 **요약해서** 줬더니, 아예 **안 주는 것보다 나쁜 코드**가 나왔다.

## 1. 무엇을 했나

AI에게 **같은 프로그램을 4번 만들게 했다.** 요구사항도, 테스트도, 주변 코드도 전부 똑같이 주고,
**딱 하나 — 설계를 어떻게 하라고 지시하는 문장만** 바꿨다.

만들게 한 것은 **티켓 예매** 하나다. "회원이 티켓을 고르고 카드로 결제하면 그 티켓이 그 사람 것이 된다.
없는 회원이면 거부, 이미 팔린 티켓이면 거부, 카드가 거절되면 실패."

### 4가지 지시

| | 뭐라고 지시했나 |
| --- | --- |
| **① 아무 지시 없음** | "구현해줘." 끝. |
| **② 요약본** | 내가 B-3·B-4를 **한 장으로 요약해서** 준 것. "책임을 나눠라", "축이 늘어난다는 걸 아는 지금에만 추상화해라" 같은 **말로 된** 규칙. |
| **③ 원칙 전량** | 내가 B-3·B-4·B-5에서 세운 것을 **줄이지 않고 그대로**. SOLID 5원칙 전부 + Anemic/Rich 판정 기준 + **B-5의 숫자로 세는 규칙**(아래). |
| **④ 원칙+설계도** | ③ + B-4에서 내가 직접 그린 **객체 설계도**(어떤 클래스를 만들지 그림으로). |

### ③에만 들어간 "숫자로 세는 규칙"

B-5 [`refactoring-criteria.md`](../task5-history/refactoring-criteria.md)에 내가 세워 둔 것이다.
**인터페이스를 만들려고 할 때마다 이걸 세게 한다.**

```
v = (지금 있는 종류 수) + (요구사항에 적힌 앞으로 생길 종류 수)

v ≥ 2  →  만든다
v < 2  →  만들지 않는다 (나중에 필요해지면 그때 만든다)

"언젠가·혹시·아마"는 세지 않는다.
주석에 "실제 운영에서는 다를 수도"라고 적혀 있는 것도 세지 않는다.
```

②의 "축이 늘어난다는 걸 아는 지금에만"과 **취지는 같다.** 다른 건 **세는가, 아닌가**뿐이다.

### 그다음 똑같은 변경 3가지를 시켰다

4개 버전 각각에 아래 3가지를 따로따로 시켰다(서로 안 섞이게 분리해서).

1. **포인트 결제 추가** — 카드 말고 포인트로도 살 수 있게
2. **1인 1매 제한** — 한 사람이 티켓 한 장만
3. **결제사 교체** — 결제 회사가 바뀌어서 API 모양이 달라짐

인수테스트 4개는 **모두에게 똑같이 주고 수정을 금지**했다. **22번 실행 전부 통과했다.**

## 2. 비교 ① — 아무 지시 없음 vs 원칙 전량

### 결과: 나온 코드가 거의 똑같다

| | ① 아무 지시 없음 | ③ 원칙 전량 |
| --- | --- | --- |
| 파일 수 | 5 | **5** |
| 코드 줄 수 | 132 | **117** |
| 인터페이스 | 0 | **0** |

**AI는 지시를 안 해도 B-3이 시킨 걸 했다.** 티켓의 규칙("이미 팔린 티켓은 다시 못 판다")을
서비스가 아니라 **티켓 객체 안에** 넣었다. 아무도 그러라고 안 했는데.

### 그런데 4번 시켜보니 갈렸다

"1인 1매 제한" 하나만 **똑같은 지시로 4번씩** 시켜봤다. 규칙을 어디에 넣는지 봤다.

| | 규칙을 **회원 객체 안에** 넣음 (좋음) | 규칙을 **서비스에 `if`로** 넣음 (나쁨) |
| --- | --- | --- |
| ① 아무 지시 없음 | **2번** | **2번** |
| ③ 원칙 전량 | **4번** | 0번 |

**아무 지시 없이 시키면 절반의 확률로 나쁘게 나온다.** 잘할 때는 잘한다. 문제는 **언제 잘할지 모른다**는 것.

나쁘게 나온 쪽은 이렇다:

```java
// 규칙이 서비스에 눌어붙었다. 회원한테 물어보고 서비스가 판단한다.
if (tickets.countByUserId(userId) >= 1) {
    throw new TicketLimitExceededException("이미 티켓을 가진 회원입니다: " + userId);
}
```

좋게 나온 쪽은 이렇다:

```java
// 회원이 스스로 판단한다. 몇 장 가졌는지 밖에 알려주지도 않는다.
public Ticket take(Ticket ticket) {
    if (held >= LIMIT) { throw new TicketLimitExceededException(userId); }
    return ticket.reserveFor(userId);
}
```

### 여기가 제일 중요하다: **테스트로는 이 차이가 안 잡힌다**

8번 다 인수테스트 **전부 통과**다. 테스트는 "지금 잘 돌아가나"를 묻지, **"다음에 이 규칙이 바뀔 때
어디를 열어야 하나"를 묻지 않는다.**

그래서 AI가 짠 코드를 "테스트 통과했으니 OK"로 받으면, **절반의 확률로 규칙이 서비스에 눌어붙은 코드를
받고도 모른다.** 그걸 잡으려면 사람이 읽어야 하고, 읽어서 잡으려면 "이게 왜 나쁜지"를 말로 할 수 있어야 한다.

**이게 AI 시대에 객체지향이 기본기인 이유라고 본다.** 코드를 짜는 능력이 아니라 **읽고 판정하는 능력**이
남는다. B-2가 시킨 게 정확히 그거였다.

### 정리

- **평균은 비슷하다.** AI는 지시 없이도 웬만큼 한다.
- **최악이 다르다.** 지시가 없으면 절반은 망하고, 있으면 안 망한다.
- **지시의 값 = "잘 나오게 하는 것"이 아니라 "못 나오는 경우를 없애는 것"이다.**

## 3. 비교 ② — 요약본 vs 원칙 전량

이게 이번 실험에서 **가장 크게 갈린 곳**이고, 나한테 제일 뼈아픈 부분이다.

### 결과: 요약본이 아무 지시 안 한 것보다 나빴다

| | ① 아무 지시 없음 | ② **요약본** | ③ **원칙 전량** |
| --- | --- | --- | --- |
| 코드 줄 수 | 132 | **277** | **117** |
| 인터페이스 | 0 | **3개** | **0개** |
| 포인트 결제 추가 | 고친 파일 1 | 고친 파일 **3** | 고친 파일 **1** |
| 1인 1매 추가 | 고친 파일 1 | 고친 파일 **3** | 고친 파일 **1** |
| 결제사 교체 | 고친 파일 1 | 고친 파일 **2** | 고친 파일 **1** |

**원칙 전량이 모든 항목에서 이겼다.** 코드는 절반 이하(117 vs 277)고, 세 변경 전부 더 적게 고쳤다.

### 왜 갈렸나 — 요약본은 AI가 말을 지어내게 뒀다

요약본의 문장은 이거였다: **"축이 실제로 늘어난다는 걸 아는 지금에만 추상화가 정당하다."**

AI는 이 문장을 통과할 **이유를 지어냈다.** 내가 인프라 코드 주석에 이렇게 써 뒀는데:

> "실제 운영에서는 DB를 읽고 쓰지만, 이 실험에서는 메모리로 동작하는 시뮬레이터다"

AI가 이걸 **"봐, 이미 두 종류잖아(운영 DB / 메모리). 축이 늘어난 거지"** 라고 읽고 인터페이스를 만들었다.
말이 되는 것 같지만 **틀렸다.** "실험에서는 시뮬레이터"는 요구사항이 아니라 그냥 설명이다.

원칙 전량의 규칙은 이 구멍을 **명시적으로 막았다**: *"주석에 '실제 운영에서는 다를 수도'라고 적혀 있는
것도 세지 않는다."* 그래서 AI가 지어낼 수가 없었다.

> **형용사는 AI가 합리화하고, 숫자는 못 한다.**

### 그리고 요약본이 만든 인터페이스는 내 기준으로도 과설계였다

내가 B-5에 **"구현이 1개뿐인 인터페이스 = 과설계(Speculative Generality)"** 라고 적어 뒀다.
그 기준을 요약본이 만든 코드에 그대로 대보면:

| ② 요약본이 만든 인터페이스 | 실제 구현 개수 | 내 기준으로 판정 |
| --- | --- | --- |
| `Members` (회원 조회) | **1개** | ★ 과설계 |
| `Payments` (결제) | **1개** | ★ 과설계 |
| `Points` (포인트) | **1개** | ★ 과설계 |
| `Tickets` (티켓 저장) | **1개** | ★ 과설계 |
| `Payer` (결제 수단) | 2개 | 정당 |

| ③ 원칙 전량이 만든 인터페이스 | 실제 구현 개수 | 판정 |
| --- | --- | --- |
| `PaymentMethod` (결제 수단) | 2개 | 정당 |

**요약본은 5개 중 4개가 과설계. 원칙 전량은 1개 중 1개가 정당.**
내가 요약하면서 빠뜨린 규칙이, 내가 "이건 나쁜 신호"라고 정리해 둔 바로 그것을 스스로 불러왔다.

### 인터페이스를 안 만든 게 옳았다는 증거

"인터페이스를 미리 만들어두면 나중에 바뀔 때 편하다"는 게 상식이다. **이번엔 반대로 나왔다.**

원칙 전량은 처음에 결제 인터페이스를 **안 만들었다** (결제수단이 카드 하나뿐 → `v=1` → 만들지 않음).
그러다 **포인트 결제가 실제로 왔을 때** (`v=2`) 그때 만들었다.

| 포인트 결제에 대응한 비용 | 새 파일 | 고친 파일 |
| --- | --- | --- |
| ③ 원칙 전량 (**그때 만듦**) | 5 | **1** |
| ② 요약본 (**미리 만들어 둠**) | 6 | **3** |

**늦게 만든 쪽이 더 쌌다.** 미리 만든 인터페이스가 막상 온 변경과 **모양이 안 맞았기 때문**이다
(미리 만든 건 `charge(카드정보, 금액)`인데, 포인트는 "누가" 쓰는지가 필요했다).

결제사 교체에서도 마찬가지였다. 인터페이스를 가진 쪽이 **더 비쌌다**(2파일 vs 1파일) — 인터페이스와
어댑터를 같이 고쳐야 하니까.

### 그럼 인터페이스는 아무 값도 없었나?

하나 있었다. 결제사가 바뀌었을 때, 인터페이스를 가진 버전만 **예매 로직이 안 열렸다.**
나머지는 예매 코드 안에 새 결제사 사정이 들어왔다.

그래서 값을 매겨보면:

| | 낸 값 | 받은 값 |
| --- | --- | --- |
| 인터페이스 3개 | 코드 **+145줄** | 결제사 교체 때 예매 로직이 안 열림 |
| 그 "안 열림"의 실제 크기 | | **4줄** |

**145줄 내고 4줄 아꼈다.** 이 규모에선 밑진 장사다.

**단, 이건 이 프로그램이 작아서다.** 예매 로직이 20줄이라 결제사 사정이 새어들어와도 4줄이면 고친다.
500줄짜리에 결제사 호출이 열 군데 있으면 계산이 달라진다. 이 한계는 리포트에 적어 뒀다.

## 4. 설계도까지 준 버전(④)은 어땠나

내가 B-4에서 직접 그린 설계도를 통째로 줬다. 거기엔 `ChargePort` 같은 인터페이스가 **그림으로** 그려져
있다. "이 설계에 따라 구현해줘"라고 했다.

**AI는 설계도를 따르지 않았다.** 그리고 왜 안 따랐는지를 조목조목 댔다:

> `my-design.md`를 한 군데 따르지 않았습니다. 설계도가 포트 3개를 두라고 했지만, 규칙의 게이트를
> 실제로 세어 보니 셋 다 `v=1` → **만들지 않음**이었습니다. 설계도가 근거로 댄 축은 셋 다 무너집니다:
>
> - **"결제수단 추가"·"DB 교체"** — 요구사항에 없습니다. 오히려 환불·취소를 "범위 밖"으로 못박았죠.
> - **"테스트에서 가짜로 갈아끼우는 축"** — **인수테스트를 읽어 반증했습니다.** 테스트는 가짜를 안
>   꽂습니다. 주어진 인프라가 이미 메모리 시뮬레이터라 진짜를 그대로 넘깁니다.
> - 남은 근거는 주석의 "실제 운영에서는 …"인데, **규칙이 정확히 그 문장을 무효로 선언합니다.**

**내가 B-5에서 세운 규칙이, 내가 B-4에서 그린 설계도의 오류를 잡아냈다.**
그것도 하나는 **인수테스트를 직접 읽어서** 반증했다.

이건 B-4에 내가 적어둔 문장이 그대로 실현된 것이다 — *"설계도는 확정 스펙이 아니라 구현·테스트가
검증할 가설이다."* 가설이 틀렸고, 구현이 그걸 잡았다.

**그래서 설계도는 줄 필요가 없다.** 좋은 AI라면 반증하고, 나쁜 AI라면 그냥 베낀다. 둘 다 이득이 없다.
줘야 할 건 **판단 기준**이다.

---

## 5. 결론 — AI에게 어떻게 지시할 것인가

**1. 세어서 판정되는 규칙만 통한다.**
"축이 있으면 추상화해라"(말) → AI가 이유를 지어냈다.
"v = 지금 종류 + 요구사항에 적힌 종류, v≥2면 만든다"(숫자) → 지어낼 수가 없었다.
**같은 취지라도 형용사냐 숫자냐가 결과를 갈랐다.**

**2. 요약하면 안 준 것만 못하다.**
내가 원칙을 한 장으로 줄이면서 LSP를 빼먹고 숫자 규칙을 말로 바꿨더니, **아무 지시 안 한 것보다
2배 큰 코드에 과설계 인터페이스 4개**가 나왔다. 규칙은 줄이면 그 빈자리를 AI가 채운다.

**3. 설계도가 아니라 기준을 준다.**
설계도를 준 버전은 설계도를 반증했다. 기준이 설계 결과물보다 위에 있다.

**4. 한 번 보고 판단하면 틀린다.**
아무 지시 없는 AI는 **절반의 확률로** 잘했다. 한 번 잘한 걸 보고 "얘 이거 잘하네" 하면 틀린다.
실제로 1차 실험에서 내가 그렇게 틀렸다.

**5. 미리 만들지 않는 게 이겼다.**
"나중을 위해 인터페이스를 미리 뚫어두자"는 이번에 **밑졌다.** 미리 만든 건 막상 온 변경과 모양이 안
맞았고, 필요해졌을 때 만든 쪽이 더 쌌다. YAGNI가 숫자로 확인됐다.

## 6. 이 실험이 틀렸던 지점

**AI가 자기가 실험 대상인 걸 알고 있었다.** 1차 때 커밋 메시지에
`최초 구현: 아무 지시 없는 버전`처럼 **실험 정보를 그대로** 써 뒀는데, Claude Code는 **최근 커밋
메시지를 AI에게 자동으로 보여준다.** 그래서 변경을 시킬 때 AI가 자기 조건을 읽을 수 있었다.
실험 기록과 실험 환경을 같은 저장소에 둔 게 원인이다. 요구사항 문서에서는 실험 정보를 지운 버전을 따로
만들어 줬으면서, 정작 같은 정보를 커밋 메시지에 썼다. 폴더 이름·커밋 메시지·브랜치 이름을 전부
중립적으로 바꿔 다시 돌렸다.

**내가 준 규칙이 약했다.** 위에 쓴 대로다. 자산 전량으로 다시 돌리니 **결론이 뒤집혔다.**

**지표를 나중에 바꿨다.** 처음엔 "고친 파일 수"로 예측을 잠갔는데, 결과를 보니 그 숫자가 구조를 못 봐서
"한 파일이 몇 가지 이유로 열리나"로 바꿨다. 사후에 유리한 지표를 골랐다는 비판이 가능하다. 반론은 두 가지 —
바꾼 지표가 B-5에 **미리** 세워둔 것이고, 새 지표로 재도 **원칙 전량 쪽이 유리해지지 않았다.**

**이 프로그램이 너무 작다.** 예매 로직이 20줄이라 인터페이스의 값이 안 드러난다. "미리 만들면 밑진다"는
결론은 **이 규모에 한정**된다.
