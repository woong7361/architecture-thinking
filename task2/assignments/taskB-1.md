## 제출물 1: OOP가 해결하려는 진짜 문제

우리 팀은 Go를 처음 도입했지만, 사내 다른 팀은 이미 Go를 쓰고 있었다. 그래서 그 팀의 가이드를 일부 따랐고, 도메인을 행동 없는 데이터 struct로 두는 anemic 스타일도 그렇게 들어왔다. 여기에 우리 팀은 hexagonal과 DDD를 추가로 얹었다. 그런데 도메인에 행동이 없다 보니, 비즈니스 로직이 갈 곳을 잃고 facade 한 곳으로 전부 몰렸다. 요구사항이 바뀔 때마다 그 facade가 계속 아팠다. 이 경험이 나에게 남긴 질문은 "OOP가 진짜로 풀려던 문제가 뭐길래, 안 지키면 이렇게 아픈가"였다.

OOP의 원래 목적을 찾기 위해 저명한 출처를 찾아보았다. 시뮬라(Nygaard, Dahl)는 현실을 코드로 모델링하려 했고, 앨런 케이는 "The big idea is messaging"이라며 객체들이 메시지로 협력해 시스템을 확장하는 것을 노렸다. '변경'이라는 답의 뿌리는 발명자가 아니라 데이비드 파나스의 1972년 논문("On the Criteria To Be Used in Decomposing Systems into Modules", *Communications of the ACM*, 1972)이다. 그는 "바뀔 가능성이 높은 설계 결정에서 출발해, 각 모듈이 그 결정을 다른 모듈로부터 숨기도록 설계하라"고 했다(정보 은닉). 이 아이디어를 실무자들이 수십 년간 쌓아올리며 목적을 재정의했다 — 샌디 메츠는 『Practical Object-Oriented Design in Ruby』에서 "설계는 완벽을 달성하는 행위라기보다 변경 가능성을 보존하는 기술이다"라고 했고, 로버트 마틴은 『Clean Architecture』에서 SOLID의 목적을 "변경을 견디는(tolerate change) 구조를 만드는 것"으로 정의했다. 조영호는 『오브젝트: 코드로 이해하는 객체지향 설계』에서 "훌륭한 객체지향 설계란 협력하는 객체 사이의 의존성을 적절하게 관리하는 설계다"라고 말하며, 데이터 중심 설계는 너무 이른 시점에 데이터 구조를 확정하게 만들어 변경에 취약하다고 지적한다. 단어는 달라도 결국 한 곳을 가리킨다 — 요구사항이 바뀔 때 그 변경을 한 군데에 머물게 하는 것.

그래서 내 결론은, OOP가 푸는 진짜 문제는 "세상을 어떻게 모델링하나"도 "데이터를 어떻게 묶나"도 아니라 **요구사항 변경이 올 때 그 파급을 한 곳에 국소화하는 것**이다. 이건 발명자의 의도가 아니라 실무가 검증하며 골라낸 목적이다. 돌아보면 내가 도메인에서 행동을 빼 facade로 변경이 번진 것은, 파나스가 말한 '숨길 경계'를 스스로 지운 결과였고, OOP가 막으려던 그 문제를 반대편에서 실증한 셈이다.

## 제출물 2: 역할·책임·협력 + Tell, Don't Ask

객체지향의 본질은 '데이터를 어떻게 묶느냐'가 아니라 '어떤 협력에서 무슨 책임을 지느냐'다. 제출물 1의 결론이 "변경의 파급을 한 곳에 국소화"라는 **목적**이라면, 역할·책임·협력은 그 목적을 이루려 도메인을 나누는 사고방식이다. Rebecca Wirfs-Brock의 책임주도설계는 출발점을 "무슨 데이터를 갖는가"가 아니라 "어떤 협력에서 무슨 책임을 지는가"로 뒤집는다. 협력이 먼저, 그 몫이 책임, 같은 책임을 대신할 자리가 역할이고, 데이터는 맨 마지막에 따라온다. 나는 이 순서를 반대로 했다가 아팠다. 도메인에서 행동을 빼 데이터 자루로 만들자 판단이 전부 facade로 샜다.

이 관점을 지키는 메커니즘이 'Tell, Don't Ask'다. 남의 데이터를 꺼내 내가 판단하지 말고, 그 객체에게 시키라는 뜻이다. task1 환불 코드에서 `RefundService.cancel`은 `refund.succeed()`라고 시킬 뿐 `refund.setStatus(SUCCEEDED)`로 상태를 직접 쓰지 않는다. `Refund.status`는 private이고, 열린 건 `succeed()/fail()/timeOut()` 메시지뿐이다. 만약 상태를 직접 물어 판단했다면 "어떤 상태에서 어디로 갈 수 있는가"라는 전이 규칙이 Service로 새고, Refund는 다시 데이터 자루가 된다. 핵심은 private이라는 문법만으로 캡슐화가 지켜지지 않는다는 것이다. setter를 다 열면 문법은 캡슐화지만 규칙은 노출된다. 데이터로 하는 결정의 책임을 데이터의 주인에게 남기는 것, 그게 묻지 않고 시켜서 캡슐화를 지킨다는 말의 실체다.

## 제출물 3: 캡슐화·다형성이 변경 비용을 낮추는 메커니즘

**캡슐화 — 변경을 객체 경계 안에 가둔다.** 주문(`Order`)이 환불을 반영하는 코드는 이렇다.

```java
// Order.java — 상태 전이 규칙이 이 안에 있다. 밖으로 열린 건 applyRefund 메시지뿐이고,
// status를 바꾸는 setter는 없다.
public void applyRefund(long refundAmount) {
    // ... 검증 ...
    canceledAmount += refundAmount;
    status = (canceledAmount == amount) ? OrderStatus.REFUNDED : OrderStatus.PARTIALLY_REFUNDED;
}
```

"얼마를 환불하면 어떤 상태가 되는가"라는 규칙이 `Order` 안에만 있다. 이 규칙이 바뀌어도 호출자는 여전히 `applyRefund(금액)`만 부르므로 변경이 `Order` 경계를 넘지 않는다. 만약 `order.setStatus(...)`처럼 상태를 밖에서 직접 쓰게 열려 있었다면, 규칙이 바뀔 때마다 그 판단이 모든 호출부로 번졌을 것이다. 캡슐화가 변경 비용을 낮추는 메커니즘은 "무엇이 바뀔지"를 한 객체 안에 숨겨, 변경의 파급 반경을 그 경계로 제한하는 것이다.

**다형성 — 조건 분기 대신 타입 교체로 변경을 흡수한다.** 반대로, taskB-2에서 비평한 `RefundProcessor`는 환불액 계산을 이렇게 한다.

```java
// RefundProcessor.java — 정책이 하나 늘 때마다 이 switch를 직접 고쳐야 한다.
return switch (request.policy()) {
    case PRORATION -> RefundCalculator.calculate(...);
    case MANUAL    -> manualAmount(...);
};
```

정책이 `switch` 분기로 박혀 있어, 새 정책이 생기면 기존 코드를 수정하게 된다. 이를 `RefundPolicy`라는 인터페이스(역할)로 바꾸면, 정책마다 구현 클래스를 하나씩 두고 `RefundProcessor`는 그 역할에만 의존한다. 그러면 정책 추가가 기존 코드 수정 없이 새 클래스 추가로 끝난다. 같은 원리를 내 task1 코드가 이미 쓰고 있다 — `PgClient`를 인터페이스로 두어, PG사를 바꾸거나 테스트용 Fake로 갈아끼워도 호출부 코드는 한 줄도 바뀌지 않는다. 다형성의 메커니즘은 바뀌는 부분을 역할 뒤에 두어, 변경을 '기존 코드 수정'이 아니라 '새 타입 추가'로 전환하는 것이다.
