## 답안 1: SOLID 5원칙 분석 노트

### SRP (Single Responsibility) — B-2 직접 적용

- **개념.** 한 모듈은 **변경 이유가 하나**여야 한다. 곧 한 액터에게만 책임을 진다는 뜻이다. "기능 하나"가 아니라 "바뀔 이유 하나"다.
- **어기면.** 한 모듈이 여러 이유로 바뀌게 된다. 그래서 한 관심사를 고치는 김에 같은 자리에 얽힌 다른 관심사를 건드려 멀쩡하던 기능이 깨지고, 관심사 하나를 검증하려도 나머지 전부를 세워야 해 테스트가 비싸진다.
- **B-2 처방.** `reserveTicket`은 지금 **예약 규칙 판단 + 결제 + 저장 + 조립**을 한 몸에 한다. 변경 이유가 최소 3개다 — 예약 규칙·결제 방식·저장 방식. 이걸 각자 하나의 책임을 지도록 쪼갠다.
  - `Ticket` — **티켓의 예약 상태에 대한 불변식**을 책임진다. "이미 예약된 티켓은 다시 예약될 수 없다"를 스스로 검증하고 상태를 전이한다.
  - 결제 담당 — **외부 결제 API와 통신해 값을 청구하는 것**만 책임진다. 외부 시스템 연동이라는 I/O가 이 객체에 격리된다.
  - `Repository` — **티켓의 영속화**만 책임진다.
  - `TicketService` — 도메인 규칙은 `Ticket`에 맡기고, **예매 유스케이스의 조립과 트랜잭션 경계**를 책임진다.
  - 각 객체가 바뀔 이유가 하나뿐이라, 결제가 바뀌어도 예약 규칙 코드는 열리지 않는다.

### DIP (Dependency Inversion) — B-2 직접 적용

- **개념.** 고수준 정책은 저수준 세부가 아니라 인터페이스 같은 **추상에 의존**하고, 세부가 그 추상을 구현한다. 의존의 방향을 뒤집어 정책을 세부로부터 지킨다.
- **어기면.** 고수준 정책이 저수준 구체에 못박혀, 저수준 구현이 바뀔 때마다 고수준까지 함께 열어야 하고 다른 구현으로 갈아끼우거나 확장하기 어렵다. 정책을 검증할 때도 실제 외부 구현에 발이 묶여 테스트가 힘들다.
- **B-2 처방.** `TicketService`가 구체 외부 API인 `PaymentApi`에 직접 의존하니, 예매 정책이 결제 벤더 세부에 묶였다. 해법은 헥사고날의 얇은 포트다. `charge(...)`만 가진 `PaymentPort` 인터페이스를 두고, 서비스가 남의 외부 구현이 아니라 **내가 통제하는 도메인 추상에** 의존하게 한다. 그러면 앞의 두 문제가 한꺼번에 풀린다. 테스트는 실제 결제 API 대신 내가 만든 가짜 구현으로 갈아끼워 **메모리 안에서 내 값만으로** 검증하고, 결제수단 교체나 벤더 변경은 포트를 구현하는 새 어댑터만 더하면 되어 서비스를 열지 않는다.

### OCP (Open-Closed) — 개념 + 짧은 예

- **개념.** 확장에는 **열려** 있고 수정에는 **닫혀** 있어야 한다. 기능 추가를 '기존 코드 수정'이 아니라 '새 구현 추가'로.
- **어기면.** 기능 하나 늘릴 때마다 잘 돌던 코드를 다시 열어 회귀 위험을 감수하고, 분기가 여러 곳으로 번진다.
- **짧은 예.** '포인트 결제 추가' 시 지금은 `reserveTicket` 몸통에 `if(type==CARD)/else` 분기를 삽입해야 한다. 결제수단을 `PaymentPort` 다형성으로 뽑으면, 포인트 추가는 `PointPayment` 구현 하나를 더하는 일이 되고 예약 로직은 닫힌 채로 남는다. 단, 결제수단이 실제로 늘어날 때만 이 추상화가 정당하다. 아니라면 과설계다.

### LSP (Liskov Substitution) — 개념 + 짧은 예

- **개념.** 상위 타입을 쓰는 코드는 어떤 하위 타입을 끼워 넣어도 똑같이 동작해야 한다. 하위 타입이 상위 타입의 **약속을 그대로 지켜야** 한다는 뜻이다. 더 까다로운 입력을 요구하거나, 결과를 덜 주거나, 예상 못 한 예외를 던지면 그 약속을 깬 것이다. 상속과 구현은 겉모양이 아니라 이 약속을 물려받는 일이다.
- **어기면.** 상위 타입만 믿고 짠 코드가 특정 하위 타입에서만 어긋난다. 컴파일은 멀쩡히 통과하고 잘 끼워지지만 실행 중에 깨져서 찾기도 어렵다. 결국 호출부가 상위 타입을 못 믿고 `instanceof`로 타입을 되물어 분기하게 되면, 다형성도 OCP도 함께 무너진다.
- **짧은 예.** `PaymentPort.charge(paymentInfo, amount)`의 계약이 "`amount`는 0보다 크기만 하면 된다"라고 하자. `CardPayment`는 1,550원이든 얼마든 그대로 결제한다. 그런데 `PointPayment`가 "포인트는 100원 단위로만 쓸 수 있다"며 `amount`가 100의 배수일 때만 동작한다면, 계약을 지켜 1,550원을 넘긴 서비스는 카드 자리에 `PointPayment`를 끼운 순간 실패한다. 시그니처는 같아도 자식(`PointPayment`)이 부모(`PaymentPort`)의 행동 규약보다 더 까다로운 입력을 요구해 규약을 깼기 때문이다. 이렇게 자식이 부모의 행동 규약을 깨면 대체가 불가능해진다.

### ISP (Interface Segregation) — 개념 + 짧은 예

- **개념.** 클라이언트는 **자신이 쓰지 않는 메소드에 의존하지 않아야** 한다. 뚱뚱한 인터페이스를 역할별 좁은 인터페이스로 분리. DIP가 의존의 *방향*(내가 통제하는 추상에 의존)을 다룬다면, ISP는 그 추상의 *너비*(역할 단위로 좁혀라)를 다룬다.
- **어기면.** 안 쓰는 메소드의 변경이 무관한 클라이언트에 파급되고, 구현체는 빈 구현이나 `UnsupportedOperation`으로 필요 없는 메소드까지 억지로 채운다.
- **짧은 예.** `PaymentApi(charge + refund + queryHistory)`를 **서로 다른 클라이언트**가 나눠 쓴다 — 예매는 `charge`, 취소 흐름은 `refund`, 정산/마이페이지 화면은 `queryHistory`. 이걸 한 덩어리로 두면 취소용 `refund` 계약 변경이 예매까지 재컴파일·회귀시키고, 어댑터는 안 쓰는 메소드를 빈 구현으로 채운다. `ChargePort` / `RefundPort` / `HistoryPort`로 잘라 각 클라이언트가 **자기 역할 포트에만** 의존하게 한다. 예매가 의존하는 것은 `charge`만 가진 좁은 `ChargePort`뿐이라, 결제의 나머지 관심사로부터 격리된다.

## 답안 2: My Design (TicketService)

설계도를 결과로 던지지 않고, 규칙대로 **협력 → 책임 → 역할 → 생성** 순서로 밟는다. 핵심은 **driver가 협력이라는 것** — 객체가 아니라 *행위*에서 출발하고, 객체는 그 행위에 정보 전문가를 붙일 때 비로소 태어난다. 이 순서는 워터폴이 아니라 가설이라, 뒤 단계에서 앞이 틀렸음을 발견하면 되돌아온다. 이 설계도는 확정 스펙이 아니라 구현이 검증할 밑그림이다.

### ① 협력 — 예매가 성립하려면 *무슨 일*이 일어나야 하나

객체가 아니라 행위에서 출발한다. **여기엔 객체 이름이 하나도 없다. 행위(책임 후보)만, 수신자는 전부 미정(?).**

```
"예매하라"가 올바르게 끝나려면 —
  a. 예매 요청을 받아들인다                          → ?
  b. 요청자가 실재하는(예매 자격 있는) 사람인지 확인 → ?
  c. 예매 대상을 확보한다                            → ?
  d. 그 대상이 지금 예약 가능한 상태인지 판단한다      → ?   (이미 팔렸으면 거부)
  e. 대가를 청구한다                                → ?
  f. 대상을 '예약됨'으로 전이한다(누구 것인지 기록)   → ?
  g. 그 전이를 영구히 확정한다                       → ?
  h. b~g가 도중 실패해도 모순 상태를 안 남기게 묶는다  → ?   (돈만 받고 예약 안 됨 방지)
```

여기서 **행위 수준의 결정** 하나: `d(가능 판단)`를 `e(청구)` 앞에 둔다 — 못 파는 자리에 돈부터 걷으면 안 되니까(fail-fast). 아직 "누가"는 없다.

### ② 책임 배정 — 정보 전문가로 수신자를 붙인다 → *여기서 객체가 태어난다*

각 행위에 "이 일을 하는 데 필요한 정보를 가진 자"를 묻는다. 답하는 순간 객체가 생긴다.

- **d, f (예약 가능 판단 · 상태 전이).** 필요한 정보 = 대상의 **예약 상태**. 그걸 소유한 자에게 준다 → `**Ticket**` 이라는 도메인 객체가 태어난다. d·f가 같은 정보(상태)에 붙으니 한 객체로 모인다(높은 응집).
- **e (청구).** 필요한 정보 = 결제 수단·외부 결제 시스템과 통신하는 법 → **결제 담당**이 태어난다.
- **c, g (확보 · 영속화).** 필요한 정보 = 대상이 어디 저장돼 있는지 → `**TicketRepository**`.
- **b (요청자 실재 확인).** 필요한 정보 = 유저가 어디 저장돼 있는지 → `**UserRepository**`.
  - ⟳ *되돌아오기(정상):* "이거 예매의 책임 맞아? 인증 앞단 일 아냐?" 잠깐 ①로 되돌아가 묻는다. → **존치.** "실재하는 유저에게만 예매"는 예매의 **업무 전제조건**이고, 이를 저장소 제약(FK)에 떠넘기면 정책이 저장 세부로 새고 `UserNotFound`라는 도메인 의미가 저수준 제약 위반 예외로 뭉개진다. 그래서 b는 이 협력이 소유한다.
- **a, h (요청 수신 · 원자성 경계 · 조립).** 필요한 정보 = 협력 전체의 순서와 원자성. 개별 도메인 객체는 그걸 모른다 → 협력을 **조정하는 자**가 태어난다: `**TicketService**`.
  - `h`의 근거: `e(청구)`는 외부라 되돌릴 수 없다. "청구 성공 + 확정 실패"의 모순을 막는 **트랜잭션·보상 경계**는 순서를 아는 조정자만 질 수 있다. `Ticket`은 순수 불변식만, 경계는 서비스가 진다 — 그래야 도메인이 순수하게 남아 Mock 0개로 검증된다.

**책임표 (변경 이유 하나 = SRP):**


| 행위                   | 태어난 객체                    | 정보 전문가 근거                      | 변경 축     |
| -------------------- | ------------------------- | ------------------------------ | -------- |
| d·f 예약 판단·전이         | `**Ticket**` (도메인)        | 예약 상태(`reserved`,`userId`)를 소유 | 예약 규칙    |
| e 청구                 | **결제 담당** (ChargePort 구현) | 외부 결제 통신을 앎                    | 결제 방식    |
| c·g 확보·영속화           | `**TicketRepository**`    | 저장 매체를 앎                       | 저장 방식    |
| b 유저 실재 확인           | `**UserRepository**`      | 유저 저장소를 앎                      | 저장 방식    |
| a·h 조립·**원자성/보상 경계** | `**TicketService**`       | 협력 순서·원자성을 앎                   | 유스케이스 흐름 |


**이제 수신자가 붙은 협력:**

```
Client → TicketService.reserve(userId, ticketId, payInfo)   ┐ 원자성/보상 경계
  ├─ b  userRepo.findById(userId)          없으면 UserNotFound     │  = TicketService 소유
  ├─ c  ticketRepo.findById(ticketId)      대상 확보               │
  ├─ d·f ticket.reserve(userId)            가능 판단+전이(거부 가능) │
  ├─ e  chargePort.charge(payInfo, price)  청구                    │
  └─ g  ticketRepo.save(ticket)            확정(실패 시 e 보상)      ┘
```

### ③ 역할 — 갈아끼울 축만 인터페이스로

②에서 태어난 객체 중 **구현이 교체되는 축**만 포트로 뽑는다. 축 없으면 안 뽑는다(과설계 경계).

- **결제 담당 → `ChargePort`.** 결제수단이 늘어나는 축(포인트 추가) + 벤더 교체 + 테스트 격리. **방향(DIP):** 벤더 API가 아니라 내가 통제하는 `ChargePort`에 의존. **너비(ISP):** `refund`·`queryHistory` 없이 `charge`만. **OCP:** 포인트 추가 = 어댑터 한 장.
- **저장 → `TicketRepository` / `UserRepository`** (포트): DB 교체 + 테스트 대체 축(DIP·테스트 격리).
- `Ticket`**은 역할화하지 않는다** — 예약 규칙이 다형으로 갈리는 축이 아직 없다

### ④ 생성 — 맨 마지막, 최소만

`TicketService`는 세 포트를 **생성자 주입**으로 받는다. 실제 구현체를 만들어 꽂는 건 바깥의 몫 — 사용 책임과 생성 책임을 분리한다. 구현체 이름·컨테이너 선택은 지금 정하지 않는다

### 객체 설계도 (ASCII)

**화살표 = 의존 방향.** 정책(서비스)과 세부(어댑터)가 서로를 모른 채 가운데 포트에서 만난다(DIP).

```
                ┌──────────────── 도메인 ────────────────┐
      d·f 전이   │  Ticket  「예약 불변식의 주인」          │  ✔
   ┌────────────►│  - reserved / userId                    │
   │             │  + reserve(userId) … 이미 예약이면 거부 │
```
