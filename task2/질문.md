# 열린 질문 — E2E·인수 `.feature`의 관찰 경계와 단위 테스트의 역할

## 맥락

리팩터링 과정에서 Gherkin `.feature`의 문장은 유지됐지만, 이를 실행 코드에 연결하는 step 정의가 내부 setter와 포트 타입에 의존해 컴파일부터 깨졌다. `.feature` 자체를 도메인 언어로 작성하는 것만으로는 충분하지 않았다. 실행을 담당하는 glue와 fake가 구현 세부를 알면 리팩터링 안전망 전체가 구조 변경에 영향을 받는다.

먼저 `.feature`와 E2E를 같은 것으로 볼 수는 없다. `.feature`는 행위를 서술한 명세다. 이 문서에서는 실제 API, 데이터베이스, 외부 시스템까지 연결하는 실행을 E2E라는 작업 용어로 사용한다. 같은 feature를 Inbound Port와 fake outbound에만 연결하면 애플리케이션 경계의 인수테스트가 된다. 따라서 이 질문은 명세가 어떤 내용을 담을지와 그 명세를 어느 실행 범위에서 검증할지를 나눠 다뤄야 한다.

현재 `generate-test`는 도메인 언어의 Gherkin 계약과 단위 테스트를 분리 생성한다. 실험판 `generate-test-v1`은 한 단계 더 나아가 다음 구조를 선택했다.

- boundary feature: `When`은 Inbound Port 하나와 1:1로 대응한다.
- `Then`은 반환값, 외부에서 관찰 가능한 도메인 상태, outbound 효과의 누적 또는 최종 결과만 표현한다.
- 계산, 상태 전이, 불변식의 세부는 별도의 도메인 규칙 예시표로 분리한다.
- 호출 순서, 호출 횟수, 내부 예외 타입, 기존 구현의 우연한 동작은 사후 특성화 테스트의 책임으로 미룬다.

이 방향은 설계로는 정해졌지만 아직 실증이 끝나지 않았다. 특히 feature의 고도를 높였을 때 어떤 결함을 놓치는지, feature를 실행 가능하게 만드는 step과 fake가 다시 구현에 결합하지 않는지를 확인해야 한다.

## 문제 재정의

목표는 `.feature`의 종속을 없애는 것이 아니다. 종속이 전혀 없으면 아무 계약도 검증할 수 없다. 목표는 종속 대상을 내부 구조가 아니라 비즈니스 경계의 행동으로 제한하는 것이다.

서로 다른 두 축도 구분해야 한다.

- 명세의 고도: feature 문장이 비즈니스 경계만 표현하는가, 내부 메커니즘까지 표현하는가
- 실행 범위: 실제 외부 시스템까지 통과하는 E2E인가, 애플리케이션 포트와 fake를 사용하는 경계 인수테스트인가

feature 문장이 경계 언어로 깨끗해도 step이 내부 구조에 결합할 수 있다. 반대로 feature와 step이 모두 경계에만 결합해도 실제 어댑터를 통과하지 않으면 배선과 직렬화 결함은 잡지 못할 수 있다.

구분해야 할 대상은 다음과 같다.

- 허용할 종속: 유스케이스 입력, 반환 결과, 외부에서 조회 가능한 도메인 상태, 외부 협력에 반영된 최종 또는 누적 효과
- 피할 종속: 클래스와 메서드 이름, 내부 객체 상태, 호출 여부·순서·횟수, mock 검증, 언어 기본 예외, 테스트만을 위한 getter

다만 feature에서 세부를 제거하고 나머지를 모두 단위 테스트로 보내면 다른 문제가 생길 수 있다. 개별 규칙의 계산 오류는 단위 테스트가 잡을 수 있지만, 입력 변환, 유스케이스 조합, 트랜잭션 경계, 보상, 재시도, 중복 효과처럼 여러 경계를 연결할 때 생기는 오류는 단위 테스트만으로 놓칠 가능성이 있다.

## 검토할 접근

### 접근 A — 경계 전용 feature + 나머지는 단위 테스트

`.feature`에는 유스케이스 입력과 반환·외부 관찰 결과만 남긴다. 계산과 불변식은 단위 테스트로 검증한다.

- 장점: 내부 리팩터링에 가장 강하고 feature가 비즈니스 계약으로 읽힌다.
- 위험: 경계 사이의 조합, 배선, 트랜잭션, 재시도에서 발생하는 결함을 누락할 수 있다.

### 접근 B — feature에 세부 상태와 상호작용도 포함

저장 상태, 협력자 호출, 예외 타입과 순서까지 feature 또는 step에서 검증한다.

- 장점: 현재 구현의 동작을 세밀하게 보존하고 회귀 탐지 범위가 넓다.
- 위험: 정당한 리팩터링에도 테스트가 깨진다. 정책 계약과 구현 특성화가 한 파일에 섞인다.

### 접근 C — 세 계층으로 역할 분리

1. boundary feature는 유스케이스 경계의 최종 계약을 검증한다.
2. 규칙 예시표와 단위 테스트는 계산·상태 전이·불변식을 검증한다.
3. 어댑터 계약 테스트, 소수의 실제 E2E, 사후 특성화 테스트는 배선·변환·호환성과 의도적으로 보존할 구현 동작을 검증한다.

- 장점: 리팩터링 내성과 결함 탐지 범위를 함께 가져갈 수 있다.
- 위험: 테스트 종류와 책임 경계를 관리해야 하며 같은 사실을 여러 계층에서 중복 검증할 수 있다.

현재로서는 접근 C가 유력한 가설이지만, 실제 결함 주입과 리팩터링 실험으로 확인하기 전에는 결론으로 고정할 수 없다.

## 다듬어진 핵심 질문

> E2E 또는 애플리케이션 경계 인수테스트에서 사용하는 `.feature`는 구현 세부에 종속되지 않도록 `Given`에는 경계에서 의미 있는 입력 조건, `When`에는 하나의 Inbound Port, `Then`에는 반환값·외부에서 관찰 가능한 도메인 상태·outbound port에 반영된 최종 또는 누적 효과만 두는 것이 적절한가?
>
> 계산, 상태 전이, 불변식 같은 세부 규칙을 규칙 예시표와 단위 테스트로 내리면 feature의 리팩터링 내성은 높아진다. 그러나 입력 변환, 배선, 트랜잭션, 보상, 재시도, 중복 효과처럼 경계 사이에서만 드러나는 결함이 feature와 단위 테스트 사이에서 누락될 수 있다. 그렇다면 어떤 결함은 반드시 boundary feature에 남겨야 하고, 어떤 결함은 단위·어댑터 계약·사후 특성화 테스트로 내려야 하는가?
>
> 같은 feature를 포트와 fake에 연결하는 경계 인수테스트와 실제 어댑터까지 연결하는 E2E 중 어디까지 자동 생성·실행해야 하는가? 또한 `generate-test` 계열 스킬은 명세의 고도와 실행 범위를 어떤 생성 규칙과 rubric으로 각각 강제하고, 생성된 테스트가 세부에 결합되지 않으면서도 필요한 결함을 놓치지 않는다는 것을 어떤 실험으로 검증해야 하는가?

## 하위 질문

1. 외부에서 관찰 가능한 도메인 상태와 테스트를 위해 새로 노출한 내부 상태를 가르는 기준은 무엇인가?
2. outbound fake의 결과를 보는 테스트는 경계 인수테스트다. 실제 outbound 시스템까지 확인해야 하는 시나리오는 어떤 기준으로 고르는가?
3. outbound port를 검증할 때 포트 이름과 호출 여부가 아니라 최종 메시지나 누적 효과만 본다면 충분한가?
4. 성공·거절 결과뿐 아니라 부분 실패, 재시도, 동시 요청, 보상 실패도 feature의 경계 행동으로 봐야 하는가?
5. feature 텍스트는 안정적이지만 step 정의만 깨지는 경우도 리팩터링 내성 실패로 판정해야 하는가?
6. 정책 계약을 만드는 feature와 현재 구현의 우연한 동작을 보존하는 특성화 feature를 다른 job으로 분리해야 하는가?
7. 단위 테스트로 내린 규칙이 유스케이스 조합에서 올바르게 연결됐다는 것은 어느 계층에서 확인해야 하는가?

## 확인 실험

같은 정책을 세 접근으로 생성하고 다음 변화를 각각 주입해 비교한다.

- 행위는 유지한 채 내부 객체와 메서드를 재구성한다.
- 포트 구현과 타입 이름을 바꾸되 경계 계약은 유지한다.
- 도메인 계산 규칙을 잘못 구현한다.
- 입력을 잘못 변환하거나 결과를 잘못 매핑한다.
- outbound 효과를 누락하거나 중복 반영한다.
- 부분 실패 뒤 보상, 재시도, 동시 요청 처리를 잘못 구현한다.

각 변화에서 다음을 측정한다.

- 비즈니스 행위가 같은 리팩터링에서 `.feature`가 그대로 유지되는가?
- step과 fake의 변경이 테스트 어댑터 한곳에 국소화되는가?
- 실제 행위 결함은 feature, 단위, 어댑터 계약 중 책임진 계층에서 실패하는가?
- 어느 계층에서도 잡히지 않는 결함이 있는가?
- 같은 사실을 여러 계층이 중복 검증해 유지 비용이 커지지 않는가?

이 실험을 통과해야 “feature는 경계에만 종속되고 나머지는 단위 테스트로 내린다”는 고정된 설계 결정을 `generate-test` 계열 스킬에서 실증된 운영 규칙으로 사용할 수 있다.
