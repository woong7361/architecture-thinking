- 어떻게 했는가: `thinking-review-gate` Level 1 기준으로 사실과 승인 조건이 뒤섞이지 않는지 검토했다. `apply_patch`로 대상 문단만 수정했고 `git diff`와 `git diff --check`, 키워드 검색으로 변경 범위와 문구를 확인했다.
- 배운 점 / 다음에 볼 것: 계약 테스트의 자동화 시점은 AI가 case를 발견한 때가 아니라, 사람이 그 case의 근거를 계약 기준본으로 승인한 때다. report는 오답을 실패시키는 심판이 아니라, 현재 심판이 다루지 못하는 범위를 사람에게 올리는 장치다.

### [21:22] C-6 report를 feature 계약 게이트의 후보 입력으로 재정의
- 맥락: 사용자가 문단을 `다음 개선`으로 확정하는 표현이 아니라 산출물에서 제안하는 형태로 바꾸고, feature 계약을 따로 생성·판정하는 게이트와 역할을 나누라고 정정했다.
- 고민한 것: report를 구현 게이트의 추가 심판으로 볼지, feature 계약 게이트로 보낼 후보 발견 산출물로 볼지 구분했다. 기존 `notes`와 새 report가 중복되지 않게 자유 서술을 근거·가정·영향·확인 방법으로 구조화하는 제안으로 정리했다.
- 트레이드오프: 구현 AI가 테스트를 바로 추가하면 빠르게 커버리지를 늘릴 수 있지만 생성자가 판정 기준까지 만든다. report만 남기면 즉시 실패로 바꾸지는 못하지만, feature 계약 게이트의 소유권을 유지하고 미검증 위험도 추적할 수 있다.
- 결론: C-6의 문단을 구현 AI가 자동 게이트 밖의 위험을 구조화된 report로 제출하는 방식을 `제안해 볼 수 있다`로 바꾸었다. report는 feature 계약 게이트의 후보 입력이며, 사람이 승인한 case만 다음 실행의 계약·input·테스트에 반영한다.
- 어떻게 했는가: `thinking-review-gate` Level 1으로 `taskC-6.md`, skeleton-agent의 사람·Implement·Gate 역할 분리, `notes`의 외부 계약 추측 기록 규칙을 확인했다. `apply_patch`로 대상 문단만 교체한 뒤 `git diff`, `git diff --check`, 키워드 검색으로 검증했다.
- 배운 점 / 다음에 볼 것: 자동 게이트 파이프라인에서 발견과 판정을 분리할 수 있다. 구현 AI는 심판이 놓친 범위를 발견해 다음 계약 생성 단계에 전달하고, feature 계약 게이트가 이를 정식 판정 기준으로 승격할지 결정해야 생성자가 심판을 겸하는 문제를 피할 수 있다.
