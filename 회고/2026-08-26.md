- 어떻게 했는가: SeloWhisper와 CrisperWhisper 모델 카드, Transformers 장문 ASR 문서, faster-whisper 공식 이슈, VoxLab과 발표 코치 저장소를 웹에서 확인했다. Level 2 검토를 통과한 뒤 현재 PC가 RTX 3060 12GB와 RAM 약 64GB임을 확인해 0.8B 모델 실험의 하드웨어 제약을 점검했다.
- 배운 점 / 다음에 볼 것: 가장 간단하다는 판단은 범용 기능 수가 아니라 현재 요구를 만족하는 최소 구성으로 해야 한다. 전용 모델도 검증을 없애지는 못하지만, 한 편의 사람 라벨을 고정 캘리브레이션 샘플로 만들면 반복 검증 비용을 줄일 수 있다. 구현할 때는 SeloWhisper의 장문 chunk 경계와 특수 토큰 보존부터 작은 샘플로 확인한다.

### [15:24] 필러 문맥 판정과 발표 피드백을 두 AI reviewer로 재분리
- 맥락: 앞선 안에서는 Python이 필러 문자열을 판정하도록 두었지만, 사용자가 `그`처럼 문맥에 따라 의미어와 머뭇거림이 달라지는 표현은 AI가 구분해야 한다고 지적했다. 전사 뒤에는 전달 방식과 논리를 별도 관점에서 동시에 검토하기를 원했다.
- 고민한 것: 모든 판정과 집계를 AI에 맡길지, 정규식 판정을 유지할지, AI가 문맥을 분류하고 코드는 schema 검증과 집계만 할지 비교했다. 하나의 코치 agent와 전달·논리 reviewer 두 개를 두는 방식도 함께 비교했다.
- 트레이드오프: 모든 작업을 AI에 맡기면 단순하지만 빈도 수치가 누락되거나 재실행마다 달라질 수 있다. 정규식은 재현 가능하지만 의미가 있는 표현을 필러로 오탐한다. AI 분류와 결정적 집계를 결합하면 구성은 조금 늘어도 의미 판단의 유연성과 산출물의 추적성을 함께 얻는다. reviewer 두 개는 토큰 비용이 늘지만 서로 독립적인 전달 관점과 시니어 논리 관점을 보존한다.
- 결론: delivery reviewer가 필러를 `filler`, `lexical`, `uncertain`으로 문맥 분류하고 속도 해석, transcript 기반 어투, 발표 구조를 평가한다. senior logic reviewer는 주장과 근거, 예시 적합성, 논리 도약과 예상 질문만 평가한다. 두 reviewer는 같은 고정 입력을 보고 병렬 실행하며, Python은 속도 계산, schema 검증, 분류 결과 집계만 담당한다.
- 어떻게 했는가: role은 Markdown, rubric은 YAML, 실행 입력과 출력 계약은 JSON과 JSON Schema로 분리하는 파일 구조를 설계했다. custom agent TOML에는 전체 기준을 복제하지 않고 자원 경로와 책임 경계만 두도록 했다. thinking-review-gate Level 2 검토를 실행해 4.25점으로 통과했고, timestamp 지원은 구현 전 확인 조건으로 두며 AI 분류의 비결정성에 대비해 원문·annotation·rubric 버전을 함께 저장하도록 보완했다.
- 배운 점 / 다음에 볼 것: 재현성을 얻는다는 이유로 의미 판정까지 코드에 맡길 필요는 없다. AI가 애매한 관찰을 구조화해 남기고 코드는 그 결과를 검증·집계하면 책임을 더 정확히 나눌 수 있다. 구현 전에는 전사 응답의 timestamp granularity와 custom agent가 외부 role·rubric 파일을 읽는 실제 연결 방식을 작은 smoke test로 확인한다.

### [15:58] 스피치 리허설 skill의 prompt 권위를 role Markdown으로 고정
- 맥락: 사용자가 앞선 설계를 승인하면서 진단 도구라는 성격을 재확인했고, runner나 실행 코드에 prompt를 남기지 말고 변경 책임을 한곳에 두라고 요청했다.
- 고민한 것: Python runner가 agent prompt를 조립하는 기존 하네스 형태를 따를지, custom agent TOML에 역할 전체를 넣을지, role Markdown을 유일한 본문으로 두고 skill이 병렬 실행만 지휘할지 비교했다.
- 트레이드오프: runner가 prompt를 조립하면 실행은 명시적이지만 역할 기준이 코드로 새기 쉽다. TOML에 역할 전체를 넣으면 custom agent는 독립적이지만 사람이 검토할 role 문서와 중복된다. role Markdown 한곳에 본문을 두면 로더 지침이 하나 더 필요하지만 변경 권위가 분명하고 rubric, schema, mechanics의 실패 원인을 분리할 수 있다.
- 결론: 별도 runner를 만들지 않았다. 두 role prompt는 `references/roles/`에만 두고, rubric은 `references/rubrics/`, 출력 계약은 `schemas/`, 실행 mechanics는 `scripts/`가 각각 소유한다. custom agent TOML에는 필수 `developer_instructions`로 권위 role 파일을 읽으라는 최소 loader만 남겼다.
- 어떻게 했는가: `skill-creator` initializer로 `.codex/skills/speech-rehearsal/`을 만들고 두 project custom agent를 `.codex/agents/`에 추가했다. 전사, immutable review context, AI label 집계 스크립트와 JSON Schema, 단위 테스트를 작성했다. 테스트 5개, TOML parse, JSON 문법, prompt 중복 검색, trailing whitespace, multipart 구성을 확인했다. thinking-review-gate Level 2 최종 attempt는 4.7점으로 통과했다.
- 배운 점 / 다음에 볼 것: 단일 책임은 모든 설정을 한 파일에 몰아넣는 것이 아니라 같은 판단 본문을 한 곳에서만 소유하게 하는 것이다. orchestration, role, rubric, schema, mechanics는 서로 다른 변경 이유가 있으므로 분리하되 본문을 복제하지 않아야 한다. 다음에는 D-4 녹화나 transcript로 실제 병렬 reviewer를 실행하고, 필러 누락과 실제 API 응답 형식을 end-to-end로 확인한다.
