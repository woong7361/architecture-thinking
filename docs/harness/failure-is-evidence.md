# 실패를 산출물로 남긴다

## 무엇을 막는가

실패가 재시도 과정에서 사라져, 같은 실패가 반복되는데도 반복이라는 사실을 아무도 세지 못하는 것을 막는다.

## 원리

실패를 산출물로 남긴다. 거절과 오류를 구분하고, 각 실패에 분류와 규칙 이름을 붙여 기계가 집계할 수 있는 모양으로 쓴다.

성공한 검사의 세부는 매번 파일로 남기지 않는다. 실패한 검사만 남긴다.

모델 응답 원문은 파싱 전에 저장한다. 성공해도 저장한다.

최종 실패는 통과 산출물로 대체하지 않고 별도 파일로 고정한다. 어느 반복에서 무엇에 막혔는지, 분류별로 몇 건이었는지, 어떤 산출물이 마지막이었는지를 적는다.

## 메커니즘

거절과 오류는 조치가 다르다. 거절은 재작성으로 회복되지만 오류는 환경이나 코드를 고쳐야 하므로, 둘을 같은 실패로 적으면 집계가 섞여서 품질이 낮은 것인지 파이프라인이 고장난 것인지 구분할 수 없다.

분류와 규칙 이름을 붙이는 이유는 사람이 읽기 위해서가 아니다. 여러 기록을 모아 같은 규칙이 반복해서 깨지는지 세려면 실패가 같은 모양이어야 하는데, 자유 문장으로 적힌 실패는 세어지지 않으므로 [[slow-loop]]의 입력이 되지 못한다.

원문을 성공에도 저장하는 것은 실패 경로 자체에 버그가 있을 때를 대비하는 장치다. 실패했을 때만 저장하면 그 경로가 깨진 순간 아무것도 남지 않고, 원문이 없으면 응답이 잘려서 온 것인지 파서가 틀린 것인지도 가를 수 없다. 오래 돌린 실행이 앞부분만 남기고 끝나면 그 실행 전체를 버린다.

## 예

구조 위반, 계약 위반, 품질 거절, 역할 침범, 단계 실행 실패, 실행 환경 실패, 반복 상한 초과를 서로 다른 분류로 둔다. 모든 분류가 오류를 뜻하지는 않는다. 품질 거절은 파이프라인이 정상 동작한 결과이고, 조치는 재작성이다.

## 경계

- 성공한 검사의 세부를 매번 남기면 기록 폴더가 노이즈로 차서 실패를 찾지 못한다. 성공은 다음 단계가 실행됐다는 사실로 확인한다.
- 최종 실패 파일에 마지막 오류만 담지 않는다. 그러면 원인이 아니라 증상만 남는다.
- 실패를 남기는 것은 실패를 허용하는 것과 다르다. 반복 상한은 따로 둔다. [[iteration-cap]]
- 통과한 기록만 모아 신호를 내면, 통과 기록에 절대 나타나지 않는 실패가 사각지대가 된다. 하한 미달이 그렇다.

## 검증

- [ ] 실패 산출물의 분류값이 정해진 집합 안에 있는가. 집합 밖 값이나 빈 값은 집계를 깨뜨린다.
- [ ] 실패한 기록의 수와 실패 파일의 수가 맞는가. 차이는 조용히 사라진 실패다.
- [ ] 각 단계 호출마다 응답 원문이 남아 있는가. 성공 호출에도 있어야 한다.
- [ ] 최종 실패 파일에 다음 조치가 필드로 적혀 있는가. 분류와 규칙 이름만 있으면 읽는 쪽이 매번 조치를 새로 추론한다.
